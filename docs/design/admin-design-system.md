⇒ **以下是把 §1 每一個與脈絡有關的顏色重算一次的結果**(含**沒有人指名**的三處):

| 對象 | 疊/混算後 | 對比 | 判定 |
|---|---|---:|---|
| 主文字 `#111827` on `#f7f8fa` | — | 16.69 | ✅ |
| 強調 `#0066b1` on `#f7f8fa` / `#ffffff` | — | 5.59 / 5.94 | ✅ |
| **危險 `#e4002b`** on `#ffffff` / `#f7f8fa` | — | **4.85 / 4.56** | ✅ **但只差 0.06 過關** |
| **`accent-hover`** = mix(accent, black 8%) | **`#005b9e`** | 白字 **7.02** | ✅ |
| **`accent-active`** = mix(accent, black 14%) | **`#005290`** | 白字 **8.05** | ✅ |

**算法**:WCAG 相對亮度公式;`color-mix(in oklab, C, black P%)` 自行實作 sRGB→Oklab→縮放→sRGB,
**正向對照 = mix 0% 精確回 `#0066b1`**(不精確就代表實作壞了)。**與 E 窗獨立算的逐字相同。**

🔴 **兩件算完才看得到的**:
1. **hover / active 的【狀態變化極弱】**:`accent → hover` 只差 **1.18**、`hover → active` 差 **1.15**。
   ⚠️ **我不宣稱這違反 WCAG**(1.4.11 的「所需」有解釋空間)——
   **這是可用性題,標成【待裁】:Sean 或設計決定要不要加大級距。**
2. 🔴 **卡片與底的分界只有 1.06** —— 而這套語言**沒有陰影**(`--elev-flat: none`)
   ⇒ **卡片邊界幾乎完全靠那條 `#d7dee8`(對比 1.27)的邊框撐著。**
   **這是「無陰影 + hairline」語言的必然結果,不是錯** —— **但下一個人要知道:動 `--border` 的值,動到的是「卡片還看不看得出來」。**

### 🔴 三處【改】的理由與量法(WCAG AA 正文 4.5:1)
```
次要文字  #64748b on #f7f8fa  4.48 → #64738a 4.53   色相 215° 不變
成功      #16a34a on #ffffff  3.30 → #12883e 4.55   色相 142° 不變
警告      #f59e0b on #ffffff  2.15 → #a56a07 4.50   色相  38° 不變
```
**改法紀律:保色相、只調明度到剛好過標。** 依據 = Sean 逐字「**有不適合我們或者我們需要再依照類似風格建置上去**」。
⚠️ **警告色動最多**(明度 0.502→0.338)—— 橘色在白底上先天難達標,**這是標準的物理限制,不是 OD 選錯色。**

### 🔴🔴 三階邊框 —— **【長】,BMW M 沒有這個分法**

**依據的原則**(稿裡的):**無陰影、以 hairline 分隔**(`--elev-flat: none` `:57`;OD 自己有兩階 `--border` `:19` / `--border-soft`)。

| 角色 | 用在哪 | 對比要求 | 值 |
|---|---|---|---|
| `--border-interactive` | **輸入框、可聚焦元件的邊界** | 🔴 **必須 ≥3.0**(WCAG 1.4.11) | 待定 |
| `--border` | 卡片、區塊邊界 | 視覺用,無硬要求 | `#d7dee8` **【抄】** `:19` |
| `--border-soft` | **表格 hairline、裝飾性分隔** | **無**(裝飾性不受 1.4.11 管) | `#edf1f6` **【抄】** |

**🔴 判別句(下一個人照這個分,不要憑感覺)**:
> **「使用者需不需要靠這條線才知道【這裡是一個控制項】,或【它現在是什麼狀態】?」**
> **任一為是 ⇒ `border-interactive`(必須達 3.0)。兩者皆否 ⇒ 另外兩階。**

⚠️ **判別句的第二半是修訂補上的,而它原本漏掉** —— 第一版只問「可不可以點」,
**而 1.4.11 的原文是「識別 UI 元件【與狀態】所需」**(就寫在下面五行)。
🔴 **漏掉「狀態」會判錯這些**:**錯誤態的紅框 / checkbox 已勾未勾 / 單選的選中框 / 停用態** ——
**它們都不是「可不可以點」的問題,而它們正是 1.4.11 管的。**
**⇒ 自己引的標準與自己寫的判別句相隔五行卻對不上,是這份檔第一次修訂的 must-fix 之一。**

⚠️ **為什麼不把所有邊框拉到 3.0**:實算 `#d7dee8` 要達 3.0 得變成 **`#7a91b3`**(對比 3.03)——
**那是中灰藍的明顯線條,不是 hairline。**
🔴 **WCAG 1.4.11 管的是「識別 UI 元件與狀態所需」的視覺資訊,不管裝飾性分隔線。**
**硬拉會同時毀掉設計語言、又誤讀標準** —— 做出來的東西已經不是「達標的 BMW M」,是別的東西。

### 🔴🔴 focus 環:**OD 那個值不合格,不要照抄**(`accessibility-review` 跑出來的)

```
--focus-ring: 0 0 0 4px rgba(0, 102, 177, 0.24)     ← OD :60

24% alpha 疊在底色上的【實際顏色】與對比：
  疊在 #f7f8fa ⇒ #bcd5e8   對比 1.43     需要 3.0   🔴 不過
  疊在 #ffffff ⇒ #c2daec   對比 1.44     需要 3.0   🔴 不過

  #0066b1 on #f7f8fa ⇒ 5.59  ✅        #0066b1 on #ffffff ⇒ 5.94  ✅
```
🔴 **WCAG 2.4.7(可見焦點)+ 1.4.11(非文字對比 3.0)** ⇒ **24% 的藍在淺底上幾乎看不見。**
⚠️ **這條特別值得記**:我原本把它標成 **【抄】直接照搬** ——
**因為它「看起來就是個 focus 環」,而我沒有把 alpha 疊算回底色。**
**半透明色的對比不能看它宣告的顏色,要看它疊在底上的【實際顏色】。**

**⇒ 改法(保持 BMW M 的視覺意圖:細環、不搶眼)**:**降低透明度或改用不透明的 accent 描邊**,
**值待定,但硬要求是疊算後 ≥3.0。** 依據 = 契約 `requiredStates` 含 `focus` + WCAG 2.4.7。

| wide | 1920 | 1726 | 1412 | 0 | ✅ |
| mobile ×3 / foldable / tablet-portrait | 360–820 | — | — | — | ⚠️ **未量** |

(公式 `容器 = 視窗 − 194`,五筆實測驗證:1024/1280/1440/1600/1920。)
🔴 **`laptop 1366` 與 `desktop 1440` 是員工最可能用的兩台機器,而它們正是過不了的兩格。**
**根因與 `#519` 相同:14 欄固定寬相加 1412,而 `@container` 在 900 就把欄全放出來。**
⚠️ **OD 的 `--container-max: 1220px`** `:64` **比我們的表格還窄** ⇒ **不要照抄那個上限,先解決欄寬。**

### 6.5.2 篩選列
**現況有十個控制項,而它們用了【四種】互動語言**:
```
chip（單選）          全部 / 待收款,待訂貨 / 未到貨
select（單選）        付款狀態 6 值 ／ 出貨狀態 4 值 ／ 建立日期 5 值
展開式複選 checkbox   來源 4 值 ／ 管道 4 值
單一 checkbox         顯示刷卡未付款（預設不勾）
```
🔴 **【長】規則:員工要能一眼看出哪個是單選、哪個是複選。**
**依據** = 契約 `requiredStates` 要求每個控制項有可分辨的狀態 + Sean 常設準則「不用人教能做對」。
⚠️ **這是設計題,本檔不決定用哪種形態** —— **只釘住「四種語言混用時必須有可分辨的視覺差異」這條要求。**

🔴 **兩條功能面硬約束(外觀可以變,這兩條不能碰)**:
1. **篩選功能不動** —— Sean 逐字「我們目前的功能比較強」。
2. **搜尋詞刻意不進 URL**(是 PII,住 httpOnly cookie)⇒ **不要設計「複製此篩選連結」「存成書籤」** ——
   其他九軸都會進 URL,**只有搜尋詞不會 ⇒ 連結貼給別人會靜默丟掉搜尋條件。**

### 6.5.3 分頁

**共用元件**:`components/shared/list-pagination.tsx` —— `/orders` `:265`、`/customers` `:71`、`/products` `:100`
**三頁 import 同一支** ⇒ **量其中一頁的結果對三頁都成立。**

**現況(真站實測 + 原始碼對照,不是推測)**:
```
整條逐字：第 1–20 件 / 共 20336 件（第 1／1017 頁）  上一頁  下一頁
來源      list-pagination.tsx:56-59
停用態    NAV_DISABLED = 'text-muted-foreground pointer-events-none opacity-50'  :9
          （實測 opacity 0.5 + pointer-events: none，逐字對上）
```
| 規則 | 來源 |
|---|---|
| `page` 走 URL,**`page=1` 省略不寫** | **【長】** 依據 = 「等於預設值就不進 URL」既有紀律 |
| 停用態要**看得出來**(半透明 + 灰字 + 不可點),不是只有不可點 | **【長】** 依據 = 契約 `requiredStates` 含 `disabled` |
| 按鈕圓角跟隨 `--radius`(→ 直角) | **【抄】** |
| 🔴 **頁數多時必須能跳頁** | **【長】** 見下 |

🔴 **唯一的真缺口:不能跳到指定頁。**
```
20,336 件 ÷ 每頁 20 = 1017 頁
⇒ 要看第 500 頁，員工得按 499 次「下一頁」
```
⚠️ **要講準**:**不是「不知道在第幾頁」** —— 畫面明寫「第 1／1017 頁」。
**是「知道有 1017 頁而到不了」。**
🔴 **知道有 1017 頁卻只能一頁一頁按,可能比不知道更讓人放棄。**
**依據** = Sean 2026-08-16 逐字「搜尋、分類、篩選…應該是你會自己補上去」。

> **⬜ 未確認**:重整/回上一頁之後回不回得到原本那頁。**沒有人驗過。**

### ⚠️ 兩個量分頁的坑(**獨立的兩件,都是實錘,寫給下一個人**)

**① 要量【整條容器】,不是內層 nav**
```
:54  <div className='flex items-center justify-between gap-4'>   ← 整條
:55    <p …>第 X–Y 件 / 共 N 件（第 A／B 頁）</p>                  ← 頁碼在這半
:60    <div className='flex items-center gap-2'>                  ← 只量到這個 ⇒ 只會看到「上一頁 下一頁」
```
**⇒ 量到 `nav.parentElement` 會漏掉頁碼;要 `parentElement.parentElement`。**

**② 🔴 這個 repo 的中文文案用【全形斜線 `／` U+FF0F】**
```
:58 同一句話裡有兩種斜線：'/' U+002F（「/ 共」）與 '／' U+FF0F（「第 A／B 頁」）
⇒ 用半形 / 寫的正則【打不到】頁碼，會得到 false
```
🔴 **影響面超出分頁** —— **repo 裡任何「第 X／Y」形狀的文案都吃這個。**
**⇒ 針對中文 UI 文案的 grep / regex,全形與半形都要試。**

> 🔴🔴 **而這兩個坑加起來造成的結論是「分頁沒有頁碼」—— 一個【功能缺口】等級的假報告。**
> **判別句(比上面兩條更根本)**:
> **手上有真畫面時,先讀 `innerText` 看它到底寫什麼,再決定要不要用正則問它。**
> **用一個【會失敗的間接方法】取代一個【不會失敗的直接方法】,是這種誤報的共同起點。**

### 6.5.4 狀態膠囊
**現有值域(逐字,來自篩選選項)**:
```
付款狀態  已付款 / 待付款 / 付款確認中 / 已退款 / 已退部分
出貨狀態  未訂貨 / 已向廠商訂貨 / 已到貨 / 已出貨
```
| 規則 | 來源 |
|---|---|
| 🔴 **狀態膠囊維持圓角(pill)—— 而這與 OD 相反,見下** | **【長】** **不是【抄】。** 我們自己的判斷,依據 = §6.5.4 的「形狀傳達可不可以互動」;**OD 的實際立場是方角** |
| 語意色只用 `success` / `warn` / `danger` 三個,**不自己發明第四個** | **【抄】** `:25-27` |
| 🔴 **膠囊不是按鈕** —— 不給 hover / 不給 `cursor: pointer` | **【長】** 依據 = 稿的「M 三色條只當品牌標記、不當按鈕」紀律,同一條推廣到狀態標示 |

### 🔴🔴 圓角衝突的裁決:**pill 給「只能看的」,直角給「可以互動的」**

> ## 🔴🔴 **修訂:這條裁決與 OD 相反,而我第一版把它標成【抄】**
> **實查 OD `:205-206` 逐字**:
> ```
> /* ── 狀態膠囊：方角（BMW M 的工業直角），顏色由貨品軸決定 ── */
> .cap{ … border-radius:0 … }
> ```
> ⇒ **OD 對狀態膠囊的立場是【方角】,而且寫了註解說明理由。**
> **OD 全檔唯一的 pill 是 `:316 .legacy`** —— **那個 class 名字就是「被換掉的那一版」。**
>
> 🔴 **而我當初的依據是 OD `:56` 的 `--radius-pill: 9999px` 宣告** ——
> **那顆 token 的 `use` 是 0**,與我在 §2 親手判死的 `--radius-lg: 14px` **是同一種東西,只差一行(`:55` vs `:56`)**。
> ⇒ **我在同一份檔裡一邊寫「以實際用值為準、不以宣告為準」,一邊拿一個 use=0 的宣告當靠山。**
> **這正好命中本檔開頭那條「【抄】不是免檢票」** —— **而那條規則是我自己寫的。**
>
> ⚠️ **裁決本身沒有被推翻,它降級了**:
> **它從「照 BMW M 做」變成「我們刻意與 BMW M 不同」** —— **後者需要 Sean 拍板,前者不需要。**
> 🔴 **⇒ 已標【待 Sean 裁】**:狀態膠囊要跟 OD 一起變方角(全站無 pill),還是保留 pill?
> **本片不動狀態膠囊(它們用 `rounded-full`,不吃 `--radius`)⇒ 現況維持圓角,等他決定。**
> ✅ **不受影響的**:**篩選 chip 直角化仍然成立且理由更強** —— **OD 那邊也是方角。**

**現況實測(同一列上兩種圓角語言,緊鄰)**:
```
分頁按鈕「下一頁」   76×36  圓角 6px    ← 控制項
篩選 chip「全部/手動/自動」 48×26  圓角 999px  ← 也是控制項，卻是 pill
```
⚠️ 而 BMW M 的方向是 **圓角 → 直角**(`--radius` 8px → 0)⇒ **那個 `999px` 要怎麼辦是本檔要答的。**

**🔴 裁決與判別句**:
> **形狀傳達的是「可不可以互動」,不是「重不重要」。**
> **可以點的 ⇒ 直角**(跟所有控制項一致)。**只能看的 ⇒ pill**(跟所有狀態標示一致)。

⇒ **篩選 chip 是控制項 ⇒ 跟按鈕一起變直角,失去 pill。**
⇒ **狀態膠囊只能看 ⇒ 保持 pill。**
✅ **好處**:**pill 這個形狀從此在整個後台只有一個意思 ——「這是狀態,不要點它」。**
🔴 **而這與 §1 三階邊框用的是【同一條判別線】**(「這是控制項嗎 / 它的狀態是什麼」)——
**一條判別線同時決定邊框與圓角,下一個人不用記兩套。**

**來源**:**【長】** —— 依據 = 稿的「M 三色條只當品牌標記、不當按鈕」+「圓角 → 直角」兩條原則的交集。
⚠️ **BMW M 本身沒有處理過「篩選 chip」這種東西**(它是行銷/編輯頁的語言)⇒ **這是我們長出來的,不是抄的。**

### 6.5.5 🔴 空狀態 —— **完全沒有現況,整節是【長】**
**依據**:契約 `requiredStates` 九態含 `empty`;Sean 北極星「員工不用人教能獨立跑完一天」。

🔴 **為什麼這一格特別重要**:**空狀態是「員工第一次用這個功能時看到的畫面」** ——
**它同時是最少人設計、最多人第一次接觸的那一格。**

**每個空狀態必須回答三件事**:
```
① 現在為什麼是空的      （沒有資料？篩選篩掉了？還沒開始用？——三者的文案完全不同）
② 他可以做什麼          （一個明確動作，不是「請稍後再試」）
③ 做不了的話找誰        （而不是讓他卡在那裡自己想）
```
⚠️ **①的三種成因不可共用一句文案** —— **「篩選篩掉了」寫成「目前沒有資料」會讓員工以為系統壞了。**

### 6.5.6 按鈕與輸入框
```
現況 button.tsx    hover 10 / focus 5 / active 0 / disabled 2 / transition 1
現況 ADMIN_INPUT_CLASS（components/shared/admin-form.tsx:19-20，15 個消費端）
     'border-input bg-background h-9 rounded-md border px-3 text-sm'
```
| 規則 | 來源 |
|---|---|
| 圓角 → **直角**(`rounded-md` 會因 `--radius` 改為 0 而自動變) | **【抄】** |
| 輸入框邊界用 **`--border-interactive`**(≥3.0) | **【長】** 依據 = §1 判別句 + WCAG 1.4.11 |
| **`active:` 要補**(現況九支原件只有 sidebar 有) | **【抄】** `:24` accent 壓深 14% |
| **`input` 的 `hover:` 要補**(現況零) | **【長】** 依據 = 契約九態含 `hover` |
| 🔴 **`ADMIN_INPUT_CLASS` 這個字串不改** —— 只改它引用的 token 值 | **【長】** 依據 = 「從 token 層改,不要一個元件一個元件改」 |

⚠️ **`h-9` = 36px**:AA(2.5.8,24×24)過、AAA(2.5.5,44×44)不過。**本輪不改,見 §5 的分級說明。**

### 🔴🔴 數字對齊那條的更正:**目標對,而它預設的手段不是我們該用的**

```
skill 說：「數字一律用 font-mono」
我第一版查：orders-table.tsx font-mono 只有 1 處（:309 料號）⇒ 我判「現在就壞著」
🔴 而真值（實查，正向對照 grep -c radius globals.css = 11 證明 grep 是活的）：
   orders-table.tsx  tabular-nums  4 處 —— :313 數量 / :322 單價 / :330 金額 / :337 小計
   全 admin 分母      font-mono 7 檔/14 行   ·   tabular-nums 16 檔/45 行
```
⇒ ✅ **已達成。做法是 `font-variant-numeric: tabular-nums`(等寬【數字】),不是 `font-mono`(等寬【字體】)。**

**而 `tabular-nums` 比 `font-mono` 更適合我們**:
- **它只讓數字等寬,中文與標籤仍用比例字體** ⇒ 版面不會變醜
- **`font-mono` 會把整格切成等寬字體,而中文在等寬字體下很難看**

🔴 **⇒ 不要照 skill 的字面去加 `font-mono`,那會把已經對的東西改壞。**

> **這件事的形狀值得記(比這條規則本身重要)**:
> **skill 給的是【目標】,而它預設的【手段】未必是我們該用的那個。**
> **拒絕它的 baseline(圓角/陰影/字體)是這件事的粗版;**
> **這一條是細版 —— 目標我同意,手段我不採用,而兩者都要寫下來,否則下一個人只會看到「skill 說 X」。**

## 7. 列印(A4、黑白可讀)—— 🔴 **這一節是【驗收條款】,不是提醒**

⚠️ **修訂前這裡是一段警語,而警語不會擋住任何人** ——
**它住在【設計參照】,而寫列印的人讀的是【列印需求書】** ⇒ **沒有東西會在有人跳過時叫。**

### 🔴 列印片的驗收條款(**要抄進 `docs/specs/2026-08-16-print-docs-design-brief.md`**)
```
□ 本檔所有 AA 對比數字【不得】直接引用 —— 它們是螢幕彩色算的，紙上是灰階
  ⇒ 列印片要自己用【灰階明度】重算一次，並把算式寫進那份檔

  ⇒ 紙上的邊界只能靠【線與留白】，那是另一套規則，本檔沒有
□ 語意色（success / warn / danger）在黑白列印下會變成三個接近的灰
  ⇒ 不得只靠顏色傳達狀態（WCAG 1.4.1 的同族要求）
```
🔴 **這三條是【必答】,不是參考** —— **沒有回答就不算列印片做完。**

### 為什麼要抄過去而不是連結過來
**這份檔的讀者是做螢幕 UI 的人,他不會去讀列印需求書;而做列印的人不會來讀這份。**
⇒ **條款要住在【會被讀的那份檔】裡。** 連結只在兩邊都會被讀時才有效。

**背景(兩件螢幕沒有、紙上才有的問題)**:

1. **黑白列印下對比要重算** —— **本檔所有 AA 數字都是【螢幕彩色】算的**,紙上是灰階,**那些數字不通用**。
2. 🔴 **紙上沒有 hover / focus** —— 邊界只能靠**線與留白**。
   ⇒ **而我們的三階邊框正是為【螢幕互動】分的**(判別句是「需不需要靠它知道可以點」)
   ⇒ **那三階在紙上沒有對應意義,不要直接套。**
