數法(2026-08-29 實跑):
```
grep -o 'SKU-0002' shipping-3item.html | wc -l   ⇒ 2   ← 第 3 個品項在紙上出現兩次

## ⚠️ 那兩行(`下單:…` / `本次出貨:N 項`)的代價 —— **而它有解析度限定**
```
在 1..12 的每一格, 拿掉它們【都沒有讓頁數改變】⇒ 門檻一格都沒有往後移
🛑 而正對照只證明這把尺看得到【650 字元(= 一個完整品項)】的差
   而那兩行只有約 60 字元 ⇒ 尺【沒有被證明】看得到那個量級
⇒ 正確字面:**小於一個品項列, 且不足以在 1..12 移動任何門檻**。不是「代價為 0」。
```
📌 而它們**不是**任何回歸的兇手:`git log -S'本次出貨:{lines.length} 項'` ⇒ `14f8a8e8`, 落地 2026-08-15。

## 🔴 而真正的成因不是「幾項」—— 是**餘裕是零**
```
`.pd-sheet` 的 `min-height`(⛔ ~~271mm~~ ⇒ **2026-08-29 起 250mm**, 見下)+ 頁尾 `margin-top: auto`
⇒ 內容【永遠恰好等於那個 min-height】, 不論 1 項還是 7 項
   (2026-08-29 改值前量:六份不同的紙 × 三種形狀, 全部剛好 **1024px**;
    改值後那個常數變成 **945px**, 而【永遠恰好等於它】這件事沒變)
⇒ 改值前實測:可印高 271mm ⇒ 1 頁;**269mm ⇒ 連只用 68% 的那張也變 2 頁**
⇒ **當時是 2mm 寬的懸崖;改值後懸崖在 250mm。而它與品項數、資料、字型都無關。**
```

### 🔴 2026-08-29 `min-height` 271mm ⇒ **250mm**(Sean 逐字「可以」)

🛑 **而這【不是把機制修掉】—— 是把懸崖搬家。**(2026-08-29 code-reviewer 抓到, 原句寫「已修」。)
```
`margin-top:auto` 把頁尾釘在框底 ⇒ 內容【仍然】永遠恰好填滿 min-height ⇒ **餘裕仍然是零**
⇒ 只是那個框從 271mm 變成 250mm
🔴 ⇒ 可印區低於 250mm 的裝置上, 同一件事會【一模一樣地】再發生
```
📌 **⇒ 所以正確的字面是「在 Sean 那台上不再發生」, 不是「這個問題修好了」。**
```
成因:Sean 那台 HP 的【那組設定下】可用高在 **[252, 265.6) mm** 之間
     (他實測:縮放 98% 仍兩張 ⇒ 上界 271×0.98=265.6;93% 才一張 ⇒ 下界 271×0.93=252)
     🔴 **252 是【下界】不是量到的點值** —— 而 94~97% 沒有問過。
     ⇒ 所以「≤252 保證安全」是對的, 而【不要】把 252 當成那台機器的真實能力。
⇒ 而 271mm 之下, 在他那台上【連一項的單也是兩頁】(實測 0 項 / 0 項)
實測(可印 252mm):271mm ⇒ 0 項/0 項 · 260mm ⇒ 0 項/0 項 · **250mm ⇒ 6 項/4 項**
✅ 而在我們宣告的世界(可印 271mm):271mm 與 250mm 都是 **7 項/5 項** ⇒ **容量零代價**
🔴 而【它什麼時候要重算】:換一台印表機 / 使用者改列印邊界設定 ⇒ 用同一個縮放回推法重量

```

## ⇒ 怎麼重跑一次(HTML 是產生得出來的, 沒有收進 repo)

```bash
# 0. 先 build —— 量測要吃【建置後的 CSS】,不是原始碼
TURBO_FORCE=1 pnpm build

# 1. 產 HTML(既有管線;它會寫進 /tmp/pcm-print-measure/)
npx vitest run --project admin \
  'apps/admin/src/app/print/orders/[id]/shipping/[shipmentId]/page-measure.test.tsx'
#   ⚠️ 它開頭會 rmSync 整個輸出目錄 ⇒ 產完【立刻把檔複製走】,否則下一次跑就沒了

# 2. 數頁數
sh scripts/pagecount.sh /tmp/pcm-print-measure/shipping-1item.html
#   exit code 三態分得開:0=成功(頁數在 stdout) · 3=Chrome 沒產出 PDF · 4=數不出頁數
#   ⚠️ 機器負載高時會 ENV-FAIL ⇒ `sh scripts/pagecount.sh --selftest` 會自己說是不是環境問題
```
🔴 **本檔那四個世界的 fixture, 現有管線只造得出其中一部分。** 要造另外三個:
```
出貨單「尚未出貨:無」⇒ 條件是 outstandingRows.length === 0(shipping-doc.tsx)
   而 outstandingQuantity = max(0, quantity − cancelled − shipped − 這箱)
   ⇒ fixture 給 quantitySummary: { quantity:1, orderedQuantity:1, instockQuantity:1,
      cancelledQuantity:0, shippedQuantity:0 } + 這箱出 1 + shippedAt: null ⇒ 得 0
🛑 而給 `quantitySummary: null` ⇒ outstandingQuantity 回 null ⇒ 而【null 一定會被列出來】
   ⇒ 那樣永遠走「有未出貨表」那條, 而你會以為自己在量正常情況
✅ 活錨(證明你在哪個世界, 而不是以為):
   ⛔ ~~走「無」那條   ⇒ expect(html).toContain('這張訂單沒有還欠客人的品項')~~
   🔴 **2026-08-30 傍晚 Sean 拿掉了那句話** ⇒ **那個字面已經不在碼裡**
      ⇒ 照這一行寫的人會拿到一個【永遠對不上的錨】, 而他不會懷疑一份被路由表背書的檔。
   ✅ 走「無」那條   ⇒ expect(html).toContain('以下空白')

## ⚠️ 這份東西量不到什麼(四行, 不可略)

1. 用的是 **fixture 資料**, 不是真訂單(品名 20 字 / 地址 17 字 / 單價六位數)。
   而真單通常更短 ⇒ 真的印會**比這裡更矮**, 不會更高。
2. 量的是 **playwright chromium / headless Chrome**, **不是任何一台印表機**。
3. 每一發都附**加總回核**(直接子元素高度含 margin 相加 vs 總高, 差 0~1px)⇒ 表上沒有漏掉的區塊。
4. 🔴 **「真印表機」那一格【至今未驗】** —— 所有量測都是 PDF 的墨水位置,
   而**不可印區是印表機的、不是 PDF 的**。要驗掉它, 要有人用實體印表機印一張、
   **照抄**紙上最下面正中央那一行字(不能問「有沒有」——那在兩個世界是同一句話)。
