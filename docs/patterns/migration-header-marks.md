# migration 檔頭的 `pcm:` 標記 —— 唯一一份解釋

> ⟦0e-DDLINTOVC-MARK⟧ · 線【DB】`-db` 2026-09-06 建。主視窗 `-f8` 裁【甲:新標記與 never-apply 並存】+【乙:補版控型記進帳本】。
> 🔴 **本檔存在的理由是量到的**:Fable 2026-09-06 R3 F9 —— 三支 migration 各自複製了 **15 行**同樣的解釋,
> 裡面手寫了一份「讀它的是誰」的清單,而**那份清單在 commit 當下就已經過期**(它漏了 `scripts/state-gates.sh`)。
> 📌 **註解裡的註冊表會過期,而沒有東西會叫。**⇒ 解釋只留這一份,檔頭只留一行指標。

## 0. 唯一的 parser

`scripts/lib-migration-header-marks.sh` —— **文法只有這一份**,四支工具都 `source` 它,讀不到就 fail-closed 擋下。

🔴 **為什麼收攏**(Fable R3 F4 實錘,當場複驗):收攏之前四支工具各寫一份 parser,而它們有**兩種文法** ——
`case *"-- pcm:ddl-into-vc:"*`(`--` 後恰好一個空白)vs `^--[[:space:]]*`(任意空白、要行首)。
餵 `--  pcm:ddl-into-vc: x`(兩個空白)⇒ **兩把尺說「補版控型」、兩把尺說「一般檔」,而畫面上沒有東西說兩邊不同。**

📌 而這解釋了一個模式:codex R1 抓 8 條、R2 又抓 8 條,而我每次都以為折完了 ——
**N 份 parser + N 份訊息,一個修法在結構上只能是局部的。那不是紀律問題。**

`--selftest` 10 格(含「兩個空白」「零空白」「值是空的」「沒有標記」「ESC 控制字元被剝掉」雙向)。

## 1. 文法

- 只看**檔頭前 20 行**。一支檔中段【提到】某個標記字面,不該把它自己變成那一型。
- 形狀 = 行首 `--`、任意空白、`pcm:<key>`,帶值的 key 再接 `:` 與值。
- 值前後空白剝掉;**字元白名單** `A-Za-z0-9_., "-`,其餘一律剝掉。
  🔴 為什麼是白名單:codex R2 指出只刪反斜線不夠 —— ESC / CR 一樣能重畫終端、把後面的安全提示蓋掉。
  **白名單不需要知道下一個沒想到的字元長什麼樣。**
- 帶值的 key 而值是空的 ⇒ **不算合法標記,而且要出聲**。靜默的「看起來有標記」最貴。

## 2. key 註冊表

| key | 帶值 | 意思 | 讀它的 |
|---|---|---|---|
| `never-apply` | 否 | 本支不 apply 到正式庫 | `migration-ledger-divergence.sh`(⑨)· `state-gates.sh:21` |
| `not-needed-now:` | 是 | 目標已達成,目前不需要貼;值 = 複查方法 | `migration-ledger-divergence.sh`(⑩) |
| `ddl-into-vc:` | 是 | **補版控型**:物件在正式庫上早就有了;值 = 物件名 | `is-migration-applied.sh` · `deploy-order-gate.sh` · `migrations-not-in-ledger.sh` · `migration-new-file-static-checks.sh` |

⚠️ **這張表是【文件】不是【機制】** —— 沒有任何東西會在你加了新 key 而沒登記時叫,也沒有東西會在讀者變動時更新它。
⇒ **查「誰讀它」的可重跑方法**(比這張表可靠):
```
grep -rln 'pcm:<key>' scripts/ .husky/
```

## 3. 兩個軸,不可互相推導

- `never-apply` = **這支要不要貼**
- `ddl-into-vc` = **物件在線上了嗎**

🔴 **為什麼要分開**(2026-09-06 量到):4 支 `never-apply` 裡 **1 支不是補版控型** ——
`20260904010000:3` 逐字「本支【刻意不貼】—— 而它不是『還沒貼』」,理由是保留一格會綠的不變式測試,與「物件在線上」無關。

## 4. 補版控型:四支工具各做什麼

| 工具 | 帶標記時的行為 | rc 變嗎 |
|---|---|---|
| `is-migration-applied.sh` | 每個物件的存在性判別力降成【零】;畫面、產出的 SQL、結果標籤三處都降;明說**看 0 不要看 1** | 否 |
| `deploy-order-gate.sh` | 擋人訊息裡點名,並說「不要照出路①去先 apply」 | **否 —— 刻意的** |
| `migrations-not-in-ledger.sh` | 標成「不是候選」,並算出真正候選數 | 否 |
| `migration-new-file-static-checks.sh` | 把「已 apply 本體不得動」改成「它從來沒有以檔 apply 過 ⇒ 改它不受那條限制」 | 否 |

🛑 **`deploy-order-gate` 為什麼只印不放行**:該檔逐字寫著「**本閘刻意不提供【打一行宣告就過】的欄位
(那種例外兩次被對抗審查證明是儀式)**」⇒ 一個檔頭註解就是那種宣告。
✅ **要讓閘不誤擋,走的是帳本那條路**(見 §5),不是讓標記變成放行券。

## 5. 補版控型要記進 `supabase/APPLIED.tsv`(`-f8` 2026-09-06 裁乙)

第四欄**開頭固定字面**(不要改寫):
```
【補版控型】物件在正式庫 ≠ 本檔被 apply;本檔從未以檔 apply
```
- **為什麼記**:不記 ⇒ 它永遠 PENDING ⇒ 部署閘擋掉每一次碰到那些物件的 app 改動
  (實例:`packages/adapters/src/supabase/helpers/fitment-queries.ts:132` 的 `.rpc('search_products_by_vehicle')`),
  而每次都印「可能誤擋…要 Sean 在場」—— Fable R3 逐字:**那句話訓練的是 `--no-verify`**。
- **為什麼帳本比檔頭強**:第二欄綁 sha ⇒ **檔內容一改就自動變回 PENDING、閘正確重燃**;
  而檔頭標記對內容改動**完全不敏感**。
- 🛑 **代價要明寫**:「APPLIED」這個字面 ≠ 執行過。那句固定字面就是在擋這個誤讀。
- 第三欄寫【未知】是刻意的:這些物件何時進正式庫沒有任何來源,寫記帳日會讓一個推出來的東西長得像量到的。

## 6. 這份文件答不出什麼

- **repo 裡到底有幾支補版控型** —— 只答得出「帶了標記的有幾支」。要真數,得先有標記再回頭掃(雞生蛋)。
- **標記說的是不是真的** —— 沒有任何工具能核實一個自我宣告。唯一便宜的對帳是
  `is-migration-applied` 產的 SQL **回 0** 那一格(0 = 標記是假的,或物件被砍了)。
- **`never-apply` / `not-needed-now:` 的兩份 parser 仍在原處**(`migration-ledger-divergence.sh` · `state-gates.sh`)——
  **那是已知缺口,不是漏掉**;收攏它們要動 pre-push 閘與 state-gates,另片。
