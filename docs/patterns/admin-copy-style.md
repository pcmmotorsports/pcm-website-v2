# 後台中文文案標準

來源：Sean 2026-09-21 要求全面改善後台中文，以及 Claude 的回覆、功能命名和介面寫作。語氣以自然、直接、可理解的台灣繁體中文為準。

## 寫作方式

員工看到文字後，應能回答：現在發生什麼事？按下去會做什麼？接下來需要做什麼？

- 按鈕：動作＋對象，例如「登記收款」「儲存收件資料」「查看出貨紀錄」。單用「確認」「處理」「更多」只適合上下文已清楚的地方。
- 既定名稱：保留 Sean 自訂的狀態、欄位及功能名稱，例如「已收未定」「已收已定」。這次改善的是說明與提示，不藉機重新命名。
- 說明文字：直接說明功能與操作結果，不用「上面那顆」「不是你改的」等含糊或多餘的句子。
- 表單：標籤寫資料名稱，提示補格式或限制，送出按鈕寫實際動作。
- 成功訊息：說明已完成的結果，例如「收款紀錄已新增」。不宣稱尚未發生的外部動作。
- 錯誤訊息：問題＋下一步。只有確認可安全重試時才建議重試；付款、退款和物流結果不明時先確認原作業狀態。
- 空白畫面：區分「沒有符合條件的資料」「尚未新增」「資料載入失敗」「沒有查看權限」。
- 用詞一致：同一概念固定一種名稱；按鈕、標題、提示與說明要同步。不同概念不為了字面一致而合併。
- 語氣自然：少用括號和破折號，不用「這不是你操作錯誤」「不是沒有，是讀不到」反覆解釋系統的內部判斷。
- 工程細節只在員工需要回報時放進「詳細資訊」。不要直接顯示 RPC、白名單、fail-closed、資料表名稱或測試理由。

## 必須保留的意思

| 情況 | 文案要保留的區別 |
|---|---|
| 登記收款 | 新增已收到款項的紀錄，不等於向客戶扣款 |
| 更正收款紀錄 | 帳務更正，不等於真的退錢 |
| 退款 | 申請退款、退款處理中、完成退款、人工登記退款，不能混稱 |
| 取消與作廢 | 取消訂單、作廢出貨單、作廢紀錄，各自指向不同資料 |
| 物流 | 建立出貨單、取得託運單號、列印託運單、交寄與送達，是不同進度 |
| 結果不明 | 尚未確認，不等於失敗或從未送出，不能暗示直接重送安全 |
| 金額與數量 | 保留金額、件數、剩餘量、計算範圍及限制條件 |
| 缺少資料 | 未填、查無、載入失敗、資料不完整各有不同意思 |

## 改寫示例（方向範例，不代表所有程式已改）

| 原寫法 | 清楚的寫法 |
|---|---|
| 登完這筆之後，上面那顆「已收未定／已收已定」是系統照收款總額自己算的，不是你改的。 | 儲存後，系統會依收款總額更新訂單的收款狀態。 |
| 改金額申請讀不到（不是沒有，是讀不到）。重新整理；還是一樣請通知系統維護。 | 金額修改申請載入失敗，請重新整理。若仍無法載入，請聯絡系統管理員。 |
| 還不能用（要先做後端） | 此功能尚未開放。 |
| 員工名單現在讀不到，所以先不讓你建單（不是沒有員工）。 | 員工名單載入失敗，暫時無法建立訂單。請重新整理；若仍無法載入，請聯絡系統管理員。 |
| 功能做完了 | 功能已修改並通過本機測試，尚未上線。〔只適用這個事實狀態〕 |

## 修改範圍與驗收

文案修改保留狀態代碼、表單欄位名稱、API、權限、金額計算與操作流程。商品品名、人工翻譯、品牌、料號與法定用語先核對專案既有詞彙表，不納入介面文案的全域替換。

每次按一段實際操作流程修改，檢查該流程的選單、標題、按鈕、確認視窗、成功及失敗提示。更新有必要的文案測試，同時保留行為斷言；不能只改測試期待字串就宣稱正確。

測試通過後，在本機或測試資料畫面檢查長度、換行、截斷及上下文。會改變業務意思的名稱先列出狀態定義與前後對照，再請 Sean 決定。正式上線另需授權。
