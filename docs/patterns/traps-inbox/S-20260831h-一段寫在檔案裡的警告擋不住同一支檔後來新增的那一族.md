# 一段寫在檔案裡的警告,擋不住同一支檔【後來新增】的那一族

> 線【出貨】`-1e` · 2026-08-31 · **我自己挖到的**(codex 那一輪沒提這格)

## 現場

`apps/storefront/src/app/api/cron/anomaly-alert/route.test.ts` 的 `CLEAN_RESULT` fixture 裡,
有一段警告逐字寫著:

> 🔴 F-004:這三欄**必須明寫**,不能靠「fixture 沒有它 ⇒ undefined ⇒ falsy ⇒ 剛好走 200」。
> 那種過關是**假的**:route 讀的是 `result.orderRefundsStuckUnknown`,
> 而一個缺欄位的 fixture 與「查得到而且沒事」在這裡印同一個結果。

**而那段警告底下八行之後新增的另一族(出貨那四欄)—— 一欄都沒有寫進去。**
那一片就是靠 `undefined ⇒ falsy` 過的,**正是它警告的那種過關**。

## 📌 成因不是「有人沒讀」

```
加新欄的人【在往下加】—— 他不會回頭讀八行前的警告。
而那段警告涵蓋的是【它寫下來那一刻已經存在的欄位】, 不是這個 fixture 的未來。
```
🔴 **⇒ 一段警告的射程, 是它落筆那一刻的東西;而檔案會繼續長。**

## ⚠️ 而它的失效【零訊號】

```
少一欄 ⇒ undefined ⇒ falsy ⇒ route 走 200 ⇒ 測試全綠
⇒ 與「查得到而且沒事」印同一個結果 —— 那正是那段警告自己寫的那句話
```
📌 **⇒ 它預測了自己失效的樣子, 而那沒有讓它不失效。**

## ✅ 可執行的那一步(而它不是「再寫一段警告」)

```
要涵蓋【未來那一族】, 得是一個【新增時會變紅】的東西, 不是一段文字:
· 讓 fixture 的型別是完整的 domain 型別(不是 inline object)⇒ 少一欄 typecheck 就紅
  ⚠️ 而本例的 fixture 是 `checkSpy.mockResolvedValue` 的引數 ⇒ 型別鬆 ⇒ 少欄不紅。**這是它能發生的原因。**
· 或一格斷言:把 fixture 的 key 集合與 domain 型別的 key 集合比對
```
🛑 **我今天只做了【補齊那四欄 + 我新增的三欄】,沒有裝上面那道機制。**
⇒ **所以同一件事會在下一族欄位再發生一次。未解,不是已解。**
