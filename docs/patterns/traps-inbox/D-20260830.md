## D-1 一個 view 的【行為】由 `WHERE` 決定,而它的【約定】住在 `COMMENT` 裡 —— 兩個都要讀

**當班實錘(2026-08-30)**。

我要判「出貨通知信第一次接上線會不會對舊單補寄」,於是去讀那支 view 的 `WHERE`:
```
WHERE s.shipped_at IS NOT NULL AND s.deleted_at IS NULL AND (…) AND NOT EXISTS (…)
🔴 零時間界線（interval 0 ／ now() - 0 ／ days 0 ／ shipped_at > 0，負對照 0）
```
⇒ 我得出「它會撈到所有歷史單」(**那是對的**),
⇒ 然後把「那顆 cutoff 要用自己一顆、還是共用既有那顆」寫成一個**要 Sean 拍的設計題**。

### 🔴 而答案早就在【同一支檔】的 `COMMENT ON VIEW` 裡
```
'⚠️ 本 view 【不】自帶起始線 —— 它回的是【歷史上全部】還沒排過信的配對。'
'cutoff 由呼叫端以 shipped_at 條件加上（env SHIPPED_EMAIL_CUTOFF，
  鏡像 order_created 那條的 B4_DEPLOY_CUTOFF）'
```
✅ **⇒ 那顆 env 的【名字】與【它是自己一顆】,寫這支 view 的人早就定了。**
🛑 **⇒ 所以那個「設計題」不存在 —— 而我差點拿它去佔 Sean 一次注意力。**

### 📌 判別句
> **一個 view 的【行為】由 `WHERE` / 索引 / 觸發器決定;**
> **而它的【約定】(誰負責給什麼、為什麼這樣切、哪些東西刻意不在裡面)住在 `COMMENT` 裡。**
> **⇒ 兩個都要讀。而讀碼的人的習慣是只讀前者。**

🔴 **而它為什麼特別容易漏**:
```
· WHERE 讀起來像「事實」，COMMENT 讀起來像「說明」
  ⇒ 而我們被訓練成「不要相信註解，要看碼」
  ⇒ ⇒ 而那條訓練在這裡【剛好害了我】：那段 COMMENT 不是在描述碼，是在【指派責任】
· 而 COMMENT ON VIEW 在檔案的【最下面】，離 WHERE 幾十行
· grep 一個欄位名會命中 WHERE，而不會讓你讀到 COMMENT
```

### 下次那一刻要做的動作
> 讀一支 view / 表 / 函式要下任何「它會不會…」的結論之前,
> **把那支檔的 `COMMENT ON` 段落整段讀完** —— 不是 grep,是讀。
> ⇒ 而具體到可執行:`grep -n 'COMMENT ON' <檔>` 拿到行號,然後**開那幾段**。

⚠️ **鄰居但不同**:正本 `:10097`「守門掃【來源】,而人讀的是【輸出】」——
那一條講的是**兩個不同的產物**(原始碼 vs 渲染結果),而**尺與人不在同一個平面**;
**本條講的是【同一支檔的兩段】,而讀的人只讀了其中一段。**
📌 **⇒ 共通的母題是「答案在一個你的習慣不會去的地方」,而落點不同。**

### ✅ 而它有一個【正面】的對照,同一支檔裡
同一支 migration 另有 `public.pcm_shipped_email_unsendable`,而它的 COMMENT 逐字:
> 「分開的理由…它們永遠不會消失,留在這裡會由最舊那端永久擋住後面的有效信」

📌 **⇒ 也就是:這個 repo 已經有一個慣例 ——【被排除的東西要有自己的一張表,不是消失】。**
🔴 **⇒ 而那個慣例也只寫在 `COMMENT` 裡。** 我是因為這一次去讀了才知道它存在。
⇒ **一個沒有人讀的慣例,與一個不存在的慣例,在下一個人身上是同一件事。**
