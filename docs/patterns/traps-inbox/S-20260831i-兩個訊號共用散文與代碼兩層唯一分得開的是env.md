# 兩個訊號共用【散文】與【reason 代碼】兩層,唯一分得開的是 `env`

> 線【出貨】`-1e` · 2026-08-31 · **同一天撞了兩次**,而第二次是在修第一次的時候撞的

## 現場

一支每日 cron route 上有兩個不同的訊號,各自對應**一顆不同的 env**:
```
SHIPPED_EMAIL_CUTOFF   ⇒ 出貨信缺口那一段
B4_DEPLOY_CUTOFF       ⇒ 訊號 4(訂單成立信沒被建出來)
```
兩個都在「沒設」時印一行 `console.info`。而它們:
```
散文        兩行都寫「還沒上膛 ⇒ 這一輪不查(不是失敗)」        ← 撞第一層
reason 代碼 兩行都是 `skipped_no_cutoff`                        ← 撞第二層
env         SHIPPED_EMAIL_CUTOFF / B4_DEPLOY_CUTOFF             ← **唯一分得開的**
```

## 我撞了兩次,而第二次是在修第一次的時候

```
第一次 一條既有斷言寫 `not.toContain('還沒上膛')` ⇒ 訊號4 也印那句 ⇒ 誤紅
       ✅ 改用 reason 當錨
第二次 改完之後又紅 ⇒ **連 reason 都一樣是 `skipped_no_cutoff`**
       ✅ 只好用 env 當錨, 並加一格正對照(另一顆 env【在】log 裡 ⇒ 證明 spy 不是空的)
```
📌 **⇒ 我以為換了一層更「結構化」的錨就安全了 —— 而那一層也是共用的。**

## 🔴 而這【不只是測試的問題】

```
一個人在 log 裡看到「還沒上膛」, 或看到 `skipped_no_cutoff` ——
**他一樣不知道是哪一顆 env 沒設。**
```
⇒ 📌 **那條 log 對【人】也沒有判別力, 而測試只是先撞到而已。**
🔵 **⇒ 測試斷言撞到的錨衝突, 是那條 log 自己的缺陷的第一個症狀。**

## 判別句

```
一條 log 要回答的是「**是哪一個**」, 不只是「發生了什麼」。
兩個訊號共用文案時, 分得開它們的那個欄位就是唯一的錨 —— 對測試與對人都是。
⇒ 而【共用幾層】要當場數:散文 / reason / code / 前綴 …… 一層一層試,不要試一層就以為安全。
```

## ⚠️ 射程 / 我沒做的

```

  所以「人分不出來」那一半**今天仍然成立**。那是已知而未修, 不是已解。
· 我沒有掃過這支 route(或別支)還有幾組訊號共用文案。**未數。**
```
