## 兩個實例並排

### ✅ 對的那個 —— 客人下載明細 PDF(片 C3,本窗自己做的)
```
情境  伺服器產 PDF 需要中文字型;字型沒被打包進函式包 ⇒ 讀不到
若不擋 PDF 照樣產出來、HTTP 200,而**每個中文是方框**
        ⇒ 那個世界與成功的世界, 在所有機器可讀的訊號上完全一樣
處置  embedded === 0 / uncovered > 0 / 版面 CSS 讀不到 ⇒ **回 500, 不產那張紙**
```
**為什麼它是對的, 兩格:**
```
① 擋掉的範圍 = 【這條 route】。而它守的就是這條 route 的產出 ⇒ 範圍與守的東西重合
② 出路      = `/account/orders/<id>/statement` 那一頁還在, 那顆「列印 / 儲存成 PDF」的鈕也還在
             ⇒ 客人**照樣拿得到明細**, 只是多按一下
```

### ❌ 錯的那個 —— 出貨告警的 env(出貨線,同日 codex 打回;**轉述,未親驗**)
```
情境  一顆打錯的出貨 env
處置  整支告警啞掉 —— **含付款、退款**
```
**為什麼它是錯的:**
```
① 擋掉的範圍 = 【整支告警】。而它守的是【出貨那一格】 ⇒ 🔴 **範圍遠大於它守的東西**
② 出路      = 無。告警啞了就是啞了, 沒有人會從別的地方收到那些訊息
```

## 🔴 判別句(兩問,缺一不可)
```
問一:我擋掉的東西, 有沒有超出【我在守的那一件事】?
     超出 ⇒ 我用一個小問題的偵測, 關掉了一堆與它無關的東西。
問二:被擋的人,有沒有別的路可以拿到他要的東西?
     沒有 ⇒ 那不是 fail-closed, 那是 fail-dead。
```
📌 **⇒ 「fail-closed」這個詞永遠聽起來是對的, 而它自己不含這兩個問題的答案。**

## 🛑 而還有第三個問題,它決定這道閘活不活得下去
```
一個 fail-closed 若沒有出路, **它會被下一個人整支刪掉** ——
而刪掉它的人不會覺得自己在拆保護, 他會覺得自己在修一個「一直在擋我的東西」。
⇒ 所以「有沒有出路」不只是使用者體驗, 它是**這道閘的存活條件**。
```
(這一句與正本既有的「守門紅了沒有出路會被整支刪掉」是同一件事 ——
 本則的貢獻是把它接到 fail-closed 的判準上, 而不是重寫它。)
