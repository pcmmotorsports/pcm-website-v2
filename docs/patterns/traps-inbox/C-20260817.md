## 量的那份頁面裡**沒有我剛寫的 CSS** —— 而症狀長得像「我的 CSS 寫錯了」〔安靜〕

**實例(2026-08-17 夜,C 窗 `#601` 整幅阻印版面)。**

量測管線的 fixture **內嵌的是【建置產物】的 CSS**
(`page-measure.test.tsx` 的 `builtCss()` 去 `.next` 撈 chunk,理由是那才是紙上真的會生效的樣式)。

我加了兩個新的 Tailwind class(`min-h-[170mm]`、`text-4xl`)⇒ 直接跑 fixture、`--png` 開圖:

    看起來「完全沒有生效」——版面與加之前【一模一樣】

**而我的 CSS 沒有錯。** 病是:**那兩個 class 在建置產物裡還不存在**
(Tailwind 是掃原始碼產 CSS 的 ⇒ 沒有重新 build,就沒有那兩條規則)。
`TURBO_FORCE=1 pnpm build` 之後同一份 fixture 一次就對。

### 為什麼它安靜(而且會把人帶往錯的方向)

    直覺結論：「我的 CSS 寫錯了」  ⇒ 接著會去改 CSS、換寫法、加 !important
    真正的事實：「我量的那份頁面裡沒有我的 CSS」
    ⇒ 兩者的【觀測】完全相同：一張看起來沒變的圖。
    🔴 而錯的那條路【有東西可以做】，所以人會一直做下去。

📎 **比「沒生效」更糟的一種**:如果那個 class 剛好**部分**存在
(例如 `text-4xl` 別的頁面用過、`min-h-[170mm]` 沒有)⇒ 圖會**變一半**,
那更像「我的 CSS 只對了一半」。

### 判別句(改樣式之後要量之前,當場問)

> **我量的這份產物,是在我改完之後產生的嗎?它裡面有我剛寫的那個 class 嗎?**
> 用一條命令答,不要用記憶:`grep -c 'min-h-\[170mm\]' <那份 fixture>` ⇒ 期望 ≥1。
> **回 0 ⇒ 先 build,不要改 CSS。**

### 動作

1. **動任何 Tailwind class 之後、量之前:先 `TURBO_FORCE=1 pnpm build`。**
   (`TURBO_FORCE=1` 的理由同 `#524`:少了它,turbo 命中快取會 replay 舊產物。)
2. **量之前先 grep 那個 class 在不在 fixture 裡** —— 那是這一族唯一便宜的量具。
3. 這一條**寫進管線檔頭**(`page-measure.test.tsx` 的用法段已經寫著「要先 build」)——
   🔴 **而我讀過那一段還是踩了**:它寫的是「先 build,它要讀建置產物的 CSS」,
   我讀成「**第一次**要先 build」。⇒ 檔頭那句要改成
   「**每次動樣式之後**都要先 build」,不然它只擋得住第一次。

📎 **同一族的第三個實例(方向不同、成因相同)**:memory
`feedback_vercel-build-cache-served-stale-css` —— Vercel 建置快取送舊 CSS,
**同一顆 commit,線上產物與本機產物不同**。
🔴 **共通母題:量到的產物 ≠ 你以為的產物。** 三個都出現在「同一顆 commit」這個假設之下:
```
本則      我改了 code，而【還沒 build】       ⇒ 量到的產物比 code 舊
Vercel 那則 我 build 了，而【快取送了舊的】    ⇒ 線上產物比 build 舊
（第三種，尚未在本 repo 遇到但同族）
          fixture 是上一輪產的、忘了重產     ⇒ 量到的產物比這一輪舊
          （本窗 2026-08-17 夜差點踩：主視窗拿 18:13 的 fixture 去驗 18:57 落地的功能，
             Sean 因此白印一趟紙 —— 那一發是【人】重用了一條當時正確的路徑）
```
⇒ **判別句對三種都成立**:**我手上這份產物,是在我那個改動【之後】產生的嗎?**
用一條命令答(`ls -l` 的時間戳、或 `grep` 那個新字面在不在產物裡),**不要用記憶**。

## 我驗過**自己的**量法,然後換成儀器 —— **而我沒有再驗那把儀器**〔安靜〕

**實例(2026-08-17 夜,C 窗 + 主視窗 + T 線,同一條鏈上三個人)。**

要量的東西:跑四綠那一刻**有幾個 vitest 在並行**(那是「機器吵不吵」的唯一硬證據)。

### 這條鏈的四步,每一步都看起來是在往上修

```
① 我手打一條： ps -Ao command | grep -c '[v]itest'        ⇒ 回 2
② 我自己抓到它壞了：那 2 個是【我自己的 shell】——
   我的命令列裡就有 vitest 這個字，[v]itest 那個括號技巧
   只避開 grep 自己，避不開【包住它的那個 shell】
   ⇒ 我明說「我沒有一把驗證過的量具，所以我不報那個數字」   ← 這一步是對的
③ merge dev 之後拿到 T 線寫的儀器 ⇒ 它印「並行 vitest 行程數：… 12 …」
   我把 12 報出去，並逐字寫「新儀器量的，不是我手打的」      ← 這一句是誠實的
④ 而那把儀器犯的是【同一個錯】，只是範圍更大：
   dev 上的版本 count_matching '[v]itest'
   ⇒ 撈進【全陣任何窗】命令列裡出現那個字的行程
     （實測的假命中：別窗 grep 的 pattern、別窗一支叫 vitest-sampler.sh 的腳本）
   兩個世界實測：真的有在跑 舊尺 23~25 / 新尺 2
                 沒有在跑   舊尺 ≥3    / 新尺 0   ← 舊尺有【地板】
   ⇒ 那個 12 對應的真 run 數【可能是 1、也可能是 0】。不可換算，只能重量。
```

### 🔴 為什麼它安靜:**一個被信任的量具,會關掉它所有下游的懷疑**

    第 ② 步我【驗了】那把尺 ⇒ 抓到
    第 ③ 步我【換了】一把更好的尺 ⇒ 不驗了
    ⇒ 「換成專用儀器」在直覺上是【提升】，所以它自帶一層豁免

而下游(主視窗)自陳:
> 「你逐字寫『新儀器量的,不是我手打的』,**而我把『儀器量的』讀成了『可信的』**,
> 然後在上面建了三層推論。」

🔴 **傳染路徑很乾淨**:上游驗過自己 ⇒ 改用儀器 ⇒ 上游不再驗 ⇒ 下游更不會驗。
**懷疑在鏈上是單向遞減的。**

### 🔴🔴 第二層,而它比第一層更難防:**誠實的限定,會被讀成保證**

「不是我手打的」這句話的**本意**是**縮小**我的宣稱(我沒有親手算)。
**它被讀成的意思**是**放大**可信度(有專用工具背書)。
⇒ **同一句話,兩個相反的作用。** 而我寫它的時候只想到第一個。

### 判別句(兩條,分別擋兩層)

> **「這個數字是量出來的」只回答了【誰產生它】,沒有回答【它有沒有判別力】。**
> ⇒ 換了量具 = **重新驗一次**,不是**繼承上一把的信用**。

> **我這句限定,在讀者手上是【縮小】還是【放大】我的宣稱?**
> ⇒ 會被讀成放大 ⇒ 那不是限定,是背書。改寫成「**我沒有驗過這把尺**」。

### 動作

1. **任何量具第一次用之前,雙向表演一次**:該有的世界要 >0、該沒有的世界要 =0。
   🔴 **「該沒有的世界要 = 0」是這一族的關鍵那一半** —— 舊尺的病就是**它有地板**
   (沒有 vitest 在跑時仍回 ≥3),而**地板在「有在跑」那一側是看不出來的**。
2. **報別人的儀器讀數時,連「我驗過沒有」一起報。** 沒驗 ⇒ 寫「未驗」,不寫「儀器量的」。
3. **退回一個已經發出去的數字時,連【它撐起的推論】一起點名退**
   (本例:「12 個並行之下全綠」那個反例整條收回,不是只改那個數字)。

📎 與本檔前一則(「量的那份頁面裡沒有我剛寫的 CSS」)同族:
那則是**產物比我以為的舊**;本則是**量具比我以為的鈍**。
**兩者的共通症狀:輸出是一個看起來完全正常的數字。**

## `grep -c` 數的是**行數**,而我拿它去數**次數** —— 在單行檔上它恆回 0 或 1〔安靜〕

2026-08-17 深夜,C 窗量「這份揀貨單 fixture 裡有幾個勾選框」:

```
grep -c 'picking-checkbox' picking-truncated.html      ⇒ 1
grep -o 'picking-checkbox' picking-truncated.html | wc -l ⇒ 12
```
**那份 HTML 是一整行**(元件 render 出來的 `innerHTML`,沒有換行)
⇒ `-c` 只答得出「這個字面出不出現」,答不出「出現幾次」。
而 `1` 是一個**完全合理的數字** —— 它甚至與「這一格守門有生效」相容。

### 🔴 為什麼它安靜:**這個習慣在【正常的檔】上被驗證過幾百次**

同一天在同一個 repo 裡,對一份**多行 markdown** 跑同樣兩條:
```
grep -c '我沒跑那條命令' guard-and-instrument-traps.md      ⇒ 3
grep -o '我沒跑那條命令' guard-and-instrument-traps.md | wc -l ⇒ 3   （一致）
grep -c '內容型斷言守不住' …                                ⇒ 2 ／ -o 也是 2
```
⇒ **`-c` 與 `-o` 在人寫的檔上幾乎永遠一致**,因為一行放一個句子。
⇒ 於是這個習慣**從來沒有被打臉過**,直到它遇上第一份機器產的單行檔。
🔴 **不是「我不知道 `-c` 是行數」** —— 是**「行數」與「次數」在我的日常樣本裡是同一個數**,
所以那個區別在腦子裡從來沒有被啟用過。

### 判別句(落筆寫下任何 `grep -c` 的數字之前)

> **我數的這個東西,一行裡會不會出現兩次?**
> 答不出來 ⇒ 那個檔是不是機器產的、是不是壓過、是不是 `innerHTML` 之類的單行輸出?
> 只要有一個是 ⇒ **`-c` 的那個數字不能用。**

📎 反向也成立、而且更毒:**`-c` 在單行檔上永遠 ≤ 1**
⇒ 拿它當「有幾個」的守門,那格在「12 個」與「200 個」兩個世界裡**印同一個 1**
⇒ 一格**永遠不會紅**的守門。

### 動作

1. **數次數一律 `grep -o <字面> <檔> | wc -l`。** `-c` 只留給「有沒有」。
2. **當場雙向表演**:餵一份該是 0 的、一份該是 N 的,**兩個數要不一樣**。
   本例實測 `0 / 12 / 200` 三個值分得開 ⇒ 這把尺才算可信。
3. 🔴 **把數字寫進 commit body / 報告時,把命令一起貼**
   —— 這一族唯一擋得住的地方是**下一個人看得到我用的是哪個旗標**。

📎 同族第三則。前兩則是**產物太舊 / 量具太鈍**,本則是
**量具本身沒壞,是我問了它一個它答不出來的問題,而它照樣給了我一個數字。**

## 那道 `console.warn` 判的是**第 49 頁**,而出事的世界**第 0 頁就 break 了**〔安靜〕

> 📎 2026-08-18 C 窗(`#629` 站點 2)。

`apps/storefront/src/lib/products.ts` 的車款翻頁迴圈:

```
:682   const PAGE_SIZE = 1000;
:695   .range(from, from + PAGE_SIZE - 1)
:705   if (page === MAX_PAGES - 1 && data && data.length === PAGE_SIZE) {
         console.warn('撞到 MAX_PAGES=50 仍是滿頁，車輛下拉可能被截斷');
       }
:719   if (!data || data.length < PAGE_SIZE) break;
```

**`:705` 那道 warn 寫得很好** —— 它的註解逐字寫著
「MAX_PAGES 撞頂是**靜默截斷**(下拉少一截、沒人會叫)⇒ 至少留 log」。
**作者知道靜默截斷很危險,而且動手做了一道。**

🔴 **而伺服器端 `max-rows` 掉到 1000 以下的那個世界:**
```
第 0 頁 .range(0, 999) ⇒ 伺服器夾到 500 列 ⇒ 500 < 1000 為真 ⇒ :719 break
⇒ page 停在 0，永遠走不到 MAX_PAGES - 1 = 49
⇒ 🔴 那道 warn 一次都不會響，而下拉少了一大截
```

### 🔴 為什麼它安靜:**它在 code review 時看起來【有守門】**

```
讀 code 的人看到  ：一個 console.warn + 一段講靜默截斷有多危險的註解
他得到的印象      ：這條路上有人守著
而事實            ：那道守門守的是【另一種截斷】，
                    出事那一種會讓迴圈在它之前就結束 ⇒ 它到不了
```
🔴 **「有一道守門」與「那道守門在會出事的那條路上」是兩件事,
而它們在 code review 時長得一樣 —— 都是一個看得見的 `console.warn`。**

⚠️ **這比「沒有守門」更糟**:沒有守門時,下一個人可能會去加一道;
**有一道到不了的守門時,他會以為這裡已經有人顧了。**

### 判別句(看到任何 log / warn / alert / 守門格,當場問)

> **我擔心的那個世界跑起來,會經過這一行嗎?**

**不是**「這個條件寫得對不對」,是「**這個條件會不會被執行到**」。
📎 具體做法:把那個世界的**控制流走一遍**,看它在哪一行離開 ——
本例是 `:719` 的 `break`,而守門在 `:705`,**同一個迴圈裡、順序上還在它前面**,
**卻永遠不會同時成立**(`length < PAGE_SIZE` 與 `length === PAGE_SIZE` 互斥,
而 warn 還多要求 `page === 49`)。

### 動作

1. **加守門時,連同「哪一條路會經過它」一起寫進註解。**
   本例該寫的是:「**這道守的是 MAX_PAGES 撞頂;`max-rows` 那一面會讓迴圈在它之前結束 ⇒ 它到不了**」。
2. 🔴 **不要寫成「它沒有涵蓋 X」** —— 那句讀起來像「再加一個條件就好」,
   而真相是**那條路上根本到不了這一行**,要換位置不是加條件。
3. **審查時對每一道守門問一次判別句**,而不是看它存不存在。

📎 與本檔「射程上限只會往上搬一層」那則互補:
那則是**限定句被讀成結論**;本則是**守門被讀成保護**。
**兩者的共通點:讀的人拿到的是一個【安心的訊號】,而那個訊號沒有承擔它看起來承擔的東西。**

## 我們寫**原始碼**的書寫慣例,一路印到了**給倉庫的紙**上〔安靜〕

> 📎 2026-08-18 C 窗 · 紙上文字審查一輪掃出**四則,同一個形狀**。

```
① markdown 星號 **   前人犯過兩次，我今晚第三次（落筆當下自己看到）
② 表情符號 🔴        合計那句開頭 —— 我們寫註解的嚴重度標記
③ 邏輯符號 ⇒         合計旁那句中間 —— 蘊含符號，意思是「所以」
④ 量詞 筆 vs 項      同一張紙上數同一種東西用兩個量詞
```

### 🔴 為什麼它安靜:**這四個東西在原始碼裡都是【有意義的】**

`**` 是強調、`🔴` 是嚴重度、`⇒` 是蘊含、`筆` 是寫的人當下順手的量詞 ——
**在 code 與交接信裡,它們全都讀得通,而且是這個 repo 的日常。**
🔴 **而紙上沒有那個上下文** ⇒ 揀貨的人拿到的是**一個看得到、但讀不懂的東西**:
一顆黑點、一個缺字框、一個他不知道要怎麼唸的箭頭。

⚠️ **而三次都是同一支檔、同一批人寫的** ⇒ **這不是粗心。**
是**寫的人在兩個語域之間切換** —— 註解與紙上文案**寫在同一個檔、同一段編輯裡**。

### 🔴🔴 所以修法不能是「寫的時候小心一點」

**寫的人在那一刻【並不覺得自己在切換語域】。** 他就是在寫這一片,而這一片同時包含
「給下一個工程師看的註解」與「給倉庫員工看的紙」。
⇒ **只有機制擋得住。**

### 機制的形狀:**禁範圍,不禁白名單**

**理由不是偏好,是本 repo 的歷史事故** —— 白名單版在 `shipping-doc` 那片
**被穿透過兩次**(「請重新整理再列印一次」/「麻煩您重新整理一下再列印看看」都全綠)。

```
禁  U+1F300–U+1FAFF   表情
    U+2190–U+21FF / U+27F0–U+27FF   箭頭（⇒ = U+21D2）
    U+2200–U+22FF     數學運算子
而紙上真的在用的兩個符號【本來就不在那幾段裡】：
    ·   U+00B7   規格分隔，紙上 265 處
    ——  U+2014   破折號
⇒ 🔴 不必開例外，也就【沒有例外可以被鑽】
```
📎 而第 ④ 則(量詞)禁的是**「數字 + 筆」這個形狀,不是「筆」這個字** ——
**商品名稱可能真的含「筆」**(油性筆、簽字筆),整字禁會**誤傷真商品**。
🔴 **這一則的判別句:我禁的這個東西,真實資料裡會不會合法出現?**

### 判別句(在同一個檔裡同時寫註解與紙上文案時)

> **這一行字,是寫給下一個工程師看的,還是寫給拿著紙的人看的?**
> 後者 ⇒ **它不能依賴任何「我們這裡的寫法」。**

### 動作(本則)

1. **審查不要 grep 原始碼** —— 會**漏掉組出來的字串**、也會**誤抓註解**(而註解正是這類符號最多的地方)。
   **掃渲染產物**,抽出紙上真的會出現的字。
2. **每發現一種出口,擴進【同一格】守門,不另開新格** ——
   守門數不增加而覆蓋面增加,且下一個人只要讀一格就知道全部禁了什麼。
3. 🔴 **報數字時把「一致」講清楚**:同輪另一個量測是
   「紙上中文字後接的標點:**半形 626、全形 0**」——**那是一致,不是 626 個錯字。**
   **一個數字在報告裡會被讀成什麼,跟它是不是真的,是兩件事。**

## 一張站點表**在被寫下來的當下就開始過期**〔安靜〕

> 📎 2026-08-18 C 窗 · `#629`(一個號一張站點表)。

`#629` 登記的是「code 依賴一個住在伺服器設定裡的數字」。它有三批站點,
而**沒有一處被改**。B 窗立的抬頭句:**「登記不等於處置完畢。」**

🔴 **而追下去發現還有第二層,比那句更難防:**

```
主視窗轉來「8 處」（條列裡卻有 9 條路徑）
我在自己的 checkout 上重跑 ⇒ 10
換到 dev 上、並且把【劃掉版】分開數 ⇒ 12 行 = 待辦 10 + 訃聞 2
   🔴 而其中 2 處是【從來沒有人列過】的 —— A 窗剛進 dev 的新檔
```
⇒ **站點表寫完的那一刻,分母就已經不是那個數了。**
**新增的站點沒有任何機制會通知這張表。**

### 🔴 為什麼它安靜:**一張清單看起來就是一個【完整的集合】**

「站點表」這三個字本身在承諾一件它做不到的事。
讀的人拿到的是**一個有邊界的東西**,而它其實是**某個人在某個時點掃到的快照**。
⚠️ 而**表越完整、越有行號、越可信,它越像已經處理過了** ——
本表每一列都附 `檔案:行號`,**那讓它更像一份結案報告。**

### 🔴 三個數字全部是真的,而沒有一個能拿去當「還剩幾件」

```
8   轉述時把原文的括號「（含劃掉版 2 處）」吃掉之後剩下的
10  我在【比 dev 舊 31 顆】的基底上數的（含訃聞）
12  現在的 dev 上（含訃聞）⇒ 拆開 = 10 待辦 + 2 訃聞
```
🔴 **成因不是誰記錯,是:那個數字是【某個 checkout 在某個時點】的性質,不是 repo 的性質。**
📎 同一時刻 `products` 分支上兩處**已經是劃掉版** ⇒ **「我說還沒改」與「它說已改」同時為真。**

### 判別句(寫下任何「共 N 處」之前)

> **這個 N 是哪一個 checkout、哪一個時點數出來的?**
> 答不出來 ⇒ **那不是一個數量,是一張快照。** 寫進報告時要把那兩件跟著寫。

### 🔴 而這一則是被【它自己那句自指】救到的

上一輪我在表裡寫了一句:
> **「引用站點清單前自己跑一次那支 sweep,不要照抄任何人給的條列 ——【包含本表】。」**

⇒ **這次真的生效了,而生效的對象是我自己的表。**
🔴 **一條規矩第一次擋到的人是寫它的人 —— 這件事本身就是那條規矩該存在的證據。**
(而它同時說明:**寫的人並不因為寫了它就免疫**。同夜另一則:我一邊做文字審查、一邊自己寫出一個量詞不一致。)

### 動作

1. **寫「共 N 處」時,連【checkout + 時點】一起寫。** 沒有這兩樣的 N 是一張快照。
2. **要分「待辦 vs 已改」,不能用原字面** —— 本 repo 的更正慣例是**劃掉不刪**,
   **訃聞裡面也含那個字面**。分法:`git grep -l '<字面>' <ref>` → 逐行判斷含不含 `~~<字面>~~`。
   ✅ **已寫進 `scripts/literal-sweep.sh` 的「掃描限度」輸出第 5、6 條** ——
   **不然每個用它的人都要自己重新發現一次。**
3. **要分「沒改」與「改了但沒進 dev」,只能掃所有 worktree 與所有分支。**
   (2026-08-18 實跑:19 個 worktree + 45 個本機分支 ⇒ 才看得到 `products` 上的劃掉版。)
4. 🔴 **站點表要自己寫上「本表可能已過期,引用前重跑」** —— 包含它自己。

## 修法的範圍,被**當時剛好在痛的那幾處**決定了〔安靜〕

> 📎 2026-08-18 C 窗。**這一則打臉的是本檔上面那條**(「只改被指名那一處」)——
> 而它是那條的**新變體,而且更難防**。

2026-08-18 我診斷出一個根因:
> **同一句話有兩個所有權人(量測管線一份、`page.test.tsx` 一份)⇒ 必然會漂。**

**診斷是對的。而我的修法只改了 4 格,同一支檔裡還有 9 格一模一樣的問題。**

```
13 格在斷言文案字面
我修了 4 格 —— 就是【讓 dev 紅掉的那幾格】（B 態那批）
而我在 commit body 裡把它寫成【根因修法】：「拆掉同一句話有兩個所有權人」
⇒ 🔴 那句話的字面比事實大
```

### 🔴 為什麼它安靜:**那 9 格現在【全是綠的】**

它們**只有在有人去改那 9 句文案的時候才會紅**。
⇒ **這個缺口的觸發條件,是【下一個人做一件正常的事】。**
🔴 **而一個不完整的修法,與完整的修法,在測試輸出上長得一模一樣。**

📎 **它是怎麼被撈出來的**:我去做**別的事**(印文案給 Sean 看)、套上提案之後撞紅
⇒ **不是有人來查我,也不是我回頭複核。** 我複核過的話會複核什麼?
**我會去看我改的那 4 格對不對** —— 而病在**我沒改的那 9 格**。

### 🔴 判別句

> **我修的範圍,是【病的邊界】決定的,還是【剛好在痛的那幾處】決定的?**

⚠️ **這比上面那條難防的地方**:「讓 dev 紅的那幾格」**看起來就是一個合理的範圍** ——
它有邊界、有清單、可以數。**而它是症狀的邊界,不是病的邊界。**

### 動作

1. **診斷寫成「根因」的那一刻,先列出【這個根因總共有幾處】** ——
   **用工具數,不要用「我改到的那幾處」當分母。**
2. **修不完就在【檔頭】寫清單**,而**清單要有行號** —— 「還沒修完」沒有清單等於沒寫。
   ✅ 已做:`page-measure.test.tsx` 檔頭列了那 9 格的行號,
   並寫明「**你如果是因為改文案而紅到這裡:你沒有做錯,是這支檔還沒修完**」。
3. 🔴 **commit body 誇大過的宣稱,更正要落在【會被讀到的載體】** ——
   commit 改不動 ⇒ 落在那支檔的檔頭,不是只寫在信裡。

📎 與本檔「站點表在被寫下來的當下就開始過期」互補:
那則是**清單會過期**;本則是**清單從一開始就只涵蓋症狀**。
**兩者的共通點:一個看起來有邊界的東西,邊界不是它宣稱的那個。**
