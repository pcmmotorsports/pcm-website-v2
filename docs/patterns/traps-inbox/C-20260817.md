## 量的那份頁面裡**沒有我剛寫的 CSS** —— 而症狀長得像「我的 CSS 寫錯了」〔安靜〕

**實例(2026-08-17 夜,C 窗 `#601` 整幅阻印版面)。**

量測管線的 fixture **內嵌的是【建置產物】的 CSS**
(`page-measure.test.tsx` 的 `builtCss()` 去 `.next` 撈 chunk,理由是那才是紙上真的會生效的樣式)。

我加了兩個新的 Tailwind class(`min-h-[170mm]`、`text-4xl`)⇒ 直接跑 fixture、`--png` 開圖:

    看起來「完全沒有生效」——版面與加之前【一模一樣】

**而我的 CSS 沒有錯。** 病是:**那兩個 class 在建置產物裡還不存在**
(Tailwind 是掃原始碼產 CSS 的 ⇒ 沒有重新 build,就沒有那兩條規則)。
`TURBO_FORCE=1 pnpm build` 之後同一份 fixture 一次就對。

### 為什麼它安靜(而且會把人帶往錯的方向)

    直覺結論：「我的 CSS 寫錯了」  ⇒ 接著會去改 CSS、換寫法、加 !important
    真正的事實：「我量的那份頁面裡沒有我的 CSS」
    ⇒ 兩者的【觀測】完全相同：一張看起來沒變的圖。
    🔴 而錯的那條路【有東西可以做】，所以人會一直做下去。

📎 **比「沒生效」更糟的一種**:如果那個 class 剛好**部分**存在
(例如 `text-4xl` 別的頁面用過、`min-h-[170mm]` 沒有)⇒ 圖會**變一半**,
那更像「我的 CSS 只對了一半」。

### 判別句(改樣式之後要量之前,當場問)

> **我量的這份產物,是在我改完之後產生的嗎?它裡面有我剛寫的那個 class 嗎?**
> 用一條命令答,不要用記憶:`grep -c 'min-h-\[170mm\]' <那份 fixture>` ⇒ 期望 ≥1。
> **回 0 ⇒ 先 build,不要改 CSS。**

### 動作

1. **動任何 Tailwind class 之後、量之前:先 `TURBO_FORCE=1 pnpm build`。**
   (`TURBO_FORCE=1` 的理由同 `#524`:少了它,turbo 命中快取會 replay 舊產物。)
2. **量之前先 grep 那個 class 在不在 fixture 裡** —— 那是這一族唯一便宜的量具。
3. 這一條**寫進管線檔頭**(`page-measure.test.tsx` 的用法段已經寫著「要先 build」)——
   🔴 **而我讀過那一段還是踩了**:它寫的是「先 build,它要讀建置產物的 CSS」,
   我讀成「**第一次**要先 build」。⇒ 檔頭那句要改成
   「**每次動樣式之後**都要先 build」,不然它只擋得住第一次。

📎 **同一族的第三個實例(方向不同、成因相同)**:memory
`feedback_vercel-build-cache-served-stale-css` —— Vercel 建置快取送舊 CSS,
**同一顆 commit,線上產物與本機產物不同**。
🔴 **共通母題:量到的產物 ≠ 你以為的產物。** 三個都出現在「同一顆 commit」這個假設之下:
```
本則      我改了 code，而【還沒 build】       ⇒ 量到的產物比 code 舊
Vercel 那則 我 build 了，而【快取送了舊的】    ⇒ 線上產物比 build 舊
（第三種，尚未在本 repo 遇到但同族）
          fixture 是上一輪產的、忘了重產     ⇒ 量到的產物比這一輪舊
          （本窗 2026-08-17 夜差點踩：主視窗拿 18:13 的 fixture 去驗 18:57 落地的功能，
             Sean 因此白印一趟紙 —— 那一發是【人】重用了一條當時正確的路徑）
```
⇒ **判別句對三種都成立**:**我手上這份產物,是在我那個改動【之後】產生的嗎?**
用一條命令答(`ls -l` 的時間戳、或 `grep` 那個新字面在不在產物裡),**不要用記憶**。

## 我驗過**自己的**量法,然後換成儀器 —— **而我沒有再驗那把儀器**〔安靜〕

**實例(2026-08-17 夜,C 窗 + 主視窗 + T 線,同一條鏈上三個人)。**

要量的東西:跑四綠那一刻**有幾個 vitest 在並行**(那是「機器吵不吵」的唯一硬證據)。

### 這條鏈的四步,每一步都看起來是在往上修

```
① 我手打一條： ps -Ao command | grep -c '[v]itest'        ⇒ 回 2
② 我自己抓到它壞了：那 2 個是【我自己的 shell】——
   我的命令列裡就有 vitest 這個字，[v]itest 那個括號技巧
   只避開 grep 自己，避不開【包住它的那個 shell】
   ⇒ 我明說「我沒有一把驗證過的量具，所以我不報那個數字」   ← 這一步是對的
③ merge dev 之後拿到 T 線寫的儀器 ⇒ 它印「並行 vitest 行程數：… 12 …」
   我把 12 報出去，並逐字寫「新儀器量的，不是我手打的」      ← 這一句是誠實的
④ 而那把儀器犯的是【同一個錯】，只是範圍更大：
   dev 上的版本 count_matching '[v]itest'
   ⇒ 撈進【全陣任何窗】命令列裡出現那個字的行程
     （實測的假命中：別窗 grep 的 pattern、別窗一支叫 vitest-sampler.sh 的腳本）
   兩個世界實測：真的有在跑 舊尺 23~25 / 新尺 2
                 沒有在跑   舊尺 ≥3    / 新尺 0   ← 舊尺有【地板】
   ⇒ 那個 12 對應的真 run 數【可能是 1、也可能是 0】。不可換算，只能重量。
```

### 🔴 為什麼它安靜:**一個被信任的量具,會關掉它所有下游的懷疑**

    第 ② 步我【驗了】那把尺 ⇒ 抓到
    第 ③ 步我【換了】一把更好的尺 ⇒ 不驗了
    ⇒ 「換成專用儀器」在直覺上是【提升】，所以它自帶一層豁免

而下游(主視窗)自陳:
> 「你逐字寫『新儀器量的,不是我手打的』,**而我把『儀器量的』讀成了『可信的』**,
> 然後在上面建了三層推論。」

🔴 **傳染路徑很乾淨**:上游驗過自己 ⇒ 改用儀器 ⇒ 上游不再驗 ⇒ 下游更不會驗。
**懷疑在鏈上是單向遞減的。**

### 🔴🔴 第二層,而它比第一層更難防:**誠實的限定,會被讀成保證**

「不是我手打的」這句話的**本意**是**縮小**我的宣稱(我沒有親手算)。
**它被讀成的意思**是**放大**可信度(有專用工具背書)。
⇒ **同一句話,兩個相反的作用。** 而我寫它的時候只想到第一個。

### 判別句(兩條,分別擋兩層)

> **「這個數字是量出來的」只回答了【誰產生它】,沒有回答【它有沒有判別力】。**
> ⇒ 換了量具 = **重新驗一次**,不是**繼承上一把的信用**。

> **我這句限定,在讀者手上是【縮小】還是【放大】我的宣稱?**
> ⇒ 會被讀成放大 ⇒ 那不是限定,是背書。改寫成「**我沒有驗過這把尺**」。

### 動作

1. **任何量具第一次用之前,雙向表演一次**:該有的世界要 >0、該沒有的世界要 =0。
   🔴 **「該沒有的世界要 = 0」是這一族的關鍵那一半** —— 舊尺的病就是**它有地板**
   (沒有 vitest 在跑時仍回 ≥3),而**地板在「有在跑」那一側是看不出來的**。
2. **報別人的儀器讀數時,連「我驗過沒有」一起報。** 沒驗 ⇒ 寫「未驗」,不寫「儀器量的」。
3. **退回一個已經發出去的數字時,連【它撐起的推論】一起點名退**
   (本例:「12 個並行之下全綠」那個反例整條收回,不是只改那個數字)。

📎 與本檔前一則(「量的那份頁面裡沒有我剛寫的 CSS」)同族:
那則是**產物比我以為的舊**;本則是**量具比我以為的鈍**。
**兩者的共通症狀:輸出是一個看起來完全正常的數字。**
