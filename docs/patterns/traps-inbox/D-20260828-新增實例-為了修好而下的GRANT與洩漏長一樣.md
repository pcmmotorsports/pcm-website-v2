# 新增實例:一個為了修好而做的 `GRANT`,與一個洩漏,長得一模一樣

> **投稿窗**:線D(`-69`) · **2026-08-28 夜** · 全程在**拋棄式 PG 17.10** 量,零正式庫、零金鑰。
> **建議落點**:**併進正本 `:19251`**「一道為了**修環境**而下的權限,會弄紅一道**真正的安全稽核**」
> 那一條當第二個實例 —— **同一個母題,而觀測性【相反】**,理由見下方「與上面那次差在哪」。
> ⚠️ **這不是一個待辦項** —— 就算那個方案最後沒做,這條坑仍然成立(它講的是 `security_invoker` 與窄角色互斥這個事實)。

## 判別句
> **一個為了修好而做的 `GRANT`,與一個洩漏,長得一模一樣。**

## 場景(當場量的,不是設想)
要把「經銷價」從另一個 Supabase 專案搬過來,而不能讓它公開。做法是開一個**只讀那一支 view** 的窄角色:
```sql
CREATE VIEW dealer_catalog_v AS SELECT sku, price_store FROM products;  -- products 另有 price_cost
CREATE ROLE pcm_dealer_reader LOGIN PASSWORD '…';
GRANT USAGE ON SCHEMA public TO pcm_dealer_reader;
GRANT SELECT ON dealer_catalog_v TO pcm_dealer_reader;   -- 只有這一支
```
量到(psql 與 node `pg` 兩把客戶端印同一件事):
```
讀那支 view            ⇒ 讀得到
讀底層 products（含成本）⇒ permission denied for table products
讀另一張表 / 寫入        ⇒ permission denied
負對照 不存在的 view     ⇒ relation … does not exist
🔴 負對照那格才是讓上面三個 denied 成立的原因：錯誤訊息【分得出】「沒權限」與「不存在」
```

## 🔴 而家規會把它關掉
本 repo 的 public view 家規是 `security_invoker=true`。當場量:
```
ALTER VIEW dealer_catalog_v SET (security_invoker = true);  ⇒ 窄角色讀 view ⇒ permission denied for table products
改回 false                                                  ⇒ 讀得到（count = 2）
```
**成因**:`security_invoker=true` 讓 view 用**呼叫者**的權限去讀底層表;
而這個設計的前提正是「**呼叫者不能讀底層表**」⇒ **兩者互斥。**

## 🔴 真正的坑不是它壞掉,是【它會怎麼被修好】
```
照家規改成 true ⇒ 同步當場壞掉          ← 會叫，這一步還好
🔴 而最直覺的修法是：GRANT SELECT ON products TO pcm_dealer_reader
   ⇒ 那一刀把【成本價 / 蝦皮價 / 全部欄位】一起開給那個角色
   ⇒ 而【畫面、測試、同步結果】什麼都沒有變 —— 它只是又通了
```
📌 **修好它的那個動作,與把它洩漏出去的那個動作,是同一個動作。**

## 🔴 與正本 `:19251` 那次差在哪(這是本條的價值,不是重複)
```
:19251 那次  一道為了修環境而下的權限 ⇒ 【弄紅】了另一支 migration 的安全自檢
             ⇒ 有訊號，代價是「fail 從 21 掉到 17」這個總數蓋住了它
             ⇒ 修法是【逐項比對】取代【看總數】
本條這次    一道為了修好而下的權限 ⇒ 【什麼都沒紅】，因為它剛好讓事情通了
             ⇒ 零訊號。沒有一個總數需要被拆開，因為沒有任何數字動過
🔴 ⇒ 同一個母題（為了修而下的權限）在觀測性上有【兩種相反的形狀】
   而 :19251 的修法（逐項比對）對本條【無效】—— 沒有東西可以比對
```

## 修法(兩道,而第二道才是真正在守那個洩漏)
```
① 斷言 view 的 reloptions 【不含】 security_invoker=true
   —— 它守的是「家規沒被套上去」
② 🔴 斷言 has_table_privilege('pcm_dealer_reader','products','SELECT') = false
   —— 它守的是【那個洩漏本身】
   📌 而洩漏【可以在家規沒被套上去的情況下發生】（有人單純覺得多給一點比較方便）
      ⇒ 只有①的話，那條路上沒有閘
③ 配一發突變：真的 GRANT 一次 ⇒ ② 必須紅。沒有那一發，②「綠」也可能是它根本沒接上
```

## 查重(兩把尺,逐條看過)
```
尺一 正本標題行 grep（修復|修好|修法|GRANT|權限|洩漏|授權 ⇒ 10 條；「修」⇒ 12 條）
     逐條看過：多數是「### 修法」小節標題（不是條目本身）；真正同族的是 :19251
尺二 traps-neighbours.py：分母 正本 478 + inbox 194 + memory 1025 = 1697
     最高 0.2049（不同族）；:19251 排第 4（0.1800）⇒ 🔴 而它【就是】那一條
     ⇒ 本次工具排名撈到了，沒有落進它自己檔頭那個「排名撈不到」的失效
負對照（標題行 grep 一個現造字面）⇒ 0
```
⇒ **判:併進 `:19251` 當第二個實例,不開新條目** —— 母題相同,而**觀測性相反那一格是新的**。

## 這條【不】保證什麼
```
· 全在拋棄式 PG 17.10 量的，不是 Supabase 託管環境
  ⇒ 權限模型是 Postgres 標準的、兩邊【應該】一致，而「應該」不是「量到」
· 「下一個人會這樣修」是我推的失敗情境，不是觀察到的事件 —— 沒有人真的這樣修過
  🔴 而我判它值得寫，理由是那個修法【是最省的那一個】，不是因為有人做過
```
