## 【補丁 · 不是新條】「空有三種世界」⇒ **有第四種**

> 收件時請把這一格併進 canonical 既有那條(內容含 `空-A` / `空-B` / `空-C`),**不要新開節。**

```
空-A  沒有人在做這件事                    ⇒ 要【建】
空-B  有人在做,而他看的地方是空的         ⇒ 要【改述詞】
空-C  東西寫好了,而沒有接到任何人的路徑上  ⇒ 要【接線】
🔴 空-D  **接線了、也真的跑了,而【那條分支的條件從來沒成立過】**  ⇒ 要【構造一個合格案例】
```

### 空-D 為什麼比空-B 更難抓

```
空-B  集合是空的            ⇒ **看得出來**(scanned: 0、待辦清單空的)
空-D  集合【不是】空的      ⇒ 每一列都被處理了,只是每一列都走了【另一條分支】
      ⇒ 從外面看:它在跑、有輸入、有輸出、沒有錯誤。**只有那一條分支的計數是 0。**
```

### 實例(2026-08-22 線 C,正式庫唯讀)

一支「付款中斷時把單補完」的兜底排程,route 檔頭自己寫著「`settled` 寫入路徑**未被行使、未確認**」。
```
status     n    被兜底碰過的   最多重試   從沒被掃過
charged   10          0            0         10
failed     5          0            0          5
pending    2          2            8          0     ← 🔴 兜底碰過的只有這兩張
```
⇒ 拆成三句,而它們一句是錯的、一句是對的、而對的那句還被誤讀成失敗:
```
① 「未被行使」是【錯的】 —— 認領那一段被行使過 16 輪(2 張 × 8)
② 「settled 寫入段未被行使」是【對的】 —— 0 次
③ 🔴 而 ② 的原因不是「它失敗了」,是【至今沒有一張單符合條件】
   那兩張在金流商那側分別是「尚未授權」與「查無」⇒ **不推它們是正確行為。**
```

### 🔴 判別句

```
「這條分支的計數是 0 —— 是【它跑了而失敗】,還是【它從來沒被走到】?」
分不出 ⇒ 🔴 「它沒救過任何一張單」與「它救不了」在紀錄上長得一樣。

而要分開,唯一的路是**構造一個合格案例**(拋棄式環境做得到)——
🔴 **不是再多等幾天看看**:等待只會累積更多「走了另一條分支」的列。
```

⚠️ **本例的量法限定(必須跟著搬)**:我用 `settle_attempt_count > 0` 當「被碰過」的代理,
而那一欄只在 claim 時遞增。**若有別的路徑會清掉它,那個 2 會偏低 —— 我沒查有無此路徑。**

## 【新條】回 200 之前,有沒有把「還沒做完的事」寫進一個持久的地方?〔母題成員〕

### 判別句(先給)

> **回 200 之前,有沒有把「還沒做完的事」寫進一個【持久】的地方?**
> 有 ⇒ 快速 200 是安全的。
> 🔴 沒有 ⇒ **那個 200 說的是「我收到了」,不是「我做完了」** —— 而對方會照著它停止重送。

### 為什麼這一格特別會出事

```
「盡快回 200,處理放背景」是【對的做法】—— 很多 webhook 供應商明文要求它。
🔴 而它同時是一個【把失敗變成靜音】的做法:
   · 對方收到 200 ⇒ 停止重送 ⇒ 🔴 **重送這道兜底被我們自己關掉了**
   · 背景被砍(逾時 / 記憶體 / 部署換手)⇒ 工作消失
   · 兩邊都沒有紅字:對方看到成功,我們的 route 也回了 200
⇒ **症狀落在【第三方】身上**:客人問了問題,而回覆永遠不會送出去 —— 他看到的是「已讀不回」。
   他不會回報「系統壞了」,他會覺得沒人理他。
```

### 🔴 兩個對照實例(**一個做對、一個做錯 —— 而做對的那個證明它是可行的**)

**✅ 做對的**(2026-08-22 線 C,金流 webhook):
```
step 6  durable insert 進 inbox      ← 🔴 在回 200【之前】
step 7  after() 跑快路徑(best-effort)
step 8  回 200
⇒ 背景被砍 ⇒ 那一列還在 inbox ⇒ 由排程兜底
⇒ 檔頭自己寫著:「after() 是 best-effort、不是 durable queue,最終結算保證不在本 route,在 sweeper。」
```

**❌ 做錯的**(同日,另一條線的 LINE webhook):
```
「LINE 要求 webhook 盡快回 200,否則會逾時重送整批 events。
  防抖含數秒 sleep,故整個處理放背景(waitUntil),立刻回 200。」
⇒ 工作【只】活在背景 ⇒ 30 秒逾時砍掉背景 ⇒ **工作永遠消失**
⇒ 而 LINE 那邊什麼都沒發生:它拿到的是一個很快的 200。
```

### 修法(動作,不是更小心)

```
1. 🔴 回 200 之前,把【還沒做完的事】寫進一個【重開機也還在】的地方(表 / 佇列)。
   ⇒ 判準不是「有沒有 try/catch」,是「**行程被【砍掉】的時候,那件事還在不在**」。
     try/catch 攔不到 SIGKILL / 逾時 / OOM —— 而那三個正是背景工作最常見的死法。

2. 有了持久落點之後,再問第二題:**誰會去撿它?**
   ⇒ 落點沒有消費端 = 本檔「空有三種世界」的空-C。**兩題都要答。**

3. ⚠️ 而「加重試」不是解 —— 對方已經因為那個 200 停止重送了。**重送這道兜底是我們自己關掉的。**
```

### 🔴 它與本檔既有那條「這一欄是【誰】寫的?」是同一句話,第三個載體

```
載體①  排程器的 status 欄  ⇒ 記的是「請求排出去了」,不是「路由回幾號」
載體②  🔴 HTTP 200          ⇒ 記的是「我收到了」,不是「我做完了」      ← 本條
載體③  waitUntil / after()  ⇒ 記的是「我排了背景工作」,不是「它跑完了」
⇒ **同一句判別句、三個完全不同的載體,而三次都是不同的人在不同的地方撞到。**
⇒ 收件時建議互指,不必合併 —— **共通的是判別句,而修法各自不同**
  (①要換欄位 / ②要在回 200 前落地 / ③要有消費端)。
```
