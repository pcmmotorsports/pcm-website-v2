## 一 · 對抗審查有兩個入口會壞,而**兩邊壞掉的樣子都是安靜的**

**(a) 進去的東西被截斷** —— 本窗 2026-08-18 實錘(數法:`wc -l /tmp/cprompt4.txt` ⇒ 4 行、301 bytes,
而正常那份是 120 行)
```
我把 codex 的 prompt 用「雙引號 echo 串接」組出來,而其中一行放了反引號:
  echo "原寫法 `(tr.refundedAmount ?? 0) !== 0` ⇒ …"
⇒ zsh 把反引號當【命令替換】去執行 ⇒ (eval):1: parse error near `!=='
⇒ prompt 檔只寫出 4 行 301 bytes,**diff 完全沒進去**
```
🔴 **危險的不是它失敗,是它失敗的樣子**:這一次 codex 整個沒啟動(輸出檔不存在)所以看得出來;
**但若 codex 有跑、只是拿到一份截斷的 prompt,它會回一份【看起來完全正常】的審查意見 ——
而那份意見審的是空氣。** 而我當時是去查「輸出檔存不存在」才發現的,**不是看它回什麼**。

**(b) 出來的東西不完整** —— 同族的另一個入口(T① 先立)
```
codex 讀完檔就停、沒有列出 findings 段 ⇒ 那叫【沒跑完】,不叫【零 findings】
```
本窗當天也中過:一輪 codex 輸出 837 行全是檔案內容,尾端沒有判定段;
`grep -c 'must-fix'` 得 7 —— **而那 7 個全是它自己 skill 說明裡的字**。

### ⇒ 當場要跑的兩動(不是「更小心」)
```
送出前:wc -l <prompt 檔> 且 grep -c <diff 裡的關鍵字面> <prompt 檔>  ⇒ 兩個都要 >0 才送
收回後:grep -cE '^(PASS|FAIL)' <輸出檔>                              ⇒ 為 0 一律當沒跑完
```
🔴 **prompt 一律用寫檔工具產,不要用 shell 引號組** —— 反引號、`!`、`$` 都會被吃掉,
而 CLAUDE.md 早就寫著「雙引號內禁反引號」(**我讀過那條,當天還是踩了**)。

## 二 · `git checkout --` 對【還沒 commit 的檔】不是還原,是**毀損**

```
我跑完突變要還原,下了:git checkout -- packages/use-cases/src/settle-charge.ts
🔴 而那支檔上面【同時有我的修法(未 commit)與突變】
⇒ checkout 回 HEAD = 把突變與【修法本身】一起丟掉
```

🔴🔴 **而這次沒有出事,是因為權限分類器擋下了那一行 —— 不是因為我想起來。**
**這兩者的下一次結果不一樣**:被擋是外力,想起來才是能力。寫下來是為了讓下一次不必靠外力。
📎 同夜 A 窗踩過同一格(靶檔不乾淨時 `git checkout` 是毀損不是還原)⇒ **本窗是第二次。**

### ⇒ 當場要跑的那一動
```
還原突變【只用反向編輯】(把 mutant 字面換回原字面),不要用任何「回到 HEAD」的指令
還原後:grep -c '<修法的關鍵字面>' <檔>  ⇒ 必須 >0,證明修法還在
       cksum <檔>                        ⇒ 與突變前一致
```
判別句:**這支檔上面除了突變,還有沒有【別的未 commit 的東西】?有 ⇒ 任何回 HEAD 的動作都是毀損。**

## 三 · 測試 fixture 可以造出一個 **production 不會出現的預設形狀**,而它會把守門的入口堵住

```
settle-charge 的 tradeRecord fixture 原本【不帶】 refundedAmount 這一欄
⇒ 全部 happy path 都走在「欄缺」那一路
而 refund-baseline.ts:8 記著 2026-08-03 probe 實測:**未退款紀錄必帶該欄且為 0**
⇒ 🔴 那些格一直在測一個【線上不存在的世界】
⇒ 而正因如此,「欄在且為 0」那條真正的路【從來沒有被任何一格走過】
   —— `(refundedAmount ?? 0)` 那個洞就是躲在這裡
實錘:把守門改成「欄缺 = 停」之後,**31 格紅** —— 紅的全是那些走在不存在世界裡的格
```

🔴 **與 `feedback_green-in-a-world-that-cannot-happen` 是同族,而方向相反**:
```
那條  格在測一個【上游產不出來】的輸入        ⇒ 白測、恆綠、零症狀
本條  🔴 fixture 的【預設形狀】上游必然不會出現 ⇒ 把真正該走的那條路【整個堵住】
⇒ 前者浪費一格,後者【讓守門從來沒有機會響】。後者貴很多。
```

### ⇒ 當場要跑的那一動
```
寫或改 fixture 的預設值時問一句:**這個預設形狀,production 真的會出現嗎?**
有 probe / 實測紀錄的欄位 ⇒ 預設值就照實測寫(例:必帶且為 0 ⇒ 預設就給 0),
要測「欄缺」那個世界的格,【明確覆蓋成 undefined】,不要靠 fixture 剛好沒給。
```

⚠️ **而改 fixture 這件事本身很容易變成作弊**,判別句寫在這裡:
```
✅ 讓 fixture 符合實測現實 —— 條件:①有 probe/實測撐著 ②改完之後,那個洞【仍然被某一格抓得住】
❌ 為了讓測試過而改期望 —— 症狀:改完之後沒有任何一格會因為那個 bug 而紅
```

## 四 · **對的結論配錯的理由**,比錯的結論危險 —— 因為下一個人照【理由】決定範圍

本窗掃「守門被 null 短路」那一族時,pattern 寫成「找 `?? 0`」。
**結論抓對了兩個真洞,而理由是錯的。** 掃到最後一處才發現:

```
apps/admin/src/components/orders/order-detail-route.tsx:236
  cancellationsTruncated={detail?.cancellationsTruncated ?? true}
  ⇒ 不知道有沒有截斷時,倒向【有】⇒ 走安全路徑                 ✅ 正面教材

packages/use-cases/src/settle-charge.ts(修前)
  (tr.refundedAmount ?? 0) !== 0
  ⇒ 不知道退了多少時,倒向【沒退】⇒ 放行                        🔴 洞
```
🔴 **同一個運算子、相反的後果。`??` 本身不是病。**

**正確的判準**:
> **這個預設值,讓守門【更容易響】還是【更不容易響】?**

⚠️ **為什麼這件事要記下來**:我若不更正理由,下一個人會拿「找 `?? 0`」去擴大掃描,
於是 ①把 `?? true` 這種正面用法報成洞(假陽性稀釋真的那幾處)
②漏掉不用 `??` 但方向一樣錯的寫法(`if (x !== null && …)`、`x?.foo === bar`)。
⇒ **結論對而理由錯的時候,錯的那一半會【被繼承】,而對的那一半不會。**

### ⇒ 當場要跑的那一動
```
報一族 finding 時,除了「命中幾處」,另寫一行:**我這個 pattern 憑什麼認為它抓的是病?**
若答案是「因為它長這樣」⇒ 不夠;要能答「因為它讓守門在【某個真實狀態】下不響」。
答不出來 ⇒ 那個 pattern 抓的是【形狀】不是【病】,報告要明講,不要讓讀者以為方向也判過了。
```

📎 相關但**不是我能改的**:主視窗要求把這條補進 `V-051 立場表`(V 窗的檔)與收割時的全表。
**本窗沒有動那兩份**,只在這裡留指標。


🔴 **我拿【對 I 窗的承諾】去回答【能不能 commit】,而真正的約束是 V 窗的複驗。**

### ⇒ 當場要問的那一句

## 七 · **一個命名規則,在「同一類角色同時存在兩個」的時候還唯一嗎?**

```
traps 命名慣例  <窗>-<日期>.md
2026-08-18 同時有兩個 T 線窗(T① socket 32075 / 本窗 5681)
⇒ 兩份都叫 T-20260818.md ⇒ git merge-tree 報 CONFLICT (add/add)
⇒ 而是【收割時】才發現,不是寫的時候
```

🔴 **它與 README 記的那次(路徑少寫 `docs/patterns/` 前綴)是【不同的病】**:
```
那一次  寫錯地方        ⇒ 人的疏忽 ⇒ 提醒有用
這一次  慣例本身不唯一   ⇒ 🔴 **提醒沒有用,因為兩個人都【照著慣例做】**
```
⇒ **兩個人都沒有做錯,而結果是撞的。** 這種病寫在守則裡沒有效果 —— 讀的人會覺得「我照做了啊」。

📎 **而它今晚早就有先例**:主視窗自己說過「**窗名是雜湊、會撞、會被 reload 洗掉**」
⇒ **同一個病在【窗的身分】上發生過,現在在【它們的產出檔名】上再發生一次。**

### ⇒ 當場要問的那一句
```
**這個命名規則,在【同一類角色同時存在兩個】的時候還唯一嗎?**
不唯一 ⇒ 名字裡要有一個【該角色自己知道、而別人不會撞】的東西(socket、序號、任務名)
```

⚠️ **而解衝突的人不該替人改名**(I 窗的立場,我認同):
**「哪一份該改名」是【命名慣例】的問題,不是【內容取捨】的問題 —— 改名的人必須知道自己是誰。**

## 八 · 找錯地方的零命中,**可能漏報,也可能【誤報】** —— 而我是在【審查中】撞到後者

本窗在審 C 窗的 diff 時,要驗「那句文案的所有權有沒有真的搬到 `page.test.tsx`」。

```
我下:git show <hash>:apps/admin/src/app/orders/[id]/shipping/[shipmentId]/page.test.tsx
     ⇒ 回 0 行(路徑少了 app/print/)
而我當時正在問的問題是「文案還有沒有人守」⇒ 🔴 0 剛好長得像「沒人守」
⇒ 我差一點寫出一條 must-fix:「所有權消失了,這是放寬不是對準」
真相:正確路徑下該檔有 **108 條文案斷言**,所有權好好地在那裡
```

🔴 **收束句:分母錯的時候,零命中看起來跟真的一樣。**

📌 **而 E 窗那條(「0 命中的第一個假設應該是我找錯地方」)講的是【漏報】** ——
**本條補的是另一半:在【審查】情境裡,同一個錯會變成【誤報】。**
```
找錯地方 ⇒ 我在找東西時    ⇒ 漏報(以為沒有,其實有)
         ⇒ 我在審東西時    ⇒ 🔴 誤報(以為缺了守門,其實守門好好的)
⇒ 而誤報比漏報更貴:它會讓作者去「修」一個沒壞的東西,而且消耗掉審查的信用。
```

⚠️ **而救我的不是任何規矩,是「0 行這個數字太不合理」的直覺** ——
一支 1000 行等級的測試檔不可能是 0 行。**直覺不可靠,所以要把它變成規矩:**

### ⇒ 當場要跑的那一動
```
零命中而【那個零讓你意外】⇒ **先驗路徑,再驗 pattern,最後才下結論**
  路徑:test -e <路徑> 或 git ls-tree -r --name-only <ref> | grep <檔名>
  pattern:拿一個【你確定該命中】的字面試一次(正向對照)
🔴 三步做完之前,那個 0 不進報告 —— 尤其當它會變成一條【指控別人的 finding】。
```
