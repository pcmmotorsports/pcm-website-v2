## 發生什麼

我在一支 hook 裡埋 TEMP-PROBE 量「effect 重入幾次」:
```ts
g.__P.effect = (g.__P.effect ?? 0) + 1;
if (g.__P.effect > 40) throw new Error('TEMP-PROBE 重入 ' + JSON.stringify(g.__P));
```
跑整支測試檔 ⇒ **31 格裡 23 格丟出那個 throw**。我差一點寫成「**23 格都在迴圈**」。

## 🔴 真相:計數器是【整支檔累加】的,沒有在每一格之前歸零

⇒ 第一格真的跑到 41 之後,**後面每一格都在進門的第一行就丟**。
⇒ 那 23 格裡**有幾格真的迴圈?那一發答不出來。**

## 🛑 它壞掉的方向,才是要記的東西

· 它**不是**印一個明顯的錯誤 —— 它印的是**一個更嚴重版本的正確答案**(真的有迴圈,只是沒有 23 格)。
· 而我當時**正在找迴圈** ⇒ 📌 **一個確認我假設的讀數,比一個推翻我的讀數更難被懷疑。**
· **第二個受害者**:我拿它去驗一個假設(「`useRouter` mock 每次回新物件」),
  把 mock 改成穩定物件 ⇒ **照樣 23 格紅** ⇒ 我因此**否決了一個其實根本沒被測到的假設**。
  ⇒ 🔴 **那一發「驗證」完全無效,而它讓我少查了一條路。**(真正的兇手後來量出來是 `cascade`。)

## ✅ 判別句(下次埋計數器之前問一次)

> **這個計數器的【生命週期】,是不是就是我想量的那一段?**

· 量「一格測試裡發生幾次」⇒ 必須在 `beforeEach` 歸零。
· 量「整支檔累計」⇒ 就不要拿它當**每格**的門檻。
· 🔵 **最便宜的自檢:讓它印出來的東西自帶分母。**
  我那一版只印 `effect:41`;若它印 `effect:41 / 這是第 3 格`,我當場就會看見不對。
