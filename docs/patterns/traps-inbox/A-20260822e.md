## 🔴🔴 一段【有充分理由】的程式碼被搬到理由不成立的地方 —— 而理由**跟著搬過來了,還是讀起來很有說服力**(2026-08-22 線 A `-86`,具名自寫)

> **一句話**:它在原地是對的。搬過去之後**一個字都不用改就會運作**,
> 而**它變成了一個缺陷** —— 因為變的不是 code,是**它周圍那個世界**。

## §1 當天發生什麼

主視窗要我評估「後台加一顆『寄密碼重設信』的鈕」。而顧客站早就有同樣的功能。

`apps/storefront/src/app/login/forgot/actions.ts:38-42`,**刻意吞掉所有錯誤**:

```
寄信成功 / 帳號不存在 / AuthError（含 rate_limited)一律回同一形狀,
不上洩任何差異（連錯誤本身都不看一眼、故意不判斷 e 的內容)
```

**那段註解是對的。** 顧客站那張表單是**公開的** —— 任何人都能拿它一個一個試 email,
從回應的差別讀出「這個帳號存在」。所以它必須沉默。**那叫帳號列舉防護。**

🔴 **而把同一段搬進後台,那顆鈕會在寄失敗的時候照樣說「已寄出」。**

### 而它在後台不該沉默,理由是**量得出來的**

```
顧客站沉默的理由 = 公開表單, 誰都能拿它探帳號
後台   那個理由【不成立】—— 操作的是已登入員工, 他手上【本來就有客戶名單】
⇒ 沒有東西可洩漏 ⇒ 🔴 沒有理由沉默
⇒ 而沉默的代價在後台【變成純虧損】:員工以為信寄出去了, 客人在等一封不存在的信
```

## §2 🔴 為什麼它特別容易活下來:**註解會跟著搬,而且它仍然很有說服力**

這是本條與一般「複製貼上缺陷」最不一樣的一格。

```
一般的複製貼上缺陷 ⇒ 到了新地方會【壞掉】或【長得突兀】, 有機會被看見
本條             ⇒ 到了新地方【完美運作】, 而且旁邊附著一段
                    寫得很好、講得很清楚、而且【在原文脈絡下完全正確】的理由
```

🔴 **越是寫得好的註解,越容易被整段搬走 —— 而註解正是那個不能搬的東西。**

⇒ **一段程式碼的可攜性,和它的理由的可攜性,是【兩件事】**;
   而我們平常只檢查前者(「這段能不能編譯 / 能不能跑」),
   **後者沒有任何機械形態**。

## §4 🔴 與 ㉓ 的關係:**本條是 ㉓ 那條修法的邊界**

㉓ 的修法是:**「引用別人的結論時,連範圍一起引」**。

🔴 **而本條的範圍【已經一起搬過來了】** —— 那段註解本身就把適用條件講得很清楚
(「不上洩任何差異」「連錯誤本身都不看一眼」)。

```
㉓   的病 = 範圍在【搬運途中】掉了       ⇒ 修法 = 把範圍一起搬
本條 的病 = 範圍【完整搬到了】, 而       ⇒ 🔴 修法【失效】:
            那個範圍在新地方【不成立】       搬得再完整都沒用, 要問的是別的問題
```

⇒ **「連範圍一起引」防得了省略,防不了【範圍本身換了世界】。**

## §4b 🔴 與「守門只驗被擋住」那條的關係:**本條是它的【上游】,而修法不一樣**

那條(`:5574`)講的是:守門只斷言了安全那一半,**可用性那一半沒有人在驗**。
它的實例與本條的症狀**一模一樣**:員工做了一個動作,而畫面不告訴他失敗了。

🔴 **但它預設那個沉默是【被忘記的】。本條的沉默是【被決定的】,而且決定得有道理。**

```
:5574  病因 = 沒有人想到要驗那一半     ⇒ 修法 = 補一格斷言（它補了 r=denied, 突變恰好 1 紅)
本條   病因 = 有人【刻意】選了沉默,     ⇒ 🔴 修法【相反】:補斷言會把缺陷【焊死】
              而那個選擇在原地是對的        —— 因為原地的測試正在斷言「失敗要回同一形狀」
                                            ⇒ 照抄那格 ⇒ 綠, 而它在保護這個缺陷
```

⇒ **同一個症狀,兩種相反的處置。** 分辨它們的問題不是「畫面有沒有講」,而是:
> 🔴 **這個沉默,是沒人想到,還是有人寫下了理由?**
> **有理由 ⇒ 去讀那個理由,別急著補斷言。**

## §5 判別句(落筆當下就問得出來)

> 🔴 **我搬的這段 code,它的理由在新地方【還成立嗎】?**
> 📌 具體問法:**那段註解裡的「因為」後面那句話,拿到新地方念一次,還是真的嗎?**

而它有一個**更好操作的版本**,因為它逼你講出一個具體的人:

> 🔴🔴 **這段防護在防【誰】?那個人到得了新的這個地方嗎?**
> ```
> 顧客站:防【任何路人】     ⇒ 到得了（公開表單)
> 後台  :同一個路人         ⇒ 🔴 到不了（要先登入)⇒ 防護對象不存在 ⇒ 防護變成純成本
> ```

## §6 動作

```
· 搬任何【帶著安全 / 隱私 / 防濫用理由】的程式碼之前, 先把那個理由念出來,
  問「這句話在新地方是真的嗎」—— 🔴 而不是問「這段 code 對不對」
· 🔴 搬過去之後, 那段註解【必須改寫】—— 留著原文比刪掉更糟:
  它會讓下一個人以為這裡也想過同一件事
· 若判定理由不成立而拿掉防護, 在新的那段寫明【為什麼這裡不需要】,
  並指回原處 —— 否則下一個人會「發現漏洞」再把它加回來
```

## §7 ⚠️ 本條答不出什麼

```
· 🔴 這個缺陷【還沒有發生】—— 後台那顆鈕還沒有人寫。
  本條是在【搬之前】抓到的, 所以我沒有「它真的害了誰」的實例。
  ⇒ 這是一條【預測】, 不是一份事故報告。引用時不要升級它。
· 我沒有掃過 repo 裡【已經發生過】這個形狀的地方 —— 那會是一次獨立的清點,
  而它的難處正是本條的主題:🔴 那些地方全都在正常運作, 沒有東西會紅。
```
