## 條 F · **一個功能可以做完、通過驗收,然後在下一個週期靜靜失效**【安靜】

> 母題:`:12989` 那條的**功能層版本**。那條講守門,這條講**產物**。

### 當天發生什麼(2026-08-22,線 A 在排「上傳商品圖片」的第一步時)

我本來要寫「第一步 = 接 Supabase Storage」。**而商品明細頁自己講了一句話,把那個順序推翻了**
(`apps/admin/src/components/products/product-detail.tsx:197-198`,逐字):

> 圖片這一項**沒有「鎖住不給改」的機制** —— 只有「來源那天沒給值就不覆蓋」那一層,
> **擋不住供應商換圖**。

同一段還寫著:**多數商品每天會被覆蓋一次**。

⇒ **如果先做上傳功能:**
```
Day 0  員工上傳一張圖 ⇒ 畫面正確 ⇒ 驗收通過 ⇒ 這一片收工
Day 1  供應商同步管線跑過去, 那一格有值 ⇒ 覆蓋
       🔴 沒有錯誤、沒有紅、沒有告警。圖就換回去了。
Day N  某個客人或員工發現圖不對 ⇒ 而【沒有人會把它連回那一片】
```

### 🔴 這一族與「守門失效」的差別:**它連一個曾經正確的時刻都有**
```
恆真守門       從來沒對過   ⇒ 還有機會被問「它會不會紅」
守門後來失效   曾經有履歷   ⇒ :12989 那條
🔴 功能後來失效 【驗收當天是真的對的】—— 它有截圖、有測試、有人肉眼看過
               ⇒ 而失效發生在【驗收之後的某個週期】, 那時已經沒有人在看
```
📌 **驗收是一個時點,而覆蓋是一個週期。** 用時點的證據去保證週期上的行為,**中間永遠有一段沒有人看。**

### 判別句(排一片工之前問)
> **我做出來的東西,產物住在誰的地盤上?那個人多久來一次?**

```
住在【只有我寫】的地方        ⇒ 一般情況, 不必特別處理
🔴 住在【別的程式也會寫】的地方 ⇒ 先答:誰贏?怎麼標?被蓋掉的時候有沒有訊號?
   —— 而這三題【必須在做之前答】, 因為做完之後那三題會變成「已知問題」而不是「阻擋條件」
```

### 而它的處置**不是加測試**
測試跑在 CI 上,而覆蓋發生在**正式站的排程裡** ——
**任何在 CI 裡跑的東西都證明不了「明天早上那張圖還在」。**
```
✅ 可行的三種（由弱到強):
   ① 做之前先決定【誰贏】, 並且把那個決定寫進【同步管線那一側】, 不是只寫在上傳那一側
   ② 產物加一個【來源標記】（這張圖是人上傳的 / 是同步來的)⇒ 被蓋掉時看得出來
   ③ 🔴 最強的:讓同步管線【不能】覆蓋人工來源 —— 那是機制, 前兩種是約定
```
📌 **而 ① 與 ③ 的差別是今晚一直在講的那件事**:①是「我們說好」,③是「它做不到」。
📎 而 ③ 那種做法有一條 memory 專門在講:`feedback_look-for-the-path-that-dissolves-the-question`
   ——「**先查有沒有一條讓這個題目不成立的路**」。**這裡就是那種路:讓「誰贏」不再是一個要記得遵守的約定。**

### 這一條擋得住什麼
一整族「**做完了、驗收過了、而它在某個週期後不算數**」的工。
🔴 **而這種工最貴的地方不是白做,是它會被記成【已完成】** ——
下一個人估工時會跳過它,而使用者持續遇到那個問題。

  🔴 所以它是**風險,不是事故**(而「一條規則配一個假實例,比沒有實例更糟」——
