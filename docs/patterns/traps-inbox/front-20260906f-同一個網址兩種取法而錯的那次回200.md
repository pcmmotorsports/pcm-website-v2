## 發生什麼

我要驗一個剛上線的改動:打 `/products?search=GILLES TOOLING` 時,server 會不會 `redirect()` 成 `?pbrands=gilles`。
我用**最方便的那條路**量:
```js
const r = await fetch(`/products?search=${encodeURIComponent(q)}`, { redirect: 'follow' });
r.redirected // ⇒ false
r.url        // ⇒ /products?search=GILLES TOOLING   ← 沒有跳
```
**三個品牌三發都這樣** ⇒ 我差一點回報「**n-gram 那片沒有生效**」。

**改用真的瀏覽器導覽同一個網址** ⇒ **當場跳到 `/products?pbrands=gilles`**,50 筆全是那個品牌。

## 🔴 它為什麼特別難抓

· **不是錯誤**:`fetch` 回 **200**,不是 404、不是 500、不是逾時。
· **不是空的**:它回了 **32,516 bytes 的合理 HTML**(三發的長度還幾乎一樣 —— 那本身就是個線索,而我當下沒讀出來)。
· ⇒ 📌 **它是一份「看起來完全正常」的答案,而那個答案與事實相反。**
· 🎯 **成因在 RSC / router 快取那一層**:`fetch` 與**文件導覽**在 Next 的 App Router 上**走的不是同一條路**
  (⚠️ 這一句我**沒有深挖到機制層**,標**未確認**;確定的是**兩者給出相反的結果**,那是量到的)。

## ✅ 判別句

> **量「使用者會看到什麼」時,用【使用者的那條路】—— 不要用一個更方便的替身。**

🔵 而**替身有一個共同的外觀**:它比較快、比較好寫、而且**它回得出東西**。
🛑 **第二句更重要**:**替身給出的否定結論,永遠要用真路徑再打一次才算數。**
　 —— 肯定結論比較安全(它至少走通了一次),**否定結論才是替身最會騙人的地方**。

## 🔴🔴 第二次實錘(2026-09-07,線 `-f3` 自己再踩一次)—— **而這一條規矩【當時已經寫在這裡了】**

**同一個病、換一個受詞**:昨天是 `fetch` 對 `?search=<品牌>` 的 `redirect()` 失明;
今天是 **`curl`** 對 `?search=煞車` 的 `redirect()` 失明。

```
curl  /products?search=煞車  ⇒ 200 / 34,377 bytes / 內容是「商品目錄」的殼、零商品
真瀏覽器 同一個網址          ⇒ 轉到 /products?categories=拉桿與把手 · 煞車離合器拉桿
                              ⇒ **1,138 件商品**、50 張卡
```
`排氣管` 同款 ⇒ 轉到「排氣系統 · 尾段排氣管(Slip-On)」⇒ **376 件商品**。

🎯 **它為什麼比昨天那次更貴**:我用那個假讀數**連跑了五輪逐段排除**,每一輪都量得很扎實 ——
`RPC_ID_CAP=1000`(推 dev→main 上線才推翻)· `count:'exact'` 逾時 · `.in()` URL 過長 · anon RLS · 權限。
**每一輪的結論都對, 而它們排除的都是【不存在的病】。**
⇒ 而我還把它寫成**擋上線**的板列(`⟦search-CJKZERO1⟧`),端出「客人找不到商品 = 買不到」。

🛑 **連帶的第二個誤讀**:我一直說「**連 log 都沒有 ⇒ 那一發死掉了**」。
**真相是 `redirect()` 用丟例外實作 ⇒ 寫在它後面的 `[searchByKeyword]` / `[catalogRoute]` 兩行【本來就不會執行】。**
⇒ 📌 **那不是「死掉沒留痕」, 是「本來就不印」** —— 而這件事 memory
`reference_next-redirect-throws-so-cleanup-after-it-is-dead-code` **也早就記過了**。
