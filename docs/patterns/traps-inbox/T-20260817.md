## 一、量具在【成立】與【不成立】兩個世界印同一個東西 —— 一晚七次,七種偽裝〔安靜〕

**判別句(舊):我這把尺,在「成立」與「不成立」兩個世界,會不會印不同的東西?先餵一發證明它會。**
🔴 **判別句(本晚新學到的、補在後面):先看它的【分佈】,不要只看它在我這一發印了什麼。**

> 這一節是**同一個病的七個實例**,刻意並列不拆開。
> 🔴 **其中三個(5/6/7)是【同一把尺的三個版本】** —— 那個演進本身是最好的教材:
> **每一次我都以為修好了,而下一次的偽裝都不同。**
> **七次我都是「認真的」** —— 有量法、有數字、有的還做了兩個世界的對照。
> **每一次的偽裝都不同,而判別句都是同一句。**

### 實例 1 · 區段標題被當成結論(`changed in both`)

收割判準 B② 用 `git merge-tree <base> <a> <b> | grep -c 'changed in both'` 當「衝突預演」。
自造拋棄式 repo,兩個世界各餵一發:

| 世界 | `changed in both` | 真的 `git merge` |
|---|---|---|
| 同一檔、**不同段** | **1** | ✅ 併得起來 |
| 同一檔、**同一行** | **1** | 🔴 撞了 |

⇒ **兩個世界同一個數。** `changed in both` 是**區段標題**(「這個檔兩邊都動過」),不是「會衝突」。
**偽裝:那個字串長得像結論。**

### 實例 2 · 在玩具上驗過了,而玩具沒有真實情境的形狀(`<<<<<<<`)

我把實例 1 更正成 `grep -c '<<<<<<<'`,**並且在自造的兩個世界上驗過它會分辨**(0 vs 1)。
**隔一批再用,它說 2,真 merge 零衝突。**

| 量法 | 玩具:改不同行 | 玩具:改同一行 | 玩具分得出來 | **真 repo** |
|---|---|---|---|---|
| `grep -c 'changed in both'` | 1 | 1 | ❌ | ❌ |
| `grep -c '<<<<<<<'`(舊三參數形式) | 0 | 1 | ✅ | 🔴 **假警報(說 2,實際 0)** |
| `git merge-tree --write-tree A B` 的 **rc** | 0 | 1 | ✅ | ✅ **與真 merge 一致** |

🔴 **成因**:舊三參數形式做的是 **trivial merge**(無 rename 偵測、不走 `ort`)。
我的玩具是**線性三行、從來沒 merge 過**,而我真正要量的分支**基底裡有一顆 merge commit**。
**偽裝:我做了雙向表演,而且過了。** ⇒ **雙向表演過關 ≠ 量具在真實場景準確。**
**現行建議:** `git merge-tree --write-tree <dev> <界線> >/dev/null 2>&1; echo "rc=$?"`(`0`=可併)。
**不要接管線去數字串** —— 這整條教訓就是「數字串」數到的是別的東西。

### 實例 3 · 痕跡會跟著它記錄的東西一起消失(stash reflog)

`#625` 要判「主樹三個未追蹤檔是不是被 `git stash -u` 移走又 `pop` 回來」。
本來要寫:「`git stash list` 空、`.git/logs/refs/stash` 不存在 ⇒ **沒有人 stash 過**。」
**落筆前先驗那把尺**(拋棄式 repo):
```
stash 之前            .git/logs/refs/stash  不存在
stash -u + pop 之後   .git/logs/refs/stash  🔴 仍然不存在
```
⇒ `pop` 丟掉 stash 條目時**連 ref 與它的 reflog 一起收掉**。
**偽裝:一個「查無紀錄」讀起來像「沒發生過」。**
📎 同族 memory `feedback_the-monitor-goes-silent-with-what-it-monitors`。

### 實例 4 · 為了回溯補一個沒被記錄的欄位而造的代理指標(區間重疊數)

`#618` 要問「紅的那幾發是不是併發造成的」,而**舊的 25 發沒有記併發數**(儀器當晚才裝)。
我造了代理指標:每發都有起始時戳與 `Duration` ⇒ 算**區間重疊數**。
```
區間重疊數   紅:min=0 中位=0 max=0
             綠:min=0 中位=0 max=0
```
🔴 **兩組都是 0。** 成因:**那 25 發全是【同一個窗】的循序 run**,彼此**天生不重疊**;
真正造成併發的是**別的窗那些從來沒被搶救的 run**。

⚠️ **它會怎麼害人**:那個 0 完全可以被寫成
> 「紅的那幾發區間重疊數是 0 ⇒ **併發不是原因**」

**一句有數字、有量法、看起來很嚴謹的話,而它是反的 —— 它會推翻一個可能是對的假說。**
**我只差一步就寫出來了 —— 差的那一步是【把兩組的分佈都印出來】。**
**偽裝:創造感。** 「原始欄位沒記,我用別的算出來」那個成就感,
會蓋掉「**它算得出來 ≠ 它量得到差異**」這個問題。

### 實例 5 · 「這個數字是儀器量的」回答了【誰產生它】,沒回答【它有沒有判別力】

**跨窗傳染,而傳染路徑本身是這一則的重點。**
```
C 窗先用手打的 grep -c '[v]itest' ⇒ 自己抓到它壞掉（很好）
⇒ 它改用「儀器」(我寫的 RUN-CONTEXT)，並逐字寫「新儀器量的，不是我手打的」
⇒ 主視窗把「儀器量的」讀成「可信的」，據此寫了三層推論
⇒ 而那把儀器是【我】寫的，而它壞掉的方式跟 C 窗剛剛抓到的【是同一種】
```
🔴 **一個被信任的量具,會關掉它所有下游的懷疑。**
主視窗原字自陳:**「這個數字是量出來的」只回答了【誰產生它】,沒有回答【它有沒有判別力】。**
⇒ **動作**:引用別人的儀器數字時,問一句「**那把尺驗過嗎?驗的是哪兩個世界?**」——
**「它是自動量的」不是答案。**

### 實例 6 · 你越把一個字面寫清楚,它越會出現在不該出現的地方

**同一把尺的第二版,而這次的污染源是【我們正在討論它】。**
I 窗當場量到:**零個真 run,而 `pgrep -f '[v]itest\.mjs'` 讀到 5** ——
```
3 個  它自己的 zsh（同一條命令裡 echo 了一段含該字面的解釋文字）
2 個  別窗的 codex（🔴 prompt 文字裡有那個字面）
🔴 而我自己也做過同一件事：我請 codex 審這把尺，prompt 裡就寫著那個字面
   ⇒ 我一邊量它，一邊把它的讀數推高
```
🔴🔴 **這把尺的地板高度 = 現在有多少人正在打字提到它** ——
**而討論強度【在事故當天最高】。** ⇒ **最糟的一種噪音:它與調查的力度正相關。**
📌 I 窗自陳:**「我是在寫『怎麼避免這個坑』的那一條命令裡踩到這個坑的。」**
📎 判別句(I 窗抽,主視窗核可):
> **命令列是【任何人都能寫進去的字串】,而執行檔名與檔案系統不是。**
> **凡是從 `ps`/`pgrep` 的【命令列】數東西,你數的是「誰提到過它」,不是「它在不在跑」。**

**⇒ 修法不是把字面再收窄(那只是把地板降低),是換一種不靠字串的證據:**
標記檔 —— **只有真的有那一發 run 才會存在的東西**,而且**不需要任何人記得任何事**。
(現行第三版就是這個;它換了一種瞎:只數走那支腳本的 run,已寫在欄位名與檔內限定。)

### 實例 7 · 一把「會跟著世界動、但單位是錯的」尺,比完全不動的尺更難發現

I 窗複驗第一版時,補上了我漏掉的**主污染項**:13 個命中裡
**10 個是【同一發 run 的 worker 行程】**、1 個是真 runner、2 個是 shell。
⇒ 我列的兩類(別窗 grep 的 pattern、`vitest-sampler.sh`)成立,**而在它那一發裡是小項**。
🔴 **重點不是誰列得對,是【兩者都不是「run 數」這個單位】。**
🔴 **而 worker 數會跟著 run 數一起動** ⇒ **舊尺看起來「有反應」** ——
它在雙向表演裡會過,因為它真的會隨世界變化,**只是變化的單位不是你要的那個**。
⇒ **動作:雙向表演之外,再問一句「它的【單位】是什麼?」**
   驗法=**造兩個獨立的個體**,那個數必須是 2(現行格25-b 就是這一格)。
   📌 它解掉了一個真實的分歧:同一時刻**我報 2、I 窗報 1**,
   而字串尺量的數字**沒有人分得出那是「兩發 run」還是「一發兩個命中」**。

### 這七個實例的共同動作

1. 🔴 **任何要寫成「沒有 / 查無 / 零命中 / 沒有關聯」的檢查,先餵一發【該命中的】證明它會亮。**
   **本節七個實例裡,五個是靠這一步當場擋下的**(實例 2 是唯一漏出去的,而它漏出去正是因為
   **我以為我做了這一步** —— 我做了,只是樣本不像真的)。
2. 🔴 **代理指標:第一件事是印【兩組】的分佈,不是印你關心的那一組的值。** 兩組同值 ⇒ 當場作廢。
3. **驗量具的樣本要帶上真實情境的結構特徵**(這裡是:基底含 merge commit、多次來回、多來源)。
4. **能直接問工具「會不會撞」就不要自己解析它的輸出** —— **rc 是工具的結論,字串是工具的中間值。**
   📎 memory `feedback_pasting-intermediate-values-hides-your-own-arithmetic`。
5. **代理指標作廢時,寫下它為什麼瞎**(這裡是:資料集來源單一 ⇒ 結構上不可能有重疊),
   下一個人才不會再造一次同一個。**回溯補欄位失敗是正常的**,正解是把欄位加到儀器上往前收
   (已做:`RUN-CONTEXT`),不是硬從舊資料裡榨出一個數。
6. 🔴 **給出去的建議被推翻時,要去改【收訊者會讀的那份檔】,不是補一封信。**
   本節兩次更正都同步改了 `T-004` 交件信 §②(收割窗收件時會讀的那份)。
   **而前一版的錯誤建議刻意留著加作廢註記** —— 刪掉的話,讀者會以為只錯過一次,
   **而「錯了兩次、第二次是在自以為驗過之後」才是這一節的重點。**

## 二、「突變沒紅」有兩個世界,而報告上長得一樣〔安靜〕

**判別句:我這一發突變,有沒有【證據】證明它真的執行了?**

「跑完了、沒有任何一格紅」可以是兩件完全相反的事:
```
世界 1  斷言沒有判別力     ← 我以為我在量的
世界 2  突變本身根本沒跑起來（語法錯／注入位置錯／檔被改壞）
```
**而報告那一欄印的是同一句話。**

**實例(`#620` 突變 M19)** ——
```sh
awk '/^  case "\$rx_dir" in$/ { skip=3 } skip>0 { skip--; next } { print }' "$B" > "$T"
```
`skip=3` 刪掉 `case` 那行與兩個分支,**把 `esac` 留下來** ⇒ 孤兒 `esac` = 語法錯
⇒ **整支跑不起來** ⇒ 零 `FAIL` 行 ⇒ 我的報告印出:
```
實得:🔴🔴 零紅(這一發沒有任何格擋住 = 那道斷言沒有判別力)
```
**那句話是假的,而它讀起來像一個很嚴肅的發現。**
🔴 **抓到它的不是報告,是它同時留下的兩個垃圾目錄**(`3/` 與 `7/`,另一個 bug 的產物)。
**如果那一發剛好沒留下副作用,我會把一道好的守門當成廢的拆掉。**

**為什麼它安靜**
- 突變測試的心理預期是「應該要紅」⇒ **沒紅**會被自動歸因到「斷言不行」——
  **確認偏誤的方向剛好與錯誤的方向一致。**
- `sh script.sh --selftest || true` 把 rc 吃掉,**語法錯與「跑完沒紅」回同一個 rc**。

**動作(做進 harness,不是「記得」)**
1. 每一發突變**先驗它跑起來了**:語法錯的 rc(通常 2)與「跑完全綠」(0)**分得開**,報告要印那個 rc。
2. 更便宜的一道:**突變後先數總格數**;`合計 PASS=n` 那一行不見了 ⇒ 它根本沒跑到結尾。
3. 🔴 **「零紅」永遠不可以直接寫成結論** —— 它是「要再查一次」的訊號,不是一個發現。

🔴 **同一個坑在【寫下來之後】又犯了一次(22:3x,同一晚)**
我做 `M29`(把 `vitest_mark_begin` 從 `four_greens` 拿掉)時,又寫成
`grep -v '^  vitest_mark_begin$' "$B"` 掃整份檔案 ⇒ **連格25-g 自己那一行也刪掉**
⇒ 紅的是 **格25-g** 不是我預期的 **格25-j** ⇒ **紅的理由被污染。**
**我一小時前才把這個坑寫進本檔(canonical `②-b`),而我照樣犯。**
⇒ 📎 那正是 memory `feedback_written-down-is-not-enforced` 與
`feedback_knowing-rule-is-not-executing-rule` 的當日第 N 次:
**寫下來不等於不會再犯 —— 抓到它的是「紅在哪一格與我預期的不同」,不是我記得那條規則。**
⇒ **所以本則的動作第 1 條要改成機制**:**突變的射程一律用 `awk` 切函式範圍**,
不要用 `grep -v` 掃整檔 —— **那不是紀律問題,是預設寫法的問題。**

**與既有條目的關係**
與「假紅」三兄弟(還原方式錯 / 注入方式錯 / 打擊範圍錯)**互為鏡像**:
那三個講「紅了而理由不對」,本則講「**沒紅,而沒紅的理由不是斷言沒用**」。
與 canonical `②-b` 同源:**病根都是「突變的射程不是我以為的那個」。**

## 三、守門認的是【措辭】,不是【行為】—— 兩個方向都會出錯〔安靜〕

**判別句:這道守門看的是命令字串/元資料,還是那件事真的發生了?**

**方向 A:該擋的沒擋** —— B 窗 `B2`:`CREATE OR REPLACE FUNCTION` **不換 OID**
⇒ 函式本體被掏空時,`tgname/tgenabled/tgtype/tgfoid` **一個位元都沒變、全綠**,而三道保護全失效。

**方向 B:不該擋的擋了**(本窗實際撞到)—— 我在**自己剛 `mktemp -d` 出來、用 `init.templateDir=` 建的、
本來就沒有任何 hook 的拋棄式 repo** 裡要跑 `git commit --no-verify`,
pre-commit 閘仍以「偵測到 `--no-verify`,那會跳過 pre-commit hook」擋下。
⇒ **它看的是【命令字串】,不是【那個 repo 有沒有 hook】。**
⚠️ **代價不是被擋一次**(我改用 `core.hooksPath=/dev/null` 就過了,**沒有停用任何東西**),
**是它會訓練人去繞** —— 而繞法一旦學會,在**真的有 hook** 的 repo 裡一樣管用。
📎 同族 `#616`:**守門擋住的正是它自己想被記錄下來的地方。**

**為什麼它安靜**:方向 A 印的是綠、方向 B 印的是一段**寫得很有道理的拒絕理由**
—— **兩者都像是守門正常運作。**

**動作**
- 加任何「認字串/認元資料」的守門時,**同一次就寫下它認不到的那個世界**,放進檔頭。
- 方向 B 的守門要**給出口**(`#616` 那道給了,設計是對的),而出口要**短、一眼看得到**,
  不能藏在一段長訊息的末段。

## 四、容器的【名字】是一個對內容的宣稱,而沒有任何東西讓它們保持同步〔安靜〕

**判別句:我是照這個目錄/檔案的【名字】決定不打開它的嗎?**

**實例(`#618`,我自己踩的)** `docs/probes/2026-08-17-vitest-red-runs/` ——
我要分析隨機紅,第一個念頭是**「這裡面全是紅的,所以我【沒有對照組】」**,
並準備照這個前提寫「資料不足」。打開來數:
```
ls -1 *.txt | wc -l                        ⇒ 25
逐檔 grep -cE 'Test Files.*failed'  紅 7 / 綠 18     ← 🔴 綠是紅的 2.5 倍
```
🔴 **對照組一直都在。** 目錄名叫 `red-runs`,而 **72% 是綠的**;`README.md` **沒有更正這件事**。

**為什麼它安靜**
- **名字不會過期報錯。** 搶救第一批時它可能真的全是紅的;後來有人一併存了綠的當對照,
  **而名字是在第一批的時候取的。** 沒有任何機制會因為內容變了而讓名字紅。
- **它的失效方向是「讓人不打開」** —— 一個讀起來很精確的名字,
  **比一個含糊的名字更有效地阻止了下一個人去數**。(我不是懶,我是**信了它**。)

**動作**
- **要對一個容器的內容下宣稱之前,先數它。**
- 名字裡帶**分類詞**(`red-runs` / `failures` / `errors` / `todo`)的,

## 寫一支防某個病的工具,不會讓那支工具免疫於那個病

**事實**(全部可回放):

**判別句**:
> 這支工具防的那個病,我有沒有拿【它自己】餵過一發?

## 五、🟢 **正面版本**:一格有判別力的測試,會在它作者沒預期的地方救人〔本檔唯一的正面條目〕

**判別句:如果這一格是恆綠的,我剛剛那個動作會被什麼擋下?**

> 🔴 **本檔其餘各則都在講「守門守不住」。這一則是它的正面版本,而它只有一個實例** ——
> 主視窗指名要它進來,理由:**「恆綠」那一整族討論到目前為止沒有正面對照。**

**實例(2026-08-17 22:4x,`RUN-CONTEXT` 加 `build` 那一欄時)**
我把並行數的標記檔機制從「一種」重構成「兩種共用一套」(`vitest` / `build`,各一個子目錄)。
重構完跑 selftest:
```
FAIL  格25-b 兩發獨立 run ⇒ 並行數必須是 2   得到「0」預期「2」
FAIL  格25-c 自己那支標記檔不得算進去          得到「0」預期「2」
FAIL  格25-d PID 已死的標記檔不得算進去        得到「0」預期「1」
FAIL  格25-e 而且那支死掉的標記檔要被順手清掉  得到「left」預期「cleaned」
```
**成因**:那四格仍在往**舊的扁平路徑**寫標記檔,而計數已經改讀 `.../<種類>/<pid>`。
**機制沒壞,是格子沒跟著改路徑。**

🔴 **而重點在這裡**:
> **如果那四格當時是「恆綠」的,我不會發現路徑改了。**
> 我會 commit 一支**永遠回 0** 的並行數量具 —— 而 `0` 是一個**看起來完全正常的值**
> (它先前正常運作時印的就是 `0/0/0`)。

⇒ **那四格原本是為了別的事寫的**(單位、不算自己、PID 回收、順手清檔),
**它們在這一刻替我抓了一次重構事故**,而**沒有一格是為了「偵測重構」而存在的**。

**為什麼這一則值得留**
- 全檔其餘各則的形狀是「**我以為守住了而沒有**」;本則是「**我沒預期它會守,而它守了**」。
- 🔴 **恆綠的格子在同一刻【什麼都不會做】** —— 它不會阻止你,也不會告訴你。
  **一格有判別力的測試,它的價值不封頂在它被寫下來的那個理由裡。**

**動作**
1. 重構之後**先看 selftest 紅了幾格、紅在哪** —— **紅在意料之外的格子是好消息**,
   它告訴你那幾格是活的;**全綠反而要問一句「它們還連著被測物嗎?」**
2. 🔴 收到「這一格是不是多餘的?」這種質疑時,判準不是「它抓過 bug 嗎」,
   而是 **「拔掉它,哪一類動作會變成無聲的?」**
3. **把這種事件寫下來** —— 守門的成本天天付、收益只在事故當天出現,
   而**沒有紀錄的收益在下一次精簡討論裡等於 0**。
