## 「突變沒紅」有兩個世界,而報告上長得一樣〔安靜〕

**判別句:我這一發突變,有沒有【證據】證明它真的執行了?**

「跑完了、沒有任何一格紅」可以是兩件完全相反的事:
```
世界 1  斷言沒有判別力     ← 我以為我在量的
世界 2  突變本身根本沒跑起來（語法錯／注入位置錯／檔被改壞）
```
**而報告那一欄印的是同一句話。**

**實例(2026-08-17 夜,`#620` 突變 M19)**
我要證「拿掉 `run_context()` 的絕對路徑閘之後,格23-b/格23-c 會紅」。突變寫成:
```sh
awk '/^  case "\$rx_dir" in$/ { skip=3 } skip>0 { skip--; next } { print }' "$B" > "$T"
```
`skip=3` 刪掉 `case` 那行與兩個分支,**把 `esac` 留下來** ⇒ 孤兒 `esac` = 語法錯
⇒ **整支腳本跑不起來** ⇒ 沒有任何一行 `FAIL` ⇒ 我的報告印出:
```
實得:🔴🔴 零紅(這一發沒有任何格擋住 = 那道斷言沒有判別力)
```
**那句話是假的,而它讀起來像一個很嚴肅的發現。**

🔴 **抓到它的不是報告,是它同時留下的兩個垃圾目錄**(`3/` 與 `7/`,另一個 bug 的產物)。
**如果那一發剛好沒留下副作用,我會把「這道斷言沒用」寫進 backlog,然後把一道好的守門拆掉。**

**為什麼它安靜**
- 突變測試的整個心理預期是「應該要紅」,所以**沒紅**會被自動歸因到「斷言不行」——
  那是我本來就在找的答案,**確認偏誤的方向剛好與錯誤的方向一致**。
- `sh script.sh --selftest || true` 這種寫法把 rc 吃掉,語法錯與「跑完沒紅」**回同一個 rc**。

**動作(做進 harness,不是「記得」)**
1. **每一發突變先驗它跑起來了**:`sh <mutated> --selftest; rc=$?` ——
   語法錯的 rc(通常 2)與「跑完全綠」的 rc(0)**分得開**,報告要印那個 rc。
2. 或更便宜的一道:**突變後先數總格數**。`合計 PASS=n` 那一行不見了 ⇒ 它根本沒跑到結尾。
3. 🔴 **「零紅」永遠不可以直接寫成結論** —— 它是一個**要再查一次**的訊號,不是一個發現。

**與既有條目的關係**
- 與「假紅」三兄弟(還原方式錯 / 注入方式錯 / 打擊範圍錯)是**鏡像**:那三個講「紅了而理由不對」,
  本則講「**沒紅,而沒紅的理由不是斷言沒用**」。
- 與 canonical `②-b`(突變打到測試自己那一行)同源:**兩則的病根都是「突變的射程不是我以為的那個」。**

## 守門認的是【措辭】,不是【行為】—— 兩個方向都會出錯〔安靜〕

**判別句:這道守門看的是命令字串/元資料,還是那件事真的發生了?**

同一個病有兩個方向,今晚兩邊各撞一次:

**方向 A:該擋的沒擋(元資料說得出「保護在」,說不出「保護還在」)**
B 窗 `B2`:`CREATE OR REPLACE FUNCTION` **不換 OID** ⇒ 函式本體被掏空時,
`tgname/tgenabled/tgtype/tgfoid` **一個位元都沒變、全綠**,而三道保護全失效。

**方向 B:不該擋的擋了(本窗今晚實際撞到)**
我在**自己剛 `mktemp -d` 出來的拋棄式 repo** 裡要跑 `git commit --no-verify`——
那個 repo 是我用 `init.templateDir=` 建的、**本來就沒有任何 hook 可以被繞過**。
pre-commit 閘仍以「偵測到 `--no-verify`,那會跳過 pre-commit hook」擋下。
⇒ **它看的是【命令字串】,不是【那個 repo 有沒有 hook】。**
⚠️ **這個方向的代價不是被擋一次**(我改用 `core.hooksPath=/dev/null` 就過了,沒有停用任何東西),
**是它會訓練人去繞** —— 而繞的方法一旦學會,在**真的有 hook** 的 repo 裡一樣管用。
📎 同族:`#616`(codex 掛死守門會擋住「描述它自己」的 commit)——
**守門擋住的正是它自己想被記錄下來的地方。**

**為什麼它安靜**
兩個方向都**不會有錯誤訊息說「我判錯了」**:方向 A 印的是綠、方向 B 印的是一段
寫得很有道理的拒絕理由。**兩者都像是守門正常運作。**

**動作**
- 加任何一道「認字串/認元資料」的守門時,**同一次就寫下它認不到的那個世界**,放進檔頭。
- 方向 B 的守門要**給出口**(`#616` 那道就給了,設計是對的)——
  而出口要**短、一眼看得到**,不能藏在一段長訊息的末段。

## 一個「很有信心的零」,可能來自一把在兩個世界印同樣東西的尺〔安靜〕

**判別句:我這把尺,在【有】與【沒有】兩個世界,會不會印不同的東西?先餵一發證明它會。**

**實例一(收割判準 B②,2026-08-17 夜實測)**
`git merge-tree <base> <a> <b> | grep -c 'changed in both'` 被當成「衝突預演」。
自造拋棄式 repo,兩個世界各餵一發:

| 世界 | `changed in both` | `<<<<<<<` | 真的 `git merge` |
|---|---|---|---|
| 同一檔、**不同段** | **1** | 0 | ✅ 併得起來 |
| 同一檔、**同一行** | **1** | **1** | 🔴 撞了 |

⇒ **左欄兩個世界同一個數 = 零判別力。** `changed in both` 是**區段標題**
(「這個檔兩邊都動過」),不是「這個檔會衝突」。
🔴 **代價是【假警報】方向** —— 它不漏真衝突,只會製造來回,
**而真成本是它會訓練人忽略那道檢查**(同 E 窗「一直叫的守門會被改鬆」)。

> ⚠️ **本節原本在這裡推薦 `grep -c '<<<<<<<'`,那個建議【已被同一晚的實測推翻】。**
> 它在玩具 repo 上分得出來,**在真 repo 上仍然假警報**。
> **現行建議與三把尺的完整對照,見本檔最後一節**(「在玩具上驗過的量具,可能在真的 repo 上仍然錯」)。
> 🔴 這一段**刻意留著不刪** —— 刪掉的話,讀者會以為只錯過一次。

**實例二(`#625`,同一晚,而這次我差點寫出結論)**
我要判「主樹那三個未追蹤檔是不是被 `git stash -u` 移走又 `pop` 回來」。
本來要寫:「`git stash list` 空、`.git/logs/refs/stash` 不存在 ⇒ 沒有人 stash 過。」
**落筆前先去驗那把尺**(拋棄式 repo,`stash -u` + `pop` 之後看那個檔在不在):
```
stash 之前            .git/logs/refs/stash  不存在
stash -u + pop 之後   .git/logs/refs/stash  🔴 仍然不存在
```
⇒ `pop` 丟掉 stash 條目時連 ref 與 reflog 一起收掉
⇒ **那把尺在兩個世界印同一個東西,「沒有紀錄」證不了「沒發生過」。**

**為什麼它安靜**
一個零讀起來像一個結論,而**它只是「我的檢查沒看到」**。
兩者的差別**不會出現在輸出裡**,只出現在「我有沒有去驗那把尺」。

**動作**
- 🔴 **任何要寫成「沒有 / 查無 / 零命中」的檢查,先餵一發【該命中的】證明它會亮。**
  本檔三個實例裡,**兩個是靠這一步當場擋下的**。
- 零命中要附**分母**與**正向對照**(例:`grep -rl '#625'` ⇒ 0,分母 3020 檔,
  正向對照 `grep -rl '#612'` ⇒ 4 檔命中 ⇒ 那個 0 是量出來的)。

## 🔴 在玩具上驗過的量具,可能在真的 repo 上仍然錯 —— 而我因此連錯兩次〔安靜〕

**判別句:我驗那把尺用的樣本,有沒有【真實情境才有的那個形狀】?**

**一晚之內同一條線我給了兩次建議,兩次都被實測打掉:**

```
第一次  我說「changed in both ⇒ 2 ⇒ 會撞」        真 merge ⇒ 零衝突   ❌
        （那是【區段標題】,不是衝突）
第二次  我改推「grep -c '<<<<<<<'」,並且【在自造的兩個世界上驗過它會分辨】
        ⇒ 隔一批再用,它說 2,真 merge ⇒ 又是零衝突          ❌
```

**三把尺,正確構造的兩個世界(base `a b c`,兩邊各改一行):**

| 量法 | 世界1 改不同行 | 世界2 改同一行 | 玩具上分得出來? | 真 repo 上? |
|---|---|---|---|---|
| `grep -c 'changed in both'` | 1 | 1 | ❌ 兩世界同值 | ❌ |
| `grep -c '<<<<<<<'`(舊三參數形式) | 0 | 1 | ✅ | 🔴 **假警報(說 2,實際 0)** |
| `git merge-tree --write-tree A B` 的 **rc** | 0 | 1 | ✅ | ✅ **與真 merge 一致** |

🔴 **為什麼第二把尺在玩具上過、在真 repo 上炸**:`git merge-tree` 的**舊三參數形式做的是
「trivial merge」** —— 沒有 rename 偵測、不走 `ort` 策略。我的玩具 repo 是**線性、三行、
從來沒有 merge 過**,沒有真實歷史才有的那個形狀(**我的分支基底裡已經有一顆 merge commit**)。
⇒ **玩具通過的是「這把尺會不會動」,不是「這把尺在我要用的地方準不準」。**

**⇒ 現行建議(git 2.39.5 實測,兩個世界 + 一個真 repo 反例都對得上):**
```bash
git merge-tree --write-tree <dev> <界線> >/dev/null 2>&1; echo "rc=$?"   # 0=可併 1=有衝突
```
**不要接管線去數字串** —— 這一條的整個教訓就是「數字串」數到的是別的東西。

**為什麼它安靜**
兩次我都**做了該做的動作**(自造兩個世界、看它會不會印不同的東西),
**而兩次都得到了「它會分辨」這個正確答案** —— 只是那個答案的射程只到我造的那個樣本。
**沒有任何一步是偷懶的,錯的是我沒問「我的樣本像不像真的」。**

**動作**
- 驗量具的樣本,**要帶上真實情境的結構特徵**(這裡是:基底含 merge commit、檔案大、多次來回)。
- **能直接問工具「會不會撞」就不要自己解析它的輸出** —— rc 是工具的結論,字串是工具的中間值。
  📎 同族:`feedback_pasting-intermediate-values-hides-your-own-arithmetic`。
- 🔴 **給出去的建議被推翻時,要去改【收訊者會讀的那份檔】,不是補一封信。**
  本則兩次更正都同步改了 `T-004` 的 §②(收割窗收件時會讀的那份)。
