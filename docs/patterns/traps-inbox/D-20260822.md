## 分母錯有兩個方向,而「修掉太窄」的那一手會直接越過下一條界〔安靜〕

**判別句:我數的這個集合,和【那道閘實際看得到的】那個集合,是同一個嗎?**

一句話:分母太窄會漏掉該守的;把尺放寬修掉它之後,**放寬本身不會在正確的地方停下來**。
兩個方向的錯**長得完全不一樣**,而兩次都會產出一個看起來很紮實的數字。

**實例(2026-08-22,同一片、四十分鐘內,兩個方向各一次)**

```
派工單寫「9 支沒守門的 .py」   ⇒ 尺太窄:`scripts/*.py` 是非遞迴的
                                  漏掉 scripts/admin-probe/、scripts/storefront-probe/ 底下 3 支
我回報改成「全 repo 18 支」     ⇒ 尺太寬:`find . -name '*.py'` 越過了 .gitignore 那條界
                                  多算了 .screenshots/e16-scratch/restore_types.py
codex 更正成「tracked 17 支」   ⇒ 對的那把尺是 `git ls-files '*.py'`
```
重跑:
```bash
ls scripts/*.py | wc -l                          # 14  非遞迴
find . -name '*.py' -not -path './node_modules/*' -not -path './.git/*' | wc -l   # 18  含 ignored
git ls-files '*.py' | wc -l                      # 17  ← 閘實際守得到的
git check-ignore -v .screenshots/e16-scratch/restore_types.py   # .gitignore:105
```

**為什麼它安靜**
三個數字**都是真的**,而且三條命令都會乾淨地跑完、印出一個整數。
沒有任何一條會說「你數的不是閘會看到的那些」——
🔴 **分母的錯不會讓工具紅,它讓工具用一種很有把握的語氣回答一個沒被問的問題。**

而放寬那一手特別安靜,因為它**帶著一次成功的更正的動能**:
我剛剛才證明對方的尺太窄,同一個動作再多推一格,感覺仍然像在修正。

**動作**
- 為「一道閘 / 一次覆蓋率宣稱」數分母時,**分母的定義是那道閘的取檔機制**,不是「這個 repo 裡有幾個」。
  pre-commit 閘 ⇒ `git ls-files`(它只看得到 tracked);CI 閘 ⇒ 那支 workflow 的 paths。
- 數字旁邊寫**是哪把尺**(照 §6-b 第 2 條:數字要帶著它的座標離開現場)。
  「18 支 .py」與「17 支 tracked .py」是兩個宣稱,只有後者能拿來說「這道閘守得到幾支」。
- 🔴 **而 17 也還不是「這片新守住的數」**(codex R2 #4 抓到,我原文寫錯):
  其中 5 支 `package.json` 早就有各自的 `--selftest` 閘 ⇒ **淨新增 = 12**。
  ⇒ 一句話裡藏了**三個**不同的分母:磁碟 18 / tracked 17 / 淨新增 12,而它們讀起來都像「這片的成果」。
- 🔴 **量法本身也有分母**:`git ls-files '*.py'` 只看**你當下所在的目錄以下** ——
  在 `scripts/storefront-probe/` 跑只得到 **2**。而 lint-staged 的射程是整個 repo
  ⇒ **不固定在 repo root 跑,數出來的就不是這道閘的分母。**(已同步寫進 `check-syntax-nonts.ts` 檔頭。)
- 🔴 修正別人的分母之後,**對自己的新分母再問一次同一句判別句** —— 那正是我沒做的那一步。

**與既有條目的關係**
「掃描字集比宣稱窄(假陰性)」與 §714 那節「字集比宣稱寬(假陽性)」講的是**同一次量測的兩端**;
本條講的是**兩次量測之間**:第一次的更正,製造了第二次的錯,而方向相反。

## 補正一條既有教訓:`git checkout -- <檔>` 拿的是【index】,不是【HEAD】〔安靜〕

> 🔴 **這條不是新發現。** 主體早在 2026-08-10 就由 E 窗落檔:
> memory `feedback_mutation-restore-scope-git-checkout-wipes-uncommitted-edits`
> (「突變還原不能用 `git checkout`,會把未 commit 的當輪編輯整片抹掉;只准 cp 或反向套用」)。
> **我今天原封不動地又犯了它兩次**,而查重工具把它排在**第 5 名**(0.5587)——
> 前四名都不是它。這正是本工具檔頭已記的失效①。
> ⇒ 本節**只補那條沒說對的機制**,以及它在多窗環境下多出來的那一格。

**判別句:我要回去的那一版,現在住在哪裡?我這條命令會去那裡拿嗎?**

**要補正的一句**:既有那條寫「它還原到 HEAD」「作用域是相對 HEAD/index 的全部差異」。
**`git checkout -- <path>` 的來源是 index,而且只有 index。** 零 commit 的 repo(根本沒有 HEAD)照樣還原得成功:
```bash
mkdir -p /tmp/p && git -C /tmp/p init -q
printf 'STAGED-版本\n' > /tmp/p/f.txt && git -C /tmp/p add f.txt
printf '工作樹-版本\n' > /tmp/p/f.txt && git -C /tmp/p checkout -- f.txt
cat /tmp/p/f.txt          # ⇒ STAGED-版本
git -C /tmp/p rev-parse HEAD   # ⇒ fatal: unknown revision 'HEAD'
```
平常 `index == HEAD`,所以兩種說法**碰巧同義** —— 直到有人 stage 了東西。

**多窗共用工作樹多出來的那一格(2026-08-22 實例)**
```
第 1 次  靶 = scripts/check-syntax-nonts.ts(我改了、未 commit、index 乾淨)
         `git checkout --` ⇒ index == HEAD ⇒ 我這片五處改動全部消失
         `git status` 回「乾淨」。而乾淨在這裡的意思是:你的工作沒了。

第 2 次  靶 = scripts/check-syntax-nonts.gate.test.ts
         同一條命令,但這時【另一個窗把我的檔 staged 了】(我從未跑過 git add)
         ⇒ 它拿回 index 那一版 = 我 R1 的版本 ⇒ 只掉了 R2 的兩處
         🔴 錯得比第一次【小】,所以更難發現 —— 是 grep 覆核撈到的,不是任何紅燈。
```
自證:
```bash
git status --porcelain -- <檔>   # `MM` = index 與工作樹各有一版；` M` = 只有工作樹那一版
git diff --cached --stat          # index 裡到底是誰的哪一版
```

**為什麼它安靜**
① 命令一個字沒變而語意換了(來源從「和 HEAD 一樣的 index」變成「別人 add 進去的 index」)。
② 還原成功、與還原成「別人的某一版」,在 `git status` 上都可以是乾淨的。
③ 🔴 **index 是多窗共用的** ⇒ **我的還原基準會被別人的 `git add` 改掉,而我不會收到通知。**
④ 🔴 而我今天是**在跑「用來證明第一次那條教訓」的那一發突變時**,再犯了同一條。

**動作(既有那條的兩形狀不變,只加這三句)**
- 要 HEAD 就**明寫** `git checkout HEAD -- <檔>`;裸的 `git checkout --` 在共用工作樹裡基準不可信。
- **「我剛才那一版」git 裡不存在任何指標** ⇒ 只能自己 `cp`。`git stash` / `git restore` 同一個問題。
- 還原之後**不要用 `git diff` 判斷成功**(它只答「和 index 一不一樣」),改 `cmp -s "$BK" "$F"` 或 grep 剛加的字面。

**與既有條目的關係**
`mutation-harness-restore.md` 記「用一個會殺掉還原的方式跑它」(還原沒發生);
memory 那條記「還原作用域太大」(還原發生了、範圍太寬);
**本節記第三種:還原發生了、範圍剛好、而它回到的是別人的版本。**

### 補:那個「別人」是誰 —— 具名、同一天、雙方都在場的實例

> 上面第二節寫「它拿回 index 那一版 = 我 R1 的版本」,而**當時我不知道是誰 stage 的**。
> 主視窗自陳(2026-08-22,本片 R2 交件後):**是它。** 而理由完全正當 ——
> **它為了讓 codex 看得到 staged diff 而 `git add`,不是為了 commit。**

**這才是這條 traps 真正的形狀:**
```
「為了審查而 stage」與「為了 commit 而 stage」，在 index 裡長得一模一樣。
⇒ 審查回 FAIL、作者去修 ⇒ index 停在【被判 FAIL 的那一版】
⇒ 而那一版從此看起來像「準備好了」：不會過期、不會紅、不會有人通知任何人。
```
🔴 **而它同時是兩個人的坑,方向相反:**
- 對 **stage 的人**:那顆 index 變成一顆看起來備妥、實際被判 FAIL 的舊版。
- 對 **改的人(我)**:我的 `git checkout -- <檔>` 的還原基準,被別人的 `git add` 悄悄換掉了 ——
  🔴 我以為我在還原到「乾淨」,實際還原到「**審查判 FAIL 的那一版**」。

**兩邊都沒有做錯任何一件被規定的事**,而損害是真的(我掉了 R2 的兩處改動)。
⇒ 這正是為什麼它是結構、不是「有人不小心」。

### 第三面:`git add` 的那幾支,與 `git commit` 出去的那幾支,是兩件事

主視窗 2026-08-22 當天第三次撞上同一顆 index,而這次是**送出**方向:
```
它要 commit 線B 的地址欄那片，stage 時看到的是   4 files, 105 insertions
commit 輸出印出來的卻是                          8 files, 273 insertions
🔴 多出來的 4 支就是我這片 —— 而且是【codex 判 FAIL 的那一版】。
```
成因:`git commit` 不帶 pathspec 時送的是**整個 index**,不是它剛 `git add` 的那幾支。
處置:`reset --soft` 丟棄 `02ba395b`(未 push)+ `git restore --staged` 我那 4 支 + 重下,
現在 `7aa53f39` = 4 files / 105 insertions(我自己 `git show --stat` 核過,不是轉述)。

🔴 **而抓到它的不是任何一道閘** —— 是 commit 輸出自己印的「8 files」與它腦子裡的「4 files」對不起來。
⇒ **這一面的判別句:我剛才那個動作,印出來的數字跟我以為的一樣嗎?**
   `git add` 有 pathspec、`git commit` 沒有 ⇒ 兩個動作的**作用域不同**,而輸出裡沒有任何字說這件事。

### 第四面(同一片,一小時後,我自己):**還原的【驗證】本身沒有判別力**

上面三面講「還原回到錯的版本」。這一面是:**還原根本沒發生,而我跑了一條檢查說它發生了。**
```
突變 274 行  `? Number(m[1]) : null`  →  `? 999 : null`
還原用       restore(){ [ -f "$BK" ] && cp "$BK" "$G" && rm -f "$BK"; }
🔴 缺陷①  第一次呼叫就把備份 rm 掉了 ⇒ 第二次呼叫 `[ -f ]` 為假、【安靜地什麼都不做】
          （`&&` 串起來的函式，前一格為假就整條略過，而 shell 不會說任何話）
我的驗證     grep -c 'Number(m\[1\]) : null'   ⇒ 印 1  ⇒ 我判「已還原」
🔴 缺陷②  那個 1 來自【第 51 行的 checkShell】—— 一支我從來沒碰過的函式，
          它剛好有一模一樣的片段。突變在 274 行，而我的尺量的是【整支檔】。
真相       999 一直留在檔裡，是 30 分鐘後跑全套測試才紅出來的。
```
**兩個缺陷各自都會產生一個綠**,而合在一起讓「我還原了」這句話讀起來完全成立。

🔴 **判別句:我這條驗證,在【還原成功】與【還原失敗】兩個世界,會印出不同的東西嗎?**
`grep -c '<某個片段>'` 幾乎永遠答不出來,因為**它的分母是整支檔**
(母條:memory `feedback_greps-denominator-is-the-whole-file`)。

**改法(兩條都要,少一條就還是綠)**
- 還原**不要用 grep 驗**,用 `cmp -s "$BK" "$F"` —— 它的分母就是那份備份,沒有第二種解讀。
- 備份**不要在 restore 裡刪**;刪在 trap 的最後一步,或乾脆不刪。
  🔴 更根本的一句:**一個「只能成功一次」的還原函式,在多發突變的 harness 裡是必然的洞。**

**動作(四邊各一句)**
- **stage 給審查的人**:審查回 FAIL 的**當下**就 `git restore --staged <路徑>` 或重新 add ——
  不要留一顆被判 FAIL 的 staged 版本過夜。(主視窗已落檔為流程。)
- **改檔的人**:動手前先 `git status --porcelain -- <你的檔>`,看到 `M ` 或 `MM` 就知道
  **index 裡有一版不是你放的** ⇒ 這時 `git checkout --` 的意思已經不是你以為的那個。
- **commit 的人**:`git commit` 一律帶 pathspec;不帶就等於送出整顆共用 index。
  而**收工時看一眼 commit 輸出的 files/insertions 對不對得上你 stage 時看到的** ——
  這片三次撞擊裡,唯一被抓到的那次就是靠這個。

**收尾(2026-08-22 當場量,不是轉述)**:主視窗回報已重新 add;我自己核過 index 的字面 ——
`git show :package.json` ⇒ glob 是 `[sS][hH]…[pP][yY]`;`git show :scripts/check-syntax-nonts.ts`
⇒ 有 `src=open(p,'rb')`;三支測試檔的新格也都在 index 裡。**staged 的確實是 R2 版。**
