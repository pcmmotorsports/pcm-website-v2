## 尺量的是【分類】,而我讀成【嚴重度】 —— **而我是廣播出去之後才撞到反例的**〔安靜〕

### 判別句

> 🔴 **我這條命令 grep 的那個字串,是一個【程度】還是一個【類別】?**
> 類別 ⇒ 它旁邊還有幾個平行的類別,而我的 grep 一個都沒抓。

引申:**「這個檢查回 0」與「這件事沒發生」之間,隔著「還有幾種長相我沒列」。**

### 實例(2026-08-17 夜 I 窗;本 session 實跑輸出)

收割前用 `git merge-tree` 做不落地衝突預演。我先前對全陣廣播的判準是:

```
git merge-tree $(git merge-base dev <界線>) dev <界線> | grep -c 'changed in both'
```
並且加了一句聽起來很嚴謹的話:「`changed in both` **不等於**會撞,真判準是 `grep -c '^+<<<<<<<'`」。
**後半是對的,而前半的框架是錯的** —— 我把 `changed in both` 當成「會撞」的**粗糙版**,
它其實是 `git merge-tree` 的**其中一個分類標籤**。

當晚收 A 窗 `7edc8a30` 那一發:

```
grep -c 'changed in both'   ⇒ 0      ← 只跑這條會判「乾淨,可以收」
grep -c '^+<<<<<<<'         ⇒ 1      ← 真的撞
實際印出來的標籤是   added in both           （兩個窗各自從零建了同一個路徑）
```
⇒ `changed in both` 這把尺**看不見** `added in both` 與 `removed in both`。

**修法(兩條擇一,不要只跑第一條)**:

```
git merge-tree $(git merge-base dev <界線>) dev <界線> | grep -cE '^(changed|added|removed) in both'
git merge-tree $(git merge-base dev <界線>) dev <界線> | grep -c '^+<<<<<<<'
```
後者在本例抓到了,而前者的字集是我自己列的 ⇒ **能只信後者就只信後者**
(⚠️ 而後者也有它的射程:它抓的是**輸出裡的字面**,若被比對的內容本身就含 `<<<<<<<`
會自命中 —— 那時要開輸出看那幾行落在哪個檔的哪一段,不能只看數字)。

### 為什麼它安靜

`grep -c` 回 `0` 在終端機上,和「真的沒有這件事」是同一個畫面。
而分類標籤的**數量**不會有任何東西提醒你 —— **git 不會說「你還有兩個標籤沒查」。**

### 🔴 這一則獨有的那一面:**廣播讓一個錯的量法在全陣同時生效**

我不是自己用了那條命令而已 —— 我**把它當成收割紀律廣播給了全陣**,而當時它讀起來
比原本的做法更嚴謹(它甚至**更正了**一個更粗的用法)。
⇒ **一個錯的量法,只要它比前一版精確,就會被當成改進而擴散。**
⇒ **動作**:凡是要**廣播**一條量法(不只是自己用),先問一句 ——
**「我這條 grep 的字集,是誰列的?工具的文件,還是我的印象?」** 我的印象 ⇒ 先去把平行項列完。

## 一份講「不要有兩個真相」的檔,長出了兩份〔安靜〕

### 判別句

> 🔴 **我現在要建的這個東西,有沒有人已經被指派在建它?**
> 而這一問要問在**動手之前**,不是 commit 之後。

### 實例(2026-08-17 夜;主視窗與 I 窗各一手)

主視窗裁定開 `docs/patterns/traps-inbox/` 暫存區,並在**同一則訊息**裡叫 A 窗建 `README.md`。
I 窗(我)把 README 當成「機制的一部分」,自己寫了一份並 commit(`aa7f9758`)。
⇒ `git merge-tree` 印 **`added in both`**:

```
merge-base 有這個檔 ⇒ NO      dev 有 ⇒ YES(我的)      界線有 ⇒ YES(A 窗的)
```
🔴 **而那份 README 自己第 5 節的標題逐字是「這個目錄自己的已知風險:第二個真相」。**
一份專門用來防止同一則活在兩個地方的檔,**在它被建立的那一刻就活在兩個地方**。

### 為什麼它安靜

兩邊都**照指示做了**、兩邊都**做對了**、兩邊的產物**各自都是好的**。
⇒ 沒有人做錯事,而衝突是真的。**它不是品質問題,是協調問題,而協調問題不會在任何一邊的檢查裡出現。**

### 動作(不是決心)

- **派工端**:指派「建一個新檔/新目錄」之前,先講清楚**誰建**;同一則訊息裡同時裁定機制又派人建,
  很容易漏掉「裁定的人自己可能也會順手做」。
- **執行端**:把一個東西當成「機制的一部分」順手做掉之前,先問一句
  **「這件事有沒有可能已經被派給別人了?」** —— 這一問的成本是一則訊息。
- **歸戶**:寫「這是派工競態、不是誰的錯」的時候停一下 —— **派工的人是誰?** 競態有人負責,
  而「競態」兩個字讀起來像沒有。

## 一條指向【別的檔】的量法,會在那個檔被更正的時候**安靜地反向**〔安靜〕

### 判別句

> 🔴 **我寫的這條量法,查的是【我這個檔】還是【別人那個檔】?**
> 別人那個檔 ⇒ **它被更正的那天,我的量法不會壞掉,它會開始給相反的答案。**

一般化:**壞掉的量法會讓人停下來,反向的量法不會** —— 它照樣印出結果,而結果讀起來像確認。

### 實例(2026-08-17 夜 I 窗;本 session 實跑輸出)

`docs/specs/2026-06-13-m3-3ds-webhook-master-plan.md:24-25` 原本這樣寫(逐字):

```
· **`STATUS.md`**(專案 SSoT)逐字:「🟡 M-3 prod checkout 仍不可開(**3DS flag 全 false**…)」。
  量法:`grep -n '3DS flag 全 false' STATUS.md`。
```
那條量法**當時是對的**:命中 ⇒ STATUS 確實那樣主張。
而我在 `6074a448` 把 STATUS 那欄改掉了,**並且照規矩留痕**(`~~本欄原寫「3DS flag 全 false」~~`)。

```
落地後當場跑:grep -c '3DS flag 全 false' STATUS.md   ⇒ 1
```
🔴 **它還是命中 —— 而命中的是那句話的【訃聞】,不是那句話。**
⇒ 照它跑的人會得到「STATUS 還這樣寫」,**而事實相反**。

🔴 **這比回 0 更糟**:回 0 至少看得出「這句話不在了,去查一下」;
**命中會讓人以為問題還在原地**,他不會再往下查。

### 為什麼它安靜

留痕(刪除線)是**正確**的做法 —— 不留痕的話,引用它的人會找不到自己引的東西去哪了。
⇒ **正是那個正確的做法讓下游的量法反向。** 兩件對的事湊在一起,產生一件錯的事,
而**兩邊各自都沒有做錯**,所以任何一邊的檢查都不會叫。

### 動作(不是決心)

- **寫**跨檔量法時,同一段標明「**這條量的是 `<那個檔>` 的現況,那個檔一改本條就要重寫**」。
- **改**一個被別處引用的字面時,`literal-sweep.sh` 撈出來的每一處要**分兩類**:
  ①**引用它的敘述** ⇒ 改敘述 ②**引用它的量法** ⇒ 🔴 **量法不能只改敘述,要換成現在還會給正確答案的那條**,
  或刪掉並寫明「原量法已失效,因為 `<檔>` 已於 `<日期>` 改寫」。**留一條會反向的量法,比不留更糟。**
- 換掉之後**當場跑一次新舊兩條**,把兩個輸出並排寫進去(舊的命中什麼、新的命中什麼)。

### 與既有條目的關係

- canonical 的「**更正本身會過期**」:那條講的是**更正這件事**本身的下游;
  本條窄一級 —— **下游是一條【量法】的時候,它不會過期,它會反向。**
- memory `feedback_absence-read-as-verified`:那條是「0 被讀成沒事」;
  **本條是它的鏡像 ——「命中被讀成還在」。** 同一個病,兩個方向。
