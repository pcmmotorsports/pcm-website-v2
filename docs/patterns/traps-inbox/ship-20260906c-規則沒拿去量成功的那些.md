## 一個能解釋失敗的規則, 我沒有拿它去量【已經成功的那些】〔安靜〕

**線** `-ship` 2026-09-06 · 貼板 39 · **自述**

### 事情
Sean 貼一支 migration, 逐字 `ERROR: 42601: unterminated quoted string`。
我找到一個能解釋它的規則 —— **「單引號字串裡有 ASCII 分號 ⇒ Supabase SQL Editor 切一刀」** ——
當場寫成靜態檢查的規則⑦。
🔴 **而它第一次跑就命中 `20260905320000`** ——
那一支**帶著同樣的 ASCII 分號**(第 206 行, 碼位 `0x3b`, 逐字元量過), 而**它貼成功了、已經在正式庫上**。

### 🎯 母題
**一個能解釋失敗的規則, 不等於一條規則。**
它可能只是「剛好涵蓋了現場」的形狀 —— 而**要分辨這兩者, 唯一的方法是拿它去量【已知成功】的那些。**

### ✅ 判別句
> **這條規則套在【已知成功】的那些身上, 會印什麼?**
> 印紅 ⇒ 它不是規則, 是一個描述現場的句子。

### 🔵 收窄之後長什麼樣(而它仍然是假說)
```
判準改成【行尾】的分號(後面到換行只剩空白):
  39 第二版(貼下去紅)     字串內分號 8 個 · 其中 2 個在行尾  ⇒ 紅
  20260905320000(貼成功)  字串內分號 1 個 · 0 個在行尾       ⇒ 綠
```
🛑 **兩個資料點與它一致, 而沒有人量過那個編輯器的 parser。**
⇒ 它擋不到「行中分號而編輯器其實也會切」那個世界 —— **那句話寫在碼裡, 不是寫在這裡就算了。**
⇒ 🔵 而**第三個資料點會自己送上門**:Sean 貼第三版的結果(紅或綠)就是它。
