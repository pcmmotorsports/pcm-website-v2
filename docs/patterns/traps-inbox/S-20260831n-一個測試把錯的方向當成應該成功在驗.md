# 一個測試把【錯的方向】當成「應該成功」在驗 —— 那比沒有測更糟

> 線【出貨】`-1e` · 2026-08-31 · codex R1 must-fix 抓到

## 現場

我寫了一支 RPC:把「已經放棄」的信重排回佇列。述詞是**黑名單** —— 只擋 `status = 'sent'`。
我造了六個世界去驗它,其中一個是:
```
世界 4:status = 'sending' 且 attempts 已經燒完 ⇒ 我列成【應該成功】
       ⇒ 它真的成功了 ⇒ 我在交件裡記成 ✅,還特地寫「這一格證明 claimed_at 有被清掉」
```

**codex 指出那一格是錯的**:
> `sending` 代表 sweeper **正握著那一列**,而 provider 可能**已經收信了**。
> 把它重置成 `pending` ⇒ 舊持有者因世代柵欄**無法標 sent**
> ⇒ 逾 provider 冪等窗後再送 ⇒ **那位客人收到兩封。**

## 📌 判別句

```
一個測試不只可能【漏掉】錯誤 —— 它可能【主動替錯誤背書】。
而那比沒有測更糟:
  · 沒測的地方, 還有人會懷疑
  · 被測過而且綠了的地方, **沒有人會回頭看**
```

## 🔴 而它為什麼特別難自己發現

```
那一格【真的通過了】—— 它驗的東西(claimed_at 被清掉)也【真的成立】。
⇒ 錯的不是斷言, 是**我把那個世界放進「應該成功」那一欄**這個決定。
⇒ 📌 **斷言可以被突變檢驗, 而「期望值放在哪一欄」不能** ——
   它是我寫下去的, 而沒有任何一發突變會質疑它。
```
🛑 **⇒ 這一格只有【不共用我前提的人】看得到。** 今天看到它的是 codex。

## ✅ 修法(而它是今天第三次同一個母題)

黑名單 ⇒ **白名單**:只認 `pending` / `failed`。
那張表有 7 態,黑名單會把 `sending` / `skipped_order_ineligible` / `skipped_shipment_voided`
一起翻回去,而每一種都有自己的狀態契約。
📌 **⇒ 黑名單在跟【下一個沒想到的狀態】賽跑,而白名單讓新增的那一態預設落在安全那側。**

· 而本則沒有可機械執行的守門 —— 「期望值放對欄了嗎」我想不出一條命令能問。**未解。**
