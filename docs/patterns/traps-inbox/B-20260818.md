## `head -N` 之後的清單長度恆等於 N,而它看起來就是一份完整清單〔安靜〕

**判別句:這個數字是 `wc -l` 出來的,還是我數畫面上有幾行?**

**實例(同一段落裡犯兩次,2026-08-18)**:寫 `#231` 的估算時引用了兩個分母。
```
落筆寫「settleCharge 引用點共 8 支檔」        ⇒ 重數 36
落筆寫「needs_manual_review 全樹 12 支檔」    ⇒ 重數 24
```
兩個都來自**上一輪一條接了 `head -8` / `head -12` 的 grep** ——
我把**被截斷的輸出**讀成了總數。

**可重跑**:
```bash
git grep -ln "settleCharge" -- 'apps/**' 'packages/**' | grep -v '\.test\.' | wc -l      # 36
git grep -ln 'needs_manual_review' -- 'apps/**' 'packages/**' 'supabase/**' \
  | grep -v '\.test\.' | wc -l                                                            # 24
```

**它為什麼安靜**:
- `head -N` 的輸出**沒有任何「還有更多」的訊號** —— 它就是 N 行,乾乾淨淨。
- 🔴 **而兩個錯的數字旁邊【都附了 grep 命令】,我對它們有信心。**
  那正是全稱句 hook 自己承認的天花板,逐字(`~/.claude/hooks/quantifier-assertion.js:9-11`):
  > ❌ **判不了那條數法數的是不是正確的東西**
  ⇒ **這是那個天花板的第一個實例。附了命令 ≠ 跑對了那條命令。**

**動作**:任何要寫進檔案的分母,**落筆當下重跑一次帶 `| wc -l` 的版本**。
探索時用 `head` 沒問題,**引用時不行**。

**與既有條目的關係**:同族於「量錯東西」,但更前面一層 —— **量具是對的,我讀錯它的輸出。**

## merge:「衝突」看得見,「重複」看不見〔安靜〕

**判別句:兩邊 diff 的行號區間有沒有【重疊或相鄰】?相鄰更要看 —— 那正是「各自補一段」的形狀。**

**實例(2026-08-18)**:I 窗與 B 窗**各寫了一段**「上面那兩句引文的事實部分已不成立」
到 `docs/specs/2026-08-17-m4b-order-items-max-rows-plan.md` §2-e 底下。
兩段**位置相鄰但不重疊** ⇒ **git 自動 merge、兩段都留下、零衝突標記**。

**可重跑**:`git merge-tree --write-tree HEAD dev; echo $?` ⇒ `0`。
🔴 **`rc=0` 只保證【沒有文字打架】,不保證【沒有重複】。**

**它為什麼安靜**:
- 衝突有 `<<<<<<<` 可以 grep,**重複沒有任何標記**。
- 兩段**各自都正確** ⇒ 兩邊 review 時都看不出問題。
- 下一個讀的人會以為那是**兩件事**,而它是一件事的兩種措辭。

**動作**:merge 之後,對**兩邊都動過的檔**掃一次「同一件事有沒有被講兩次」;
併起來時**在段首寫明它是併出來的**,否則下一輪又會被拆讀成兩件。

## 兩份文字各自正確,合併之後【代名詞失去指涉】〔安靜〕

**判別句:這段文字裡的「我」「本檔」「上面那段」,在合併之後還指得到原來那個東西嗎?**

**實例(2026-08-18)**:`SupabaseOrderAdapter.ts` 的註解,兩邊各寫了
```
I 窗版：「本檔改動者未自驗，轉錄 V 窗量測」
B 窗版：「主視窗與我均未自驗」
```
兩句在各自的 commit 裡都精確。**merge 之後那個「我」指不清是誰** ——
讀者不知道是誰沒自驗,而**那正是這句話存在的唯一理由**。
⇒ 已改成「**I 窗與 B 窗均未自驗,轉錄 V 窗量測**」。

**它為什麼安靜**:
- **兩邊 review 時都看不到** —— 各自看都對,錯誤只在「合併後」這個第三個狀態裡存在,
  而**沒有人 review 那個狀態**(merge 通常只被檢查「有沒有衝突」)。
- 同族:任何**相對指涉**(「上一節」「見下」「那兩處」)在搬檔 / 併檔之後都會漂,
  而 `traps-inbox/README.md` 已經記過搬檔那一半(「數字離開量測現場,量測範圍要跟著它走」)。

**動作**:在**會被搬或會被併**的檔裡,把「我」寫成**窗名**、把「上面那段」寫成**錨點或行號**。

## 「還沒開始」與「開不了工」在進度表上長得一樣,而處置完全相反〔安靜〕

**判別句:這件事沒進展,是【沒有人做】還是【做不了】?**
**答「做不了」⇒ 下一句必須是「卡在誰手上、缺哪一道」。**

**實例(2026-08-18)**:sweeper 心跳表的**寫入端**在三份文件裡都寫著
「⏳ 一行都沒開始」,而主視窗照那個字面裁「可以做,去做」。
**實際上它做不了**:
```
sweeper_heartbeat 不在 database.types.ts（grep -c ⇒ 0）
那份檔【從真實 DB 生成】，而該表的 migration 還沒 apply 到任何真實 DB
⇒ .from('sweeper_heartbeat') 通不過 typecheck
```
**實測(拋棄式探針,已刪)**:
```
error TS2769  No overload matches this call
error TS2353  'job_name' does not exist in type 'RejectExcessProperties<…44 more…>'
```
⇒ 真正的鏈:**Sean apply ⇒ `supabase gen types` ⇒ 寫入端 ⇒ 健康端點**。頭在 Sean 手上,不在施工窗。

**它為什麼安靜**:
- 「⏳ 未開始」是一個**看起來已經交代過的狀態** ⇒ 沒有人會去問「為什麼沒開始」。
- 🔴 而**兩者的處置相反**:「還沒開始」要**派人**,「開不了工」要**按一個鈕**。
  派人到一個開不了工的地方,那個人會花一輪才發現,**而他很可能改用繞過的方式做完**
  (手改生成檔 / `as any` / 自建型別)—— 那會讓「型別與真實 schema 不同」變成
  **沒有任何東西會紅**的狀態,且生成檔下次重生會把手改的部分**靜默蓋掉**。

**動作**:進度表上的「未開始」要能回答**為什麼**。
repo 既有慣例是對的(`docs/phase-1-backlog.md:12778` 逐字
「⏸ **等 A1 apply 後 `supabase gen types` 才能開工(型別雞生蛋)**」)—— **`⏸` 與 `⏳` 是兩個符號。**
