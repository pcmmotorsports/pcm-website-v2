## 事件(一次,兩個實例,同一支檔)

那支 migration 我交件時附了四綠 + SQL 平衡檢查 + codex 讀碼審查。**它根本跑不起來。**

```
① ERROR: function pg_catalog.nullif(text, unknown) does not exist        （4 處）
② ERROR: missing FROM-clause entry for table "pg_catalog"
   ← SELECT pg_catalog.current_user
```

**兩個都是我自己加上去的。** 加的原因是本 repo 有一條真的規矩:
函式要 `SET search_path = ''`,而那之後**所有識別字都要 schema 限定** ——
否則 `search_path` 一空,`btrim` 這種東西就找不到。

⇒ 我照做了。**而 `NULLIF` 與 `current_user` 不是函式,是 SQL 建構(語法關鍵字)。**
它們沒有 schema,加了前綴就變成「去 `pg_catalog` 找一個叫 `nullif` 的函式」—— 那個東西不存在。

## 🔴 為什麼四道閘全綠

```
pnpm typecheck / lint / build   →  .sql 不進它們的分母（本來就不讀）
scripts/check-syntax-nonts.ts   →  它【只做配對平衡】，引號/括號/dollar-quote 都閉合 ⇒ 綠
                                   （slice-checkpoint.md:197 逐字：「語法、欄名、型別、語意一律抓不到」）
codex 對抗審查（讀碼）          →  R1 九條 must-fix，**沒有一條是這兩個**
                                   —— 它讀出了 ACL 邏輯的漏洞，而 `pg_catalog.nullif` 讀起來很正常
我自己複查                      →  我加前綴的當下，正在【遵守一條真的規矩】
                                   ⇒ 複查時看到它，只會確認「嗯，有加限定」
```
📌 **那個前綴讀起來不像錯誤,它讀起來像【紀律】。** 這是它躲過所有人的原因。

## 🔴 判別句

> **那個前綴,你有沒有確認它指的東西【真的是一個函式】?**

具體怎麼查(一行,不需要 DB 以外的東西):
```sql
select proname from pg_catalog.pg_proc where proname = 'nullif';   -- ⇒ 0 列 ⇒ 它不是函式
select proname from pg_catalog.pg_proc where proname = 'btrim';    -- ⇒ 有列  ⇒ 它是   ← 正對照
```
**兩個世界印不同的東西。** 沒有正對照的話,「0 列」與「我查詢寫錯了」分不開。

### 已知會被誤加前綴的一族(**不完整,而不完整這件事就是重點**)
```
NULLIF / COALESCE / GREATEST / LEAST / CASE / CAST / EXTRACT
current_user / session_user / current_date / current_timestamp / localtime
```
⚠️ **這張表列得越像完整,越容易讓沒命中的那一類靜默通過。**
⇒ **不要拿它當 checklist,拿上面那條查法當 checklist。**
