# V 窗 traps(2026-08-18 · 複驗/對抗審查窗)

> 依 `README.md` 慣例:一窗一檔、暫存待併入 canonical `../guard-and-instrument-traps.md`。

> 🔴 **四條的母題都是同一個:量到的是 A,講出去的是 B。** 而四種變形的**引信位置各不相同**,所以分開寫。

## V-1 一個【真的數字】被拿去支持一個它沒有支持的結論

**當班實錘**:`SupabaseProductAdapter.ts:195` 註解逐字「實測 3 個分類破千(1,642 / 1,627 / 1,295,2026-08-17 anon 側 production)…**於是它看起來像「全部」**」。
我讀到這句 ⇒ 判定「分類頁的商品靜默消失、客人看不到」⇒ 寫進候選清單 ⇒ **主視窗端給了 Sean**。
**真站實測推翻**:分類頁「外觀與後視鏡」2822 件,第 1 頁「顯示 1-50 / 共 2822」、分頁列到 57、第 57 頁「2801-2822」**末頁到得了**,22 = 2822−2800 對得上 ⇒ **零截斷,客人看得到全部**。

🔴 **那個數字是真的**(我自己用 exact count 逐一量過 107 個分類,三個破千數字逐字對上)。**錯的是我把它當成另一件事的證據。**
- 那三個是**子分類**,而畫面篩選是**上層分類**。
- 我查的 `listByCategory` **根本不是分類頁走的那條路**(分類頁走 `fetchCatalogPage` → RPC `search_catalog_by_vehicle`,有 total 有分頁)。

**與「數字錯」完全不同**:數字錯有機會被複算抓到;**數字對而推論錯,複算永遠是綠的。**

**下次那一刻要做的**:引用一個數字去支持結論前,問**「這個數字量的是不是我結論講的那個東西?」** —— 具體到本例是:**這個數字量的是「資料庫裡有幾筆」,而我的結論講的是「客人看得到幾筆」。中間隔著一整條呼叫鏈。**

## V-3 同一支 grep、同一次執行,**同時往兩個方向錯**

**當班實錘**:數「撈清單卻不取完整性訊號」的地方。
```
36  原數:git grep -nE '\.range\(|\.limit\(' -- 'packages/adapters/src/supabase/*.ts' \
        | grep -v '\.test\.' | grep -vE "count: 'exact'"
22  🔴 扣掉【註解行】—— 14 個命中是 * 或 // 開頭的說明文字,不是呼叫   ← 多算
 9  🔴 再扣掉【方法內其實有 count,只是不在同一行】                    ← 少算
    成因:-v "count:'exact'" 是【行級】排除,而 count 宣告與 .range() 在同一方法的不同行
```
⇒ **高估 4 倍。** 而**兩個誤差方向相反、會互相抵消一部分** ⇒ 比單向錯更難察覺:總數看起來「差不多合理」。

🔴 **而我當班稍早才用「grep -c 把註解當程式碼」抓過別人**(T① 那格 waitFor 9 vs 真呼叫 4)。**知道規則不等於執行規則。**

🔴🔴 **同一天,同一條坑,我在【自己寫的那份表】上又踩了一次** —— `V-051` 立場表的 §2 統計原本寫:
```
fail-closed      7 處(#1 #2 #4 #6 #7 #8 #9 #10)   ← 列了 8 個編號,寫 7
fail-open + 明示 4 處(#5 #11 #12)                  ← 列了 3 個編號,寫 4
fail-open 無明示 1 處(#3)
```
**合計 7+4+1 = 12,與表格列數 12 相符 ⇒ 看起來完全正常。** 而**分項各錯一個、方向相反、剛好抵消**。
⇒ **總數對不代表分項對。** 抓到它的不是複算總數,是我加第 13 列時**逐一數編號**。
⇒ **對照方法**:寫「N 處(清單)」這種句子時,**讓清單自己算出 N**(我最後是跑一小段 python 逐項分類再 Counter),不要人工填 N。

**下次那一刻要做的**:行級 grep 出來的數字要當結論前,兩件事各做一次 ——
① **扣註解行**:`| grep -vE ':[0-9]+: *(\*|//)'`
② **問排除條件的作用域**:我排除的那個字面,和我要找的那個呼叫,**保證在同一行嗎?** 不保證 ⇒ 行級排除是錯的量具,要回到**方法/區塊**層級判斷。

## V-4 共用樹的「零留痕」只能靠**歸屬**證明,不能靠計數

**當班實錘**:在主樹做突變複驗,動手前 `git status --porcelain` = 3,動完 = 5。
兩筆新的是 `today-read.ts` / `rule-based-engine.ts` —— **我沒碰過**;而原本那筆 `phase-1-backlog.md` 消失(有人 commit 了)。
⇒ **「前後數字一致」在八窗共用的主樹上本來就不成立**,拿它當零留痕證據會同時產生偽陽與偽陰。

**我實際用的證法**:我碰過的那支檔 `cksum` 與備份**逐字相同**(`4226791685` / `4193481617` / `1245510601` 各自對上),其餘 dirty **逐筆指出屬於誰**(附該檔 last commit 或它正在被誰改)。

**下次那一刻要做的**:共用樹上報零留痕,報的是**逐筆歸屬 + 我碰過那幾支的 cksum**,不是一個總數。
📎 併帶:**別窗工作樹的寫入可能被權限層擋下**(當班兩次)。那時**不繞道、不請人代跑** —— 改用「複本突變」:確認靶檔 runtime import 情況 ⇒ 複製進 scratchpad ⇒ 在複本上突變 ⇒ 用真函式跑。**repo 內零檔案被改**,而結論一樣硬(先 `diff` 證明兩樹該檔逐字相同)。

## V-5 🔴 同一個人、同一夜、兩種標準 —— **而分野是「趕不趕」,不是「懂不懂」**

**當班實錘**:同一夜我做了三次突變複驗。
```
錢那兩顆(refund-judgment / settle-charge)  ⇒ 用【複本法】:複製進 scratchpad、在複本上突變、
                                              用真函式跑 ⇒ repo 內零檔案被改 ✅
C 窗那顆(picking-doc)                      ⇒ 🔴 直接 cp 覆蓋【別窗施工中】的工作樹
```
兩者我都知道複本法。差別只有一個:**第三顆我想快一點。**
後果:那棵樹 `porcelain` = 2(`picking-doc.tsx` + `page-measure.test.tsx` 都是 C 窗未 commit 的修改),而我**看到了那個 2、判成「不是我的所以無所謂」**。還原後我的備份與工作樹該行不同 ⇒ **我無法證明沒吃掉它剛寫的東西**(我只備份了要動的那一支,沒記錄動手前它那兩個檔的 cksum)。

🔴 **「知道正確做法」不是防線,因為趕的時候放棄的正是正確做法。** 防線只能是機械的:
**動手前 `porcelain` 不是 0 ⇒ 先問「這些 dirty 是誰的」,而不是「這些不是我的」。**
**別窗施工中的樹不當突變靶** —— 要嘛等它 commit,要嘛複本法。
📎 受害窗補的半句(同樣機械):**「不是我的」與「沒有人在用」是兩件事,而它們在 `git status` 上長得一樣。**

### V-5b 🔴🔴 **後來證實我【真的覆蓋了】—— 而證據是受害方給的,不是我自己找到的**

我當時報「**我分不出**是我覆蓋了、還是它之後又改回來」(我只備份了要動的那一支,沒記錄動手前它那兩個檔的 cksum)。
**C 窗分得出來,而且方法不需要 cksum** —— 它的動作序列:
```
① 它突變:「200 項上限」→「200 個上限」
② 它還原:跑 python 改回「項」⇒ 腳本印出「還原」
③ 它跑全量 ⇒ 3 failed,其中一格抱怨 expected … to contain '200 項上限'
④ 它開檔看 ⇒ :175 竟然還是【個】—— 而那個「個」正是【我備份裡的版本】
⇒ 時間軸對得上:我的 `cp 還原` 發生在它的 python 還原【之後】,把它的「項」蓋回「個」
```
🔴 **判別法(受害方給的,值得單獨記)**:**「我做了 X 而檔案不是 X」= 有第三方寫入。不需要 cksum,只需要記得自己做過的順序。**

🔴🔴 **而最該記的是它的歸因**:它當時把這件事記成「**還原沒吃到**」(commit body 就是那樣寫的)—— **那是錯的歸因,而它是最自然的那個。**
```
加害方(我)  沒察覺 —— 因為我的還原「成功了」,cksum 對得上我的備份
受害方(它)  自責   —— 一個「我明明做了而它沒發生」的小異常,預設歸因是【我自己疏忽】
⇒ 🔴 兩邊都不會發現。第三方寫入因此變成隱形的。
```
⇒ **這一則的完整形狀需要兩個人**:我提供「我做了什麼」,它提供「它觀察到的異常」。**任何一邊單獨都拼不出來。**
⇒ 併入 canonical 時**兩面要寫在一起**,只寫加害方那半(「動手前問 dirty 是誰的」)會漏掉:**受害方要學的是「不要把『我做了 X 而它沒發生』預設歸因成自己」。**

📎 **`../mutation-harness-restore.md` 要補一半**:它寫的是「靶檔不乾淨時 `git checkout` 會吃掉**你自己的**改動」;
**另一半是「不乾淨也可能是【別人正在改】,而那時連 `cp` 還原都會吃掉他的」。**

📎 併帶:**我報這件事時有的證據是「突變內容 grep ⇒ 0、測試 43 passed」,而我明寫了「現在綠 ≠ 它的改動沒被我吃掉」**(它可能有一段還沒寫完的東西不見了而測試照樣綠)。**證據 A 證不到 B,就要講出來** —— 尤其在自己造成的風險上。

## V-6 🔴 **讀一份操作文件,永遠讀不出「這一步我做不到」** —— 要真的照字面做一次

**當班實錘**:`pcm-customers` `docs/reviews/2026-08-17-heartbeat-e683-apply-runbook.md`(給 Sean 對著正式庫逐字照做的 apply 單)。
```
另一個窗已經【結構審】過它:每一步有沒有寫「你應該看到什麼」、失敗那格會不會導向「再試一次」⇒ PASS
🔴 而我用【第一次讀這份單子的人】的身分去跑,第一步就卡住:
   §4 逐字「在 Supabase 的 SQL editor 貼下面這一段」
   ⇒ 我試了 REST rpc/exec_sql ⇒ 404;找直連字串 ⇒ .env.local 只有 NEXT_PUBLIC_SUPABASE_URL
   ⇒ 那個介面【只有 Sean 有】,而單子的核心驗證步驟綁死在它上面
```
🔴 **為什麼「讀」抓不到**:**讀的人會自動補完** ——「那就在 Dashboard 貼一下嘛」。
**跑的人才會發現自己貼不了。** 補完的動作發生在讀者腦內,快到不會被察覺成一個假設。

🔴 **而它真正的代價不是「不方便」**:單子在失敗那格叫他「**回報施工窗**」,
**而施工窗跑不了同一段** ⇒ **一份求援指示,指向一個幫不上忙的人。**
⇒ 出事那天他只能再貼一次、把螢幕上的字唸給我們聽。

**下次那一刻要做的**(判別句):
> 🔴 **這份文件裡的每一步,有沒有人真的照字面做過一次?**
> —— 而「照字面」的意思是:**做不出來時不要用「我知道它想做什麼」補完它。做不出來本身就是一個 finding。**

📎 **這條與「開伺服器跑真的」是同一條,只是載體從【畫面】換成【文件】。**
Sean 的通則逐字是「不用再用 artifacts,直接來真的但是開伺服器做+看」——**射程比他自己講的還寬:
替身不只有 mock 畫面,【一份沒有人跑過的操作文件】也是一種替身。**

📎 併帶(同一次跑出來的):**②「表建好了沒」那一格我用一發 REST 就答出來了**(含正負對照)
⇒ **證明那一格【不需要】SQL editor** ⇒ 建議拆開時我不是提意見,**是先證明拆得開**。
**「先證明它做得到,再建議這樣做」比「建議這樣做」硬。**
