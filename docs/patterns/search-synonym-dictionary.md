## 1. 🎯 為什麼字典【不能】被「比對規則」取代(2026-09-04 量,分母 = 當時 32 列)

```
把比對從「開頭」改成「包含」之後:
  5 列  變冗餘(規則自己就找得到)
  1 列  看順序(防倒球 ⇒ 車身防倒球與滑塊 777 / 輪軸防倒球 326)
  0 列  會被送去【錯的】分類
 26 列  規則一個都找不到  ← 🎯 這 26 列就是字典的價值
```
🎯 **那 26 列是「俗稱與正式名【字面上毫無關係】」** ——
`來令片 ⇒ 煞車皮` · `卡夢 ⇒ 碳纖維部品` · `香菇頭 ⇒ 空氣濾芯` · `下巴 ⇒ 整流罩與下導流`。
⇒ 📌 **任何字面規則都吃不到它們。** 所以「改解析器就不用字典了」是錯的。

⚠️ **射程**:5/1/0/26 這組數字是**當時 32 列**下的。字典長大它會變 ⇒ **引用前重跑**
(做法:拿 `foldSearchTerm` 對「有貨的分類名」做 `includes`,見 `search-synonyms.test.ts` 的形狀)。

## 2. 🎯 「多顆膠囊」對這一半的影響 ≈ 0(2026-09-04 量)

```
32 列裡, 在「一個俗稱可以帶多顆膠囊」的世界下會變的:【1 列】(防倒球)
其餘 31 列 union 恰好 = 1 ⇒ 與今天一模一樣
```
🔴 **而那是【下界】** —— 它只看得到「俗稱是分類名的一部分」那種多重性。
**語意上的多重性(俗稱本身就指兩類東西)量不到 —— 沒有語料**(見 §5)。
🔵 **而我試過一個代理指標並判它壞掉,寫在這裡免得下一個人重做**:
查每個 `to` 的**兄弟分類**(同父層、有貨)⇒ `整流罩與下導流` 有 **12 個兄弟**,
而 `下巴` 不是那 12 個的意思 ⇒ 📌 **「有幾個兄弟」與「這個俗稱指幾個」沒有關係。**

⚠️ **而單值是寫在型別裡的**:`search-synonyms.ts` 的 `to: string`(單數)、
`synonymFor()` 回 `SearchSynonym | null`(**只回第一個命中的那一列**)。
⇒ 要多值就得改型別。**而改型別是解析器那一半的事**,不要單邊動。

✅ **一道取代兩道而且嚴格更強** —— 它順帶擋住「`to` 不在目錄樹」「`to` 沒有商品」,
因為那些在真的解析器裡本來就會表現出來。

⚠️ **它自己的天花板(不要假裝它是機制)**:餵給解析器的目錄樹是**用快照造的**,

🔴 **本檔【刻意不用行號】指 `parse-search-facets.ts`** —— 那支檔現在有人在改(多顆膠囊那片)
⇒ 行號會漂,而漂掉之後【指錯的行號比死連結難發現】(它會指到一個真實存在但不相干的地方)。
⇒ 📌 判準不是「行號好不好」,是**那支檔現在有沒有人在寫它**。

📎 完整病歷與「怎麼驗一把尺有沒有真的接上」⇒ `docs/patterns/guard-and-instrument-traps.md`
(2026-09-04 三條,搜「複述」與「截斷」)。

## 4. 🔴 一列字典可以【完全合法而永遠沒有效果】—— 四種死法

| 死法 | 今天誰在擋 | 失效條件 |
|---|---|---|
| `to` 打錯字 / 分類不存在 | §3 那道閘(解析器回 null) | 分類名快照過期 |
| `to` 的分類**沒有商品** | §3 那道閘 + `SEARCH_CATEGORY_EMPTY_NAMES` | **快照要人重跑**,見 §5 |
| `from` 被**有貨的**分類名前綴搶先命中 | §3 那道閘 | 規則改了 ⇒ 它會紅(那是對的) |
| `from` **帶空白** | §3 那道閘 | —— |

🛑 **最後一種是結構性的,不是資料錯**:`parse-search-facets.ts` 的 `splitWords()` 先用空白切開,
然後 `parseSearchFacets()` 裡那個 `for (let i = 0; i < words.length && category === null;` 迴圈**一個字一個字**(`words[i]`)拿去查字典 ⇒ **字典永遠只會被餵到單一個沒有空白的詞**。
⇒ 📌 `DB Killer` 那種俗稱**是真的**(台灣車友確實這樣講),**而這條路吃不到它**
⇒ **要它得改解析器,不是加一列字典。**

## 6. `SEARCH_CATEGORY_EMPTY_NAMES` 那份快照:今天還準,而它靠人


⇒ ✅ **而那個曝露面比想像小**:字典只指向 **27 個**分類(2026-09-04;**這個數會跟著字典長**)

## 🔴🔴 多目標:一個俗稱指【兩個分類】(Sean 2026-09-04 裁「並聯」)

Sean 原話逐字:
> 魚雷管 尾段排氣管 319 / 白鐵管 全段排氣管 251
> **這兩個搜尋出來都是 全段排氣管 尾段排氣管 並聯**

🎯 **他推翻的是「一個俗稱只能指一個分類」這個前提**,不是選了哪個選項。

### 契約(主視窗 `-94` 2026-09-04 裁;兩半各自落)

```
字典層(本檔講的這張表)  一個俗稱 ⇒ 【多筆列】(同 from、不同 to), 不是一列 to 陣列
  理由:量測台是【逐筆】量的 ⇒ 一筆一個 to 才餵得進去
解析層(線【前台】`-front`)同一個 from 的多筆 collect 成陣列 ⇒ `?categories=a,b`
DB 層                    ✅ 已上線 —— Sean 09-04 貼了 20260904160000_..._multi_category.sql
```

### 🛑 而今天只有一半在線上 —— 第二列是【待命】不是【失效】

`synonymFor` 用 `.find()` ⇒ **第一列勝**;`ParsedFacets.category` 今天是 `string | null`(單數)
⇒ 第二列在解析器那一層**還沒有出口**。

🔴 **順序是承重的**:第一列必須是**今天已經在線上生效**的那個 `to`。
把新列排到前面 ⇒ **靜靜換掉線上行為**,而 diff 看起來只是「加了一列」。

### 🔬 而釘住它的那一格, 是被一發突變逼出來的

我原本寫的是「解析器解出來的,必須等於**同名第一列**的 `to`」——
🛑 **那兩邊會一起動**:把兩列對調,第一列變成另一個 `to`,`.find()` 也回同一個
⇒ 兩邊還是相等 ⇒ **全綠**。實測:對調兩列 ⇒ `rc=0, 187 全過`。

📌 **一個從「我要寫的那行碼」推出來的期望值,從出生起就抓不到那行碼的錯。**
✅ 修法 = 期望值要來自**外面**:把今天真正生效的 `to` **寫死**在測試裡,
來源是 Sean 原話裡那兩組數(魚雷管 ⇒ 尾段 319 / 白鐵管 ⇒ 全段 251)。

### ✅ 今天守著它的三格(`search-synonyms.test.ts`)

```
① 今天生效的那一個 to 寫死    ⇒ 對調兩列 ⇒ 紅(實測 rc=1)
② 這兩個俗稱必須是多目標      ⇒ 有人「整理」掉其中一列 ⇒ 紅(實測 rc=1)
③ 解析器一旦長出【複數】分類  ⇒ 紅 —— 🎯 那個紅就是「回來把字典這半接上」的通知,
                                 它不依賴任何人記得
```

### ⚠️ 量測台(`scripts/weigh-synonym-candidates.py`)**答不了第二目標列**

有它沒它印同一個數(因為解析器沒有出口)⇒ 它會印**純冗餘**,而那句話是假的:
**它答的是「今天用不到」,不是「沒有價值」。**
⇒ 那支腳本已經改成**當場拒跑並說明理由**,不給一個看起來合理的數。
