# 突變 harness 的「還原」怎麼寫才不會被殺掉

> **來源**:2026-08-16 A 窗實錘 —— 一份**被突變的 migration 被 commit 進正式分支**(`02dd510e`,修在 `e37fbea5`)。
> **本檔要回答的那一刻**:「我要跑一支**會改檔案**的腳本」。

---

## 1. 病灶不是「忘了還原」,是「用一個會殺掉還原的方式跑它」

```bash
bash mutation-harness.sh 2>&1 | head -2
```

`head -2` 讀完兩行就關掉 pipe ⇒ 上游收到 **SIGPIPE** ⇒ 腳本**死在「已套用突變、還沒還原」那一刻**。
那份被突變的檔就留在工作區,而**接下來的 `git add` 會把它一起帶走**。

🔴 **`| head` 是每個人每天都在打的東西。** 這不是紀律問題,是**工具組合**問題 ——
所以修法不能是「記得不要接 head」。

---

## 2. 🔴 修法在 **trap body**,不在訊號清單(本節 2026-08-16 全部重寫)

> ⚠️ **本節初版是錯的。** 它寫「SIGPIPE 不觸發 EXIT trap ⇒ 要加 `PIPE`」——
> **兩句都不成立**,而且加 `PIPE` 那條**修不好任何東西**。
> 下面是我用最小可控樣本量出來的(macOS bash 3.2,五組)。

| 情境 | 檔案結果 |
|---|---|
| A. `trap … EXIT`,body **`cp` 先** | ✅ 還原 |
| B. `trap … EXIT`,body **`echo` 先** | 🔴 **沒還原** |
| C. `trap … EXIT`,body **`echo >&2` 先** | ✅ 還原 |
| D. `trap … EXIT INT TERM HUP PIPE`,body `echo` 先 | 🔴 **還是沒還原** |
| E. `trap … EXIT` + `set -o pipefail`,`cp` 先 | ✅ 還原 |

🔴 **機制**:**EXIT trap 有跑**。壞的是 trap 的**第一行 `echo` 往一個已經沒人讀的 pipe 寫** ——
那一寫就死,**還沒走到 `cp`**。
⇒ **A/C 會過不是因為訊號,是因為 `cp` 排在那個會死的 `echo` 前面。**
⇒ **D 證明加 `PIPE` 沒用**:訊號被接管之後 `echo` 改成回非零,而 `set -e` 讓 trap 函式**當場中止**
   —— 一樣走不到 `cp`。

```bash
trap restore EXIT          # ✅ 訊號清單這樣就好（要保險可加 INT TERM HUP）
restore () {
  cp "$B" "$T"             # 🔴 會改檔案的動作【排最前面】
  echo "..." >&2           # 🔴 要印字就印到 stderr（stderr 沒有被接進那個 pipe）
}
```
🔴 **絕對不要把 `PIPE` 加進清單** —— 它修不好上面任何一格,而**接管 SIGPIPE 會讓「寫入失敗」
從「終止行程」變成「回非零繼續跑」**,在會重複寫 stdout 的迴圈裡有打轉的風險。

### 🔴 兩個判別點(2026-08-16 第二輪:兩個窗量到不同結果,判別點誰都沒先寫下來)

#### 判別點 A —— `set -o pipefail` 要寫在**哪個 shell**

| 位置 | `bash harness.sh \| head -2` 的 exit |
|---|---|
| 只寫在**腳本裡**(本檔範本初版的放法) | **0** |
| 寫在**跑 pipeline 的那個外層 shell** | **141** |
| 腳本裡沒有、只有外層有 | **141** |

🔴 **`bash harness.sh | head` 這個 pipeline 是【外層 shell】組起來的。**
腳本自己只是上游成員,**它裡面的 `pipefail` 管不到把它包起來的那一個。**
⇒ 本檔範本初版把「讓 pipeline 的失敗不會被右端的 `head` 蓋掉」這句註解,
**寫在了它唯一做不到那件事的位置**。
⚠️ **與輸出大小無關** —— 500 行 + 外層 `pipefail` 一樣是 141(兩個窗各自量到同一結果)。

#### 判別點 B —— 加了 `PIPE` 之後會不會**掛住**

我第一輪量「加 `PIPE` 會無限迴圈」**沒重現**,另一個窗量到**會**。第二輪找到判別點:
**不是主體輸出的大小,是 trap body 有沒有【反覆】往那個死掉的 pipe 寫。**

| trap 含 `PIPE`,主體輸出 2MB | 結果 |
|---|---|
| a) `echo` 一次再 `cp`(`set -e` 讓 trap 中止) | 1 秒結束,**但檔案沒還原** ← 真正的傷害 |
| b) `echo \|\| true` 再 `cp` | 1 秒結束,還原了 |
| c) **trap body 裡迴圈寫 stdout**(`\|\| true` 讓它繼續) | 🔴 **掛住,`kill -9` 才停** |

⇒ **`PIPE` 把「寫失敗就終止」換成「寫失敗回非零繼續」** ——
有迴圈餵它就打轉,沒迴圈就只是**安靜地跳過還原**。**兩種都是壞的,所以結論不變:不要加 `PIPE`。**

⚠️ **誠實邊界**:另一個窗回報的判別點是「主體輸出撐不撐破 pipe buffer」,
**我在 2MB 也沒重現掛住**(見上表 a/b)。**兩邊的觀察都在,而我只能為我這三組負責。**
**不要在本檔寫任何 pipe buffer 的具體位元組數 —— 那個數我沒有量過。**

### ⚠️ 平台邊界

上面五組**只在 macOS bash 3.2 量過**。**Linux + bash 5 未驗** —— 而 **CI 跑的是 Linux**。
⇒ CI 上的行為**標為未確認**,不要引用本節當 CI 的依據。

## 3. 可複製的範本

```bash
#!/usr/bin/env bash
set -euo pipefail   # ⚠️ 這裡的 `pipefail` **管不到** `bash 本腳本 | head` 那個 pipeline ——
                    #    那個 pipeline 是【外層 shell】組的，這裡是上游成員（§2 判別點 A 實測）。
                    #    🔴 要讓「腳本被 SIGPIPE 打死」變成看得見的 exit 141，
                    #       `set -o pipefail` 要下在【你打指令的那個 shell】。

TARGET=path/to/file-under-mutation
BASE=/tmp/$(basename "$TARGET").base
SHA=/tmp/$(basename "$TARGET").sha

# 🔴 基準【當場照】—— 不要沿用上一次留在 /tmp 的那份。
#    （2026-08-16 另一次實錘：沿用舊基準的腳本把「後來新加的斷言」一起還原掉，
#      而那一輪「三發全紅」根本沒測到新斷言。）
cp "$TARGET" "$BASE"
shasum -a 256 "$TARGET" | cut -c1-16 > "$SHA"

restore_and_verify () {
  # 🔴 **改檔案的動作排最前面** —— 它前面放任何一個往 stdout 寫的東西，
  #    在「輸出被 `| head` 截斷」的情況下 trap 會死在那一行、走不到這裡（§2 實測 B）。
  cp "$BASE" "$TARGET"
  local now; now=$(shasum -a 256 "$TARGET" | cut -c1-16)
  # 🔴 驗【結果】不是驗「cp 跑了」—— cp 的 exit 0 不等於內容回來了。
  if [ "$now" != "$(cat "$SHA")" ]; then
    echo "❌❌ 還原失敗：現在 $now，基準 $(cat "$SHA") —— 檔案是髒的，不要 commit"
  else
    echo "✅ 還原已驗（shasum $now）" >&2   # 🔴 印到 stderr，不要用被截斷的 stdout
  fi
}
# 🔴 訊號清單只要 EXIT（加 INT TERM HUP 是保險）。**不要加 PIPE** —— 見 §2 實測。
#    真正決定成敗的是上面那個 body：`cp` 排在會死的 `echo` 前面。
trap restore_and_verify EXIT INT TERM HUP

# ── 每一輪：M0 基準必跑 ──────────────────────────────────────────────
# 🔴 先跑一發【沒有突變】的，確認它是綠的。
#    沒有這一發，「斷言本身壞掉」會被讀成「突變成功」——
#    2026-08-16 我的判序斷言用了 POSIX 非貪婪正規式而整段吃到底，
#    基準就紅，而那一發是唯一救得了我的東西。
run_case "M0 基準（未突變，應綠）"

# 每一發突變：anchor 必須命中，否則停 —— 沒進去的突變會製造假的「沒有判別力」
apply_mutation () {
  python3 - "$TARGET" <<'PY'
import sys
p=sys.argv[1]; s=open(p,encoding='utf-8').read()
a="<被突變的字面>"
assert a in s, "突變 anchor 沒對上 —— 停，紅綠都不算數"
open(p,'w',encoding='utf-8').write(s.replace(a,"<突變後>",1))
PY
}
```

### 三條硬性的自檢

| 問題 | 答不出來就是壞的 |
|---|---|
| **基準是什麼時候照的?** | 必須是**本次開跑當下**,不是沿用 `/tmp` 裡上一次那份 |
| **突變真的進去了嗎?** | `assert anchor in s` —— 沒命中要停,不是靜默跳過 |
| **還原之後我驗的是什麼?** | **shasum 相同**,不是「`cp` 的 exit code 是 0」 |

## 4b. 突變後【綠】的三種讀法 —— 與一顆讓突變自證「我有被執行」的信標(2026-08-18 T 線,A′3 實錘)

> 🔴 **分水嶺先問(這句在最前面)**:我這發突變改的行為,落在【可達輸入】上嗎?
> —— 可達但沒被測 ⇒ 補測(①);不可達 ⇒ 不用補(④)。看到 GREEN 就去加斷言是最常見的錯。
> (同族問句:「我餵的這組值,上游產得出來嗎」——問在突變這一側。)

> **「突變後綠」有【四】種成因,而它們印出來一模一樣**:
> ① 斷言沒判別力(我們以為在找的;實錘=over-delta,`delta>250` 是【可達但沒測】的輸入)
> ② 突變根本沒被執行到(打在死分支)
> ③ 突變被執行了,但效果被別處冗餘遮蔽(A′3:SKU 在三渲染點各出一次)
> ④ 等價突變:突變在【可達輸入】上不改變行為,任何測試都分不出——而它**不是**弱斷言
>   (實錘:refund.ts:334 `=== remainingQuantity`→`>=` GREEN+EXEC,因上游 :311 已
>   `if (req.quantity > remainingQuantity) reject` ⇒ 到 :334 時恆 ≤ ⇒ 兩者在可達輸入上恆等)。
> ②/③/④ 都會被誤讀成 ①=「發現斷言沒力」,而那個「發現」是假的。

**機制(零依賴,不裝 coverage):突變時讓那一行自己帶信標** —— 在被突變的表達式前掛一發
stderr 寫入,執行到就會出現在 run log 裡:

```text
突變字面範例(JSX 內的 map 源):
  原  {lines.map((l) => {
  變  {(process.stderr.write('MUT-BEACON\n'), lines.slice(0, 10)).map((l) => {
跑完判讀(log 就是你本來就重導的那份):
  grep -q "MUT-BEACON" run.log && echo EXECUTED || echo NOT-EXECUTED
```

**三讀法 triage(突變後綠時走這個,不要直接寫「斷言沒力」)**:

| 測試 | 信標 | 讀法 |
| --- | --- | --- |
| 紅 | (不用看) | 突變有效、斷言有力,正常收 |
| 綠 | NOT-EXECUTED | **② 突變無效**(死分支/沒被行使的路徑),換位置重打,這發紅綠都不算數 |
| 綠 | EXECUTED | **①③④ 之一**:先問分水嶺(可達否)→ 再換一個【非等價】突變打同一行。非等價突變 RED ⇒ ④(這發是等價突變、斷言其實有力);非等價突變仍 GREEN ⇒ 掃冗餘產出點區分 ①(補測)vs ③(留引信) |

**③ 遮蔽 vs ④ 等價 —— 未來不一樣,引信位置不同(2026-08-18 實錘,主視窗令分開列)**:

| 類 | 現況 | 變成真洞的條件 | 引信寫哪 |
| --- | --- | --- | --- |
| ③ 遮蔽 | 效果被下游冗餘吃掉 | **遮蔽層被拿掉** | 遮蔽層 檔案:行號(哪天刪它、這格從③變①、零訊號) |
| ④ 等價 | 突變在可達輸入上恆等 | **上游那道 reject 消失**(輸入變可達) | 上游守門 檔案:行號,不在被突變那行 |

關掉,超退並沒有真的通過——被下游 `invalid_amount`(:314-316 badComputed)部分接住;抓到

不是 `expect(r.ok).toBe(false)`。⇒ 哪天有人把它弱化成 ok 級斷言(一個看起來完全合理的簡化),
引信全綠失守,`:334` 的 ④ 在無聲中變回 ①。**引信不只是「哪一行」,還是「那一行被哪個層級的斷言守著」。**
⚠️ 而這條 V 窗是【自己踩出來】才看到的:第一版突變 harness 只斷言 `ok` 布林 ⇒ 三個變體全紅/全綠
糊成一片、分不出 ⇒ 改成 kind 級才有解析度。**量具解析度不足時,看起來會像「結果沒有差別」
(=假的等價/假的無判別力)** —— 突變 harness 自己也適用「量錯東西」那族。

**雙向驗證(2026-08-18 實跑,兩個世界印不同的東西)**:A′3 第一發原樣重放+信標 ⇒

同 fixture 下把突變改埋在 cancelledRows 分支(fixture 無取消列)⇒ test=GREEN
beacon=NOT-EXECUTED(=②被抓到)。

⚠️ 信標寫進 stderr,vitest 會帶進你重導的 log;若你的跑法吞 stderr,信標盲。
⚠️ 信標只判「執行過」,不判「執行結果影響了斷言」——③ 的排除仍要人掃冗餘產出點。
🔴 **還原機制對「你沒列進清單、卻被寫壞的檔」完全沉默(2026-08-18 實錘,harness 自己的 bug)**:
harness 的 `restore_all` 只還原你列進去的 source 檔並印 RESTORE-OK ——而一個參數索引錯誤
讓 `npx vitest … > "$LOG"` 的 `$LOG` 算成了【測試檔路徑】,vitest 輸出【覆寫進三個 tracked
測試檔】(各被砍數百行)。cksum 對「我列的那些」全過、RESTORE-OK 照印——它對那三個
【我沒列進還原清單】的檔是完全沉默的。⇒ 抓到它的【唯一】那道是**收工前的 `git status --porcelain`**:
source 檔 cksum 還原騙不過「沒列進清單卻 M 了的檔」。⇒ **收工 git status 不是儀式,它是唯一
涵蓋「我沒想到的檔」的那道。** root cause 同族「輸出的目標要由【結果】決定、不能算錯位置」——
修法在機制層(重導目標槽與資料路徑槽分開),不是提醒層。

🔴 **信標對【文字掃描型測試】盲(2026-08-18 F3 實錘)**:守門若是「掃 SQL/原始碼【文字】」
而不執行被突變的 code(例:refund-remaining-single-source 掃 migration 文字),那你埋進
註解的信標【永遠 NOT-EXEC】——因為那段根本沒被【跑】。⇒ 這裡 NOT-EXEC **不是**②(突變沒執行),
拿它判②會讓你一直重打、一直 NOT-EXEC、最後誤判「無法判定」。文字掃描型的自證是
**「我改的那個字串,在掃描器【讀到的那段】裡真的變了嗎」**(F3 第一發打錯 occurrence=改到
別的函式、掃描器讀的那段沒變 ⇒ 假 GREEN,與 A′3「沒打到被守的那個」同型)——不是 EXEC。
## 4c 🔴 **`git checkout <檔>` 當還原手段:靶檔【乾不乾淨】決定它是還原還是毀損**

> **來源**:2026-08-18 A 窗,同一輪突變裡連做三發,**前兩發沒事、第三發吃掉我的改動**。
> 🔴 **這是本檔 §1「用一個會殺掉還原的方式跑它」的續集,而且是它沒寫到的分支** ——
> §1 講的是「還原**沒跑到**」;本節講的是「**還原跑到了,而且做的事比不還原更糟**」。

### 發生了什麼(逐發,可對照)

```
發1 / 發2   靶檔 orders-table.tsx 是【乾淨的】（git status --porcelain 零輸出）
            突變 → 跑 → git checkout <檔> → diff 對備份逐字相同 ✅ 正確還原
發3         靶檔裡【有我自己未 commit 的真改動】（那一輪要收的 must-fix 本體）
            突變 → 跑 → git checkout <檔>
            ⇒ 🔴 它把檔案還原到【index 的版本】= 突變【和我的真改動】一起消失
```

### 為什麼它不會叫

```
git checkout <檔>  的語意是「拿掉這個檔的所有未暫存改動」
                   它【分不出】哪些是我要丟的突變、哪些是我要留的工作
⇒ 沒有錯誤訊息、rc=0、git status 變乾淨（看起來正是你想要的結果）
🔴 而「還原成功」與「連工作一起還原」在【git status 這個觀測面上長得一模一樣】
   —— 兩者都是「零輸出」。
```
⇒ **本檔母題「錯的那次和對的那次長得一樣」的又一個實例。**

### 修法(不是「更小心」)

```
🔴 一律 cp 備份，不要用 git checkout 當還原手段：
   cp <靶檔> "$SCRATCH/x.BAK"      # 突變【之前】
   …突變 → 跑 →
   cp "$SCRATCH/x.BAK" <靶檔>       # 還原
   diff <靶檔> "$SCRATCH/x.BAK"     # 🔴 驗，不是假設

⚠️ git checkout 只在【當場 git status --porcelain <靶檔> 零輸出】時才等價於還原。
   而那個前提會在一輪突變的中途改變（你收 finding 收到一半就不乾淨了）
   ⇒ 「這一輪開始時是乾淨的」不是依據，要問的是「【現在這一發】乾不乾淨」。
```

### 判別句

> **我要丟掉的那個改動,和我要留下的那個改動,現在住在同一個檔裡嗎?**
> 是 ⇒ `git checkout` **不能用**,它以檔為單位、分不出兩者。
> 🔴 **而這個答案在一輪突變的中途會從「否」變成「是」** —— 所以要在**每一發之前**問,不是開場問一次。

## 5. 判別句

> **我現在要跑的這支腳本,如果在中間被殺掉,會留下什麼?**
> 留下**檔案** ⇒ 它會被 commit ⇒ `trap … EXIT` + **`cp` 排在 trap body 第一行** + shasum 驗還原。
> (🔴 **不是**加 `PIPE` —— 它要嘛安靜跳過還原、要嘛讓 trap 打轉掛住,見 §2 判別點 B。)
> **而要讓「它死了」被看見,`set -o pipefail` 得下在【你打指令的那個 shell】,不是腳本裡。**
> 留下**叢集/DB 狀態** ⇒ 下一輪會跑在污染環境上 ⇒ 一樣要 trap,但症狀不同(每一發都看起來正常)。

> **而「我有還原機制」不等於「還原會跑到」** —— 這兩件事今晚各壞過一次。
