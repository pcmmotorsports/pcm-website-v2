# 一條線停住了,先分型再動手

> **誰該讀**:任何人接手、重啟、或被交辦一條「看起來停住 / 沒結論 / 沒人在做」的線。
> **什麼時候讀**:**在你說「那要開線」之前。**
> **這份檔的立場**:每一型都附 2026-08-16 當天的真實例 + 可重跑的判斷依據。
> 沒有實例的分型會被當空話跳過,所以這裡不收沒有實例的型。
>
> **為什麼需要這份檔**:「停住」是**症狀**,不是病。
> 三種完全不同的病共用這一個症狀,而**外觀一模一樣** ——
> 分錯型的代價不是白做工,是**做反**。

> ## 🔴 加新型 / 新實例的規矩
> 新條目 append 到檔尾、**只寫標題、不要自己編號**;型與型之間互相引用時**用標題文字不用編號**。
> (同 `guard-and-instrument-traps.md` 的規矩,理由相同:編號是全域狀態,而窗與窗之間看不見彼此。)

---

## 三個判別句(先問,再動手)

| 型 | 判別句 | 正確處置 |
|---|---|---|
| **甲 · 沒有落點** | 東西交出去之後,**回來的答案會被寫進哪個檔?** 答不出來 ⇒ 甲型 | **先指定落點,再去要答案。** 順序反了就會再掉一次 |
| **乙 · 結論住錯地方** | 下一個做這件事的人,**會讀到這個結論嗎?** | **把結論搬到他會讀的那份檔**;原處留指標 |
| **丙 · 照拍板在等** | 停的理由是「**做不下去**」還是「**還沒輪到**」? | **什麼都不做**,或回去問拍板的人要不要改順序 |

🔴 **順序很重要:先問丙,再問甲乙。**
因為丙型誤判的代價最高,而它最容易被當成前兩型。

---

## 丙 · 照拍板在等 —— **最危險的一型**

**特徵**:前提**還沒到**,不是被忘記。線本身健康,只是排在後面。

🔴 **為什麼最危險**:它長得跟「沒人在做」**一模一樣**,
而「重啟」一條照拍板在等的線 = **用一句「你不是說要做嗎」推翻當事人自己的拍板,而他不會發現。**

### 實例(2026-08-16,真的差點發生)
Sean 逐字:「**要建立好這個搜尋功能,之前有討論過,但是一直沒進行。**」
⇒ 主視窗當下的預設是「那要開線」。

**而實查**:
```
memory project_storefront-keyword-search-line ── 搜 `M-4b 換軌壓下未開工`
   08-08 Sean 自己拍 A，逐字：排 M-4b 之後開線
STATUS.md 當前狀態 ── 搜 `Milestone` ⇒ M-4b 後台重建，仍是現行主線
⇒ 前提【還沒到】，不是被忘記
```
**結果**:主視窗改成問他「要現在開嗎」,**他答維持** —— 那正是丙型的正確處置。
⚠️ **若沒問就派工,等於推翻他自己的拍板。**

### 判別工序(三步,都可重跑)
1. `grep` 這條線的 memory / spec,找**最後一次拍板的逐字**
2. 那次拍板如果寫了前提(「X 之後」「等 Y」),去 `STATUS.md` 查 **X / Y 現在到了沒**
3. **沒到 ⇒ 丙型。回去問要不要改順序,不要自己改。**

## 甲 · 沒有落點 —— 做完了、送出去了,回饋回來沒地方接

**特徵**:交付**發生過**,而**沒有人指定回饋要寫進哪裡**。
⇒ 回饋要嘛沒回來,要嘛回來了留在對話裡、隨 session 蒸發。

### 實例(2026-08-16)
商品編輯後台的【丁】方向畫面:
```
08-15 19:31 交付 OD `pcm-product-edit-screen`，B 窗逐字「已交付、Sean 正在看」
      ↓
此後零紀錄

數法：grep -rl 'pcm-product-edit-screen' docs/ ~/pcm-mailbox/ <memory 目錄>
     ⇒ 3 檔，全部是 B 窗 08-15 的信；docs/ 0 命中、memory 0 命中
     正向對照：全量 grep '商品編輯' ⇒ 11 檔（尺子量得到東西）
```
Sean 對這條線的逐字是「**目前最後也沒定論**」—— **與 repo 狀態完全吻合。**

🔴 **診斷**:不是沒人做,是**做完送出去、回來的東西沒有落點**。
🔴 **他抱怨的每一件事都已經被寫下來過**,而且在同一份 spec 裡 ——
**「沒定論」不等於「沒人想過」,它等於「想過的東西沒有變成他看得到的一個東西」。**

### 判別工序
- 問一句:**「這件事的答案回來之後,要寫進哪個檔的哪一節?」**
- 答得出檔名+節 ⇒ 不是甲型
- 答「先看看」「回報給主視窗」 ⇒ **甲型。先開好那一節,再去要答案。**

### 🔴 甲型的第三種形狀:**「這件有沒有人在做」本身也會沒有落點**

**最容易漏掉的一種,因為它不是關於工作,是關於【工作的狀態】。**

**實例(2026-08-16,發生在盤點這件事的人自己身上)**:
R 窗把「ADR-0004 加更正段」列進「建議下三件」,並標**⚪ 卡在沒有人**。
**而那件事在他寫下那句話之前就已經做完了**(commit `494b329c`,I 窗)。
```
主視窗知道 ／ I 窗知道 ／ 提建議的那個窗不知道
⇒ 三方各自都沒有做錯任何事
```
🔴 **「誰正在做什麼」如果沒有一個共同載體,它就跟任何其他甲型一樣會掉。**
⚠️ **而它掉的方式特別浪費**:掉的不是工作成果,是**別人重複去做同一件事的那段時間**。

**判別句**:
> **我要說「這件沒有人在做」之前,我是【查過】還是【沒看到】?**
> 沒看到 ⇒ 那是**我的視野**,不是**世界的狀態**。

**便宜的修法**:報「卡在沒有人」時**附上你查的範圍**(例:「我掃了 backlog 與 mailbox,沒掃各 worktree 的未推 commit」)——
**讓讀的人知道你的視野邊界在哪,他就能補上他那半。**

### ⚠️ 甲型修好之後,還有一個緊接著的坑:**只把答案寫進被指名的那一處**

**同一天、同一件事,兩個坑連著發生**:
`ADR-0004` 的更正段寫得很完整(兩個來源、原決議不刪、待辦明列),而 **`pg_jieba` 在該檔共 5 處**:
```
grep -c 'pg_jieba' docs/decisions/0004-m1-pre-launch-decisions.md   ⇒ 5
   :35   Q3 決議列        ← 已就地標更正 ✅
   :45 :46 更正段本身      ✅
   :86   §3.1 擴充性       ← 🔴 未提
   :116  M-6 上線前 checklist「search 切 tsvector + pg_jieba」  ← 🔴🔴 未提
更正段（40-66 行）內含 'M-6' ⇒ 0 ；含 '上線前 checklist' ⇒ 0
   （正向對照：同範圍含 'PGroonga' ⇒ 2，尺子量得到東西）
```
🔴 **`:116` 那一列是【上線前 checklist】,是會被拿去執行的東西** —— 它到今天還寫著要去做一件做不到的事。
📎 同族 memory `feedback_folding-a-finding-defaults-to-the-named-spot-only`:
**finding 給的是症狀的位置,不是病的邊界。** 折完之後拿舊字面**在同一支檔內**重掃一次,分母要印出來。

## 乙 · 結論住錯地方 —— 有答案,但下一個人不會讀到

**特徵**:結論**存在而且正確**,寫在一個**下一個做這件事的人不會打開**的載體(信、memory、對話)。
⇒ 下一個人會照**沒被更正的那份**做。

### 實例一:更正沒回到拍板檔(2026-08-16 挖出)
```
ADR-0004 Q3=A1 ── docs/decisions/0004-m1-pre-launch-decisions.md
   逐字：A1 PG tsvector + pg_jieba
      ↓ 2026-07-25 實測（MCP list_extensions 回 80 個擴充逐一比對）
pg_jieba 不在 Supabase 可用清單 ⇒ CREATE EXTENSION 不可能成功
      ↓
更正寫進 memory reference_supabase-no-pg-jieba-use-pgroonga
   該條逐字還寫著「請 Sean 重新拍 ADR-0004 的分詞路線」
      ↓
🔴 那次重拍沒有發生。ADR 那一行到今天沒改。
```
⇒ **任何人讀 repo 內最高階的決策檔,都會拿到一條蓋不起來的技術路線。**

### 實例二:🔴 **觸發條件被寫在沒有人會讀的那份檔裡**(這一種最隱蔽)

`docs/audits/2026-07-03-doc-debt-candidates.md`(10 條文件債,每條都是 Sean 決策題)
它自己寫了觸發條件,逐字:
> **建議下次動到該檔的 slice 順手提 multi-select**

**那個觸發條件成不成立 —— 實測**:
```
07-10 之後動過目標檔的 commit 數：
  docs/working-style.md         1
  docs/PHASE-1-NORTHSTAR.md     3
  docs/lessons-learned.md       4        ⇒ 合計 8 次
⇒ 觸發條件【成立了 8 次】，而【一次都沒有人提 multi-select】
```
**為什麼**:
```
docs/audits 被路由到的次數：
  CLAUDE.md 0 ／ AGENTS.md 0 ／ docs/patterns/index.md 0 ／ STATUS.md 0
正向對照（有被路由的目錄）：
  docs/patterns 11 ／ docs/runbooks 4
```
🔴 **⇒ 觸發條件本身住在一個零路由的目錄裡。**
**一個存放在「被觸發者永遠不會打開的地方」的觸發條件,不是觸發條件,是一張紙條。**

### 判別工序
- 問:**這個結論 / 這個觸發條件,住在哪個檔?那個檔被路由表指到嗎?**
  ```
  grep -c '<那個目錄>' CLAUDE.md AGENTS.md
  ```
- **0 ⇒ 乙型。** 搬到會被讀到的載體,原處留單行指標。
- ⚠️ **正向對照必跑**:拿一個確定活著的目錄數一次,證明尺子量得到東西。

## 🔴 三型可以同時成立,而處置要按最危險的那型走

`docs/audits` 那份清單**同時是甲型與乙型**:
- **乙**:住在零路由目錄
- **甲**:它指定的「落點」是一個**事件**(下次有人動到該檔),不是一個**位置**

⇒ **處置照乙型先做**(搬到會被讀到的地方),因為甲型的修法(指定落點)在乙型沒解之前**寫了也沒人看到**。

## 一條反向紀律:**不要用「看起來很舊」判斷一條線死了沒**

2026-08-16 實測兩批「一看就該清掉」的檔:
```
docs/proposals/stage-*.md   86 天沒動   ⇒ 被引用數 1 / 2 / 3 / 2 / 5   全部仍被引用
docs/recon/*.md             近百天沒動  ⇒ 7 支中 5 支仍被引用
正向對照 slice-instruction-six-piece（確定活著）⇒ 3                同一個量級
```
🔴 **86 天沒動的檔,引用數跟今天在用的檔一樣多。**
⚠️ **沒有那個正向對照,「還被引用 3 次」也可以被講成「幾乎沒人用」** ——
**判準的好壞,是靠對照組決定的,不是靠數字大小。**
