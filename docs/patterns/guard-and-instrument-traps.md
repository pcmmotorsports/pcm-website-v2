# 母題:**錯的那次和對的那次長得一樣**

> 🔴 **讀後面每一條個案時,不要問「這個檢查有沒有做」,要問:**
> **「它失敗的時候,長得跟成功不一樣嗎?」**

⚠️ **這與上面那句「拿一個相鄰的東西當成你要問的那個東西」是兩條不同的軸,不要混**:
那條講**量錯目標**;這條講**量對了目標,但兩種結果的外觀無法區分**。
一件事可以同時中兩條,也可以只中一條。

| # | 情境 | 失敗長什麼樣 | 成功長什麼樣 | 為什麼分不出來 |
|---|---|---|---|---|
| **1** | 恆綠格(§①) | 綠 | 綠 | 「紅不起來」與「這次沒問題」同一個畫面 |
| **2** | `relacl` 權限清單為空 | 空白 = **連 `service_role` 都沒授權** | 空白也符合「只准出現那兩個角色」 | 判準寫成「只准出現」,而空集合恆滿足 |
| **3** | `grep` 回 0 命中(§⑤) | pattern 沒對上 | 這個字面真的不存在 | 兩者都印 0 |
| **4** | `vitest` 的 exit code | **根本沒跑到那支測試檔** | 測試真的綠了 | 都是 `EXIT=0` |
| **5** | `cd` + `&&` 標錯目錄(§⑦) | 量了 B、標成 A | 量了 A、標成 A | 標籤自己不會反駁自己 |
| **6** | 測試模式 vs 正常模式的輸出 | 測試輸出 | 正常輸出 | 若不刻意標記,兩者逐字相同 |

🔴 **前五個是傷疤,第 6 個是主動避免的** —— 它來自 `scripts/next-backlog-number.sh` 刻意留的
「⚠️ 測試模式」那一行(2026-08-14)。**這份表裡五疤一防,那個差別本身就是進步的證據。**

**通用修法(不是決心,是一個當場要問出口的問題)**:
> 每加一道檢查,當場問:「**它會怎麼失敗?那個失敗看起來像什麼?**」
> **答不出來、或答案是「跟通過長一樣」⇒ 那道檢查還沒完成。**

## ① 恆綠格 —— 紅不起來的守門〔母題成員 1〕

**判準(逐字,拿去問自己)**:**「這格紅的時候,是誰讓它紅的?」** 講不出一個**具體可實施的突變**(改哪一行、拿掉哪個 `COALESCE`、把哪個判準反過來)⇒ 恆綠嫌疑。

**當天實例**
- `apps/admin/src/lib/payment/refund-repository.ts:233` 註解逐字記著:我一度加了一道 `if (!(key in row)) throw`,**實測紅不起來**(缺欄 = `undefined`,下面的型別檢查本來就會拋)⇒ 判定 no-op、**已刪**。
- `docs/specs/2026-08-13-445-overrefund-guard-plan.md:879`:驗收格 11 被判恆綠 —— `guard IS NULL` 在 RPC 路徑上不可達,而 plan 原本稱它是「本輪最重的負測」。**R3 的頭號 finding 配了一格無法擊發的負測。**

**常見形狀**:被更嚴格的守門**嚴格蘊含** / 斷言的是 fixture 自己設的值 / 條件不可達 / 措辭 oracle 是**檔案粒度**白名單而不是字串粒度 / **`toEqual` 的期望與 fixture 同時缺同一個鍵**(見 ①-a)。

**開工前那一條動作**:寫完守門,**當場把它弄壞一次**,看該紅的格有沒有紅。沒紅就別說「已驗證」。
🔴 **補一句(2026-08-14 V 窗實錘)**:「弄壞一次」只證明**被你弄壞的那一點**。
弄壞的位置若全落在**自己剛改過的行**,證到的覆蓋面等於零 —— 要挑**自己沒碰過**的同族位置也弄壞一次。

### ①-a `toEqual` + fixture 缺鍵 = 對那個鍵恆綠(2026-08-14 V 窗 `#476` 片1)

**本 repo 實測(不是引述 Vitest 文件)**:`toEqual` 比對時,「值為 `undefined` 的鍵」與「鍵不存在」**在本次量到的這一格上行為相同**。
數法(可重跑,`packages/adapters/src/supabase/SupabaseOrderAdapter.test.ts` 的 `DETAIL_ROW` × `findAdminOrderDetail` 那格):
```
# 把 DETAIL_ROW 裡的 voided_at 那一行刪掉,然後
npx vitest run packages/adapters/src/supabase/SupabaseOrderAdapter.test.ts
```
**補期望鍵之前 = 綠(87 passed);補之後 = `1 failed | 86 passed`。同一發突變、兩種結果。**
⚠️ **未確認**:這是對 Vitest 全版本/全比對器成立,還是只對本格這種形狀成立 —— **我只量了這一格**。
⇒ 端對端測試的 **wire fixture 少一個欄** ⇒ mapper 吐 `undefined` ⇒ **期望物件不寫那個鍵也照過**。
那格的檔內自陳可能還逐字寫著「精確比對…若被接回投影,本條會立刻紅」——**它對別的鍵是真的,對這個鍵是假的**。

- 實例:`packages/adapters/src/supabase/SupabaseOrderAdapter.test.ts` 的 `DETAIL_ROW` × `findAdminOrderDetail` 那格。
  作者為 `#476` 片1 加 `voided_at` / `void_reason` 時補了**三支** admin fixture 與 mapper fixture,
  **唯獨漏了 adapter 端的 wire fixture** ⇒ 該格對這兩欄恆綠。作者自跑的三發突變**全綠通過**
  (因為只突變了自己改過的地方),是 fresh-context reviewer 找出來的。
- 🔴 **與 `feedback_claimed-sync-but-only-patched-touched-lines` 同病**:「補了我摸到的那幾支」。
  差別在**這裡不會有任何一格轉紅來提醒你**。

**動作(兩條,都機械)**
1. 加欄之後 `grep -rn "<新欄名>" --include='*.test.*'`,**數出來的支數要等於**「構造該型別的 fixture」清單長度。
2. 對每一支 fixture **拿掉新欄各跑一次**;沒紅的那支就是恆綠格。`toEqual` 那格要**單獨**試,別與別的突變合併跑。

## ② 紅錯地方 —— 紅起來了,但紅的不是你以為的那一格

**判準**:突變之後,**去看紅在哪一行**,不要只看 exit code。

**當天實例**(這條是①的鏡像,坑集本來沒有這一面)
我要驗 `apps/admin/src/lib/payment/refund-actions.ts:331` 的 `const unhandled: never` 窮盡守。
第一發突變(只在碼表加第 10 個碼)**確實紅了,但紅在 `refund-repository.ts:323` 的 `Exclude<>`** —— 被上游先攔下,**目標那道守門根本沒被執行到**。
改構造成「碼表**與** outcome union 都加、只漏 switch case」才紅在 `refund-actions.ts:331`。

**開工前那一條動作**:突變後跑 `... > /tmp/mut.txt` 然後 **`grep -n "×\|error TS" /tmp/mut.txt`**,確認紅的位置就是你要證的那一處。

### ②-a 🔴 **測試名稱本身也是「字面 vs 事實」**(2026-08-14 V 窗 `#476` 片1)

測試名稱會被貼進報告、commit body 與交接信,**而綠燈完全不取決於它** —— 紅不紅只看斷言。
⇒ 名稱寫錯不會有任何東西叫,它是測試裡最容易長出假話的一行。
(**這句是推論,不是數出來的**:我沒有去數「有多少測試名稱是錯的」;證據是下面兩個當天實例,
各附**檔名 + 字面錨**(🔴 **刻意不附行號** —— 這兩個實例的行號在同一個施工 session 內被作者自己的
後續編輯推漂過三次;認字面才重得出來)。要自己數的話:
`grep -rn "it(\`" --include='*.test.ts' <目錄>` 然後逐條讀名稱對斷言。)

**實例(兩種形狀,同一天各一次)**
1. **參數化迴圈的名稱模板套錯清單**:`scripts/storefront-projection-leak-guard.test.ts` 的
   `for (const column of CANCELLATION_INTERNAL_COLUMNS)` 把名稱寫死成「(取消歷程的內部冪等欄)」。
   我把採購作廢的 `voided_at` / `void_reason` 塞進那份清單 ⇒ 測試名變成
   **「`voided_at`(取消歷程的內部冪等欄)」—— 既不是取消歷程、也不是冪等欄,而它是綠的。**
   修法 = 另立 `PROCUREMENT_VOID_COLUMNS` 與自己的迴圈,**不是**把兩種概念塞進同一個模板。
2. **名稱的涵蓋宣稱大於斷言**:byte-equal 那條原本叫「應用層認得『已作廢』」,
   但該片**只證了投影帶得到欄**,下游 `find`/`some` 全部仍未分流 ⇒ 名稱把「帶得到」講成「認得」。
   (codex 關卡2 nit)

**判準(拿去問自己,兩條)**
- **「這個名字說的事,這格的斷言真的證了嗎?」** —— 名稱的動詞比斷言強一級就是假話(帶得到 ≠ 認得 ≠ 會擋)。
- **參數化迴圈**:名稱模板裡的那句形容詞,對清單裡**每一個**元素都成立嗎?清單一長就要重新問一次。

**開工前那一條動作**:加完/改完測試跑一次 **`--reporter=verbose`**,**用眼睛讀那幾行印出來的名字**。
綠燈不會告訴你名字錯了 —— 上面實例 1 就是這樣被抓到的,而它已經通過了兩輪審查。

## ③ 一發突變同時紅多格 ⇒ 後面那幾格**沒有**被證到

**判準**:一發突變紅 N 格,你只證到**第一格**。其餘 N−1 格是**未知**,不是通過。
原因:同一個 `it()` 內前面的 `expect` 先失敗就短路;跨 `it()` 則是不同格各自為政、但你沒有分別構造。

**當天實例**
`apps/admin/src/components/orders/refund-ledger-section.test.tsx` 的 `[1b]` 有三道斷言:
`:53` `toContain('讀取失敗')` / `:59` `not.toMatch(/入口已.*關閉|按鈕.*收起/)` / `:64` `not.toContain('**')`。
我第一發突變把整句話換掉 ⇒ 紅在 `:53`,**後兩道完全沒被執行**。
**重構造兩次**(保留「讀取失敗」、分別只塞回假話 / 只塞回星號)才分別證到 `:59` 與 `:64`。

**同日另一例(D 窗)**:`MUT-A5a` 一發同時紅 C1/C2/C7/C8/C9 五格 ⇒ **後三格的判別力是「論證」不是「量到」**(code-reviewer 判詞,已要求補跑)。

**開工前那一條動作**:**一發突變只該紅一格。** 紅超過一格 ⇒ 把突變拆細,直到每格各有一發。

### ③-a 🔴 **重構的驗收不是三綠,是「突變紅格數逐發相同」**(2026-08-14 V 窗 `#476` 拆檔)

**判準**:重構的風險**不是「測試會紅」,是「守門悄悄失效而測試照樣綠」**。**三綠對這件事結構性盲。**

⇒ 用**突變的紅格數當不變量**:搬移前跑一次突變表、記下每發紅幾格;搬移後再跑一次,**逐發必須相同**。
搬家若讓某個守門失效,那一發會**從紅變綠** —— **三綠不會叫,這一道會叫。**

- 實例:`#476` 拆 `item-procurement-form.tsx`(410 行過鐵則 6 硬線)前後,五發突變的基準 = **`9/20/2/1/2`**
  (表在 `apps/admin/src/lib/orders/procurement-view.test.ts` 檔頂)。
- 🔴 **這給了突變表第二個用途**:它不只是「給人重跑用的紀錄」,**它是重構時的不變量基準** ——
  所以那張表值得寫進註解,而不是只活在交接信裡。

**⚠️ 前置:先驗量具,再讀結果**(同日兩窗踩同一坑,**兩種相反的誤讀**):
V 窗把 `No test files found` + `grep -c "×"`=0 差點讀成「零紅」;R 窗把同款情形的 `exit=1` 差點讀成「突變被殺掉」。
⇒ **每一發第一步是確認「這一發真的跑了 N 格」**(N = 該組測試的基準格數),`0` 或 `≠ N` 一律作廢重跑。
**「跑了幾格」是量具自檢,「紅了幾格」才是結果。**

**⚠️ 等價突變不算一發**:把恆等於 X 的東西換成另一個恆等於 X 的東西,**必綠、零資訊**。
它既不證明 no-op,也不證明有覆蓋。放進表裡要明文標注「不要拿它的綠當證據」。

## ④ 守門一裝上就自己紅 ⇒ **先分清是守門錯,還是產物錯**

**判準**:新守門第一次跑就紅時,**不要先去改產物**。先問:**「合法的產物拿去餵它,會不會也紅?」**

**當天實例**
`scripts/state-gates.sh:141-143` 的註解逐字記著:我第一版用 `iconv -f UTF-8 -t UTF-8` 當編碼閘,
結果**對合法檔也失敗**(macOS 回 `iconv(): Inappropriate ioctl for device`)⇒ 那是一道**恆紅**的閘,我差點裝上去。
改用 `file(1)`(`:146` `ENC="$(file -b "$OUT.tmp")"`)—— 那才是當初**真的把壞檔抓出來**的量具,
並用真的壞掉的位元組序列做過**負測**確認它會擋。

🔴 **這是①的另一面**:①是紅不起來(no-op),④是永遠紅(恆紅)。**兩種都不帶資訊。**

**開工前那一條動作**:新守門要跑**兩發** —— 一發合法產物(**必須綠**)、一發真的壞掉的產物(**必須紅**)。

## ⑥ 可重跑的證據 vs 不可重跑的證據

**判準**:一句斷言後面要嘛有**別人現在就能跑一遍、得到同樣結果**的東西,要嘛標【推的】/【未量】/【未確認】。**沒有第三種。**

**當天實例**
- ✅ **可重跑**:`scripts/state-gates.sh` 連跑兩次產物 sha256 逐字相同 ⇒ 證明它**真的是產生出來的、不是手寫的**。主視窗獨立重跑一次復現。
- ❌ **不可重跑**:D 的 C7/C8/C9「有獨立判別力」—— code-reviewer 認同這個結論,但明寫**「判別力是論證不是量到」**(那三發突變沒附),所以折成 nit 而不是寫進 PASS。

## 平台級陷阱:Supabase 新建 view/table **一出生就被授權給 `anon` / `authenticated`**

**`REVOKE ALL … FROM PUBLIC` 收不掉它。** 那是給**具名角色**的授權,不是 `PUBLIC`。

實查(2026-08-14,`#484a`):
```sql
select defaclrole::regrole, defaclnamespace::regnamespace, defaclobjtype, defaclacl from pg_default_acl;
-- postgres / public / r / postgres=arwdDxtm/postgres,anon=arwdDxtm/postgres,authenticated=arwdDxtm/postgres,…
```
`typ=r` 同時涵蓋**表與 view** ⇒ **任何在 `public` 新建的 view,預設 anon 與 authenticated 都讀得到。**
佐證:`has_table_privilege('anon','public.products_public','SELECT')` = `true`(那支是刻意公開的)。

**做法**:
```sql
REVOKE ALL ON public.<view> FROM PUBLIC;
REVOKE ALL ON public.<view> FROM anon, authenticated;   -- ← 少這行就是全開
GRANT SELECT ON public.<view> TO service_role;
```
🔴 **驗的時候不要只問你想得到的那幾個角色** —— 問完整 ACL,否則「migration 收哪幾個」與
「檢查問哪幾個」會共用同一個假設,第四個角色漏收時**兩邊互相驗不出來**:
```sql
select relacl from pg_class where relname = '<view>';   -- 只准出現 postgres 與 service_role
```
⚠️ `security_invoker = true` 是**第二道**(底表 RLS 以呼叫者身分套),不能拿它當第一道。

**發現於**:`#484a` codex 關卡2 R1 must-fix 1 —— 它只是說「`FROM PUBLIC` 可能不夠」,
**是回去查 `pg_default_acl` 才知道它在這個專案是真的成立。** 別人給的理由要自己驗一次再採信。

## 問「看不看得到 / 點不點得到」,**只有命中測試算數**

`getBoundingClientRect()` / `scrollWidth` / `clientWidth` 這類**回傳矩形或尺寸**的 API,
對下面三件事是**結構性盲的** —— 不是精度問題,是它們根本不表達這些概念:

| 看不到 | 例子 |
|---|---|
| `overflow` 裁切 | 祖先 `overflow:hidden` 把彈出選單切掉,rect 照樣回完整尺寸 |
| `z-index` / 覆蓋層遮擋 | 別的元素蓋在上面,rect 不會變 |
| `pointer-events` | 元素在畫面上、但點不到 |

⇒ **唯一的量具是 `document.elementFromPoint(x, y)`** —— 問「這個座標上,瀏覽器會把事件送給誰」。
**判準:回傳的是不是那個元素自己(或它的子孫)。** 中心點之外,**四個角也要測**(裁切通常從一側開始)。

### 實錘一:rect 說「沒被夾」,命中測試說「三顆全點不到」(2026-08-14 `#486`)
零 JS `<details>` 選單放進訂單表。我先用 rect 算「可見高度 94 = 需要高度 94」⇒ 結論**沒被夾**。
換 `elementFromPoint` 之後:**三顆選項全部命中「下面幾列的 stretched link」** ⇒ 一顆都點不到。
**答案整個反過來。** 沒換觀察點的話,交出去的會是一個「三綠全過、hit test 有做、但點不動」的選單。

### 實錘二:`scrollWidth` 對**控件**會誤報截斷(同日 `col-pick`)
我報過「勾選欄 15/18 被截」(依據 `td.scrollWidth(43) > clientWidth(28)`)。**那是誤報:**
- `scrollWidth` 從 **content box** 起算(28 − 8 − 8 = **12px**)⇒ 16px 的控件相對它必然溢出;
- 但 `overflow:hidden` 裁的是 **padding box(28px)**;
- 實測 padding box `25/53` vs 勾選框 `33/49` ⇒ **完整在內**;`elementFromPoint` 中心 + 四角 **五點全中**。

⇒ **`scrollWidth > clientWidth` 只是「文字會不會出現 ellipsis」的 oracle,不是「使用者看不看得到」的 oracle。**
對**控件**(input / button / svg)一律改用命中測試 + 比對**真正的裁切邊(padding box)**。

## ⑦ `cd` + `&&` 讓「標籤說的目錄」與「實際量的目錄」不一致〔母題成員 5〕

**症狀**:一條指令裡先 `cd <某處>` 再用 `&&` 串好幾段,**後面每一段都在那個目錄**。而報告裡常常把其中一段標成「主樹」「另一個 worktree」—— **標籤是寫的時候想的,不是執行時發生的。**

**2026-08-14 同日兩例、兩個不同的人、同一個機制:**
- **主視窗**:打算在主樹 `git merge <branch>`,同一條指令前面有 `cd <worktree>` ⇒ **merge 跑在該 worktree 上**,回 `Already up to date`。**沒造成損害純屬僥倖** —— 那句話讀起來像「已經是最新的了」,而實際上是「你在錯的地方問了一個錯的問題」。
- **R 窗**:兩段狀態查詢都跑在自己的 worktree,**卻把第二段標成「主樹」**。自己重查才發現。

🔴 **為什麼難發現**:兩個目錄通常都存在、指令都會成功、輸出格式一模一樣 ⇒ **錯的那次和對的那次長得一樣**。這是本檔的共同母題(「什麼都沒有」「看起來正常」被當成「檢查過了」)在**目錄**這一維的版本。

**修法(動作,不是決心)**:
- **跨目錄一律用 `git -C <絕對路徑> …` 逐條指定,不要用 `cd`**。多打幾個字換掉一整類錯。
- 報告裡每出現一次目錄名,**那一行的指令本身要看得出目錄**(`git -C /Users/.../pcm-website-v2 status`),不要靠上下文推。
- 這條在 `CLAUDE.md` 的 zsh 紀律裡有「多步驟用 `&&` 串接」,**但沒說 `cd` 會改變後續所有段的作用域** —— 本條補的是那個缺口。

## ⑧ 「共 N 處」重數了還是錯 —— 因為**同一個東西可以用好幾種【形狀】寫**〔母題成員 6〕

**2026-08-16 C 窗實錘,同一句話數了四次,四次都不對:**

```
plan 逐字寫「中文標籤目前【唯一】一份寫在 shipment-section.tsx」
  1 份  ← plan 的數法：grep 識別字 CARRIER_LABEL
  2 份  ← 我第一次更正：grep 中文標籤「新竹物流」
  4 份  ← R1 審查抓到 type CarrierCode = 'hct'|'sf'|'other'
          🔴 它一個中文字都沒有、識別字也不同 ⇒ 前兩種數法【都撈不到】
          而它偏偏是【寫入路徑】那一份
  5 份  ← R2 審查抓到 shipment-dialog 還有一個 as 'hct'|'sf'|'other' 的 cast
```

🔴 **教訓不是「plan 沒數」** —— 那太便宜了,而且會讓下一個人以為「我有數就沒事」。
**真正的形狀是:我每一次重數之後,都覺得這次總該數完了。** 四次都這麼覺得。

**為什麼難發現**:每一次重數**都撈到了新東西**,那個「又抓到一個」的手感
**恰好會被讀成「這次掃得比上次乾淨」**,而它其實只證明了「上次不完整」——
**對這次完不完整,零資訊**。⇒ 這是本檔母題(錯的那次和對的那次長得一樣)在**計數**這一維的版本。

**修法(動作,不是決心)**:
- 報「共 N 處」之前,先寫下**這個東西可能用幾種形狀寫**,再**逐形狀各掃一次**。
  以「一個值域(enum / 代碼集合)」為例,至少五種:
  ```
  型別 union      type X = 'a' | 'b'
  物件鍵          const LABEL = { a: …, b: … }
  陣列字面        [{ code: 'a' }, { code: 'b' }]
  cast            e.target.value as 'a' | 'b'
  泛型參數        useState<'a' | 'b'>('a')
  ```
- 一條 grep 交差 = 只掃了其中一種形狀。**掃描字集比宣稱窄**(本檔 ⑤)在這裡的具體長相。
- 命中之後**先逐行分類、再報數** —— 15 行命中裡大部分是測試 fixture 的單一個值,
  **不是「這個值域有哪些成員」的宣告**。直接數命中會把兩者混在一起。

⚠️ **而最刺的一點**:「命中要先分類再報數,不能直接數」這句話,
**就寫在同一份 plan 的上一節** —— 寫下那句紀律的人自己沒照做,我讀過那句、也沒照做。
📎 這是 memory `feedback_knowing-rule-is-not-executing-rule` 的又一次實錘:
**引用一條紀律,不等於把它套用到自己正在寫的那一段。**

## ⑨ 折 finding 最毒的形狀:**折出一個看起來像修好的東西,還把它寫進紀錄**

**2026-08-16 C 窗實錘,同一格斷言修了兩次,兩次都沒有判別力:**

```
R1 審查   「not.toMatch(/追蹤碼:\s*$/m) 恆真」
          —— textContent 沒有換行，那列後面永遠還有東西 ⇒ $ 碰不到
我        改成「量那一列印出來有幾個字 > 4」
R2 審查   「新斷言【仍然】恆真」
          —— 那列尾巴接著一句 JSX 常數（12 個字）⇒ 訊息改成空字串時仍得 12 > 4
🔴 而且我在 commit body 寫「那條突變是被這格新斷言接住的」= 歸因錯，
   真正接住的是它上面一行的 toContain
```

🔴 **這比「沒折」毒**:沒折至少留著一條 finding;
**折出一個假的,還在 commit body 裡替它記了一筆功勞** ⇒ 下一個人會相信那格有覆蓋。
> **假功勞會活得比那條斷言久。**

**修法(動作,不是決心)**:
- 折完「恆真」類 finding **一定要再跑一次突變**,而且要問:
  **紅的是我改的那一行,還是它上面/下面的別行?**(本檔 ② 紅錯地方,在折 finding 這一維的版本)
- 判別句:**如果把我這一行斷言刪掉,剛才那發突變還會紅嗎?**
  會 ⇒ 這行**沒有獨立判別力**,而三行看起來比兩行周全。**刪掉它,不留假覆蓋。**
- commit body 寫「這格接住了那發突變」之前,**先確認是這格接的** —— 歸因也是字面 vs 事實。
