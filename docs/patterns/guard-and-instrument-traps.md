> ### 為什麼退場(三條,第一條是決定性的)
>
> 1. 🔴 **圈號就是一個全域遞增識別碼,而多窗並行下 check-then-act 必撞** ——
>    同一夜才剛為了同一個病做了 CAS 配號(`scripts/reserve-backlog.sh`)。

> 2. **字元用完了**:`㊿` = 50 是最後一個(`U+32C0` 是 `㋀` 月份符號,**不是圈號**)。
>    2026-08-17 實測:dev 上已用到 **48**,而當時四線待收的條目加起來**還要 5 個以上** ⇒ **這一批就會用完。**
>    ⚠️ 而它會用**最難看的方式**爆掉:**補到一半發現沒號了,而前面幾條已經補好。**
> 3. **改用純數字只是把上限從 50 推到無限,病沒有變** —— 仍是「配號前要先看別人配到幾號」。
>

>
> **標題要夠短、夠特別、不要兩條長得像。**
> 🔴 **若日後兩條標題撞了 ⇒ 那是【內容重複】的訊號,不是命名問題 ⇒ 合併它們,不要加後綴。**

# 母題:**錯的那次和對的那次長得一樣**

> 🔴 **讀後面每一條個案時,不要問「這個檢查有沒有做」,要問:**
> **「它失敗的時候,長得跟成功不一樣嗎?」**

⚠️ **這與上面那句「拿一個相鄰的東西當成你要問的那個東西」是兩條不同的軸,不要混**:
那條講**量錯目標**;這條講**量對了目標,但兩種結果的外觀無法區分**。
一件事可以同時中兩條,也可以只中一條。

## ① 恆綠格 —— 紅不起來的守門〔母題成員 1〕

**判準(逐字,拿去問自己)**:**「這格紅的時候,是誰讓它紅的?」** 講不出一個**具體可實施的突變**(改哪一行、拿掉哪個 `COALESCE`、把哪個判準反過來)⇒ 恆綠嫌疑。

**當天實例**
- `apps/admin/src/lib/payment/refund-repository.ts:233` 註解逐字記著:我一度加了一道 `if (!(key in row)) throw`,**實測紅不起來**(缺欄 = `undefined`,下面的型別檢查本來就會拋)⇒ 判定 no-op、**已刪**。
- `docs/specs/2026-08-13-445-overrefund-guard-plan.md:879`:驗收格 11 被判恆綠 —— `guard IS NULL` 在 RPC 路徑上不可達,而 plan 原本稱它是「本輪最重的負測」。**R3 的頭號 finding 配了一格無法擊發的負測。**

**常見形狀**:被更嚴格的守門**嚴格蘊含** / 斷言的是 fixture 自己設的值 / 條件不可達 / 措辭 oracle 是**檔案粒度**白名單而不是字串粒度 / **`toEqual` 的期望與 fixture 同時缺同一個鍵**(見 ①-a)。

**開工前那一條動作**:寫完守門,**當場把它弄壞一次**,看該紅的格有沒有紅。沒紅就別說「已驗證」。
🔴 **補一句(2026-08-14 V 窗實錘)**:「弄壞一次」只證明**被你弄壞的那一點**。
弄壞的位置若全落在**自己剛改過的行**,證到的覆蓋面等於零 —— 要挑**自己沒碰過**的同族位置也弄壞一次。

⇒ 端對端測試的 **wire fixture 少一個欄** ⇒ mapper 吐 `undefined` ⇒ **期望物件不寫那個鍵也照過**。
那格的檔內自陳可能還逐字寫著「精確比對…若被接回投影,本條會立刻紅」——**它對別的鍵是真的,對這個鍵是假的**。

   (codex 關卡2 nit)

**判準(拿去問自己,兩條)**
- **「這個名字說的事,這格的斷言真的證了嗎?」** —— 名稱的動詞比斷言強一級就是假話(帶得到 ≠ 認得 ≠ 會擋)。
- **參數化迴圈**:名稱模板裡的那句形容詞,對清單裡**每一個**元素都成立嗎?清單一長就要重新問一次。

**開工前那一條動作**:加完/改完測試跑一次 **`--reporter=verbose`**,**用眼睛讀那幾行印出來的名字**。
綠燈不會告訴你名字錯了 —— 上面實例 1 就是這樣被抓到的,而它已經通過了兩輪審查。

### ②-b 🔴 **突變打到的是【測試自己那一行】** —— 紅在對的格,而紅的理由是錯的(2026-08-17 夜 T 窗 `#620`)

本節前兩面講的是「紅在**別的**格」。這一面是它的內側:**格名對、方向對,而紅的原因不是你以為的那個。**

**當天的原始命令與它做了什麼**
```sh
grep -v '不要拿去背書' "$B" > "$T"     # 想刪掉 drift_report() 裡那句 echo,證格18-b 守得住
```
它確實刪掉了那句 `echo`。**而它同時刪掉了格18-b 自己的 `case` pattern 那一行** ——
因為那一行為了比對輸出,裡面**也有同一個字面**。守門與它守的東西共用字面,是常態不是例外。

⇒ 那一格 **FAIL 了**、**格名是我預期的那一格**、**預期值也是我寫的那個**。
🔴 **唯一不對的是「得到」那一欄**:它印的是**隔壁格18 留在 `r` 裡的舊值**
(`開始 fp-開始 結束 fp-結束 `),而不是預期的 `no` ——
`case` 被改壞之後那一格根本沒走到任何分支去設 `r`,而 **POSIX sh 沒有 `local`,變數在格與格之間是共用的**
⇒ **一格沒設到 `r`,它就安靜地沿用隔壁那格的答案。**

**修法(改成用【結構】限定射程,不用字面掃全檔)**
```sh
awk '/^drift_report\(\) \{/ { inside=1 } inside && /^  echo/ { next } /^\}/ { inside=0 } { print }' \
  "$B" > "$T"
```
改完得到的是乾淨的 `得到「no」預期「yes」`。

**判別句(兩條)**
- **我要刪/改的那個字面,測試裡會不會也有一份?** 有 ⇒ 用 `awk`/`sed` 切出那支函式的範圍再動手。
- **看「得到」那一欄,不要只看格名。** 那個值如果**眼熟**(是上一格的答案),你打到的不是實作。

📎 三種假紅到此集滿,共同點是同一句 —— **紅了,而紅的原因不是你以為的那個**:
還原方式錯(`feedback_false-red-mutation-restored-the-implementation`)/
注入方式錯(`feedback_the-mutation-itself-broke-and-red-looked-like-success`)/
**打擊範圍錯(本節,`feedback_the-mutation-hit-the-test-not-the-code`)**。
🔴 **本節這一種最難察覺**:前兩種的紅是一條總結性的工具錯、**長得不一樣**;本節的紅**跟真的紅完全一樣**。

## ③ 一發突變同時紅多格 ⇒ 後面那幾格**沒有**被證到

**判準**:一發突變紅 N 格,你只證到**第一格**。其餘 N−1 格是**未知**,不是通過。
原因:同一個 `it()` 內前面的 `expect` 先失敗就短路;跨 `it()` 則是不同格各自為政、但你沒有分別構造。

**當天實例**
`apps/admin/src/components/orders/refund-ledger-section.test.tsx` 的 `[1b]` 有三道斷言:
`:53` `toContain('讀取失敗')` / `:59` `not.toMatch(/入口已.*關閉|按鈕.*收起/)` / `:64` `not.toContain('**')`。
我第一發突變把整句話換掉 ⇒ 紅在 `:53`,**後兩道完全沒被執行**。
**重構造兩次**(保留「讀取失敗」、分別只塞回假話 / 只塞回星號)才分別證到 `:59` 與 `:64`。

**同日另一例(D 窗)**:`MUT-A5a` 一發同時紅 C1/C2/C7/C8/C9 五格 ⇒ **後三格的判別力是「論證」不是「量到」**(code-reviewer 判詞,已要求補跑)。

**開工前那一條動作**:**一發突變只該紅一格。** 紅超過一格 ⇒ 把突變拆細,直到每格各有一發。

### ③-a 🔴 **重構的驗收不是三綠,是「突變紅格數逐發相同」**(2026-08-14 V 窗 `#476` 拆檔)

**判準**:重構的風險**不是「測試會紅」,是「守門悄悄失效而測試照樣綠」**。**三綠對這件事結構性盲。**

⇒ 用**突變的紅格數當不變量**:搬移前跑一次突變表、記下每發紅幾格;搬移後再跑一次,**逐發必須相同**。
搬家若讓某個守門失效,那一發會**從紅變綠** —— **三綠不會叫,這一道會叫。**

- 實例:`#476` 拆 `item-procurement-form.tsx`(410 行過鐵則 6 硬線)前後,五發突變的基準 = **`9/20/2/1/2`**
  (表在 `apps/admin/src/lib/orders/procurement-view.test.ts` 檔頂)。
- 🔴 **這給了突變表第二個用途**:它不只是「給人重跑用的紀錄」,**它是重構時的不變量基準** ——
  所以那張表值得寫進註解,而不是只活在交接信裡。

**⚠️ 前置:先驗量具,再讀結果**(同日兩窗踩同一坑,**兩種相反的誤讀**):
V 窗把 `No test files found` + `grep -c "×"`=0 差點讀成「零紅」;R 窗把同款情形的 `exit=1` 差點讀成「突變被殺掉」。
⇒ **每一發第一步是確認「這一發真的跑了 N 格」**(N = 該組測試的基準格數),`0` 或 `≠ N` 一律作廢重跑。
**「跑了幾格」是量具自檢,「紅了幾格」才是結果。**

**⚠️ 等價突變不算一發**:把恆等於 X 的東西換成另一個恆等於 X 的東西,**必綠、零資訊**。
它既不證明 no-op,也不證明有覆蓋。放進表裡要明文標注「不要拿它的綠當證據」。

## ⑥ 可重跑的證據 vs 不可重跑的證據

**判準**:一句斷言後面要嘛有**別人現在就能跑一遍、得到同樣結果**的東西,要嘛標【推的】/【未量】/【未確認】。**沒有第三種。**

**當天實例**
- ✅ **可重跑**:`scripts/state-gates.sh` 連跑兩次產物 sha256 逐字相同 ⇒ 證明它**真的是產生出來的、不是手寫的**。主視窗獨立重跑一次復現。
- ❌ **不可重跑**:D 的 C7/C8/C9「有獨立判別力」—— code-reviewer 認同這個結論,但明寫**「判別力是論證不是量到」**(那三發突變沒附),所以折成 nit 而不是寫進 PASS。
- ❌ **旁證 ≠ 證據**:我派 review 時提供了 `state-gates.sh`,想回報「它好不好用」。它的報告確實做了大量「這條路走不走得到」的推理 —— **形狀吻合,但形狀相同不等於用了它**,而我沒把「用了哪些工具」列成回報欄位 ⇒ **正確答案是「我不知道,不編」**,不是「應該有用」。
- 🔴 **行號會漂,而且最容易漂在「照抄審查報告」的時候**:寫這份檔時我把某支測試引成 `refund-wiring.test.tsx:294-309` —— 那是**照抄 code-reviewer 報告**的行號,而它的 base 在我加測試**之前**,實際已漂到 `:321`。
  ⇒ **引用行號前用機械複核**:`sed -n "<N>p" <檔>` 印出來,確認那一行真的含你要引的字面。本檔的每個座標都這樣核過一次(核出這一個漂)。
  ⇒ **更穩的做法:引「字面 anchor」不引純行號**(本檔已把那處改成引 `it()` 的標題)。
- 🔴 **一個數字只在「某個時點 × 某個範圍」下為真**:同一句 `grep`,code-reviewer 當時得 10、我事後在自己 worktree 得 33(期間 merge 進了別人的檔)。**兩個都不算錯,錯的是把它當成一個沒有時空的事實往下引用。**
- 🔴 **凡是要落檔的數字,一律當場重量 —— 不論它出自誰、多新**(2026-08-14 兩例,同族):
  - V 窗把 `#476` 突變表寫進測試檔時,**沒抄自己四十分鐘前寫的交接信,而是五發全部重跑**
    ⇒ 抓到兩個已經過期:①`7`→**實測 9**、③`1`→**實測 2**(期間自己又加了測試格)。
    **那兩封信是他自己剛寫的** —— 不是別人的、不是舊的。⇒ **「自己剛寫的數字」是最不被懷疑、
    也最容易過期的那一種**,因為寫的人記得的是「我算過」,而不是「我算的是哪個版本」。
  - R 窗 commit 訊息寫「刻意短 139 行」,實際 **83** 行。
  ⇒ **動作**:數字要進 commit body / 規則檔 / backlog 之前,**當場跑一次產生它的那條命令**,
    而不是回頭找「我剛剛寫在哪」。找得到的那份,正是最可能已經不成立的那份。

🔴 **配套**:一份 finding 被**第二個人開檔核過**,只證明**引用正確**,**不證明場景可達**。

## 平台級陷阱:Supabase 新建 view/table **一出生就被授權給 `anon` / `authenticated`**

**`REVOKE ALL … FROM PUBLIC` 收不掉它。** 那是給**具名角色**的授權,不是 `PUBLIC`。

實查(2026-08-14,`#484a`):
```sql
select defaclrole::regrole, defaclnamespace::regnamespace, defaclobjtype, defaclacl from pg_default_acl;
-- postgres / public / r / postgres=arwdDxtm/postgres,anon=arwdDxtm/postgres,authenticated=arwdDxtm/postgres,…
```
`typ=r` 同時涵蓋**表與 view** ⇒ **任何在 `public` 新建的 view,預設 anon 與 authenticated 都讀得到。**
佐證:`has_table_privilege('anon','public.products_public','SELECT')` = `true`(那支是刻意公開的)。

**做法**:
```sql
REVOKE ALL ON public.<view> FROM PUBLIC;
REVOKE ALL ON public.<view> FROM anon, authenticated;   -- ← 少這行就是全開
GRANT SELECT ON public.<view> TO service_role;
```
🔴 **驗的時候不要只問你想得到的那幾個角色** —— 問完整 ACL,否則「migration 收哪幾個」與
「檢查問哪幾個」會共用同一個假設,第四個角色漏收時**兩邊互相驗不出來**:
```sql
select relacl from pg_class where relname = '<view>';   -- 只准出現 postgres 與 service_role
```
⚠️ `security_invoker = true` 是**第二道**(底表 RLS 以呼叫者身分套),不能拿它當第一道。

**發現於**:`#484a` codex 關卡2 R1 must-fix 1 —— 它只是說「`FROM PUBLIC` 可能不夠」,
**是回去查 `pg_default_acl` 才知道它在這個專案是真的成立。** 別人給的理由要自己驗一次再採信。

## 收到「你的守門不夠嚴」這種 finding 時,**先構造一發它現在漏得掉的**

**不要直接加斷言。** 直接加會補出一個「看起來更嚴、實際仍漏」的守門,而且你會以為修好了。

實錘(2026-08-14 `#484a` 探針):codex 說「腳本不是 fail-closed」。我加了 `fail()` 累計與幾條 `|| fail`,
**然後自己跑負測 —— 餵一個沒有 `CREATE VIEW` 的檔,它還是 `EXIT=0`**
(`awk` 抽出空檔 → `psql -f` 空檔回 0 → 沒有任何一條 `fail` 被觸發)。
再補「抽出區段非空」「建完 view 必須存在」兩條,才變成 正向 `EXIT=0` / 負向 `EXIT=1` 且列出 3 條具名失敗。

**順序**:①構造一發現在漏得掉的 ②加斷言 ③**重跑那一發,確認它現在紅** ④正向也要再跑一次(別把好的弄紅)。

**實錘(2026-08-14 `#484a`)**:我在 migration 裡引了 `order-status-axes.ts:126-133`,
而**同一顆 commit** 因為改了那支檔、把函式往下推了 7 行 ⇒ 四處引用全錯,
**其中一處寫在 `COMMENT ON VIEW` 裡** ⇒ apply 之後那個錯行號就進了正式庫。
🔴 **是 code-reviewer 抓到的,不是我複掃抓到的** —— 因為「本 commit 自己推移了自己引用的行號」
這件事,寫的時候完全沒有感覺。

**通則**:
- 會離開 repo 的字面 ⇒ **只准寫函式名 / 常數名 / 可 grep 的字面錨**,不准寫行號。
- 留在 repo 內的註解可以寫行號,但**改了被引用的那支檔就要回頭掃一次**(見下一節)。

## 問「看不看得到 / 點不點得到」,**只有命中測試算數**

`getBoundingClientRect()` / `scrollWidth` / `clientWidth` 這類**回傳矩形或尺寸**的 API,
對下面三件事是**結構性盲的** —— 不是精度問題,是它們根本不表達這些概念:

| 看不到 | 例子 |
|---|---|
| `overflow` 裁切 | 祖先 `overflow:hidden` 把彈出選單切掉,rect 照樣回完整尺寸 |
| `z-index` / 覆蓋層遮擋 | 別的元素蓋在上面,rect 不會變 |
| `pointer-events` | 元素在畫面上、但點不到 |

⇒ **唯一的量具是 `document.elementFromPoint(x, y)`** —— 問「這個座標上,瀏覽器會把事件送給誰」。
**判準:回傳的是不是那個元素自己(或它的子孫)。** 中心點之外,**四個角也要測**(裁切通常從一側開始)。

### 實錘一:rect 說「沒被夾」,命中測試說「三顆全點不到」(2026-08-14 `#486`)
零 JS `<details>` 選單放進訂單表。我先用 rect 算「可見高度 94 = 需要高度 94」⇒ 結論**沒被夾**。
換 `elementFromPoint` 之後:**三顆選項全部命中「下面幾列的 stretched link」** ⇒ 一顆都點不到。
**答案整個反過來。** 沒換觀察點的話,交出去的會是一個「三綠全過、hit test 有做、但點不動」的選單。

### 實錘二:`scrollWidth` 對**控件**會誤報截斷(同日 `col-pick`)
我報過「勾選欄 15/18 被截」(依據 `td.scrollWidth(43) > clientWidth(28)`)。**那是誤報:**
- `scrollWidth` 從 **content box** 起算(28 − 8 − 8 = **12px**)⇒ 16px 的控件相對它必然溢出;
- 但 `overflow:hidden` 裁的是 **padding box(28px)**;
- 實測 padding box `25/53` vs 勾選框 `33/49` ⇒ **完整在內**;`elementFromPoint` 中心 + 四角 **五點全中**。

⇒ **`scrollWidth > clientWidth` 只是「文字會不會出現 ellipsis」的 oracle,不是「使用者看不看得到」的 oracle。**
對**控件**(input / button / svg)一律改用命中測試 + 比對**真正的裁切邊(padding box)**。

## ⑦ `cd` + `&&` 讓「標籤說的目錄」與「實際量的目錄」不一致〔母題成員 5〕

**症狀**:一條指令裡先 `cd <某處>` 再用 `&&` 串好幾段,**後面每一段都在那個目錄**。而報告裡常常把其中一段標成「主樹」「另一個 worktree」—— **標籤是寫的時候想的,不是執行時發生的。**

**2026-08-14 同日兩例、兩個不同的人、同一個機制:**
- **主視窗**:打算在主樹 `git merge <branch>`,同一條指令前面有 `cd <worktree>` ⇒ **merge 跑在該 worktree 上**,回 `Already up to date`。**沒造成損害純屬僥倖** —— 那句話讀起來像「已經是最新的了」,而實際上是「你在錯的地方問了一個錯的問題」。
- **R 窗**:兩段狀態查詢都跑在自己的 worktree,**卻把第二段標成「主樹」**。自己重查才發現。

🔴 **為什麼難發現**:兩個目錄通常都存在、指令都會成功、輸出格式一模一樣 ⇒ **錯的那次和對的那次長得一樣**。這是本檔的共同母題(「什麼都沒有」「看起來正常」被當成「檢查過了」)在**目錄**這一維的版本。

**修法(動作,不是決心)**:
- **跨目錄一律用 `git -C <絕對路徑> …` 逐條指定,不要用 `cd`**。多打幾個字換掉一整類錯。
- 報告裡每出現一次目錄名,**那一行的指令本身要看得出目錄**(`git -C /Users/.../pcm-website-v2 status`),不要靠上下文推。
- 這條在 `CLAUDE.md` 的 zsh 紀律裡有「多步驟用 `&&` 串接」,**但沒說 `cd` 會改變後續所有段的作用域** —— 本條補的是那個缺口。

## ⑧ 「共 N 處」重數了還是錯 —— 因為**同一個東西可以用好幾種【形狀】寫**〔母題成員 9〕

**2026-08-16 C 窗實錘,同一句話數了四次,四次都不對:**

```
plan 逐字寫「中文標籤目前【唯一】一份寫在 shipment-section.tsx」
  1 份  ← plan 的數法：grep 識別字 CARRIER_LABEL
  2 份  ← 我第一次更正：grep 中文標籤「新竹物流」
  4 份  ← R1 審查抓到 type CarrierCode = 'hct'|'sf'|'other'
          🔴 它一個中文字都沒有、識別字也不同 ⇒ 前兩種數法【都撈不到】
          而它偏偏是【寫入路徑】那一份
  5 份  ← R2 審查抓到 shipment-dialog 還有一個 as 'hct'|'sf'|'other' 的 cast
```

🔴 **教訓不是「plan 沒數」** —— 那太便宜了,而且會讓下一個人以為「我有數就沒事」。
**真正的形狀是:我每一次重數之後,都覺得這次總該數完了。** 四次都這麼覺得。

**為什麼難發現**:每一次重數**都撈到了新東西**,那個「又抓到一個」的手感
**恰好會被讀成「這次掃得比上次乾淨」**,而它其實只證明了「上次不完整」——
**對這次完不完整,零資訊**。⇒ 這是本檔母題(錯的那次和對的那次長得一樣)在**計數**這一維的版本。

**修法(動作,不是決心)**:
- 報「共 N 處」之前,先寫下**這個東西可能用幾種形狀寫**,再**逐形狀各掃一次**。
  以「一個值域(enum / 代碼集合)」為例,至少五種:
  ```
  型別 union      type X = 'a' | 'b'
  物件鍵          const LABEL = { a: …, b: … }
  陣列字面        [{ code: 'a' }, { code: 'b' }]
  cast            e.target.value as 'a' | 'b'
  泛型參數        useState<'a' | 'b'>('a')
  ```
- 一條 grep 交差 = 只掃了其中一種形狀。**掃描字集比宣稱窄**(本檔 ⑤)在這裡的具體長相。
- 命中之後**先逐行分類、再報數** —— 15 行命中裡大部分是測試 fixture 的單一個值,
  **不是「這個值域有哪些成員」的宣告**。直接數命中會把兩者混在一起。

⚠️ **而最刺的一點**:「命中要先分類再報數,不能直接數」這句話,
**就寫在同一份 plan 的上一節** —— 寫下那句紀律的人自己沒照做,我讀過那句、也沒照做。
📎 這是 memory `feedback_knowing-rule-is-not-executing-rule` 的又一次實錘:
**引用一條紀律,不等於把它套用到自己正在寫的那一段。**

**2026-08-16 C 窗實錘,同一格斷言修了兩次,兩次都沒有判別力:**

## ⑩ 餵進量具的字串**憑印象手打** ⇒ 量到的是你腦中的版本,不是 repo 裡的〔母題成員 7〕

**實例(2026-08-16,A 窗 BMW M 片4b,真瀏覽器 computed value)**:
要驗「狀態膠囊是不是方角」,做法是往真後台注入一個帶 `STATUS_CAPSULE` 的元素、讀 `getComputedStyle`。

```
第一發(手打):注入 'inline-flex items-center rounded-full px-2 py-0.5 text-xs font-medium'
             => borderRadius "1.67772e+07px"  = 圓角  => 差半步回報「方角沒落地」

真值(從原始碼讀):
  grep -h "^export const STATUS_CAPSULE" apps/admin/src/lib/orders/order-list-view.ts
  => 'inline-flex px-2 py-0.5 text-xs font-medium'      ← 沒有 rounded-full

第二發(讀出來再餵):四顆 cap-* 全部 borderRadius "0px"  => 方角其實早就落地了
```

🔴 **為什麼比一般錯誤危險:它產生的是【假紅】。**
假綠讓人**不做事**(損失是「沒發現」);**假紅讓人去修一個沒壞的東西** ——
而修的過程會產生 commit、產生「我處理過了」的紀錄 ⇒ **最後留下的證據看起來全都對。**
本例若發出去,下一個人會去**撤銷一個已經做對的改動**。

⚠️ **手打的那一發長得跟真的一模一樣**:class 名合理、量具正常運作、數字精確到小數。
**沒有任何一個環節會提示你餵錯了。**

**修法(動作,不是決心)**:
- 🔴 **任何要餵進量具的字串 —— class / selector / SQL / grep pattern / 期望值 —— 一律從來源讀出來,不准手打。**
  能 `grep -h` 出來就 `grep`,能 import 就 import;真的要貼,**貼完立刻回頭 diff 一次來源**。
- **配一顆正向對照**:本例注入一顆真的 `rounded-full` 徽章 ⇒ 量到 `1.67772e+07px`
  ⇒ 證明**量具看得見圓角**,所以那四顆的 `0px` 是量到的、不是量不到的。
  🔴 **正向對照比被測那幾顆重要,不要在報告裡把它縮成附註。**
- 判別句:**我手上這個字串,是【從 repo 讀出來的】還是【我打出來的】?**

📎 **同夜同一形狀第三次**(三個窗、三種量具、同一個病):
E 窗比對 SQL 憑印象只寫了 view 的上半;B 窗的 harness 跑在 owner 身分 ⇒ 那格永遠 green;本條。
⇒ 共同母題:**量具本身正常,而餵給它的「被測物」不是真的那一個。**

## ⑪ 對【經過編譯或求值】的東西下 grep ⇒ 你要找的字面在那一層可能叫別的名字〔母題成員 8〕

**實例(2026-08-16,A 窗 BMW M 片4b)**:要確認「那顆無限圓角還在不在編譯產物裡」。

```
原始碼一層   rounded-full                 ← Tailwind 類別
Tailwind 展開 calc(infinity * 1px)         ← 我拿去 grep 產物的就是這個
產物一層     border-radius:3.40282e38px   ← lightningcss 已把 calc() 求值成 Float32 上限
瀏覽器一層   1.67772e+07px                ← Chrome computed value 再夾一次到 2^24

grep 'calc(infinity' <產物>   ⇒  0 命中
```

🔴 **那個 `0` 不是「不存在」,是「量錯層」** —— 而**兩者的輸出完全相同**:都是空的。
本例若停在那裡,結論會是「無限圓角已經清乾淨了」,而它**一直都在**。

**修法(動作,不是決心)**:
- 🔴 **先跑一次【不帶 pattern 的抽取】,看那一層長什麼樣,再決定 pattern**:
  ```
  grep -rho 'border-radius:[^;}]*' apps/admin/.next/static | sort | uniq -c
  ⇒ 6 border-radius:0 / 3 border-radius:var(--radius) / 1 border-radius:3.40282e38px
  ```
  **有了這張分佈表,pattern 就不是猜的。**
- **沒做這一步的 `0 命中`,證不了不存在** —— 報「零命中」時要一併報「我在哪一層、用什麼 pattern、分母多少」。
- 判別句:**我要找的字面,在【我正在 grep 的這一層】叫什麼?**

📎 **這條為什麼要獨立成一坑,而不是掛在「先分類再報數」底下**:
`design-tokens.test.ts` 檔頭**早就寫著**「引用前先講清楚在數哪一個」(數宣告 vs 數選擇器)——
**而同一條規則在【同一個值】上第二次被踩到,踩的人還是讀過那句話的人。**
⇒ **那句話需要被寫成「一個當場要跑的命令」,不是一句提醒。** 這就是本條存在的理由。

## ⑫ 控制組**自己沒生效** ⇒ 那一輪的所有「綠」都不算數〔母題成員 11〕

> **2026-08-16 E 窗，測「同時掛品項會不會超量」的併發 race。**

大家都知道要有負向對照。**沒有人檢查那個對照本身有沒有生效。**

**我的第一版**：兩個交易各自「讀可出量 → 掛 3 件」，`instock = 5`，差 0.5 秒起跑。

```
不加鎖的負向對照 → 總共掛 3 件      ← ❌ 它【應該】要 6，超量才代表測得到 race
加了鎖的版本     → 總共掛 3 件      ← 看起來「通過」
```

**兩邊都是 3。** 而我要的結論正是「加鎖之後是 3」⇒ **那個綠讀起來完全合理。**

**真正的原因**：0.5 秒的時間差讓第二個交易的 `INSERT` 剛好在第一個 commit **之後**才開始，
READ COMMITTED 下它看得到 ⇒ **兩個交易被【意外】序列化了**。
⇒ **那一版測試對這個 race 零判別力**，而它**沒有任何症狀** —— 不報錯、不逾時、數字還剛好是對的。

改成「**先把可出量讀進暫存表 → 隔 2 秒 → 再寫**」之後，對照才紅（6 件），加鎖版才真的證明了東西。

### 可操作版

> 🔴 **跑完先看控制組那一格。控制組沒紅 ⇒ 這一輪的所有綠全部作廢，整輪重做，不要只補那一格。**

**併發測試特別容易踩**，因為它的失敗方式是**「測試環境比真實環境更安全」** ——
時序稍微一錯就被意外序列化，而那**看起來就像「沒有 race」**。
⇒ **對併發，「控制組要紅」不是形式，是唯一能證明你真的製造出了競態的東西。**

### 判別句

**我這一輪如果【什麼都沒壞】，是因為東西是好的，還是因為我根本沒碰到它？**

📎 比「要有負向對照」高一階：那條講**有沒有**控制組，這條講控制組**有沒有生效**。
📎 近親 §⑤（掃描字集比宣稱窄）、§① 恆綠格 —— 三者都是「**量具沒對準，而輸出長得像好消息**」。

## ⑬ **問題的形狀決定了答案的形狀** —— 「這條路守得好嗎」預設了路存在〔母題成員 12〕

### 兩個問法，同樣認真，結果完全不同

|---|---|---|

### 可操作版

**斷言一張表／一個機制的行為之前，先問：**

**驗守門之前先數 writer**，順序反了就會驗到一個沒人用的東西。

**會 ⇒ 我證的是「它被正確地閒置著」，不是「它在保護什麼」。**

## ⑮ 對 `supabase/migrations/` 的 `grep`：**命中數是「歷史上出現過幾次」，不是「現在有幾個」**〔母題成員 13〕

> **2026-08-16 E 窗，查 `#497` 兩套退款 `SUM` 是否一致。**

```
grep -rniE 'SUM\([^)]*refund' supabase/migrations/*.sql   →  5 處 / 3 個檔
```

**如果照這個數字報「五套各自實作的累加邏輯」，那會是假的。**

逐處歸屬到它所定義的**函式**之後：

```
pcm_order_refundable_remaining  被 CREATE OR REPLACE 了【三次】
  20260801120000:450  ← 被取代
  20260803150000:394  ← 被取代
  20260814190000:403  ← ✅ 活的（最後一版）
```

⇒ **三處命中其實是同一個函式的三個版本。判定路徑上實際只有兩套。**

### 為什麼這是系統性的，不是一次意外

`supabase/migrations/` 是**append-only 的歷史**：舊版 migration **永遠不會被刪**，
而 `CREATE OR REPLACE FUNCTION` 讓**最後一版靜靜蓋掉前面所有版本**。
⇒ **`grep` 看到的是全部歷史；資料庫裡跑的只有最後一版。**

### 可操作版

> **報「共 N 處」之前，先把每一處歸屬到它定義的【物件】，再看哪一版是最後生效的那一版。**
> 對函式：`grep -n 'CREATE OR REPLACE FUNCTION public\.' <檔>` 取得定義邊界後再歸屬。
> 拿不準 ⇒ **去 production 查 `pg_proc`**，那裡只有活的那一版。

### 判別句

**我數的是「有幾個」，還是「曾經寫過幾次」？**

📎 與 §⑭（答案寫在註解裡）**不同機制，不要併成一條**：
⑩ 是**沒讀**；本條是**讀了，而讀到的東西本身帶有時間維度**。

📎 **也不要與 §⑧（「共 N 處」重數了還是錯）併成一條** —— 兩條都在講「數錯」，但病因相反：
**§⑧ 是同一個東西有多種寫法 ⇒ 數【少】了**（要擴大 pattern）；
**本條是同一個東西有多個版本 ⇒ 數【多】了**（要收斂到「哪一版是活的」）。
🔴 **修法方向相反，套錯會讓另一個更糟。**

## ⑰ 受測物把測試環境換掉了 —— 你測到的是舊版,而它看起來完全正常〔母題成員 14〕

**當天實例(2026-08-16 夜 I 窗,修 `.husky/status-owner-gate.sh` 時)**

我在拋棄式 worktree 跑七格負向對照。跑到「merge 後 `chmod +x` 應該要紅」那格,拿到 **`rc=0`(該紅沒紅)**。
第一反應是「我的修法沒用」。查下去才發現:

```
那一格的前置動作是 `git merge --no-commit --no-ff dev`
而 dev 上有那支 hook 的【已 commit 的舊版】
⇒ merge 把測試樹裡的受測檔【換成了舊版】
⇒ 我測到的不是我要測的那一版
```

🔴 **沒有任何一個步驟是錯的。** `git merge dev` 是這一格的必要前置(要製造 merge 情境),
它做的事完全合理。**而它順手把受測物換掉了。**

### 與「假紅:突變腳本用 `git checkout` 還原」(`feedback_false-red-mutation-restored-the-implementation`)的差別

**不是同一條,不要併:**

| | 動手的是誰 | 為什麼難防 |
|---|---|---|
| 那一條 | **測試腳本自己**把實作還原掉 | 還記得是自己寫的還原步驟 |
| **本條** | **受測物所屬流程裡的一個正常操作** | **沒有一個步驟是錯的** —— 沒有東西可以怪 |

### 修法(做進動作序,不是「記得」)

**每一格跑之前**:①重貼受測檔 ②`grep` 一個**只有新版才有的字面**自檢 ③對不上就印 `VERSION-DRIFT` 並中止。

```sh
G() { cp "$HOOK_UNDER_TEST" .husky/status-owner-gate.sh
      grep -q '<新版獨有字面>' .husky/status-owner-gate.sh || { echo "VERSION-DRIFT"; return 9; }
      sh .husky/status-owner-gate.sh >/tmp/gg.txt 2>&1; echo $?; }
```

🔴 **命門是第 ② 步的字面怎麼挑** —— 挑錯的話這道自檢會恆真,而它長得跟有效一模一樣:

- **要挑「新版才有、舊版沒有」的字面** —— 挑兩版都有的(例如檔頭註解、函式名)⇒ **恆真、零判別力**。
- **要挑不會因為格式化/重排而消失的** —— 別挑行號、別挑縮排、別挑會被 formatter 動到的空白。
- **實務上最好挑「這次改動的理由句」**:本例挑的是註解裡的 `blob 只帶內容`
  —— 它**只存在於修好 F2 之後的版本**,而且它是一句解釋、不會被格式化吃掉。
- **挑完當場反驗一次**:拿**舊版**跑同一個 `grep`,**必須 miss**。miss 不了 ⇒ 重挑。

### 判別句

> **我剛剛量的那個檔,是我要量的那一版嗎?**
> 特別問:**這一格的前置動作裡,有沒有任何一步會動到受測物本身?**

## ⑱ 豁免誰,就對誰盲〔白名單 / allow-list 的固有盲區〕

> 📌 **本條依 2026-08-16 新規 append 到檔尾、不自己編號,編號由收割窗統一補。**
> ✅ **2026-08-17 I 窗:號已補(現為 ⑱)。** 留原文不刪 —— 它記錄的是當時為什麼沒有號。
> ⚠️ 它原本被我編成 `⑧` 並 commit(B 窗 `8f13618e`),而 dev 上的 `⑧` 是另一條
> ⇒ **merge 當場撞號。** 這正是那條新規要防的事,而我是那條新規生效前做的。

**一句話**:任何 **allow-list / 白名單 / 例外清單**,都在同一個動作裡定義了**這道守門的盲區**。
⇒ **寫下豁免的那一刻,就要問:被豁免的那個角色 / 檔案 / 路徑,能做到什麼?**

**為什麼難發現**:豁免是**刻意寫下的**,而人不會回頭懷疑自己刻意寫下的東西。
守門照常執行、照常印綠 —— **它只是從來沒有看過那個方向。**

### 實例一(2026-08-16 B 窗,真登入線 `admin_user_staff_map`)

新建表的收權斷言寫成 allow-list,明文豁免 `service_role`:

```sql
AND a.grantee::regrole::text NOT IN ('service_role', current_user)
```

而 Supabase 的 `ALTER DEFAULT PRIVILEGES` **同時授權給 `anon` / `authenticated` / `service_role` 三個**。
作者記下了前兩個、**漏掉第三個**,且對 `service_role` **只有 `GRANT`、從來沒有 `REVOKE`**
⇒ 表出生就帶 `UPDATE` / `DELETE` / `TRUNCATE`。

🔴 **兩件事同時成立才是這條的完整形狀:**

1. 洞存在(`UPDATE` 可重綁身分;`TRUNCATE` 清空整表**且不受 RLS、也不觸發 `BEFORE DELETE` trigger**)
2. **而那道守門在設計上永遠看不到它** —— 因為它被明文豁免了

實跑重現(對抗審查者用忠實樁跑的,不是推論):
`set role service_role; UPDATE … set auth_user_id=…` **成功重綁**;`TRUNCATE` **成功清空**。

**修法**:豁免對象**不是不檢查,是換一種檢查** ——
把「不看它」改成「**它的權限必須恰好等於某個集合,多一項就紅**」。

### 實例二(2026-08-16 E 窗,`payment_confirmer` 角色)

該角色對 55 張表五項權限全 0 ⇒ 看起來很安全。
🔴 **而那不是因為有東西在守,是因為它【不在 ADP 的名單裡】** ——
⇒ **任何人手寫一句 `GRANT … TO payment_confirmer`,不會有任何東西紅。**

📎 **兩個實例是同一條的兩面**:
一個是**豁免造成的盲**(我明說不看你),一個是**沒被列入造成的假安全**(我從來沒看過你)。
**共同點:那個「0」不是守出來的,是碰巧的。**

### 判別句(寫任何白名單時,當場問)

> **這份清單上的東西,如果它做壞事,我這道守門會紅嗎?**
> 答「不會」⇒ **那不是豁免,是盲區。** 至少要為它另外寫一道。

⚠️ **本條與「掃描的字集/範圍比你宣稱的窄」那條的差別**(**用標題不用編號,依新規**):
那條是**不小心**沒掃到,修法是把範圍補寬;
本條是**刻意**不掃,而修法**通常不是把豁免拿掉**(豁免多半有正當理由)——
是**為那個豁免對象另外設一道形狀不同的檢查**。

## ⑲ `git merge` 會動到你腳下的東西 —— 而「零衝突」讀起來像「沒有影響」〔**安靜**〕

> 📌 依 2026-08-16 新規 append、不自己編號,編號由收割窗統一補。
> ✅ **2026-08-17 I 窗:號已補(現為 ⑲)。** 留原文不刪 —— 它記錄的是當時為什麼沒有號。

**一句話**:`merge` 之後,**你 merge 之前量到的所有綠燈都過期了**,
而**沒有任何東西會告訴你這件事** —— `merge` 成功、零衝突、`git status` 乾淨。

併進來的每一顆都可能改到你的受測物、你的 fixture、你的 helper、你依賴的常數。

(這次結果沒變 —— **而「這次沒變」不是「不用重跑」的理由,是「重跑才知道沒變」。**)

### 實例二(同日 I 窗):**該紅的那格沒紅,而原因就是 merge**

它加了一道守門、預期會紅,**實際綠**。

守門是對的、測試是對的,**而它量的那份檔已經不是它以為的那一份。**
📎 那一格的完整形狀在「**我剛剛量的那個檔,是我要量的那一版嗎?**」那條;
**本條是它的上游**:merge 是最常見的、把受測物換掉而不會有人察覺的動作。

> 不是 ⇒ **那些綠是關於另一棵樹的,不是關於現在這棵。**

- **`merge` 之後、報告任何數字之前,重跑一次那條線的驗收。** 不要挑「應該不受影響」的跳過 ——

## ⑳ 量具用錯一個字元,而它壞掉的方式是【永遠回 0】【安靜】

### 實例(2026-08-16 B 窗):四把閘同時報「紅 0 格」

替出貨線四支寫入 action 加授權閘後,逐把做突變(拿掉閘應該要紅)。四把全部回報 `紅 0 格`。

🔴 病根:計數用的是 `grep -c "✕"`,而 **vitest 印的是 `×`(U+00D7)**。
⇒ 那個 grep **對任何輸入都回 0**,包含測試真的紅的時候。

**最毒的不是它壞了,是它壞得很一致**:
> 四個 0 排在一起,看起來像「我量了四次、結論穩定」。
> **一致性被當成了正確性的證據。**
📎 同夜 A 窗的近親:五個元件報 0,而**其中一個碰巧是真的** —— 有一格對的,讓人更相信整份。
⇒ **一致 ≠ 對;部分正確 ≠ 整體正確。兩個都會製造信心。**

### 判別句

> **這個 0 有沒有分母?我有沒有在【未突變的基準】上跑過同一支量具,看它回什麼?**

### 可重跑的量法(關鍵是先證量具會動)

```bash
npx vitest run <測試檔> 2>&1 | grep -E '^ *Tests '
```
用 vitest 自己印的 `Tests N failed | M passed` 那行,**不要自己數符號**。
突變前先跑一次基準:基準必須是 `M passed`,突變後必須看到 `failed`。
**兩個數字都變過,那支量具才算證明會動。**

## ㉑ 假紅:量法把受測物切錯邊界,而【紅看起來像成功】【吵】

### 實例(2026-08-16 B 窗):閘明明在,靜態格報「沒有授權閘」

一格靜態守門要驗「本檔每一支寫入 action 都有閘」,做法是切出函式體再找關鍵字:

```js
const body = ACTIONS.slice(at, ACTIONS.indexOf('\n}', at));   // ❌
```

🔴 TypeScript 的行內參數型別會讓簽章長這樣:

```ts
export async function voidShipmentAction(args: {
  idempotencyKey: string;
}): Promise<VoidResult> {          // ← 這裡有一個 換行 + }
```

⇒ `indexOf('\n}')` 命中的是**參數型別的收尾大括號**,函式體**在閘那一行之前就被切掉了**。

**為什麼這比假綠難察覺**:紅色會被解讀成「守門在做事、抓到東西了」。
第一反應是去改**受測物**,不是去懷疑**量法** —— 而受測物是對的。

### 判別句

> **這格紅的時候,紅的是受測物,還是我的斷言?**
> 併著問:**這格綠的時候,綠的是受測物,還是我的 mock?**
> (後者更重要 —— **紅會被查,綠不會。**)

### 修法

切到**下一個同級宣告**,不要靠括號配對的字串近似:

```js
const nx = ACTIONS.indexOf('export async function', at + 1);
const body = nx === -1 ? ACTIONS.slice(at) : ACTIONS.slice(at, nx);
```

## ㉒ 你在測一個【你自己剛剛 mock 掉】的東西【安靜】

### 實例(2026-08-16 B 窗):「沒有 cookie 要 fail-closed」那一格

`authorize.test.ts` 裡 `verifySession` 是 mock、無條件回成功。我加了一格:

cookieGet.mockReturnValue(undefined);

```

🔴 「沒 cookie 就擋下」這個行為**是由 `verifySession` 決定的,而它被我 mock 掉了**。
這格要嘛紅在「mock 沒回 null」(=我的斷言錯),要嘛綠在「我後來把 mock 調成回 null」(=我在測我自己寫的 mock)。
**兩種結果都與受測物無關。**

### 修法:改成守【契約】,那才是這一層測得到的東西

```js
cookieGet.mockReturnValue(undefined);
await authorizeAdminMutation();
expect(verifySession).toHaveBeenCalledWith(undefined);   // ✅ 沒 cookie 時傳下去的值長什麼樣
```

📎 同族但更早一層:**mock 掉跨信任邊界之後,誰在驗兩端的契約?**
本例的答案原本是「沒有人」—— codex 對抗審查點名這一格時的原話是
「authorize 接錯 cookies/headers 時,它與 action 測試**仍可各自全綠**」。

## ㉕ `cmd A B || echo "零命中"` —— 多目標命令的 exit code 是**整條**的,不是**每個目標**的〔母題成員:輸出的標籤不由結果決定〕

> **本條無編號,由收割窗統一補**(照本檔加新條目的規矩)。
> ⚠️ **【安靜】這個標記是本條首次使用**(`grep -c 安靜` 本檔落筆前 ⇒ **0**)——
> 意思是「**這個坑不會產生任何錯誤訊號**」。**是否要把它變成本檔的常設標記,收割窗決定,不要當它已經是慣例。**

### 實例(2026-08-16 R 窗,自曝)

我在對帳「P1 到底上線了沒」時跑:

```sh
grep -n 'regions' vercel.json apps/storefront/vercel.json || echo "🔴 兩支 vercel.json 都零命中"
```

**它印出了「🔴 兩支 vercel.json 都零命中」** —— 而 `vercel.json:5` 逐字 `"regions": ["sin1"]` **明明命中了**。

```
病根：apps/storefront/vercel.json 根本不存在
     ⇒ grep 對【整條命令】回非 0
     ⇒ || echo 照印
⇒ 「有一個目標不存在」被印成了「所有目標都沒命中」
```

🔴 **兩件事在輸出上長得一模一樣,而它們的結論剛好相反:**

| 真實情況 | 印出來的 |
|---|---|
| 檔存在 + 沒命中 | 🔴 兩支都零命中 |
| **檔不存在**(所以本來就不可能命中) | 🔴 兩支都零命中 |
| **檔存在 + 命中了,但另一個目標不存在** | 🔴 **兩支都零命中** ← **這次是這一種** |

⚠️ **而那句假話會讓人把結論下反** —— 我當時正要據此判「P1 沒上線」,
**而正確答案是 P1 早就上線了**(commit `93492a93`)。

### 為什麼規則擋不住(這條是 `feedback_knowing-rule-is-not-executing-rule` 的當日實例)

`CLAUDE.md` 終端機紀律逐字寫著:

> **輸出的標籤要由【結果】決定,不能無條件印**

**我讀過它,當晚還引用過它,然後照樣踩。**
📎 而同一晚**同一形狀出現三次、分屬三個窗**(另兩次:`sed 's/.*/固定字串/'` 印出六行整齊的假輸出、
無條件 `echo「上面空 = 零命中」` 而上面不空)⇒ **不是誰粗心,是預設寫法。**

### 修法(比原規則更可執行:**把一個問句拆成兩個**)

原規則說「標籤要由結果決定」,**沒說怎麼做到**。做法是:

```sh
# ❌ 一個問句同時問了兩件事，而它只有一個 exit code
grep -n PAT fileA fileB || echo "都沒有"

# ✅ 拆成兩個問句：檔【在不在】與檔內【有沒有】是兩件事
for f in fileA fileB; do
  if [ ! -e "$f" ]; then echo "$f 不存在（本來就不會有命中）"; continue; fi
  n=$(grep -c PAT "$f")
  echo "$f 命中=$n"
done
```

**三條可直接照抄的紀律**:
1. **一次只問一個檔** —— 多目標的 `grep`/`test`/`ls` 的 exit code 是聚合的,聚合值答不出「哪一個」。
2. **把「不存在」與「零命中」分開印** —— 它們的下一步動作完全不同(一個是去找檔在哪,一個是去確認事實)。
3. **改用 `grep -c` 印數字,不要用 exit code 當判斷** —— 數字帶著分母,exit code 不帶。

### 判別句

> **我這行輸出,在「事情沒發生」與「我的命令壞了」兩種情況下,會不會印出同一句話?**
> 會 ⇒ **那句話不能當證據。**

📎 同族:`feedback_suppressing-stderr-turns-broken-into-quiet`(對「零輸出=沒事」的命令加 `2>/dev/null`)
—— **那條是把壞掉藏起來,本條是把壞掉印成一句聽起來很確定的結論。後者更糟,因為它主動提供了一個假答案。**

**這不是「測試不夠」,是更深一層**:格子改實作**會紅**、覆蓋率**算它**、突變**接得住** ——
**而 fixture 的形狀讓你想分開的那兩種寫法收斂到同一個輸出。**

**實例甲(2026-08-16,A 窗片4b,R3 對抗審查抓到)**:
頭條七格 fixture **全部是單一 line**。而「分子逐列 `Math.min` 夾」與「先加總再夾」
**只有在多品項時輸出才不同**:

```
列A quantity 6 / ordered 6 / cancelled 6  ⇒ lineNeed 0，歷史 ordered 仍是 6
列B quantity 4 / ordered 0 / cancelled 0  ⇒ lineNeed 4
逐列夾  min(6,0) + min(0,4) = 0
加總夾  min(6+0, 0+4)       = 4
單 line ⇒ 兩者恆等                        ← 七格全在這裡
```
⇒ commit body 寫著「共用 `lineNeed` 所以不會漂」,而**那個機制的判別力一格都沒量過**。

**實例乙(同日、同一個窗、讀完實例甲【一小時後】)**:

差別在於:實例甲我是**寫完斷言後**被審查者問;實例乙我是**選 fixture 的那一刻**沒有問。

**修法(動作,不是決心)**:
- 🔴 **判別句要在【選 fixture 的那一刻】問,不是寫完斷言之後**:
  **我這組值,分得開我宣稱的那兩件事嗎?**
- **具體做法**:把你要排除的那個錯誤實作**當場寫出來**(不必打進檔案,寫在註解或草稿裡),

- **反向斷言尤其要問**:`not.toContain(X)` 在「X 本來就不會出現」的 fixture 上恆真,

那條是「測了一個**不會發生**的狀態」;本條是「測了一個**分不開兩種實作**的狀態」。
兩條的共同修法都是**往上游問一步**,而不是把斷言寫得更細。

## ㉘ 測試因為「兩個不同的東西字面相同」而誤撞 ⇒ **那是【使用者也會撞】的機械證據**
<!-- 🔴 依主視窗 2026-08-16 裁定:新條目 append 到檔尾、只寫標題不編號,編號由收割窗統一補。
     條目互相引用時用標題文字不用編號。

**實例(2026-08-16,A 窗片4d)**:Sean 要頭條金額拿掉 `NT$`
(`NT$ 2,480 / NT$ 0` → `2,480 / 0`)。改完之後那一排變成**兩組裸數字對**:

```
2,480 / 0   ← 金額（總額 / 已收）
4 / 2       ← 件數（已訂 / 到貨）
```
守門當場紅:預設 fixture 的總額是 `100`,金額格印 `100 / 0`,
而 **`'100 / 0'` 字面上包含 `'0 / 0'`** ⇒ 件數那格的 `not.toContain('0 / 0')` **被金額撞紅**。

🔴 **修法(加 `件數` 錨)只解決了測試那一半。另一半是:那個撞紅【本身就是證據】。**

```
問「這兩格分不分得出來？」⇒ 人憑感覺答，而他【知道】哪一格是錢
守門撞紅               ⇒ 那是一個【不知道哪格是錢】的東西，真的分不出來
```
**⇒ 員工第一天就是那個「不知道哪格是錢」的東西。**

**修法(動作,不是決心)**:
- 🔴 **測試因字面碰撞誤撞時,先問:「使用者看到的是不是同一串?」** 是 ⇒
  **那不只是斷言要加錨,是【版面需要一個視覺區隔】** ⇒ 列進要人肉眼驗的清單,不要只默默修斷言。
- **把撞紅的實例留在註解裡**,不要只留修好的斷言 —— **修好的斷言看不出這裡曾經有歧義。**
- 判別句:**我加的這個錨,使用者的眼睛也有嗎?**
  有(例如小標就印在旁邊)⇒ 可能還好;沒有 ⇒ **這是視覺缺陷,不是測試缺陷。**

📎 反向用法:**這條給了一個把「品味題」變成「可驗證題」的辦法** ——
PCM 紀律說視覺/文案品味由 Sean 拍板,而**字面碰撞是機械可測的**,
⇒ 拿它當**送去拍板時的證據**,比「我覺得可能會混淆」有力得多。

## ㉙ 分類的每一堆,要能用一條命令從**同一份輸出**撈出來 —— 撈不出來的是腦補的
<!-- append 不編號（2026-08-16 主視窗裁定），編號由收割窗補
     ✅ 2026-08-17 I 窗：**已補（現為 ㉙）**。留原文不刪 —— 記錄當時為什麼沒有號。 -->

**實例(2026-08-16,A 窗調色盤 plan)**:把 39 行調色盤命中分三堆,我報「丙類 3 行」。
**實得 2 行** —— 我把同檔的 `internal` 那一筆算進去了,**而它吃 `bg-muted`、
根本不在那 39 行裡**。

🔴 **這比「數錯」深一層**:
```
數錯       在同一個宇宙裡算錯          ⇒ 重數就會發現
本條       把【宇宙外】的東西算進來    ⇒ 重數【也不會發現】，因為它不在你數的那份輸出裡
```
我是在替每一堆補「可重跑的數法」時才發現的 —— **因為那一筆撈不出來。**

**修法(動作,不是決心)**:
- 🔴 **每一堆都要有一條命令,從【產生總數的那份輸出】撈出它自己**:
  ```
  ALL=$(grep -rnE '<pattern>' <範圍>)     ← 總數的唯一來源
  echo "$ALL" | wc -l                     ← 總計
  echo "$ALL" | grep -c '<丙的特徵>'      ← 丙  ← 撈不出來 = 它不在 ALL 裡
  甲 = 總計 − 其餘各堆                     ← 只有這一堆可以用減的
  ```
- **「逐行讀完沒有一行是 X」這種人工判讀要明寫是人工**,不要混在機械數字裡當同一種證據。
- 判別句:**這一堆,我能不能用一條命令從總表裡撈出來?**

⚠️ **連帶(同一次撞到的第二件)**:**兩個【不同分類軸】的數字不能直接相加對帳。**
同一份 39 行,按**色系**分是 `amber 25 / red 5 / emerald 5 / green 2 / sky 1`(合 38 真 code),
按**語意堆**分是 `甲 36 / 丙 2`。**38 ≠ 36 而兩邊都對** —— 差的 2 是「落在丙類的 emerald 與 sky」。
🔴 **「兩個數字對不上,而它們本來就不該對」是最容易被下一個人當成錯誤去『修正』的東西**
⇒ 報兩組數字時,**明寫它們是哪個軸、彼此不該相加**。

- 判別句:**這個 0,是這句話不在,還是我的 pattern 跨過了一個標記?**
- 📎 **這條跨所有窗**:多窗協作整晚都在用 md 錨點互相引用,**每一個都可能踩到**。

📎 **實測留痕**:那次我引了六條錨點、**每條都 `grep -c` 驗過**,只有這一條是 0

⇒ **交叉驗證在這種情況下不會發現任何東西** —— 兩顆腦給出同一個答案時,

**為什麼標〔安靜的〕**:猜錯的那一刻沒有任何症狀。

**修法(動作,不是決心)**:

  不要先問「哪裡不對」(那假設了他在評結果),也不要自己列三個可能的意思去猜。
- 🔴 **「不可實測」是觸發條件**:能實測的東西,實測勝過任何數量的腦
  (那是另一條:V 窗 2026-08-16)。**而要問人的東西,多一顆腦只會增加同時猜錯的機會。**
- 判別句:**這件事我能不能自己量出答案?**
  **不能 ⇒ 停下來問,不要用「兩個人都這樣想」當證據。**

📎 **這條與「可實測就實測」是同一枚硬幣的兩面,合起來才完整**:
```
可實測   → 去量。腦再多也不如一次實測。
不可實測 → 去問。腦再多也只是同一個誤解的複本。
```

## ㉜ 你剛寫的那把尺，自己有盲點 —— 而它會回報「0，乾淨」

> **2026-08-16 E 窗，修一條「引用了不存在的行號」的 finding 時。**

被指出 `20260811060000_…:517` 不存在（該檔只有 408 行）之後，
我**當場寫了一支腳本**，把四份報告裡所有 `檔名:行號` 抓出來、逐條比對實際行數。

```
✅ 行號在範圍內: 43
🔴 超出檔案行數: 0
```

**那個 `0` 是假的。** 因為出問題的那一條**逃過了尺**：
我在文中寫的是**縮寫** `20260811060000_…:517` —— **沒有副檔名**，
而我的正規表示式要求檔名以 `.sql`／`.ts` 結尾 ⇒ **它根本沒被匹配到。**

⇒ **我在同一個動作裡，示範了我正在修的那條 finding。**

### 可操作版

> **任何「0 命中」出來的當下，先問：我的尺長什麼樣？它掃不到什麼？**
> **而這次的尺是我自己十分鐘前寫的** —— **自己寫的量具最不會被懷疑。**

**具體做法**：量具寫完，**先拿【已知會命中的那一筆】餵它**（本例＝那條 `:517`）。
餵不出來 ⇒ 尺有洞，`0` 不算數。

### 連帶：這是「引用要寫完整檔名」的**第二個**理由

第一個理由是**可讀性**（下一個人找得到）。
🔴 **第二個理由更硬：縮寫【逃得過機械複驗】。**
⇒ 全檔名不只是禮貌，**它是讓你的引用進入可被機器檢查的集合的門票。**

📎 本例的結論方向沒變（可利用性仍低：本地圖可信、無遠端來源）——

## ㉞ 要普查一組東西，先找一個「型別／結構層」的判準把大部分**證明掉**

> **2026-08-16 E 窗，要審 20 支 RPC 的回傳面（怕外洩客戶資料）。**

**直覺做法**：20 支逐支開檔讀。貴，而且讀到第 15 支的時候注意力已經不在了。

**實際做法**：先看**回傳型別**——

```
integer  6 支  ⇒ 型別上就載不了 PII      ← 不必開檔
boolean  5 支  ⇒ 同上                     ← 不必開檔
TABLE    3 支  ⇒ 欄位在【簽章】就看得到   ← 不必開檔
jsonb    6 支  ⇒ 只有這 6 支要逐支讀 jsonb_build_object
```

**20 支變成 6 支要讀。**

### 🔴 而這與「抽樣」的差別是**本質的**，不是省力

| | 留下什麼 |
|---|---|
| **抽樣看 6 支** | 其餘 14 支**未知** —— 結論只能說「我看的那幾支沒問題」 |
| **型別分流** | 其餘 14 支**被證明不可能** —— 結論是「**全部** 20 支沒問題」 |

> **它把「我看了幾支」換成「哪幾支不可能」。**
> **前者是樣本，後者是普查。**

### 怎麼找那個判準

問：**有沒有一個【比內容更外層】的性質，能決定內容的可能範圍？**
型別、簽章、回傳基數、欄位數、ACL、`relkind`、`provolatile`…… 都可能是。
**找到了就先用它切，切不動的才逐個開檔。**

⚠️ **判準本身要正確**：`integer` 載不了 PII 是**型別保證**（可以信）；
「這支函式名字看起來只是計數」**不是**（那是猜的）。**用結構事實，不要用命名直覺。**

## ㉟ 兩個守門各自都被測到，而壞的是**它們之間的關係** —— 測資落在兩個測試的交集之外〔**安靜**〕

兩個版本**只差那兩個區塊的位置**，其餘逐字相同。跑一般人會寫的那兩格：

```
①「未取消的單，同 rec 同額重放 → 回冪等成功」   正確版 = 對調版   ← 一模一樣
②「已取消的單不得確認」（單子還沒 paid）        正確版 = 對調版   ← 一模一樣

🔴 已取消【且】已 paid 的同 rec 同額重放
     正確版 → CANCELLED_GUARD 擋下
     對調版 → {"confirmed":true,"idempotent":true}      ← 回報成功
```

**兩格功能測試在壞掉的版本上【全綠】。**

### 為什麼看不見

要看到差別，測資必須**同時**滿足「已取消」**和**「已 paid 且同 rec 同額」——
**而那正好是兩個測試各自都不會用到的組合**（①的單沒取消、②的單沒 paid）。

> 🔴 **每個測試作者都只顧自己那一半，而【沒有人負責那個交集】。**

### 🔴 它與「覆蓋率」的分界線

**覆蓋率量的是「有沒有被執行到」——而順序 bug 裡，兩個區塊【都】被執行到了。**
同理，**「兩者都存在」的斷言也擋不住它：它們確實都存在，壞的是順序。**

### 判別句

> **我這兩格各自都綠。有沒有一組輸入，是它們兩個都不會用到、
> 而【只有它】能分出對錯的？**

**做法**：把每格測資的**前提**列出來（①：未取消／②：未 paid），
**然後刻意構造一組把所有前提反過來的** —— 那組就是交集之外。

⚠️ **第一動仍是確認 harness 有鑑別力**：對調版**要真的產生不同輸出**。
沒有那一步，「兩格全綠」可能只是 harness 本身是空的。

## ㊲ 帶條件的標記要**附出口** —— 沒有出口的「未確認」最後會被某個人一次清掉〔**安靜**〕

> **2026-08-16 E 窗，把一段警語從無條件斷言改成帶條件之後，自己補的那一句。**

| 寫法 | 下場 |
|---|---|
| **不帶條件** | 斷言過強 ⇒ **誤導** |
| **帶條件、沒有出口** | 永遠停在保守那一邊 ⇒ **被當成噪音** ⇒ **下一個人乾脆整段刪掉** |
| ✅ **帶條件 + 出口** | 有人量清楚時**知道要做什麼** ⇒ 它會**被解決**，而不是**被忍受** |

### 🔴 「被當成噪音然後刪掉」是真的會發生

最後被**整體棄用** —— 而棄用者自己標明「**棄用是判斷不是驗證**」。
**⇒ 一個沒有出口的保守標記，最終的下場就是被某個人一次清掉，而且清掉的人是對的。**

### 出口長什麼樣

**寫在標記旁邊，一句話，講「誰、量什麼、量到什麼就怎麼改」：**

```
📌 量清楚之後怎麼改這段：
   長期為 0（沒在用）⇒ 可降級為「唯讀 catalog 憑證」；
   有東西          ⇒ 保留原文，並把它列進金鑰輪換清單。
```

**⇒ 它把「未確認」從一個【狀態】變成一個【待辦】。**

### 判別句

> **我這個「未確認」，要發生什麼事才會消失？**
> **答不出來 ⇒ 它不是限定，是一團會被清掉的雜訊。**

📎 近親（同一天、同一份檔）：**我這句話會被複製到哪裡去？那個地方裝得下它的限定嗎？**
—— 那條講**限定會不會跟過去**，本條講**限定會不會被解決**。
**兩條合起來才是完整的：限定要跟得過去，而且要有辦法終結。**

### 🔴 它的推論違反直覺

⇒ **交接漏了「什麼不要問他」這一項 ⇒ 新的主視窗會再問一次。**
**那不是資訊損失，是【重複打擾人】的損失，而它不會出現在任何檢查裡。**

我們原本只用它分類 traps。**在交接裡，它決定新 session 該把第一個小時花在哪**：
例如「`grep` 是 ugrep，`\b` 會靜默回 0」標成**吵**（會浪費時間但不會給錯答案）
⇒ 新人知道那條可以晚點再看。

### 判別句

> **這件事我一整晚都在用，所以我沒寫下來 —— 對嗎？**

## ㊴ commit body 那句話會讓下一個人不去查 —— 所以它比 code 更需要被核〔安靜〕

**2026-08-16 C 窗,同一顆 commit 裡兩處,都是 R2 對抗審查抓的:**

```
我寫「加框不改字，原文保留供對照」
  ⇒ 更正框被插進【原句中間】，把 `⇒ **兩種情況共用一個標籤「出貨日」，不分流。**`
     劈成兩半，還留下一行孤兒 `。**`
我寫「順手刪掉兩對逐字重複的 it()」
  ⇒ 只刪了一對。diff <(sed -n '683,693p' 該檔) <(sed -n '741,751p' 該檔) ⇒ 零差異
     而我那次的改名還讓它們變成【逐字全等】
```

🔴 **核心不是「我寫錯了」,是 commit body 的功能**:
> 它不只是紀錄,**它是一個「這件已經處理過」的訊號 —— 而訊號本身會關掉下一個人的檢查動作。**

⚠️ **為什麼比「訊息說改了而檔案沒改」更難發現**:那種是**沒做**;
這種是**做了一半**,而**做了一半在 diff 上看起來是有東西的** ——
reviewer 看到 diff 有動、body 說做完了,兩邊互相背書。

**修法(動作,不是決心)**:
- **body 裡每一句「已刪除 / 已同步 / 已更正 / 加框不改字」,落筆前跑一條會回答它的命令**,
  並把那條命令寫進 body。寫不出命令的那種宣稱,改寫成「我改了 X 處,沒有全樹掃」。
- **「順手」這兩個字是警訊**:它標記的正是「我沒有為它單獨驗一次」的那些動作。
- 判別句:**這句話如果是假的,下一個人會因為它而【不去查】哪一件事?**

**2026-08-16 C 窗,對「全測間歇性紅」定位錯誤:**

```
我：全測跑 3 次 --reporter=json，2 次紅，都指向 order-panel-wiring 的逾時
    ⇒ 我據此加了 20s testTimeout，並在 commit body 寫「修掉間歇性紅」
R2：乾淨輪零命中那格；唯一一次乾淨全測的紅是 note-compose-form 的【真斷言失敗】
🔴 病根：我那三次 JSON 跑，正好與【我自己派出去的 R2 subagent 跑全測】重疊
    ⇒ 我量到的逾時，是我自己製造的 CPU 負載
```

⚠️ **與「受測物把測試環境換掉了」是同族但方向相反,兩條都要在、不要合併**:
```
那一條   我的動作換掉了【受測物】
這一條   我的動作改變了【環境】，而我把環境的效應當成受測物的性質
```

🔴 **為什麼難發現**:逾時**確實發生了**,量到的數字**是真的**,
**錯的只有歸因** —— 而歸因不會有任何機械訊號:測試真的紅過、JSON 真的那樣寫、
補丁下去之後真的不紅了(因為負載也結束了)。**每一步都成立,結論卻是錯的。**

**修法(動作,不是決心)**:
- 判別句:**我量的時候,還有誰在動這台機器?** —— subagent、平行的窗、背景 build 都算。
- 效能類/時序類的量測,**跑之前先確認沒有自己派出去的背景工作在跑**;
  真要並行,**在報告裡標明當時的並行狀況**,不要只報數字。
- 📎 **「歸因錯」與「修法錯」要分開判**:那顆逾時補丁本身仍站得住
  (單跑實測 1962–3584ms vs 預設 5000ms,是量過的)⇒ 更正歸因,**不 revert**。

## ㊶ backlog 上的嚴重度,是它【被登記那天】的 —— 新功能接上去會改變它〔安靜〕

**2026-08-16 C 窗,出貨單金額片的關卡1 抓到:**

```
既有缺陷（早就登記）  頁層分兩次查：先拿 shippedQuantity、再拿 shippedAt
                      兩次之間有人按「標記出貨」⇒ 同一批貨兩邊都沒算到
登記當天的嚴重度      「尚未出貨那一區【多印幾件】」⇒ 方向是多報 ⇒ 刻意接受
🔴 金額接上去之後      同一個競態變成「紙上【多一筆錢】」
                      ⇒ 對客可見的金額錯誤，而紙印出去收不回來
```

🔴 **缺陷一個字都沒變,變的是它旁邊多了什麼。**
而 backlog 條目上寫的嚴重度、以及當初「刻意接受」那個決定,
**都是在【那個東西還不在旁邊】的時候下的。**

⚠️ **為什麼難發現**:
- 它**不在這一片的 diff 裡** —— 你動的是新功能,而它是舊的;
- backlog 上它是**已處置**狀態(「刻意接受、方向是多報」),讀起來像結案;
- 沒有任何機械訊號:那條登記不會因為你加了新功能而變色。

**修法(動作,不是決心)**:
- **接上一個新維度(金額 / 對外可見 / 不可回收)之前,把該路徑上【已登記的已知缺陷】撈出來
  逐條重問:「它的嚴重度在這個新維度下還一樣嗎?」**
  數法舉例:`git grep -n "已登記\|刻意接受\|不修" -- <該路徑相關檔>`
- 判別句:**這條缺陷當初被接受的理由,現在還成立嗎?**
  (上例當初的理由是「多報幾件,客人會打電話來問」——
   而「多一筆錢」的客人不會打電話來問,他會覺得被多收了。)
- 📎 與「更正本身會過期」同族,但過期的不是文字而是**判斷**:
  **敘述沒有變成假的,是它依據的世界變了。**

## ㊷ 守門用的那把尺量的是**換行符**,而體積全在行內 ⇒ 檔可以無限膨脹而永遠「合規」〔**安靜**〕

**實例(2026-08-17,I 窗,`STATUS.md`)**:規定「主表 ≤30 行嚴守」,檔內 `:4` 還自帶量法。

```
awk '/^---$/{exit} NF{c++} END{print c}' STATUS.md   ⇒ 30     ← 合規
同一次量：主表字元數                                  ⇒ 26,667
          最長的【一行】                              ⇒ 10,341 字元
```

⇒ **那一行自己就佔了主表的四成**,而規定看不到它。

### 🔴 它屬於這份母題的理由:**兩個世界印同一個數**

這一條的重點**不是「STATUS 太長」**(那只是一個症狀),是:

```
一個健康的檔    30 段、每段一兩行、總共約 2,000 字元   ⇒ 那把尺印 30
一個失控的檔    30 段、其中一段 10,341 字元、總共 26,667 ⇒ 那把尺印 30
```

**同一個數。** ⇒ 讀到「30」的人**分不出自己在哪一個世界**,
而規定寫著 ≤30 ⇒ **他會得到「合規」這個結論,而那個結論在兩個世界都成立。**
🔴 **這正是母題:錯的那次和對的那次長得一樣。**

🔴 **這把尺不是壞的,它量的東西是對的 —— 只是那個東西與它想擋的事無關。**
規定想擋的是「下一個 session 最先讀的三十行不要變成一大坨」,
而它擋的是換行符數量 ⇒ **把三十段濃縮成三十行超長的句子,規定完全滿意。**

### 它為什麼安靜

沒有任何東西會紅:`grep` 數不變、測試不紅、守門回綠。
**而且它會【看起來像在改善】** —— 每次有人「精簡」都是把換行拿掉、把句子接長,
**行數確實下降了。**

### 🔴🔴 更深一層:**規則會造出它自己要防的行為**(2026-08-17 當天實錘,主角是寫這條的人)

我寫完上面那段之後,**立刻在同一個檔上撞到它的反面**:
落帳時我**刻意不寫成一行超長句、拆成 7 行** ⇒ **主表從 28 行變 35 行,行數那把尺當場叫了。**

```
拆之前   1 行 10,341 字元   → 行數尺：滿意   體積尺：爆
拆之後   7 行  1,114 字元   → 行數尺：爆     體積尺：滿意
```

🔴 **兩把尺互相拉扯,而規定只寫了其中一把**
⇒ **照規定做的人會被推向「把句子接長」** —— **那正好是這條 trap 講的壞方向。**

**⇒ 一把尺不只是「量不到另一個維度」,它會【主動獎勵】往另一個維度膨脹。**
`STATUS.md` 那條規定不是漏了一半,是**它自己在生產它要防的東西**。

**修法**:上限**成對**訂,兩個方向各夾一把(`STATUS.md:2` 已於 2026-08-17 改成
「≤30 非空行 **且** ≤15,000 字元」)。**單獨任一把都可以被另一個方向規避** ——
行數尺 ⇒ 把句子接長;字元尺 ⇒ 把一段拆成一百行。

### 判別句

> **我這把尺量的單位,和我想擋的那件事,是同一個單位嗎?**
> 進一步:**有人為了滿足這條規定,會做出什麼動作?那個動作是我想要的嗎?**

配套:**規定一個上限的時候,同時寫下「用什麼量」與「為什麼是這個單位」** ——
`STATUS.md` 的規定原本只寫了前者。

📎 近親=〔量錯東西〕族,但這一條的特別處在於**規定本身就內建了那把錯的尺**,
⇒ **照規定做的人不會發現**,而發現它的人會被規定本身反駁(「我明明合規」)。

## ㊸ 突變「殺太多格」= 它殺的是**腳本**不是守門 —— 而突變層照樣印 PASS〔**安靜**〕

**實例(2026-08-17,V 窗 `V-021` 抓 I 窗的 harness)**:
突變 `M4` 用 `sed` 把 hook 的一行**整行清空**,結果:

```
if [ -n "$BASE" ] \
                      ← 空行
   && git diff …
⇒ sh 語法錯誤 ⇒ 每格 rc=2 ⇒ 7 格轉紅
⇒ 突變層印「PASS  M4 被殺掉(7 格轉紅)」
```

而那 7 格裡有 `cell1` / `cellA` / `cell3` —— **它們與被突變的那道檢查一點關係都沒有。**

🔴 **用錯的理由給對的答案。** 而它比假綠難察覺,因為**紅了看起來像成功**。

### 舊寫法為什麼擋不住

```
if [ "$killed" -gt 0 ]; then  PASS  # ← 對「1 格」與「7 格」回同一個答案 ⇒ 零判別力
```

**語法殺的症狀恰恰就是「殺太多格」,而這個判定式把那個症狀丟掉了。**

### 修法兩道,少一道就有洞

```
① 突變體先過 sh -n         ← 擋語法壞的
② 斷言 killed 的【格數】    ← 擋語法對、但射程不對的（① 攔不到這種）
```

🔴 **而「加了一道斷言」與「那道斷言真的擋得住」是兩件事** —— 兩道都要自己被反證過:

```
反證 A  把 M4 改回語法殺寫法          ⇒ FAIL rc=1「突變體語法就壞了」
反證 B  把 M2 預期值寫成 5（語法合法）⇒ FAIL rc=1「殺掉 1 格但預期 5」
```

### 🔴🔴 那條判別句怎麼用:**紅對了地方,而理由是【另一道守門】**(2026-08-17,同一天,同一個人)

折完上面那個修法之後,我要驗「新加的身分斷言擋不擋得住 V 窗的敵意 PoC」。
**第一版 PoC 我構造錯了**(replacement 漏了開頭的 `&&`)⇒ 突變體語法壞掉
⇒ 被**同一批加的另一道** `sh -n` 攔下,印「突變體語法就壞了」、`rc=1`。

```
我要驗的      身分斷言擋不擋得住
我拿到的      rc=1、FAIL、紅得非常合理
擋住它的      sh -n —— 而身分斷言【根本沒有被執行到】
```

🔴 **若我停在這裡,我會寫下「身分斷言擋住了 V 窗的 PoC」——而那句是假的。**
**紅的位置對、紅的顏色對、rc 對,只有「為什麼紅」是另一回事。**

**抓回它的就是這條判別句**:我預期的訊息是「**殺錯格**」,而我拿到的是「**語法壞了**」。
⇒ 補回 `&&` 之後才拿到預期那條:`🔴 殺 1 格【數量對】但紅的是 cell2,預期 cellS`。

📎 **這是「假紅」母題最難察覺的一種** —— 不是紅錯地方(那還看得出來),
是**紅對了地方而理由是另一道守門**。**兩道守門串在一起時,前面那道會替後面那道背書。**
⇒ **實務**:一次只加一道、或驗的時候**確認訊息來自你要驗的那一道**。

### 判別句

> **紅的時候問:紅在哪一格、訊息是不是我預期那條?**

**不是**「有沒有紅」。

## ㊹ 量具與它要量的範圍,位置對不對 —— **兩個相反的站錯,同一個乾淨的 0**

我設了對照組:一個**從來沒跑過**的 token,預期 `0`。

```
ps -eo pid,args | grep -c ZZNEVERRANTOKEN   ⇒ 實得 2   ← 預期 0
```

**那 2 是 `grep` 自己的命令列** —— token 就寫在它的參數裡,而 `ps` 列出了它。

⇒ **對照組壞掉,而它壞的方向會讓我把「有命中」讀成正常。**

### 兩例的共同判別句

> 🔴 **我的量具,有沒有出現在它自己要量的那個範圍裡?**

- **例 1 = 站錯位置**(在範圍外)⇒ **看不到真的東西**
- **例 2 = 站進樣本**(在範圍內)⇒ **看到的是自己**

**症狀一樣:一個看起來乾淨的數字。**

### 可操作版(三條)

```
① 選偵測字串前先問:被偵測物【可能只露出一部分嗎】?會 ⇒ 用【完整值】和【開頭那一段】各掃一次
② 數行程/數命令列這一類,過濾後【開出那一行實際內容看】,不要只看計數
③ 對照組自己也要被檢查 —— 預期 0 的東西實得非 0,先懷疑量具,不要先解釋現象
```

📎 例 1 的完整六個世界實測在 `~/pcm-mailbox/E-674g-覆核主視窗那條自驗指令-實測六個世界.md`。
📎 同族 [[feedback_assertion-measures-the-wrong-thing]](「偵測字串自命中」那一形狀)
與 [[feedback_reproducibility-is-not-validity]](**重跑一百次重出同一個錯的數**)。

⚠️ **本條與「量錯東西」那一族的差別要留著**:那一族是**量了另一個東西**;
本條是**量對了東西,而量具站錯地方** —— **前者換一把尺就好,後者換尺沒用,要換站的位置。**

## ㊺ **正在書寫某條規則的當下,是它最容易被違反的時刻**

- **來源**:2026-08-17 凌晨,**同一夜、三個互不相干的窗、各自獨立踩到**
- **母題**:**書寫的動作本身會產生「我已經在防它了」的感覺,而那個感覺會取代檢查。**

### 三個實例(不同的窗、不同的規則、同一個形狀)

| 窗 | 正在寫的那條規則 | 當場違反的方式 |
|---|---|---|
| C | **「命中要先分類再報數」** | 同一份 plan 裡自己報了一個沒分類的數,重數 `1 → 2 → 4 → 5` |
| I | **行數尺**(主表 ≤30 行的量法) | 寫完那把尺,**當場被自己那把尺叫**(主表超標) |
| E | **「掃描字集比宣稱窄」**(本檔既有母題) | 寫 ㊹ 時用 `grep -oE '^## [①-⑳]'` 數編號 ⇒ 得 **20**,而實際 **43** ——**`㉑` 之後是另一段 Unicode** |

### 判別句

> 🔴 **我現在寫的這條規則,我這一段文字本身有沒有違反它?**

**不是**「我有沒有遵守規則」——那個問題在書寫狀態下會自動回答「有,我正在寫它」。
**要問的是【這一段文字】,不是【我】。**

### 與 [[feedback_knowing-rule-is-not-executing-rule]] 的差別(**這條更窄也更毒**)

```
那一條   知道規則 ≠ 執行規則       ← 病根是「知道」與「做」之間有距離
本條     【正在書寫】規則 ≠ 遵守它  ← 病根是「書寫」這個動作【感覺起來就像在做】
```

⇒ 前者的人**知道自己還沒做**;後者的人**以為自己剛剛做完了**。
📎 同族 [[feedback_seen-written-handled-are-three-steps]] ——
「看到 → 寫下來 → 處理掉」是三步,**停在第二步會產生「我處理過了」的感覺**。
**本條是那個母題最尖銳的一個切面:寫的內容【就是】那條規則本身。**

### 可操作版

```
寫完一條規則/守門/判準,收工前的最後一個動作:
  拿它掃自己這一段 —— 一次,當場,不排進待辦
```

⚠️ **這個動作要放在【寫完當下】不是【複審時】** ——
複審時你已經離開書寫狀態,那個假感覺消失了,**而那時候錯的字面已經進了 repo**。

### 🔴 補充形狀(2026-08-17 當天再犯一次):**規則被套在「我想到它的那一格」,沒被套在所有適用的格**

E 窗的開跑清單 §3-3 逐字寫著「`has_table_privilege` 看不到欄級授權(**少報**)」。
**它把那條抄進了 P5 的檢查(那格用欄級,正確),然後在同一份報告的 §1.3 用了表級** ⇒ 把 16 個關聯報成 15。

**同一份文件、同一個人、兩小時內,一半照做一半沒照做。**
⇒ 這比「不知道」嚴重,也比「忘記」精確:**不是規則沒進腦袋,是規則只作用在【想到它的那一瞬間】。**

📎 它是 [[feedback_folding-a-finding-defaults-to-the-named-spot-only]] 的**預防版** ——
折 finding 會只處理被指名那處;**而套用自己寫的檢查表,也會只套在想到的那一格。**

**可操作版(比「記得全面套用」強,因為它是一個動作不是一個提醒)**:

```
寫下一條「這個量法會少報／多報」的警語時,當場做:
  grep 自己這份檔裡【所有】用到那個量法的地方,逐處標明用的是粗版還是細版
—— 不是收工前,是【寫下那句警語的當下】,因為那是你唯一會想到它的時刻
```

## ㊻ 把「我本來就這樣猜」變成**可查的** —— **預測先 commit,結果欄留空**

- **來源**:E 窗 2026-08-17,報價單庫稽核第一輪
- **母題**:**事後合理化不需要說謊就會發生。** 查到什麼都會覺得「本來就是這樣」,
  而那個感覺**會吃掉整輪的資訊量** —— 全中與全不中,事後讀起來一樣平。

### 做法(成本是零,因為反正都要 commit)

```
第一個 commit   只有 §0 預測 + 量具自檢,§1 結果【刻意留空】
第二個 commit   補 §1 結果
⇒ git 歷史證明預測寫在結果之前。不是紀律,是機制。
```

**實例**:`c3aecfa8`(預測)→ `e3f84c83`(結果)。五條預測,四條中。

### 🔴 值錢的不是「中幾條」,是那條**「中了而理由不同」**

該輪 `P5`(成本欄對 `anon` 開不開得到)我**自己標了最沒把握**,結果**中了 —— 而機制與我想的完全不同**:
我以為會像 A 庫那樣靠**欄級**權限擋,實際是靠**一支獨立的 view 根本沒發給 `anon`**。

⇒ **若沒先寫下預測,這一格會被寫成「安全,如預期」,而【擋法不一樣】這個事實會消失** ——
**而那個事實正是「兩個庫的結論不能互相引用」的具體證據。**

### 判別句

> **我這句「果然如此」,有沒有一個寫在看到結果【之前】的版本可以對照?**

沒有 ⇒ 那不是驗證,是敘述。

📎 同族 [[feedback_reproducibility-is-not-validity]] —— 兩條都在問「這個結論的資訊量從哪裡來」。

## ㊼ **排序準則會讓某一類東西的分數永遠是 0,而 0 分的東西不在名單上**

- **來源**:E 窗 2026-08-17。`/api/catalog/facet-counts` 連續三輪稽核零覆蓋
- **母題**:**它不是漏盤,也不是排在最後。它在【優先序清單】上根本沒有那一行。**

### 實況

```
盤點檔 :36   第一列就是它,標著「🌐 任何人」   ← 盤到了
§5 打擊順序 五條                               ← 而它不在裡面
```

排序準則是「**外部可達 × 有沒有第二道**」。
進榜五條各自帶著「唯一持憑證 / 唯一吃 unknown / 唯一靠祕密路徑段 / 完全沒盤」的框,
而它的描述是「**公開型錄計數**」= **讀起來沒東西可偷** ⇒ **第二個因子被算成 0** ⇒ 乘積是 0。

🔴 **而 0 分的項目不會排在名單尾巴 —— 它不會出現。**

### 為什麼這種漏比「漏盤」難發現

| 漏法 | 看起來像什麼 |
|---|---|
| 漏盤 | 清單短了一項,**回頭數分母就抓得到** |
| 排到最後 | 還在名單上,**看得見** |
| 🔴 **分數 0** | **一份完整、有理有據、排得很漂亮的優先序清單** |

⇒ **它的症狀是「清單看起來很完整」。**

### 判別句

> 🔴 **我的準則裡,有沒有哪個因子一旦是 0 就讓整項消失?
> 消失的東西不會排在名單尾巴,它不在名單上。**

### 可操作版

```
排完優先序,回頭做一件事:拿【盤點清單】減【優先序清單】,把差集逐項寫出理由
—— 不是「為什麼排前面」,是「為什麼它連一行都沒有」
```

📎 與「掃描字集比宣稱窄」是**同族的上一層**:那條是**量具**漏,本條是**篩選準則**漏。
**量具漏會少一個數字;準則漏會少一整類,而且外觀是一份完整的清單。**
📎 連帶 [[feedback_absence-read-as-verified]] —— **「不在名單上」會被讀成「看過了、不重要」。**

### 🔴 第二個實例(同一夜、同一個人,而這次歸零的是**我自己讀過的那條擴充**)

E 窗開工時讀了前身交接檔 `E-695` §2,逐字:

> ⚠️ **後來 Sean 擴充了一次**:後台正要開給員工用 ⇒ **「內部人員誤操作／帳號被盜」也算**。
> **但那是【擴充】,不是取代。**

**然後它用的準則是**:`外部可達 × 會不會洩漏資料 × 前身標為沒做`。

⇒ **「要登入才碰得到的東西」被第一個因子乘成 0** ——
`account/*` 三支 action、`/api/orders/[orderId]/payment-status` 的 IDOR 面**整輪沒碰**。
**而 Sean 明文擴充過的那一整軸,不是被判為低優先,是【沒有進到準則裡】。**

📎 **這一格同時是 `㊺` 與 `㊼`**:
**讀過那條規則(`㊺`)＋ 準則把它整類乘成 0(`㊼`)** ——
**兩條疊起來的症狀是:一份看起來完整、而且作者確實讀過所有背景資料的優先序清單。**

⚠️ 順帶一個**不要弄反**的邊界:同一份 `E-695` §2 也明列
**「員工之間沒有分權限」= 刻意的設計,不報**。
⇒ 補軸二時要報的是**「一個被盜的員工帳號能做到什麼」**,不是「員工彼此看得到什麼」。
**同一段文字裡,一句是該補的缺口、一句是該閉嘴的,而它們長得很像。**

## ㊽ **先證明我符合豁免條件,再用豁免條件** —— 它與「直接用」外觀一模一樣

- **來源**:E 窗 2026-08-17。`.husky/reviewer-gate.sh` 擋下一顆含 `.sh` 的 commit
- **母題**:**守門給的豁免條款,本身也需要證據。而【用了豁免】與【夠格用豁免】在 git 裡長得一樣。**

### 情境

reviewer gate 的放行條件之一逐字:「**已跑過 code-reviewer(或本片=輕量片、依分級可跳審)→ 寫標記再 commit**」。

⇒ **那一行標記自己寫、自己說了算。** 想繞永遠繞得掉 —— gate 檔頭自己就寫著它「擋的是【忘了】不是【想繞】」。

🔴 **所以真正的分歧不在 gate,在寫標記的那個人有沒有先去證明自己夠格。**

### 兩種做法的外觀對照

| | 動作 | git 裡留下什麼 |
|---|---|---|
| **A 直接用** | 覺得「這只是註解」⇒ 寫標記 ⇒ commit | 一行標記 |
| **B 先證明** | **機械驗證**「真的只有註解」⇒ 才寫標記 ⇒ commit | 一行標記 |

**兩者的 commit、diff、標記檔都可以長得一模一樣。**
⇒ **差別只在【驗證有沒有發生】,而那件事預設不留痕。**

### 本次實際做的驗證(可重跑)

```
git diff --cached --numstat -- <檔>                        ⇒ 8  0
新增行中【不是】以 # 開頭的                                ⇒ 0
刪除行中【不是】以 # 開頭的                                ⇒ 0
正向對照:新增行中【是】註解的                             ⇒ 8   ← 證明 pattern 活的
語法守門 sh -n / bash -n                                   ⇒ rc=0 / rc=0
shellcheck                                                  ⇒ 本機未安裝、未跑 ⇒ 標未確認
改後實跑(驗結果不是動作)                                  ⇒ 工具仍正常輸出
```

**然後把這整段理由寫進標記檔本身** —— 不是寫「輕量片」三個字。

### 判別句

> 🔴 **我現在用的這個豁免條款,我有沒有【先量過】自己符合它?
> 還是我只是覺得自己符合?**

### 可操作版

```
豁免條款的理由要寫進【留得下來的地方】(標記檔 / commit body),
而且要是【一條可重跑的量法】,不是一個形容詞
—— 「輕量片」是形容詞;「非註解新增 0 行、正向對照 8 行」是量法
```

⚠️ **反面**:`grep -c` 這類「數量」型驗證**必須配正向對照** ——
本次若只驗「非註解新增 = 0」而沒驗「註解新增 = 8」,
**一個把 pattern 寫錯而什麼都抓不到的檢查,也會回 0。**
📎 同族 `㊹`(量具站錯位置)與 [[feedback_absence-read-as-verified]]。

## 突變測試的第二個用途:**預測值不是拿來對答案的,是拿來製造【意外】**〔正面用法〕
<!-- 🔴 刻意【不編號】(2026-08-17 I 窗,作者身分):E 窗未收的那批已占用 ㊹,
     依制度「作者只寫標題不編號、收割窗東西到齊再統一補」。 -->

> **本檔到這一則為止都是失敗案例。這一則是【它該怎麼用】。**

**實例(2026-08-17,I 窗收 C 窗那批,驗它宣告的三發突變)**:

它宣告 `P2 = 列印鈕改回無條件 ⇒ 紅 2`。
**而我把 P2 誤讀成「鈕改回舊名」**(`列印出貨明細單` → `列印出貨單`)⇒

```
rc=0、零格轉紅
```

⇒ **我打錯了靶,而那個 0 是真的:入口鈕改名這件事零測試覆蓋。**

### 🔴 沒有預測值,這件事不會被發現

如果我只是「跑一跑看有沒有紅」,`rc=0` 會被讀成**這一發沒殺到、算了**。
**是因為我【預期它會紅 2】,零紅才變成一個需要解釋的東西** ⇒ 我去查 ⇒ 查出兩件:
①我打錯靶(我的錯)②**而那個位置真的沒人守**(不是我的錯,是本來就沒有)。

```
教科書用法   預測中了 ⇒ 守門有效           ← 確認你已經知道的事
第二個用途   預測沒中 ⇒ 去查為什麼         ← 找到你不知道的事
```

**沒有預測值就不會有意外,只會有「跑完了」。**

### 📌 那個 0 的處置也要寫出來 —— **「記了但不立案」也是一種處置**

```
事實    入口鈕改名零測試覆蓋（rc=0、零格轉紅）
判斷    影響低（純文案、Sean 肉眼會看到）、屬〔安靜〕
處置    記在收割 commit body，**不另立 backlog**
```

🔴 **為什麼要寫出來**:不寫的話,下一個人看到那個位置沒有守門、也沒有 backlog 號,
**會讀成「沒有人發現過」** —— 而事實是**有人發現、量過、判斷不值得一個號**。
**兩者對他的下一步影響完全不同。**

### 判別句

> **這一發我預期它紅幾格、紅哪一格?**
> **拿到的和預期不一樣的時候,我是去查為什麼,還是把它讀成「這發沒殺到」?**

## 用識別字 grep 找一個東西「在不在」——**三個方向都會出錯,而它們分開看像三個巧合**

- **來源**:2026-08-17 一夜之內、**三個不同的窗、三個相反的方向**
- 🔴 **本條起不再編圈號**(圈號已用完;互相引用改用標題文字)

### 三個方向

| 方向 | 誰踩的 | 形狀 | 症狀 |
|---|---|---|---|
| **看不到** | B 窗 | **命名讓 grep 抓不到** —— 同一個概念用了別的變數名 | 零命中,而東西在 |
| **多看到** | C 窗 | **註解與訃聞讓 grep 多抓** —— 一條規則被遵守得越徹底,提到它的註解越多;而**留痕的更正也會被舊字面掃到** | 命中數膨脹,而真正的實例只有幾個 |
| 🔴 **掃錯層** | E 窗 | **架構把那件事放在別層** —— 我在 action 檔找 `.eq('customer_user_id')` 零命中 ⇒ 推測「只有 RLS 一軸」;而那一軸在 **use-case 層**(`packages/use-cases/src/update-address.ts:38-43` 先 `verifyAddressOwned` 才 `repo.update`) | 零命中,而東西在**上面一層或下面一層** |

### 🔴 三者只有一個共同修法

```
命中(或零命中)之後,開檔讀那一段
```

**不是「換更好的 pattern」** —— 三個方向都不是 pattern 不夠好:
- 「看不到」要的是**再想一個命名變體**
- 「多看到」要的是**逐行分類再報數**
- 「掃錯層」要的是**先問這件事在這個架構裡會住在哪一層**

⇒ **共同的只有「不要停在數字上」。**

### 判別句

**大部分時候答案是「有」,而那一句本身很便宜;**
**它要抓的是那少數幾次 —— 而那幾次,是整片白工。**

## 片界照【員工看到的那一頁】切,不照【adapter 檔】切

**2026-08-17 實例**:儲值金流水(`SupabaseWalletAdapter`)與訂單歷史(`SupabaseOrderAdapter`)
**有同一個病**(頂層查詢無上限、靜默截斷),而我把它們切成兩片

🔴 **而它們渲染在同一張客人卡的上下相鄰兩區**(`customer-detail.tsx`)。

⇒ 只修其中一片的結果:
```

```
⇒ **一半明確失敗、一半靜默錯誤,擺在同一個畫面上** —— 對那個員工來說,
**這比兩邊都壞更難懂**:他會以為「有紅字的那塊壞了、沒紅字的那塊是好的」。

> **我這個片界,是照【使用者在一個畫面上看到的東西】切的,還是照【我們的檔案結構】切的?**

⚠️ **反向的界線也要寫**(否則這條會被拿去反對所有拆片):
**兩張表的做法若不同型**(例如一個能用既有分頁元件、一個不能)⇒ **仍然分片**,
但要在兩片的 plan 裡**互相指名**,不能只寫「另有一片」。
**同片的理由是「使用者看到的是一件事」,不是「程式碼長得像」。**

### 🔴 修正:**片界 ≠ 發布界**(2026-08-17 同日,A 窗提出、主視窗採納並修正自己那條裁定)

⇒ **一次推兩片,員工就不會看到中間狀態** ⇒ **同批推已經滿足這條規則。**

## 用一個【聽起來嚴謹的詞】蓋住一個【較弱的性質】—— 而詞本身不會問你

**2026-08-17 實例**(A 窗,儲值金分頁 codex R2):
一支測試對五個 spy 共用 `toHaveBeenCalledWith(CUSTOMER_ID)`,而其中一支的簽名加了第二個參數
⇒ 那格紅了。我把它改成「只驗第一個參數是 `CUSTOMER_ID`」,**並在註解裡寫**:

> ⚠️ 這是**收窄斷言的範圍**、不是放寬它:餵錯客人 id 仍然會紅。

**codex 一句話打回**:那是**放寬** —— 五支 spy 現在**全都**允許任意多餘參數與重複呼叫。

🔴 **而我當下真的以為它是收窄。** 我的理由是「我只驗一個東西,所以範圍更小」——
**那是【斷言文字】的範圍變小,不是【能通過的輸入】變小。**

### 判別句(這一條不必靠自覺,它有機械形狀)

> **改完之後,【能通過的東西】變多還是變少?**
> **變多 = 放寬**,不管它讀起來多像收緊。

⇒ 落筆寫下「**收窄 / 加嚴 / 更精確 / 更保守 / 更嚴格**」這一族詞的當下,就地回答那一句。

### 為什麼這族特別難自己抓

```
量錯東西那族   量具站錯位置       ⇒ 結果會怪，還有機會被察覺
這一族         描述與動作方向相反 ⇒ 【描述聽起來是嚴格的那一邊】
                                    ⇒ 讀的人（包括我自己）不會去驗它
```
📎 **同族的另一半是「誇大一個好處」**(例如把一個未量的改善說成已達成);
這一條是**把一個壞處講成好處**。**共同點:用詞的方向自己不會報錯。**

⚠️ **反向界線**:真的有需要收窄斷言範圍的時候(例如那格本來就不該管參數),**做法不是刪掉條件,
是把它移到該管的地方** —— 本例最後的修法是**逐支維持精確,只有真的改了簽名的那一支寫出它的新參數**。

🔗 **與本檔 C 窗那條「測資讓【要區分的那兩件事在資料裡從來沒有分開過】」同族**
(2026-08-17 解衝突時發現):那條是**測資**讓兩個世界重合,這條是**用詞**讓兩個性質重合
—— 🔴 **兩者都不會有任何症狀,因為重合的那一刻看起來就是「一致」。**
📎 我同日的預防版:替身也要吃 `categoryRaw`,**不吃的話那條下推在測試裡零判別力**
—— 那正是「不要讓要區分的兩件事在測資裡重合」。

### 第二例(同日,而且是**寫完上面那一則之後幾十分鐘**)

推薦引擎的低分層我寫:「`otherCat` 走 `seededOrder` **亂數** ⇒ 取樣可接受」。
**codex 更正**:`seededOrder` **只洗牌「handle 前 800 筆」** —— 它**不是對全品牌隨機取樣**。
⇒ 正確說法是「**低分層允許一個有偏的候選池**」。

🔴 **我用「亂數」讓一個【有偏】的取樣聽起來像【無偏】。**

### ⇒ 兩例合起來的形狀(這才是這一條要記的東西)

```
第一次  把【放寬】說成「收窄」
第二次  把【有偏】說成「隨機」
共同    用一個【聽起來嚴謹的詞】蓋住一個【較弱的性質】
🔴 兩次都不是狡辯 —— 落筆當下我真的以為它是那個較強的性質
```

### 📌 可操作版(升級,取代上面那個只管「收窄」的版本)

> 寫下任何**評價性的形容詞**(收窄 / 加嚴 / 隨機 / 完整 / 等價 / 安全 / 精確)之前,問一句:
> **「這個詞的【強版本】要成立,需要什麼條件?我驗過那個條件嗎?」**

```
「收窄」的強版本  要「能通過的東西變少」   ← 我沒驗，而它其實變多
「隨機」的強版本  要「取樣涵蓋全母體」     ← 我沒驗，而它只涵蓋前 800 筆
```
🔴 **兩次都沒驗那個條件,而【詞本身不會問你】。**

⚠️ **而「我寫完第一則之後幾十分鐘又犯一次」這件事,本身是這一條的一部分** ——
**它證明這族不是「記得就好」**:知道這個陷阱**不會**讓你在下一次落筆時想起它,
因為觸發點不是「我在講一個危險的東西」,而是**「我在找一個準確的詞」**,
而那一刻感覺上完全無害。

## 你跑了量法、輸出就在畫面上,然後填了**別的數**〔安靜〕

### 實例(2026-08-16 B 窗,寫交接信時)

一條命令裡同時做了三件事:

```bash
date "+%Y-%m-%dT%H:%M"      # ⇒ 2026-08-16T23:36
git rev-parse --short HEAD  # ⇒ 1c2c8e0c
python3 …                   # 把值寫進 B-554-STOP.md
```

**寫進去的是 `23:47`。** hash 對、時間錯。

🔴 **它會騙過所有既有的檢查**:

```
「有沒有量法？」   ✅ 有，就在同一條命令裡
「量法跑了嗎？」   ✅ 跑了，輸出就在畫面上
「數字對嗎？」     ❌ 不對 —— 而【前兩問都通過】
```

📎 與「別人檔案裡的自述值讀起來跟自己量的一樣」**不同**:那條是**沒量**,
本條是**量了、看到了、然後沒用它**。⇒ 既有判別句「這個值是我量的嗎?」在這裡**答案是「是」**,而值仍然是錯的。

📎 與「看到 → 寫下來 → 處理掉是三步」同族**而更難**:
**前兩步都做了,斷在【把手上的值放進去】那一步** —— 而那一步從外面看不出來有沒有發生。

### 判別句(既有那句不夠用)

> ~~這個值是我量的嗎?~~
> **我手上這個值,和量法那一行印出來的,是同一個字串嗎?**

### 動作(不是決心)

🔴 **填任何量測值時,把那一行輸出【貼在旁邊】,不要只填結果。**
貼了就不可能填別的數 —— 這是把「記得核對」換成「格式上做不到」。

```markdown
- **tip**：`1c2c8e0c`（2026-08-16T23:36 當場 `git rev-parse --short HEAD`）
```
比只寫 `tip: 1c2c8e0c` 強,因為**命令與值並排**,不一致當場看得見。

## 量測值與預期不符時,**兩個方向都錯,中間那條是去查**〔安靜〕

### 實例(2026-08-16 B 窗):抽出來的函式只有 23 行

寫抽取工具把五支 RPC 的現行定義抽出來,其中 `admin_add_shipment_items` **只有 23 行**,
而同組其他四支是 94–136 行。

**兩個直覺方向都會出事**:

```
當它正常   ⇒ 以為 23 行就是那支的全部
             ⇒ 新版的稽核 INSERT 會被插進【薄封裝】而我以為插在邏輯裡
當它壞掉   ⇒ 去「修」抽取腳本的結束條件
             ⇒ 把一支【本來是對的】工具改壞，而且改完會抽出多餘的東西
```

**實際去查的結果**:那支 2026-08-07 就被重構成薄封裝了,真邏輯在 `pcm_b2_add_items_impl`
(來源檔 `20260807230000_…:11` 逐字寫著)。**23 行是對的。**

### 為什麼它安靜

**與預期不符的值本身不是錯誤訊號** —— 它同樣可能是「我的預期過期了」。

### 判別句

> **這個值與我的預期不符 —— 錯的是【值】,還是【我的預期】?**
> 兩個都可能,而**在查清楚之前,對哪一邊動手都是猜。**

### 動作

- 不符的第一動是**去讀來源**(那支東西為什麼會是這個樣子),不是去改量具、也不是去接受。
- 🔴 **同組有對照時特別要查**:四支 94–136 行、一支 23 行 —— **離群值是最便宜的線索**,
  而「其他四支看起來對」正是讓人放過它的原因。

## 摘要層:**被讀得多、被查得少** —— 而我們的檢查全長在內文層〔安靜〕

### 這不是一個地方,是一**層**

單看任何一個都像個案。**四個並排才看得出它是一層**(2026-08-16 一夜之內,四個不同的窗各撞一個):

| 位置 | 為什麼被讀得多 | 為什麼被查得少 |
|---|---|---|
| **檔案標題** | 每次開檔都讀到 | 改內文時不會回頭看標題 |
| **commit body** | 收割、回顧、交接都在讀 | 🔴 **零守門** —— 三綠看 code、靜態檢查看 code、hook 看 index,**沒有一個看它** |
| **STATUS 主表** | Sean 唯一固定會讀的東西 | 欄位只要格式對就讀起來對 |
| **交接信 `§0`** | 新 session 第一個小時**只會讀這一段** | 寫的人是照「全文」的正確性在自我檢查 |

### 三個當晚的實例

- **標題**:`B-554-STOP.md` 標題寫「三支 migration 驗過,**等 apply**」——
  而 apply 還差兩個前置。內文 `§0.3` 寫對了,**但標題被讀的次數遠多於內文**。
  ⇒ **改標題比在內文補一段有效。**
- **commit body**:`8fb1efb9` 寫「另收一條官方事實**進殘留段**」,而三個載體 grep **全部零命中** ——
  它只存在於 commit 訊息裡。(完整形狀見「commit body 宣稱的動作,沒有任何載體」那條。)
- **位置錯而 grep 看不出來**:某窗的交接檔**檔頭有**「本表是快照、開工先重新點名」這句警告,
  **而表在檔頭下面** ⇒ **讀表的人不會回頭讀檔頭**。警告存在、且無效。

### 為什麼它安靜

摘要層的句子**在寫的當下是對的**。它變錯的那一刻,底下的內文**同時被改對了** ——
於是 `git diff` 有東西、測試綠、grep 數也對。**唯一沒動的就是那句摘要。**

### 判別句

> **我改的這件事,有沒有一個【摘要層的說法】也要跟著改?**
> 標題 / commit body / STATUS 欄 / 交接信第一段 —— **逐個點名,不要憑印象。**

### 動作

- 內文改到「結論變了」時,**先去改標題**,再回來改內文(順序反過來就會忘)。
- 摘要層要寫**還差什麼**,不要寫**已經做完什麼** —— 前者過期時會刺眼,後者過期時很安詳。
- 🔴 警告要放在**被它推翻的那句話之前**,不是放在檔頭。**檔頭的警告只保護從頭讀的人。**

## 規則綁在【實作的詞彙】上,換實作就自動失效 —— 而且它不會報錯

> ⚠️ **編號待補(2026-08-17 B 窗;依收割窗規矩,作者只寫標題、不編號)**

### 症狀

一條寫得很好的規則,在實作換掉之後**安靜地變成一句沒有對象的話**。
它不會紅、不會被過期掃描抓到 —— 因為它**字面上仍然成立**,只是它指的那個東西不存在了。

### 當天實例(2026-08-17 真登入線 B1-b)

主視窗給的檔頭規則第 ⑤ 條原句:
> 「想為它**加臂**之前,先問『我要擋的那件事發生在 apply 之前還是之後』」

而那份設計**正要把「臂」這個概念整個換掉**(枚舉框架 → 儲存層直讀)。
⇒ 規則落地的那一刻就開始失效:**下一個人要加的東西會叫別的名字**,
於是他讀到這條規則時會覺得「我加的不是臂,所以這條不管我」。

**同一天的實錘(同一支檔)**:我寫過註解「四臂由行為格守」,
**而拆掉 A14 家族之後那句話還在** —— 它從一句正確的描述變成一句誤導,**零機械訊號**。

### 判別句(寫規則、寫驗收條款、寫檔頭警語時當場問)

> **這句話裡有沒有哪個名詞,是【現在這個做法】才有的?**
> 有 ⇒ **換成那個名詞背後的意圖。**

- 「加**臂**」→「加**任何東西**」
- 「**四臂**由行為格守」→「這個斷言涵蓋的**每一種情況**」
- 「跑 `xxx-harness.sh`」→「跑**這條線的驗收**」(腳本會改名)

### 與既有教訓的關係(互補的兩面,不是重複)

- house `feedback_rules-need-applicability-clauses-not-just-prohibitions`:
  規則要寫**判別句**,否則擋不住誤引用 —— 因為**誤引用者不知道自己在那個情境裡**。
- 🔴 **本條**:**判別句本身若用了實作的詞彙,換實作就自動失效。**
  ⇒ 前者管「有沒有判別句」,本條管「**判別句活得比實作久嗎**」。

## 兩個量具坑:`awk` 的 `\s` 與「識別字 grep 對變數格漏數」

> ⚠️ **編號待補(2026-08-17 B 窗;作者只寫標題、不編號)**
> 兩個都發生在**同一次估工作量**的過程裡,而那個估計要寫進給 Sean 的簡報。

### 坑一:POSIX `awk` 不支援 `\s`,而它**不會報錯**

要數「斷言區塊裡有多少非註解的實碼行」:
```
awk '… !/^\s*--/ …'    ⇒ 122 行的檔案回報 219   ← \s 沒有被當成空白類,幾乎沒有一行被濾掉
awk '… !/^[ \t]*--/ …' ⇒ 122                    ← 正確
```
🔴 **危險的地方不是它錯,是它【錯得很合理】**:229 總行 vs 219 實碼,
看起來就像「這段註解不多」。**沒有正向對照就看不出來。**

**動作**:數完立刻加一條**互補的量法**,兩個數字相加要等於總數 ——
本例:實碼 `122` + 註解 `97` = 總行 `229` ✅。**對不上就是量具壞了。**

### 坑二:識別字 grep **看得到字面,看不到執行**

```
grep -cE '^\s*cell "A1[356]'  ⇒ 4     ← 只數到【寫死名字】的格
逐行讀                          ⇒ 7     ← 迴圈裡 `cell "$cid …"` 產生的三格,grep 全部看不到
```
⇒ 用 `for` 迴圈 + 變數產生的測試格,**在任何識別字 grep 的統計裡都是隱形的**。

📎 這是 house `feedback_identifier-grep-systematically-misses-behavior-tests` 的**新形狀**:
那條講的是「斷言渲染字面」的測試被漏掉,本條是**變數命名**讓 grep 漏掉 ——
**同一個病根:grep 看得到字面,看不到執行。**

**判別句**:
> **我數的這個東西,有沒有可能是【跑起來才存在】的?**
> 有 ⇒ grep 給的是下限,**要嘛逐行讀,要嘛去數它的輸出**(例如跑一次數 `✅`/`🔴` 的行數)。

## `SUM` 對得上,**不代表帳對** —— 而報告裡那兩個詞看起來一樣〔安靜〕

**口徑字面(主視窗 2026-08-17 裁定升級;來源 V 窗 `V-033`,可整行複製走):**

> 引用 `customer_wallet_balance_check` 或 op4 候選 gate 的結果,只能寫「**SUM 一致**」,
> **不得寫「對帳一致」「帳目相符」** —— 兩筆等額互抵的錯帳,SUM 對得上,而帳是壞的。

**為什麼要把它寫成口徑而不是「注意一下」:**

    SUM 式對帳    對「等額互抵的兩筆錯」    天生全盲
    列數式對帳    對「換內容不換筆數」      天生全盲
    ⇒ 兩者都過 ≠ 帳對

🔴 **這條的危險在【翻譯那一步】,不在量具本身。**
`SUM` 一致是**量到的**,而「帳目相符」是**推出來的** ——
中間那一步沒有任何東西擋著,而**寫報告的人不會覺得自己在推論**。
📎 Sean 看的是報告不是 SQL ⇒ **那個詞就是他拿到的全部事實。**

**判別句(錢族專用,可與五條分頁準則並用):**
> **這個對帳,在【漏一筆 + 多一筆】的世界裡,會不會剛好對上?**
> 會 ⇒ 你手上那個「一致」只證明了它自己那把尺,**不證明帳對**。

📎 同族但方向不同:上面「坑一/坑二」講的是**量具量錯東西**;
本條的量具**沒錯**,錯的是**把量具的名字換成了一個更大的詞**。

## 輸出**合法、格式正確、數量合理** —— 而它量的不是那件事,**且它不會紅**

> ⚠️ **編號待補(2026-08-17 A 窗;依收割窗規矩,作者只寫標題、不編號)**

### 症狀

「量具表演兩個世界」那一關**過了**,數字**也合理**,而**量到的不是你以為的那個東西**。
與既有的「恆綠格」「紅錯地方」不同:**這裡沒有任何一格是假的** ——
尺本身有判別力、自檢會通過、輸出的數字量級也對。**壞的是尺與對象之間那一步。**

🔴 **為什麼它比假綠更難抓**:假綠會被結果打臉(該紅沒紅),
而這一族**結論的方向常常沒變** —— 只有數字變了,**於是不回頭查就永遠不會被打臉。**

### 兩個子族 —— **分族的理由是【偵測手段不同】,不是成因不同**(2026-08-17 E 窗抽出)

| | 尺與對象的關係 | **偵測手段** |
|---|---|---|
| **甲 · 尺對準了別的東西**<br>「尺沒壞,是我把它對準了別的東西」 | 尺有判別力,但量的不是你以為的那個對象 | **看產出** —— 把被量的東西輸出成人看得懂的形式,看一眼 |
| **乙 · 尺的射程看不到那一層**<br>「我看不到的東西被寫成不存在」 | 尺對準了,但它**看不到**對象的一部分 | **換一個不受同一個限制的來源再量一次** |

🔴 **兩句原字收錄(E 窗)**:
> 「三次的輸出都是**合法、格式正確、數量合理**的,沒有一次會紅。
>  三次都是靠**『另外量一格』**抓到的 —— 欄級版 / 正向對照 / 成對特徵。」
>
> 「這就是第 0 條為什麼不是『多做一步』:**它是這族唯一的偵測手段,而這族【不會自己現形】。**」

### 子族甲的實例 ①②③(2026-08-17 A 窗,同一條線一天內;本 session 實跑輸出)

**① 編碼:量到的是亂碼字串的寬度**

`python3 -m http.server` **不送 charset** ⇒ 瀏覽器猜錯編碼、整頁中文變亂碼,
而量寬度的尺照樣跑完、照樣印出一組**漂亮的數字**:

```
甲 3/3 被切   丙 3/3 被切   戊 0/3 被切     ← 這一組是量亂碼量出來的
```
補上 `<meta charset="utf-8">` 重量 ⇒ **丙 從 3/3 變 1/3**。
🔴 **兩個版本都支持「會被切」這個方向** ⇒ **若沒有回頭查,那個錯永遠不會被結果打臉。**
📎 抓到它的不是量具自檢(自檢量的也是亂碼、照樣綠),是**去看網頁標題發現是亂碼**。

要回答「三軸橫排在 360px 面板放不放得下」,我用自己訂的樣式量:

```
而設計稿(`overview-desktop.html:348-352`)是**膠囊**:
`border-radius:999px; padding:2px 8px; font-size:12px; gap:4px`。
照真規格重量:

```
🔴 **字一樣、殼不一樣,而殼佔了 51px。**
⇒ **我量的是「這串字要多寬」,不是「設計稿那個東西要多寬」。**
📎 病根在鐵則 1 那一步被跳過:**沒 grep 設計稿字面就先開瀏覽器量了。**

**③ 對照組自己是空的:`git diff A...B` 對一個祖先必回空**

量具自檢(頁尾 script 自己印,兩個世界給不同答案才採信):同一段字塞 40px ⇒ 判被切、塞 600px ⇒ 判沒切,兩格皆 ✅。
⚠️ **範圍限定**:這組數字只在 **1500×1000 視窗 / Chromium / 面板 720px** 下量過一次,
其他視窗尺寸與其他瀏覽器**未確認**;字型落回系統字(稿沒有內嵌 BMWTypeNext)⇒ 換機器可能再變。

### 為什麼它安靜

```
① 兩個數字【不在同一個視線裡】—— 讀者在讀散文，或在看數字卡，不會同時做
② 寫死的那個【格式完全正確】—— 有單位、有比較、有結論，讀起來比活的那個更像結論
③ 活的那個【沒有宣稱自己是權威】—— 它只是一個數字，散文才在講「所以你該怎麼辦」
④ 🔴 沒有任何機械訊號:檔案有改（改的是別處）、grep 數不變、測試不紅、對帳器只比按鈕
```
🔴 **這一族與「摘要層被讀得多、被查得少」是鄰居但不是同一條**:那條講**兩層**(摘要 vs 內文),
本條講**同一層裡的兩份**,而且其中一份**會自己更新**——**會自己更新的那一份,正是讓另一份無聲過期的原因。**

### 🔴 嚴重度不看「錯多少」,看**錯的方向會不會改變他的決定**

```
散文版  被切 23px  ⇒ Sean 大概會說「那就讓它顯示⋯，不用處理」
真值    被切 74px  ⇒ 切掉五六個字 ⇒ 他大概會說「那要處理」
```
⇒ **同一個欄位、同一個問題,兩個數字導向【相反的裁示】。**
判準:**一個錯的數字若不會改變任何人的下一步 = nit;會改變決定的 = must-fix。**
(這也是為什麼「差 51px」這種描述不夠 —— 要講的是**那 51px 讓他做出哪個不同的選擇**。)

### 動作(不是決心)

1. 頁面上有 **live 值**時,**散文不要複述它** —— 改成指過去(「左邊那格就是當場量的」)。
   複述 = 手上多了一份**不會自己更新的副本**,而分岔時先錯的是副本那一份
   (本次實例即如此:live 值跟著 360→720 自己變了,散文沒有)。
2. 非要寫死不可(要拿它論證、要講結論)⇒ **把量測條件寫在數字旁邊跟著走**
   (哪個寬度、哪個瀏覽器、哪一版),不要只寫數字。📎 同 `00-work-rules` §6-b 第 2 條。
3. **改版面尺寸 = 全檔重掃那個尺寸下算出來的每一個數字。** 這次是 360→720,
   而稿裡跟著錯的不只 mark 3:`360` 字面原有 **6 處**,改完剩 3 處(全是刻意留的更正紀錄)。
   🔴 掃舊字面會掃到**它自己的訃聞**(更正說明裡本來就引用舊字面)⇒ **逐處開檔讀,不要一律當漏改**。
4. 交出去之前問一次:**這一頁上還有哪裡在講同一件事?** —— 這一步比「再讀一遍」有用,
   因為再讀一遍只會讓兩個數字**各自都讀起來很正常**。

### 🔴 近親(同日同一條線撞到的第二種形狀):**一個沒有本體的數字**

> **判別句:我要引用的這個數字,它的清單在【哪一個檔案】裡?**
> **答不出檔名 ⇒ 那個數字沒有本體。**

上面那條是**兩份在講同一件事,一份過期**;這一條更極端:**只有一份,而它是空的**。

**實例(2026-08-17 A 窗,交接第二天)**:`A-222-STOP` 兩處寫著「**26 項忘記畫**」,
而**那 26 項是什麼,四種方法全查不到**:
```

```
🔴 **只有數字活下來,清單從來沒有存在過任何載體。**

**為什麼它特別安靜**:
```
① 「26 項」是【具體數字】⇒ 讀起來像已經數過了（含糊的「一些項目」反而會被追問）
② 它出現在【交接信】⇒ 讀的人預設它是上一任盤點的產物，不是隨手寫的
③ 🔴 最省事的接手方式是【寫一張 26 項的表】—— 而那樣做不會有任何人發現

```

## 量對了東西,卻量的是**一個重製品** —— 而它比原件更像原件〔安靜〕

**實例(2026-08-17 晚,C 窗出貨明細單「貼底」)。**

要回答的問題:「金額區貼齊紙底」與「單品項訂單一頁印完」能不能同時成立。
量到的:貼底技法(`flex` + `min-height:Xmm` + 底部區 `margin-top:auto`)一開,
`X` 從 271 掃到 180mm **全部變成 2 頁** ⇒ 記成「兩者互斥,成因未查明」。
一整條線停在那裡,而下一步被排成「去查 `min-height` 為什麼會這樣」。

**真正的病**:那些數字量的是**設計稿版面的一份重製**,不是**正式頁**。
換到正式頁重量,同一組技法 **v2(271mm)⇒ 1 頁、v3(180mm)⇒ 1 頁** ——
**互斥不存在,那個「矛盾」也不存在**(全表與量法在
`docs/specs/2026-08-17-qc5-tracking-off-paper-decommission-list.md` §4c-2)。

### 為什麼它安靜

    重製品做得越忠實 → 越沒有人起疑 → 它量出來的數字越被當成事實
    而「像」是【溝通】的驗收標準，不是【量測】的驗收標準——
    這兩個用途共用同一份產物時，沒有任何機械訊號會告訴你用錯了

🔴 前一任自己寫下的那句話最準:
**「主視窗要的是【溝通用的像】;我拿它去做【量測用的等價】。而我沒有察覺那是兩個用途。」**

### 三件讓它翻案的動作(缺一都翻不了)

1. **不要再量同一個東西。** 前一任卡住不是因為量得不夠多,是因為**一直在量同一個對象**。
   四個對照組排得很好,而它們全部長在同一份重製上 ⇒ 再加十組也翻不了案。
   **換對象,不是加樣本。**
2. **配負向對照。** 新一輪七格全是 1 頁 —— 而「七格都 1 頁」與「我注入的 CSS 根本沒生效」
   **是同一個觀測**。加 `min-height:400mm` 兩發**都變 2 頁**,那七個 1 才有證據力。
   📎 這是 [[量具要雙向表演]] 的同一條:**該紅的餵一發必須紅。**
3. **把它輸出成人看得懂的形式看一眼。** 頁數只回答「幾頁」,不回答「**貼底有沒有成功**」——
   而後者才是原問題。`scripts/pagecount.sh --png` 就是為了這一格補的
   (在那之前,那句「量完要看一眼」寫在檔頭 `:25`,**沒有落點,所以沒有被執行**)。

### 判別句(下結論之前當場問)

> **我量的這份東西,是使用者/紙/客人真的會碰到的那一份,還是一份為了給人看而做出來的?**
> 是後者 ⇒ 我量到的是**那份重製的性質**,不是那個技法的性質。

> **這個「矛盾」,有沒有可能只是我量錯了對象?**
> 🔴 一個**物理上說不通**的量測結果(對超過 180mm 的內容設 `min-height:180mm` 竟然有作用),
> 第一個該懷疑的是**量測對象**,不是 CSS 規範。

### 收尾的口徑(這一步最容易寫壞)

翻案時要寫**「推翻的是【前提】不是結論」**,並明說**下一個人不必回頭重查什麼**。
寫成「我發現前一任錯了」的話,那三個已排除的候選會被下一個人重跑一遍 ——
**而它們的排除是對的、很值錢。**

📎 與本檔既有那條「基準可能是壞掉壞出來的」同族、方向相反:
那條講**基準本身壞掉**;本條講**基準沒壞,只是它不是你要的那個東西**。

## 檔案在磁碟上,而不在 git 裡 —— **每一道檢查都對,而它們量的是【隔壁那件事】**〔安靜〕

> ⚠️ **編號待補(2026-08-17 I 窗;依 08-17 丙裁定,新條目不編號、互相引用用標題文字)**

### 判別句

> 🔴 **我要的那件事,是【磁碟上有這個檔】還是【git 裡有這個檔】?**
> 兩者不是同一件事,而我跑的每一道檢查都只看得到前者。

一般化:**我的檢查看的是「動作有沒有執行成功」,還是「目的有沒有達成」?**
`cp` 回 0 只證明 `cp` 成功了,它對「這個檔會不會被 commit」**一個位元都沒說**。

### 實例(2026-08-17 夜 I 窗;本 session 實跑輸出)

要把 24 支 vitest 完整輸出從 `/var/folders` 的 tmp 搶救進 repo(`logs/` 在 `.gitignore:48`,
原本 `git ls-files logs/ | wc -l` ⇒ `0`)。第一版搬成 `docs/probes/<dir>/<run>.log`。

```
cp 全部成功                                             （零錯誤輸出）
wc -l 逐支對「共 N 行」  ⇒ 24 對得上 / 0 對不上          （還跑了負對照,見下)
ls docs/probes/2026-08-17-vitest-red-runs/*.log | wc -l ⇒ 24
──────────────────────────────────────────────────────────────
git check-ignore -v docs/probes/2026-08-17-vitest-red-runs/<任一>.log
   ⇒ .gitignore:49:*.log        ← 全域一條 *.log,把它們整批吃掉
git diff --cached --name-only | grep -c '\.log$'  ⇒ 0
```

🔴 **上面前三行【全部是真的】,而東西一個都沒進 git。** 沒有任何一項會紅。
🔴 **而它差點成功** —— 我是在收尾那一格順手跑 `git check-ignore` 才撞到的;
少跑那一格,這一顆 commit 會長成「25 files changed」還是「1 file changed」我都不會發現,
因為我當時看的是 `ls` 的輸出。

**修法**:副檔名改 `.txt`(不動 `.gitignore` —— 那是共用設定,加一條 `!` 例外會被下一個人再壓掉)。
`README` 同目錄寫明「**不要改回 `.log`**」與理由。

### 這一則的檢查怎麼寫才算數(兩條,缺一不可)

```
逐支、不是只驗第一支:
  for f in docs/probes/2026-08-17-vitest-red-runs/*.txt; do git check-ignore -q "$f" && echo 被忽略: $f; done
  ⇒ 零輸出
真憑據是 index 不是磁碟:
  git diff --cached --name-only | grep -c '\.txt$'   ⇒ 24
負對照(不然「零輸出」和「量具壞掉」長得一樣):
  touch docs/probes/2026-08-17-vitest-red-runs/_x.log && git check-ignore -q 該檔  ⇒ 命中
  ⇒ 上面那個「零輸出」是量出來的
```

### 為什麼它安靜

`.gitignore` 的設計就是**靜默**的 —— 被忽略的檔不會出現在 `git status`、不會有警告、`git add <目錄>`
也不報錯。⇒ **這個機制在正常運作時,和「我搬失敗了」在終端機上是同一個畫面。**

### 動作(不是決心)

- **凡「把東西放進 repo」這個目的**:落筆說「已搬進 repo」之前,跑一次 `git diff --cached --name-only`
  並**數它**。`ls`/`cp` 的成功不算數。
- **凡新增一整個目錄**:先 `git check-ignore -v <該目錄裡的一個檔>`,**再**開始搬。
- **零命中的檢查一律配負對照** —— 造一個「應該要被抓到」的靶,確認量具真的會叫。

### 與既有條目的關係

同一族的第三面(前兩面是 2026-08-17 當天收的):

| 條目 | 錯在哪 |
| --- | --- |
| **一個沒有本體的數字** | 數字活著,而它指的清單從來不存在 |
| **標「不適用」的格子其實是對照組** | 誠實地把最強的證據丟掉 |
| **檔案在磁碟上,不在 git 裡**(本條) | 每一道檢查都對,而它們量的是隔壁那件事 |

- memory `feedback_check-scope-narrower-than-risk-scope`:同源。本條是**事前**應用的一次
  (逐支驗、不是只驗第一支),那條的前兩次都是事後才發現。
- memory `feedback_absence-read-as-verified`:`git status` 的乾淨在這裡**不是**「沒事」,是「看不到」。

### 實例(2026-08-17 夜 I 窗;本 session 實跑輸出)

收割前用 `git merge-tree` 做不落地衝突預演。我先前對全陣廣播的判準是:

```
git merge-tree $(git merge-base dev <界線>) dev <界線> | grep -c 'changed in both'
```
並且加了一句聽起來很嚴謹的話:「`changed in both` **不等於**會撞,真判準是 `grep -c '^+<<<<<<<'`」。
**後半是對的,而前半的框架是錯的** —— 我把 `changed in both` 當成「會撞」的**粗糙版**,
它其實是 `git merge-tree` 的**其中一個分類標籤**。

當晚收 A 窗 `7edc8a30` 那一發:

```
grep -c 'changed in both'   ⇒ 0      ← 只跑這條會判「乾淨,可以收」
grep -c '^+<<<<<<<'         ⇒ 1      ← 真的撞
實際印出來的標籤是   added in both           （兩個窗各自從零建了同一個路徑）
```
⇒ `changed in both` 這把尺**看不見** `added in both` 與 `removed in both`。

**修法(兩條擇一,不要只跑第一條)**:

```
git merge-tree $(git merge-base dev <界線>) dev <界線> | grep -cE '^(changed|added|removed) in both'
git merge-tree $(git merge-base dev <界線>) dev <界線> | grep -c '^+<<<<<<<'
```
後者在本例抓到了,而前者的字集是我自己列的 ⇒ **能只信後者就只信後者**
(⚠️ 而後者也有它的射程:它抓的是**輸出裡的字面**,若被比對的內容本身就含 `<<<<<<<`
會自命中 —— 那時要開輸出看那幾行落在哪個檔的哪一段,不能只看數字)。

### 為什麼它安靜

`grep -c` 回 `0` 在終端機上,和「真的沒有這件事」是同一個畫面。
而分類標籤的**數量**不會有任何東西提醒你 —— **git 不會說「你還有兩個標籤沒查」。**

### 🔴 這一則獨有的那一面:**廣播讓一個錯的量法在全陣同時生效**

我不是自己用了那條命令而已 —— 我**把它當成收割紀律廣播給了全陣**,而當時它讀起來

⇒ **一個錯的量法,只要它比前一版精確,就會被當成改進而擴散。**
⇒ **動作**:凡是要**廣播**一條量法(不只是自己用),先問一句 ——

## 量具壞掉的時候,**它的錯誤訊息會偽裝成你要的那個數字**〔安靜〕

### 判別句

> 🔴 **我這條命令有沒有 `2>&1`,而右邊接的是 `wc -l` 或 `grep -c`?**
> 有 ⇒ **錯誤訊息現在是「資料」了。** 它會被算進去,而算出來的數字**看起來完全合理**。

前兩種失敗是「**訊號被丟掉**」(stderr 導去空、`$?` 被管線右端吃掉);
**這一種是「訊號變成了資料」** —— 更毒,因為前兩種會給你一個 `0`(至少可疑),
**這一種給你一個中等大小的正整數**。

### 實例(2026-08-17 夜 I 窗;本 session 實跑輸出)

```

rc（不接管線,直接跑）                 ⇒ 1        ← find 有報錯

type find                            ⇒ shell function（snapshot-zsh-…）
find --version                       ⇒ bfs 4.1.1
ISO 對照 '2026-08-17T00:00:00'        ⇒ 66      ← 量具是活的（正向對照）
```
⇒ 那個 `10` = **0 個檔 + stderr 的錯誤訊息行**。

結果變成「**錯誤被算進答案**」。**善意的那一手就是製造它的那一手。**

### 動作(不是決心)

- **要數東西的管線,不要接 `2>&1`。** 要看錯誤就分兩發跑,或把 stderr 導掉之後**另外**看 `rc`。
- **凡是拿管線輸出當結論**:那條的 `rc` **不是**你關心的那支指令的。
  ⇒ 要嘛不接管線,要嘛在**跑 pipeline 的那個 shell** 下 `set -o pipefail`
  (寫在腳本裡管不到包住它的那一個)。
- **判準寫進交接檔時**,凡形狀是 `<cmd> | wc -l` / `| grep -c` 的,

## 比較圖會製造出不存在的差別〔安靜〕

> **一張比較圖的預設失敗方式,不是漏講差別,是【讓人以為某個東西是差別】。**
> (主視窗抽的,我照用。)

### 判別句

> **我這張圖上,有哪些東西是【兩案一樣】的?我有沒有明講它們一樣?**

### 症狀

並排兩案時,讀者會把**兩案相同的東西**讀成差別 —— **因為它出現在一張「講差別」的圖上**。
版面本身就在說「左右不同」,而讀者不會逐項去問「這一項到底一不一樣」。

### 實例(2026-08-17 A 窗,artifact `1ff3e1de`「採購擺哪」)

Sean 要判「採購那塊留在訂單層,還是搬進品項展開列」。兩案並排之後,**這兩件事其實完全相同**:
```
① 同一個品項的兩家供應商  ⇒ 兩案都是兩列並排看得到（乙案收進展開列之後仍在同一張表裡）
② 可填可改的八個欄位      ⇒ 兩案一欄都沒有增減
```
**不標明的話,它們讀起來像乙案的代價。** ⇒ 圖上另立一塊
「**這兩件事兩案是一樣的 —— 不是差別**」。

🔴 **而真正的差別也因此才浮出來**:不是「同一項的兩家」(那不是差別),
是**跨品項** —— 甲案「某家供應商那三筆一起看」是一眼,乙案做不到(那三筆分在第 4、第 8 與第 3 項裡)。
**先把假差別劃掉,真差別才看得見。**

### 為什麼它安靜

```
① 沒有人會回報「我以為那是差別」—— 他只會【據此改主意】，而改完看起來完全正常
② 圖越漂亮、對比越強，這個效果越大（並排＋色塊＋大數字都在說「左右不同」）
③ 作者最不可能發現：作者知道哪些一樣，所以【他讀那張圖時不會誤讀】
```

### 動作(不是決心)

1. 產出任何比較物(圖 / 表 / A-B 選項)之前,先列一份「**兩案相同**」的清單,**並且把它印在圖上**。
2. 相同的那些**要放在同一個視覺份量**,不要縮成小字 —— 縮小等於沒寫。
3. **先劃掉假差別,再找真差別**:本次真差別是在劃掉假差別之後才浮出來的。

### 與既有條目的關係

本族其餘各條都在講「**量錯東西**」;**本條是【呈現】讓讀者量錯東西** ——
壞的不是我的量測,是我把量測結果擺出來的方式。

### 為什麼它安靜

    「我沒跑那條命令」  ⇒ 寫出來是「找不到」
    「我跑了、回 0 」    ⇒ 寫出來也是「找不到」
    ⇒ 這兩個世界在【句子】這一層沒有差別，而句子就是下一個人拿到的全部

而且它**還附了一個看起來很嚴謹的自我限定**(「未查到,不是不存在」)——
那個限定**讓句子更可信**,卻**一個字都沒有增加證據**。
🔴 **免責貼紙貼在一個沒做過的動作上,只會讓它更難被質疑。**

### 判別句(落筆寫「找不到 / 查無 / 沒有」的當下)

> **我剛剛真的跑了那條命令嗎?那條命令長什麼樣?它回了什麼?**
> 三個問題有任何一個答不出來 ⇒ 我要寫的不是「沒有這個東西」,
> 是「**我還沒查**」。這兩句話對讀的人做的事完全相反:
> 前者**關掉**他的尋找動作,後者**把動作交給**他。

### 動作(三條,缺一都會退回原狀)

1. **命令與結果一起落筆。** 沒有 `⇒ N` 就不准寫「找不到」。
2. **配正向對照。** 同一支 `grep` 在同一個範圍找一個**一定存在**的字,證明它會命中。
   (本例:找 `自取` ⇒ 27 檔 ⇒ 那把尺是活的。)
3. **標「未確認」時必附【缺哪一道檢查】。** 附不出來 = 免責貼紙,重寫。

### 📎 同族的另一個方向(2026-08-17 夜,B 窗)

B 窗把**已經拍過的板**寫成「還沒人拍」;我把**存在的東西**寫成「查無」。
⇒ **同一個沒做的動作:沒跑那條命令就先寫了結論。**
兩個方向的共通症狀:**產出的檔看起來完全正常**,而它關掉的是下一個人的動作
—— 一個讓他**不去找**,一個讓他**去等**。

📎 與本檔既有那條「量對了東西,卻量的是一個重製品」的關係:
那條是**量了、而量錯對象**;本條是**根本沒量、而寫得像量過**。
**後者比前者便宜得多也常見得多** —— 它連一次執行都不需要。

## **內容型斷言守不住「那個東西在哪一層」** —— 而繞過它的那條路,畫面幾乎一樣〔安靜〕

**實例(2026-08-17 晚,C 窗 `Q-C20` 續頁抬頭,`566bfcdf`)。**

要守的事:**列印時第 2 頁上要看得到「這是哪一張訂單、哪一箱」**。
做法是在品項表的 `<thead>` 裡多一列帶訂單編號與箱號 —— 靠的是**瀏覽器對 `<thead>` 的原生逐頁重複**。

**直覺會寫的守門**(而它是壞的):

```js
expect(textOf(container)).toContain('PCM-2026-0042')   // ← 恆綠
```

🔴 **因為頁首本來就印著一個訂單編號。** 把那一列**搬出 `<thead>`**
(挪去 `<caption>`、或表格上方的 `<div>`):

    畫面    幾乎一樣（同樣的字、同樣的位置）
    textContent  照樣含訂單編號
    四綠     全綠
    而列印時   第 2 頁變回沒有單號 —— 也就是這件事整個沒做

⇒ **內容型斷言在「已經壞掉」的那個世界裡照樣通過。**

### 為什麼它安靜

    這一族的壞法不是「東西不見了」，是「東西還在，只是搬到了不會被重複的那一層」。
    而「在哪一層」不在 textContent 裡，也不在畫面上 —— 它只在【列印時】才有後果。

### 修法:**釘位置,不釘存在**

```js
const bar = t.querySelector(':scope > thead > tr.contbar > th');   // ← 位置
expect(bar).not.toBeNull();
expect(bar?.textContent).toContain(orderDisplayId);               // 內容只是附加
expect(bar?.getAttribute('colspan')).toBe('3');
const rows = [...t.querySelectorAll(':scope > thead > tr')];
expect(rows[0]?.classList.contains('contbar')).toBe(true);        // ← 還要排在欄名【上面】
```

### 🔴 第二條,與上面同等重要:**不要假設「今天共用同一份 JSX」永遠成立**

出貨明細單有**三張**品項表,今天它們共用同一個 `Section` 元件
⇒ 一格斷言看起來就夠了、一發突變也會同時打到三張。
**而守門守的是契約,不是今天的實作細節。** 哪天有人把「訂單取消」那一區拆出去自己寫,
共用那一格**照樣綠**,而那一區靜默失去抬頭。⇒ **三張各釘一次。**

### 判別句(寫守門的當下)

> **我先想一下:這件事會怎麼被弄壞、而畫面看起來一樣?**
> 想得出那條路 ⇒ **照那條路去釘**,不要照「東西在不在」去釘。
> 想不出來 ⇒ 我還不知道我在守什麼,先別寫那格。

### 這格自己的雙向表演(不做這步就不算完)

    M1 `contbar` class 改名        ⇒ Tests 1 failed | 60 passed   rc=1
    M2 抬頭那一列與欄名那一列對調  ⇒ Tests 2 failed | 59 passed   rc=1
    兩發都先 cp 一份到 /tmp 再改，跑完 cp 回來並 diff -q 驗還原，
    git status --porcelain <該檔> 只剩本次修改那一行。

📎 與本檔上一則的關係:上一則是**沒跑那條命令**;本則是**跑了、而那條命令量的是別的東西**。
**兩則的共通點:產出看起來完全正常。**

## 結論對、而理由只有一半 —— **拿半個理由能推翻半個結論**〔安靜〕

> **來源:V 窗(Fable)2026-08-17 驗我一條宣稱時的原字,主視窗轉來。**
> 我把它擴寫成條目,**那句判別句是它的,不是我的**。

### 判別句

> **我給的理由,少了哪一段之後仍然成立?**
> 少一段就垮 ⇒ 那一段一定要寫出來。**理由不完整比結論錯更危險 ——
> 因為下一個人是【照理由】決定要不要重看,不是照結論。**

### 實例(2026-08-17 A 窗,我自己那條)

我在 plan 裡寫「空箱區**不可能**搬進品項展開層」,理由只給一段:
```
我寫的    shipments 表沒有 order_id ⇒ 它與這張訂單之間一條線都沒有
反駁      繞 shipment_items → order_items 就推得出訂單 —— 【對非空箱確實推得出】
⇒ 我的理由被推翻了一半，而【結論仍然成立】
```
**結論靠的是另外兩段,而我一段都沒寫**:
```
② 空箱【依定義】零 shipment_items 列 ⇒ 間接路徑對空箱是空集合，真的無路
③ COMMENT 自己寫「一箱可含多張訂單」⇒ 掛到某一個品項的展開層對【任何】箱都是型別錯誤
   （多對多硬塞一對一），不只空箱
```

### 為什麼它安靜

```
① 結論是對的 ⇒ 任何驗證「結論」的動作都會通過
② 理由讀起來完整（有出處、有行號、語氣肯定）—— 缺的是【我沒想到要寫的那兩段】，
   而缺席的東西沒有任何形狀
③ 🔴 最危險的下游不是「有人反駁」，是【有人反駁成功之後把結論一起丟掉】
   —— 他手上只有那半個理由，推翻它就沒有別的了
```

### 動作(不是決心)

1. 寫「不可能 / 做不到 / 一定會」這種**強結論**時,**列出所有承重的理由**,不要只寫最好講的那一段。
2. **自我攻擊一次**:每一段理由假設被推翻,結論還在嗎?**還在 ⇒ 那段不是承重的,而承重的那段我沒寫。**
3. 別人替你補上缺的那半時,**把補的那半寫進原檔**,不要只留在訊息裡。

### 與既有條目的關係

- 與「**比較圖會製造出不存在的差別**」互補:那條是**多講了不存在的東西**,本條是**少講了承重的東西**。
- 📎 memory `feedback_scoped-claim-this-only-affects-X` 記過「**理由錯而結論對不代表沒事**」——
  **本條是它的另一半:理由【不完整】而結論對,一樣不代表沒事。**

## 一條指向【別的檔】的量法,會在那個檔被更正的時候**安靜地反向**〔安靜〕

### 判別句

> 🔴 **我寫的這條量法,查的是【我這個檔】還是【別人那個檔】?**
> 別人那個檔 ⇒ **它被更正的那天,我的量法不會壞掉,它會開始給相反的答案。**

一般化:**壞掉的量法會讓人停下來,反向的量法不會** —— 它照樣印出結果,而結果讀起來像確認。

### 實例(2026-08-17 夜 I 窗;本 session 實跑輸出)

`docs/specs/2026-06-13-m3-3ds-webhook-master-plan.md:24-25` 原本這樣寫(逐字):

```
· **`STATUS.md`**(專案 SSoT)逐字:「🟡 M-3 prod checkout 仍不可開(**3DS flag 全 false**…)」。
  量法:`grep -n '3DS flag 全 false' STATUS.md`。
```
那條量法**當時是對的**:命中 ⇒ STATUS 確實那樣主張。
而我在 `6074a448` 把 STATUS 那欄改掉了,**並且照規矩留痕**(`~~本欄原寫「3DS flag 全 false」~~`)。

```
落地後當場跑:grep -c '3DS flag 全 false' STATUS.md   ⇒ 1
```
🔴 **它還是命中 —— 而命中的是那句話的【訃聞】,不是那句話。**
⇒ 照它跑的人會得到「STATUS 還這樣寫」,**而事實相反**。

🔴 **這比回 0 更糟**:回 0 至少看得出「這句話不在了,去查一下」;
**命中會讓人以為問題還在原地**,他不會再往下查。

### 為什麼它安靜

留痕(刪除線)是**正確**的做法 —— 不留痕的話,引用它的人會找不到自己引的東西去哪了。
⇒ **正是那個正確的做法讓下游的量法反向。** 兩件對的事湊在一起,產生一件錯的事,
而**兩邊各自都沒有做錯**,所以任何一邊的檢查都不會叫。

### 動作(不是決心)

- **寫**跨檔量法時,同一段標明「**這條量的是 `<那個檔>` 的現況,那個檔一改本條就要重寫**」。
- **改**一個被別處引用的字面時,`literal-sweep.sh` 撈出來的每一處要**分兩類**:
  ①**引用它的敘述** ⇒ 改敘述 ②**引用它的量法** ⇒ 🔴 **量法不能只改敘述,要換成現在還會給正確答案的那條**,
  或刪掉並寫明「原量法已失效,因為 `<檔>` 已於 `<日期>` 改寫」。**留一條會反向的量法,比不留更糟。**
- 換掉之後**當場跑一次新舊兩條**,把兩個輸出並排寫進去(舊的命中什麼、新的命中什麼)。

### 與既有條目的關係

- canonical 的「**更正本身會過期**」:那條講的是**更正這件事**本身的下游;
  本條窄一級 —— **下游是一條【量法】的時候,它不會過期,它會反向。**
- memory `feedback_absence-read-as-verified`:那條是「0 被讀成沒事」;
  **本條是它的鏡像 ——「命中被讀成還在」。** 同一個病,兩個方向。

主視窗裁定開 `docs/patterns/traps-inbox/` 暫存區,並在**同一則訊息**裡叫 A 窗建 `README.md`。

merge-base 有這個檔 ⇒ NO      dev 有 ⇒ YES(我的)      界線有 ⇒ YES(A 窗的)

```
同一題「採購那塊要不要搬進品項展開列」，兩種給法：

第一次 · 文字   主視窗告訴 Sean:「搬過去之後一次只能展開看一項」

🔴 **而他拍板的依據,是【文字版沒有講對的那一層】**:
```
文字講的  「一次只能看一項」
真正的痛  「同一家供應商跨三項的單，甲案一眼掃完，乙案散在第 4、第 8、第 3 三個展開層裡」
⇒ 這一層是【畫圖的時候才長出來的】——
   畫之前我以為代價是「要多點幾下」，畫出來才看到代價是「某些問題【問不出來】」
```

### 為什麼文字會漏掉那一層

```
① 文字描述的是【單一元件的行為】（「一次只開一項」）
   而代價發生在【乘出來之後】（8 項 × 3 家供應商的分佈）—— 單一元件的描述裡不存在「分佈」
② 寫文字的人腦中有一張圖，而【他描述的是那張圖的規則，不是那張圖】
   規則是對的，而讀的人腦中生不出同一張圖
③ 🔴 沒有人會回報「你的文字讓我低估了代價」—— 他只會【不採取行動】，而不行動沒有任何形狀
```

### 動作

1. **視覺類 / 版面類的取捨,一律畫出來**(Sean 08-17 常設令)——
   本則是那條令的**乾淨正面實例**:同一題、同一天、兩種給法、兩種結果。
2. **要放「乘出來」的樣子**(多列 / 多品項),不要單一元件 —— **代價住在乘出來的那一層。**
3. 畫完之後**回頭看自己原本的文字描述**:如果兩者講的不是同一件事,
   **那份文字要更正,不能留著** —— 它會被下一個人當成結論引用。

### 與既有條目的關係

- 與「**比較圖會製造出不存在的差別**」是同一張圖的兩面:那條講**圖會多講**,本條講**文字會少講**。

## 一把尺可以【分母是空的】,也可以【方向是反的】——**兩種印出來都很正常**〔安靜〕

> 來源:2026-08-18 凌晨 I 窗(收割窗),**同一輪之內三發、三種不同的失效方式**,
> 而三發**全部**是自己在做「驗證別人」的動作時,對**自己剛寫的量法**做負向對照才抓到的。
> 母題與本檔開頭那句同一個:**錯的那次和對的那次長得一樣。**
> 本節把三發寫在一起,因為它們是**同一個母題的三個面**,分開讀會各自像是「不小心」。

### 三發

**發一 · 分母是空的**
```
我要驗「已經收進 dev 的那幾批,commit body 有沒有作者自陳未授權」
我跑    git log --format='%h %B' 35f73b27..d4cf1175 | grep -E '偏離|未拍板|…'
印出    (零命中)
真相    35f73b27 是 d4cf1175 的【後代】 ⇒ 那個範圍裡是 0 顆
        🔴 grep 對【空輸入】回零命中,而它印出來與「掃過 5 顆而乾淨」一模一樣
```
🔴 **`grep` 不會告訴你它讀了幾行。** 零命中有兩個世界:**掃過而乾淨** / **根本沒東西進來**,
而**輸出完全相同**。⇒ 修法不是更小心,是**先報分母**:批內顆數 0 就判「範圍算錯」,不判「乾淨」。
(正確範圍:merge 顆那一批 = `<merge>^1..<merge>^2`。)

**發二 · 方向是反的,而它朝【安全】那邊錯**
```
我要驗「這個分支的基底,是不是已經在 dev 裡」
我跑    git merge-base --is-ancestor dev 25e1656c     ⇒ NO
它問的是「dev 是不是 25e1656c 的祖先」——而 dev 剛落了我自己兩顆 commit ⇒ 當然不是
正確    兩者的 merge-base(a207be42)是不是 dev 的祖先 ⇒ YES
```
🔴 **這一發最值錢的不是錯本身,是它【不會被發現】的機制**:
它的錯誤結論是「**不要收**」⇒ 我照做 ⇒ **不會出事** ⇒ **沒有任何東西會告訴我量法寫反了**。
⚠️ 而下一次同樣的寫法,可能朝**另一個方向**錯。
⇒ **判別句:我這把尺上一次「叫我不要做」的時候,我有沒有回頭確認它叫對了?**
**往安全方向錯的錯,沒有反饋迴路。**

**發三 · 失敗的命令仍然把【原字串】印到 stdout**
```
我寫    P2="$(git rev-parse "$M^2" 2>/dev/null || true)"
        if [ -z "$P2" ]; then 報「不是 merge 顆」; fi
真相    git rev-parse <非 merge 顆>^2 失敗時,**仍然把 `<sha>^2` 這個原字串印到 stdout**
        ⇒ P2 拿到一個【非空的垃圾值】⇒ 那道 -z 守衛【從來不會成立】
後果    一路掉到 grep,分母是空字串、`[ "$N" = "0" ]` 也不成立
        ⇒ 印出「✅ 零命中」而且 rc=0
```
🔴 **這一發的諷刺之處**:那支腳本**就是為了防發一而寫的**,而它自己犯了同一個形狀 ——
**一個為了避免假通過而寫的工具,自己產生了一次假通過。**
⇒ 修法:`git rev-parse --verify --quiet`(失敗時**不印東西**、回非 0),
並且對顆數加一道「**空字串與非數字都當算錯**」——只擋 `0` 是不夠的,空字串不等於 `0`。

### 動作(三條都是「換一個不需要記得的寫法」,不是「更小心」)

1. **任何回報零命中的地方,先報分母** —— 分母算不出來就報「算錯」,不報「乾淨」。
2. **`--is-ancestor` 這種有方向的尺,寫完立刻問「它兩個世界都會答對嗎」** ——
   特別是**它叫你不要做**的那一次,那一次沒有人會替你複查。
3. **不要用 `$(cmd || true)` 接一個「失敗時可能還有輸出」的命令** ——
   改用該命令自己的靜默/驗證旗標(`--verify --quiet` / `-q`),或**分開檢查退出碼**。

### 與既有條目的關係

- 與「**什麼都沒有被讀成檢查過了**」是同族,而本節補的是**上游**:
  那條講「零命中不等於不存在」,本節講 **「零命中」這個輸出本身可能是分母造出來的**。
- 發二與「**一裝就不叫的守門會被當冗餘刪掉**」互為反面:
  那條講**沒救過人所以被刪**,本條講**叫錯了卻因為方向安全而沒人發現**。
