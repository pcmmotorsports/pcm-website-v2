# 一個做法要能傳染,需要什麼?

> **產出**:T 窗,2026-08-18 凌晨。**起因**:一夜之內撞到**四個形狀完全相同**的實例
> (前三個本窗自己撞到,第四個 V 窗交來)——
> 同一個 repo 裡,**對的做法寫在一個檔、錯的做法在另一個檔**,而第三次連「不准補 0」這句話
> **都已經寫在 code 裡了**。
>
> 🔴 **本檔刻意不寫成「這個 repo 的對的做法傳不出去」** —— 那是一句感嘆,讀完沒有人知道要做什麼。
> 本檔問的是:**一個做法要能傳染,需要哪幾層?四個實例各自缺了哪一層?哪一層可以花錢買?**
>
> ⚠️ **本檔的成本估算是【量到的】**(§4 有可重跑的命令與數字),**而嚴重度分級是判斷**。兩者分開讀。

## §1 四個實例(每個都附「對的那一半在哪」)

| # | 錯的那一半 | 對的那一半(同 repo) | 現況 |
|---|---|---|---|
| ① | `settle-charge.ts` 用 `(refundedAmount ?? 0) !== 0` 當閘 ⇒ **欄缺被翻成「沒退款」⇒ 放行** | `refund-baseline.ts:8` / `refund-judgment.ts:12` **明文標成鐵律**:該欄缺時**嚴禁** `?? 0`,兩處實作皆「欄缺 = abort / 停」 | 已修 `a1210748` |
| ② | `shipping-doc.tsx:92` `reportedTotal !== null && …` ⇒ **總數沒拿到時整道守門短路 ⇒ 出貨單照印** | `SupabaseWalletAdapter.listEntries` 對同一種狀態 **throw**,理由逐字:「本方法以『共 N 筆』為前提,**沒有 N 就不回傳一份看起來完整的一頁**」 | 已轉 C 窗 |
| ③ | `catalog-page.ts:64` `price: row.price_general ?? 0` ⇒ **目錄卡片印 NT$ 0** | `mappers/product.ts:206` **throw**,docstring `:176` 逐字:「@throws 若 `price_general` 為 null(雙寫過渡期缺欄、**不 silent 補 0**)」 | 顯示層 must-fix,未修 |
| ④ | `tier.ts:48` `PCM_DEV_TIER_OVERRIDE === '1' && …` ⇒ **沒有 production 硬閘**;env 一旦是 `'1'`,任何人加 `?tier=store` 就覆蓋會員等級(經銷價防護鏈最上游) | `proxy.ts:18` 與 `authorize.ts:18` **同一種 dev flag,兩處都寫了** `NODE_ENV !== 'production' && …`;還配一格 `proxy.test.ts:27` 擋測試環境外洩 | 潛在,見下方兩條限定 |

### ④ 為什麼是這四個裡**最乾淨**的一個(V 窗 2026-08-18 交來)
```
同一個 repo、同一種東西(dev 用的後門 flag)、而【對的寫法就在隔壁檔案裡,還寫了兩份】
⇒ 「對的做法沒有辦法傳染」在這裡的具體形狀是:
   **寫對的人和寫漏的人,可能連彼此的檔案都沒打開過。**
```

🔴 **而我讀 code 時看到一個更利的角度(V 窗沒點,我補)**:
```
tier.ts:25 的 JSDoc 逐字寫著「僅當 env flag PCM_DEV_TIER_OVERRIDE=1 時生效、**production 預設關**」
而 :48 的 code 只有   process.env.PCM_DEV_TIER_OVERRIDE === '1'
⇒ 🔴 那個「關」是【部署狀態】,不是【程式保證】——
  它成立只因為那個 env 沒被設,而不是因為 code 擋著。
⇒ 這是「註解寫的是想守什麼,斷言寫的是真表達得出什麼」的又一例,
  而這一次註解裡的那個詞(「預設關」)讀起來就像 code 有擋。
```

**兩條限定,引用時必須一起帶(V 窗要求,而理由成立)**:
```
1 🔴 它不是被忘記,是【被排程了】—— tier.ts:51-52 自己寫著
   「H-1(#215)…M-2-08 接真經銷價前須改為 server 端認證查 customers.tier。**本行現狀未改、只釘樁。**」
   ⇒ 下一個人讀本檔時要知道:有人早就知道。
2 🔴 【今天走不到】—— V 窗實測 `vercel env ls production --project pcm-website-v2`
   ⇒ PCM_DEV_TIER_OVERRIDE 命中 0
   (正向對照 NEXT_PUBLIC_SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY / TAPPAY_3DS_ENABLED 各 1;
    負向對照 假名 ZZ_BOGUS_ENV_NAME ⇒ 0 ⇒「沒列到」與「我讀不到清單」分得開)
   ⇒ **潛在,不是現行繞過。**
   ⚠️ 🔴 **上面這一段是【讀來的】** —— repo 內那兩處 code 我自己驗過,
      而 `vercel env` 那部分我沒有存取權、沒有重跑,來源是 V 窗。
```

⇒ **真正的風險是「哪天有人為了 debug 在 Vercel 面板加上它」** —— 而那一刻**沒有任何東西會擋**,repo 內也不會有訊號。
**補一行 `NODE_ENV !== 'production' &&` 就讓那個未來動作變成無害**,而那一行的範本在同一個 repo 裡已經有兩份。

🔴 **四次的形狀完全一樣**:**寫下來的地方守住了,沒寫下來的地方沒守住 —— 而它們在同一個 repo、常常是同一個欄位。**

## §2 四層框架:一個做法要能傳染,需要什麼

```
1 有沒有一個【寫下來的地方】?
2 寫下來的那個地方,跟【要用它的人】會不會相遇?
3 有沒有東西會在【違反的那一刻】叫?
4 而裝那個「會叫的東西」,划不划算?(機制裝在沒有事的那條路上是淨負)
```

### 逐層對四個實例

**第 1 層:有沒有寫下來 ⇒ 四個實例【全部有】✅**
```
① 標成鐵律,兩個檔各寫一次   ② 理由寫在 code 裡,而且寫得很好
③ 連 @throws 都標了         ④ 🔴 對的寫法【就在隔壁檔案,而且寫了兩份】
⇒ 🔴 問題不在這一層。再寫一次規則,不會改變任何事。
```

**第 2 層:寫的地方與用的地方會不會相遇 ⇒ 四個實例【全部不會】❌**
```
① refund-baseline.ts / refund-judgment.ts  vs  settle-charge.ts     不同 package
② SupabaseWalletAdapter                     vs  shipping-doc.tsx     不同層
③ mappers/product.ts                        vs  catalog-page.ts      不同 app
④ proxy.ts / authorize.ts(admin)          vs  tier.ts(storefront) 不同 app
⇒ 寫的人與用的人【不會同時打開那兩個檔】。這一層無法靠「更用心」修好。
⇒ 🔴 而 ④ 是這一層最赤裸的證據:同一種 dev flag、同一個 repo、對的寫法有兩份範本,
  而漏的那一處連一行 `NODE_ENV !== 'production' &&` 都沒有。
```

**第 3 層:違反的那一刻有沒有東西會叫 ⇒ 四個實例【全部沒有】❌**
```
三綠不紅、type 正確、lint 不管、測試也綠(而 ① 的測試 fixture 還剛好造了一個
production 不會出現的形狀,讓真正該走的那條路從來沒被走過 —— 見 traps-inbox/T-20260818.md 第三則)
⇒ 🔴 這才是唯一可以花錢買的那一層。
```

**第 4 層:划不划算 ⇒ 見 §4(有量過,不是估的)**

## §3 這一族的判準演進(三層,愈後面愈好但條件愈嚴)

本檔的四個實例與同夜掃出的正反例,把判準逼出了三層:

```

   ?? 本身不是病。判準:這個預設值讓守門【更容易響】還是【更不容易響】?
   反例 order-detail-route.tsx:236 `cancellationsTruncated ?? true`
```

## §4 🔴 第 3 層做不做得成機制 —— **我試了,做得成一半**

**假說**:這一族有一個可掃的形狀 ——
**同一個欄位名,在 repo 的某處被【throw 拒絕 null】,在另一處被 `??` 補值。**
🔴 **它的規則來源是 repo 自己的立場,不是一份要人維護的清單** —— 那是它可能划算的原因。

### 原型實測(可重跑)

```sh
# 步驟1:誰被明確拒絕過(throw 前兩行內有 null/undefined 檢查)
grep -rnB2 'throw new Error' --include='*.ts' packages/ apps/ | grep -v '\.test\.' \
  | grep -oE '[a-z_]+ === null|[a-zA-Z]+ === undefined' | sort | uniq -c | sort -rn
```
落筆當下輸出(去掉 `raw` / `so` / `d` 這類區域變數雜訊後):
```
2 price_general === null      ← 實例 ③ 的拒絕方
1 count === null              ← 實例 ② 的拒絕方
1 amount === undefined        ← 實例 ① 修完之後的樣子
```

```sh
# 步驟2:拿這些欄位名去找他處的 ?? 補值
for f in price_general count refundedAmount; do
  echo "$f 拒絕 $(grep -rn "$f === null\|$f === undefined" --include='*.ts' --include='*.tsx' packages apps | grep -v '\.test\.' | wc -l) 處 / 補值 $(grep -rnE "$f *\?\?" --include='*.ts' --include='*.tsx' packages apps | grep -v '\.test\.' | wc -l) 處"
done
```
落筆當下輸出:
```
price_general   拒絕 2 / 補值 1     ⇒ 🔴 正好是實例 ③ 那一對
refundedAmount  拒絕 3 / 補值 1     ⇒ ⚠️ 見下面「第一次跑就自己產生假陽性」
count           拒絕 2 / 補值 8     ⇒ 8 處待 triage(這就是真正的工作量)
reportedTotal   拒絕 0 / 補值 0     ⇒ 🔴 實例 ② 這個形狀【掃不到】
```

### 結論:**做得成一半,而另一半要誠實說出來**

```
✅ 掃得到:實例 ① 與 ③ 的形狀(`<欄位> ?? <值>` vs 同名欄位在他處被 throw)
   —— 規則來源是 repo 自己的 throw,不需要人維護清單
❌ 掃不到:實例 ② 的形狀(`x !== null && <判斷>`)
   —— 它不是補值,是【短路】。
❌ 也掃不到:實例 ④ 的形狀(**該有的那一行【不在】**)
   —— 前三個是「寫錯了什麼」,④ 是「【少寫】了什麼」。
   🔴 **掃「有什麼」比掃「少什麼」容易一個數量級** —— 要掃 ④ 得先有一份
   「哪些 env flag 屬於 dev 後門」的清單,而那份清單要人維護 ⇒ 回到第 1 層的問題。
⇒ 🔴 **四個實例、三種語法形狀,而一支掃描只蓋得住一種。**
  這是本成本表能被信任的原因 —— 一支抓得到全部的工具,通常是還沒被誠實量過。
⚠️ 必須剝註解:第一次跑,`refundedAmount ??` 那一筆命中的是**我自己寫的註解**
   (settle-charge.ts:425 在講「這裡原本寫 ?? 0」)⇒ **掃描第一次跑就自己產生了一個假陽性**
```

### 成本 / 換到什麼(給拍板用)

```
成本  一支唯讀腳本 + selftest,約與 plan-approval-drift.sh 同級(該支 132 行、6 格 selftest)
      每次跑的成本:兩趟 grep,秒級
換到  「同一個欄位在 A 檔被拒絕、在 B 檔被補值」這一對,在【違反的那一刻】被列出來
      —— 而四個實例裡有兩個是這個形狀
沒換到 ① 實例 ② 那種短路形狀 ② 方向判斷(哪個預設值是對的仍要人判)
      🔴 ⇒ 它的產出是【要人看的清單】,不是判決。這一點必須寫在輸出裡,否則
        「看起來很完整的清單」會讓讀的人以為方向也被判過了(同 traps 第四則)
```

🔴 **而我不建議現在就做這支腳本,理由與主視窗否掉另一支時相同**:
```
現在四個實例已經逐個處理或定位完(①已修 ②已轉 ③待修 ④潛在且已排程)⇒ 這支腳本【當下抓不到新東西】
它的價值在【未來】:下一次有人寫下同款補值時被抓到
⇒ 那是「機制裝在會出事的路上」,划算;但它的效益要等下一次違反才兌現
⇒ **建議:等 `count` 那 8 處 triage 完,若其中有真洞 ⇒ 立刻做;若 8 處全是合法 ⇒ 這個形狀的
   母體比想像小,那就不做,把結論寫回本檔。**
```

## §5 這份文件本身怎麼用

```
· 要判「某個做法為什麼傳不出去」⇒ 走 §2 四層,答案幾乎都在第 2、3 層
· 要判「該不該為某一族裝機制」⇒ 走 §4 的三問:掃得到嗎 / 掃不到的那半是什麼 / 母體多大
· 🔴 而第 1 層(有沒有寫下來)幾乎永遠是 ✅ —— **所以「再寫一次規則」是最沒有效益的動作**,
  而它同時是最容易做的那個。這是本檔存在的主要理由。
```

⚠️ **本檔的分母限定**:四個實例來自 2026-08-17 夜到 08-18 凌晨的一輪工作
(①②③ 本窗掃 admin 出貨/錢/權限/顯示 + storefront;④ V 窗掃 repo 外設定時交來)。
**這不是全 repo 的普查**,而「四次」這個數字只代表**這一輪撞到四次**,不代表全部只有四處。
🔴 而它們是**四個人各自撞到的**,不是同一次掃描的產物 ⇒ **母體大小完全未知。**
