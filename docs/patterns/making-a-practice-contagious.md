# 一個做法要能傳染,需要什麼?

> **產出**:T 窗,2026-08-18 凌晨。**起因**:一夜之內撞到**三個形狀完全相同**的實例 ——
> 同一個 repo 裡,**對的做法寫在一個檔、錯的做法在另一個檔**,而第三次連「不准補 0」這句話
> **都已經寫在 code 裡了**。
>
> 🔴 **本檔刻意不寫成「這個 repo 的對的做法傳不出去」** —— 那是一句感嘆,讀完沒有人知道要做什麼。
> 本檔問的是:**一個做法要能傳染,需要哪幾層?三個實例各自缺了哪一層?哪一層可以花錢買?**
>
> ⚠️ **本檔的成本估算是【量到的】**(§4 有可重跑的命令與數字),**而嚴重度分級是判斷**。兩者分開讀。

## §2 四層框架:一個做法要能傳染,需要什麼

```
1 有沒有一個【寫下來的地方】?
2 寫下來的那個地方,跟【要用它的人】會不會相遇?
3 有沒有東西會在【違反的那一刻】叫?
4 而裝那個「會叫的東西」,划不划算?(機制裝在沒有事的那條路上是淨負)
```

### 逐層對三個實例

**第 1 層:有沒有寫下來 ⇒ 三個實例【全部有】✅**
```
① 標成鐵律,兩個檔各寫一次   ② 理由寫在 code 裡,而且寫得很好   ③ 連 @throws 都標了
⇒ 🔴 問題不在這一層。再寫一次規則,不會改變任何事。
```

**第 2 層:寫的地方與用的地方會不會相遇 ⇒ 三個實例【全部不會】❌**
```
① refund-baseline.ts / refund-judgment.ts  vs  settle-charge.ts     不同 package
② SupabaseWalletAdapter                     vs  shipping-doc.tsx     不同層
③ mappers/product.ts                        vs  catalog-page.ts      不同 app
⇒ 寫的人與用的人【不會同時打開那兩個檔】。這一層無法靠「更用心」修好。
```

**第 3 層:違反的那一刻有沒有東西會叫 ⇒ 三個實例【全部沒有】❌**
```
三綠不紅、type 正確、lint 不管、測試也綠(而 ① 的測試 fixture 還剛好造了一個
production 不會出現的形狀,讓真正該走的那條路從來沒被走過 —— 見 traps-inbox/T-20260818.md 第三則)
⇒ 🔴 這才是唯一可以花錢買的那一層。
```

**第 4 層:划不划算 ⇒ 見 §4(有量過,不是估的)**

## §3 這一族的判準演進(三層,愈後面愈好但條件愈嚴)

本檔的三個實例與同夜掃出的正反例,把判準逼出了三層:

```
① 方向倒向哪邊
   ?? 本身不是病。判準:這個預設值讓守門【更容易響】還是【更不容易響】?
   反例 order-detail-route.tsx:236 `cancellationsTruncated ?? true`
        ⇒ 不知道有沒有截斷時倒向【有】⇒ 走安全路徑 ✅

② 有沒有把「不知道」說出來
   picking-doc.tsx:81 註解逐字:「null(不知道)算 false —— 不知道就不要叫人去揀。
   但【它不可以就這樣消失】:合計旁邊要把『不知道』那幾項單獨講出來」✅

③ 🔴 去把「不知道」變成「知道」
   products.ts:434-439(`#393-A`,Sean 2026-08-11 拍 A):零列且 page > 1 時
   **再打一發 offset:0 limit:1 把 total 探回來**
   ⚠️ 這一層只在【探得回來】時可行 ⇒ **它是有條件的最佳解,不是通則。**
```

## §4 🔴 第 3 層做不做得成機制 —— **我試了,做得成一半**

**假說**:這一族有一個可掃的形狀 ——
**同一個欄位名,在 repo 的某處被【throw 拒絕 null】,在另一處被 `??` 補值。**
🔴 **它的規則來源是 repo 自己的立場,不是一份要人維護的清單** —— 那是它可能划算的原因。

### 原型實測(可重跑)

```sh
# 步驟1:誰被明確拒絕過(throw 前兩行內有 null/undefined 檢查)
grep -rnB2 'throw new Error' --include='*.ts' packages/ apps/ | grep -v '\.test\.' \
  | grep -oE '[a-z_]+ === null|[a-zA-Z]+ === undefined' | sort | uniq -c | sort -rn
```
落筆當下輸出(去掉 `raw` / `so` / `d` 這類區域變數雜訊後):
```
2 price_general === null      ← 實例 ③ 的拒絕方
1 count === null              ← 實例 ② 的拒絕方
1 amount === undefined        ← 實例 ① 修完之後的樣子
```

```sh
# 步驟2:拿這些欄位名去找他處的 ?? 補值
for f in price_general count refundedAmount; do
  echo "$f 拒絕 $(grep -rn "$f === null\|$f === undefined" --include='*.ts' --include='*.tsx' packages apps | grep -v '\.test\.' | wc -l) 處 / 補值 $(grep -rnE "$f *\?\?" --include='*.ts' --include='*.tsx' packages apps | grep -v '\.test\.' | wc -l) 處"
done
```
落筆當下輸出:
```
price_general   拒絕 2 / 補值 1     ⇒ 🔴 正好是實例 ③ 那一對
refundedAmount  拒絕 3 / 補值 1     ⇒ ⚠️ 見下面「第一次跑就自己產生假陽性」
count           拒絕 2 / 補值 8     ⇒ 8 處待 triage(這就是真正的工作量)
reportedTotal   拒絕 0 / 補值 0     ⇒ 🔴 實例 ② 這個形狀【掃不到】
```

### 結論:**做得成一半,而另一半要誠實說出來**

```
✅ 掃得到:實例 ① 與 ③ 的形狀(`<欄位> ?? <值>` vs 同名欄位在他處被 throw)
   —— 規則來源是 repo 自己的 throw,不需要人維護清單
❌ 掃不到:實例 ② 的形狀(`x !== null && <判斷>`)
   —— 它不是補值,是【短路】。同一族的病,兩種語法,一支掃描只蓋得住一種
⚠️ 必須剝註解:第一次跑,`refundedAmount ??` 那一筆命中的是**我自己寫的註解**
   (settle-charge.ts:425 在講「這裡原本寫 ?? 0」)⇒ **掃描第一次跑就自己產生了一個假陽性**
```

### 成本 / 換到什麼(給拍板用)

```
成本  一支唯讀腳本 + selftest,約與 plan-approval-drift.sh 同級(該支 132 行、6 格 selftest)
      每次跑的成本:兩趟 grep,秒級
換到  「同一個欄位在 A 檔被拒絕、在 B 檔被補值」這一對,在【違反的那一刻】被列出來
      —— 而三個實例裡有兩個是這個形狀
沒換到 ① 實例 ② 那種短路形狀 ② 方向判斷(哪個預設值是對的仍要人判)
      🔴 ⇒ 它的產出是【要人看的清單】,不是判決。這一點必須寫在輸出裡,否則
        「看起來很完整的清單」會讓讀的人以為方向也被判過了(同 traps 第四則)
```

🔴 **而我不建議現在就做這支腳本,理由與主視窗否掉另一支時相同**:
```
現在三個實例已經逐個處理完(①已修 ②已轉 ③待修)⇒ 這支腳本【當下抓不到新東西】
它的價值在【未來】:有人第四次寫下同款補值時被抓到
⇒ 那是「機制裝在會出事的路上」,划算;但它的效益要等下一次違反才兌現
⇒ **建議:等 `count` 那 8 處 triage 完,若其中有真洞 ⇒ 立刻做;若 8 處全是合法 ⇒ 這個形狀的
   母體比想像小,那就不做,把結論寫回本檔。**
```

## §5 這份文件本身怎麼用

```
· 要判「某個做法為什麼傳不出去」⇒ 走 §2 四層,答案幾乎都在第 2、3 層
· 要判「該不該為某一族裝機制」⇒ 走 §4 的三問:掃得到嗎 / 掃不到的那半是什麼 / 母體多大
· 🔴 而第 1 層(有沒有寫下來)幾乎永遠是 ✅ —— **所以「再寫一次規則」是最沒有效益的動作**,
  而它同時是最容易做的那個。這是本檔存在的主要理由。
```

⚠️ **本檔的分母限定**:三個實例都來自 2026-08-17 夜到 08-18 凌晨的一輪掃描
(admin 出貨/錢/權限/顯示 + storefront)。**這不是全 repo 的普查**,而「三次」這個數字
只代表**我這一輪撞到三次**,不代表全部只有三處。
