## 1. 事實（**Sean 在 `pcm-quote-v2` 跑的，我沒有那個庫的帳號**）

我給的診斷 SQL **刻意只回數字、不回內容**：

```sql
SELECT count(*) AS 排程數,
       count(*) FILTER (WHERE command ~* 'bearer|secret|token|key|password') AS 疑似含祕密的排程數
  FROM cron.job;
```

**回傳：`排程數 9` / `疑似含祕密的排程數 2`。**

⚠️ **「疑似」兩個字要留著**：那是**一個正規表示式的命中數**，不是「確認有祕密」。
`key` 這種字也可能出現在無害的地方（`ORDER BY key`、`api_key_name` 這類欄名）。
**⇒ 現況＝「有 2 筆值得人看一眼」，不是「有 2 把外洩的鑰匙」。**

## 2. 誰讀得到 `cron.job`（**網站庫實測**）

| 角色 | schema USAGE | 表授權 | **真的讀得到** |
|---|---|---|---|
| `postgres` | ✅ | ✅ | 🔴 **是** |
| `supabase_admin` | ✅ | ✅ | 🔴 **是** |
| `anon` / `authenticated` / `service_role` / `payment_confirmer` / `pcm_audit_ro` | ❌ | ✅ | **否** |

⚠️ **這張表量自【網站庫】。** 報價單庫的 `anon` 那格 Sean 量過（`false`，與此一致），
**其餘角色在報價單庫我沒量** ⇒ 標**未確認**。
📎 教訓：**交出一份表時，量測來源要寫在表上，不是寫在信裡** —— 表會被複製走，信不會跟著走。

### 🔴 所以這條的真正意義是：**它與「誰能開 Dashboard」是同一個信任面**

`postgres` **正是 Supabase Dashboard SQL editor 的身分**。
⇒ **任何能開那個 Dashboard 的人，讀得到排程定義裡的每一個字。**

**⇒ 這不是「對外曝露」**（外部角色兩層都不通）。
**它是「祕密的儲存位置選錯了」** —— 祕密應該住在只有需要它的執行體看得到的地方，
**而不是住在一個「任何管理員一眼就看到」的定義欄位裡。**

## 3. 為什麼**現在**值得處理（不是「以後再說」）

1. **後台正要開給員工用。** 今天「能開 Dashboard 的人」約等於 Sean；**那個集合正在變大。**
2. **祕密寫在定義裡 ⇒ 它會出現在每一次的備份、每一次的 schema dump、每一張截圖。**
   **它的散布面比它的儲存位置大得多，而且不可回收。**
3. 🔴 **輪換成本**：祕密一旦寫進排程定義，**輪換它要改排程**
   ⇒ 「該換了」與「換了會不會弄壞排程」被綁在一起 ⇒ **實務上就是不換。**

## 4. 下一步（**我唯讀，只交要跑的東西**）

### 4.1 先確認是哪兩筆 —— **只要名字，不要內容**

```sql
-- 🔴 只回 jobname / schedule，【不回 command】。
--    要判斷「該不該處理」不需要看到祕密本身。
SELECT jobid, jobname, schedule,
       (command ~* 'bearer|secret|token|key|password') AS 疑似含祕密
  FROM cron.job
 ORDER BY 疑似含祕密 DESC, jobid;
```

⚠️ **若某筆的 `jobname` 是 NULL 或無意義，也不要改抓 `command`** ——
改用 `left(command, 40)` 這種**截斷**也不安全（祕密可能就在前 40 字）。
**正解是：由能讀的人（Sean）自己看，然後只告訴我們「那是什麼用途的排程」。**

### 4.2 處理方向（三個，代價不同）

| 方向 | 做法 | 代價 |
|---|---|---|
| **甲：搬進 Vault** | Supabase 有 `vault` schema（**我今晚量過：`anon` 對它零 USAGE**）；排程改成從 vault 取 | 要改排程定義、要驗排程仍會跑；**但這是唯一真的解決「儲存位置」的** |
| **乙：改用 DB 設定** | `ALTER DATABASE … SET`，排程讀設定值 | 比甲簡單；⚠️ **但 `pg_db_role_setting` 對很多角色可讀** —— **要先量誰讀得到，不要換一個位置繼續躺著** |
| **丙：只輪換、不搬家** | 換掉那兩把祕密 | **最快，但沒有解決問題** ——下一把仍然寫在同一個地方 |

🔴 **我不選。** 但要點名一件：**乙有一個「看起來安全其實只是換個地方躺」的風險**，
而那正是今晚反覆出現的形狀 ⇒ **選乙的話，第一動是量 `pg_db_role_setting` 的可讀面。**

### 4.3 動任何一個之前

**動排程定義 = 動平台設定 + 可能影響金流／同步排程** ⇒ **鐵則 12 ④，要 plan + Sean 拍板。**
