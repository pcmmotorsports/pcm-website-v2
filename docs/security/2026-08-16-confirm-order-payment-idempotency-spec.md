# 規格：釘住 `confirm_order_payment` 的冪等樹與守門順序

- **來源**：E 窗 Phase 2 §6.10（`docs/security/2026-08-16-security-audit-run1-phase2-hunt.md`）
- **狀態**：**規格，不是實作。** E 窗唯讀 ⇒ migration／測試由別的窗寫。
- **日期**：2026-08-16

---

## 1. 為什麼要現在寫（**風險不是「它壞了」，是「有人會刪掉它」**）

`settleCharge` 有**四個入口**，三個先 `claimPollSettle` 節流，**webhook 的 `after()` 那個沒有**
（`api/checkout/tappay-notify/[secret]/route.ts:191`）。那是**刻意的**（該檔 `:14`：best-effort 快路徑）。

⇒ **webhook 這條路可以與 sweeper 同時對同一張單跑 `settleCharge`。**
⇒ **它的安全不是由它自己保證的，是由 `confirm_order_payment` 的冪等樹保證的。**

**而那是一條跨檔依賴，目前【零測試在斷言它】。**

🔴 **這條特別毒的三個理由：**

1. **冪等樹長得像可以刪的東西** —— 它的形狀是「提早 `RETURN`」，
   而「這段是不是多餘的」正是重構時最容易被問的一句。
2. **刪掉之後，三條有節流的入口【不會壞】** —— 只有 webhook 那條會，
   **而它需要真實的併發才重現** ⇒ 一般測試環境照樣綠。
3. **它壞的方式是【重複入帳】** —— 直接是錢。

⇒ **不能等「哪天做了併發實測再說」。** 規格現在就要落地，因為
**要防的事件（有人刪掉它）可能明天就發生。**

---

## 2. 要釘住的**兩件**（第二件比第一件更容易被忽略）

### 2.1 冪等：同一筆重放必須是 **no-op**

`confirm_order_payment` 現行行為（`20260810170000` 版，PF-D(3)）：

> `paid` 且 `rec_trade_id` + `amount` **雙等** ⇒ **no-op 冪等成功（真 `RETURN`、不 `UPDATE`、不刷時間戳）**

**要斷言的三件，缺一不可：**

| # | 斷言 | 為什麼不能省 |
|---|---|---|
| a | 第二次呼叫**回傳成功**且 `idempotent = true` | 回失敗會讓上游把已成交的單當失敗處理 |
| b | 第二次呼叫**沒有再 `UPDATE`** | 這才是「不重複入帳」的實質 |
| c | 🔴 **`updated_at` 沒有被刷** | **這是最容易被實作者省掉的一格**，而它是「真的沒寫」與「寫了一樣的值」唯一分得出來的證據 |

### 2.2 🔴 **順序**：取消守門必須排在冪等樹**之前**

原始碼註解逐字（同檔）：

> 「冪等樹的提前 `RETURN` 也是『成功』，**讓它先跑等於沒擋**。」

⇒ **「已取消且已 `paid` 的同 rec 同額重放」必須被拒，而不是回冪等成功。**

🔴 **這一格為什麼必須單獨存在**：
**把兩者順序對調，行為會變，而「冪等」與「取消守門」各自的測試【照樣全綠】** ——
因為各自單獨都還在，壞掉的是**它們之間的相對位置**。

⇒ **順序本身要有一格守，不能只斷言「兩者都存在」。**

### 2.2-a ✅ 上面那句**已經實測過了**（拋棄式 PG 17.10，2026-08-16）

> 原本這是我的**推論**。做成最小 harness 跑了一次 —— **推論成立，而且比我寫的更乾淨。**

兩個版本**只有那兩個區塊的位置不同**，其餘逐字相同：

```
版本 A（正確）：取消守門 → 冪等樹
版本 B（對調）：冪等樹   → 取消守門
```

**兩個「一般人會寫的功能測試」：**

```
①「未取消的單，同 rec 同額重放要回冪等成功」
     版本 A → {"confirmed":true,"idempotent":true}
     版本 B → {"confirmed":true,"idempotent":true}     ← 一模一樣

②「已取消的單不得確認」（單子還沒 paid）
     版本 A → ERROR: CANCELLED_GUARD
     版本 B → ERROR: CANCELLED_GUARD                   ← 一模一樣
```

**🔴 而真正的情境 —— 已取消【且】已 paid 的同 rec 同額重放：**

```
     版本 A → ERROR: CANCELLED_GUARD                   ← 正確：擋下
     版本 B → {"confirmed":true,"idempotent":true}     ← 🔴 錯誤：回報成功
```

⇒ **兩格功能測試在壞掉的版本上【全綠】。**
**要看到差別，測資必須【同時】滿足「已取消」與「已 paid 且同 rec 同額」** ——
而那**正好是兩個功能測試各自都不會用到的組合**（①的單沒取消、②的單沒 paid）。

> 🔴 **這就是為什麼「兩者都存在」的斷言擋不住這個 bug：**
> **它們確實都存在，順序才是壞的那一半。**

⚠️ **這證的是【機制】不是【他們那支函式】**：我用的是同構的最小模型，
**沒有搬 `confirm_order_payment` 的真實 schema 來跑** ⇒ 撐得住「順序對調會製造這個行為差」，
**撐不住「他們那支的每一條路徑都如此」**。§3 的 N3 仍然要在真函式上跑。

## 3. 負向對照（**交付前必跑；沒有這節，上面每一條都可能是恆真的**）

在**拋棄式 PG**上跑（**絕不在正式庫**）。每格都要看到**紅**，而且**紅的是預期那一條訊息**。

| 格 | 突變 | 期望 |
|---|---|---|
| N1 | **拿掉冪等樹**（讓第二次呼叫走進 `UPDATE`） | §2.1-b／c **必須紅**（觀察到第二次真的寫了） |
| N2 | 冪等樹**保留但刷 `updated_at`** | §2.1-c **必須紅**、而 a／b **可能仍綠** ⇒ 證明 c 有獨立判別力 |
| N3 | 🔴 **把取消守門移到冪等樹【之後】** | §2.2 **必須紅**；⚠️ **同時確認 §2.1 那幾格仍綠** —— 若它們也紅，代表 §2.2 沒有獨立判別力，要重寫 |
| N4 | 把 `rec_trade_id` 比對改成恆真 | 「不同 rec 重放」那格必須紅 |

🔴 **N2 與 N3 是這份規格的核心**：
沒有 N2，`updated_at` 那格可能只是跟著 a／b 一起紅（沒有獨立價值）。
沒有 N3，**順序**根本沒有被測到 —— 而順序正是註解裡點名的那個坑。

⚠️ **每格跑完 `ROLLBACK`，並驗零留痕**（再跑一次全套應全綠）。

## 4. 落在哪一層 —— **DB 層，理由三條**

| 選項 | 判斷 |
|---|---|
| 應用層測試（vitest，mock RPC） | ❌ **mock 掉 RPC ⇒ 斷言的是 mock 的行為，不是那棵樹**。跨信任邊界的 mock 正是本 repo 已知的假綠來源 |
| E2E | ❌ 要真 TapPay stub + 真併發，**成本高到不會被維護**，而且失敗時難歸因 |
| ✅ **DB 層：migration 尾段斷言 + 拋棄式 PG 的突變測試** | 與這條線既有慣例一致（金流片普遍在 migration 尾段自斷言）；**而且它守在被改的那一層** |

🔴 **決定性理由**：**要防的動作是「有人改那支 SQL 函式」。**
守門必須跟被守的東西在同一層，否則**改的人不會執行到它**。
📎 同族判準：`payment_confirmer` 那份規格也是這個理由（那句 `GRANT` 可以不經過 repo）。

**具體形狀建議**：新一支 migration，尾段 `DO $$ … $$`：
1. 用 `pg_get_functiondef` 取出 `confirm_order_payment` 的定義；
2. 斷言**取消守門的字面出現在冪等樹的字面【之前】**（字串位置比較，`strpos`）；
3. 任一不成立 ⇒ `RAISE EXCEPTION`，訊息**逐字說明對調之後會怎麼壞**。

⚠️ **這是「指紋式」斷言，有已知代價**：函式被合法重寫時它會誤紅。
**本 repo 已有同款做法**（`20260810220000` 用 `prosrc` 指紋釘住四支函式的 pre／post image）
⇒ **不是新機制，照既有慣例做即可**；誤紅時的正解是**回來確認順序仍對、再更新指紋**，不是拿掉斷言。

## 6. 附帶一件（**同族、同一支 fallback 的另一道護欄**）

### 6.1 背景

`begin_charge_attempt` 的回傳 jsonb **含 `fallback_token`**
（2026-08-16 逐支審回傳面時發現，見 phase2 §5.1-b）。

那**不是 PII，是一把能力憑證** —— 它正是 `mark_charge_attempt_charged_fallback` 三道護欄之一。

**今天不構成升級**，理由是**另一道護欄**：那支 fallback **同時要求 `auth.uid() = customer_user_id`**，
而 `payment_confirmer` 是 **DB 登入角色、沒有 JWT 身分** ⇒ 拿到 token 也用不了。

### 6.2 🔴 問題不在今天，在「另一道護欄被別人以別的理由改掉」的那一天

**「今天用不了」這個結論，整個掛在 `auth.uid()` 那道上。**
而**改那道的人，不會知道它同時在守「`fallback_token` 外流」這件事** ——
他打開的是 `mark_charge_attempt_charged_fallback`，**不是** `begin_charge_attempt`。

> 📎 判別句：**會來改這件事的人，他會打開哪一個檔？**
> ⇒ **警告要放在【他會打開的那一個】，不是放在【發現問題的那一個】。**

### 6.3 建議：兩邊都留一句（**我唯讀，只交文字**）

**(a) 放在 `begin_charge_attempt` 的 `COMMENT ON FUNCTION`：**

> 🔴 本函式回傳 `fallback_token`（能力憑證，非 PII）。
> 它之所以外流也不構成升級，**依賴的是 `mark_charge_attempt_charged_fallback`
> 那道 `auth.uid() = customer_user_id` 的歸屬閘** ——
> **動那道之前先回來看這裡。**

**(b) 🔴 更重要的一句，放在 `mark_charge_attempt_charged_fallback` 的 `COMMENT ON FUNCTION`：**

> 🔴 本函式的 `auth.uid() = customer_user_id` 那道**不只擋「別人的單」**，
> 它同時是「**`begin_charge_attempt` 回傳的 `fallback_token` 外流之後仍然用不了**」的唯一理由。
> **放寬或移除它之前，先確認 `fallback_token` 的散布面。**

⚠️ **(b) 比 (a) 重要**：(a) 是給「讀 `begin_charge_attempt` 的人」，
而**風險是「改 `mark_..._fallback` 的人」造成的** —— **只寫 (a) 等於警告寫在沒有人會打開的地方**
（本 repo 今晚已經有一個同形狀的實例：`pcm_order_refundable_remaining` 的 allowlist 警告寫在
它自己的 `COMMENT` 裡，而新增 status 的人不會去讀那支函式）。

⚠️ **我沒有實作這兩句**（唯讀）。**也沒有實測 `fallback_token` 目前散布到哪些地方**
（誰拿得到、有沒有進 log／回應）⇒ **(b) 裡「先確認散布面」那句是要求，不是我已經查過的結論。**
