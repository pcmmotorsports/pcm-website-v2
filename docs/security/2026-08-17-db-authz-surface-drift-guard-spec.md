# DB 授權面漂移守門規格 —— 「RLS 開著、零 policy」那 71 張表的保護是**靠沒人動它**(**規格,E 唯讀不實作**)

- **窗**:E(資安稽核,唯讀)　**日期**:2026-08-17　**兩庫皆適用**(網站庫 `pcm-website-v2` / 報價單庫 `pcm-quote-v2`)
- **起因**:第三輪量到報價單庫 **78 張表全部 `relrowsecurity=t`,而有 policy 的只有 7 張** ⇒ **71 張是「RLS 開著、零 policy」= 預設 deny-all**。**那是安全的那一邊** —— 但**它的安全性來源是「沒有人幫它加 policy」,而不是任何一道會叫的東西。**

---

## 0. 🔴 這份規格要守的那句話

> **今天誰在那 71 張表上加一條 `USING true`,整張表就對 `anon` 打開,而【不會有任何東西紅】。**
> `grep` 掃不到(policy 在 DB 不在 repo)、三綠不紅、覆蓋率算不到。

⚠️ **這不是「現在有洞」** —— 現況乾淨(見 §2 基準)。**這是「這個面沒有量測」。**

---

## 1. 🔴 要偵測的是【新增的寬鬆 policy】,不是「policy 總數」

**為什麼不能守總數**:policy 數量**會因為正常開發而變**(每加一個新功能表就可能 +1)⇒ 守總數的東西**會一直叫**,而**一直叫的守門會被關掉**。那比沒有守門更糟。

⇒ **守的是「授權面有沒有變寬」**,判準三條(任一觸發即報):
```
① 出現【新的】 permissive policy，其 roles 含 anon 或 authenticated，且 qual = 'true'
   （＝無條件全表讀，不是「有條件」）
② 既有 policy 的 qual 從「有條件」變成 'true'      ← 比新增更隱蔽
③ 任何表的 relrowsecurity 從 t 變成 f              ← 直接關掉 RLS
```
**實作形狀**:把「上次的授權面」存成一份 checked-in 的基準檔(排序後的正規化文字),每次比對 **diff**,而不是比對**數字**。
⇒ **新增一條有真條件的 policy ⇒ diff 有一行,但不觸發 ①②③ ⇒ 不報。** 這樣它才不會一直叫。

## 3. 🔴 四條要件逐條套用(尤其第 0 條)

### 第 0 條:正向 + 反向對照(**同一次執行內**)

| 格 | 餵什麼 | 期望 |
|---|---|---|
| **正向(已知該被抓到)** | 在**交易內**建一條 `CREATE POLICY … TO anon USING (true)` 於一張暫時表 | **必須報** |
| **反向(已知不該被抓到)** | 在**交易內**建一條 `… TO anon USING (some_real_column)` | **必須不報** |
| **基準格** | 不動任何東西 | **必須零報**(否則 allowlist 沒設對) |

🔴 **兩個構造格一律 `BEGIN … ROLLBACK`**(PCM 既有紀律:交易模擬 + 零留痕驗證)。**跑完要驗 `pg_policies` 數回到基準值。**
🔴 **沒有這三格,守門的「零報」與「它根本沒在掃」是同一個輸出。**

### 斷言層 / 輸出層 / 命名(四條要件的其餘三條)

- **斷言層**:比對**正規化後的文字 diff**,不是計數。🔴 **`qual` 為 `NULL` 的 policy(例如只有 `WITH CHECK` 的)不可被 `qual <> 'true'` 這種寫法靜默略過** —— `NULL <> 'true'` 得 `NULL`,那一列會**從兩邊的桶裡都掉出去**(本 repo 當天踩過同型:`NULL NOT LIKE`)⇒ **明確處理 NULL**。
- **輸出層**:`rc` 三態分得開 —— `0` 無漂移 / `3` 偵測到放寬(真發現)/ `2` 用法錯 / `1` **探針自壞**(連不上 DB、基準檔缺、權限不足)。🔴 **「連不上 DB」絕不可回 0。**
- **命名**:🔴 **不要叫 `check-rls-policies.sh`** —— 它守的**不只 policy**,還有 `relrowsecurity` 與(見 §4)`relforcerowsecurity`。**建議 `scripts/audit-db-authz-surface.sh`**。

## 4. 🔴 明寫它【偵測不到】什麼(這一節不可省)

1. **`relforcerowsecurity = 0` ⇒ 表 owner 繞過 RLS**,而**那不是 policy 能管的**。加再多 policy 都擋不住 owner。⇒ 本守門**只能回報這個旗標的值**,**不能宣稱「RLS 有效」**。(網站庫同族已知案例:`E685-1`,`security_invoker=false` 的 view 由 owner 繞過。)
2. **欄級授權(`has_column_privilege`)不在本守門範圍** —— 而**表級乾淨不等於欄級乾淨**(當天實錘:報價單 `products` 表級無 `anon`、欄級 31/57)。⇒ 要守欄級是另一支。
3. **`BYPASSRLS` 角色**不受 RLS 管,本守門不查角色屬性。
4. **它偵測的是「狀態變了」不是「阻止狀態被改」** ⇒ **偵測頻率就是暴露窗**,這句要寫進腳本檔頭。

## 5. 與 `E686-1` 那支探針**分開兩支檔**(a4 要我判,理由如下)

| | `E686-1` 探針 | 本規格 |
|---|---|---|
| 觀測點 | **外部 HTTP**(`/rest/v1/`) | **DB catalog**(`pg_policies` / `pg_class`) |
| 憑證 | publishable **anon key** | **稽核 DB 角色**(`pcm_audit_ro`) |
| 問的問題 | 「外面打得到嗎」 | 「裡面的授權面變寬了嗎」 |

⇒ **合成一支會讓檔名必然比範圍窄**(它會同時是 HTTP 探針又是 DB 稽核),而且**兩者的 `rc=1`(探針自壞)成因完全不同**(網路 / DB 連線)⇒ **合併會讓「工具自壞」這一態失去診斷力。**
✅ **建議:兩支檔,但共用同一份「四條要件」的檔頭註解**,並互相 `@see`。
