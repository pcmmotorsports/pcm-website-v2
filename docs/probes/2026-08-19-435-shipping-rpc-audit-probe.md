## 2. 「零稽核」的後果具體是什麼(第 2 格,用我熟的那條線的語言)

### 出貨這個動作改了什麼狀態
```
建箱 / 加品項 ⇒ 決定「這一單的哪些品項,裝進哪一箱」
標記出貨     ⇒ 那一箱變成【已出貨】,而 shipments 有 CHECK:
               shipments_shipped_needs_tracking(20260805170000:161-164)
               ⇒ 已出貨必須有 tracking_number,**除了 `other`(自取/自送)那一族**
作廢 / 復原  ⇒ 把一箱推出 / 拉回那個狀態
```

### 🔴 出錯的時候,誰、什麼時候、怎麼發現 —— **這正是我做過的那條線的問題形狀**
```
客人打電話說「我收到的東西少一件」
⇒ 查 shipments:看得到「這箱裝了 A、B」
⇒ 而**看不到**:是誰把 C 從這箱拿掉的?什麼時候?還是 C 從來沒被加進來?
⇒ 🔴 **作廢/復原最毒**:一箱被作廢又復原,狀態最後長得跟沒發生過一樣,
  **而中間那段時間發生過什麼,一個字都沒有。**
```
📌 與 `#423` 的病灶**逐字同族**(那份檔頭):
> 「今天唯一追得到『誰』的欄位是 `order_payments.actor`,而它來自 picker cookie,
>  `actor.ts:6-7` **逐字自陳「這不是登入 / 授權邊界」** ⇒ 它記的是【畫面上被選的人】。」
⇒ **出貨線連那個都沒有。**

## 3. 有沒有做對的前例(第 3 格)⇒ ✅ **有,而且判準已經拍板**

### 3-1 前例
```
git grep -ln "INSERT INTO ... admin_audit_log" -- 'supabase/migrations/*' ⇒ **21 檔**
其中 20260812150000_m4b_e10_423_payment_audit.sql = **#423**,
即「同一次掃描抓到的 7 支裡的另外兩支」⇒ **同一個病、隔壁的線、已經修好**
```

### 3-2 🔴🔴 而它的**判準**已經拍板,而套用之後五支**不是齊頭一樣**
`#423` 檔頭逐字(主視窗 `D-569-A:1` 裁,**明文寫「未來第三條線照它裁」**):
> 「**『帳本列即稽核』只在列上帶外部不可否認材料時成立**
>  (TapPay 回應、外部退款編號這類**非我方單方面產生**的證據)。
>  **沒有外部佐證 = 純內部宣稱 ⇒ 必須補 `admin_audit_log`。**」

**套到出貨線**:
```
admin_create_shipment      純內部宣稱(誰決定裝哪些)         ⇒ 🔴 必須補
admin_add_shipment_items   純內部宣稱                         ⇒ 🔴 必須補
admin_void_shipment        純內部宣稱                         ⇒ 🔴 必須補
admin_unvoid_shipment      純內部宣稱                         ⇒ 🔴 必須補
admin_mark_shipment_shipped ⚠️ **要分兩族**:
   · 有 tracking_number(新竹物流給的)⇒ **那是外部不可否認材料** ⇒ 判準上「帳本列即稽核」成立
   · 而 `other`(自取/自送)那一族 **沒有 tracking_number**(20260805170000:195 逐字)
     ⇒ **純內部宣稱** ⇒ 那一族仍要補
```
🔴 **所以那條判準在這裡是【逐列】不是【逐支 RPC】** ——
```
而 RPC 只能整支決定寫不寫稽核 ⇒ 兩種收法:
  甲 第五支【一律寫】(最簡單,而對有單號那族是多寫一筆)
  乙 第五支【只在沒有 tracking_number 時寫】(貼判準,而多一個分支要測兩族)
⇒ **這是本片唯一的設計判斷**,其餘四支照抄 #423 即可。
```
📌 **而我傾向甲**:多寫一筆稽核的成本 ≈ 0,而乙多一個分支就多一個會寫錯的地方;
判準說的是「**至少要有**」不是「**不准多**」。⚠️ **而這是我的判斷,不是拍板。**

## 4. 🔴 要不要動 migration ⇒ **要,而它會卡住**(第 4 格 —— 你要求早點知道)

```
那五支是 SECURITY DEFINER 函式 ⇒ 補稽核 = **改函式本體** = 一支新 migration
⇒ 🔴 **要 Sean apply**,而 apply 一律是他的動作
⇒ 而本 repo 現在【已經有一支等他 apply 的東西】(M-4a 佇列出口那支,不得 apply 清單上)
⇒ **這一片交出來之後也會排在同一個佇列裡等他。**
```
**⇒ 早點知道的用途**:如果目標是「走查窗那一站按得動」,**補稽核【幫不上那一站】** ——
稽核是**事後查得到**,不是**現在按得下去**。
🔴 **那兩件要分開講**:
```
走查窗按不動        ⇒ 那是【功能/權限/UI】問題,本片不解
零稽核              ⇒ 那是【出事後查不到】問題,本片解
⇒ 主視窗說「零稽核可能就是它按不動的原因之一」—— **我認為不是**:
  稽核是 INSERT 一筆 log,它不會擋住任何動作。
  ⚠️ 除非那五支現在**根本沒被接上 UI** —— 而**那我沒查**,標未確認。
```
