# ⓪ 先把機制講準(前兩版我自己講過寬,這是收斂後的)

```
含多位元組字元的【字元類別】，在 BSD grep（/usr/bin/grep）與 git grep 上
是【位元組】類別 ⇒ 它的行為不是「壞掉」，是【換了一個意思】：
  · 混合型 [-–]      ⇒ **安靜退化成只剩 ASCII 成員**（= [-]，輸出逐字節相同）⇒ **少報**
  · 範圍型 [①-⑳]    ⇒ **退化成一組位元組**（含 E2 / E3 開頭的一大片 CJK）⇒ **多報**
  · 全多位元組 [–]   ⇒ 回 0 ⇒ **最容易被發現的那種**
而 ugrep（Bash 工具裡手打的 `grep`）與 JS RegExp 是【字元】語意 ⇒ 沒有這個問題。
🔴 ⇒ **手打驗證會過、`#!/bin/bash` 腳本裡跑同一條會不一樣，而兩邊都不報錯。** 判別 `type grep`。
```
📌 **方向不是固定的** —— 這一點很重要,下面第 ① 條就是**多報**。

# 🔴 ① `docs/patterns/guard-and-instrument-traps.md` 的數法 —— **多報 11**
**⚠️ 這支檔的擁有者是 G2。本窗只量、不改。**

檔內 `:12` 寫著(它自己說「自己重跑,不要照抄」):

## 受控實驗(同一份檔、同一刻、只換引擎)
```
/usr/bin/grep -cE  ⇒ **59**
ugrep       -cE    ⇒ **48**
python3 re（字元語意，正解） ⇒ **48**
```

## 多出來那 11 行是什麼(差集,逐行開檔看過)
```
comm -23 <(/usr/bin/grep -nE '^## [①-⑳㉑-㉟㊱-㊿]' <檔> | cut -d: -f1 | sort) \
         <(         grep -nE '^## [①-⑳㉑-㉟㊱-㊿]' <檔> | cut -d: -f1 | sort)
⇒ 11 行。逐行取 `^## ` 之後第一個字元的碼位：
     「 U+300C × 9      【 U+3010 × 1      ✅ U+2705 × 1
⇒ **一個編號都沒有。** 它們是以標點或表情符號開頭的標題。
```
成因:`①`=`E2 91 A0`、`㉑`=`E3 89 91` ⇒ 類別退化成**含 `E2` 與 `E3` 的位元組集合**
⇒ **任何第一個位元組是 `E2` / `E3` 的字元都中** ⇒ 那涵蓋一大片 CJK 標點與符號。

## 🔴 而更該報的是這一句:**檔內對「失敗方向」的描述是反的**
`:14-17` 逐字寫著這條數法過期過兩次,然後下結論:
> 「⇒ **範圍型 pattern 是會過期的字面,不是永久工具** —— 而**它每次過期的方向都是「看起來比較少」**。」

**「每次都是比較少」是全稱句,而它在 BSD grep 上不成立** ——
上面量到的是 **59 > 48**,方向是**比較多**。

📌 🔴 **為什麼這一句比那個數字重要**:
```
「它只會少報」⇒ 讀的人會把它當成【保守估計】⇒ **看到數字偏大時不會起疑**
而實際上它在真 grep 上偏大 11 ⇒ **那個「保守」的心理保護是假的**
```
⇒ 建議(**不是我拍**,那支檔歸 G2):數法改成不用範圍類別,例如
`grep -cE '^## [^ -~]'`(而它會多算所有非 ASCII 開頭的標題 ⇒ 也不對)——
**最穩的是交替列舉,或乾脆改用 `python3 -c` 數。**

# ✅ ③ `scripts/who-is-touching.sh:44` `'^### #${N}[ ]?[.·]'` —— **今天沒事**
```
/usr/bin/grep -cE "^### #655[ ]?[.·]" docs/phase-1-backlog.md ⇒ **1**（抓到）
```
🔴 而它沒事的理由**又不一樣**:那個類別在 **pattern 的最尾端** ——
BSD 只要消耗**一個位元組**(`·` 的第一個位元組)就走到 pattern 結尾 ⇒ 成功。
⇒ **哪天有人在它後面接東西(例如 `[.·]\s`),它就會當場壞掉。**

📌 ②③ 合起來是本份最該記的一句:
> **「今天沒事」有三種完全不同的理由,而它們都不是「這條 pattern 是對的」。**
