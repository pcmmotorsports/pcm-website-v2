# 🔴 二、根因不是「一道過濾器」,是**兩個不同的定義**

| | 客戶**列表**的「訂單數」 | 客戶**明細**的「訂單歷史」 |
|---|---|---|
| 來源 | RPC `admin_search_customers` 的 `active_order_count` | `listSummariesByCustomer` |
| 條件 | `WHERE customer_user_id = … AND **cancelled_at IS NULL**` | `.eq(customer_user_id).**neq('payment_status','unpaid')**` |
| 出處 | `supabase/migrations/20260816030000_m4b_admin_customer_list_view.sql:83-86` | `packages/adapters/src/supabase/SupabaseOrderAdapter.ts:582` |
| **含不含未付款** | **含** | **不含** |
| **含不含已取消** | **不含** | **含** |

## 🔴 所以它會**往兩個方向**打架
```
情況甲(我今晚實際撞到的):客人有【未付款】的單
  列表 2 筆 / 明細 0 筆  ⇒ **列表比較多**
  實據:G3 沙盒測試 —— 列表逐字「… | 一般會員 | 2 | 3,000 | 2026-08-19 | 2026-08-18」
                        明細逐字「目前沒有訂單紀錄。」

情況乙(從 code 推,我沒有拿別人的資料去驗):客人有【已取消】的單
  列表不算它 / 明細算它 ⇒ **明細比較多**
  ⚠️ 這一格我**沒有實測** —— 要驗得看別人的客戶明細,而那不是我該看的
```
📌 **兩個方向都會發生 ⇒ 這不是「一邊漏了」,是【兩邊各自對,而它們對的不是同一件事】。**

## 而 migration 的作者**知道這件事**,並且做了對的一半
`20260816030000...:28-32` 檔頭逐字:
```
🔴 欄名自己講口徑,不靠 COMMENT(codex 關卡1:「訂單數」實際是「未取消訂單數」,名字會誤導)

   **UI 標籤仍是 Sean 指定的「訂單數 / 消費金額 / 最後下單」** —— 那一層的誠實
   (標籤旁要不要加「不含已取消」)是接線片的事,不是本片。
```
⇒ 🔴 **他把口徑寫進【欄名】,而 UI 標籤照 Sean 指定的寫成「訂單數」** ——
   **那個「接線片的事」到今天沒有人做。**
⇒ 而**另一邊(明細)連一個帶口徑的名字都沒有** ⇒ 兩邊唯一的共同點是**畫面上都叫「訂單」**。

# 🔴 三、而主視窗問的「**只有一個數字而它是錯的**」—— 那就是**客人自己那一頁**

```
apps/storefront/src/app/account/page.tsx:157   stats={{ …, orderCount: orders.length }}
而 orders 就是 listSummariesByCustomer 的結果(同檔 :128)
⇒ **「TOTAL ORDERS」那個數字與下面那張訂單清單【是同一個陣列】**
```
**而 code 自己把這件事當成優點寫下來**(`account/page.tsx:125` 逐字):
```
orderCount 與 Overview 最近訂單同源此 orders、**天然一致**(Q5=A)
```
🔴 **那句話是對的,而它正好是問題**:
```
兩個數字同源 ⇒ 它們永遠一致 ⇒ **永遠不會打架** ⇒ **沒有任何東西可以拆穿那道過濾器**
⇒ 客人看到「TOTAL ORDERS 0」與「目前尚無訂單紀錄」,兩個互相印證,而**兩個都是錯的**
```
📌 **為了保證一致而做的同源設計,把唯一的證人也一起拿掉了。**
⇒ 這比後台那個矛盾**更難發現** —— 後台至少有兩個數字會吵起來;客人那邊**安靜**。

# 四、三題的答案收在一起

```
① 那道過濾器還服務哪些畫面?  ⇒ 恰好兩個:客人的會員中心、後台客戶明細。**沒有第三個。**
② 哪個畫面上有兩個數字會打架?⇒ 後台的【列表 ↔ 明細】(不是同一頁,是一次點擊之隔)
                                而它**兩個方向都會打架**(未付款 / 已取消 各一個方向)
③ 哪個畫面只有一個數字而它是錯的?
   ⇒ 🔴 **客人自己的會員中心** —— 而且是【刻意同源】造成的,不是疏漏
```

## 便宜的修法方向(建議,要 Sean 拍)
```
甲 最便宜:把兩邊的口徑寫到【標籤旁邊】——
   列表「訂單數(不含已取消)」/ 明細「訂單歷史(不含未付款)」
   ⇒ 零查詢改動,而它讓兩個數字【不再看起來是同一件事】

   ⇒ 🔴 而那要先決定「未付款的孤兒單算不算他的訂單」—— 那是 #249/#278/#659 那一族的本題,

⚠️ 而【客人那一頁】無論選甲或乙都仍然安靜 —— 它需要的是**別的東西**
   (例:那道過濾器濾掉幾筆就顯示一句),而那正是 `#659` 在講的
```
