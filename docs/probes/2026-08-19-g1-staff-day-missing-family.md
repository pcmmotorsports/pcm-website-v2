# 「員工的一天」12 站漏了哪一族 —— 2026-08-19 G1

> 主視窗:Sean 的上線判準逐字是「員工的一天」,而**那份清單本身沒有人驗過它完不完整**。
> **本份不重做那 12 站**(`docs/runbooks/sean-admin-staff-day-checklist.md` 已經有了),補它漏掉的那一族。
> **純讀。沒有按任何寫入。**

## ① 現有 12 站的**分類軸**是什麼
```
第 0 站 登入
第 1–9 站  收款 → 採購 → 到貨 → 尾款 → 出貨 → 退款 → 備註 → 編輯訂單 → 取消
第 10 站 首頁金額 / 第 11 站 篩選鈕
```
🔴 **軸 = 一張【訂單】的生命週期** —— 每一站都是「員工**對一張單**做的下一個動作」。
⇒ 而那條軸**天生看不到**一整族:**不是員工主動做的,是【客人找上門】而被動觸發的。**
📌 **這不是那份清單寫得不好** —— 它照 Sean 的原題(員工的一天)組織得很準。
**是那個題目本身有兩半,而只有一半被寫下來。**

## ③ 分類(主視窗要的「做不到」再分)
```
功能不存在          A（改地址）/ D（退貨換貨）/ E（鑑賞期話術，連文件都沒有）
有資料而沒有入口    B（email_outbox 有表、後台 0 檔）/ F（double_charge 有表、後台 0 檔）
要 Sean 才走得下去  G（三格待拍板）/ C 的乙案（蓋停權功能）
✅ 已被現有 12 站涵蓋 H、I
```
🔴 **注意 B 與 F 的形狀相同:資料在 DB 裡、而員工看不到。**
⇒ **那不是「還沒做功能」,是「做了一半 —— 寫進去了而沒有讀出來」。**

## ④ 回答主視窗的那個岔路:**是結構問題,不是漏列**
```
若只是漏列 ⇒ 補幾站進去就好
而 A–G 七站【沒有一站】能塞進「一張訂單的生命週期」那條軸:
  它們的觸發點不是【訂單狀態變了】，是【電話響了】
⇒ 🔴 **那是第二條軸,不是第 13 站。**
```
⇒ **建議**:那份 runbook 加**第二部分「客人找上門的一天」**,而不是把 A–G 併進 0–11。
📌 理由:**兩條軸的驗收方式不同** —— 訂單那條可以「照著點」,而客人那條要問「**電話來了你怎麼辦**」。

## ⑤ 🔴 而有一格我建議先問 Sean,不要先蓋
**A / D / E 三站,他們一定已經遇過。** ⇒ **先問「你們現在實際上都怎麼處理?」**
`#302`(免運)那條的教訓:**我們以為沒做的事,店裡可能早就有一套紙上流程。**
⇒ **問到之後再決定要不要做成功能** —— 否則會做出一個跟他們現行做法打架的東西。
