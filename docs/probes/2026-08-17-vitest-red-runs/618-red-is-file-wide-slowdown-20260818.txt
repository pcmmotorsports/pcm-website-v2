# #618 那題答了:紅的當下是【整個檔變慢】,不是【單格卡住】

答的人:G1,2026-08-18 19:4x CST。
🔴 **零機器成本** —— 沒有再跑任何一發。資料是今天已經存下來的兩份 RED 樣本 + 三發綠的 json。
   我原本以為要再等一個隨機紅才答得了,**而檔級總時一直印在紅的 log 裡。**

## 資料(兩個檔各自:綠三發 vs 紅一發)
```
ForgotPasswordPage.test.tsx（15 格）
  綠  2091 / 2014 / 3301 ms      （run1/2/3，sha 1e59e8c4）
  紅 11232 ms                    （17:38 那發，7 格失敗；樣本 1660cabf-...-83518-RED.txt）
  ⇒ 檔級 3.4–5.6x

MobileCatalogUxPreview.test.tsx（9 格）
  綠  1247 / 1573 / 2173 ms
  紅 19637 ms                    （18:43 那發，1 格失敗；樣本 1660cabf-...-2nd-RED.txt）
  ⇒ 檔級 9.0–15.7x
```

## 🔴 結論:是【檔級(至少)的全面變慢】,不是單格卡住
MobileCatalogUx 那發最乾淨(只有 1 格失敗):
```
檔級總時 19637 ms  −  逾時那格 5060 ms  =  其餘 8 格約 14.6 秒
而綠的時候：整檔 9 格只要 1.2–2.2 秒
⇒ 沒有失敗的那 8 格也慢了大約一個數量級
```
⇒ **逾時不是「某一格卡住」,是那個 worker 上的東西整批變慢,而 5000ms 門檻先咬到最慢的那一格。**

⚠️ **這個算式的假設寫出來**:我用「檔級總時 − 失敗那格的時間」去推其餘格子,
   而**紅的 log 沒有印沒失敗那幾格的個別時間**(預設 reporter 只印失敗的)。
   ⇒ 那 14.6 秒是**推的**,不是逐格量到的。要逐格量得在紅的當下用 json reporter 跑。

## 這對修法方向的意思
```
✗ 「調高 testTimeout」            ── 那是動驗證本身（R4 立即停止訊號），而且它治的是症狀
✗ 「替那 9 格開特例」              ── 同上；而且最靠近懸崖的 #350c 守門 4（2566ms）不在紅過的名單裡
? 「找出什麼東西讓一個 worker 整批變慢」 ── 這才是本檔指向的方向
```
🔴 **我不提修法,也不建議動門檻。** 本檔只把方向從「門檻夠不夠鬆」換成
   **「什麼東西會讓一個 worker 上的所有格子同時慢一個數量級」**。
   候選(**都沒有查證,列出來是為了讓下一個人有起點,不是結論**):
   worker 重用/回收、模組重新 transform、jsdom 環境重建、GC、記憶體壓力。

## 還沒做的
```
· 紅的當下用 json reporter 跑一發 ⇒ 才有逐格資料（現在那 14.6 秒是推的）
· n=1 紅 / 檔。兩個檔各只有一發紅
· 「檔級」是不是等於「worker 級」我沒查 —— vitest 的 pool 設定與檔到 worker 的對應沒讀過
  ⇒ 本檔一律寫「檔級」，不寫「worker 級」，雖然後者才是我懷疑的東西
```
