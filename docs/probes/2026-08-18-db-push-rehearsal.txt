## ① `supabase db push` **強制 TLS**,而 `sslmode=disable` 它不理
```
--db-url postgresql://postgres@127.0.0.1:55501/postgres
  ⇒ failed to connect: tls error (server refused TLS connection)
加 ?sslmode=disable ⇒ 【一模一樣的錯】，CLI 忽略它
解：給拋棄式叢集一張自簽憑證
  openssl req -new -x509 -days 1 -nodes -subj "/CN=localhost" -keyout data/server.key -out data/server.crt
  chmod 600 data/server.key
  postgresql.conf 追加 ssl=on / ssl_cert_file='server.crt' / ssl_key_file='server.key'
  ⇒ 之後 psql "...?sslmode=require" 通、db push 通
```
📌 **這一格單獨就值回票價**:真 apply 那天若在這裡卡住,是卡在正式庫前面而不是拋棄式 DB 前面。
⚠️ 射程:這是**本機**現象。正式 Supabase 本來就有 TLS ⇒ 真 apply 不會撞這一格。
   它擋的是**彩排**,不是真 apply。**寫清楚免得下一個人以為真 apply 要準備憑證。**

## ② push **不是整批原子的** —— 一支一支來,成功一支記一支
實測(把 182 支推進空 DB,第 55 支炸):
```
帳本筆數 54          ← 前 54 支全部 applied 且【已記帳】
失敗那支 20260712183000 在帳本裡 ⇒ 0 筆   ← 失敗的不記
```
⇒ **中途失敗 = 前面的東西【已經在庫裡了】,不會因為後面炸就一起退回。**

## ③ 重跑 = 從失敗那支續跑,**已記帳的一支都不會重跑**
原封再推一次:
```
rc=1（同一支同樣失敗）
Applying migration 的次數 ⇒ 1   ← 只重試失敗那支
帳本仍然 54                      ← 前面 54 支一支都沒重跑
```
🔴 **這一格直接回答「不帶 `IF NOT EXISTS` 的那支會不會在重跑時炸」:不會** ——
   只要它成功過一次並記了帳,重跑根本不會執行到它。

## ④ 一支 migration 跑到一半失敗 ⇒ **整支回滾,不留半成品**
構造(在另一個乾淨 DB):
```sql
-- 20260101000001_half_then_fail.sql
CREATE TABLE public.probe_partial (id int);
CREATE INDEX probe_partial_idx ON public.probe_partial (id);
SELECT 1/0;              -- 在 statement 2 炸
```
量到:
```
probe_partial 存在？ ⇒ 0   ← 不存在，前半的 DDL 沒有留下
probe_first  存在？ ⇒ 1   ← 【正向對照】前一支建的表在，證明這把尺量得到「存在」
帳本            ⇒ 1   ← 只記成功那支
```
⇒ **失敗的 migration 不會留下半個表**,所以重跑不會撞到自己上一次的殘留。

## ⑤ 🔴 帳本裡有一支本機目錄沒有的版本 ⇒ **整發拒絕,一支都不推**
```
Remote migration versions not found in local migrations directory.
try repairing: supabase migration repair --status reverted <version>
```
⇒ fail-closed。**修復指令也彩排過**:`migration repair --status reverted <version>` rc=0,帳本清空。
📎 這跟 memory `reference_quote-repo-migration-ledger-desync`(報價單 repo 本地 146 檔 vs ledger 160 筆
   ⇒ 不能跑 db push)是**同一個機制** —— 那條 memory 現在有可重跑的量法了。

# 🔴 補上 B 那格(主視窗明令):不加 `--include-all` 時,舊時間戳的 migration 會怎樣?

**擔心的失敗模式**(主視窗提,場景真實 —— G5 手上那份草稿時間戳是 08-16,而正式庫已 apply 到 08-18):
> 那支較舊的**安靜地不被選中**,而輸出是 `Remote database is up to date.`
> —— 與「真的沒東西要推」**一模一樣** ⇒ 會讓人以為已經套完。

## ⇒ 實測:**那個失敗模式不存在。** 三個世界,各印不同的東西
拋棄式 PG,先 apply 一支 `20260101000000`,再放進一支**較舊**的 `20251201000000`(帳本沒有):
```
世界一  不加旗標（Sean 跑的形狀）   rc=1
        Found local migration files to be inserted before the last migration on remote database.
        Rerun the command with --include-all flag to apply these migrations:
        supabase/migrations/20251201000000_older.sql
        🔴 grep -c 'up to date' ⇒ **0**

世界二  加 --include-all            rc=0   Would push these migrations: • 20251201000000_older.sql

世界三  把那支舊的拿掉、不加旗標     rc=0   grep -c 'up to date' ⇒ **1**
```
⇒ **`up to date` 那句只在【真的沒東西要推】時出現。**
⇒ 不加旗標時它**不是安靜跳過** —— 它**失敗(rc=1)、指名那支檔、並告訴你要加哪個旗標**。

## 這一格同時更正我自己先前寫的一句
~~「不加它 ⇒ 那種在已 apply 之後才被加進來的舊時間戳 migration,**可能不會被推**」~~
字面上沒錯(它確實沒被推),**而它漏了最重要的那一半:它不會被安靜地漏掉。**
⇒ 正確講法:**不加旗標時,舊時間戳的 migration 會讓整發【失敗並具名】,不會被無聲跳過。**
🔴 我原本那句會讓人去防一個**不存在的**失敗模式 —— 而防錯的東西也是成本。
