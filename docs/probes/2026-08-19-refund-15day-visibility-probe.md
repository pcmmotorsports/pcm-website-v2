# 偵察 —「15 日內退款」那個承諾,能不能變成看得到的

> 🔴 **只偵察,不寫 plan。** 第 1 格的答案決定它是「一小片」還是「要 Sean apply」。純讀,零 code。
> 承諾原文(`/terms` 逐字):「經本公司**確認應退款**者,於**確認之次日起【15 日內】**依原付款管道退還」

---

## 0. 一句話結論:**有時間戳,而【明顯的那一個是錯的】**

```
✅ 不必新欄位 —— 現有欄位就夠
🔴 而「確認應退款」在系統裡**不是一個點,是兩個候選**,而它們可能差好幾天
⇒ 選錯的話,顯示出來的到期日**會比法定的晚** ⇒ 那比不顯示更糟
```

---

## 1. 「確認應退款」那一刻有沒有時間戳(第 1 格)

### 1-1 🔴 最像的那個欄位 **`confirmed_at`,是【終點】不是【起點】**
```
order_refunds(20260725130100_m3_rf2a2_order_refunds_ledger.sql:96-103):
  status  CHECK (status IN ('processing', 'confirmed', 'failed'))
  created_at    timestamptz NOT NULL DEFAULT now()
  confirmed_at  timestamptz
```
而 `confirmed_at` 的寫入語意(`20260803150000:391` COMMENT 逐字):
> 「④ **confirmed 必帶 `tappay_refund_id`**(P7C09,Sean Q3=A 不鬆綁)…**轉 confirmed 時 `confirmed_at=now()`**」

⇒ 🔴 **`confirmed_at` = 錢真的退回去了那一刻**(有 TapPay 的退款編號才算)。
⇒ **那是那 15 天的【結束】,不是開始。** 名字很像,而語意相反。
📌 **這一格是本偵察最重要的**:一個叫 `confirmed_at` 的欄位,在一句叫「**確認**之次日起」的承諾旁邊
—— **看起來就是它**,而拿它當起點會讓每一張單的到期日都算晚。

### 1-2 ⇒ 起點的兩個候選,**而它們是不同的事件**
```
候選 A:order_refunds.created_at
  = 退款列被建出來(status='processing')= **有人決定要退了、而且開始退**
候選 B:payment_double_charge_anomalies.resolved_at / refund_claimed_at
  (20260702… 那張表:status 預設 'open';refund_claimed_at / refund_claimed_by /
   resolved_at / resolved_by / resolution_note)
  = **判定這一筆該退**(而還沒開始退)
```
🔴 **而 B 比 A 早** —— 中間隔著「值班查證 → 決定 refund/dismissed → 真的去按退款」。
```
而承諾的字面是「經本公司【確認應退款】者,於【確認】之次日起」
⇒ **字面上更接近 B,不是 A。**
⚠️ 而【法律上哪一個才算「確認」】**不是我能判的** —— 那要 Sean 或他的法律意見。
```

### 1-3 ⚠️ 而有一族單**根本不經過 B**
```
雙扣 anomaly 是【自動偵測出來的那一族】。
而客人主動申請退款、或員工手動退 —— 那些單**沒有 anomaly 列**
⇒ 它們只有 A(order_refunds.created_at)
⇒ 🔴 **所以起點的定義必須對兩族都成立**,不能只挑 B
```

## 2. 顯示放哪(第 2 格)—— 判準用「員工什麼時候需要知道」
```
① 退款區塊(訂單詳情)⇒ **他正在處理這一張**的時候
② 訂單列表 / 退款列表 ⇒ **他在找「哪一張快到期」**的時候
🔴 而這兩個需求不同:①是「這張還剩幾天」、②是「哪幾張要先做」
⇒ **只做 ① 不解病** —— 見第 3 格
```

---

## 3. 🔴🔴 超過 15 天的看得到嗎(第 3 格)—— **這一格才是病**
```
只顯示到期日 ⇒ 過期的單**混在列表裡**,而顏色/文字都要人一張張看
⇒ 而那正是「要有人記得」的另一種形狀 —— **從「記得要退」變成「記得要看」**
⇒ 🔴 **所以至少要能【篩】或【排序】**,否則這片只是把承諾抄到畫面上
```
📌 判別句:**做完之後,一張超過 15 天的單,會不會【自己跳出來】?**
不會 ⇒ 那還是靠人記得。

## 5. ⇒ 體積:**取決於第 1 格那個決定,不取決於技術**
```
若起點 = A(order_refunds.created_at)  ⇒ **零新欄位、純顯示 + 一個排序/篩選** ⇒ 小片
若起點 = B(anomaly 的判定時點)        ⇒ 仍是零新欄位(欄位已存在),而
                                        🔴 **要處理「沒有 anomaly 列的那一族」** ⇒ 邏輯分岔
若兩族要用不同起點                     ⇒ 那是**產品/法律決定**,不是技術決定
```
⇒ 🔴 **所以這片現在卡的不是工,是【那 15 天從哪一刻算起】。**
