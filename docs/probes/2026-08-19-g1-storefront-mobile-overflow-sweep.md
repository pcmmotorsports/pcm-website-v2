## ⑦ 追加(同日稍後):**尾端測試** —— 而我的篩選器自己出過一次錯

上面 §② 的商品頁只有 0.23%。追加一輪**便宜篩選 + 尾端量測**,想法是:
**溢出是資料驅動的(字太長)⇒ 與其亂數多抽,不如把最長的那幾支挑出來量。**

### 7-a 🔴 第一版篩選器【全部抽到 0】,而那看起來像「沒有長字串」
```
病灶:`python3 - "$u" <<'PY'` —— heredoc 佔走 stdin ⇒ 腳本裡的 `sys.stdin.read()` 讀到空字串
症狀:306 支全部回 name=0 / label=0 / fits=0
🔴 而「全部 0」如果不看分佈,會被讀成「這些商品都沒有長字串」= 正好相反的結論
```
✅ **修法與自檢**:body 寫檔、用參數傳;並**先拿已知有 82 字 label 的那頁當正向對照** ——
抽到 `name=58 / label=82 / fits=20`,**82 與瀏覽器量到的一致** ⇒ 抽取器活了才跑全批。

### 7-b 修好之後的分佈(取樣 **296 / 19,782 ≈ 1.5%**)
```
說明書 label   中位 0（177 支沒有說明書）/ 最大 **82**（= 已知那支）/ 次高 74、71
適用 fits      中位 21 / 最大 56
商品名         🔴 **這一欄不可用** —— 每支都回 58 且內容相同
               ⇒ 我的 regex 抓到的是頁面裡【共用的車型字串】，不是該商品自己的標題
```
### 7-c 尾端 8 支的瀏覽器實測(390 / 320 各一次)⇒ **全部 0 溢出**
```
gbracing-fs-r9-2025-lhs-r    390: n=0 scrW=390 lab=82   320: n=0 scrW=320 lab=82
evotech-prn016013            390: n=0 scrW=390 lab=54   320: n=0 scrW=320 lab=54
其餘 6 支                     390/320 皆 n=0，selfCheck.ok 全 true
```
🔴 **而這裡露出篩選器的第二個問題**:curl 篩到 evotech 有 71-74 字的 `label`,
**瀏覽器實測那幾支的 `.pd-ir-doc-n` 只有 0 或 5 或 54** ⇒ **我的 regex 在那些頁抓到的不是說明書標籤。**
⇒ **篩選器的欄位定義不可靠;可靠的是瀏覽器那 16 發。**
📌 教訓與 §7-a 同族:**便宜的尺要先證明它量的是那個東西,而「有數字」不等於「量對了」。**

### 7-d 這一段真正買到的東西
```
✅ 已知最長那支（82 字）在 390 與 320 都不再溢出 —— 修法對【已知最壞情況】成立
✅ 另外 7 支尾端候選也全乾淨
⚠️ 而【商品頁全集仍未量】—— 1.5% 取樣 + 一個欄位定義不可靠的篩選器，合起來仍是下界
```
