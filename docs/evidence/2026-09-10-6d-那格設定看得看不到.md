# 🟢 §0 答案:**有一支 API 讀得到它 —— 而【我這個 session 讀不到】**

```
✅ 官方有專用端點(Supabase Management API):
   GET /v1/projects/{ref}/postgrest      逐字標題「Gets project's postgrest config」
   出處 https://supabase.com/docs/reference/api/v1-get-postgrest-service-config

🔵 而還有第二支, 它更貼近我們要的問題:
   GET /v1/projects/{ref}/database/openapi   逐字說明:
   「Returns the PostgREST OpenAPI specification for the project.
     **This is the replacement for querying `/rest/v1/` directly with the anon key.**」
   ⇒ 📌 官方自己說它是【拿 anon key 去打 /rest/v1/】那個做法的替代品
     —— 那正好是我昨天拒絕做的那一發。
```

🔴 **而我這個 session 讀不到它們**:
```
我手上的 Supabase MCP 沒有那一格 —— 實測 get_project(bmpnplmnldofgaohnaok) 回傳逐字只有:
  id · ref · organization_id · organization_slug · name · region · status
  · database{host,version,postgres_engine,release_channel} · created_at
⇒ 🔴 【沒有任何一個欄位在講 exposed schemas】
而那兩支端點要 Management API 的 personal access token ⇒ 我沒有, 也不該碰。
```

# ⚪ §1 負對照(你點名要的那一格)—— **而它的答案是結構性的**

**你問**:那個 API 對一個【確定被暴露的 schema】回什麼?沒有這一格,一個「查不到 net」分不出「它沒被暴露」與「這支 API 不回這個」。

✅ **而 `get_project` 這一支不用試就分得出來** —— 因為它**連 `public` 都沒提**。
```
public 是【確定被暴露】的(整個顧客站都走它)
而 get_project 的回傳裡【沒有 public、沒有 graphql_public、沒有任何 schema 欄位】
⇒ 🎯 所以「用 get_project 查不到 net」= 【這支 API 不回這個】, 不是【net 沒被暴露】
⇒ 📌 這一格不是我沒做, 是它的答案寫在回傳的形狀裡:那把尺根本沒有那一格
```

# 🔴 §2 而查文件撿到一個【比原問題更重要】的東西

**Supabase 官方 troubleshooting 逐字**(`PGRST002` 那一篇):
> 「**Manual Overrides** — If you have manually executed `ALTER ROLE authenticator SET pgrst.db_schemas`, **the Dashboard UI will no longer manage your schemas.** You must manually update the role configuration:
> `ALTER ROLE authenticator SET pgrst.db_schemas = 'public, example_schema';`」

🎯 **⇒ 那一格設定有【兩個住處】,而它們會互相取代:**
```
① 面板(Dashboard)  ← Sean 2026-09-09 抄的那一份
② DB 裡的 ALTER ROLE authenticator SET pgrst.db_schemas
🔴 而【只要有人做過 ②, 面板就不再管事】—— 而面板上仍然會顯示東西
⇒ 📌 那是一個【看得到而已經失效】的畫面, 比看不到更難發現
```

## ✅ 而今天這一格是乾淨的,**而證據已經在 repo 裡了**
