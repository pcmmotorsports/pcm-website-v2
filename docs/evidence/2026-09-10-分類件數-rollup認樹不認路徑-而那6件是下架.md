## 1 誰算那個 rollup

```

productCount 從哪來:
```

⇒ ✅ **不是 DB 算的,是【前台 TS 在記憶體裡加起來的】**;DB 只回每一列的直接件數。

## 2 🔴 它認的是 `parent_category_id`,**不是** `raw_path`

```
buildCategoryTree 逐字:
  if (c.parentId !== null) { subsByParent.get(c.parentId) … }
  summaries.filter((c) => c.parentId === null)   ← 頂層的定義
```

⇒ 🟢 **全程沒有碰過 `raw_path`。**
🎯 **⇒ 所以「同名而路徑不同」不會被算進錯的樹** —— 今天那三列同名(`維修零件` /
`維修零件 · 維修零件` / `服務與其他 · 維修零件`)各自掛在**自己的 parent 底下**,
`服務與其他 · 維修零件` 那一列**從來就是算在「服務與其他」那棵樹**,不會漏到「維修零件」。

🔵 **`raw_path` 在別的地方有用**(那道 `categories_raw_path_key` UNIQUE 靠它擋同層同名),
**而件數這條路不看它。** 📌 **兩個結構並存,而只有一個在算給客人看的數字。**

### 🛑 而射程遠不只這一列

```
全站 products 26,460 · 其中 delisted_at 非空 【559】
```

📌 **⇒ 任何一句「`products_public` 有 N 件」的唯讀讀數,都是【`pcm_readonly` 看到的 N】,
　　不是【客人看到的 N】,而兩者最多差 559。**

🎯 **判別句:一個「唯讀」的身分,不等於一個「跟客人一樣」的身分。
　　而它讀出來的數字,長得跟客人看到的數字一模一樣。**

🔴 **本 session 自己就受影響**,逐一列出來不掩蓋:
- `⟦search-DUPCATNAMES⟧` 那份寫「有貨那一列 **1,646** 件 vs 空的 0 件」
  ⇒ **客人側是 1,640**。🟢 **而結論不變**(1,640 仍然遠大於 0,「選錯 = 拿到空分類」那句仍成立)。
- 「最貴的商品 NT$ 265,000」那一發也是走 `products_public`
  ⇒ **沒有重驗它在不在那 559 裡面**(它有畫面、我在正式站開得起來 ⇒ 吻合「沒下架」,而**那是推論**)。

✅ **修法(給下一個人,不是給這一片)**:要問「客人看得到幾件」,
　條件要**自己補上 `AND delisted_at IS NULL`** —— 🛑 **不能靠 view 的名字裡有 `public` 這個字。**
