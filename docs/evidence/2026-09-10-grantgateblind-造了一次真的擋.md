## 一、怎麼造的

在**拋棄式分支** `scratch/gateprobe` 上(**用完即刪,沒有推、沒有合**)造出那個組合:

```sql
-- supabase/migrations/29990101000000_zzq_gate_probe.sql   ← 新檔 ⇒ 不在帳本 ⇒ PENDING
GRANT UPDATE (zzq_probe_col) ON TABLE public.zzq_probe_table TO service_role;
```
```ts
// apps/admin/src/lib/zzq/zzq-probe.ts   ← app 碼同時提到表名與欄名
return client.from('zzq_probe_table').update({ zzq_probe_col: 1 });
```
再用 `pre-push` 的 stdin 形狀餵它:`<local-ref> <local-sha> <remote-ref> <remote-sha>`。

## 三、🔴 而板列那句「構造一次真的擋」**問錯了受詞** —— 它不擋

板列(以及我接手時)預期的是「**擋**」。實測:
```
0 blocked   ·   1 欄位警告(不擋)   ·   rc=0
```
⇒ 🔴 **`rc=0` 表示一次真的 `git push` 會【放行】。**
⇒ 📌 **那道修法把它從【瞎】變成【看得見】,沒有變成【擋得住】。**

🛑 **而那是刻意的,不是漏做** —— 閘自己把判斷交回給人,輸出逐字:
> ✅ **你要自己判的那一句:上面那幾支檔,有沒有【真的】在讀那一欄?**

### 為什麼它只能警告 —— 讀數說明了

正檔那一發把 **12 支 pending 全部列出來**當「那支 migration」,而**真正宣告那一欄的只有 1 支**。
⇒ 📌 **它配得出「app 碼提到了某個表.欄」,配不出「是哪一支 pending migration 宣告的」** ⇒ **它沒有足夠資訊去擋,只能叫人看。**

⇒ ✅ **所以板列那一格的正確結論是**:
```
⛔ ~~缺的檢查 = 看它會不會擋~~
✅ 它【不擋】, 而那是設計。缺的檢查其實是:【有沒有人會去讀那一行警告】
```
🔴 **而那把問題從「閘夠不夠強」換成「那行警告有沒有觀眾」** —— 後者沒有任何自動化答得出來。
