## 1 🔴 先算差 —— 而差來自 policy 的形狀,不是表的重要性

我們今晚實際引用過的八張表,它們的 SELECT policy:

```
表                                   給誰            USING
categories                           PUBLIC          true                       ⇒ 差 0
products                             PUBLIC          delisted_at IS NULL        ⇒ 🔴 有差
product_variants                     PUBLIC          EXISTS(母商品未下架)        ⇒ 🔴 有差
customers                            authenticated   auth.uid() = user_id
                                     service_role    true                       ⇒ 差 0(後台身分)
orders                               authenticated   customer_user_id = auth.uid()
                                     service_role    true                       ⇒ 差 0(後台身分)
shipments                            同 orders                                   ⇒ 差 0(後台身分)
email_outbox                         service_role    true                       ⇒ 差 0
product_fitments_effective_sync_log  service_role    true                       ⇒ 差 0
```

**實際差幾列:**

```
表                bypass 看到   客人看到    差
products             26,460      25,901    559
product_variants     61,193      60,472    721
categories              116         116      0
⚪ 負對照 delisted_at IS NOT NULL AND delisted_at IS NULL ⇒ 0
```

### 🟢 一次除罪:五張表的唯讀讀數【安全】

`orders` / `customers` / `shipments` / `email_outbox` / `sync_log` 的 public 面**只有 `service_role` 那條 `USING (true)`**。
⇒ 🎯 **後台看到的就是 `USING (true)` 那一份,而那與我 bypass 看到的【是同一份】。**
⇒ ✅ **所以今晚那些「訂單 8 / 客戶 15 / 箱子 4 / outbox 7」全部成立,不用重看。**

🛑 **而那不是因為它們沒有 RLS** —— 是因為**它們的受詞是後台,而後台就是 `service_role`**。
📌 **同一張表換一個受詞(「客人看得到幾張訂單」)答案會變成 0 —— 而那是對的,不是缺口。**
