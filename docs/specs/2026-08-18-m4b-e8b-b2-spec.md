## §3 設計

### 3.1 登入 body 加一個**選填**欄 `account`

```
{ account?: string, password: string, code?, recoveryCode?, setupSecret? }

account 留空  ⇒ 走【現行這一整條路】，一行都不動 ⇒ sub = { kind: 'fallback' }
account 有值  ⇒ 走【新的個人帳號路】                ⇒ sub = { kind: 'user', staff_id }
```
🔴 **「留空走舊路」是 D0-b 的硬要求**(母 plan §3):本片單獨上線 = **零行為改變**。

**🔴 「留空」的定義(codex must-fix:沒定義 ⇒ 壞掉的具名請求會靜默變成備援)**:
```
走【備援】的，只有兩種情形：欄位【不存在】，或值是【空字串 ''】
其餘一律走【具名】：
  · 只有空白的字串（' '）⇒ 具名分支，然後【驗不過而失敗】，不得 trim 成空值
  · 非字串（number / object / null / true）⇒ 🔴 直接 400，不得正規化
⇒ 判別句：把壞掉的具名請求變成「成功的備援登入」＝ 把一個錯誤降級成一個【權限狀態】。
```

**🔴 多階段流程要一路帶著 `account`(codex must-fix)**:
現行登入是**單一端點多階段**(`login/route.ts:20-24`:密碼 → TOTP / recoveryCode / setupSecret)。
⇒ **第二段請求若沒帶 `account`,依上面的定義它就變成一次備援登入** —— 而使用者以為自己在做具名登入的第二步。
```
規定：具名登入的【每一段】都必須帶同一個 account
     第二段沒帶 ⇒ 🔴 拒（不是退回備援）
     第二段帶了【不同的】account ⇒ 🔴 拒
⚠️ 驗收要有這兩格，而且要有對照組（備援登入的第二段本來就沒有 account ⇒ 必須照舊會過）
```
🔴 **`sub` 要等 B3 才進 payload** ⇒ 本片先把 `sub` **算出來**,B3 才把它**簽進去**。

### 3.3 🔴 關掉 legacy fail-open(本片最容易漏、而漏了最貴的一件)

`issueSession`(`:116-133`)現在的行為:新 cookie 基礎建設缺 ⇒ **退回 legacy `ADMIN_COOKIE`**。
**而 legacy cookie 帶不動 `amr`,更帶不動 `sub`。**

⇒ **本片硬規定**:
```
account 有值（= 這是一次具名登入）而新 cookie 發不出來
   ⇒ 整個登入【失敗】，回一個明確的設定錯誤
   ⇒ 🔴 不得退回 legacy 分支（那會發出一顆「登入成功但沒有身分」的 cookie）
account 留空（備援）⇒ 現行行為一字不動，legacy 分支照舊可用
```
📎 **為什麼這是最貴的一條**:退回 legacy 的那一顆 cookie **活 30 天**(`:65` `maxAge: 60*60*24*30`),
而且**在畫面上與成功登入完全一樣**。⇒ **一次設定失誤 = 一個月的無身分 session,零徵兆。**

### 3.3-b 🔴🔴 legacy 的**另一半**:不是只有「發不發得出來」,還有「**收不收**」

> **2026-08-18 pull 後在最新樹上實地盤點才發現的缺口** —— 本檔 §3.3 只寫了**發**那一半。

`lib/auth-server.ts:41-47` `hasValidLegacy()` 逐字註解「**過渡雙讀**」,而 `:50` `requireAdmin()` 的邏輯是:
```
有新 cookie 且 SESSION_SECRET 設好 ⇒ 驗新 cookie
否則                              ⇒ 【接受 legacy】（除非 require_2fa 開著）
```
⇒ **就算 B2 讓具名登入不再【發】legacy cookie,一顆【已經在瀏覽器裡】的 legacy cookie
仍然可以通過 `requireAdmin` —— 而它最長活 30 天(`login/route.ts:65`)。**

🔴 **這一半為什麼比發那一半更容易漏**:發那半在**登入端點**裡,你改 B2 一定會讀到它;
收那半在**另一支檔的守門函式**裡,而它**今天是正常運作的功能**(過渡雙讀是刻意的)。

🔴🔴 **2026-08-18 關卡1 更正:legacy 的接受點【有兩個】,我只寫了一個。**
codex 逐字:「規格只要求關閉 `hasValidLegacy()`,**但 middleware 也獨立接受 legacy cookie**;
照規格施工會讓舊 cookie 仍可**讀取整個報價單後台**。」**我開檔核過,屬實**:
```
接受點 A  lib/auth-server.ts:41-47 hasValidLegacy() ← requireAdmin() 用
接受點 B  middleware.ts:82-90       ← 自己讀 ADMIN_COOKIE、自己比、直接 NextResponse.next()
          （matcher 涵蓋除少數靜態資產外的【全部路徑】，:95-99）
```
⇒ **只關 A 而不關 B ⇒ 舊 cookie 照樣進得了整個後台**,而 `requireAdmin()` 那道看起來已經修好了。
📎 這正是本檔 §3.3 那個病的第三次:**「不發」≠「不收」,而「不收」本身也有兩個地方。**

**⇒ 本片的規定(三條,不要只做第一條)**:
1. **具名登入不得發 legacy**(§3.3 已寫)。
2. 🆕 **開關打開之後,`hasValidLegacy()`(接受點 A)必須關掉** —— 否則「每個人都有自己的帳號」與
   「**任何人拿著一顆舊 cookie 就是管理員**」同時成立。
3. 🆕🆕 **同一個開關必須同時關掉 `middleware.ts:82-90`(接受點 B)** ——
   **兩個接受點要吃同一顆開關,不得各自判斷**(各自判斷 = 遲早只改一個)。
   ⇒ 開關的讀取寫成**一個共用函式**,兩處 import 它。
   🔴🔴 **函式要叫什麼(關卡1 R2 must-fix:我上一版把語意寫反了)**:
   旗標叫 `QUOTE_REQUIRE_REAL_IDENTITY`(**開 = 要求真身分**),而我舉例的函式叫 `legacyAcceptanceEnabled()`
   ⇒ **兩者語意相反**。施工者若讓它直接 `return process.env.QUOTE_REQUIRE_REAL_IDENTITY === '1'`,
   **打開「要求真身分」反而會打開「接受 legacy」** —— 而那個錯誤的方向**看起來完全正常**。
   ```
   ⇒ 硬規定：函式名與旗標【同向】，一律用 requireRealIdentity()
        export const requireRealIdentity = () =>
          process.env.QUOTE_REQUIRE_REAL_IDENTITY === '1';
     兩個接受點都寫成： if (requireRealIdentity()) { /* 不收 legacy */ }
   🔴 【不要】出現任何名字裡有 legacy/allow/enabled 而語意相反的中間層。
   📎 形狀：反向命名的 bug 不會在測試裡長得像 bug —— 它長得像「開關沒有生效」。
   ```

**⇒ 開關本身的規格(codex:「沒有確定名稱、預設值與兩個執行點」)**:
```
名稱    QUOTE_REQUIRE_REAL_IDENTITY
        🔴 【不要】叫 ADMIN_REQUIRE_REAL_IDENTITY —— 那是 admin repo 的開關，兩個 repo 兩顆
預設    關（未設 / 空字串 / 拼錯 一律當關；比對方式對齊 proxy.ts:17-18 的正向字面 === '1'）
執行點  恰兩處：lib/auth-server.ts 的 hasValidLegacy()、middleware.ts:82-90
        🔴 而【讀開關的地方只有一處】：共用函式。兩個執行點 import 它。
```

### 3.4 首次登入強制改密碼 —— **2026-08-18 關卡1 之後整段重寫**

> ⛔ **舊版被打掉的兩個錯(留痕,因為錯的形狀比結論值錢)**:
> 1. 我寫「選甲的理由:**`authorize` 那條路本來就要查那張表**」——
>    **實碼不是那樣。** `authorize/route.ts` 全檔零 `admin_user_staff_map`(我開檔核過)、
>    它只讀一個**沒有身分**的 session。⇒ **我用一個不存在的既有查詢當理由。**
> 2. 我把攔截點寫成「登入頁 + SSO `authorize`」——
>    codex 逐字:「員工可直接開 `/dashboard` 或呼叫後台 API 繞過」。**屬實。**

#### 🔴 正解:把「首次改密碼」**擋在【發 session】那一刻**,而不是擋在【用 session】那些地方

```
具名登入密碼驗過 ⇒ 查映射拿 staff_id ⇒ 🔴 順手看 must_change_password_at
   有值（要改）⇒ 【不發任何 session】，回 409 + { mustChangePassword: true }
   NULL（不用改）⇒ 照常發 session
```
**⇒ 這一個決定同時解掉 codex 的四條**:
- **不需要 session 帶身分** ⇒ 不再依賴 B3(舊版把 `sub` 算出來又丟掉,而 `authorize` 沒東西可查)
- **不可能繞過** ⇒ 沒有 session 就過不了 `middleware.ts:56-92` 那道閘 ⇒ `/dashboard`、任何 API、SSO `authorize` **全部到不了**
  (`authorize` **不在** `PUBLIC_PATHS`(`:28`)⇒ 它本來就要先過 middleware)
- **母 plan §6 第 9 條(不得經 SSO 繞過改密碼頁)⇒ 在型別上構造不出來**,不是靠再加一道閘
- **不必列舉入口** ⇒ 沒有「還有哪個入口沒擋到」這個問題
📎 判別句(house):**與其在每個出口攔,不如讓那張票根本發不出來。**

#### 改密碼端點(codex:「規格沒有定義改密碼 API」—— 屬實,補在這裡)

```
POST /api/admin/password
body { account, currentPassword, newPassword }
🔴 它【不吃 session】—— 因為需要改密碼的人根本沒有 session（見上）
① 用 account + currentPassword 走 Supabase Auth 驗一次（與登入同一條路）
   ⇒ 驗不過 ⇒ 與登入失敗【同一句訊息、同一個狀態碼】
② 驗過 ⇒ 用 Auth 的管理介面改成 newPassword
③ 成功 ⇒ 清掉 admin_user_staff_map.must_change_password_at（設 NULL）
   🔴 ①②③ 三步不是同一個交易（跨系統）⇒ ③ 失敗的世界 = 密碼已改而旗標還在
      ⇒ 症狀是「改完還是叫我改」，安全方向正確 ⇒ 明寫成已知代價，不加補償交易
④ 這支端點【要進 middleware 的 PUBLIC_PATHS】—— 否則沒有 session 的人打不到它
   🔴 而它一進白名單就變成【未登入可達】⇒ 限速與訊息一致性照 §3.5 一併適用
```
🔴🔴 **UI 放哪(關卡1 R2 must-fix `[折錯]`:我上一版只決定了 API,沒決定畫面)**:
```
決定：改密碼是【登入頁自己的一個狀態】，不是另一條路由。
      登入回 409 + { mustChangePassword: true } ⇒ 同一個頁面切換成「請設定新密碼」表單
🔴 為什麼不開新頁：middleware 的 matcher 涵蓋除少數靜態資產外的全部路徑（:95-99），
   而 PUBLIC_PATHS 只有三條（:28）。開一條新路由 ⇒ 沒有 session 的人【會被導回登入頁】
   ⇒ 施工者會看到一個「一直跳回登入頁」的迴圈，而它長得像 cookie 壞掉。
⇒ 因此 PUBLIC_PATHS 只需要多【一條】：那支 API。頁面本身就是 '/'（已在白名單）。
```
⚠️ **「只能改自己的」是靠 ① 保證的**:你得先打得出**那個帳號自己的現行密碼**。
**本片不做「忘記密碼」**(母 plan §2 非目標:不做寄信)。

#### 欄位放哪(甲案維持,而理由換掉)

`admin_user_staff_map` 加 `must_change_password_at timestamptz`(NULL = 不必改)。
**新理由(舊的那個是錯的)**:登入那條路**本來就要查這張表**拿 `staff_id`(§3.2 第 ③ 步)——
**那是 B2 自己引入的查詢,不是既有的** ⇒ 一次查詢同時回答「他是誰」與「要不要先改密碼」。
🔴 **而它多一支 migration ⇒ 多一次 apply**,代價不變。

#### 🔴🔴 codex 抓到的那個「所有人都免改」的世界(must-fix,已折)

```
B1-c 先 seed 兩列 ⇒ B2 才 ALTER TABLE 加這一欄 ⇒ 既有兩列自然得到 NULL
⇒ NULL = 不必改 ⇒ 【那兩個帳號的初始密碼永遠不會被要求換掉】，而沒有任何東西會紅
```
**⇒ 本片的 migration 硬規定**:加欄那支**必須在同一支檔內回填**
```sql
UPDATE public.admin_user_staff_map SET must_change_password_at = now()
 WHERE must_change_password_at IS NULL;      -- 建欄當下：現存的每一列都要改密碼
```
**並在同一支檔加一道落地斷言:回填後【零列】仍是 NULL。**

🔴🔴 **加欄那一行本身要帶 `DEFAULT now()`(關卡1 R2 must-fix)**:
```sql
ALTER TABLE public.admin_user_staff_map
  ADD COLUMN must_change_password_at timestamptz DEFAULT now();
```
**否則:日後新增員工的那支 migration 只要【沒寫這一欄】,那一列就得到 NULL = 免改密碼**
⇒ **新人的初始密碼永遠不會被要求換掉,而沒有任何東西會紅。**
⚠️ **`DEFAULT` 是給【未來新增的列】的,回填是給【現有的列】的 —— 兩件事,兩個都要做。**
(只做 `DEFAULT` ⇒ 現有兩列仍是 NULL;只做回填 ⇒ 下一個新人漏掉。)
⚠️ 那道斷言的負向對照:**故意插一列 NULL ⇒ 必須紅**(否則它在「回填根本沒跑」的世界也綠)。
🔴 **而那一發要在【哪裡】跑(關卡1 R2 nit)**:**在 migration 的交易【裡面】、斷言【之前】插那一列**
(拋棄式 PG 上跑,整支回滾)。**不是 apply 之後另外跑一支 verifier** ——
`COMMIT` 之後那道斷言**不會自己重跑**,事後插 NULL 不會有任何東西紅。
⇒ 可以直接掛進 `scripts/e8b-b1-probe/run.sh` 的那組突變(它已經是這個形狀)。

### D-1 🔴 **改完密碼之後,誰有權把那個旗標清掉?**(R2 標 `[折錯]`,而它打中的是我自己)

**問題**(我今天親手造出來的兩半,相隔幾小時):
```
上午：B1-b 我把 service_role 的權限收成【只有 SELECT】（:287），
      並加了一道斷言「service_role 不得有 INSERT/UPDATE/DELETE/TRUNCATE」（:294）
下午：B2 我要求「改完密碼 ⇒ 清掉 must_change_password_at」
⇒ 🔴 清旗標是一次 UPDATE，而【沒有人有權做它】
⇒ 失敗世界：密碼改成功了、旗標永遠清不掉 ⇒ 使用者每次登入都被要求再改一次密碼，永遠進不去
```

| 案 | 做法 | 代價 |
|---|---|---|
| **甲(我推薦)** | 建一支 `SECURITY DEFINER` 函式,**只做「清掉這一欄」這一件事**,`GRANT EXECUTE` 給 `service_role`;表本身維持零寫入權 | 多一個 DB 物件,而它是 `SECURITY DEFINER` ⇒ 要照 `docs/patterns/revoking-function-execute-in-supabase.md` **下兩道 REVOKE**(PUBLIC + 具名角色),否則新函式出生自帶 `anon` EXECUTE |
| 乙 | 直接 `GRANT UPDATE (must_change_password_at)` 給 `service_role`(欄級) | 🔴 **要放寬我今天才加的那道斷言** —— 而「想動驗證本身」是 `R4` 的立即停止訊號。**不推薦,而且不該由施工窗自己決定** |
| 丙 | 旗標不放這張表,改放 Supabase Auth 的 `user_metadata` | 狀態跨系統;而**「server 端能不能可靠讀寫 user_metadata」正是未解前提②的一部分** ⇒ 拿一個未解前提去解另一個問題 |

**推薦甲的一句話**:**它讓「這張表只有 migration 能寫」這個保證繼續成立,而唯一的例外是一支只做一件事、且被收好權的函式。**

### ✅ **裁定:甲**(主視窗 2026-08-18)

**追加的依據(不是我原本寫的,是它補的)**:甲**是本 repo 的既有形狀,而且今天已經用過一次** ——
G4 的 90 天清理函式就是 **owner-defined `SECURITY DEFINER` + 只 `GRANT EXECUTE`**,理由一模一樣:
**不要給表寫入權,只給一個窄的動作。**

🔴🔴 **而那兩道 REVOKE 是【必要條件】不是註腳(主視窗逐字)**:
```
新函式【出生就自帶 anon 的 EXECUTE】（Supabase 的 ALTER DEFAULT PRIVILEGES）
⇒ 兩道 REVOKE 照 docs/patterns/revoking-function-execute-in-supabase.md：
     REVOKE ALL ON FUNCTION …() FROM PUBLIC;
     REVOKE ALL ON FUNCTION …() FROM anon, authenticated;
🔴 「沒做」不等於「少一道保護」，等於【開了一個對外的洞】
   —— 那支函式是 SECURITY DEFINER，anon 執行得到它就等於 anon 改得動那張表
⇒ 因此：兩道 REVOKE + 一道【收權斷言】要寫進 migration 的斷言段，**不是寫進註解**。
   斷言的形狀照 b1b 既有那一套（has_function_privilege('anon', …, 'EXECUTE') 必須為 f，
   而且要有負向對照：故意 GRANT 給 anon ⇒ 必須紅）。
```

### D-2 🔴 **具名登入要不要支援「多階段」?**(R2 標 `[折錯]`)

**問題**:現行登入是**單一端點多階段**(密碼 → TOTP / 備用碼 / bootstrap),而**每一段是獨立的 HTTP 請求**。
我上一輪規定「每段都要帶同一個 `account`」——
**而 server 端沒有任何 challenge / 暫存狀態可以證明第二段與第一段是同一個人。**
⇒ **那條規則只剩前端自律,而驗收第 15 格(帶不同 account 必拒)構造不出來。**

| 案 | 做法 | 代價 |
|---|---|---|
| **甲(我推薦)** | **具名登入只走單段**(密碼)。`require_2fa` 若是開的 ⇒ 具名登入**直接明確拒絕並說明**,不靜默降級 | 哪天要開 2FA,具名登入會**整條擋住** ⇒ 那時必須先做 `E8-C`。**而 `Q5=A` 本來就把 per-user 2FA 排除在本期之外** |
| 乙 | 做一個 server 端 challenge(第一段回一個短命 token,第二段必須帶回) | **新機制 + 新儲存 + 新過期語意** ⇒ 明顯超出 B2 的體積,而且它自己會需要一輪審查 |

**它的依據不需要新拍板**:①`Q5=A` 明文把 `twofa`/`totp`/`force-relogin` 排除在這條線外
