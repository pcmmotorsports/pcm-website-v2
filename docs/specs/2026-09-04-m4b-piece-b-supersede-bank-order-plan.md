## 2. ✅ 系統自動取消【有前例】, 不必發明

```

### 🔴 而逾期那支留了一條**不變量**, 它直接管到本片
```
🔬 同檔 :249 逐字:

>
> ### 🔴 而位置改過一次, 那是這一片最重要的一格
> ```
> ⛔ 第一版:advisory lock 之後、cart dedup 之【前】
>    🛑 後面還有四個早退(duplicate · needs_settle · user_in_flight · order_locked)
>    ⇒ 那四條路上刷卡 attempt 根本沒取得, 而匯款單已經被取消 ⇒ **客人兩張單都沒了**
>    📌 **原子性保證的是「要嘛都發生要嘛都不發生」,**
>       **而我讓「都發生」裡的那個【都】只涵蓋我看得到的那一段。**
> ✅ 訂正:移到**最後一個早退之後、attempt 已經真的取得之後**(`v_attempt_id` 非 NULL)。
> ```
> ### 🔴 取消條件也改過:**照抄 canonical, 不自己想**
> ```
> ⛔ 我原本寫 `status IN ('pending','charged')` ⇒ **比 canonical 窄, 漏掉 `released`**
> ✅ 照抄逾期那支(20260903080000:176-179)的 `a.status <> 'failed'` ——
>    而該檔 :169 說「條件與 admin_cancel_order 步7 逐字相同」
> 🛑 **三處刻意逐字相同, 而它們【不共用】** —— 改任一處之前先讀另外兩處。
> ```
> ### 🔴 而多了一道守門:**目標單必須是刷卡單**
> ```
> 本函式原本沒驗過目標單的付款方式 —— 在片 B 之前那不痛(它只開 attempt);
> 而片 B 之後它會【取消別的單】⇒ 對匯款單誤呼叫 ⇒ 取消同車另一張匯款單 + 替匯款單開刷卡 attempt
> 📌 **一個原本無害的缺漏, 會因為【後來加進來的副作用】變成有害。**
> ```

### ⇒ 舊敘述(存查, 已作廢)

```
在 begin_charge_attempt 的 cart dedup 述詞加第四支:
  OR (o.payment_channel='bank_transfer' AND o.payment_status='unpaid' AND a.id IS NULL)
⇒ 撈到之後走**第三個出口**:
   · 就地 UPDATE 那張單:cancelled_at = now(), cancelled_reason = <新的 reason>
   · 🔴 而**不 return** —— 繼續往下走, 讓這次刷卡**取得鎖、正常扣款**(Sean 拍的乙 = 讓他刷)

### 為什麼寫在 SQL 裡而不是 TS
```
✅ **原子性**:取消那張匯款單與取得這次刷卡的鎖, 必須是同一個交易 ——
   否則中間斷掉 ⇒ 匯款單被取消了而刷卡沒開始 ⇒ **客人兩張單都沒了。**
🛑 而 TS 那層做不到:它是兩次 RPC。
```
⏰ **作廢條件**:`begin_charge_attempt` 改成非 advisory-lock 的實作。
