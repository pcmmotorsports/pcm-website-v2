## 1. 🔴 這件事值不值得做的判準:**`proxy.ts` 寫得出單元測試嗎?**

**不是「比較乾淨」。** 那 18 支裡最重的三支:

```
apps/admin/src/proxy.ts                      ← B3 線 codex F14 點名的【讀取閘 / auth 邊界】
apps/admin/src/app/api/sso/start/route.ts
apps/admin/src/app/api/sso/callback/route.ts
```

**現行設定下,這三支寫不出行為層單元測試** —— 而它們是**認證邊界**。

### ⚠️ 而我要先講一件 plan 不能替它回答的

**alias 修好 ≠ `proxy.ts` 就測得出來。** alias 只解決**解析**;
`proxy.ts` 還可能有**其他不可測因素**(Next runtime 依賴、env、side effect)。
🔴 **⇒ 驗收條件必須是「`proxy.ts` 真的多出一格行為層測試並且會紅」,不是「alias 設定改好了」。**
📎 那正是 traps 那條:**「改了設定」與「那個設定生效了」是兩件事。**

## 2. 三個候選 + 我的推薦

### 甲 · root config 用 `projects`,per-app alias

**vitest 版本實測 `4.1.5`** ⇒ **原生支援 `projects`**(現行 config 的 `workspace` 字樣只出現在**註解**裡,
`grep -n 'projects\|workspace' vitest.config.ts` ⇒ 唯一命中是 `:6` 的說明文字 ⇒ **目前沒有在用**)。

```
優點  一次解決 18 支；shadcn 積木再進來也自動涵蓋
      per-app alias 是 vitest 官方形狀，不是繞路
缺點  動的是【全域】設定 ⇒ 爆炸半徑最大（見 §3）
      要重新安排 include glob 與 setup 檔的歸屬
```

### 乙 · admin 全面轉相對路徑

```
優點  零設定改動、零爆炸半徑
缺點  🔴 與 shadcn 生成物對抗 —— 9/18 是積木，而【每引入一顆新積木就多一支】
      ⇒ 它會自己長回來，而擋它的只能是【人記得改】
      📎 今晚已經證明五次：靠「記得」的防線會失效
```

### 丙 · 每個 app 一份 vitest config

```
優點  隔離最徹底；各 app 自己的 alias / setup / include 互不影響
缺點  測試指令變成多條（`pnpm test` 要能一次跑完，否則會有人只跑一半 ⇒ 假綠）
      重複設定會各自漂移（今晚「兩個都叫 typecheck」那件的同族風險）
```

### 🔴 我推薦 **甲**,而理由不是它最漂亮

1. **乙的失敗模式是「會自己長回來」** —— 9/18 是生成物,**而生成器固定產 `@/`**。
   選乙等於**把一個結構問題換成一條需要人維護的紀律**,而今晚我們已經數過那種防線的成功率。
2. **丙把「一份設定」變成「N 份會各自漂移的設定」** —— 而**「兩個都叫 typecheck 的東西涵蓋範圍不同」
   那件事今天才剛咬過我們一次**(root `package.json` 的 `&&` 後半沒人跑)。
3. **甲是 vitest 官方形狀**,而且 `projects` 天生就是為 monorepo 設計的。

⚠️ **甲的代價我不淡化**:它動的是**所有測試的解析設定**,而**改壞了可能是安靜地壞**(解析到錯的檔)。
⇒ 那就是 §3 的驗收條款要擋的。

## 3. 🔴 爆炸半徑與驗收條款(缺一不可)

**它動的是所有測試的解析設定 ⇒ 改壞了全部測試一起壞,而且可能【安靜地壞】(解析到錯的檔)。**

### 已量的半徑

```
storefront 測試檔 import `@/` 者   75 支   ← 🔴 改壞這些是最大風險
packages/ 用 `@/` 者                0 支   ← 不受影響（正向對照，證明上面那個 75 不是量錯範圍）
admin 非測試檔 import `@/` 者      18 支   ← 這次要救的
```

### 驗收條款(每一條都要能 yes/no)

```
① proxy.ts 真的多出一格【行為層】測試（不是 readFileSync 文字層），
   且【用突變證過它會紅】—— 突變靶：把那道讀取閘拿掉
   🔴 這一條是「值不值得做」的判準本身，不能用「alias 設定好了」代替

② storefront 那 75 支【仍然解析得到】
   量法：改前後各跑一次 `pnpm test`，比對【檔數與通過數】
   🔴 不能只看 rc=0 —— 解析失敗有可能表現為【檔被 silently skipped】
      而那正是 vitest.config.ts:32-33 註解記著的舊事故（"silently skipped"）
   ⇒ 驗收要比對【Test Files 的數字】，不是只看綠

③ 一發【負向對照】：故意把 admin 的 alias 指到錯的路徑
   ⇒ admin 那批必須紅；若它照樣綠，代表這個 alias 根本沒生效
   🔴 沒有這一格，「改好了」與「改了但沒生效」在畫面上是同一句

④ shadcn 那條污染鏈：選甲 ⇒ 自動涵蓋（新積木進來不需要任何人做事）
   ⇒ 驗收 = 引入一顆新積木（或構造一支用 `@/` 的新檔），不改任何設定，它就測得到

⑤ 那 33 支繳稅註解怎麼辦
   ⚠️ 不要在同一片裡清 —— 那會讓這片的 diff 大到看不出重點
   ⇒ 但要在 plan 裡寫下【它們會變成過期字面】，並開一個後續項
   🔴 不寫的話，下一個人讀到那些註解會以為現在還要繳那個稅
```
