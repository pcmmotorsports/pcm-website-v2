## §1 那個「不加 deferrable trigger」的決定,**要翻案**。理由不是複雜度,是前提

**原決定的兩個理由,逐條檢查**:

| 原理由(逐字) | 現在成不成立 |
|---|---|
| **「RPC 權威已足」** | 🔴 **不成立** —— 「已足」的前提是單一寫入者,本片加入第二個 |
| **「避免複雜度」** | ⚠️ **不得照抄** —— 那是在「只有一個寫入者、風險已被結構消除」的前提下的取捨。**前提沒了,取捨要重算,不是把結論搬過來。** |

### 1-1 翻案的代價,我量了(不是憑感覺說「很便宜」)

**deferrable constraint trigger 的成本 = 每筆交易對受影響訂單跑一次聚合**:
```sql
SELECT sum(line_total) FROM public.order_items WHERE order_id = <該單>;
```
**量級**:單張訂單的品項數(個位數~十幾);訂單量 memory 記 **每月 100-300 筆**,
**正式庫現況 13 筆**(2026-08-15 主視窗實測)。

🔴 **codex R1 #2 打中兩點,逐條折**:

**① 「若 `order_id` 沒索引,聚合會掃全表」** ⇒ **有索引,而且我原本的措辭是錯的**:
```
20260604120000:179  CREATE INDEX order_items_order_idx ON order_items(order_id);
```
⚠️ **我原文寫「用主鍵索引撈十幾列」—— `order_id` 不是主鍵,主鍵是 `id`。**
**那個字面錯讓論證看起來比實際有依據。** 正確講法:**走 `order_items_order_idx` 這支次級索引。**

**② 「多列變更各自排入 deferred 事件、未按訂單去重 ⇒ 不是『每筆交易一次』」** ⇒ **成立,我原文是錯的。**
`CONSTRAINT TRIGGER … FOR EACH ROW` 會**逐列**排事件 ⇒ 改 N 個品項就檢查 N 次(同一張單重複算 N 次)。
🔴🔴 **R2 #3 要我【選定】不是列兩案,而 codex 補的那條是硬約束不是偏好**:
> **`FOR EACH STATEMENT` + transition table **不能直接保留 deferred constraint-trigger 語意**。**
> **「採交易內『已檢查』標記後中途切成立即檢查,再次修改同單可能被跳過。」**

> 🔴🔴 **2026-08-15 關卡2 之後補記 —— 下面「不去重」那個結論已經被推翻一半,而推翻的方式很重要:**
> **codex 關卡2 指出還有第三種去重,而它不在我當時考慮的兩案裡**:
> **「同一個 row-event 內」**把 `v_old` 與 `v_new` 當場比一次(`order_id` 沒變 ⇒ 第二次是同一張單、同一個答案)。
> ✅ 它**不是**下面第 2 點否決的那案:那案是**跨 statement 記憶**(標記某單「本交易已驗過」)⇒ 之後再改同一單會被跳過 ⇒ **漏檢**;
> 這案只在**同一個 row-event 內**比兩個值,跨單調撥時 `v_new ≠ v_old` ⇒ **兩張單照樣各檢查一次,零漏檢**。
> ⇒ **已採用。** 效果:RPC 一次改單原本對同一張單做 4 次相同 `sum`(items trigger 2 次 + orders trigger 2 次),現在 2 次。
> 🔴 **判別句(這條比結論本身值錢)**:我把「去重」當成**一個**選項的兩種強度,
> 而它其實是**三個不同作用域**(跨交易 / 跨 statement / 同一 row-event)。
> **否決了其中最危險的那個,不等於否決了整類。**
>
> ⚠️ **而第 3 點的成本推論也跟著失效**(它建立在「不去重」上)——**改前件不會讓後件自己更新**,
> 下面第 3 點的「N 次仍是十幾列 × N」現在要讀成「去重後 N=1 的情形只算 1 次」。**本片 N=1,結論不變、理由變了。**

**⇒ ~~選定:`FOR EACH ROW` constraint trigger,而且【不去重】~~。三條理由裡第 1、2 條仍成立,第 3 條見上方補記**:
1. **`CONSTRAINT TRIGGER` 語法本身只支援 `FOR EACH ROW`** ⇒ transition table 那案**不是取捨,是不可用**
   (要 transition table 就得放棄 `DEFERRABLE`,而 DEFERRED 是本方案的必要條件,見上)。
2. 🔴 **「交易內已檢查標記」有 codex 指出的正確性風險**:標記之後同一交易再改同一張單 ⇒ **可能被跳過**
   ⇒ **它把「多算幾次」的成本問題,換成「可能漏檢」的正確性問題。** **那個交換不划算。**
3. **成本重算**:不去重 ⇒ 每筆受影響的品項列各檢查一次。
   單次成本 = 走 `order_items_order_idx` 撈該單十幾列做 `sum` ⇒ **N 次仍是十幾列 × N**,
   而 N = 本次改動的品項數(本片一次只改一列,**N = 1**;片 2/片 3 可能批次)。
   ⚠️ **⇒ 本片 N=1,去重無收益;批次那片再評估,而那時要重估的是【它】不是本片。**

**⇒ 成本結論定稿(關卡2 後修訂)**:
**「每筆受影響的品項列一次,而同一 row-event 內 `order_id` 沒變時只算一次;本片 N=1。」**
~~不是「每交易一次」,是「每筆受影響的品項列一次,除非去重」。~~ **← 措辭作廢。**
~~**← 措辭作廢,已選定不去重。**~~ **← 這句也作廢了(關卡2 採用了同 row-event 去重)。**

### 2-2 第二層:constraint trigger —— **定位是縱深防禦,不是「唯一讓它變成保證的東西」**

#### 🔴 先更正我自己的論證(codex R1 #4 打中,而且它的反例在本 repo 是成立的)

**我原文寫**:~~「人數變多不會讓約定變成保證。」~~
**codex 的反例逐字**:「**多支受權限封閉的 RPC 都在同一交易重算金額,表級寫入又不可繞過;寫入者變多仍可維持結構保證。**」

🔴 **而那個反例不是假想 —— 本 repo 就是那個結構**:
```
20260611120000:239  REVOKE INSERT, UPDATE, DELETE, TRUNCATE ON TABLE public.orders FROM service_role;
                    -- 保留 SELECT
```
⇒ **`service_role` 根本改不了 `orders`,寫入只能經 owner 的 SECDEF RPC。**
**⇒ 「兩支 RPC」不等於「兩個可以亂寫的人」,它們仍在同一道權限閘後面。**

**⇒ 論證改寫(這才是我該說的)**:
> **第一層(RPC 內重算)提供的是「所有已知寫入路徑都會算對」。**
> **它沒提供的是「未來新增的寫入路徑也會算對」—— 而 `#13` 之後這條線還有片 2(改品項)、片 3(改數量)。**
> **⇒ trigger 的價值不是取代第一層,是讓【下一個寫入者】不必記得。**

**⇒ 定位:縱深防禦。** 不宣稱「沒有它就沒有保證」,**宣稱「有它,保證就不依賴每個新 writer 都記得」。**

#### 🔴 DEFERRED 的必要性(codex R1 #1 打中我自陳的最弱點)

**codex 逐字**:「**立即檢查只會在『先改 item、再改 order』這個實作順序誤報;改由 trigger 同步重算,或 RPC 結尾明確驗證,就不必 DEFERRED。突變測試只能證明 DEFERRED 適合目前方案,不能證明它是唯一必要方案。**」

✅ **成立。我把「對這個方案必要」寫成了「必要」。** 三個候選並列,選一個並寫理由:

| | 做法 | 為什麼不選 / 選 |
|---|---|---|
| 甲 | **RPC 結尾自己驗一次** | 🔴 **它就是第一層** —— 對「未來的新 writer」零覆蓋,而那正是要防的 |
| 乙 | **trigger 同步重算 `orders.subtotal`**(不是檢查,是代算) | ⚠️ **把「誰負責算」搬進 DB** ⇒ RPC 與 trigger 兩邊都在算,**下一個人不知道該改哪邊**;且它讓錯誤變成靜默修正,**不會紅** |
| **丙 ⭐** | **`DEFERRABLE INITIALLY DEFERRED` constraint trigger,只檢查不代算** | 允許交易中途不一致(**改 item 與改 order 之間必然有一瞬**),**在 COMMIT 那一刻判定** ⇒ 不誤報、不代算、對新 writer 有效 |

🔴 **改寫後的宣稱**:**「DEFERRED 是【丙這個做法】的必要條件,不是【這個問題】的必要解。」**
**突變測試證的也只到這裡** —— 驗收條件 §5-1 的措辭跟著改。

```sql
  from public.orders o left join public.order_items i on i.order_id = o.id
 group by o.id, o.display_id, o.subtotal
having o.subtotal <> coalesce(sum(i.line_total),0);
-- 預期：零列。🔴 非零 ⇒ trigger 一裝，那些單的下一次任何改動都會炸 ⇒ 先修資料再 apply。

-- ② 金額欄的約束在正式庫真的長那樣嗎（關掉三份文件共同掛的「repo 字面 vs DB 實況」）
select conname, pg_get_constraintdef(oid)
  from pg_constraint
 where conrelid in ('public.orders'::regclass,'public.order_items'::regclass)
   and contype = 'c' order by conname;

-- ③ 有沒有我沒查到的 trigger 在動金額（0b §6-1 明列未查）
select tgname, tgrelid::regclass, pg_get_triggerdef(oid)
  from pg_trigger
 where tgrelid in ('public.orders'::regclass,'public.order_items'::regclass)
   and not tgisinternal;
```
