# 附錄 A · 🔴 給 `#525` × `admin_customer_list_v` 的守門(**可直接貼進那支 migration**)

> ⚠️ **這一節不屬於 `#538`,是主視窗 2026-08-16 另派的。** 放這裡只因為它還沒有自己的 plan。

## A.1 要守什麼(一句話)

`#525` 的搜尋走 **`.rpc('admin_search_customers')` ⇒ 它查 `public.customers`**;
而列表(void-readers)走 **`.from('admin_customer_list_v')`**。
🔴 **兩者是不同的來源,而 `.in('user_id', ids)` 建立在「它們的列集合相同」之上。**
**今天成立(view 無外層 `WHERE`),而【沒有東西守著它繼續成立】。**

**壞掉時的症狀**:搜尋命中 → 列表取不到 → 畫面「共 0 位」+ chip 寫著「目前搜尋:王小明」
⇒ **員工得到「查無此人」,而那個人明明存在。**

## A.2 🔴 天真寫法會對【好的 view】誤報 —— 實測,不是推的

**拋棄式 PG 17.10 實跑**(三個子查詢的真實形狀):
```
候選①  v_def ~* '\mwhere\M'                     good ⇒ 1   bad ⇒ 1   🔴 兩個都命中，零判別力
候選②  行首恰兩個空白的 WHERE（^  WHERE ）       good ⇒ 0   bad ⇒ 1   ✅ 分得出來
```
⚠️⚠️ **上面那個 ✅ 只對【b1 = 外層 WHERE】成立。**
🔴 **A.8.1 實測:同一道對【子查詢 FROM】與【JOIN】兩種繞法【都漏】。**
**⇒ 讀到這裡不要停 —— A.2 只是「天真寫法為什麼不行」,不是「這就是答案」。答案在 A.8.3。**
**原因**:那支 view 的定義裡**本來就有三個 `WHERE`** —— 它們在**算欄位的相關子查詢**裡。
`pg_get_viewdef(oid, true)` 的 pretty-print 把**外層子句排在行首 2 格**、
**子查詢的 `WHERE` 縮到 10 格** ⇒ **縮排就是那個判別點** ——
⚠️ **而它只對【外層 WHERE】這一種繞法有效(A.8.1 實測:子查詢 FROM 的 `WHERE` 縮到 11 格,同樣漏)。**

⚠️ **而這正是那支 migration 註解裡記著的教訓的同一個坑**:
> 「初版那句『`pg_get_viewdef` 會印成 `FROM a, b` 所以擋得到』是**推的、而且是錯的**。」
🔴 **所以我沒有猜輸出格式 —— 我把兩種 view 都建出來,印給自己看。**

**實測到的原文(節錄)**:
```
good:  ...
         FROM customers c;
bad:   ...
         FROM customers c
        WHERE deleted_at IS NULL;      ← 行首 2 格
```

## A.3 ⇒ 可直接貼的 SQL(照 `:140-179` 的既有風格)

```sql
  -- ⑤ 🔴 `#525` 連動:本 view 必須與 public.customers 【逐列等同】
  --    理由:客戶搜尋走 RPC(查 public.customers)拿 id,列表在【本 view】上 `.in('user_id', …)` 取列。
  --    兩者列集合一旦分岔 ⇒ 搜得到的人列表列不出來,而畫面只會寫「共 0 位」——
  --    員工得到「查無此人」而那個人存在。**那是靜默的,沒有任何東西會紅。**
  --
  --    🔴 為什麼不是直接找 'where':本 view 定義裡**本來就有三個 WHERE**(算欄位的相關子查詢)。
  --       拋棄式 PG 17.10 實測:`v_def ~* '\mwhere\M'` 對**好的 view 也命中** ⇒ 零判別力。
  --       `pg_get_viewdef(oid, true)` 把外層子句排在**行首 2 格**、子查詢的縮到 10 格
  --       ⇒ **縮排是判別點**。(格式是**印出來看的**,不是推的 —— 見本檔 ② 那條「初版推錯」的教訓。)
  --
  -- ⚠️⚠️ **本層(字面層)【已知不完整】,而且是列舉式的 —— 不得當成「擋得住」。**
  --    2026-08-16 實測三種繞法,三道字面檢查各只抓到一種:
  --      外層 WHERE   ⇒ 只有本條抓到
  --      子查詢 FROM  ⇒ 只有「FROM 白名單」抓到，本條漏
  --      JOIN         ⇒ 只有既有的 join 正規式抓到，本條漏
  --    🔴 **真正擋得住的是 ⑥(行為層,雙向 EXCEPT)** —— 它不管你【怎麼】篩,只管【篩了沒】。
  --    ⇒ 本條的價值是「空庫上也有一點東西」,**不是「防線」**。
  --    🔴 **要補第四種繞法之前先想:那只會 +1,而 ⑥ 本來就抓得到它。**
  IF EXISTS (
    SELECT 1 FROM regexp_split_to_table(v_def, E'\n') AS l WHERE l ~ '^  WHERE '
  ) THEN
    RAISE EXCEPTION '客戶列表 view 驗收失敗 — 最外層出現 WHERE,會篩掉列。'
      '`#525` 的關鍵字搜尋在 public.customers 上找 id、在本 view 上取列 ⇒ '
      '兩者列集合必須相同。要加篩選請先改搜尋那一側,否則員工會看到「查無此人」而那個人存在。';
  END IF;
```

## A.4 ⛔ **【已被 A.8.5 取代,保留供對照 —— 不要複製本節的 SQL】**

> 🔴 **本節的 ⑥ 是【純量列數比較】,而 A.8.2 實測它會放行「筆數相同、集合不同」的 view。**
> **正確版本在 A.8.5(雙向 `EXCEPT`)。保留本節是因為【它錯在哪】值得看,不是因為它還能用。**

### A.4(原文)⚠️ 第二道(行為層)—— **要配前提格,否則空表恆真**

`A.3` 釘的是**定義的字面**;下面這道釘的是**真實列數**。**兩道都要,理由不同。**

```sql
  -- ⑥ 行為層:view 與 customers 逐列等同(補 ⑤ 的盲區 —— ⑤ 只看得到 WHERE，
  --    看不到「有人把 FROM 換成另一張表」或加了 JOIN 造成的列數變化)。
  -- 🔴 前提格:分母為 0 時本斷言【恆真】(拋棄式 PG 實測:空表時 good/bad 都相等)
  --    ⇒ 沒有這一格,新庫上這道會靜默通過。
  SELECT count(*) INTO v_cnt FROM public.customers;
  IF v_cnt = 0 THEN
    RAISE WARNING '⚠️ customers 表為空 ⇒ 下面的「列數等同」斷言【沒有判別力】,本次未真正驗證。';
  ELSE
    IF (SELECT count(*) FROM public.admin_customer_list_v) IS DISTINCT FROM v_cnt THEN
      RAISE EXCEPTION '客戶列表 view 驗收失敗 — view 列數(%) 與 customers(%) 不符,'
        '違反 `#525` 依賴的「兩者列集合相同」。',
        (SELECT count(*) FROM public.admin_customer_list_v), v_cnt;
    END IF;
  END IF;
```
⚠️ **⑥ 用 `RAISE WARNING` 不是 `EXCEPTION`** —— 空表是**合法狀態**(新庫、測試庫),
不該讓 apply 失敗;但**必須留痕**,否則「通過」與「沒驗到」長得一樣。

### A.9.1 ✅ 量到的(PG 17.10,拋棄式叢集,跑完即刪)

```
① SET LOCAL 與讀取【同一交易】內          ⇒ 'on'      ✅ 讀得到
② 交易外、分成兩個 statement              ⇒ (NULL)    🔴 讀不到
③ 交易 COMMIT 之後、同一連線再讀           ⇒ (NULL)    ✅ 符合 LOCAL 語意（不外洩）
④ SET LOCAL 與【DO 區塊】同一交易          ⇒ NOTICE: DO 讀到: on   ✅ 讀得到

正向對照（證明差別來自 LOCAL 這個字，不是測法壞掉）：
   ② 換成 SET（非 LOCAL）                 ⇒ 'on'      ✅ 量具是活的
   再換一條【新連線】讀那個值              ⇒ (NULL)    ✅ SET 也只活在該連線
```

### 🔴🔴 A.9.2 而題目問的不是最容易破的那個前提

**主視窗問的是「pooler 會不會讓 `SET LOCAL` 失效」**(house 有一條 pooled 連線 no-op)。
🔴 **而量下去,【交易邊界】更前面就會讓它失效**:
> **`SET LOCAL` 是交易範圍的。它與那個 `DO` 區塊若不在同一個 `BEGIN…COMMIT` 裡,直連也是 no-op。**
⇒ **就算 `db push` 走直連、就算 CLI 強制 session mode,前提沒滿足照樣不生效。**

> 🔴 **可攜的一條:當一個機制有兩個以上的前提,先被問的往往不是最容易破的那一個。**
> **⇒ 列前提要列完再挑,不要順著問題給的那一個往下鑽。**

#### ⚠️ 而我撤回 A.8.6 那個「改推 fail-closed」的立場,理由是前提沒了

#### 🔴🔴 A.9.0-a 而我實測 RLS 那件,**結果與轉述給我的不同,而差別改變了目錄層的價值**

**轉述給我的**:「對底表加 RLS ⇒ 行集分岔,而 view 定義一個字都沒動」。
**我量的(PG 17.10,`security_invoker=true` 的 view + 一個受 RLS 限制的角色)**:
```
加 RLS 前   customers=3   view=3
加 RLS 後   customers=2   view=2      🔴 兩邊【一起】掉
⇒ 我的行為層（view vs customers）⇒ 相等 ⇒ 【通過】
⇒ view 定義 md5 完全相同 ⇒ 定義層也看不到
```
🔴 **⇒ RLS 不會讓 view 與 customers 分岔 —— 它讓兩者【同步縮小】。**

**而真正分岔的是另一對,我量出來了**:
```
同一個 reader 角色下：
  view 看得到       = 2      ← security_invoker ⇒ 吃 RLS
  customers 看得到  = 2
  🔴 搜尋 RPC 看得到 = 3      ← SECURITY DEFINER ⇒ 【繞過 RLS】
```
⇒ **`#525` 的搜尋會找到 3 個 id,而列表只列得出 2 個** ——
**症狀正是本節一開始那個:「搜得到的人,列表列不出來,而畫面寫【共 0 位】」。**

**⇒ 三個結論**:
1. ✅ **目錄層【必要】** —— 它是**唯一【資料無關】**看得到這件事的一層。
   ⚠️ **2026-08-16 訂正**:我原本寫「**唯一**看得到的一層」,**那句過寬,已被打掉。**
   🔴 **行為層【看得到】,只要比對的是【對的那一對】** —— 我自己的數據就證明了:
   ```
   RPC 看得到 3 ／ view 看得到 2   ⇒ 比對這一對就會紅
   而我的 ⑥ 比的是 view vs customers ⇒ 2 vs 2 ⇒ 通過
   ```
   > 🔴 **病不是「行為層看不到權限」,是【我比對的那一對物件選錯了】。**
   **⇒ 那是一個可執行的改進,不只是一句限定**:⑥ 若要涵蓋權限層,
   **要比的是「搜尋 RPC 回的 id 集合」vs「view 看得到的 id 集合」,而不是 view vs 底表。**
   ⚠️ **但那一版的 ⑥ 需要【以列表那條路的角色】跑,而 apply 時是 apply 者的身分**
   ⇒ **能不能在 migration 裡構造出來,我沒量。標未確認。**
2. 🔴 **我的行為層(⑥)對 RLS 有盲區,而我原本以為它「三種繞法全抓」** ——
   **那句話只對【view 定義層面】的三種繞法成立,不涵蓋權限層。已在 A.8.3 附近標。**
3. ⚠️ **目錄層要釘的不只是 view 的 `security_invoker`,還有【底表的 `relrowsecurity`】** ——
   兩者都在 `pg_class`,**零資料需求**:
   ```sql
   SELECT relrowsecurity FROM pg_class WHERE relname='customers';   -- 必須 false，或
   SELECT reloptions      FROM pg_class WHERE relname='admin_customer_list_v';
   ```
   🔴 **而若哪天 RLS 是刻意要開的,那就必須同時改搜尋那一側(RPC 也要吃 RLS),不能只開一邊。**
