## 2. 🔴 成本已經變了(`P-296-NOTE` 的估算過期)

P-296 逐字寫:
> 「三欄若最終要撤,會動到已收割的 `36b01103` —— 但兩片**都還沒 apply**,所以撤的成本現在最低。
>  **這個時間窗會在 Sean 批 apply 那天關掉**。」

⇒ **今天(2026-08-10 中午)已經 apply。** 那個窗**關了**。
撤欄成本從「改一顆未 apply 的 commit」變成「**再寫一支 migration 動正式庫的錢面表**」
—— 而動正式庫錢面 schema 命中鐵則 12③,要走完整流程 + Sean 批 apply。

⚠️ 這條**不是**支持 A 的理由本身(沉沒成本不該影響決策),但它改變了 B 的**真實價碼**:
B 現在是「新增一張表 + L5a-1 寫入端改寫 + L5b 契約」,而不是 P-296 當時估的「趁還沒 apply 順手改形狀」。
⚠️ **分開估價(審查 nit)**:「撤三欄」是**可選的清理**、不是 B 的必付成本(可以留著當冗餘);
把它算進 B 會高估 B。真正讓 B 變貴的是**改寫已上線的讓路寫入端**。
🔴 而 **C 兩者都不用付**。

## 3. L5b 到底要回答什麼?(這才是判準)

L5b = 補償盯梢與退款。它對每一筆被讓路的舊 attempt 要決定「**該不該退錢**」。
那個決定需要三樣輸入:

| 輸入 | 從哪來 | 三欄夠不夠? |
|---|---|---|
| ①這筆是被讓路的嗎(認人) | `superseded_at IS NOT NULL` | ✅ 夠 |
| ②它後來到底有沒有真的扣到錢 | 🔴 **現在去查 TapPay Record**(權威只有這個) | ✅ 與紀錄形狀無關 |
| ③退款要冪等、不重複退 | TapPay refund 鍵消耗性 + 本地冪等鍵 | ✅ 與紀錄形狀無關 |

🔴 **關鍵**:②是**當下觀察**,不是歷史觀察。
「這筆錢現在到底在不在」只能問 TapPay 現在,**問不出來也不能靠當初讓路時那一眼**
(那一眼的意思只是「當時查不到/當時恆 PENDING」,`settle-charge.ts:101-108` 逐字提醒過
`record_not_found` **不是「沒扣款」的證明**)。
⇒ 🔴 **精確講法(審查 nit 1;v1 寫「沒有價值」太滿)**:當初的觀察快照
**不是自動退款判定的必要條件、也不是充分條件**。它仍有價值——只是價值在
**客訴爭議 / 對帳差異 / TapPay 事後改狀態**那一面,不在「這筆現在該不該退」那一面。
⇒ 這正是把它放進 **L5b 的 ledger(C 案)** 而不是放進讓路寫入端(B 案)的理由。

## 4. 那 append-only 換到什麼?(誠實列)

| P-296 列的三項 | 是決策價值還是稽核價值? |
|---|---|
| ①不可覆寫(結構性,非寫入端自律) | ⚠️ **主要是稽核**;決策面上,L5a-1 閘⑥ `superseded_at IS NULL` 只構成 **RPC-local first-write-wins**(審查 nit 2:不得稱「整體 write-once」——繞過該 RPC 直寫就沒有它) |
| ②保存整段觀察快照 | **稽核**(§3 已證退款決策用不到) |
| ③多筆歷史、重試/重複裁定看得見 | **稽核**;且目前一筆 attempt 只會被讓路一次(閘⑥) |
| ~~解決 provenance~~ | 🔴 **換不到**——P-296 自己就寫明「誰能 insert 一樣是 ACL 問題,獨立表不會比較安全」 |

⇒ 三項全部落在**稽核/爭議追溯**那一側。稽核有價值,但它**不是 L5b 能不能正確退款的前提**。

## 5. 【v1 遺留】維持 A 會放棄什麼 —— 🔴 **C 案把這三條大部分收回來了**
> 以下三條是 v1 對 A 的誠實列舉。C 之下:①②③ 的**稽核面由 ledger 補上**;
> 仍未收回的是「讓路那一刻本身」的結構性不可覆寫(那要 B 才有,C 只保證 L5b 側的紀錄不可覆寫)。

1. **沒有原始觀察證據**:日後客訴爭議「你們憑什麼判定要退/不退」,我們手上只有
   `reason` 兩個值的分類標籤,沒有當時 Record 回了什麼。
2. **write-once 是寫入端自律不是結構性質**:閘⑥ 擋覆寫,但那是 RPC 裡的一行 WHERE;
   繞過 RPC 直接 UPDATE 就能改(`SOLE-WRITER` 偵測器只掃 `public` 函式面,跨 schema/trigger/
   動態 SQL 全盲——L5a-1 檔頭已縮窄過這個宣稱)。
3. **看不到重試史**:一筆 attempt 若因任何原因被讓路兩次(目前閘⑥ 讓它不可能,但那是自律),
   我們只會看到最後一次。

⇒ **這三條列為 backlog 候選**,若日後真的出現爭議或需要稽核鏈,再開 B 案;
那時它是「補稽核」的獨立片,不是 L5b 的前置。

## 6. 🔴 需要 Sean 拍嗎?**C 之下判不需要**(理由已換,v1 那版不成立)

**C 沒有那個問題**:它從第一天就把決策與觀察記下來,不放棄任何東西。

判準逐條:

- 資料:✅ **純新增一張表**,不動任何已 apply 的既有表與欄。

⇒ **設計形狀可自裁**。⚠️ 但 **apply 仍要 Sean 批**(新表=schema 變更,鐵則 12③,既有規矩不變)。
⚠️ 若日後有人主張改回 B(動已 apply 的錢面表)——**那必須排 Sean**,這條保留。

## 7. 對 L5b 片級 plan 的直接影響(v1 只有三條,漏了整個退款安全面)

**認人與判定**
- 認人來源 = `payment_charge_attempts.superseded_at IS NOT NULL AND status='released'`。
- **不得**把 `superseded_by_order_id` 當受益單做金額/歸屬推論(L5a-1 檔頭硬契約)。
- 退款判定**必須**基於**當下** Record 觀察,不得基於 `superseded_reason`(§3)。

**🔴 退款安全(審查 MF5;C 案的 ledger 正是這些東西的落腳處)**
- **強識別**:Record 比對必須用強鍵;弱識別(rec 與 bank 皆 null)**歧義即 fail-closed 不退**
  (`settle-charge.ts:109` 已逐字說明弱識別不能安全判斷)。
- **併發 claim**:兩個 worker 同時處理同一筆 ⇒ 必須有 DB 層唯一的「退款意圖 / claim 狀態」,
  不能靠應用層自律。
- **持久化冪等鍵**:🔴 TapPay refund 鍵**消耗恆久無 TTL**(memory
  `reference_tappay-refund-api-multiple-partial-and-overrefund`)⇒ 重試**必須換鍵**,
  而換了哪些鍵、每個鍵的結果,要 durable 記著——**這就是 ledger 的主要用途**。
- **逾時後先對帳再重試**:退款呼叫逾時(送出了但沒收到回應)**不得直接重試**,
  必須先走 Record 對帳確認上一次到底成立沒有;`6002` **不等於錢沒動過**(同上 memory)。
- ⇒ ledger 的最小欄位:attempt id / 當下 Record 快照 / 決策 / 冪等鍵 / 呼叫結果 / 時間。
