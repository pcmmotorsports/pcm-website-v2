## §2 L4:撞窗即時對帳(件②)

**現況**(母 plan §1.1 實測):per-user 閘 10 分鐘固定;撞窗當下**完全不裁決**;唯一提早釋鎖的路徑綁 `cart_session_id` ⇒ 換裝置無效。

**修法**:`begin_charge_attempt` 回 `user_in_flight` 時,action 層先對那張在途單跑一次 `settleCharge`;裁出 `failed`(Record 明確 -1/5、已 markFailed 釋鎖)才重試 `begin` **一次**;其餘一律照舊擋。

**三道護欄(缺一就從修復變成新洞)**
1. **節流**:每張在途單每 N 秒最多觸發一次 Record 查詢。🔴 已有現成基礎設施 `PgPollSettleThrottleAdapter`,**優先複用、不要新寫一套**。
2. **只放行 `failed`**:`auth_or_pending` / `record_unverified` / `record_not_found` / `record_unreachable` 一律維持擋住。
3. **重試 begin 恰一次**,不迴圈。

**預期效果與兩片的分工邊界**(P-251-A ② 要求寫清楚):
- **L4 管的是「撞到窗的當下能不能靠對帳裁出終態」** —— 客人**按取消**時 Record ≤1 秒轉 `5 CANCEL`,
  L4 裁出 `failed` → 釋鎖放行。這條零風險(明確終態,不需要補償)。
- **客人直接關掉分頁**時 Record 仍是 `4 PENDING`,L4 裁不出來 ⇒ **由 L5a 的新結帳讓路承接**
  (標 superseded + 釋鎖 + 放行 + 掛補償盯梢)。
- ⇒ 零等待上線後,**兩型都是零等待**,差別只在「靠哪一條路達成、要不要補償」:
  取消型走 L4(無補償)、關頁型走 L5a(有補償)。
⚠️ 驗收文案不得寫成「L4 讓所有情況都能馬上重刷」—— 那會讓 L5a 的補償責任被誤讀成不存在。

## §3 L5:殭屍裁定 + 事後補償(件③,Q9=A)

### 3.1 讓路的**兩個**觸發點(v2 核心改動)

**觸發 A —— 客人發起新結帳的當下(主路徑、零等待)**

```
客人重新加購物車 → 下單 → begin_charge_attempt
  撞到 per-user 閘 / cart dedup 而擋下時,不再直接回 user_in_flight,改為:
    1. 對那張在途單做一次**新鮮 Record 觀察**(不吃任何快取欄位)
    2. 觀察結果分流:
       · 明確終態 -1/5     → markFailed 釋鎖 → 放行(這條 L4 已有,零風險)
       · paid / AUTH        → 不放行,顯既有單(客人其實已經付成功了)
       · 查無 / 恆 4 PENDING → 🔴 **讓路**:標記 superseded + 釋鎖 + 放行新單
                                 ← 同時把它掛進補償盯梢
    3. 鎖下重驗 status='pending' 且 order 仍 unpaid(TOCTOU 契約)
  ⇒ **沒有年齡條件**。客人關掉頁面後隔 3 秒回來重下單,也走得通。
```

**觸發 B —— 排程(降級為歸檔用途;去留=本 plan 的裁量,我裁「保留」)**

理由:觸發 A 只在「客人自己回來」時發生。**再也沒回來的單**若沒有 B,會永遠停在 pending
⇒ 對帳簿永久雜訊 + `needs_manual_review` 天花板那條路仍在。
⇒ **保留 10 分鐘 cron,但它不再承擔「擋雙扣」職責**,只做收斂與歸檔;
   它釋鎖時**同樣**要標 superseded、同樣掛補償盯梢(兩條路徑共用同一段程式碼,不各寫一份)。

🔴 **風險已經改變,寫在這裡以免有人照 v1 估**:v1 只有超過 10 分鐘的單會被讓路;
v2 是**每一次客人重新下單**都可能產生一筆待補償的舊授權 ⇒ **補償機制的觸發頻率顯著變高**,
它的正確性從「保險」升級成「主要防線」。§4 的「L5b 單獨審查」因此不是建議,是必要。

🔴 **兩型都讓路**(Q7):`record_not_found` 與「恆 `4 PENDING`」的放棄型都要處理。
🔴 **不得只憑 `last_settle_error` 放行**(L2 檔頭硬契約):那一欄只有 sweeper 的 stuck 路徑會寫,callback/preflight 完全不落欄 ⇒ 會停在舊觀察上。**釋鎖前必須有自己的新鮮觀察。**
🔴 **不鎖新單**(Sean 逐字):客人重新加購物車 → 直接下單要走得通。
🔴 **不變量**:新單 = 新 orderId + 新 attempt,**絕不對 cancelled 單掛新 attempt**(L3a 檔頭已寫;違反 ⇒ 三處擋人查詢立刻漏)。

### 3.2 補償盯梢(這片的核心,也是最危險的部分)

被 L5 清掉的 attempt **不是就此丟掉**,而是進**長期低頻對帳**;一旦觀察到它後來轉 `AUTH` 或已請款 ⇒ **自動全額 refund**。

🔴 **自動退款的觸發條件必須極嚴,寧可漏退也不可誤退。**
誤退的後果**比雙扣更糟**:客人付了錢、訂單成立、貨可能已出,我們卻把錢退回去。
⇒ 條件必須包含一個 **durable 標記**「這筆是被 L5 自動裁定放行的」。
⚠️ **不能只看 `attempt.status = 'released'`** —— 既有 preflight release CAS(客人自己按重新付款)也會產生 `released`,那些不在本片授權範圍內(見 §6 未涵蓋)。

**冪等**(既有實測紀律,memory `reference_tappay-refund-api-*`):
- refund 的 `bank_refund_id` **恆久消耗、無 TTL** ⇒ **重試必換鍵**;
- 反面用途:`at-most-once` 可依賴 ⇒ 同一把鍵重送不會退第二次;
- 需要 durable 記錄「這筆已補償過 / 用了哪把鍵 / 結果」,否則重試會換鍵再退一次 = 退兩次。
- 🔴 `6002` **不等於**錢沒動 ⇒ 走 Record 對帳確認,不看回應碼下結論。

**盯多久**:L1b 實測 20 分鐘後仍可能成功、**上界未知** ⇒ 盯梢**不設短期上限**,跟著既有 sweeper 的低頻節奏走到 terminal 為止。

### 3.3 對客體驗口徑(Sean 已確認,寫進驗收)

> 按取消 = 馬上可重刷;**關掉頁面、重新加購物車 = 一樣馬上刷得過(零等待)**;
> **錢永遠不會真的少**(可能一扣一退、退款隔日生效)。

⚠️ **v1 的「放置=最多等 10 分」已被 P-250-A 推翻**,那句話不要再出現在任何對客文案或驗收條件裡。

## §5 測試設計(反恆真;每條守門配自己的突變)

1. **L4 只放行 `failed`**:五種 settle outcome 各一條負測,只有 `failed` 放行。突變:讓 `auth_or_pending` 也放行 ⇒ 只紅一條。
2. **L4 節流真的生效**:連按兩次 ⇒ 第二次不得再打 Record。🔴 斷言要數 **Record 呼叫次數**,不是數回傳值(兩次回傳一樣 = 量錯東西)。
3. **L5a 三岔各自可殺**:終態 -1/5 → 放行 / paid·AUTH → 不放行顯既有單 / 查無·恆 PENDING → 讓路,
   三條各一個突變、各自只紅對應那條。🔴 特別是**中間那條**:把 `AUTH` 也當成可讓路 ⇒ 會對「客人其實
   已經付成功」的單放行新單 = 真雙扣且無補償依據(補償只認 superseded 標記),這條必須有自己的負測。
4. 🔴 **零等待**:構造「舊 attempt 建立 3 秒前、狀態 pending」⇒ 新結帳必須**走得通**。
   突變:加回任何年齡條件 ⇒ 這條紅(釘住 Sean 的逐字要求,防止有人「順手加個保險」把它改回等待)。
5. 🔴 **L5b 誤退防線**:構造「沒有被自動裁定標記、但後來轉 AUTH」的 attempt ⇒ **不得**被退。
   突變:把 durable 標記條件拿掉 ⇒ 這條必須紅。**這是本片最重要的一條測試。**
6. 🔴 **冪等**:同一筆補償跑兩次 ⇒ 只退一次、第二次認得出「已補償過」。
   突變:拿掉 durable 帳 ⇒ 退兩次、該條紅。
7. **觀測性**:每次自動裁定與每次自動退款各留一行零 PII log(`orderId` / `attemptId` / 原因 / 金額不入 log 的前提下記筆數與結果碼)。沒有它,「補償機制在跑」與「它死了」在觀測上一樣。
