## 0. 🔴 先講一句會改變你判斷的:**「帶單號」不是改文案**

```
現在那支告警程式【拿不到單號】—— 不是沒寫，是【取不到】：
  check-anomaly-alerts.ts:18 逐字
    「reader 走 payment_confirmer SECDEF 受控窗、**對 anomaly 兩表零表權**；
      回傳**只計數、零 PII/零金額/零 id**」
  而那支 RPC `get_payment_anomaly_alert_summary` RETURNS jsonb，裡面**全是 count(*)**
  （20260701130000:43-95 逐行看過）
⇒ 🔴 **沒有任何 id 出得來。**
```

### ⇒ 所以這一片要動 **migration**,而它命中三條鐵則
```
12⑤ 對外發送（LINE 推播）      ← 原本就知道
12② 權限（要讓那個受控窗回 id）← 🔴 新的
12③ DB 結構（改那支 RPC）      ← 🔴 新的
⇒ 標準片、9 步 SOP 全走、commit 前 codex 對抗審查
```

### 🔴 而「零個資」是**刻意的設計**,不是漏寫
```
理由（原設計）：LINE 訊息會留在手機、可能被轉發/截圖
⇒ 而 Sean 2026-08-19 在收到一封他看不懂的告警之後【親自推翻它】
⇒ 他採納的理由：**沒單號他查不到，那則告警等於只說「有事」**
   ⇒ 而一個看不懂又查不到的告警，兩週後會被當成背景噪音
📌 **這一段要寫進 commit body** —— 下一個人要知道那道閘是【被誰、為什麼】打開的，
   而不是以為有人忘了它存在。
```

## 3. 🔴 三個要你拍的(而它們會改變做法,不是潤飾)

### Q1 · **多筆的時候長什麼樣**(現在是 1 筆,而 5 筆時不能變成五段)
```
甲 列前 3 筆單號 + 「另有 N 筆」  ⇒ 訊息長度有上界，而他一眼看得到最急的
乙 只給總數 + 一句「請到後台看」  ⇒ 最短，而他還是得自己去找是哪幾筆
👍 我建議甲，理由：他要的就是「哪一筆」，而乙等於把問題退回原點
```

### Q2 · 🔴 **兩類共用一個計數,而它們的處置不同 —— 要不要分開講**
```
現況：那個計數是【pending 孤兒】∪【被讓路轉人工】的聯集
而 code 註解逐字：「兩者的處置完全不同：前者查 Record 對帳、後者是『錢被讓給另一張單』要走退款線」
🔴 而我【沒有查出】怎麼從資料上乾淨分辨這兩類（兩條路都是 count>=8 轉人工，寫在同一個欄）
⇒ 甲 帶了單號之後【不分類】—— 他點進那一筆就看得到細節，分類是後台的事
   乙 先把分辨方法查清楚，訊息裡分兩句寫
👍 我建議甲，理由：**單號本身就把分類問題溶掉了** —— 而乙要先做一份我還沒做的查證
```

### Q3 · **要不要保留一句「先查清楚再退款」**
```
現況那封有「皆為候選、待查證，勿直接退款」⇒ 白話但重要
👍 我建議保留（草稿已含），理由：那是唯一一句在防【動錯錢】的
```
