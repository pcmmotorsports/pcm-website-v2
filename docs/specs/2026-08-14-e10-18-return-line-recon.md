## §2 已出貨的**量**要退,取消線走得到哪一步?**那些量一步都走不到。**

`apps/admin/src/lib/orders/cancel-view.ts:217` 逐字:「可取消量 = `quantity − instock − cancelled`,
而 **`shipped ⊆ instock`**(Sean 2026-08-05 拍板)」。
⇒ 已出貨 ⊆ 已到貨 ⇒ 那些量**從可取消量整份扣掉**。全出貨的單每項可取消量 = 0
⇒ 觸發 `cancel-view.ts:147` 的 `nothing_cancellable` ⇒ 畫面吐 `:118` 那句 hint。

🔴 **這是閉環的死路,不是「還沒做的功能」**:取消線**刻意**把已到貨擋掉(`20260730150000:119`),
把責任交給退貨線;退貨線不存在 ⇒ **已出貨的那些量在後台完全沒有出口**。

⚠️ **第二版更正範圍(C 窗 M3)**:第一版結論句寫「已出貨的**單**沒有出口」= **過度概化**。
照上面那條公式,買 5 / 到貨 2 / 已取消 2 的單,可取消量 = 1 > 0 ⇒ **部分出貨的單走得到取消線**;
**`nothing_cancellable` 是整單級的**:`cancel-view.ts:147` 逐字「**每個品項的尚可取消量都是 0** ⇒ 整單模式與部分模式都送不出去」。
⚠️ **而「全數到貨」不是唯一的歸零路徑** —— `cancelled` 也參與那條公式(`instock=3 / cancelled=2 / quantity=5` 同樣是 0)。
本段自己那個 5/2/2 的例子正好證明這件事,**我第三版原本那句「只有全數到貨才觸發」與自己的例子相衝,已改。**
🔴 **我內文寫對了(「全出貨的單」)、結論那句寫錯** —— 而下游引用的是結論句。
**正確講法:沒有出口的是「已到貨/已出貨的那部分數量」,不是整張單。**

## §3 貨的軸與退貨的關係(只列事實,不選)

四個計數欄都在 `order_item_quantity_summary`:`ordered` / `instock` / `cancelled` / `shipped`,
關係由具名 CHECK 釘死:`oiqs_instock_le_ordered`(`20260730150000:113`)、`oiqs_shipped_le_instock`(`20260806100000:144`)。

| 記法 | 動作 | 會撞到什麼 |
|---|---|---|
| ① 下修 `instock` | 退回 = 當作沒到貨 | `shipped <= instock` 會擋 ⇒ **必須同時下修 `shipped`**。`shipment-candidates.ts:57` 已預期這條路 |
| ② 新增第五軸 `returned_quantity` | 只加一筆、不動既有四軸 | 不撞現有 CHECK,但要新增欄 + 新不變式,且**四軸的既有讀者要不要扣掉它,每個都要回訪** |

🔴 **既有機制最接近的 = `admin_delete_item_receipt`**(呼叫端在 `receipt-repository.ts:250`)——
現行唯一會下修 `instock` 的路徑。

⚠️ **第二版更正(C 窗 M2):我把硬擋講成了軟風險。**
第一版寫「拿它當退貨用會讓**帳查不出真相**」——語氣像是做得到但不乾淨。**實際上根本做不到。**
`20260810233000:458-459` 的 `COMMENT ON FUNCTION` 逐字:
「🔴 **唯一守門 = 刪除後 `instock` 不得低於「已出貨 + 已裝進未出貨包裹」;不成立回 `P4A03`** 並列出全部相關包裹。」
⇒ **已出貨的量被守門擋在外面,連拿它當退貨用都做不到。**
🟢 **這反而讓 §2 的死路結論更硬**:取消線擋、`delete-receipt` 也擋 —— **兩條既有出口都關著。**
(語意層那句仍成立:它是「到貨登記錯了、撤銷登記」,不是「貨真的回來了」。)
⚠️ 而 `#498` 說它對「作廢的採購」還沒有分流(卡在 Sean 桌上)⇒ 它自己也還沒收乾淨。
