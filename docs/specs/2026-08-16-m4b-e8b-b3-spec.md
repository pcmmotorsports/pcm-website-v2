### 2.2 ✅ **plan v4 §8 依賴的那個機制,已實查證實**

plan v4 §8 寫:「**靠版本欄 `v:2` 擋(舊 validator 見 v=2 直接 reject)**,

**兩邊的 validator 逐字都是 `if (o.v !== 1) return false;`**:
- 報價單 `lib/session.ts:110`
- admin `apps/admin/src/lib/session/session.ts:110`

⇒ **`v:2` 的 cookie 會被舊 validator【硬拒】,不是被忽略。**
⇒ **plan 那條 rollback 策略成立,而且現在有證據,不是假設。**

### 2.3 ⚠️ 而 plan §8 另一句要**加限定**

plan `:238` 寫「報價單 `isPayload()` **容許額外欄**」——
**那句對,但它只在「不動 `v`」的情況下才是風險**:
`isPayload` 逐欄檢查、**不拒絕未知的 key**(`lib/session.ts:107-118`)
⇒ 若 B3 只加 `sub` 而**不**把 `v` 升到 2,舊 validator 會**靜默忽略 `sub`**,
而 cookie 仍然有效 ⇒ **那正是「靜默退回無身分語意」。**

**⇒ `v:2` 不是可選的,它是唯一擋住這個退化的東西。**
🔴 **本片不得只加欄不升版。**

## §3 `sub` 的形狀(plan §7-Q1=A 拍板)

```ts
type SessionSub =
  | { kind: 'user';     staff_id: string }   // 真人登入
  | { kind: 'fallback' };                    // 備援共用密碼登入（Q2=A 保留）
```

🔴 **型別上不存在「沒有 `sub` 的 v:2 session」** —— 這是 plan `§7-Q1=A` 的原話,
它的意思是:**備援路徑不是「沒有身分」,是「一種明確的身分」。**
⇒ 若寫成 `sub?: …`(可選),那個「不存在」就沒有了 ⇒ **必須是必填的 union。**

**`staff_id` 的值域**:與 B1-b 的 CHECK 白名單同一組(`sean` / `staff_1` / `staff_2`)。
⚠️ **兩邊各自硬編碼會漂**(A 庫改了名單、這裡沒改)⇒ **本片要決定一個單一來源**,見 §7-1。

## §4 順序:B3 **必須在 B2 之後**

```
B1-b  建映射表（空）
B2    塞三列（Auth user ↔ staff_id）
B3    session 帶 sub          ← 本片
```
**理由**:`sub.staff_id` 的值要從**映射表**查出來。B2 之前那張表是空的
⇒ 登入成功但查不到 staff_id ⇒ **要嘛簽出一個沒有身分的 v:2(型別上不允許)、要嘛整個登入失敗。**
🔴 **兩種都不能接受,所以順序是硬的。**

## §5 混版部署(這片最容易出事的地方)

兩個 repo 分開部署 ⇒ **四種組合都會真實發生**:

| 報價單(簽發) | admin(收) | 會發生什麼 | 可接受嗎 |
|---|---|---|---|
| 舊 v:1 | 舊 v:1 | 現況 | ✅ |
| **新 v:2** | **舊 v:1** | admin 的 `o.v !== 1` **硬拒** ⇒ **所有人被登出** | ⚠️ **要規劃,不能撞上** |
| 舊 v:1 | **新** | 新 admin 收到 v:1 ⇒ **必須決定:接受(過渡)還是拒絕** | 見下 |
| 新 | 新 | 目標狀態 | ✅ |

🔴 **決定(本規格拍,不佔 Sean 時間):新 admin 的 validator【同時接受 v:1 與 v:2】,
但 v:1 一律視為「無身分」,而在 `ADMIN_REQUIRE_REAL_IDENTITY` 開關打開之後【拒絕 v:1】。**

**為什麼**:
- 過渡期要能同時活著(否則部署順序稍差就全員登出)
- 而開關打開 = 我們宣告「從現在起身分是必需的」⇒ 那一刻 v:1 就該死
- 📎 這讓 §5 那個「開關開著而 session 沒帶身分」的驗收格(plan §6-6)**有東西可測**

⚠️ **部署順序因此是硬的:先部署 admin(能收兩種),再部署報價單(開始發 v:2)。**
反過來會撞上表格第二列 ⇒ **所有人被登出**。

📎 兩邊的簽章都是 `base64url(payloadJSON) + '.' + base64url(HMAC(payloadJSON))`
(`lib/session.ts:7` 檔頭註解)⇒ 只要 `sub` 在 `payloadJSON` 裡就涵蓋得到。
**而「只要」那兩個字,正是需要一格測試的地方。**

## §7.1 定案:`staff_id` 的驗證走 **(b)** —— 而查完之後發現**它已經實作好了**

### 決定(一句)

> **B5 收到 `sub.staff_id` 之後,必須把它丟進 `resolveStaff()`,不得直接使用。**
> **admin 端不持有任何 `staff_id` 白名單。**

### 🔴 為什麼這不是「少做一道檢查」—— 兩個問題,兩個地方,不是重複

| 問題 | 誰是權威 | 在哪 |
|---|---|---|
| **誰【可以被綁定】帳號** | 報價單庫 `admin_user_staff_map` 的 CHECK | B1-b |
| **誰【現在可以操作】** | **A 庫 `staff` 表的 `is_active`** | 既有的 `resolveStaff()` |

**這兩個問題不同,所以兩個地方不是「同一份清單抄兩次」。**
⇒ (c) 共用常數檔會把它們**合併成同一份**,而那正是 house 教訓「兩處硬編碼會漂」的形狀。

### ✅ 而 (b) 需要的東西 **repo 裡已經有了**(2026-08-16 實查)

```
apps/admin/src/lib/session/actor.ts:32   getSessionActor() → resolveStaff(…)
apps/admin/src/lib/staff.ts:38-43        resolveStaff(id)  → pickStaff(await listActiveStaff(), id)
apps/admin/src/lib/staff.ts:25-35        listActiveStaff() → 讀 staff 列、**filter(is_active)**
apps/admin/src/lib/staff.ts:16-22        pickStaff()       → 找不到就 null
```
⇒ **一次查詢同時給三件事:**
1. **成員資格**(不在 A 庫 `staff` ⇒ null)
2. **存活**(`is_active=false` ⇒ 被 filter 掉 ⇒ null)
3. **fail-closed**(`listActiveStaff` 在 DB 失敗時回**空陣列** ⇒ 一律 null,`staff.ts:31-34`)

🔴 **⇒ 我先前釘給 `B5` 的那條 R2 finding(「每次用的時候重新確認 `is_active`,不可只在綁定當下驗一次」)
【現有這條路徑已經滿足】** —— 只要 B5 不繞過它。

📎 **形狀值得記**:我本來要為 B3 設計一套新的驗證機制,
**而正確答案是「不要繞過既有的那一條」。**
⇒ **判別句:我要加的這道檢查,現有的哪一條路徑已經在做了?**

### 為什麼不是 (a):admin 啟動時讀一次

- **啟動期相依**:讀失敗 ⇒ 要嘛啟不動、要嘛拿著空白名單啟動(fail-open 或 fail-closed 都難處理)
- 🔴 **更關鍵:它是【快取】** —— 而 `is_active` 是**會變的**。
  啟動時讀一次 ⇒ **一個離職員工在下一次重啟前都還是「有效」的**
  ⇒ **這正好把「每次用的時候驗」退化回「綁定那一刻驗」**,而那是 R2 抓到的原病。

### 為什麼不是 (c):共用常數檔

- **兩處硬編碼必然漂**:A 庫加了人而常數檔沒改 ⇒ 那個人登入後被當成未知
- 🔴 **而漂的方向是靜默的**:常數檔不會因為 A 庫改了而紅
- 📎 house 教訓原句:**「兩份會漂」** —— 而 (c) 是製造第二份的唯一一案

### ⚠️ (b) 的代價,寫下來不掩蓋

1. **每次操作多一次 DB 查詢**(`listActiveStaff`)。
   ⇒ 現況已經如此(`getSessionActor` 本來就這樣),**本片不引入新成本**。
2. 🔴 **DB 失敗時,所有人都變成「未知身分」而不是「系統錯誤」** ——
   `listActiveStaff` 逐字「DB 失敗時回空陣列並留 server log」(`staff.ts:24`)。
   **方向是安全的(fail-closed),但症狀會是「全公司突然都沒權限」而不是「資料庫掛了」。**
   ⇒ **本片不改它**(改它是另一個決定),但**列在這裡**,免得那天有人查半天。
