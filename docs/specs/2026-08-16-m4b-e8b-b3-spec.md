## §3 `sub` 的形狀(plan §7-Q1=A 拍板)

```ts
type SessionSub =
  | { kind: 'user';     staff_id: string }   // 真人登入
  | { kind: 'fallback' };                    // 備援共用密碼登入（Q2=A 保留）
```

🔴 **型別上不存在「沒有 `sub` 的 v:2 session」** —— 這是 plan `§7-Q1=A` 的原話,
它的意思是:**備援路徑不是「沒有身分」,是「一種明確的身分」。**
⇒ 若寫成 `sub?: …`(可選),那個「不存在」就沒有了 ⇒ **必須是必填的 union。**

**`staff_id` 的值域**:與 B1-b 的 CHECK 白名單同一組(`sean` / `staff_1` / `staff_2`)。
⚠️ **兩邊各自硬編碼會漂**(A 庫改了名單、這裡沒改)⇒ **本片要決定一個單一來源**,見 `docs/specs/2026-08-17-m4b-e8b-b5-spec.md` §7.1(2026-08-17 搬走,原寫「見 §7-1」已是跨檔)。
🔴🔴 **「單一來源」≠「一份共用清單」(codex R3 `must-fix`,2026-08-17 補;不補的話這句會把人導向相反實作)**:
**`docs/specs/2026-08-17-m4b-e8b-b5-spec.md` §7.1 已明文拒絕 (c) 共用常數檔** —— 定案是**每個問題各自指向【它自己的權威】**
(綁定 → 報價單庫 CHECK;在職 → A 庫 `is_active`),**不是把兩張清單合併成一份放在中間**。
⇒ 讀到「單一來源」四個字要接著讀下面那張表,**不要去建一個新的共用檔**。

> 🔴🔴 **「白名單」這三個字在本檔指兩張不同的清單,不要當成同一張(codex `#9`,2026-08-17 折)**
> codex 逐字:驗收要求拒絕白名單外 `staff_id`,後文卻禁止 admin 持有白名單
> ⇒ **施工者只能複製 DB CHECK 或無法完成驗收,執行位置未定。**
>
> | 這張清單 | 是什麼 | 權威在哪 | **誰執行、在哪一刻** |
> |---|---|---|---|
> | **綁定白名單** | 誰**可以被綁定**成 `staff_id` | 報價單庫 `admin_user_staff_map` 的 **CHECK**(B1-b) | 🔴 **寫入映射列的那一刻**(該表的 `INSERT` / `UPDATE`)—— **不是簽發 session 的那一刻** |
> | **在職名單** | 誰**現在可以操作** | **A 庫 `staff` 表的 `is_active`** | **收端(B5),每次用的時候**,走既有 `resolveStaff()`(`docs/specs/2026-08-17-m4b-e8b-b5-spec.md` §7.1) |
>
> 🔴 **admin 端【永遠不持有】綁定白名單** —— 它拿到 `sub.staff_id` 之後做的是 `resolveStaff()`,
> 那查的是**在職名單**,不是綁定白名單。**兩張清單各自有權威,不互相抄** ⇒ 這正是 `docs/specs/2026-08-17-m4b-e8b-b5-spec.md` §7.1 拒絕 (c) 共用常數檔的理由。
>
> ⛔⛔ **本表 2026-08-17 第一版把執行時機寫錯,同日修正(codex R2 `must-fix`)**
> 原寫「綁定白名單在**報價單側、簽發 v:2 的那一刻**執行」—— **不成立**:
> 🔴 **簽發時做的是 `SELECT`,而 `SELECT` 不會重跑 `CHECK`。**
> `CHECK` 只在**那一列被寫進去**的時候擋;簽發端讀到什麼,取決於那一列**當初**寫進了什麼。
> ⇒ **簽發端該做的是**:依**已驗證的 `auth_user_id`** 精確查出 `staff_id`;
>   **查無 / 不是恰一筆 ⇒ 該次登入失敗**(§4)。**它不比對任何清單。**
>
> 🔴🔴 **而這留下一個【未決】,我不假裝它被折掉了**:
> **§6 第 6 格要驗的「`staff_id` 不在綁定白名單 ⇒ 拒絕」,在 runtime 沒有執行者。**
> 若 `CHECK` 成立,那個狀態**構造不出來**(⇒ 該格恆綠、零判別力);
> 若要讓它在 runtime 真的擋(防 `CHECK` 漂移 / 繞過 / 直接改庫),**就必須另定一道應用層驗法**,
> **而那道驗法需要一份清單 —— 等於把 (c) 共用常數檔那個「兩份會漂」的病請回來。**
> ⇒ **這是取捨,不是漏寫;歸 plan 層決定,`#9` 記為【未折】。**

## §4 順序:B3 **必須在 B2 之後**

```
B1-b  建映射表（空）
B2    塞三列（Auth user ↔ staff_id）
B3    session 帶 sub          ← 本片
```
**理由**:`sub.staff_id` 的值要從**映射表**查出來。B2 之前那張表是空的
⇒ 登入成功但查不到 staff_id ⇒ **要嘛簽出一個沒有身分的 v:2(型別上不允許)、要嘛整個登入失敗。**
⛔ ~~**兩種都不能接受,所以順序是硬的。**~~
🔴 **上面這句 2026-08-17 已修正,不要照它讀** —— 「整個登入失敗」**是正確的 runtime 結果**,
**不能接受的是【營運上停在那個狀態】**。**正解在下面這個框裡,不要跳過。**

> 🔴🔴 **「不能接受」的主詞是【營運狀態】,不是【runtime 行為】(codex `#10`,2026-08-17 折;
> 原句未加刪除線 ⇒ 跳過本框的人會讀到相反結論,codex R3 `must-fix`,同日補刪除線)**
> 原句只寫到這裡就停,而 codex 逐字指出:**「個人密碼驗證成功但映射查無/逾時 ⇒ 正確安全結果就是登入失敗」**
> —— 我把那個**正確結果**寫成「不能接受」,而規格又**沒有禁止**任何替代作法
> ⇒ **照字面做的施工者會去發明一個「比登入失敗好」的行為。**
> ⚠️ 我**沒有窮舉**他會發明出什麼(數不出來、也不假裝數得出來);
> 下面只**明文禁止我想得到的三條**(codex 點名兩條 + fail-open 一條),**這張禁止清單不是窮舉**
> ⇒ **不在清單上的變通,一律回來問,不得自行判定「這條不算」。**
>
> **⇒ 本片的硬規定,拆成兩層,不要混:**
>
> | 層 | 規定 |
> |---|---|
> | **runtime(不可違反)** | 映射**查無 / 逾時 / DB 例外** ⇒ **該次登入失敗,fail-closed**。這是**正確結果,不是待改善項**。 |
> | ↳ **這一列不禁止的事**(codex R2 `nit`) | **同一次請求內的有限次重試(bounded retry)沒有被禁止** —— 本列管的是「**重試用完之後**」:那時**必須失敗**,不得改走別的身分。⇒ **不要把這列讀成「第一次逾時就不准再試」。** |
> | **排程(所以順序是硬的)** | 不希望**營運上**進入「人人登入失敗」那個狀態 ⇒ 所以 **B3 必須排在 B2 之後**。 |
>
> 🔴 **明文禁止(三條,施工者不得自行變通)**:
> ① **不得**在映射查無時改簽 `kind:'fallback'` —— fallback 是**一種身分**(§3),不是「查不到時的退路」;
>    那等於讓「映射壞掉」自動取得備援權限。
> ② **不得**採用 client / 請求端傳入的 `staff_id` —— 它必須來自**報價單側查映射表的結果**。
> ③ **不得**把 DB 逾時/例外當成「暫時放行」 —— 見 `docs/specs/2026-08-17-m4b-e8b-b5-spec.md` §7.1「兩個世界長得一樣」那段,
>    fail-closed 的代價已經寫在那裡,**代價是知情接受的,不是拿來換 fail-open 的理由**。

### 5-B 真正的跨 repo fail-closed 點:**`amr` enum**(V 窗 `F-1` 指出的那個)

跨 repo 會互相咬到的欄位,依 `apps/admin/src/lib/sso/exchange.ts:7` 的合約逐字有**兩個**:`amr` 與 `auth_time`
(數法:`grep -n 'ok:true' apps/admin/src/lib/sso/exchange.ts` ⇒ 回應形狀就那一行)。
⛔ **本節第一版寫「會咬到的只剩 `amr`」—— 錯,codex 2026-08-17 抓。`auth_time` 一樣會咬:**
`parseAuthTime()`(`exchange.ts:39-46`)只收 `number` 或**純數字字串**,且要 `0 < n <= now+30`
⇒ 報價單若改送 ISO 字串、毫秒、或時鐘快超過 30 秒 ⇒ 回 `null` ⇒ `exchange.ts:84` `if (authTime === null) return null`
⇒ **同樣是登入失敗**。⇒ **兩個欄位都是跨 repo fail-closed 點,而兩個都沒有版本號在保護。**

以下先講 `amr` 這一半(`auth_time` 那一半見本節末):

| 在哪 | 逐字 | `檔案:行號` |
|---|---|---|
| 報價單(送出端) | `type SessionAmr = 'pwd' \| 'totp' \| 'bootstrap' \| 'recovery'` | `~/API大量上架/PCM報價單-V2` `lib/session.ts:11`(`origin/main` = `482bec5`;2026-08-17 當場 `git fetch` 後只讀 origin/main) |
| admin(收下端) | `type AdminSessionAmr = 'pwd' \| 'totp' \| 'bootstrap' \| 'recovery'` | `apps/admin/src/lib/session/session.ts:20` |

**兩邊目前逐字相同。** 而 `apps/admin/src/lib/sso/exchange.ts:11` 逐字寫著:
「`amr` admin 端自驗(**報價單 exchange 直透 DB 值、無白名單**)」
⇒ 報價單**不過濾**,admin 才過濾(`exchange.ts:81-82`:`const amr = sanitizeAmr(rec.amr); if (!amr) return null;`)。

🔴 **後果:報價單若新增一個 amr 值(例如 `passkey`)而 admin 還沒加進 enum ⇒ 那次登入直接失敗。**
⛔ **本節第一版寫「admin 濾掉它;若過濾後為空才失敗」—— 錯,codex 2026-08-17 抓。它根本不過濾。**
`sanitizeAmr()` 逐字(`apps/admin/src/lib/sso/exchange.ts:33-35`):
「🔴 fail-closed(Fable/Codex MF1):**任一元素不在 enum → 整包拒**(非靜默過濾降級)」
⇒ `['pwd','passkey']` **也會失敗**,不需要「只剩一個未知值」這種條件。
⇒ **失敗面比我原本寫的大得多**:只要那次登入的 amr 陣列裡出現一個 admin 不認得的值,那個人就登不進去。
📎 而這個「整包拒」是**刻意設計的**(註解自述是 Fable/Codex 的 must-fix 修法),不是 bug ——
   它換來的代價就是上面那條硬順序。
⇒ **這就是真正的跨 repo fail-closed 點。** 方向是安全的(擋住而不是放行),
   但它**擋的是登入本身**,而且**沒有任何版本號會先警告你** —— `v` 保護不到它。

**`auth_time` 那一半(同族,合約同樣沒有版本號)**

| 送出端 | 收下端的要求 | `檔案:行號` |
|---|---|---|
| 報價單 `exchange` 回 `auth_time` | `number` 或**純數字字串**;`Number.isSafeInteger` 且 `0 < n <= now+30` | `apps/admin/src/lib/sso/exchange.ts:39-46` |

🔴 報價單若改送 ISO 8601、毫秒、或它的時鐘比 admin 快超過 30 秒 ⇒ `parseAuthTime` 回 `null`
⇒ `exchange.ts:84` ⇒ **登入失敗**。方向一樣是安全的,一樣**沒有版本號會先警告**。
⚠️ **時鐘那一項我未量**:兩邊實際的時鐘偏差多少、有沒有 NTP,我沒查 ⇒ 這是「理論上會咬」不是「量到會咬」。

⚠️ **硬順序(跨 repo 這一軸)**:**先在 admin 的 enum 加新值並部署,再讓報價單開始送。**
(`auth_time` 同理:先改 admin 的 parser 再改報價單的送出格式。)
⚠️ **而 B3 這一片不動 `amr`** ⇒ 5-B 對本片**不觸發**;寫在這裡是因為原表把 5-A 誤植成跨 repo,
   **下一個人會照那張錯的表去規劃跨 repo 部署,而那張表指的方向是錯的。**
