只要一個**內嵌陣列**破千的關係即可,而 `brands → products_public` 就是:

|---|---|---|---|---|

## 1. 🔴 病根是「零訊號」,不是「上限太低」

```

## 8-原. 🔴 商品那兩面的結論 —— **量完之後,我不建議照片一原案做**

**這一節推翻的是本檔 §4「片一 · 收邊界」對【商品那兩支常數】的適用性,不是整份 plan。**

### 為什麼商品這兩面「只補 `.limit()`」是**淨負面**

```
現況    上限 1000（伺服器 max-rows）  最大 29   零訊號
只補片一 上限 N（我方常數）           最大 29   零訊號   ← 懸崖被【拉近】了
```
本檔 §4 自己就寫了這個 ⚠️(「問題從『不知道有沒有被截』變成『一定在我方常數處被截,而仍然不知道』」),
**而當時那是推論;現在檔頭那張表把它變成實測** —— 被截時**真的**只回 200、**真的**沒有任何 header 會變。
⇒ 在**沒有旗標**的前提下把上限從 1000 收到 N,**唯一的效果是讓截斷更早發生**。

### 三個選項(**我推薦甲,但這是主視窗/Sean 的裁量,我不自己拍**)

```
甲  code 零改動，只把量測值與失效條件寫進註解與本檔    ← 我推薦
乙  limit + 旗標一起做（照訂單那面的完整形狀）          ← 正確但中鐵則 8
丙  只補 limit，不做旗標                                ← 不建議，理由見上
```

**推薦甲的理由(三條,都可被推翻)**:
1. **今天最大 29,離 1000 有 34 倍**;乙要動 domain 型別 + mapper + 顯示端(鐵則 8),
   **為一個 34 倍外的狀態付這個成本**,而它的症狀是零。
2. 商品變體不是「單一客人一次操作就能撐大」的東西 —— 訂單品項可以(Sean 明答「有可能破千」),
   **變體數是上架時決定的**,要長到 1000 需要有人一款商品開一千個規格。
3. 丙會讓事情更糟(見上)。

🔴 **甲的代價要寫清楚,不能只講好處**:選甲 = **接受「若某天真的超過 1000,我們一樣不會知道」**。
⇒ 所以甲**不是「什麼都不做」**,它的產出是**那段註解**:寫上今天 29、量測時點與側別、
以及**「這個結論在什麼條件下失效」**,讓下一個讀到的人不必重量一次,也不會誤以為它被保護了。

📎 **下一個人最可能踩的**:看到 §2 表格裡商品那兩列寫著「🔴 無(上限)」就直接去補 `.limit()`。
**那張表沒有錯,但它列的是「有沒有設上限」,不是「該不該設」。**
