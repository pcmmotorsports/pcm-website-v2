## 2. 🔴 ② 這支 RPC 的 `GRANT` 給誰、什麼時候給 —— **一個設計選擇,選了一條**

**codex R1 MF5 打掉了 v1 的中心宣稱**:
> 新 public RPC 一經 `GRANT`,便立即可被既有角色經 SQL / PostgREST 呼叫。
> 「repo 沒呼叫端、flag 不存在」**不是安全閘**。

### ✅ 選 **乙:`REVOKE ALL FROM PUBLIC`,而【不 GRANT 給任何角色】。`EXECUTE GRANT` 延到 `2j`。**

**理由(而不選甲「內建預設關閉的 DB 閘」)**:
```
· 乙是【沒有能力】，甲是【有能力而自我約束】。前者不需要相信任何一行碼是對的
· 甲要多寫一個開關 ⇒ 那是第二個可能寫錯的東西，而它的失效方向是 fail-open
🔴 · 兩條都做 ⇒ 「哪一道在承重」變成不可量（主視窗 2026-08-29 指令逐字）⇒ 只做一條
· 而乙就是本 repo 既有的做法：`close_released_attempt` 逐字
  `REVOKE ALL ON FUNCTION … ` + 自檢「應 4 角色零 routine 顯式 grant;拒繼續」（20260624120010:143/:165）
```
🔴 **`REVOKE ALL FROM PUBLIC` 不是可選的** —— 新函式**預設 `PUBLIC` 可 `EXECUTE`**
(CLAUDE.md 路由表:「新物件出生就自帶 anon 權限、repo 內零 `GRANT` 字面可掃、**三綠不紅**」)。

### 🔴 驗收:**要能演反面**(不是「我沒 GRANT」而是「它真的呼叫不了」)
```
世界 A（本片交付的狀態）：以 anon / authenticated / service_role / payment_confirmer 四個角色
   各 SET LOCAL ROLE 後呼叫 ⇒ **四發全部 42501 permission denied**
世界 B（負對照，證明尺是活的）：臨時 GRANT EXECUTE 給其中一個角色 ⇒ **該發不再是 42501**
   ⇒ 然後 REVOKE 還原
```
📌 **只有世界 A ⇒「呼叫不了」與「我根本沒呼叫到那支函式」印同一個 42501。**

## 4. ④ Rollback

### 4a. 形狀:**單一交易腳本**(母 plan v8 定案,`:718`)
```
BEGIN;
  <閘：見 4b>
  DROP FUNCTION public.<2g writer>(<完整簽章>);
  <把 §1a 的兩處名單改回空陣列>
COMMIT;
```
🔴 **禁止只抄座標逐句手跑** —— 本 repo 慣例是 `psql -f` 逐句 autocommit、**無 `ON_ERROR_STOP`**
⇒ `DO … RAISE` 之後後續每一句照跑,**閘等於被滾過去**(母 plan 實跑證實)。**這句要寫進本片檔尾的 rollback 段本身。**

### 4b. 🔴 閘 —— **v1 寫「有 payment_refunds 列存在就 abort」是錯的**(codex R1 MF7)
那證不了那一列是 2g 寫的,而 `payment_refunds` **本來就會有別人的列** ⇒ **誤擋**。

**改成三道**:
```
① **來源判準**：只看【由本函式寫的】列 —— 判準本檔尚未定（見 §6-3，與回傳碼集同批定稿）
   候選：父列上記 writer 標記欄／事件表的 event 來源碼。**要定一個，不能靠推論**
② **caller 已停**：2j 若已接線，回退次序是 **2j → 2g → 2f/2e**，不得跳號
   （v1 完全沒有這一格）
③ **三態版本閘**：只接受「本片的 post-image」或「已是 pre-image」，對著陌生版本不回退
   （形制照 scripts/l5b2-2a-rollback.sql）
```

### 4c. ⚠️ 「rollback 掉本片」**不等於回到原狀**
母 plan §4b 逐字:已寫 `sent` 或落 `result_unknown` 的 refund,**錢可能已經在外面動了**。
⇒ **回退後仍必須有人對帳。**承接它的「人工佇列四件」是 `2d` 的驗收條件 —— 而 `2d` 已 apply。
⚠️ **那四件做完沒,本檔【未驗】。**

## 5. 🔴 ⑤ 那兩個空陣列的驗收 —— **v1 那發突變是恆真的**

**codex R1 MF6 逐字**:
> 2g 的**靜態 `INSERT` 本來就會被文字掃描抓到**,無法證明陣列承重。

📌 **⇒ 我昨天才在別人身上抓恆真守門,而 v1 自己在【驗收】那一格寫了一個。**

**改成兩個世界,而靶要是掃描【刻意看不到】的**:
```
靶 = 一支用【動態 SQL】寫 payment_refunds 的臨時函式（EXECUTE format(...)）
     ⇒ 文字掃描【看不到】它（那五種靜默放行形狀之一，閘自己列的）

世界 A：靶的函式名【在】名單裡 ⇒ 兩支 rollback 必須 **abort**
世界 B：把名字從名單移除、靶仍在庫 ⇒ 兩支 rollback **放行**
⇒ **A 與 B 不同 = 名單真的在承重。A 與 B 相同 = 那兩行等於沒填。**
```
🔴 **而 2g 自己的函式名要填進去的理由不變** —— 它今天是靜態 `INSERT`、掃描抓得到,
**而「抓得到」是實作細節,不是不變量**:哪天有人把它改成動態 SQL,名單就是唯一還在的那道。

> **零角色可 `EXECUTE` ⇒ 沒有任何主體能呼叫它;而 `2f` 的否決條件會從恆假變成會擋 ⇒ 員工手動退款線的行為【會】改變。**

⚠️ **而母 plan §3a-10 要求在 apply 停點對他講一句話**:`lock_timeout` 會讓員工原本「等一下就成功」的競爭**直接失敗**,而那個秒數**沒有量過**。
