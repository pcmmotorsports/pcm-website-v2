## §B5-3 件 1 · payload 型別(admin 收端要收成什麼)

### 現況(2026-08-18 當場讀)

```
apps/admin/src/lib/session/session.ts:22-32   interface AdminSessionPayload { v: 1; sid; iat; exp; amr; auth_time }
apps/admin/src/lib/session/session.ts:112     if (o.v !== 1) return false;          ← isPayload 的版本閘
apps/admin/src/lib/session/session.ts:93      return { v: 1, sid: newSid(), … };    ← buildAdminSession 硬寫 v:1
```

### 規格

**(1) 型別改成【以 `v` 為判別欄的 union】,不是在原介面上加選填欄。**

```ts
export type AdminSessionSub =
  | { kind: 'user'; staff_id: string }
  | { kind: 'fallback' };

interface AdminSessionCommon { sid: string; iat: number; exp: number; amr: AdminSessionAmr[]; auth_time: number }
export interface AdminSessionPayloadV1 extends AdminSessionCommon { v: 1 }
export interface AdminSessionPayloadV2 extends AdminSessionCommon { v: 2; sub: AdminSessionSub }
export type AdminSessionPayload = AdminSessionPayloadV1 | AdminSessionPayloadV2;
```

🔴 **`sub` 在 `v:2` 裡是【必填】,不得寫成 `sub?:`** ——
理由逐字引 `docs/specs/2026-08-16-m4b-e8b-b3-spec.md:66-69`:「型別上不存在『沒有 `sub` 的 v:2 session』…
備援路徑不是『沒有身分』,是一種明確的身分」。寫成選填 ⇒ 那個「不存在」就沒有了。

🔴 **為什麼是 union 而不是 `v: 1 | 2` 加選填欄**:union 之下,
**「拿到一個 `v:2` 卻讀不到 `sub`」在型別上構造不出來**,而選填欄要靠每個呼叫端自己記得判。
📎 這與 §7.1 拒絕 (c) 共用常數檔是同一個判準:**讓錯誤形狀不存在,勝過讓每個人記得檢查它。**

**(2) `isPayload()` 只管【形狀】,不管【政策】。**

- `o.v === 1` ⇒ 照現行五欄驗完即可(`:113-118` 不動)。
- `o.v === 2` ⇒ 五欄照驗,**外加** `sub` 必須是上述 union 的合法值:
  `kind==='user'` ⇒ `staff_id` 必須是非空字串;`kind==='fallback'` ⇒ **不得有 `staff_id` 欄以外的殘留意義**(多帶欄位照現行 `isPayload` 慣例容許,見下方 ⚠️)。
- 其他 `v` ⇒ `false`。

⚠️ **現行 `isPayload` 容許額外欄位**(`:109-119` 逐欄檢查、無「不得有其他欄」那一道)
⇒ **`{kind:'fallback', staff_id:'sean'}` 這種形狀在型別上不合法、在 runtime 會被放行。**
🔴 **所以判別一律用 `sub.kind`,永遠不要用「有沒有 `staff_id`」判**。
**缺的那一道**(要不要在 `sub` 上做嚴格 exact-shape 檢查)= **本片不做,明寫成缺口**;
理由:全檔沒有一個地方做 exact-shape,單獨在這裡做會與其餘欄位的鬆緊不一致,而**收益要靠「有人用 kind 以外的方式判」才兌現**。

**(3) 「哪些版本可以進來」是【政策】,住在 `verifySession()`,不住 `isPayload()`。**

```
verifySession: 驗簽 → isPayload(形狀) → exp 檢查(:156) → 🆕 版本政策
```
政策一句:**`ADMIN_REQUIRE_REAL_IDENTITY` 開 ⇒ `v:1` 一律拒;關 ⇒ `v:1` / `v:2` 都收。**
⇒ 直接滿足 §B5-1 第 1 / 2 格,而且**只有一個地方在判**(`proxy.ts:40` 的讀取閘走的就是它)。

🔴 **開關的寫法對齊既有慣例、不發明新的**:`proxy.ts:17-18` 現行逐字是
`process.env.NODE_ENV !== 'production' && process.env.ADMIN_DEV_BYPASS === '1'`
⇒ 本開關同樣用**正向字面比對** `process.env.ADMIN_REQUIRE_REAL_IDENTITY === '1'`,
**拼錯 / 沒設 / 空字串一律當【關】**(= 今天的行為)。
⚠️ 而這個 fail-safe 方向要講清楚:**這裡的「安全邊」是「維持現狀」不是「更嚴」** ——
它擋的是「打錯字就把全公司鎖在門外」。**真正的收緊由 B7 那一步刻意打開,不靠預設值。**

**(4) ✅ §B5-1 第 3 格(`v:2` 送到【舊】admin ⇒ 拒絕)——【現在就成立】,本窗當場核過。**
`session.ts:112` 逐字 `if (o.v !== 1) return false;` ⇒ 舊 admin 收到 `v:2` **整包拒**。
⇒ plan v4 §8 那個 rollback 安全網**不是假設,是現有 code 的行為**。
🔴 **而它只在「舊 admin 這一版還在跑」時成立** ⇒ B5 一上線,那道保護就換成 (3) 的政策了 ⇒ **格 3 要在 B5 【部署之前】跑,跑完就沒得跑了**。

## §B5-5 件 3 · `actor.ts` 改讀 session(「改成什麼」)

### 現況(2026-08-18 當場讀,`actor.ts:33-36` 全文)

```ts
export async function getSessionActor(): Promise<StaffActor | null> {
  const store = await cookies();
  return await resolveStaff(store.get(ACTOR_COOKIE)?.value);
}
```
⇒ **身分的唯一來源是使用者自己選的 cookie。** 這正是本線要換掉的那一行。

### 規格:改成【三層,順序是硬的】

```
第 1 層  verifySession(ADMIN_SESS_COOKIE)  →  拿到 v:2  →  身分【只】從 sub 來
           sub.kind === 'user'      ⇒ return await resolveStaff(sub.staff_id)
           sub.kind === 'fallback'  ⇒ return null        （備援 = 無具名身分）
第 2 層  拿不到 v:2 而開關【開】     ⇒ return null        （不得回退去讀 ACTOR_COOKIE）
第 3 層  拿不到 v:2 而開關【關】     ⇒ 維持現行這一行     （= 今天的行為，零改變）
```

🔴 **三條硬規定(對應 §7.1 矩陣的三條,這裡是它的實作面):**

1. **`v:2` 存在時,`ACTOR_COOKIE` 【一個字都不讀】。** 不是「讀了再覆蓋」——
   讀了就會有人想「兩邊不一致時要不要合一下」,而那正是 §7.1 標為**未折**的那題。**不讀 = 那題在這條路上不存在。**
2. **`fallback` 回 `null`,而 `null` 的意思是「沒有具名身分」,不是「未登入」。**
   ⇒ 呼叫端不得把 `null` 當成「導去登入頁」——`fallback` 依 §7.1 矩陣**讀取是允許的**。
   🔴 **這一條很容易寫反**:今天 `null` 只有一種意思(還沒選人),改完之後它有兩種來源。
   **⇒ 若呼叫端會因此分不清,施工者要回報,不得自行加第三種回傳值**(那是型別決定,屬 plan 層)。
3. **寫入的攔截點仍在寫入端**(`authorizeAdminMutation`),**不靠 `getSessionActor` 回 `null` 順便擋住** ——
   §7.1 第 3 條硬規定逐字:「讀取是允許的,它一定走得到」。

### ⚠️ 本節【刻意不決定】的那一件(不是漏寫)

**`sub.staff_id='sean'` 的 session 配上瀏覽器裡舊的 `pcm_admin_actor=staff_2`** ——
上面第 1 條已經讓 `sub` 贏(§7.1 矩陣本來就要求「稽核 actor 必須等於 `sub.staff_id`」),
**而「要不要順手把那顆舊 cookie 清掉、要不要因此拒絕該次請求」仍然未決**(§7.1 已標,歸 `#4`/`#5`/`#12`)。
🔴 **本片的實作在兩種決定下都不用改**(不讀就是不讀)⇒ **它不擋 B5 開工**,但**B6 下架下拉時必須回來收這顆 cookie**。

### 驗收(接續編號)

| # | 構造 | 預期 |
|---|---|---|
| 14 | `v:2` + `sub.kind='user'` + 該 staff 在 A 庫啟用中,**且瀏覽器帶著不同人的 `pcm_admin_actor`** | ✅ 回 `sub` 那個人;🔴 **稽核不得記成 cookie 那個人**(= §7.1 驗收第 8 格在 `actor.ts` 這一層的對應) |
