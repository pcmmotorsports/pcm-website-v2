## 1-a 兩個結論,而它們不一樣 —— 不要合起來讀

```
① 性別  = 【本片要新增的蒐集】而政策沒列 ⇒ 🔴 這是本片造成的, 要一起處理
② 生日  = 🔴🔴 【已經在收了】而政策也沒列 ⇒ **這是一個【既有】缺口, 不是本片引入的**
   證據:customers.birthday 欄 08-05 就存在(init migration :19)
        design 會員中心本來就有生日輸入格(AccountPages.jsx:669)
   ⇒ **不得寫成「本片發現並修好了一個 bug」** —— 本片只是【撞到】它。
   ⇒ 而它也【不是本片可以自己修的】:改法律頁 = 鐵則 12⑤ 對外不可回收。
```

## 1-b 🔴 而改那份文字有一道機制在守,不是靠自律

```
apps/storefront/src/data/legal-content-hash.test.ts 檔頭逐字:
  「legal_terms_versions 那一列說『版本 X 的內容雜湊是 H』, 客人簽的是 X,
    而客人實際讀到的字必須真的雜湊出 H, 且 migration 裡寫的也必須是同一個 H。
    沒有這些測試, 以後有人順手改一句條款, version 不動 → 稽核時
   【客人同意的內容】查無對證, 而三綠 / 型別 / lint 全部都是綠的(改字串不會讓任何東西紅)」
```
⇒ **改一個字 ⇒ 那支測試會紅 ⇒ 要同時發新版本號 + 新雜湊 + migration。**
⇒ 🔴 **所以「順手在政策裡加兩個詞」這件事【不存在】。它是一片有體積的工作。**
⇒ **本片不做它。列成前置,交給主視窗排。**
