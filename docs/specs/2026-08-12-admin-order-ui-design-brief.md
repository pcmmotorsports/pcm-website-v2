### 已定位的第一個病灶(附證據)

採購區(「採購(向供應商訂貨)」)是一張 **9 欄表格**包在 `overflow-x-auto` 裡

問題在**第 9 欄「到貨登錄」裡塞了一包展開表單**。Sean 截圖裡可辨識的欄位有五個
(到貨幾件 / 什麼時候到的 / 溢收幾件 / 備註 / 「登錄到貨」按鈕;**來源=截圖肉眼,未逐行核 `item-procurement-form.tsx` 386 行的完整欄位集**)。

同截圖中前八欄的值多為短字或「—」(單列樣本,未統計多列)⇒ **橫向空間被前八欄吃掉、真正要操作的第九欄反而沒位置**。

### 🔴🔴 Sean 2026-08-12 補充的「真實工作流順序」—— 這是本案最高權威的素材

> 逐字照抄,**不要改寫、不要濃縮**。這是老闆本人描述他每天怎麼跑一張單:

> 「通常我們有訂單 之後,當然會先確認收款狀況,那網路上的訂單一定是刷卡沒問題,一定是全額,
> 那考量到如果是我們手key 訂單就一定會有收現金,等等再來才是我們確認好收完的現金金額之後呢
> 回去採購等於說跟國外下單嗎?那下單完之後就是等到貨等到貨完之後是看要不要收尾款,
> 基本上最常用的流程應該是這些,然後最難的大概就是取消,所以放最下面沒問題,
> 那 訂單的資訊在最上面會感覺重複的資訊太多了,應該可以精簡一些變成不需要這麼多重複的資訊,
> 然後建立包裹的擺放位置也蠻奇怪的,不知道怎麼形容比較好但是就是很 不直覺,
> 或者把建立包裹換成出貨這兩個字,然後整體的順序在編排跟精簡一下就 可以好用一些」

> 「你先讓OD 依照市面上大部分者種介面怎樣安排、設計,讓整個UI順手順眼,
> 同時用電腦、手機好操作(主要是電腦)」

**從這段可以直接讀出的設計指令(不是我推的,是他講的):**

1. **主流程順序 = 收款 → 採購(跟國外下單)→ 等到貨 → 收尾款 → 出貨**;**取消放最下面**(他明說「放最下面沒問題」)。
   ⇒ 現行版面若不是這個順序,就是順序錯了。
2. **兩種單走不同路**:網路訂單(刷卡、全額、沒問題,幾乎不用管)vs **手 key 訂單(會收現金,要人工登記)**。
   ⇒ 收款區的預設樣貌應該讓「沒事的那種」佔最少空間、「要動手的那種」最顯眼。
3. **訂單標頭重複資訊太多** ⇒ 頂部要精簡,別把同一件事講三遍。
4. **「建立包裹」這個詞與它的位置都不對** ⇒ 他自己給了改名方向:**「出貨」**。位置要落在流程末端(收完尾款之後)。
5. **參考市面上同類介面的通行做法**(電商後台 / 進銷存 / 訂單管理系統)去安排,不要自創一套。
   目標詞是他的原話:**「順手順眼」**。
6. **電腦優先**、手機也要能用。
7. **「做錯了要能收回」是一整族需求**(Sean 同日連補三句,逐字):
   > 「然後採購也要可以取消,有可能key錯資訊之類」
   > 「登入到貨也要可以取消」
   > 「畢竟可能原本以為這個商品要給這個訂單,其實要先給另外一個訂單」

   ⇒ **採購紀錄**與**到貨登錄**兩者都要有「撤/改」的入口。第三句透露的意圖比字面更大:
   他要撤到貨**不只是打錯字**,而是**這批貨其實該給另一張單** —— 也就是**跨訂單調撥**的需求雛形。
   - Design 這邊要處理的:兩個撤銷入口**放哪、份量多大**。
     它們是**誤植的救濟**,不是業務流程的一步 ⇒ 不該和「登錄到貨」這種主動作同級,但也不能藏到找不到。
   - **不要**在 demo 裡自己發明調撥流程(那是功能設計、要 Sean 先拍)。
   - ⚠️ 功能面(能不能撤、已出貨的怎麼算、留不留痕、調撥怎麼做)由 Claude Code 另查另立條目。

### 要 Design 回答的

- **一張表格裡塞可操作表單**這個形狀本身要不要留?(留 → 怎麼保證窄容器下操作區優先;不留 → 表單搬去哪:抽屜 / 展開列 / 彈窗 / 側欄)
- 「唯讀資訊」與「要動手的操作」在同一張卡裡怎麼分層,讓員工一眼知道**哪裡可以改**
  (Sean 的第二句抱怨=「可以編輯地方很多但很不直覺」⇒ 現在**編輯點沒有視覺語言**,看起來全是文字)。
- 文字炸裂:中文長字串(品名 / 車種 / 供應商名)在窄欄的處理規則(截斷 + tooltip / 換行 / 縮排到次行)。

- 丙:**主從式** —— 訂單層一行(單號/日期/客戶/金額),品項層縮排成子列,操作類入口只出現在訂單層那一行。

### 素材與約束

  客名與料號變成可點之後長什麼樣。
