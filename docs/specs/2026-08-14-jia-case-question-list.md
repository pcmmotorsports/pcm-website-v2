# 甲案問題清單 · 「鎖做在我們這邊」要先問清楚什麼

> 對稱於 `2026-08-14-yi-case-question-list.md`。**是問題清單,不是設計。**
> 用途:Sean 要能兩案並排比較,而不是只看到其中一案的困難就被推去選另一案。
> 甲案 = `products` 表加逐欄鎖 + `rpm-transform` 讀鎖決定要不要展開該欄的 key。

## A. 批次寫入:逐欄鎖會直接踩到一個已經出過事的坑(**先答這題,它決定甲案貴不貴**)

**現況**(`rpm-load.ts:47-58`,**親驗** postgrest-js v2.105.3 `PostgrestQueryBuilder.ts:1359-1362`):
`.upsert(陣列)` 的 `?columns` 取**全批 key 聯集** + `defaultToNull=true`
⇒ 同批混「有此 key」與「省此 key」的列時,**省 key 的列會被寫 NULL,不是保留現值**。
出過真事故:`products.manuals` 是 `jsonb NOT NULL` ⇒ 那不是寫錯值,是 **23502、整批 500 列全敗**。
現行解 = `groupByKeySignature()`(`:70`)把 key 集合相同的列分同一批;`BATCH_SIZE = 500`(`:15`)。

> 🔴 **2026-08-14 訂正(A 窗 M1,我開檔複驗成立)—— 本節原本的前提句是錯的,而且我讀過那段 docstring 還寫反了。**
> 原寫「**今天所有條件省 key 都是供應商級 all-or-nothing ⇒ 全批 key 一致 ⇒ 只有 1 組**」。
> `rpm-load.ts:59-60` 逐字:「條件省 key 的欄**已達三個**(`description` **per-row**、
> `manuals`/`video_url` **per-row 來源 null 防清空**)」⇒ **逐列 key 差異早就在生產跑。**
> `:62-63` 的「只會有一組」**只對 rpm 那一家**(兩個 flag 都 false)成立,不是全體。
> ⇒ **正確對比不是「1 組 → 2ⁿ 組」(從零到有),而是「已經是多組 → 再多長幾組」。**
> 🔴 我原本的寫法會讓甲案成本被高估;Sean 已選乙,**那個選擇不該建立在錯的對比上**。

1. 要鎖的欄有幾個?**每多一個可鎖欄,分組數上限翻倍(n 欄 → 最多 2ⁿ 組)**,每組再各自切 500 一批。
   ⇒ 願意接受同步時間變多少?(現況整個 matrix 12 家序列跑完 **約 10-13 分鐘**,`rpm-sync.yml:69` 實測)
   **答「時間可以多一倍」⇒ 甲案在批次面不設限;答「不能變慢」⇒ 甲案要先做分組數量測、可能改單一 RPC(見第 3 題)。**
2. ~~`groupByKeySignature` 的設計意圖涵不涵蓋逐列?~~ **這題作廢(A 窗 M2):文件已明文回答** ——
   `rpm-load.ts:61` 逐字「按 signature 分組是同一件事的一般解,**新增條件欄自動涵蓋、不需再改這裡**」。
   **改問真正未知的那半**:**逐列鎖之後實際會長出幾組、每組幾列?**
   **答「量過、組數可控」⇒ 照現行分組走;答「量不出來」⇒ 甲案要先做一次乾跑量測才能估工。**
   ⚠️ 這題**要跑一次真同步才答得出來**,不是讀 code 能答的(我 §F 列為未量測)。
3. 分組後每組可能只剩幾列 ⇒ 大量小批次 HTTP 往返。**要不要改寫成單一 RPC / SQL 一次做完?**
   **答「要」⇒ 甲案多一支 RPC(鐵則 12③、另一個規模的工程);答「不要」⇒ 接受小批次往返、但要吃第 1 題的時間代價。**

## B. 鎖狀態要怎麼進到同步流程裡

**現況**:`transformGroup()` 是**來源列 + 供應商設定**的純函式 —— `ctx`(`rpm-import.ts:275-286`)裡
**沒有任何目標庫的狀態**。同步流程是「讀來源 → transform → 寫目標」,**transform 這一步看不到目標庫**。

4. 要讓 transform 知道「這列這欄被鎖了」,得先把目標庫的鎖狀態讀出來餵進去 ——
   **這是同步管線的形狀改變,不是加個 if。** 誰做?我們這條線還是另開?
5. 要多讀一次全表的鎖旗標(現況目標庫只在對賬階段讀 `readActiveExternalIds`)⇒ 多一趟全表讀,可接受嗎?
   **答「可接受」⇒ 照現行形狀加一趟讀;答「不可」⇒ 要改成讀取與對賬合併一趟,牽動既有對賬碼。**
6. 乾跑(`--dry-run`)也要模擬鎖嗎?不模擬的話乾跑報告會和實際寫入不一致 ⇒ **乾跑的防誤殺價值會下降**。
   **答「要模擬」⇒ 乾跑也要讀鎖、成本同第 5 題;答「不模擬」⇒ 要明寫「乾跑數字不含鎖」,否則它會被當成實際結果。**

## C. 鎖的語意(這幾題不問清楚,做出來會是另一個東西)

7. 鎖是**自動**的(員工一改該欄就自動上鎖)還是**手動**的(要按一個鎖頭)?
   **答「自動」⇒ 員工不必學新動作,但會鎖到他只是手滑改過的欄;答「手動」⇒ 語意清楚,但員工忘了按就等於沒鎖。**
8. 🔴 **怎麼解鎖?** 鎖上之後那一欄**永遠不再收來源更新** ——
   供應商改了規格 / 改了名字,我們這邊會**安靜地停留在舊值**。誰會發現?要不要有「這欄鎖了 N 天」的提醒?
9. **上下架欄要不要可鎖?** 🔴 若可鎖:供應商停產了、我們卻鎖著「上架中」⇒ **客人買得到一個已經不存在的東西**。
   (現況下架權威在來源側,`rpm-transform.ts:356` 逐字。)這題我建議答「不可鎖」,但那是 Sean 的生意判斷不是我的。
10. 🔴 **價格欄要不要可鎖?** 若可鎖 ⇒ **價錢權威就落在我們這邊,和 Sean 原話「價錢應該以後台為主」相反。**
    甲案要成立,這題必須先有答案。
