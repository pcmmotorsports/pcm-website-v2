## §3 表:加**兩欄**,不是加一顆 `jsonb`

🔴🔴 **`CHECK` 的值域是【B3 那個 union 的鏡像】,加變體要同步改(2026-08-18 R2 must-fix)**:
漏掉 `bootstrap` 那一支的後果**不是「拒絕得很清楚」,是【隱性 23514】** ——
authorize 照 B3 規格寫入 `sub_kind='bootstrap'` ⇒ **`CHECK` 當場擋下 ⇒ 首次建置那次 SSO 直接失敗**,
而錯誤訊息只會說 `sso_codes_sub_shape` 違反,**不會說「這個變體沒人登記」**。
📎 **這一格就是主視窗說的「每張執法表多一列」清單裡的 `B4 CHECK 值域`那一項** ——
**清單是轉述的,而這一項我親自對上了。**

🔴 **兩段 DDL 必須在【同一個明文交易】裡(2026-08-18 關卡1 must-fix)**:
`ALTER … ADD COLUMN` 成功而 `ADD CONSTRAINT` 失敗 ⇒ 資料庫停在**有欄位、沒有 CHECK** 的半套狀態,
而**應用層那一刻就寫得進壞形狀**(`user` 沒有 `staff_id`、`fallback` 帶了 `staff_id`)。
⇒ migration 檔頭 `BEGIN;` / 檔尾 `COMMIT;`,**不倚賴「Postgres 的 DDL 是交易性的」這個直覺** ——
`apply_migration` 有沒有自己包一層**至今未確認**(`docs/specs/2026-08-16-m4b-e8b-b1-spec.md` §4.4 逐字)。
⚠️ **驗收**:apply 之後查 `pg_constraint` 確認 `sso_codes_sub_shape` 在;
**不在而欄位在 ⇒ 立刻走 rollback,不要「補跑一次 ADD CONSTRAINT」**(那會讓半套狀態多活一段時間)。

```sql
BEGIN;

ALTER TABLE public.sso_codes
  ADD COLUMN sub_kind     text,      -- 'user' | 'fallback' | 'bootstrap' | NULL（NULL = B3 之前簽的碼）
  ADD COLUMN sub_staff_id text;      -- 只有 kind='user' 才有值

ALTER TABLE public.sso_codes
  ADD CONSTRAINT sso_codes_sub_shape CHECK (
       (sub_kind IS NULL     AND sub_staff_id IS NULL)
    OR (sub_kind = 'fallback'  AND sub_staff_id IS NULL)
    OR (sub_kind = 'bootstrap' AND sub_staff_id IS NULL)   -- 🆕 2026-08-18 R2 must-fix
    OR (sub_kind = 'user'      AND sub_staff_id IS NOT NULL AND btrim(sub_staff_id) <> '')
    --  🔴 2026-08-18 nit：原本寫 sub_staff_id <> ''，擋不掉【單一空白 ' '】
  );

COMMIT;
```

🔴 **為什麼是兩欄 + CHECK,不是一顆 `sub jsonb`**:
`docs/specs/2026-08-17-m4b-e8b-b5-spec.md` §B5-3 已經量到一個**構造得出來的壞形狀** ——
`{kind:'fallback', staff_id:'sean'}`(admin 的 `isPayload` 容許額外欄,不會拒)。
**jsonb 讓那個形狀在資料庫裡也合法;CHECK 讓它【寫不進去】。**
⇒ **在來源殺掉它,勝過在每個收端記得判。**(同一判準見 §B5-3「讓錯誤形狀不存在」。)

🔴 **兩欄都必須 NULLable(expand 的硬要求)**:migration 先上、應用層後上,
中間那段時間 authorize 還是舊版、**不會寫這兩欄** ⇒ 有 `NOT NULL` 就當場全站登入失敗。
📎 母 plan `:196` 逐字「新欄先加**選填**,舊寫入端照樣能跑」。

### 🔴 而上面只寫了好處。**代價兩條**(2026-08-18 第三輪抓,本節原本一條都沒寫)
```
① union 的值域從此有【兩份權威】：TS 的 SessionSub ／ DB 的 sso_codes_sub_shape CHECK
   漂掉的症狀 = 隱性 23514 ⇒ 發碼 500 ⇒ 那個人登不進 admin
   🔴 而【本線已經被這個形狀咬過一次】：R2 抓到 CHECK 漏了 bootstrap ⇒ 這不是假想的代價
② 今後每加一個 sub 變體都要一次 production DDL，而 DDL 要 Sean 在場
   ⇒ 消費者清單（b5-spec）的真實成本比它寫的【貴一級】：
     清單上每一項是改 code，而這一項是【約一個人的時間】
```
📎 **結論不變(仍選兩欄)** —— 而**理由窄會讓人做出不同的決定**:只讀到好處的人會以為「加變體很便宜」。

### ⚠️ `sub_staff_id` 要不要加 FK 指向 `admin_user_staff_map` ⇒ **現在答不了,B1-b 落地後重評**

```
量法：cd ~/API大量上架/PCM報價單-V2 && git grep -n 'admin_user_staff_map' -- .   ⇒ 0 命中
```
⇒ **被指向的那張表今天不存在**;FK 還要求被指向欄有 `UNIQUE`,而 **B1-b 的表形狀未定**。
🔴 **另一條代價**:`sso_codes` **無清理機制**(見 §11)+ FK ⇒ **一顆過期的碼會【永久】擋住那個人的解綁 / 改名。**

## §4 authorize:身分從哪裡來(**唯一合法來源 = B3 的 session**)


`app/api/sso/authorize/route.ts:49` 現行逐字 `const session = await getSession();`,
`:61-62` 已經在用 `session.amr` / `session.iat` ⇒ **B4 只是多帶一個欄位,不新增取得管道**。

```
session.sub.kind === 'user'      ⇒ insert 帶 sub_kind='user',      sub_staff_id=session.sub.staff_id
session.sub.kind === 'fallback'  ⇒ insert 帶 sub_kind='fallback',  sub_staff_id=NULL
session.sub.kind === 'bootstrap' ⇒ insert 帶 sub_kind='bootstrap', sub_staff_id=NULL   🆕 2026-08-18
🔴 這三支要寫成 exhaustive switch + assertNever（B3 §3.9「加變體的紀律」）——
   寫成 if/else 的版本會讓 bootstrap 靜默落進最後那個 else
session 沒有 sub ⇒ 兩欄都不寫（NULL）
  🔴 **B4 之後這一支【不可達】**：報價單走甲，v:1 一律拒；而 v:2 一定帶 sub（B3 §3.9）
     ⇒ 它是【防禦性分支】，不是一個會發生的情況 ⇒ **不給它驗收格**
     （一格「已知構造不出來」的驗收，留在表上只會讓表的通過率說謊）
```

🔴 **明文禁止三條(照抄 B3 §4 的禁令,因為同一個誘惑在這一層長得一模一樣):**
1. **不得**在 `session.sub` 缺席時改寫 `sub_kind='fallback'` —— fallback 是**一種身分**,不是「查不到時的退路」。
2. **不得**從 query string / header / 任何請求端輸入取 `staff_id`(`:43` 現在只收 `state`,**維持只收 state**)。
3. **不得**在這裡查 `admin_user_staff_map` 補身分 —— 查映射是 **B2/B3 登入那一刻**的事;
   在這裡查等於**同一件事有兩個執行點**,而兩個點會漂。

🔴 **`session.sub` 不存在時,兩欄寫 NULL,而【發碼仍要成功】** —— 這是本片的**安全性質**
(expand:它不會弄壞現況)。**而它【不是】「可以先做」的理由** ——
**順序仍是母 plan §4 的 B3 → B4**,而它是硬的(`plan:219-220` 逐字「順序是硬的,不是建議」)。

## §5 exchange:兩處要改,而**漏改第二處的症狀是靜默無身分**


```
:66  .select('amr, auth_time')                        ⇒ 加 sub_kind, sub_staff_id
:71  NextResponse.json({ ok:true, amr, auth_time })    ⇒ 有 sub_kind 才加 sub
```

**回應形狀(與 admin `ExchangeResult` 對齊,見 `…-b5-spec.md` §B5-4)**:
```
sub_kind = 'user'      ⇒ { ok:true, amr, auth_time, sub:{ kind:'user', staff_id:<sub_staff_id> } }
sub_kind = 'fallback'  ⇒ { ok:true, amr, auth_time, sub:{ kind:'fallback' } }
sub_kind = 'bootstrap' ⇒ { ok:true, amr, auth_time, sub:{ kind:'bootstrap' } }   🆕 2026-08-18
sub_kind IS NULL       ⇒ { ok:true, amr, auth_time }        ← 不帶 sub 欄，不是 sub:null
```
🔴 **`sub` 缺席要用「沒有這個欄」表示,不要用 `sub:null`** ——
admin 那端(§B5-4 (2))把「沒有」與「形狀壞」分成兩條路,而 `null` 會掉進**形狀壞 ⇒ 整包拒**那一條。

🔴🔴 **這一片最容易出的錯,就是只改 `:71` 而忘了 `:66`。**
症狀:`data.sub_kind` 恆為 `undefined` ⇒ 回應永遠不帶 `sub` ⇒ **admin 永遠拿不到身分,而每一層都「正常」**
(碼換得到、登入成功、沒有任何錯誤)。**typecheck / lint / 現有測試全部看不到**(`.select()` 吃的是字串)。
⇒ **§7 第 3 格就是為了這一行存在的。**

⚠️ **`exchange` 不做任何白名單過濾** —— admin 端擋在收取(`sanitizeSub`),報價單這端擋在寫入(§3 的 CHECK)。
🔴 **兩端都要有,不是二選一** —— DB 裡若有 CHECK 之前寫進去的舊列,CHECK 管不到它。

## §6 可觀測性:兩個【收斂】,它們一起讓「我們自己壞了」變成看不見


### (1) `401` 同時承擔【重放 / 過期 / 攻擊】與【我們自己壞了】
```
報價單 app/api/sso/exchange/route.ts:69   if (error || !data) return unauthorized();
   ⇒ error 被整個丟掉、【零 log】
admin  apps/admin/src/app/api/sso/callback/route.ts:65  唯一訊號 = reason:'exchange-failed'
```
🔴 **後果**:本檔 §7 自己寫的那個災難(欄位還沒 apply / schema cache 沒 reload ⇒ **全員登不進 admin**)
**在日誌上與「有人重放一顆過期碼」是【同一個字】。**
**⇒ 本片必須做的(而它很小)**:
```
· 回應【不變】——維持 401、不洩因（那是刻意的，改它會變成攻擊者的探針）
· 🔴 而【伺服器端要 log 出 error 本身】：至少 error.code / error.message
  （Supabase 的 schema 錯與「查無此碼」是兩個不同的 code）
· 判別句：不洩給【外面】≠ 不記給【自己】——現在是兩者一起沒有
```
⚠️ **不要改成回不同的狀態碼** —— 那會讓攻擊者分得出「碼錯」與「系統壞」。

### (2) `sub_kind IS NULL` 有【三個生產者】,而只有【一個可觀測值】
```
生產者一：B4 之前簽的碼（正常的歷史資料）
生產者二：rollback ② —— 退回舊 authorize，它不寫那兩欄
生產者三：§5 那個靜默 bug —— 只改 :71 忘了 :66（本檔自己說「§7 第 3 格就是為了這一行存在的」）
⇒ 三種在 DB 裡【長得一模一樣】
```
🔴 **後果**:開關開之後「全員登不進」時,**沒有任何東西分得出是哪一種**;
而且**永遠不能對 NULL 列告警**(生產者一是正常的)。
**⇒ 本片能做的(誠實寫,不假裝解決了)**:
```
· 🔴 本片【不解決】它 —— 要真的分開，得再加一個欄位（例如 wrote_by_version），
  那是範圍擴張、要它自己一輪審查
· ✅ 本片要做的是【不要讓它更糟】：§7 格 3 是唯一抓得到生產者三的守門 ⇒ 那格不得跳過
· ✅ 並寫下【什麼時候它會變成真的問題】：B7 開關打開之後
  —— 在那之前 NULL 是常態，之後 NULL 應該歸零
  ⇒ 🔴 那一刻【才】可以對 NULL 列告警，而那是 B7 的事、不是本片的
```
📎 **判別句**:**一個值有幾個生產者,決定它能不能拿來告警** —— 三個生產者一個值 = **零告警能力**。

## §10 `'bootstrap'` 這個【字面】同時是兩個軸的值(無解,只能標)

```
報價單 lib/session.ts:11   type SessionAmr = 'pwd' | 'totp' | 'bootstrap' | 'recovery'   ← 強度軸
B3 spec §3               type SessionSub = … | { kind:'bootstrap' }                     ← 身分軸
而 B4 把兩者寫進【同一列】：sso_codes.amr[] 與 sso_codes.sub_kind
```
🔴 **而它們會【不一致】,那不是 bug 是設計**:B3 `§3.10` 逐字「**`amr` 升級、`sub` 不動**」
⇒ **存在 `amr = {pwd,totp}` 而 `sub_kind = 'bootstrap'` 的列。**
⇒ **任何以字面 `'bootstrap'` 為鍵的 `grep` / 白名單 / 部署閘,分不出自己在看哪一軸。**

**⇒ 本片能做的(不改名,因為改名要動跨 repo 契約)**:
```
· 🔴 凡是掃 'bootstrap' 的守門／查詢，pattern 一律【帶欄位名】：
    sub_kind = 'bootstrap'      （身分軸）
    'bootstrap' = ANY(amr)      （強度軸）
  —— 不得寫成裸的 grep 'bootstrap'
· 📎 判別句：一個字面在兩個軸上都合法時，【欄位名就是軸】——
  丟掉欄位名的查詢，等於丟掉「我在問哪一個問題」
```
⚠️ **這一條沒有守門,只有紀律** ⇒ 誠實標:**它靠人記得,而人會忘。**
真正的解是**改名**(例如身分軸用 `'setup'`),而那要動 B3/B4/B5 三份契約 ⇒ **另一片,不在本片。**
