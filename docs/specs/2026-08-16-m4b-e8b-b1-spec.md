| `test_01` | TEST | ✅ | ✅ | ⚠️ **停用,不刪**(見 §3) |

### 🔴🔴 承重結論:映射不能是「每個 staff 都有一個 Auth user」

`op4_backfill` / `payment_confirmer` **沒有人會登入它們,而 `admin_audit_log` 會寫它們**。
⇒ **型別上必須容得下「有 actor 身分、無 Auth user」這一類。**

**⇒ 映射表方向:以 Auth user 為主鍵、`staff_id` 為必填**,
**而不是**以 `staff_id` 為主鍵、Auth user 為 `NOT NULL` 外鍵。
> **判別句:哪一邊可以沒有對象?** —— 答案是「staff 可以沒有 Auth user」,
> **所以 staff 不能當那張表的必填來源。**

⚠️ **這是 plan 從頭到尾沒有的一個型別維度。** 沒有 `§5④` 就會在 B1 寫成硬約束,
而那要靠另一支 migration 才改得回來(鐵則 12 ③)。

## §4 硬規則(寫 migration 時逐條照做)

### 4.1 🔴 禁用 `IF NOT EXISTS` / `OR REPLACE`

一律裸 `CREATE`。理由與失敗形狀見 `docs/patterns/revoking-function-execute-in-supabase.md` §3.2。
**一句話**:報價單庫的 repo 與正式庫**可能不一致**;不一致要**當場紅**,不要靜靜跳過 ——
**跳過之後,本片的 `REVOKE` 與斷言會對著那個既有物件跑而且很可能通過,拿到綠燈而什麼都沒建。**

### 4.2 🔴 開頭帶前提斷言(把 `§5③` 的一致性檢查縮到本片真正碰到的物件上)

本片依賴的每一個既有物件,先驗存在與形狀,查無就 `RAISE EXCEPTION`。
✅ **這在報價單 repo 是既有做法,不是我發明的**:
量法 `git grep -li "RAISE EXCEPTION" origin/main -- supabase/migrations | wc -l` ⇒ **12**
(分母:`git ls-tree --name-only origin/main supabase/migrations/ | wc -l` ⇒ **16**)。

**必含的前提斷言(這是 `§5②` 那次查詢的接班人):**
```
auth_state.require_2fa = false
totp_devices     零列
recovery_codes   零列
否則 RAISE EXCEPTION，訊息直接指向 plan §7-3「本線範圍必須當場擴張」
```
🔴 **為什麼放本片而不是 B2**:整個 7 片的拆法建立在「不碰 TOTP」上,**B1 就已經依賴它**。
📎 **這條把「我 2026-08-16 查到 0」換成「每次 apply 都再問一次」** ——
查到的事實會過期,斷言不會。**而斷言要住在會被重複執行的東西裡,才有那個性質。**

### 4.3 🔴 尾端帶新物件收權 fail-closed 斷言

用 `~/pcm-mailbox/E-684-新物件收權斷言樣板.md` 的樣板,**不自己另寫一套**。
- ✅ 本窗已打兩發驗過:**只有欄級授權 ⇒ 紅並指名欄位;收乾淨 ⇒ 綠且零 ERROR**(2026-08-16,PG 17.10)。
- ⚠️ **清單只列本片新建的物件**,不要順手加既有表 —— house 對型錄表有**刻意的**欄級授權,加進去會紅,而那是誤報。
- ⚠️ **它只檢查你列出來的物件** ⇒ 防「忘記收權」,**不防「忘記列」**。
  ⇒ **列清單當正式步驟做**:寫完 migration 用
  `grep -cE 'CREATE (TABLE|VIEW|MATERIALIZED VIEW)|CREATE( OR REPLACE)? FUNCTION' <本檔>`
  對一次清單長度,**兩個數不一樣就是漏列**。
