## §2 映射表的形狀(v2 —— 系統帳號**不進**這張表)

### 先把三類分清楚,因為 v1 就是在這裡混掉的

| 類別 | 成員 | 會登入嗎 | **進映射表嗎** | 在 `admin_audit_log.actor` 出現嗎 |
|---|---|---|---|---|
| 真人 | `sean` / `staff_1` / `staff_2` | ✅ | ✅ | ✅ |
| 系統帳號 | `op4_backfill` / `payment_confirmer` | ❌ | 🔴 **不進** | ✅ |
| 無用途 | `test_01` | ❌(B1-a 停用後) | ❌ | 未知(見 §3) |

🔴 **v2 的核心更正:映射表只描述「會登入的人」。**
系統帳號**不需要映射**,因為它們**從來不經過登入路徑** —— 它們是 A 庫 audit log 裡的 actor 字串,
**而那個欄位本來就是 text、本來就不指向這張表。**

⇒ **「型別上要容得下無 Auth user 的 actor」這個需求是真的,但它的歸屬不是這張表** ——
**它由 `admin_audit_log.actor` 是 text 欄這件事已經滿足了。**
📎 **v1 把一個【已經被別的機制滿足的需求】,硬塞進一張新表的型別裡。**

### 形狀

```
報價單庫 · public.admin_user_staff_map
  auth_user_id  uuid  PRIMARY KEY  REFERENCES auth.users(id) ON DELETE RESTRICT
  staff_id      text  NOT NULL  UNIQUE
  created_at    timestamptz NOT NULL DEFAULT now()
```

- **`auth_user_id` 當主鍵**:一個 Auth user 對一個 staff 身分。
- **`staff_id UNIQUE`**:**單帳號制** —— 一個 staff 身分只能綁一個 Auth user。
  ⚠️ **這是一個決定,不是預設。** 若日後要允許「一個人兩個帳號」,要拆 binding 表。
  **現在選單帳號制,理由:稽核軌要能從 actor 反查到唯一一個登入者,不然本線的目的就沒達成。**
- **`ON DELETE RESTRICT`**:**Auth user 不准被刪**,要停用走 Auth 的 ban/disable。
  🔴 理由同 `test_01`:刪掉會讓映射消失,而稽核軌指向的 `staff_id` 就再也查不到是誰登入的。
- **換 email 不影響**:綁的是 `auth.users.id`(uuid),不是 email。
  📎 這正是 plan `§7-Q3=C` 當初拍「帳號用 email」時要的職責分離。

### 🔴 `staff_id` 的參照完整性:**沒有 FK,而這是已知且刻意的**

跨庫,Postgres 建不了 FK。**三個候選,本規格選 (c),理由寫在下面:**

| 案 | 做法 | 為什麼不選 / 選 |
|---|---|---|
| (a) | 在報價單庫**鏡像一份 staff 表**並同步 | ❌ 多一條同步鏈,而同步失敗是靜默的 |
| (b) | 不驗,應用層自己小心 | ❌ 那不是設計,是省略 |
| **(c)** | **寫入端唯一入口 + CHECK 白名單** | ✅ 見下 |

**(c) 具體**:`staff_id` 加 `CHECK (staff_id IN ('sean','staff_1','staff_2'))`。
- **白名單是硬編碼的,而那正是它的價值**:新增員工 = 一支 migration = 一次 review。
  **本線的目的是「知道是誰」,而不是「方便加人」。**
- ⚠️ **代價寫清楚**:A 庫加了新 staff 而這裡沒改 ⇒ 那個人**綁不了帳號**(insert 被 CHECK 擋)。
  **那是 loud 的,不是靜默的** ⇒ 可接受。
- 🔴 **`test_01` / 系統帳號都不在白名單裡** ⇒ **它們在型別層就綁不了帳號**,不靠人記得。

## §4 硬規則

### 4.1 🔴 禁用 `IF NOT EXISTS` / `OR REPLACE`

一律裸 `CREATE`。理由與失敗形狀見 `docs/patterns/revoking-function-execute-in-supabase.md` §3.2。
**一句話**:repo 與正式庫可能不一致;不一致要**當場紅**,不要靜靜跳過 ——
**跳過之後,本片的 `REVOKE` 與斷言會對著那個既有物件跑而且很可能通過,拿到綠燈而什麼都沒建。**

### 4.2 前提斷言(B1-b 開頭)

✅ **fail-closed 斷言在報價單 repo 是既有做法**:
量法 `git grep -li "RAISE EXCEPTION" origin/main -- supabase/migrations | wc -l` ⇒ **12**
(分母 `git ls-tree --name-only origin/main supabase/migrations/ | wc -l` ⇒ **16**)。

**必含:**
1. **2FA 前提**(`§5②` 那次查詢的接班人):
   `auth_state.require_2fa = false` 且 `totp_devices` 零列 且 `recovery_codes` 零列,
   否則 `RAISE EXCEPTION`,訊息直接指向 plan §7-3「本線範圍必須當場擴張」。
   🔴 **放 B1 不放 B2**:整個 7 片的拆法建立在「不碰 TOTP」上,**B1 就已經依賴它**。
   📎 **把「我 08-16 查到 0」換成「每次 apply 都再問一次」** —— 查到的事實會過期,斷言不會。
2. **物件形狀前提**(codex 關卡1 #5 折入):
   `auth.users` 存在且 `id` 是 `uuid`;本片要建的表**不存在**(裸 `CREATE` 會撞名,但斷言要先講清楚為什麼);
   `public` schema 存在。**查無 / 型別不符 ⇒ `RAISE EXCEPTION`。**
   ⇒ **等於把未解的 `§5③` 一致性檢查,縮到本片真正碰到的那幾個物件上就地做掉。**

### 4.3 尾端新物件收權 fail-closed 斷言

用 `~/pcm-mailbox/E-684-新物件收權斷言樣板.md` 的樣板,**不自己另寫一套**。
- ✅ 本窗已打兩發驗過:**只有欄級授權 ⇒ 紅並指名欄位;收乾淨 ⇒ 綠且零 ERROR**(2026-08-16,PG 17.10)。
- ⚠️ 清單**只列本片新建的物件**;house 對型錄表有**刻意的**欄級授權,加進去會紅而那是誤報。
- ⚠️ 它**只檢查你列出來的物件** ⇒ 防「忘記收權」,**不防「忘記列」**。
  ⇒ 寫完用 `grep -cE 'CREATE (TABLE|VIEW|MATERIALIZED VIEW)|CREATE( OR REPLACE)? FUNCTION' <本檔>`
  對一次清單長度,**兩個數不一樣就是漏列**。

### 4.4 🔴 交易邊界:**動手前要實證,不能假設**(codex 關卡1 #6)

若 MCP `apply_migration` **沒有**把整份 SQL 包在單一交易裡,
**尾端收權斷言失敗時,前面的 `CREATE` / `REVOKE` 可能已經提交** ⇒ 留下半套狀態。

⇒ **B1-b 動手前必做**:在**拋棄式 DB** 上重播一支「前半成功、尾端故意失敗」的 SQL,
確認整支回滾。**做不到原子 ⇒ 另備 forward rollback migration**(不能靠 `git revert`,那不會移除已套的 schema)。
⚠️ **這一項本規格【未做】。列為 B1-b 的開工前置。**

## §6 驗收(v2 —— **分成「拋棄式環境跑」與「正式庫跑」兩組**)

🔴 **codex 關卡1 #7 折入:破壞性的格子【不可以】在正式庫跑** ——
故意把 `require_2fa` 設 true、故意漏 REVOKE、故意加欄級授權,**都是在正式庫寫入一個刻意不安全的狀態。**

### A 組 · 只在拋棄式 PG 跑(破壞性)

| # | 構造 | 預期 |
|---|---|---|
| A1 | `require_2fa = true` | 🔴 紅,且訊息指向 plan §7-3 |
| A2 | 漏一道 REVOKE | 🔴 紅,並指名物件 |
| A3 | 只下欄級授權 | 🔴 紅,並指名欄位(樣板已具此能力,本窗實測過) |
| A4 | 重跑同一支 SQL | 🔴 紅,**且必須紅在 `CREATE` 的 duplicate-object SQLSTATE(`42P07`)** —— 紅在別的地方不算(codex #8) |
| A5 | 前半成功、尾端故意失敗 | 🔴 **整支回滾**(這是 §4.4 那個未做的實證) |
| A6 | 塞一列 `staff_id = 'op4_backfill'` | 🔴 被 CHECK 擋(**證明系統帳號在型別層綁不了帳號**) |
| A7 | 塞一列 `staff_id = 'sean'` | ✅ **成功** —— 沒有這一發,A6 的紅可能來自任何原因(壞輸入要響 + 好輸入要安靜) |

⚠️ **A6/A7 的構造前提**:拋棄式 PG **沒有 `auth.users`**(那是 Supabase 平台建的)。
⇒ 要跑這兩格,得先在拋棄式庫**建一個 `auth` schema + 最小 `users(id uuid primary key)` 樁**。
**這是構造成本,不是做不到** —— 而**寫下來免得下一個人把它讀成「構造不出來」而跳過。**

### B 組 · 正式庫 apply 之後跑(唯讀,零寫入)

| # | 查什麼 | 預期 |
|---|---|---|
| B1 | 表存在、欄型與 CHECK 白名單符合 §2 | 相符 |
| B2 | `anon` / `authenticated` 對新表**零權限**(含逐欄 `has_column_privilege`) | 零 |
| B3 | **讀** `pg_constraint` 裡那條 CHECK 的定義,確認白名單**不含** `op4_backfill` / `payment_confirmer` / `test_01` | 相符 |
| B4 | `test_01` 在 A 庫 `is_active = false` **且該列仍在** | 相符 |

🔴 **B3 是【讀約束的定義】,不是塞一列試試** —— 塞一列是**寫入**,而本組明訂零寫入。
**行為面那一格在 A6/A7(拋棄式)。**
⚠️ **B3 比 A6 弱,而弱在明處**:它證的是「那條 CHECK 的字面對」,
**不證「它真的擋得住」** —— 那要靠 A6/A7,而那兩格跑在拋棄式庫上。
📎 **兩格是分工不是重複:一個證字面、一個證行為,而正式庫上只能做前者。**

### 🔴 靜態檢查(不靠跑,補 A4 的不足)

`grep -niE 'if not exists|or replace' <本片 migration>` ⇒ **必須零命中**。
**A4 證的是「撞名會紅」,這一條證的是「我沒寫那個字面」** —— 兩者不互相取代。
