## §2 映射表的形狀(v2 —— 系統帳號**不進**這張表)

### 先把三類分清楚,因為 v1 就是在這裡混掉的

| 類別 | 成員 | 會登入嗎 | **進映射表嗎** | 在 `admin_audit_log.actor` 出現嗎 |
|---|---|---|---|---|
| 真人 | `sean` / `staff_1` / `staff_2` | ✅ | ✅ | ✅ |
| 系統帳號 | `op4_backfill` / `payment_confirmer` | ❌ | 🔴 **不進** | ✅ |
| 無用途 | `test_01` | ❌(B1-a 停用後) | ❌ | 未知(見 §3) |

🔴 **v2 的核心更正:映射表只描述「會登入的人」。**
系統帳號**不需要映射**,因為它們**從來不經過登入路徑** —— 它們是 A 庫 audit log 裡的 actor 字串,
**而那個欄位本來就是 text、本來就不指向這張表。**

⇒ **「型別上要容得下無 Auth user 的 actor」這個需求是真的,但它的歸屬不是這張表** ——
**它由 `admin_audit_log.actor` 是 text 欄這件事已經滿足了。**
📎 **v1 把一個【已經被別的機制滿足的需求】,硬塞進一張新表的型別裡。**

### 形狀

```
報價單庫 · public.admin_user_staff_map
  auth_user_id  uuid  PRIMARY KEY  REFERENCES auth.users(id) ON DELETE RESTRICT
  staff_id      text  NOT NULL  UNIQUE
  created_at    timestamptz NOT NULL DEFAULT now()
```

- **`auth_user_id` 當主鍵**:一個 Auth user 對一個 staff 身分。
- **`staff_id UNIQUE`**:**單帳號制** —— 一個 staff 身分只能綁一個 Auth user。
  ⚠️ **這是一個決定,不是預設。** 若日後要允許「一個人兩個帳號」,要拆 binding 表。
  **現在選單帳號制,理由:稽核軌要能從 actor 反查到唯一一個登入者,不然本線的目的就沒達成。**

### ✅ `staff_id` 是**永久識別碼**,不是可回收的位置(Sean 2026-08-16 拍板)

> **Sean 逐字:「甲｜新人拿【新代號】staff_3,舊的停用不刪」**

**⇒ 代號永不重用。** 三條下游影響,**寫在這裡而不是只記在信裡**:

1. 🔴 **任何「找一個沒被使用的代號來用」的邏輯都是錯的。**
   新人 = **新代號**(`staff_3`、`staff_4`…),不是撿一個空出來的。
2. **離職 = `is_active = false`,不是 `DELETE`** —— 與 `test_01` 的處置同一條規則(見 §3)。
3. ⚠️ **稽核軌的保證變強了,但【不是型別層的】** —— 這句 v3 寫過頭,2026-08-16 R3 更正:
   `staff_id UNIQUE` **只擋「同時綁兩個 Auth user」**。
   🔴 **`DELETE` 掉那列再 `INSERT` 一列,就把 `staff_2` 重綁到另一個人身上了** ——
   而歷史稽核的解讀會跟著翻轉,**零訊號**。
   ⇒ **「永不重用」目前靠的是【寫入只經 migration review】的流程層,不是型別。**
   **⇒ 而那正是本規格自己說要避免的「靠人記得」。**

   **補上型別層的那一半(本片必做):**
   > **映射表的列【禁止 DELETE】** —— 加一支 `BEFORE DELETE` trigger `RAISE EXCEPTION`,
   > 訊息寫明「代號永不重用(Sean 2026-08-16 拍板);要停用請走 Auth 側 disable,不要刪這列」。
   > **驗收**:A 組加一格 —— **`delete from admin_user_staff_map` ⇒ 必須紅**(壞輸入要響);
   > 且 **`insert` 一列合法的 ⇒ 必須成功**(好輸入要安靜)。
   ⚠️ **這道 trigger 擋得住誤刪,擋不住有意的人**(他可以先 drop trigger)——
   **它的目的是讓「重綁」變成一個需要刻意繞過的動作,不是變成不可能。**
- **`ON DELETE RESTRICT`**:**Auth user 不准被刪**,要停用走 Auth 的 ban/disable。
  🔴 理由同 `test_01`:刪掉會讓映射消失,而稽核軌指向的 `staff_id` 就再也查不到是誰登入的。
- **換 email 不影響**:綁的是 `auth.users.id`(uuid),不是 email。
  📎 這正是 plan `§7-Q3=C` 當初拍「帳號用 email」時要的職責分離。

### 🔴 `staff_id` 的參照完整性:**沒有 FK,而這是已知且刻意的**

跨庫,Postgres 建不了 FK。**三個候選,本規格選 (c),理由寫在下面:**

| 案 | 做法 | 為什麼不選 / 選 |
|---|---|---|
| (a) | 在報價單庫**鏡像一份 staff 表**並同步 | ❌ 多一條同步鏈,而同步失敗是靜默的 |
| (b) | 不驗,應用層自己小心 | ❌ 那不是設計,是省略 |
| **(c)** | **寫入端唯一入口 + CHECK 白名單** | ✅ 見下 |

**(c) 具體**:`staff_id` 加 `CHECK (staff_id IN ('sean','staff_1','staff_2'))`。
- **白名單是硬編碼的,而那正是它的價值**:新增員工 = 一支 migration = 一次 review。
  **本線的目的是「知道是誰」,而不是「方便加人」。**
- ⚠️ **代價寫清楚**:A 庫加了新 staff 而這裡沒改 ⇒ 那個人**綁不了帳號**(insert 被 CHECK 擋)。
  **那是 loud 的,不是靜默的** ⇒ 可接受。
- 🔴 **`test_01` / 系統帳號都不在白名單裡** ⇒ **它們在型別層就綁不了帳號**,不靠人記得。

`auth_user_id` **要等 Sean 在 Supabase 後台開完帳號才存在** ——
而 migration 是在那之前跑的。⇒ **建表時那張表必然是空的。**

⚠️ **而 v3 之前全文沒有任何一句說「那誰來塞」** —— (c) 案自稱「寫入端唯一入口」,

## §4 硬規則

### 4.1 🔴 禁用 `IF NOT EXISTS` / `OR REPLACE`

一律裸 `CREATE`。理由與失敗形狀見 `docs/patterns/revoking-function-execute-in-supabase.md` §3.2。
**一句話**:repo 與正式庫可能不一致;不一致要**當場紅**,不要靜靜跳過 ——
**跳過之後,本片的 `REVOKE` 與斷言會對著那個既有物件跑而且很可能通過,拿到綠燈而什麼都沒建。**

### 4.2 前提斷言(B1-b 開頭)

✅ **fail-closed 斷言在報價單 repo 是既有做法**:
量法 `git grep -li "RAISE EXCEPTION" origin/main -- supabase/migrations | wc -l` ⇒ **12**
(分母 `git ls-tree --name-only origin/main supabase/migrations/ | wc -l` ⇒ **16**)。

**必含:**
1. **2FA 前提**(`§5②` 那次查詢的接班人):
   `auth_state.require_2fa = false` 且 `totp_devices` 零列 且 `recovery_codes` 零列,
   否則 `RAISE EXCEPTION`,訊息直接指向 plan §7-3「本線範圍必須當場擴張」。
   🔴 **放 B1 不放 B2**:整個 7 片的拆法建立在「不碰 TOTP」上,**B1 就已經依賴它**。
   📎 **把「我 08-16 查到 0」換成「每次 apply 都再問一次」** —— 查到的事實會過期,斷言不會。
2. **物件形狀前提**(codex 關卡1 #5 折入):
   `auth.users` 存在且 `id` 是 `uuid`;本片要建的表**不存在**(裸 `CREATE` 會撞名,但斷言要先講清楚為什麼);
   `public` schema 存在。**查無 / 型別不符 ⇒ `RAISE EXCEPTION`。**
   ⇒ **等於把未解的 `§5③` 一致性檢查,縮到本片真正碰到的那幾個物件上就地做掉。**

| # | 送法 | 尾端失敗後,前面的 `CREATE` | 判定 |
|---|---|---|---|
| A | 整份當**一則訊息**送(`psql -c "a; b; c"`) | **0 張**(全回滾) | 隱式交易 |
| B | **逐句送**(`psql -f`,無明文 BEGIN) | 🔴 **2 張留著** | **無原子性** |
| C | 逐句送 **+ 明文 `BEGIN`/`COMMIT`** | **0 張** | 全回滾 |
| D | 一則訊息 **+ 明文 `BEGIN`/`COMMIT`** | **0 張** | 全回滾,**無副作用** |
| E | 檔**中間**寫了 `COMMIT`,之後才失敗 | 🔴 **2 張,前半被釘死** | 最毒 |
| F | `BEGIN` 裡放 `CREATE INDEX CONCURRENTLY` | 整支失敗(`cannot run inside a transaction block`) | 例外情境 |

### 🔴 結論(這條把「未知的阻塞」變成「我自己手上的規則」)

**我不需要知道 `apply_migration` 是 A 還是 B** ——
**只要我在 migration 檔開頭寫 `BEGIN;`、結尾寫 `COMMIT;`,A/B/D 三種送法都是原子的。**

⇒ **B1 的硬規則三條:**
1. **檔案開頭 `BEGIN;`、結尾 `COMMIT;`。**
2. 🔴 **檔案中間絕不出現 `COMMIT`**(實測 E:那會把前半釘死,而後面失敗你也救不回來)。
   🔴 **量法(R3 更正 —— 我第一版的守門有三個旁通,實測過):**
   ```bash
   grep -ciE '(^|;)[[:space:]]*(commit|end|rollback)[[:space:]]*;' <本檔>
   # 必須恰好 1，且那一命中在最後一行
   ```
   **第一版寫 `grep -ci '^ *commit;'`,四臂實測它放行三種毒檔:**
   | 檔的形狀 | 舊守門 | 新守門 |
   |---|---|---|
   | 正常(檔尾一個 COMMIT) | 1 ✅ | 1 ✅ |
   | 同一行 `select 1; commit;` | **0**(看不見) | **2** 🔴 抓到 |
   | 中段 `ROLLBACK;` | **1 過關** | **2** 🔴 抓到 |
   | 中段 `END;`(COMMIT 同義字) | **1 過關** | **2** 🔴 抓到 |
   ⇒ **`ROLLBACK` 與 `END` 的毒性等同實測 E**:交易在中途結束,後面每句各自 autocommit。
3. ⚠️ **不得使用不能在交易內執行的語句**(`CREATE INDEX CONCURRENTLY`、`VACUUM`…)。
   B1 用不到,但**寫下來免得下一個人加了之後整支炸而不知道為什麼**(實測 F 的錯誤訊息會直說)。

**這才是這一項該有的收法:不是查到答案,是讓答案不重要。**

🔴🔴 **2026-08-18 補(codex 關卡1 R3 `[不確定]`,角度=假設審查)——【台帳】那一半本節從頭到尾沒有提**:

   ```

   **原版錯在哪(留著,因為那是「守門在合格檔上誤報」的實例):**
   | 道 | 原版 | 在合格檔上的結果 | 病因 |
   |---|---|---|---|
   | ① | 不剝註解 | **誤報 2 處** | 抓到我自己寫的規則說明註解 |
   | ② | `grep -ci '^ *commit;'` | 通過,但**放行三種毒檔** | 只想到 `COMMIT` 一個字(見 §4.4) |
   | ③ | `CREATE …` 含 TRIGGER | **3 vs 2 不符 ⇒ 誤報漏列** | trigger 沒有 ACL,本來就不該列 |
   ⇒ 📎 **一道守門在【它該放行的東西】上紅,和在【它該擋的東西】上綠,一樣糟** ——
   前者會讓人把守門關掉。
3. 🔴 **apply 當下要看螢幕**:有沒有
   `there is already a transaction in progress` 這類**巢狀交易 WARNING**。
   - **有** ⇒ 代表 `apply_migration` 自己也包了一層。**不影響正確性**(§4.4 實測 D 已證仍全回滾),
     但**記下來寫回 §4.4**,那是我們第一次知道它的送法。
   - **沒有** ⇒ 🔴 **代表【送法仍然未知】,不代表它是逐句送**(R3 F5 更正)——
     送法 A/D 同樣零 WARNING;而 MCP 若走 HTTP API,`NOTICE`/`WARNING` **常根本不回傳**。
     ⇒ **不要把「沒看到 WARNING」寫回 §4.4 當成「已知它是 B 那種」** ——
     那會把一個沒有根據的事實記成權威紀錄。**原子性不受影響(明文 `BEGIN` 涵蓋所有已測送法),
     而送法本身仍是未知。**
   ⚠️ **這一項【只有第一次 apply 的那幾秒】看得到。** 事後查 log 不一定留。
4. 🔴 **apply 失敗時,先看它紅在哪一行**,再決定要不要重跑:
   - 紅在**前提斷言** ⇒ 世界跟規格假設的不一樣 ⇒ **停下,不要改斷言**(那是 R4 換路訊號)
   - 紅在 `CREATE` **撞名**(`42P07`)⇒ ⚠️ **兩種成因,不要跳到結論**(R3 F7):
     ① **上一次部分成功後重跑**(更常見)② `§5③` 那個不一致真的存在。
     ⇒ **先查那張表是誰建的、什麼時候建的**,再決定。**兩種成因都不准加 `IF NOT EXISTS`。**
   - 紅在**尾端收權斷言** ⇒ 檢查步驟 3 的 WARNING:**若整支沒回滾,那張表已經建好了**
     ⇒ **此時不可重跑**(會撞名),要先確認實際狀態。
   - 🔴 **紅在其他地方**(語法錯、權限不足、`REVOKE` 失敗…)⇒ **落在上面三類之外,
     不要硬塞進最像的那一類。** 先把錯誤原文貼出來再判。
   - 🔴🔴 **根本沒有紅、而是【沒有回應/連線中斷/timeout】** ⇒ **`COMMIT` 有沒有發生【未知】**。
     **這是最危險的一種**:重跑可能撞名(表已建)、也可能正常(沒建)。
     ⇒ **不要重跑。** 先用唯讀查詢確認那張表在不在、trigger 在不在,再決定。
5. **apply 成功後**:跑 §6 B 組(報價單庫唯讀)。`B1-a` 另跑 §6 C 組(A 庫)。

## §8 決策點(codex 關卡1 兩輪逼出來的)· **狀態:1 題已拍,2 題是判讀**

> 🔴🔴 **三題的來源強度不同,不要混著引:**
>
> | 題 | 狀態 | 來源強度 |
> |---|---|---|
> | `Q-B1-1` | ✅ **Sean 拍板甲** | **逐字**:「甲｜新人拿【新代號】staff_3,舊的停用不刪」 |
> | `Q-B1-2` | 🟡 **主視窗判讀為甲** | ⚠️ **Sean 未逐題回覆。這是判讀,不是拍板。** |
> | `Q-B1-3` | 🟡 **主視窗判讀為甲** | ⚠️ 同上;且本題**不急**、屬 `B6` |
>
> **⇒ 引用 `Q-B1-2` / `Q-B1-3` 時不得寫成「Sean 拍板」。**
> 📎 今天已經有太多「結論對、來源錯」的實例 —— 而錯的來源會讓下一個人去查一個不存在的拍板,
> 查不到之後**連結論一起丟掉**。

🔴 **`Q-B1-2` 甲案的一個前提,不是可選項:**
甲案(兩邊各做一次)**含那道「登入時回頭確認 A 庫 `staff.is_active`」**(已歸給 `B5`,見 §2)。
**少了它,「漏停一邊」就沒有任何東西擋** ⇒ **那道不是加分項,是甲案成立的條件。**

```
Q-B1-1：員工代號可以重複使用嗎？

  情境：staff_2 這個人離職，之後新人接手。新人要用哪一個代號？

  A: 甲｜代號永不重用（推薦）

       好處：翻舊紀錄時「staff_2 做的」永遠指同一個人。
       代價：代號會越來越多，名冊上會有一排停用的人。

     乙｜代號可以接手
       新人沿用 staff_2。
       好處：名冊乾淨。
       🔴 代價：過去的稽核紀錄會變成【指向新人】——

  我推薦甲。理由一句話：乙會讓我們花整條線建立的稽核軌，在第一次換人時就失真。
