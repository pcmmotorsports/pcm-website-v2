## §1 🔴 為什麼現在【不】跑(這一段比規格本身重要)

主視窗裁定,原字採用:
> **你造的負載形狀是你選的**(N 發並行你的靶),
> **而真實的負載形狀是八個窗在做不同的事**(build / vitest / codex / playwright 混著)。
> **如果紅與「形狀」有關而不只與「數量」有關,你造出來的那一格會是一個【不存在的世界】。**

📎 同族:memory `feedback_green-in-a-world-that-cannot-happen`
(**突變會紅、覆蓋率算它、零症狀** —— 一格可以既有判別力又測一個不會發生的狀態)。
🔴 **而這一次是它的鏡像**:我可能造出一個**紅得出來、而那個紅不會在真實世界發生**的世界。

**另一個理由(成本不對稱)**:儀器現在是準的(第三版標記檔),而**八個窗持續在跑四綠**
⇒ **高並行的樣本會自然發生,帶著可信的數字**,而那些是**真實負載形狀**下的樣本。
⇒ **等它來的成本是 0,造它的成本是「可能得到一個不存在世界的答案」。**

## §3 若將來真的要跑:規格與雙向判準

**觸發條件(全部成立才跑,缺一不跑)**
```
1 被動收集跑了【足夠久】而「高並行」那兩格仍然是空的
  ——「足夠久」由主視窗定，不由執行者自己判（否則它會被解釋成「我等不及了」）
2 而同期【確實發生過】高並行（用 RUN-CONTEXT 自己證明，不是憑印象）
  ⇒ 若連高並行都沒發生過，缺的是負載不是實驗
3 主視窗排定時間窗（會吃 CPU，其他窗要知道）
```

**設計**
```
自變數  刻意維持的並行 vitest run 數 N ∈ {0, 1, 2, 4}
        🔴 靶用【我自己造的】拋棄式 run，不去干擾別窗（照 mutation-harness-restore 的紀律）
        ⚠️ 而它們必須走 dev-four-greens.sh 才會落標記檔 ⇒ 儀器數得到它們
應變數  完整套件的紅率、逾時格數、Duration
每格    ≥5 發（低於 5 發連「巧合」都排除不了）
```

**🔴 雙向判準(事前寫下,事後不得改)**
```
支持「並行造成紅」   N=0 那組紅率顯著低於 N=4 那組
                    且 N=4 的紅【集中在會逾時的那幾類】（spawn / jsdom / 純 TS 單元三類都要看）
推翻                N=4 全綠，或 N=0 也照樣紅
                    ⇒ 🔴 這個方向【更重要】：它會把整條負載假說打掉，而那省下所有後續投資
兩者皆非            紅率有差而不顯著 ⇒ 明寫「樣本不足」，不得寫成「傾向支持」
```

**🔴 三條事前限定(照 `#608` 那個已死假說的教訓)**
```
1 N=0 那組【必須在真的安靜時跑】—— 不夠閒的時候跑它，紅了會誤推翻一個可能是對的假說
2 Duration 不可單獨當判準：它【部分內生】（逾時自己會把時間拉長）⇒ 慢可能是果不是因
3 🔴 F-2 的二分不夠 —— 第三類（純 TS 單元）也會逾時（C 窗實錘）
   ⇒ 每一組都要分三類記，不可以只記總數
```

- **本檔不是批准。** §3 只有在 §3「觸發條件」三條全成立、且主視窗排了時間窗之後才動。
