### 🔴🔴 基線要建在【哪一張表】—— 這一格原本是缺的,現在有量測了

**起因**:Sean 跑 `pg_auth_members` 回 **2 列**(postgres / authenticator),而稍早那發
`pg_has_role(...,'MEMBER')` 回 **4 列**(supabase_admin / authenticator / supabase_storage_admin / cli_login_postgres)。
**差兩個。主視窗把「為什麼」丟回給我,而我去量了、沒有推。**

**本機重建一個同形狀的世界**(`svc` = service_role;`pgx` = postgres;
`storage_like`/`cli_like` 是 **pgx 的成員**、不是 svc 的;`admin_like` = superuser):
```
尺 A  pg_auth_members 直查 roleid=svc      ⇒ pgx
尺 B  pg_has_role(...,'MEMBER')            ⇒ admin_like, cli_like, pgx, storage_like, supabase_admin
```

⇒ 🔴 **差額的成因量到了,而且是兩個不同的來源**:
```

  而 postgres 是 service_role 的直接成員（Sean 那張表:admin_option=true / inherit_option=true）
  ⇒ 🔴 尺 A【看不到它們】，因為 A 只問「誰被直接授予 svc」
```

### 🔴🔴 而若短命成立,問題不是「漏了一列」,是【基線會閃爍】—— 這是白名單那族的第三次

```
有人跑一次 supabase CLI 登入 ⇒ 集合多一列 ⇒ 紅；他登出 ⇒ 又綠

```
**R4 審查者說它沒有解**:「已知短命名單」本身就是白名單 ⇒ 會過期 ⇒ 那一格又要自己有告警。

**🔴 而我提一個【不靠名單】的解 —— 用結構屬性,不用名字**:
```
短命角色與常駐角色有一個【機械上分得開】的差別：**短命的通常帶有效期**（`pg_roles.rolvaliduntil`）。
⇒ 基線只收 `rolvaliduntil IS NULL`（＝沒有到期日 ＝ 常駐）的成員；
   帶到期日的那些【本來就會自己消失】，把它們算進基線等於把時鐘算進去。
✅ 為什麼這不是白名單：它不列舉【哪些名字】，它問【這個角色是不是被建成會過期的】。
   ⇒ 平台明天換一個名字建臨時角色，這條仍然成立；而白名單當場漏。
   ⇒ 🔴 這正是今天那條「換屬性不是換閾值」的正面用法。
⚠️ **而它可能不成立** —— 我沒有任何證據說 Supabase 的 CLI 角色帶 `rolvaliduntil`。**這是待驗,不是結論。**
⚠️ 而若它們**不帶**到期日 ⇒ 這條路死掉，那時才回頭談名單，**並且那份名單要自己有過期告警**。
```

# ⑥ 裁定:基線用哪一把尺(2026-08-19,Sean 拍甲之後,主視窗指派)

> **這一格原本是「還沒定案」,現在定案。不需要 Sean、不需要新查詢 —— 材料早就量完了,
> 只是沒有人寫下最後那一句。**

## 裁定(一句話)

> **基線用尺 B:`pg_has_role(rolname,'service_role','MEMBER')`,superuser 留在基線裡不過濾。**

## 理由(三條,全部是量到的,不是推的)

```
① 尺 A（pg_auth_members 直查）漏【遞移】
   實測（本機同形狀世界，事件二「有人被加進 postgres 而遞移取得 svc」）⇒ **A 沒反應**
   而正式庫確實有遞移成員：supabase_storage_admin rolsuper=false
   ⇒ 它出現在 pg_has_role 裡【只能】是遞移，不是 superuser 恆真
   ⇒ 用 A 當基線 ＝ 對「有人繞路拿到權限」完全無感。

② 尺 C（閉包 + 排 superuser）漏【新的 superuser】
   實測（事件一「新增一個 superuser」）⇒ **C 沒反應**
   ⇒ C 的「乾淨」是拿盲區換來的。我上一版選 C，那是錯的。

③ 尺 B 兩種事件都紅。
   而「superuser 恆真」不構成反對理由：
   🔴 **它毒得死【空集合斷言】（「這個集合必須是空的」⇒ 永遠 RAISE），
      毒不死【相等斷言】（「這個集合與上次相同」⇒ 常數項在兩邊同時出現、互相抵銷）。**
```

## 🔴 附帶裁定甲:**基線述詞不得含 `current_user`** —— 這是本次新抓到的

```
Sean 那發 pg_has_role(...,'MEMBER') 回【4 列】而不是 5 —— `postgres` 不見了。
成因不是遞移、不是 superuser：**是查詢自己寫著**
    AND rolname NOT IN ('service_role', current_user)          （本檔,`grep -n "NOT IN ('service_role', current_user)"` 兩處命中）
而他以 postgres 身分在 SQL Editor 跑 ⇒ **postgres 把自己過濾掉了。**
```
⇒ **`current_user` 隨【誰執行】而變。** 把它留在基線述詞裡,
**同一個真實世界會因為「誰 apply」而產生兩份不同的基線** ——
那是最惡的一種漂移:它不會紅在該紅的時候,會紅在換人 apply 的時候。

**⇒ 判準(可機械套用):述詞可以固定,不可以隨執行者變。**
```
✅ 留著 rolname NOT LIKE 'pg\_%'   —— 固定述詞，對每個執行者相同。
```
