| # | 內容 |
|---|---|
| ① **它是什麼** | **apply-time sanity check** —— 隨 migration 跑的一次性快照 |

| ⑤ 🔴 **給下一個人的一句** | **想為它加任何東西之前,先問:「我要擋的那件事,發生在 apply 之前還是之後?」**<br>**答案是「之後」⇒ 你要找的是 `#554`,不是這個檔。** |

## §2 為什麼換(病根一句)

**「查的集合比世界窄」在這條線出現三次**(表級 → 欄級 → 欄位枚舉),R2 又添 `MAINTAIN` 與
`WITH GRANT OPTION` **兩個新成員**。
⇒ **只要用 `has_*()` 逐權限型別枚舉,這個債就永遠長。**

🔴 **決定性的證據(V 窗拋棄式 PG 17.10 實測 S0–S3)**:
| 狀態 | 實測 |
|---|---|
| S0 新表 | `pg_attribute.attacl` 非空欄數 = **0** |
| S1 `grant update (a)` + 表級 MAINTAIN | attacl 非空**恰 1 欄**;**表級授權不污染 attacl** |
| S2 revoke 欄級 | 歸 **0**、無空陣列殘留 ⇒ **零誤報** |
| S3 `grant references … with grant option` | `relacl` 逐字 `r1=x*/postgres`、MAINTAIN 顯示 `m` |

⇒ **`WITH GRANT OPTION`(`*`)與 `MAINTAIN`(`m`)在儲存層免費看到** ——
**而那正是我昨夜花一整段時間補進清單的兩樣東西。**

## §3 三層設計(各司其職,射程 = 儲存位置)

### 第 1 層 · 儲存層白名單(主力,免枚舉)
- **`relacl`**:現行 `v_extra` 已是 **grantee 級**;**升級為 aclitem 級** ⇒ 連 `*`(grant option)與 `m`(MAINTAIN)一起看到
- **`attacl` sweep**:**非空即紅,並印出來** ⇒ 覆蓋 **所有欄 × 所有權限型別(含未來 PG 新增)× 所有角色**,一道查詢
- 🔴 **射程明確**:relacl = 表級 / attacl = 欄級。**不用腦記,看儲存位置就知道。**

#### 🔴 **MA-3(V 窗 R4 must-add):owner 身分本身要被斷言** —— R2 `#5` 那題的答案

我在 plan 第一版寫「新設計必須答:owner 是不是白名單的一部分?**這一題我現在答不出來**」。
**V 窗答了,而且是實測(F6)**:
```sql
coalesce(relacl, acldefault('r', relowner))   -- v_extra 既有讀法
  ⇒ 展開後 owner 的 DELETE / TRUNCATE 【逐字可見】(postgres=DELETE, postgres=TRUNCATE)
```
⇒ **儲存層讀得到 owner 的隱含權限** ⇒ 第 1 層白名單加一條:**斷言 `relowner` = 預期身分(`postgres`)**。

🔴 **形狀值得記**:R2 `#5` 的 owner 法(把 SET 可達角色變成 owner)在新設計下
**紅在「owner 身分不符」** —— **不是把 owner 排除在射程外,是把 owner 身分本身變成被斷言的值。**
📎 **與既有拍板不衝突**:出威脅模型的是「`postgres` 本人作惡」,**不出模型的是「owner 換人」**。

### 第 2 層 · 函數層(只留一道,**不可退役**)
- **predefined roles**(`pg_write_all_data` 族)的**隱含權限不進 `relacl`/`attacl`**
- V 窗實測:`grant pg_write_all_data to r3` ⇒ `has_table_privilege('r3','t','UPDATE')` = **t**,
  而 `relacl` = **NULL**、attacl 非空欄 = **0** ⇒ **儲存層對隱含權限全盲**
- ⚠️🔴 **不要因為「儲存層更完整」就把函數層整個拆掉** —— 那會長出新的靜默失敗面

#### 🔴 **MA-1(V 窗 R4 must-add):第 2 層的權限清單【必須機械推導,不准手寫】**
第 2 層躲不掉「對每個可達角色查**哪些**權限」⇒ **枚舉債會在第 2 層轉世**,
**手寫清單 = R2 `#4`(漏 `MAINTAIN`/`TRIGGER`)原地復發** —— 換了框架卻把同一個病帶過去。

**機械解(V 窗實測 E6)**:
```sql
select distinct privilege_type from aclexplode(acldefault('r','postgres'::regrole))
  ⇒ PG 17.10 回【恰 8 項,含 MAINTAIN】
```
⇒ **由跑著的那台伺服器自己說出它有哪些表權限型別**,PG18 新增型別**自動入列**。
迴圈對可達角色逐項查這個**推導集**,不查任何手寫陣列。
📎 實測 F4:`has_table_privilege('pg_maintain','t','MAINTAIN')` = **t** ⇒ R2 `#4` 的路徑被接住。
📌 同款技巧 `acldefault('f',…)` 可推導**函式**權限集 ⇒ nit `#9`(函式迴圈)也用得上。

🔴 **這條的份量,精確版(V 窗窄確認打回我的原句,我接受)**:
> **少了 MA-1,「不用維護清單」只對【第 1 層】成立 —— 而 R2 `#4` 住的正是第 2 層。**

⚠️ **我原本寫的是「少了它,丙只是把清單從一個地方搬到另一個地方」—— 那句講重了半格,已撤回。**
**差別在哪(這半是重點,不是措辭)**:第 1 層的免枚舉收益(**欄 × 角色 × 型別三個維度**的債)
**不因 MA-1 缺席而消失**。原句會讓未來某個發現「`acldefault` 在某環境不可行」的人
**誤以為整個丙案失去意義而回退全部** —— 而他該做的只是補第 2 層。

📎 **這件事今天發生了兩次,方向相反,值得並記**:
- 我打回主視窗的「丙之後不會再長新臂」—— **好處講得比實際大**
- V 窗打回我的「只是搬家」—— **壞處講得比實際大**
⇒ **兩者同一個病:一句有說服力的話,它的【範圍】比它的【方向】更容易寫錯。**
而**兩次都是下游打回上游**。

## §5 驗收設計(要能被單獨打紅,否則不算)

每一格照本線既有紀律:**世界 + 負測 + 前提斷言**,且**突變只紅它自己**。
- attacl sweep → 突變:授一個欄級權限 ⇒ 必紅;撤掉 ⇒ 必綠(S2 已證零誤報)
- relacl aclitem 級 → 突變:加 `WITH GRANT OPTION` ⇒ 必紅(舊查法看不到,可做**新舊對照**)
- **owner 法**(R2 #5)→ 突變:把 SET 可達角色變成 owner ⇒ **紅在「owner 身分不符」**(MA-3)

### 🔴 MA-2(V 窗 R4 must-add):predefined role 那一對驗收 —— **我把它的實測用超範圍了**

我在 plan 第一版寫「用 V 窗的 r3 實測當驗收格」,並**主動請它確認我有沒有用超範圍**。
**答案:有。**
> r3 與 `service_role` **零 membership** ⇒ **我的可達性迴圈根本掃不到它** ⇒ 照抄當驗收格,**紅不起來**。

⇒ 突變的 grant 對象**必須是 `service_role`**(或 SET 可達角色)。
而且 🔴 **`INHERIT` 是【每筆 grant 各自記】的(PG16 起)** ⇒ **兩個世界紅在不同的子檢查,要分成兩格**:

| 突變世界 | 有效權限集檢查(恰好 `{SELECT,INSERT}`) | 可達性迴圈(第 2 層) |
|---|---|---|
| `grant pg_write_all_data to service_role`(inherit 預設 true) | **紅**(E1:成員有效權=t) | 也紅 |
| 同上 `with inherit false, set true` | **綠 = 盲**(F1:有效權=f) | 🔴 **唯一會紅的**(F2 SET=t / F3 自身權=t) |

🔴 **只做上面那一格是不夠的**:迴圈被拆掉時它**照樣紅**(紅錯來源)
⇒ **`SET-only` 那一格才是「第 2 層不可退役」的真證據。**

📎 **V 窗自己在這裡也錯過一次並留痕**:它先用 `ALTER ROLE noinherit` 想測,
而**那不改既有 membership**(實測 E4 因此仍 `t`)⇒ 它測到的不是它以為的東西。
**修正版是顯式 `with inherit false`。** —— 兩個窗在同一個機制上各錯一次,方向不同。
