## 2. 成本公式結論

### 2.1 報價單實際用的公式形式(R-XLSX §2,逐字)

```
明細小計   G{n} = F{n} * E{n}                     單價 × 數量
營業稅     G{tax} = F{tax} * 0.05                 5% 外加(F{tax} = 未稅小計)
總計       G{n} = SUM(...)                        明細 + 稅金
成本→售價  報價!F{n} = 成本!F{n} * 1.2   (一般零件)
           報價!F{n} = 成本!F{n} * 1.25  (特定料件)
建議售價   成本!J{n} = ROUNDUP(F{n} * 1.2, -1)    ×1.2 後無條件進位到十位
```

### 2.2 與規格 §1.2b 記載的 `x*0.63*45*1.15`(曾低估 17%)是否一致

**🔴 不一致,而且不是「數值差異」,是兩條不同層級的公式:**

| | 報價單實測公式 | 規格 §1.2b 記載的公式 |
|---|---|---|
| 語意 | **加價**(成本 → 售價),markup ×1.2 / ×1.25 | **到岸成本**(供應商牌價 → 落地成本):`0.63`≈折數、`45`≈匯率、`1.15`≈運費/關稅加成 |
| 在這 15 檔中 | ✅ 存在(但**只有 1/15 檔**做跨表引用) | ❌ **零命中** |
| 匯率係數 | R-XLSX §3 逐字:「**匯率 ❌ 完全沒有**……無 `*45`、`/33` 之類的換匯係數,也無匯率儲存格」 | 公式核心即匯率 |
| 關稅/運費 | R-XLSX §3:關稅 ❌ 無計算;運費 ❌ 無計算欄(只在注意事項條款文字) | `1.15` 即此 |

**明確差在哪**
1. 規格 §1.2b 引 Sean 逐字「我們報價單都有成本公式」——**部分成立**:有的是「成本→售價」加價公式,**不是**被實證低估 17% 的那條到岸成本公式。
2. 「低估 17%、真值 `x*0.63*45*1.15`」的來源是 memory `project_eazi-grip-agency-launch-decisions`(另一條供應商線),**在本批 15 檔維修報價單中讀不到**。規格把兩件事併成一句,應拆開重寫。
3. 因此規格 §1.2b「接報價單成本公式前先驗證公式正確性」這個前置條件**仍然成立,但對象要改**:要驗的是 eazi-grip 那條到岸成本公式,不是報價單的 ×1.2。

### 2.3 就算要搬,報價單公式也不可直接沿用(R-XLSX 實證的四個地雷)

- **加價率每格各自寫死**,`defined_names` 全空、**無任何具名參數儲存格** ⇒ 沒有單一真相可搬。
- **跨表引用列號已錯開**(報價 r12 → 成本 r11、報價 r21 → 成本 r18)⇒ 任一邊增刪列會**靜默算錯**。
- **小計公式覆蓋不完整**:多數檔 `G=F*E` 只填部分列,有一檔 31 列明細只有 1 格有公式;R-PDF §1.3 另實測「售價非公式產生、有列與 數量×單價 對不上」。
- **稅基 SUM 範圍與實際明細範圍普遍不符**,且 12 檔中 4 檔稅金列留空(該單未加稅)⇒ **報價單不是銷項憑證,不可當 401 銷項來源**。

### 2.4 順帶(規格未提但影響接單據)
- 報價單 **無任何單號/流水號**,唯一識別靠檔名;同案多版本用 `(定案)`/`正式`/`oem`/`-1`/`成本` 後綴區分,**無版本欄位、無 supersedes 關係** ⇒ 系統必須自行發號並建 `quote_group + revision`。
- 報價日期是 `=TODAY()` **動態公式**,每次開檔就變 ⇒ **沒有日期快照**,系統必須自己存 `issued_on`。
- 折扣無欄位,以 `優惠:<遮蔽>` 文字貼在總計旁、**未進 SUM**;收款沖銷用**負數單價明細列**表示 ⇒ 兩者都要正規化成欄位。

## 3. 憑證附件功能的真實需求(依 R-IMG 實況,非想像)

### 3.1 母體事實(不是推測)
- 28 張影像:**發票 0 張、收據 0 張**。分三類:A 損傷/現況特寫(約 15)、B 證件/車籍翻拍(4–5)、C 完工/交車照(約 8)。
- 🔴 **沒有任何一個案子只有 1 張影像**:實測分組為 9 / 8 / 6 / 3 張。
- 檔名全部是 LINE 匯出格式 `S__<8-9 位數字>[_0].jpg`;同批傳輸連號。

### 3.2 硬需求(直接可寫進規格)
1. **多檔上傳是主要形態,不是可選項**:必須支援多選 + 拖曳整批、一次 10 張以上。
2. **排序用檔名數字,不可用上傳時間**:A 類是逐零件拍的,順序 = 報價單品項順序;唯一順序線索是 LINE 連號。
3. **時間戳不可信**:實測 5 張 EXIF 相機欄位全為 null(LINE 已剝除);`ContentCreationDate` 無法判定是拍攝或下載時間 ⇒ **上傳時間由系統自記,拍攝日期要人工填**。
4. **大小/尺寸**:實測 77 KB – 1.88 MB、最大邊 2364 px ⇒ 單檔上限**不得低於 5 MB**(建議 10 MB)。
5. **縮圖是必需品且 ≥ 400 px**:直式(0.75)與橫式(1.33)混在同一組;200 px 縮圖**看不出刮痕與缺角**,等於縮圖失效。建議固定容器 + `object-fit: cover`。
6. **兩個正交維度,不可壓成單一 enum**(使用者已用實體資料夾在做):
   - `stage`:施工前/損傷佐證 · 完工/交車 · 證件/車籍
   - `purpose`:保險理賠 · 一般維修
7. 🔴 **PII 分級是硬需求**:B 類含姓名、證號、出生日期、完整住址、大頭照、車牌、VIN,風險比零件照高三個量級;實務行為是「證件正反面全拍、混在同一批 LINE 訊息傳」⇒
   - 附件需 `is_sensitive`,預設**前台/客戶端不可見**;
   - **上傳當下就要分類**(不能事後),否則證件會混進「可以給客戶看的完工照」相簿;
   - **縮圖也要受權限保護**——縮圖若走 public CDN 等於證件外洩。
8. **OCR:結論是不值得做**。A+C 類 23/28 張完全無文字;B 類雖有結構化文字但底紋是密集防偽花紋、塑膠套反光、翻拍梯形變形、民國/西元混用,且車籍資料在報價單裡已經有了。若真要做,投報最高的只有行照的「廠牌型式」+「車身號碼」兩欄,且必須「OCR 出草稿 → 人工確認」而非直接落庫。
9. **格式**:實際只有 jpg(27)+ png(1)。同層存在 `.psd` 中間檔(使用者會用影像軟體處理證件),只收 jpg/png 會擋掉——大概率可接受,但要知道。

### 3.3 🔴 關聯性:影像上零單號 ⇒ 上傳時必須強制綁單
- R-IMG §3 實測:**沒有任何影像上寫著訂單號、報價單號或料號**。關聯全靠三層間接線索:資料夾名稱(自由文字、三種命名格式混用)、兄弟檔案檔名、行照「廠牌型式」欄(且與報價單車型**拼法不一致**、不能當 join key)。
- 反例逐字:某保險案 3 張證件影像對應同層的和解書與定案報價單,但影像本身無任何線索;**拿掉資料夾結構後完全無法還原歸屬**。
- ⇒ 系統設計結論:附件**必須在上傳當下綁定單據 ID**(order/quote/repair id),不得靠檔名或資料夾推斷。

### 3.4 跨文件關聯鍵的真相(R-PDF §4)
- 報價單 ↔ 和解書 ↔ 警方初判表,**唯一可自動對上的鍵是「車牌」**;三者都沒有保單號、理賠案號、維修單號。
- 🔴 但報價單的**專用 `車牌號碼` 欄實測 12 檔全部空白**,車牌實際散落在 `電話` / `地址` 欄,換牌情形以 `舊牌(已換牌 新牌)` 塞在同一格 ⇒ 數位化時這是最需要清洗的一點,也代表**不能假設現有資料的車牌欄可用**。
- 保險案的金流方向:和解金由保險公司**直接匯入維修廠帳戶**(不經車主)⇒ 「維修單對象」與「應收帳款對象」不是同一人,規格目前沒有這個模型。

## 6. 一句話結論

真實 401 是**憑證分類表**(統計鍵 = 格式代號 × 稅別 × 進貨/固定資產),我方規格建的是**複式會計帳**(統計鍵 = 會計科目);兩套鍵不重疊,規格目前只有後者 ⇒ **就算把 §1.2a 全部實作完,401 仍然填不出來**。補齊 M1–M15 才談得上 C10 說的「可匯出給記帳士的憑證登錄簿」;M16 則是另一個 domain(維修佐證影像),不能與會計憑證共用一張表。
