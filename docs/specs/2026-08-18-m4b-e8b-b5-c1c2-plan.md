### migration 草稿的欄位設計(§7-3 已讀完,不是待辦)
逐字實查 `docs/specs/2026-08-16-m4b-e8b-b1b-migration-draft.sql`:`:136` `staff_id text NOT NULL UNIQUE`、`:146` `CHECK (staff_id IN ('sean','staff_1','staff_2'))`、`:139` 逐字「跨庫建不了 FK,所以用 CHECK 當參照完整性的替代」。
```sql
sub_kind  text NULL CHECK (sub_kind IS NULL OR sub_kind IN ('user','fallback','bootstrap'))
staff_id  text NULL                       -- 🔴 刻意不抄 B1-b 的人員白名單 CHECK
-- 🆕 跨欄一致性 + staff_id 值域(折關卡1 R2 兩條)
CHECK (
  CASE
    WHEN sub_kind = 'user' THEN staff_id IS NOT NULL AND btrim(staff_id) <> ''
    WHEN sub_kind IS NULL  THEN staff_id IS NULL
    ELSE staff_id IS NULL                 -- fallback / bootstrap
  END
)
```
⛔ **r2 初版那個 `OR` 串是【壞的】,留訃聞**:
~~`CHECK ((sub_kind='user' AND staff_id IS NOT NULL) OR (sub_kind IN (…) AND staff_id IS NULL) OR (sub_kind IS NULL AND staff_id IS NULL))`~~
🔴 **它放行 `sub_kind IS NULL` + `staff_id IS NOT NULL`** —— 三段分別是 `NULL / false / false`,
整式 = **`NULL`**,而 **Postgres 的 `CHECK` 對 `NULL` 是【通過】不是【擋】**。
⇒ 那正是它要擋的那個不可能狀態,而它會安靜放行。**改用 `CASE`:每個分支都回真正的布林,沒有 `NULL` 出口。**
🔴 **`btrim(staff_id) <> ''` 是折另一條**:r2 初版只管「非 NULL」,而 `staff_id=''` / `'   '` 照樣過
⇒ 與 `exchange.ts:71-74` 和 `isPayload` 的非空白判準**不一致**,而 DB 是最後一道。
### ✅ 已實測(2026-08-19T00:2x,拋棄式 Postgres 17.10、`LC_ALL=C`、不碰 `.env*`、不碰正式庫、已收攤驗死)
**兩種寫法 × 九個世界,同一發跑完。`check_violation` 攔下來當 `REJECT`,其餘 `ACCEPT`。**

| `sub_kind` | `staff_id` | 期望 | 舊 `OR` 串 | 新 `CASE` |
|---|---|---|---|---|
| `user` | `'sean'` | legal | ACCEPT | ACCEPT |
| `fallback` | NULL | legal | ACCEPT | ACCEPT |
| `bootstrap` | NULL | legal | ACCEPT | ACCEPT |
| NULL | NULL | legal | ACCEPT | ACCEPT |
| NULL | `'x'` | **ILLEGAL** | 🔴 **ACCEPT** | ✅ REJECT |
| `user` | NULL | ILLEGAL | REJECT | REJECT |
| `fallback` | `'x'` | ILLEGAL | REJECT | REJECT |
| `user` | `''` | **ILLEGAL** | 🔴 **ACCEPT** | ✅ REJECT |
| `user` | `'   '` | **ILLEGAL** | 🔴 **ACCEPT** | ✅ REJECT |

🔴 **雙向表演成立**:四個 legal 世界**兩種寫法都 ACCEPT**(正向對照 —— 證明量具不是「什麼都拒」);
五個 illegal 世界裡舊寫法**漏 3 個**、新寫法**全擋**。

⛔ **而這一發推翻了我自己手推的數字,留痕**:
我先前跟 Sean 報「三種不可能狀態裡漏一種」。**實測是五種裡漏三種。**
病根:**我手推時只列了三個 illegal 世界,`staff_id=''` 與 `'   '` 那兩個維度【不在我的測資裡】**

   結論裡「`CHECK` 對 `NULL` 放行」是 SQL 標準三值邏輯、跨版本穩定;
   而 `btrim` 行為在不同 locale 下未測 ⇒ **apply 那一片仍要在目標庫跑同一張表一次。**
🔴 **不抄人員白名單的理由(判斷,寫下來讓人推翻)**:B1-b 那個白名單管**誰可以【現在】被綁定**,而稽核表記**當時發生過什麼**。套上去 ⇒ 某人日後被移出白名單的那一刻,**寫入歷史本身開始 RAISE** —— 那是一張登入事件表,它壞掉的方式是「登入被稽核擋住」。
🔴 **而不加的代價寫全**(折 codex #23):**DB 不會擋 typo 與未知 ID** ⇒ 報表可能因為一個錯字分裂成兩個人;**且靜態 CHECK 本來也不會**因白名單日後移除人員而自動改變 ⇒ 兩邊都不是「自動正確」,差別只在**誰在什麼時候壞**。
🔴 **兩欄必須 NULL-able**:既有列沒有值,且混版部署期(admin 新 / 報價單舊)本來就會插入沒有 sub 的列。

### 🔴 驗收條件那一行(不是只寫在說明裡)
**「稽核 ✅」這一格在 apply 之前【不得勾】。** `login-event.ts` 檔頭逐字:console 是「**1 小時軌跡**」、DB 才是「留得住的那半」
⇒ **apply 之前,登入時的身分只活一小時。** 驗收表上寫的是「console 那半 ✅ / DB 那半 ⏳ 等 apply」,**不是「稽核 ✅」**。

### 格 18 / 18b · 兩開關四組合 —— 🔴 它證的不是功能,是**兩個東西沒有偷偷耦合**
```ts
// 18  發【開】收【關】= 分階段上線的中間態,也是第二開關存在的理由
it('🔴 發開收關:有 sub ⇒ 簽 v:2;而【舊 v:1 cookie 仍然收得進來】(沒有人被登出)', async () => {
  process.env.ADMIN_ISSUE_V2_SESSION = '1';
  delete process.env.ADMIN_REQUIRE_REAL_IDENTITY;
  // (a) 發:走 callback,上游帶 sub ⇒ 簽出的 cookie verifySession 回 v:2 且 sub 逐字相同
  // (b) 收:另外【raw 簽】一顆 v:1 ⇒ verifySession 必須【回非 null】
  //     🔴 (b) 是這一格的承重點:少了它,「發開」與「收開」耦合在一起也會綠
});

// 18b 發【關】收【開】= 退場中
it('🔴 發關收開:有 sub 也【不簽 v:2】;而 v:1 被拒', async () => {
  delete process.env.ADMIN_ISSUE_V2_SESSION;
  process.env.ADMIN_REQUIRE_REAL_IDENTITY = '1';
  // (a) 發:上游帶 sub ⇒ 簽出來的必須是 v:1(或依 §2 件2 表的第二列行為)
  // (b) 收:raw 簽的 v:1 ⇒ verifySession 回 null
});
```
🔴 **這兩格的斷言形狀是「一格裡同時量兩個旋鈕」,而那是刻意的**:
```
分開兩格量 ⇒ 每一格只翻一個旋鈕 ⇒ 【兩個旋鈕其實是同一個】那個世界照樣全綠
同一格量兩邊 ⇒ 「發」與「收」必須給出【不同方向】的結果 ⇒ 耦合當場現形
```
📎 這正是為什麼它們是那一裁的**附帶條件而不是可選** —— 沒有它們,「兩個開關」與「一個開關」在測試上分不出來。
