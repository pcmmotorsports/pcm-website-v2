### §0c 🔴 落差表:Sean 要的那三個東西,別人做成幾個欄位 / 我們現在有幾個

**這張表是本檔 v2 的重點** —— 三個「甲」聽起來各是一件事,**實際上每一個都是一組**。
**來源**:`~/pcm-mailbox/主-ALL-006-電商後台調研原文.md`(研究代理 2026-08-15 產出;WooCommerce 部分為官方文件,最可核實)。

| Sean 要的 | 別人實際做成什麼 | 我們現在有 | **落差** |
|---|---|---|---|
| **特價保留原價**(`Q-P-1=甲`) | **三欄一組**:原價 + 特價 + **生效區間 From-To**(Woo 起訖精確到 23:59);Shopify `Compare at price` **每個變體各自獨立設**。🔴 **原價在特價期間不消失** —— 它是展示用資料,不是被覆蓋的歷史 | **1 欄**(`price_general`) | **缺 2 欄 + 區間語意**;且要決定**商品層還是變體層**(Shopify 是變體層) |
| **草稿**(`Q-P-2=甲`) | **兩條獨立軸**:發布狀態(Draft / Pending Review / Published)**×** 型錄可見度(**四值**:Shop and search / Shop only / Search only / Hidden)。Medusa 另有 `proposed`(編輯完成待核准)、蝦皮有「審核中(2 個工作天)」 | **1 欄、2 值**(`delisted_at` 空/非空) | **缺 1 整條軸 + 一條軸從 2 值變 3~4 值**;「待核准」是第三個概念,我們完全沒有 |
| **庫存數量**(`Q-P-3=甲`) | **數量 + 開關 + 第三態 + 兩條門檻**:`Manage stock` 開關(關掉=永遠視為有貨)、數量、**Backorder 第三態**(再細分「允許但通知客戶」vs「直接允許」)、**低庫存門檻**與**缺貨門檻是兩條不同的線,觸發不同通知** | **0 欄**(商品側無數量);`availability` **2 值 CHECK** | **缺 4 個概念**;而 Sean 另加「前台不顯示」⇒ 再加一層可見性 |

🔴 **加總**:三個「甲」= **至少 7 個新欄位/概念**,不是三個。**這個工作量現在沒有人估過。**
### 🔴 設計約束(不是觀察):低庫存門檻與缺貨門檻**必須是兩條線**

低庫存 = **營運警訊**(該補貨了)/ 缺貨 = **交易警訊**(不能再賣)。**兩者觸發不同的通知、給不同的人看。**
🔴 **為什麼寫成約束而不是觀察**(主視窗 2026-08-15 升級):**併成一條是最省事的做法,而省事的做法會被下一個實作者自動選中。**
⚠️ **對本店更嚴重**:補貨前置期是**跨國訂貨**,不是隔天到 —— **賣到 0 才反應,等於斷貨數週。**
(來源:研究代理原文概念 4。)

## §1 WooCommerce 的商品編輯頁分成哪幾塊(來源:官方文件,2026-08-15 查)

**Product data 面板的分頁**(逐字取自 [Product Editor settings](https://woocommerce.com/document/managing-products/product-editor-settings/)):

| 分頁 | 管什麼 |
|---|---|
| **General** | 一般價 `Regular price`、**特價 `Sale price`(可排程起訖日)**、稅別 `Tax status` / `Tax class` |
| **Inventory** | `SKU`、**是否管理庫存**、**庫存數量**、**允許缺貨下單(三選一)**、**低庫存門檻**、**庫存狀態(In stock / Out of stock / On backorder)**、`Sold individually` |
| **Shipping** | 重量、尺寸(長寬高)、運送類別 |
| **Linked Products** | 加購 `Upsells`、交叉銷售 `Cross-sells`、群組商品 |
| **Attributes** | 商品自有屬性 / 全站共用屬性;可標「用於變體」 |
| **Variations** | 變體(顏色、尺寸…),僅 variable 類型 |
| **Advanced** | 購買備註、排序 `Menu order`、是否開放評論 |

**商品類型**(來源:[Managing Products](https://woocommerce.com/document/managing-products/)):Simple / Grouped / External-Affiliate / Variable,另有 Virtual、Downloadable 兩個標記。

## §2 🔴 它有而我們**沒有概念**的地方(不是功能清單,是概念清單)

**這一節是本調研最重要的部分** —— 功能可以後面補,概念缺一個,後面所有功能都會歪。

### 2-1 🔴🔴 「能不能賣」在 Woo 是**三條獨立的軸**,我們只有一條

| Woo 的軸 | 意思 | 我方對應 |
|---|---|---|
| **發布狀態** Published / Draft / Private | **這筆資料做好了沒** | ❌ **沒有**。我們沒有草稿概念 —— 建了就是上線 |
| **型錄可見度** Shop and search / Shop only / Search only / **Hidden** | **要不要讓人找到** | ❌ **沒有**。我們只有「顯示或不顯示」 |
| **庫存狀態** In stock / Out of stock / **On backorder** | **現在有沒有貨** | 🟡 **只有兩值**(`availability` CHECK = `in-stock` / `out-of-stock`,`20260507004826:33-40`),**沒有 backorder** |

**而我們把「能不能賣」全壓在一個 `delisted_at` 上**(非空 = 下架 ⇒ RLS 隱藏 + `create_order` 擋單)。
🔴 **後果具體化**:Sean 想「**先把商品建好但還不要上架**」時,現在**沒有地方放** ——
唯一做法是設 `delisted_at`,而那同時代表「已下架」,**兩件事在資料上長得一模一樣**。
⚠️ **這正是我剛做完的 `#20` 片2 那條線的延伸**:片2 讓「誰決定上下架」有了答案(`listing_set_by`),
**但「上下架」本身仍是單一軸** —— 片2 沒有、也不該解這個。
(來源:[Catalog visibility 為獨立設定](https://woocommerce.com/document/managing-products/product-editor-settings/) + [搜尋彙整](https://woocommerce.com/document/products-visibility-by-user-roles/),2026-08-15 查。)

### 2-2 🔴🔴 「特價」在我們這裡**沒有欄位可放** —— 而 Sean 說特價功能依賴這條線

Woo:`Regular price` 與 `Sale price` 是**兩個欄位**,且特價**可排程起訖**。
我方實查:
```
grep -c "sale_price|compare_at|discount_price"  packages/adapters/src/supabase/database.types.ts  ⇒ 0
```
⇒ **`products` / `product_variants` 完全沒有特價欄位。** 現有價格欄只有三個:
`price_general`(零售)、`price_store`(經銷,NULL)、`price_by_tier`(jsonb 分級價)。
🔴 **「打折」現在只能靠直接改 `price_general`** —— 而那樣做**原價就消失了**,
畫面上做不出「原價劃掉、特價紅字」,事後也查不出「這件曾經賣多少」。
⚠️ **memory 逐字**:特價功能「要等這個後台能設定優惠價才存在」⇒ **這是那條依賴鏈的實際卡點,不是抽象風險。**

### 2-3 🔴 「庫存數量」我們沒有 —— 只有「有貨/沒貨」

Woo 有 `stock_quantity` + 低庫存門檻 + 缺貨下單策略(來源:官方 `wp_wc_product_meta_lookup` 欄位含 `stock_quantity` / `stock_status`,
[Database Description](https://github.com/woocommerce/woocommerce/wiki/Database-Description),2026-08-15 查)。
我方實查:`instock_quantity` **確實存在,但在 `order_item_quantity_summary`(訂單側彙總),不在商品側**。
⇒ **商品沒有數量概念** ⇒ 做不出「剩 2 件」、「低庫存提醒」、「賣完自動下架」。

### 2-5 🔴 變體屬性要先標「是否用於生成變體」—— 這條我上一版沒查到,而它對我們特別致命

**Woo/Medusa 的屬性可以「只是展示用,不參與變體矩陣」**(原文概念 5;Woo `Attributes` 分頁有「用於變體」勾選)。
🔴 **缺了它的後果**:**每加一個展示用屬性,都會把笛卡爾積炸開。**
⚠️ **對重機零件特別嚴重** —— 材質 / 產地 / 認證 / 適用年份這類欄位很多,**它們是說明,不是可選規格**。
**我方現況**:`product_variants.spec` 是逐變體的自由格式 jsonb,**沒有「哪些屬性參與組合」的概念**,
也**沒有全站共用的屬性字典**(§2-4 已列)。⇒ **做變體編輯之前,這條要先有答案。**

### 2-6 🔴 訂單/操作 Log 要分三種,而我們今天剛上線的那頁只有一種

**原文概念 9**:Log 分 **①系統自動事件** 與 **②人工留言**,而人工留言再分 **「客戶看得到」** 與 **「內部限定」**。
- **WooCommerce**:系統事件紫色、私訊灰色,**兩種顏色兩種語意**
- **Shopify**:訂單頁 timeline 分 Fulfillment / Payment / Customer-initiated **三類**;
  另有**店鋪級 Activity Log(含操作者身分,上限 250 筆)**⇒ **訂單層與店鋪操作層是兩份不同的 log**
- 蝦皮/露天:🔴 **查無**官方文件描述

🔴 **缺了會怎樣(原文逐字)**:「一個 timeline 混著系統事件、內部吐槽、對客訊息,**員工不敢寫真心話 ⇒ 有記錄但沒人敢用**。」
✅ **已由主視窗轉訂單線/客人線處理(2026-08-15)** —— **本檔到此為止,商品線不展開。**
(A 窗讀同一份原文、獨立指到同一格 ⇒ 兩個窗各自撞上,優先度因此被調高。)

### §2-2a 🔴 特價有兩個可能的家,而它們的關係沒有人寫下來過

`Q-P-1=甲` 之後,「特價」要落在哪一層變成**下一片的核心設計題**:

| 層 | 欄位 | 回答的問題 |
|---|---|---|
| **商品層** | (**目前不存在**,要新增,如 `sale_price` + 起訖) | **這件商品現在賣多少** |
| **訂單層** | `orders.discount_total`(**已存在**,實查所屬表 = `orders`) | **這一筆單實際折了多少** |

🔴 **兩者不是二選一,也不是矛盾 —— 是兩件事**:商品層決定標價,訂單層記錄成交結果。

⚠️ **而經銷價也走 `discount_total`** ⇒ **同一個欄位會同時承載「會員等級折扣」與「商品特價」兩種來源**,
**那代表事後可能分不出「這筆單為什麼便宜」。** 這條要在設計時處理,不是實作時。
⚠️ **主視窗提到的 `#513` 我在本樹查不到**(`grep -c "#513" docs/phase-1-backlog.md` ⇒ 0)——

## §4 模板/現成方案:能不能套(回答 Sean 8/11 那題)

**先講結論**:🔴 **WooCommerce 本身套不進來,它是 WordPress/PHP 生態**;我們是 Next + Supabase + R2。
**能拿的是它的「概念與分塊」,不是它的 code。**

**真正可評估的「模板」有三類**,各自的取捨:

| 方向 | 是什麼 | 好處 | 代價 / 風險 |
|---|---|---|---|
| **甲:後台 UI 模板** | 買/用一套 admin UI kit(表單、表格、媒體上傳元件) | 省畫面工;媒體上傳這種難做的元件現成 | 🔴 **與現有 admin 視覺不一致**(我們已有一整套 OD 設計的後台);**資料層完全不解決** |
| **乙:Headless commerce 後台**(如 Medusa admin) | 直接用它的商品管理介面 | 商品/變體/價格概念完整、久經考驗 | 🔴🔴 **它要它自己的資料庫 schema** —— 我們的 `products` 是報價單每日同步的目標表,**兩套 schema 會打架**;等於重做同步管線 |
| **丙:自建,但照抄成熟的「分塊」** | 沿用 §1 那七個分頁的切法,自己刻 | 資料層可以逐塊補、與同步策略一起設計;不引入外部相依 | 畫面工全是自己的;**要 Sean 逐塊拍板要不要做** |

⚠️ **這三個我都沒有實作評估過成本** —— 上表是「取捨方向」,**不是工時估計**。
