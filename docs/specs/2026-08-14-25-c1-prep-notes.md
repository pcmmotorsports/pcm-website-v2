## 2. 🔴 我發現一個要裁的岔路(流程/方法論題,不是 Sean 的題)

**同一件事,storefront 與 admin 兩套房規,而 C1 剛好站在中間。**

- **storefront**(`app/account/profile/actions.ts`):收 `input: unknown` → `ProfileInput.safeParse`(zod)→ 回 `{fieldErrors}/{formError}/{ok}`,client 元件自己管狀態。
- **admin**(**12 支** parser;數法 `find apps/admin/src/lib -name '*-form.ts' | grep -v test | wc -l`):收 `FormData` → 手寫 parse + `anyMalformed` → PRG redirect,**零 zod**(數法 `grep -rn "zod" apps/admin/package.json apps/admin/src` = 零命中,exit 1)。

C1 要改的 `name/phone/birthday` **正是 `ProfileInput` 那三欄**(`packages/schemas/src/index.ts:166-183`),
裡面有 phone `/^[\d\s-]{8,}$/`、birthday `/^\d{4}-\d{2}-\d{2}$/` 兩條**已經被審過**的規則。

| 選項 | 做法 | 代價 |
|---|---|---|
| **A(我推薦)** | `profile-form.ts` 先用 `anyMalformed` + `readSingleString` 讀(admin 形狀防線),再把物件丟給 `ProfileInput.safeParse` 管語意 | 要加 1 個 workspace dep(`@pcm/schemas`);admin 首次出現 zod |
| B | 完全照 admin 房規手寫,把兩條 regex 抄一份到 `profile-form.ts` | **同一條規則兩份**。這個 repo 已經為這件事痛過一次 —— `schemas/src/index.ts:54` 逐字記著 `AddressInput` 與 `CheckoutInputBase`「**各抄一份**同樣的形狀與規則,靠『兩處同步』」,後來收斂成共用 |

### ✅ 已裁定 = A(主視窗 2026-08-14 夜,流程題直裁)

裁定理由**不是「zod 比較好」**,是**這個 repo 已經為 B 案付過一次學費**(`schemas/src/index.ts:54`,主視窗開檔複驗過)。
同一條 regex 放兩個地方,下次有人改一邊、另一邊**不會紅** —— 那正是「改了字面沒改載體」的溫床。
**多一個 workspace dep = 一次性成本;兩份 regex = 永久成本。**
補充事實(主視窗複驗):`zod` 本來就在 `packages/schemas/package.json:13`(`catalog:`)⇒ **A 案不是引進新套件到專案**,只是讓 admin 也依賴既有的 schemas 包。

**🔴 兩條約束(寫死,違反即片爆)**

1. **本片只在 `profile-form.ts` 這一支用 `ProfileInput`。不准順手改其餘既有 parser。** 那是另一件事、要另外立案。
   ⚠️ 數字對齊:主視窗信中寫「另外 11 支」,實際是 **12 支**(數法同上 §2;`profile-form.ts` 是新增的第 13 支)。**約束的意思不變,只是分母要準。**
2. **`anyMalformed` 判準要有負測釘死**,做法照 §4 兩條:`it.each` 逐欄「送兩份 → ok:false」,**外加**一條**手寫欄名陣列對照**。
   理由是我自己引的那條:只用 `it.each` 走訪同一顆常數,**清單少一欄時測項也跟著少一條、照樣全綠**。
