# 新竹的箱子可以「手打單號就標出貨」—— 要不要關掉 · plan · 2026-09-11 · 窗 B

> 來源:走查 F8(`docs/evidence/2026-09-11-B-後台整條線走查.md`)。
> 🛑 **只寫題, 一行碼都沒改**(碰寄信 ⇒ 鐵則 8 + 12)。等 Sean 答下面的 Q。

## 0. 一句話

新竹的箱子有兩條路可以變成「已出貨」, 而**只有一條會先確認新竹真的要來收**:

```
正路(09-10 做好)  建箱 → 送新竹 → 出貨清單按「叫車」
                   ⇒ 叫到車那一刻才標出貨、單號用新竹回的貨號、出貨信跟著排上
舊路(08-09 就有)  出貨彈窗選新竹 → 手打一組單號 →「建箱並標出貨」
                   ⇒ 立刻標出貨、出貨信立刻排上;新竹那邊可能根本沒有這張單
```

走查實例:PCM-2026-1007 手打 `1234567890` ⇒ 「已出貨」、`pcm_shipped_email_pending` 1 列;
同一箱在出貨清單寫「託運單還沒在新竹建好(draft)」(那是叫車鈕反灰的理由, `hct-dispatch-flow.ts:160`)。

## 1. 先查的三件(都有出處)

**① 手打單號這條路是誰開的、為什麼**
- `0b98c823f`(2026-08-09)「建箱彈窗收官 —— C 版出貨動線接活」:**那時候還沒有任何新竹串接**,
  手打是唯一的路。彈窗的快遞商預設就是新竹(`shipment-dialog.tsx:138` `useState<CarrierCode>('hct')`)。
- `1e432c176`(2026-08-16)Sean 拍 Q-C551 乙:單號格式不限、上限 39、只警告不擋。
- 新竹送單鈕 `7ddbba166`(2026-09-05)、叫車鈕 `0c2480eb0` / `babc2b436`(2026-09-10)**都是後來疊上去的**,
  **沒有一份 plan 決定過「新竹上線後, 手打那條要不要留」**
  (`git grep -E '手打|手動.*(貨號|單號)|貨號.*手' -- docs/plans docs/specs <runbook>` 再篩新竹 ⇒ 命中 2 行,
  都不是決定:runbook `:205` 講測試值、spec `2026-07-25…:332` 講查貨態;`2026-09-05-hct-submit-entry-plan.md` 沒提標出貨順序)。
  ⇒ 📌 它不是「刻意留給新竹開通前手動出貨」的決定, 是**開通前本來就只有它, 開通後沒人回頭關**。
- ⚠️ **相關的一個拍板**:2026-09-09 窗 B 走查時員工分不清「標出貨」與「送新竹」,
  Sean 拍甲 =「**只加說明、不藏鈕**」(`shipment-hct-submit-button.tsx:116-122`, 他沒選「藏起來」)。
  那一題問的是**送新竹那顆鈕**, 本題問的是**手打標出貨那條路** —— 不是同一題, 但方向相近, 要他知道。

**② 出貨信排上的條件**
- `pcm_shipped_email_pending`(最新 `20260907230000:149-183`)只看三件事:`shipped_at IS NOT NULL` · 沒作廢 · 有信箱 · 還沒排過。
  **不看快遞商、不看新竹狀態(`hct_status`)、不看單號從哪來。**
- DB 只要求「標出貨時非『其他』要有單號」(CHECK `shipments_shipped_needs_tracking`, 轉譯在 `20260808100000:134`)。
- 實際寄出由顧客站 `email-sweep` cron 做, 還要 `SHIPPED_EMAIL_CUTOFF` 有設(`route.ts:601-607`)。
- 打錯單號可以事後「更正單號」, 會再寄一封更正信(`pcm_tracking_corrected_email_pending`;`20260904190000`)。

**③ runbook `hct-first-shipment-activation.md:208` 是不是同一件**
- `:195-209` 講的是**反方向**:第一箱真的送新竹成功(`S9FC6P`, `hct_status=submitted`),
  而新竹回的貨號**沒有被搬進單號欄** ⇒ 彈窗要求手打單號 ⇒「送成功之後還不能標出貨, 修法待拍板」。
- 那段寫於 2026-09-10 12:20(`9d0598aad`);**同一天 18:13 / 18:46 的叫車鈕**在叫到車時用新竹貨號標出貨
  (`shipment-dispatch-hct-action.ts:162-168` `trackingNumber: only.edelno`)
  ⇒ 🔵 **在叫車那條路上, `:208` 那個缺口看起來已經補了**;而 runbook 那句沒跟著改。**吻合但未證實**(我沒在鑽機走過叫車)。
- ⇒ 📌 **兩件是同一個根的兩面**:新竹的「已出貨」有兩個入口, 一個不問新竹、一個問了但以前接不上。
  叫車鈕接上了後者, 本題是要不要關掉前者。

## 2. 兩個做法

### 甲(推薦)· 新竹的箱子只能靠「叫車」變成已出貨

```
改什麼   · shipment-dialog.tsx:快遞商 = 新竹時,「建箱並標出貨」不給按, 只剩「只建箱、先不出貨」,
           旁邊一句「新竹的箱子要按送新竹、再到出貨清單叫車;叫到車系統會自己標出貨、填貨號、寄信給客人」
         · shipment-mark-shipped-button.tsx:箱子上那顆「標出貨」對【新竹 + 還沒叫車】的箱停用, 同一句話
         · 順豐 / 其他:維持手打, 一格不動
動 SQL?  不動(之後要更硬可以在 admin_mark_shipment_shipped 加一道, 那是另一張 plan)
rollback revert 那一顆 commit;沒有資料要回復
代價     🔴 新竹那兩顆閘(送單 HCT_SUBMIT_ENABLED / 叫車)任一沒開、或新竹 API 掛了
           ⇒ 新竹的箱子標不了出貨。逃生口 = 快遞商改選「其他」、備註寫單號(信上就沒有新竹查詢)
為什麼推 對齊 Sean 2026-09-10 拍的形狀(`2026-09-10-hct-dispatch-order-plan.md` §0 逐字
         「叫車 + 標已出貨 + 寄信, 三件事對齊同一個動作, 客人收到信的時候貨真的要走了」);
         同一份 §3-a 自己把「先標出貨+寄信、再叫車」列為**收不回來**的那一種 —— 舊路正是那一種
```

### 乙 · 兩條路都留, 手打那條多一道確認

```
改什麼   · shipment-dialog.tsx / shipment-mark-shipped-button.tsx:新竹 + 還沒送新竹時,
           多一格必勾「新竹已經把貨收走了, 這個號碼是新竹給的」, 不勾不能按
         · 出貨清單那一列標「手打單號(沒經過系統送新竹)」
動 SQL?  不動
rollback revert 那一顆 commit
代價     靠員工勾;勾錯照樣會寄出一封「已出貨」而貨沒走。好處是新竹網站 / 紙本自己建單的那種仍走得通
```

### ✗ 不推:手打單號就不排出貨信
要改 view(SQL + 寄信 ⇒ 鐵則 8 + 12), 而那些箱的貨**可能真的走了**(在新竹網站或紙本建的單)
⇒ 客人反而完全收不到出貨信。

## 3. 證不到什麼

1. **正式站那兩顆新竹閘今天開不開**:讀不到 env 值。叫車閘碼註寫「2026-09-10 開著上線, Sean 拍乙」
   (`hct-client.ts:70-80`);送單閘有 `S9FC6P` 送成功為旁證 ⇒ **吻合但未證實**。甲的代價大小取決於這一格。
2. **叫車那條路我沒在鑽機走過**(對外 API)⇒ 「叫到車會自己標出貨、填新竹貨號」是讀碼, 不是量到的。
3. **正式站今天有幾箱是手打新竹單號出貨的**:沒查。要的話唯讀一句
   `select count(*) from shipments where carrier_code='hct' and hct_status='draft' and shipped_at is not null`。
