⟦b4-SETTLERETRYNEVER⟧ 重算當時失敗過一次 ⇒ 之後沒有第二次 ⇒ 永遠停在 unpaid  🔴 **本片接**

## 1. 掃什麼(兩條腿, 分開寫)
```
腿 A(NCPCRONRACE 剩下那半)
  已取消(cancelled_at IS NOT NULL)
  + 非卡軌淨額 > 0(order_payments 同軌 SUM − order_manual_refunds 未作廢 SUM)
  + 該軌【沒有】未作廢未結清的 order_pending_refunds 列
  ⇒ 這正是「錢落在已取消的單上而帳本零痕跡」那個世界

腿 B(SETTLERETRYNEVER)
  payment_channel = 'bank_transfer' + 未取消 + payment_status = 'unpaid'
  + 已收淨額 > 0
  ⇒ 這些單當初重算失敗過(或根本沒跑到), 而沒有第二次
```
🛑 **兩條腿【不共用一個 WHERE】** —— A 找已取消, B 找未取消。合成一句會讓下一個人以為只有一種。

## 2. 掃到怎麼做 —— **而題目變了:現在問的是「要不要多一道兜底」**
> 🔴 **舊題目**(⛔ 作廢):「競態一剩下那半要直接修還是只告警」——
> 　 那個主詞已經不存在了(見 §0)。**而選項本身仍然成立**, 只是它們回答的是新問題。

```
甲 = 兩條腿都【直接修】:A 呼叫 pcm_pending_refund_open_for(id, false);B 呼叫 pcm_noncard_settle_recompute(id)
     🔵 洞真的被補起來, 不需要人
     🔴 而它是【排程自動寫金流資料】—— 爆炸半徑最大的一種
乙 = 兩條腿都【只告警】:寫進既有的異常告警信(那封信我這條線做的, 已有兩個世界的段落)
     🔵 零寫入、爆炸半徑最小;客服看得到就會處理
     🔴 而它把「補」留給人 ⇒ 📌 而今天那封信【沒有人固定在讀】(R3 nit ⑥ 同一格)
丙 = A 直接修(它只是補一列待退款, 不動狀態、不動錢)/ B 只告警(它會翻 payment_status ⇒ 動狀態)
```
🔵 **本線推薦丙**, 理由是**兩條腿的動作不同級**:
　 · A 開的是一列「待退款」—— 它**不動錢也不動狀態**, 而它不開的代價是**帳本上那筆錢消失**。
　 · B 會翻 `payment_status` ⇒ 那是**狀態機**, 而排程自動翻狀態是另一個等級的授權。
⚠️ 而丙 的代價:B 那半仍然要人 ⇒ **那封信必須有人讀**。⇒ 見 §6 的未解格。

## 3. 多久跑一次
既有六條 pg_cron(實查 `cron.schedule` 字面):
```
pcm-order-ineligible-gate  */2      pcm-settle-sweep       */2
pcm-email-sweep            */5      pcm-capture-recheck    */10
pcm-expire-unpaid-orders   0 * * * *   pcm-anomaly-alert    0 1 * * *
```
🔵 **建議 `*/10`(與 capture-recheck 同頻)**。理由:
　 · 它補的是**罕見競態**, 不是熱路徑 ⇒ 不需要 `*/2`
　 · 而它**必須比 `pcm-anomaly-alert`(一天一次)密** —— 否則告警信會先報出一個
　 　 掃描器本來就要補掉的東西 ⇒ 📌 **兩個機制對同一件事講不同的話, 客服會不知道信哪一個。**
🛑 **而「多久」不是口味, 它是暴露窗**:A 那條腿沒跑之前, 那筆錢在帳本上不存在。

## 5. rollback
```
① cron.unschedule('pcm-late-payment-scanner')
② DROP FUNCTION pcm_cron.<掃描器名>(…)
③ 🛑 **資料不回滾** —— 腿 A 可能已經開出一些 order_pending_refunds 列。
   那些列本來就該存在 ⇒ 不要 DELETE;要作廢走既有的 voided_at。
④ 🔵 本片【不動】任何既有函式 ⇒ 沒有「還原上一版全文」那一步(與 070000 不同)。
```
⚠️ **而 `cron.schedule` 是 by-name upsert** ⇒ 貼之前要證明沒動到別人的那六條
　(照 `20260820070000` 的形狀:先 `SELECT jobname FROM cron.job` 存一份)。

## 6. 探針怎麼雙向紅綠
```
🟢 該綠:造一張「已取消 + 淨額>0 + 無待退款列」的單 ⇒ 跑掃描器 ⇒ 出現一列
🔴 該紅(負對照一):同一張單【已經有】未結清的待退款列 ⇒ 跑掃描器 ⇒ **不得多開一列**
🔴 該紅(負對照二):一張【未取消】的單有淨額 ⇒ 跑掃描器 ⇒ **腿 A 不得碰它**
⚪ 該紅(突變):把腿 A 的 WHERE 拿掉 NOT EXISTS ⇒ 重複開列 ⇒ 那一格要真的紅
🔬 而腿 B 要一格:一張 unpaid + 淨額>0 的單 ⇒ 跑 ⇒ (丙 案下)**只出現告警, payment_status 不動**
```
🛑 **本檔到現在為止【證不到】的一格, 先寫下來**:
　 探針是單連線 ⇒ 它驗得了「掃描器掃對了什麼」, **驗不了「它在真的競態下補得及」** ——
　 後者要兩連線 + 排程, 而排程在拋棄式 PG 裡沒有 pg_cron。⇒ 那一格只能靠**上線後看它補了幾筆**。
