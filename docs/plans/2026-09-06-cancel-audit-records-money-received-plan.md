## §0 🔴🔴 **先講:乙【照字面】做不出來 —— 而擋住它的是那支函式自己的冪等斷言**

裁的乙是「**稽核 `before` 與取消理由寫『其實收過錢 NT$X』**」。
🔬 而我讀完現行體(`20260903093000`, **19,899 字元 / 372 行可執行**)之後量到**兩道擋**:

**① 稽核 `before` 的鍵數被釘死成 2**(冪等重放路徑, 剝註解後 `:210`):
```sql
OR (SELECT count(*) FROM pg_catalog.jsonb_object_keys(v_audit.before)) <> 2
```
⇒ 🛑 **在 `before` 加第三個鍵 ⇒ 之後每一次冪等重放都會 RAISE。**

**② 取消理由被釘死成「理由碼的正規映射」**(`:144-152`):
`v_order.cancelled_reason` 必須逐字等於 `reason_code` 對應的那句話
(`'customer_request' → '依您要求取消'` …)⇒ 🛑 **在理由後面接一句「其實收過錢」⇒ 重放時對不上 ⇒ RAISE。**

⇒ 📌 **乙的兩個落點, 各自撞上一道【為了防止重放時內容漂移】而存在的斷言。**
⇒ 🎯 **而那兩道斷言是對的** —— 它們防的正是「同一次取消被寫成兩種樣子」。

### ⇒ 所以真正要決定的是【把那句話放哪裡】

| | 落點 | 代價 |
|---|---|---|
| **乙-1** | 稽核 **`after`** 加一個鍵 | `after` **沒有**鍵數斷言(`:207/:214` 只點名兩個鍵)⇒ 🟢 **最小改動**;而語意上「收過錢」是**取消前**的事實, 放 `after` 讀起來怪 |
| **乙-2** | 把 `before` 的鍵數斷言從 `= 2` 放寬 | 🔴 **那是在改一道現行的守門** ⇒ 舊列(2 鍵)與新列(3 鍵)都要過, 而**放寬之後它就不再擋「多長出一個鍵」** |
| **乙-3** | 兩個都不動, **另寫一列 `admin_audit_log`**(`action = 'order.cancel.money_note'`) | 🟢 **零回歸**(不碰任何既有斷言);而它是**第二列** ⇒ 查的人要知道去看它 |

🔵 **我傾向乙-3**, 而理由是 §0 那句話:**那兩道斷言是對的, 而它們擋我是因為我要塞的東西不屬於它們守的那個結構。**
🛑 **而乙-3 的代價要明寫**:多一列 = **多一個「沒有人會去看」的落點** ⇒ 📌 **它必須有讀取端, 否則等於沒寫**(📎 板列 `⟦f3-REDNEEDSEXIT⟧`:「一個沒有觀眾的紅, 與沒有那個紅, 在行為上相同」)。

## §2 要改什麼(**若拍乙-3**)

在**真的取消**那條路(非重放)寫完既有稽核列之後, **多寫一列**:
```
action        'order.cancel.money_note'
before        {}                      ← 刻意空:它不是狀態變更, 是一個觀察
after         {"paid_sum": <整數>, "payment_status_at_cancel": "unpaid"}
```
🔴 **金額一律整數**(分/角;`order_payments.amount` 本來就是 `integer`)—— **禁浮點**(Server 端鐵則)。
🔴 **淨額算式與 trigger 用同一份口徑**:`SUM(order_payments.amount)`(**不另寫一份** —— 另寫就會分岔)。
🔵 **只在 `paid_sum > 0 且 payment_status = 'unpaid'` 時寫** ⇒ 正常單一列都不多。

## §4 驗收(每條可 yes/no)

1. **兩個世界**:帳本有錢 + `unpaid` 的單取消 ⇒ **多那一列**;帳本零的單取消 ⇒ **不多**。
