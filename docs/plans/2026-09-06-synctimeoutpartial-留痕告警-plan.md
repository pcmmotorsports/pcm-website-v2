## 🔴🔴 而動手之前,先看一格會決定整個設計的東西

板列 `⟦b4-DEADMAN⟧` 那支 migration 的檔頭逐字寫著:

> **一個只數存在的東西的量具,對「東西沒被建出來」永遠印 0,而那個 0 看起來像正常。**

把它套到本列:

```
🛑 一個「被砍的時候寫一列」的設計, 前提是【被砍的那一刻還能寫】。
   而那正是最不能假設的一刻 —— 行程正在被殺、DB 連線可能已經斷、訊號不保證送達。
```

🔬 **而我自己上一輪就撞到這個前提的邊界,寫在板上**:
`installKillReporter()` 只在 **`SIGTERM` 真的送到那個 node 行程**時才說話,
而中間隔著 shell 與 `pnpm` 包裝、訊號走的是行程群組 —— **我構造不出那個世界**(那要真的讓一班跑超過 45 分)。
⇒ 📌 **我做的是「訊號來的時候有東西會說話」,不是「訊號一定會來」。**

### ⇒ 所以設計要**反過來**:不要在死的時候寫,要在**活著的兩端**寫

```
開工時   寫一列  started_at  ← 這一刻行程是健康的,寫得進去
收工時   回填    completed_at ← 這一刻也是健康的
⇒ 🎯 【被砍】= 那一列【永遠停在只有 started_at】
⇒ 📌 它【不需要任何訊號】—— 缺席本身就是訊號。
```

🔵 **這正是 deadman 的形狀**:不是問「有沒有壞消息」,是問「該來的有沒有來」。
🛑 **而它與 `installKillReporter()` 不衝突、也不取代它** —— 那一行答的是「停在哪一群」(診斷),
   本片答的是「有沒有停」(告警)。**兩個問題,兩個機制。**

## 甲案的四個已知障礙(**先寫出來,免得下一個人以為抄先例就會通**)

1. 🔴 **告警那條路跑在 `payment_confirmer`,而它對這類表是零表權** ——
   `20260829010000` 的檔頭逐字記過:直接查表 ⇒ `42501 permission denied`
   ⇒ **唯一的路 = owner-defined SECDEF 受控窗**,照 `20260701120000` 的範式。
   ⚠️ **而「抄了先例」不等於權限就對了**(codex 逐字)⇒ migration 裡要**當場斷言有效權限**,不假設。
2. 🔴 **N 小時那個門檻不要用猜的** —— 我量到的是 sync job 最長 8.7 分,而**整班**因 `max-parallel: 1`
   序列跑 18 個 job,2026-09-04 那班牆鐘 **101 分**。
   ⇒ 📌 **「單一 job」與「整班」是兩個數** ⇒ 門檻掛錯那一個會天天假紅或永遠不叫。
3. 🔴 **失敗 ≠ 逾時** —— 2026-09-05 那班是 failure(`sync (dbk)` 1.2 分就結束,orphan 閘擋下)。
   ⇒ 甲案的 `outcome` 欄要**分得開**:完成 / 被砍 / 自己判失敗。**三態,不是兩態。**
4. ⚠️ **首次寫入那一列自己也可能失敗** —— 若 INSERT 失敗就整支中止,等於為了觀測而讓同步變脆。
   ⇒ 建議:**開工那一列寫不進去 ⇒ 大聲 log 但不擋同步**;而**收工那一次回填失敗要擋**(它代表狀態不明)。
