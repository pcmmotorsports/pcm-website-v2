# 計畫：顧客站每頁選 200、500、1000 時，商品要全部顯示

- 日期：2026-09-22
- 派工：主視窗 pcm-website-v2-90（Sean 選甲）
- 狀態：計畫與 migration 已寫好，**尚未貼到正式庫、尚未推送**。需要 Sean 批准（鐵則 8：改資料庫函式，而且是顧客站公開呼叫的函式）。
- migration：`supabase/migrations/20260922130000_m4b_catalog_page_limit_1000.sql`
- 退回檔：`supabase/rollbacks/20260922130000-rollback.sql`
- 審查：見文末「審查紀錄」。

## 1. 問題（白話）

顧客站商品列表的「每頁顯示」有 100、200、500、1000 四個選項（Sean 09-12 指定，commit `01b5b72bc`）。前端照客人選的數字向資料庫要商品（`apps/storefront/src/lib/products.ts:592-593`：`p_offset = (頁碼 - 1) × 每頁件數`、`p_limit = 每頁件數`）。

但資料庫裡的兩支目錄函式把「一次最多回幾件」寫死成 100。所以：

- 選 **200**：頁碼算成 3 頁，但每頁只拿到 100 件。第 2 頁從第 201 件開始，**第 101-200 件、第 301-400 件客人永遠看不到**。
- 選 **500 / 1000**：只有 1 頁、100 件，其他全部不見。

主視窗在正式站實測（Yamaha MT-09 SP，共 489 件）：選 500 只看到 100 件，另外 389 件不見。通用配件區也一樣。

### 正式庫實查（2026-09-22，`scripts/readonly-prod-sql.sh` 唯讀，角色 `pcm_readonly`）

| 函式 | 參數數 | 上限 | 誰叫得到 | 本體 md5（prosrc） |
|---|---|---|---|---|
| `search_catalog_by_vehicle` | 14 | 100（兩處） | anon、authenticated、service_role | `9242dea9…` |
| `search_catalog_by_vehicle_dealer` | 14 | 100（兩處） | authenticated（SECURITY DEFINER） | `e577ec35…` |
| `search_catalog_by_vehicle`（舊版） | 11 | 100 | 只有 postgres | `169bf913…` |

- repo 最新一代是 `20260916260000`（`bash scripts/latest-definition-of.sh` 兩支都指向它）。我把那支檔裡兩支函式的本體在本機算 md5，**和正式庫讀到的完全相同**，所以正式庫跑的就是這一代。
- 另外把正式庫 `pg_get_functiondef` 的輸出和 repo 逐行比對，14 參數兩支都是 0 行差異。
- 前端一律送 14 個參數（`products.ts:588-610`），只會叫到 14 參數版。11 參數舊版的權限只剩 postgres，anon 與登入會員都叫不到，這次不動它。
- anon 的 `statement_timeout` 是 3 秒，authenticated 是 8 秒（`pg_roles.rolconfig`）。

## 2. 效能實測（改之前先量）

唯讀角色沒有權限執行這兩支函式，也不能建臨時函式，所以我把 14 參數公開版函式裡的兩段查詢（沒選車、有選車）原樣抽出來，參數換成實際值，上限分別換成 100、500、1000，直接在正式庫執行。每個情境跑 3 次，下表取中位數（括號內是 3 次裡最慢的一次）。產生查詢的程式在我的暫存區，查詢本身與函式本體逐字相同，只替換參數與上限。

| 情境 | 符合件數 | 100 件 | 500 件 | 1000 件 |
|---|---|---|---|---|
| 沒選車、全站 | 26,642 | 617 ms | 678 ms | 686 ms（753） |
| 沒選車、通用區參數 | 26,642 | 680 ms | 643 ms | 763 ms（**1,046**） |
| Ducati Panigale V4，不選年份 | 5,511 | 357 ms（首次 1,587） | 381 ms | 414 ms |
| Ducati Panigale V4，2022 年 | 5,009 | 256 ms | 417 ms | 524 ms（532） |
| Yamaha MT-09 SP，不選年份 | 4,807 | 244 ms | 411 ms | 522 ms |
| Yamaha MT-09 SP，2021 年 | 4,583 | 266 ms | 346 ms | 380 ms（471） |
| Yamaha MT-09 SP，只看通用區 | 4,317 | 220 ms | 276 ms | 270 ms |

Panigale V4 是正式庫適用商品最多的車款（1,194 件），MT-09 SP 是主視窗實測的那一台。

**這張表量到的是「100 件改 1000 件多花多少時間」：最多多約 0.28 秒（Panigale V4 2022 年那一列）。** 表上的絕對秒數不能直接拿來和 anon 的 3 秒比，原因見下面第一點。

100 件和 1000 件差不多快，是因為函式本來就要先把所有符合的商品排好序（視窗函式跑全部符合的列），上限只影響最後組 JSON 的件數。

量測的限制（量不到的部分）：

- **表上的絕對秒數低估了客人（anon）實際的成本。** 量測角色 `pcm_readonly` 有 BYPASSRLS，會跳過資料列權限檢查。正式庫 `product_fitments` 與 `product_fitments_effective` 的讀取權限是逐列檢查「對應商品未下架」（`pg_policies` 實查，Fable 審查指出），anon 選車時每一列適用車款都要多做這個檢查。這筆成本 100 件也要付，和上限無關，所以不影響上面的「增量」結論，但 anon 離 3 秒的實際餘裕沒有被證明。2026-09-11 anon 在 100 件時就碰過一次逾時（`apps/storefront/src/lib/retry-on-statement-timeout.ts` 檔頭），目前靠自動重試一次處理。
- 沒經過 plpgsql 外殼；PostgREST 最後會把結果再包成一個 JSON，這段也算在 3 秒內（估數十到一百多毫秒）。
- 冷快取第一次跑較慢（Panigale V4 100 件首次 1,587 ms）。這段是「排序全部符合商品」的固定成本，和上限無關。
- **經銷會員那支（`_dealer`）沒有單獨量。** 本體和公開版逐字相同，只多身分檢查、讀經銷版清單；它以 SECURITY DEFINER（postgres）執行，本來就跳過資料列權限檢查，所以上表的量法反而比較接近它。登入會員的限制是 8 秒。

用 anon key 從本機直接呼叫正式站的 `search_catalog_by_vehicle`（和前端送的參數相同，只讀），每個情境 3 次。時間包含台灣到資料庫的網路往返與連線建立，所以比上表多；3 秒限制只算資料庫執行時間，不含網路。

| 沒選車、全站 | 25,553 | 1,286 ms | 1,992 ms |
| Panigale V4，不選年份 | 4,926 | 1,298 ms | 1,375 ms |
| Panigale V4，2022 年 | 4,453 | 1,024 ms | 1,048 ms |

**結論：不需要降低上限。** 逾時風險主要來自既有的 anon 基線成本，不是這次的改動。

### 回傳資料大小

| 情境 | 1000 件完整回傳 | 去掉 `fitments` 後 |
|---|---|---|
| 沒選車 | 0.89 MB | 0.56 MB |
| 選車（Panigale V4 / MT-09 SP） | 約 5.6 MB | 約 0.55 MB |

- 選車時回傳很大，是因為每件商品都帶完整的適用車款清單（`fitments`）。
- 這包資料只在 Supabase 和顧客站伺服器之間傳。`catalog-page.ts:107-121` 在伺服器端就把 `fitments` 拿掉，不會送到客人的瀏覽器。
- 放進快取（`getCatalogPageCached`，`unstable_cache`）的是轉換後的卡片資料，大小接近「去掉 fitments」那一欄，約 0.55 MB，低於 Next 快取單筆 2 MB 的上限。這是用資料庫端的大小推估，沒有在 Next 端實測。

## 3. 改什麼

只改兩支 14 參數函式裡的 4 處上限：`LEAST(GREATEST(p_limit, 1), 100)` 改成 `LEAST(GREATEST(p_limit, 1), 1000)`。

- `search_catalog_by_vehicle`：沒選車、有選車各一處。
- `search_catalog_by_vehicle_dealer`：沒選車、有選車各一處。

其他一個字不動：

- 本體從 `20260916260000` 逐字抄；和來源比對只有這 4 行不同。
- 簽章不變，所以用 `CREATE OR REPLACE`，不 DROP。owner 與權限保留。
- SET 子句（公開版 `search_path = public, pg_temp`，經銷版 `search_path = ''`）跟著本體原樣帶著。`CREATE OR REPLACE` 會把 SET 子句整組換掉，所以不靠「會保留」這個說法，交給事後檢查逐字驗。

上限定 1000，是因為前端最大的每頁選項就是 1000（`products-url-parsers.ts:28`，不在清單裡的值會退回預設）。客人透過網站不會送出超過 1000 的數字。

**前端不用改。** 前端本來就照每頁選項送 `p_limit`，頁碼也用函式回傳的總數計算。上限放寬後，第 2 頁的起點（第 201 件）就會接在第 1 頁（第 1-200 件）後面。

migration 內的檢查：

- **貼之前**：兩支的本體 md5 必須是 `20260916260000` 那一代（`9242dea9…` / `e577ec35…`），而且 owner、SECURITY DEFINER、SET 子句、權限必須逐字等於 2026-09-22 讀到的值。不符合就停，代表有人先改過（只用 `ALTER FUNCTION … SET` 改設定時 md5 不會變，所以兩項都要核）。
- **貼之後 ①**：兩支本體 md5 是新的那一版（`55d387e8…` / `e1760be9…`）。
- **貼之後 ②**：沒選車、選車（Ducati Panigale V4，約 4,900 件）各呼叫一次 `p_limit = 5000`，兩次都必須剛好回 1000 件；總件數不到 1000 就停下，因為那樣驗不到截斷。函式裡沒選車、選車是兩段不同的查詢，所以兩段都要驗。
- **貼之後 ③**：兩支的 owner、SECURITY DEFINER、SET 子句、權限，逐字等於今天正式庫讀到的值。經銷版不能出現 anon。

## 4. 影響

- **客人**：每頁選 200、500、1000 時，看得到全部商品，不再跳過。選 100（預設）的行為不變。
- **速度**：資料庫端從約 0.25-0.7 秒變成約 0.27-0.76 秒（見第 2 節）。瀏覽器一次畫 1000 張卡片會比較慢，但那是 Sean 指定的選項本來就該有的行為。
- **公開 API**：任何人本來就能拿 anon key 直接呼叫這支函式。改完之後一次最多拿 1000 件（原本 100 件）。資料庫成本差不多（見第 2 節）；回傳資料最多約 5.6 MB（選車、含 fitments），原本約 0.56 MB。內容都是已公開的商品資料，沒有新的欄位外露。
- **Supabase 出站流量**：每一次選車的 1000 件查詢約 5.6 MB，比現在多約 10 倍；有人刻意重複呼叫時，這會反映在 Supabase 的流量用量（帳單），不是逾時。建議上線後觀察一週 egress 用量，不需要為此降低上限。
- **經銷會員**：同樣改成最多 1000 件。權限設定（只有登入會員能呼叫）不變，由事後檢查 ③ 驗；真正決定能不能拿到經銷價的是函式內的身分檢查（`customers.tier = 'store'`），它在本體裡，本體除了上限逐字不變，由 md5 驗。
- **不影響**：側欄件數（`catalog_facet_counts`）、搜尋、商品頁、後台。

## 5. 上線步驟（Sean 批准後）

1. Sean 批准本計畫。
2. 貼 `20260922130000`（貼板由 Sean 決定）。
3. 貼完執行 `NOTIFY pgrst, 'reload schema';`。
4. 同批執行 `pcm_acl_approve_latest`，備註帶 `20260922130000`（兩支函式換了一代）。
5. 等 2 分鐘再驗。目錄頁有 60 秒的伺服器快取（`getCatalogPageCached`），`NOTIFY pgrst` 不會清掉它，過期後的第一次請求也可能先拿到舊的 100 件，所以同一頁要重新整理兩次。
6. 用正式站走一次：MT-09 SP 選每頁 500，應看到全部商品；選每頁 200，第 1 頁 200 件、第 2 頁從第 201 件開始，而且第 1 頁的最後一件和第 2 頁的第一件不重複。退回時也照這兩步驗，數字變回每頁 100 件。

### 另一件可以一起考慮的事（不在本次範圍，要 Sean 決定）

選車時，商品頁先等專用區查完、再查通用區（`apps/storefront/src/app/products/(catalog)/page.tsx:500`、`:523`），兩次查詢互不依賴卻依序執行。每次最慢 3 秒逾時、再重試一次，最壞可能等約 12 秒。這是既有的結構，不是這次造成；改成同時查詢可以把選車頁等待時間約砍半，只動 `page.tsx` 一處，不碰資料庫。Fable 審查提出，要不要做由 Sean 決定。

碼不用跟著推，順序沒有限制。
