> **他拍的**:2026-09-10 逐字「**乙 = 要叫才來**」⇒ 接 `TransDispatchOrder_Json`。
> **射程**:只做「那顆鈕 + 它後面那條路」。**出貨清單頁本身是窗 D 的片,本檔不要求它改任何東西。**

## §0 這一片買的是什麼 —— **不是那支 API,是那句話**

Sean 選的形狀逐字:
> 他在出貨清單頁上勾好今天要出的箱,按一次
> ⇒ 那一刻**同時**:叫車 + 標已出貨 + 寄信給客人
> ⇒ **三件事對齊同一個動作,客人收到信的時候貨真的要走了**

🎯 **⇒ 本檔要守住的是那句「三件事對齊同一個動作」。** 那支 API 只是它的手段。

### 0-a 🔴 而在此之前,那三件事**各自散在不同的時間點**

```
1. TransData_Json          建單 + 拿標籤   ⇒ 新竹系統裡有這張單了     ← ✅ 已接
2. TransDispatchOrder_Json 叫司機來收      ⇒ 「我們要出貨了」         ← ❌ 本片要接的
3. (沒有這一支)             司機真的收走    ⇒ 「貨走了」               ← 🔴 新竹【不回報】
4. (沒有這一支)             貨到了          ⇒ 「客人拿到了」           ← 🔴 新竹【不回報】
```
🔬 **而「新竹沒有貨況回報」是量到的**:V15 那七支服務**全部是我們推給新竹的動作**
(建單 / 改重量 / 確認當日出貨 / 查貨號 / 逆物流 / 取消派遣 / 叫收貨),**沒有一支是「這箱到哪了」**;
而 `QueryEDELNO` 回的是 `success / edelno / epino / ErrMsg` ⇒ **答的是「這張單在不在」不是「這箱在哪」。**
⇒ 📌 **所以第 2 格是我們手上【最後一個】知道貨況的時間點** —— 那正是它值得對齊的理由。

## §1 🔴 `emark`(派遣者)—— **這一格要 Sean 給一個值,我不替他選**

V15 §8 逐字:`emark 派遣者 String(30) **必要欄位,不可為空白**`,
說明逐字:「**emark 是讓司機知道取哪個派遣者的貨件**」。

⇒ 📌 **那是一個【司機會讀的字】** —— 他到現場問「我來收 XX 的貨」。

```
甲 = 環境變數(一次設定, 全站同一個值)
     🔵 成本最低;而改它要重新部署(與 HCT_SUBMIT_ENABLED 同一族)
乙 = 後台設定頁的一格(Sean 自己改)
     🔵 他改得動;而今天【沒有那一頁】——「設定」那一頁的側欄逐字寫著「這一頁還沒做」
     ⇒ 要做這個選項, 等於順帶開一頁設定
丙 = 每次按那顆鈕的時候打字
     🔴 而它幾乎不會變(司機認的是同一個名字)⇒ 每次打一次的價值最低、打錯的機會最高
```
### 1-a 🟢 **[2026-09-10 · 兩格都答了]**

**Sean 逐字給的值:`派達有限公司`。** 存放處**判甲(環境變數)**。

🔵 **甲的理由不是「最省」**:
· **乙(後台設定頁)** ⇒ 「設定」那一頁今天側欄逐字寫著「**這一頁還沒做**」
　⇒ 📌 **為了一個字去開一整頁,那是範圍擴張。**
· **丙(每次打字)** ⇒ 它幾乎不會變 ⇒ 價值最低、打錯機會最高,
　而 🔴 **打錯的代價是【司機找不到要跟誰拿貨】。**
· **甲** ⇒ 改要重新部署,**而它幾乎不會變 ⇒ 那個代價幾乎不會被付。**
⏰ **而哪天它要變成可設定的,那是「設定頁」那一列的事,不是這一片的。**

### 1-b 🔬 `String(30)` 那一格 —— **量的,不是算的**

`派達有限公司` = **6 個中文字**。而 🛑 **V15 沒說那個 30 是【字元】還是【位元組】**:
```
字元數        6
UTF-8 位元組  18   (6 × 3)
Big5  位元組  12   (6 × 2)
⇒ ✅ 三種讀法都在 30 以內 ⇒ 【這個值安全, 不必為它加長度閘】
```
🛑 **而長度不是這一格真正的問題 —— 編碼才是**(司機會不會看到亂碼)。
✅ **而那一格今天有答案,而且是【行為】證的**:
```
第一箱 S9FC6P 送出去的那一包裡有中文(ercsig 派達有限公司 · eraddr 新北市新莊區化成路736巷18號1樓)
⇒ 新竹【收下了】而且回了正確的貨號 8947081964 · epino 回音相符 · ErrMsg 空
🔬 而送出去用的是 hct-client.ts:251 逐字 `'Content-Type': 'text/xml; charset=utf-8'`
```
⇒ 📌 **中文這條路今天是通的,而它是 UTF-8。**
⇒ 🛑 **⇒ 本片【照 `hct-trans-data.ts` 既有的做法,不自創第二種】** —— 同一支 client、同一個信封。
⚠️ 而**證不到的那一格**:我證的是「**收件人姓名與地址**那兩欄的中文通得過」,
　 **`emark` 是另一個欄位** ⇒ 📌 **同一個信封、同一個編碼,而【那一欄本身】沒有被驗過。**

## §3 🔴🔴 部分成功 —— **本檔最重要的一節**

回傳形狀(V15 §8.2,而**我實際讀過那個範例**):
```
{ "rtn_code": 1, "rtn_msg": "派遣收貨成功建檔",
  "rtn_data": [ { "num":"1", "success":"Y", "edelno":…, "epino":…, "ErrMsg":… }, … ] }
```
⇒ 📌 **每一箱各自有 `success` 與 `ErrMsg`** ⇒ **「這一批成功了嗎」不是一個是非題。**

### 3-a 三種順序,而**只有一種的失敗方向是可補的**

```
甲 先全部叫車 ⇒ 全成功才標出貨+寄信
   🔴 第 7 箱失敗 ⇒ 前 6 箱【車已經叫了】而我們沒標出貨
   ⇒ 司機會來收那 6 箱, 而客人沒收到信 ⇒ 📌 貨走了而沒有人知道
乙 先標出貨+寄信 ⇒ 再叫車
   🔴 最糟:信寄出去了而車沒叫到 ⇒ 客人以為東西在路上, 而它在架上
   ⇒ 📌 而【信收不回來】
丙 逐箱各自結算:那一箱叫車成功 ⇒ 才標出貨+寄信;失敗 ⇒ 那一箱【原封不動】
   ✅ 失敗方向是「車叫了而沒標出貨」—— 而它【可補】:箱子還在, 員工再按一次就好
   🔵 而它不是我發明的形狀 —— **API 自己就是逐筆回 success 的**
```
✅ **⇒ 丙。而理由不是偏好,是【失敗方向的可補性】**:
```
可補   車叫了而沒標出貨  ⇒ 貨還在我們手上, 再按一次
不可補 標了而車沒叫       ⇒ 客人收到「已出貨」而貨不會走
不可補 信寄了而車沒叫     ⇒ 同上, 而且更早
```
🛑 **而丙的殘餘要寫出來,不能假裝沒有**:單一箱在「API 回成功」與「DB 標出貨」之間掛掉
⇒ **車叫了而沒標** ⇒ 📌 **那一箱在畫面上看起來還沒出貨,而司機會來收它。**
⇒ ✅ **處置**:那是**可補的**方向,而**員工再按一次會怎樣**要答:
　 V15 §8 沒有寫「重複派遣」的行為 ⇒ 🔴 **未知**。
　 ✅ **[2026-09-10 定案]**:**擋住** —— 已派遣過的箱**不給再按**。
　 　 🔵 而那讓 §3-a 那個殘餘(車叫了而沒標)**變成需要人處理的一格**,不是自動補
　 　 ⇒ 📌 **那是刻意的**:在「重複派遣會怎樣」有答案之前,**寧可要一個人看一眼,也不要自動再打一發。**
　 ⏰ **要不要去問新竹是 Sean 的事** —— 端出去了,而**本片不因此停下來**。
　 ⚠️ **本檔不猜它** —— 那是 §7 的證不到。

## §5 parser —— **不能照抄 `TransData_Json`**

```
TransData_Json          直接回【陣列】            [ { success, edelno, … } ]
TransDispatchOrder_Json 包在 rtn_data 裡的物件   { rtn_code, rtn_msg, rtn_data: [ … ] }
```
🔴 **外層形狀不同** ⇒ 照抄會拿到 `undefined` 而不是錯誤 ⇒ 📌 **它會安靜地判成「沒有一箱成功」。**
✅ **而 `hct-client.ts` 的既有形狀可以沿用**:它的 `reason` 已經分得出
`soap_fault` / `body_not_soap_json` / `row_count_N` / `unrecognised_success_X`
⇒ **新增一種 `rtn_code` 不對的 reason**,而**不要把它塞進既有那幾種**。

## §6 🛑 怎麼在【不寄一封信】的情況下驗完

**這條路會寄信給客人** ⇒ 而驗收**必須**在零寄信下有效。

```
① API 那半 —— 用【假 client】驗, 不打真的
   🔵 形狀已經有了:`hct-submit-flow.ts` 檔頭逐字「本檔零 DB 依賴 ⇒ 它的每一條路都用假 client 驗得完」
   ⇒ 本片照同一個分界:決定 ⇒(組請求)⇒ 回一個【呼叫端可以直接落庫】的結果
   ⇒ 逐筆 success/ErrMsg 的每一種組合(全成功 / 部分 / 全失敗 / rtn_code 不對 / rtn_data 缺)各一格
② DB 那半 —— 拋棄式 PG, 真的那支 mark_shipped RPC
   🔴 而【不要重寫一份 UPDATE 來比】—— 那是在比我自己的兩個想法
③ 寄信那半 —— **零寄信驗法**:
   標出貨會讓那一箱落進待寄 view(`WHERE s.shipped_at IS NOT NULL`, 唯讀實量)
   ⇒ ✅ **驗「它落進去了」, 而不要跑 sweep** —— 落進去就是這一片的責任邊界,
     真的寄出去是 `pcm-email-sweep` 那條線的事
   🛑 而拋棄式 PG 上**本來就沒有 sweep 在跑** ⇒ 零寄信是結構上的, 不是靠記得不要跑
④ 🔴 第一發真的 API ⇒ **Sean 在場**, 像第一箱那樣。而**送出去之前把那一包逐欄印出來**。
```
