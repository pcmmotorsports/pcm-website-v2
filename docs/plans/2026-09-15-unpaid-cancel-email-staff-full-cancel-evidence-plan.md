# 2026-09-15 · 未付款取消信:用「員工真的整單取消」的證據取代「曾有取消紀錄」—— plan

> **本檔只是 plan,零碼改動。** 碰 view / RPC(schema)+ 寄信 ⇒ 鐵則 8 + 12,等批。

## 1. 白話

- 未付款的單被**員工**整單取消,系統會寄一封「您的訂單已取消」給客人(Sean 09-03 拍甲);**系統自動取消的不寄**。
- 系統今天分辨「是不是員工取消」的方法是:**這張單曾經有一筆取消紀錄**(`order_cancellations`)。
- 而**部分取消**也會留下取消紀錄。所以一張「員工先取消了其中一件、後來整張被**系統**取消」的單,會被當成員工取消 ⇒ 誤寄。
- `20260915210000` 已經排掉其中一種系統取消(逾時自動取消 `payment_expired`)。**還剩一種**:未付款的匯款單,客人改用刷卡付款,系統把匯款單標成被取代(`superseded_by_card`)。
- **今天有沒有真的發生**:正式庫 2026-09-15 唯讀,未付款而取消的單共 5 張,`superseded_by_card` **0 張** ⇒ 目前沒有客人會收到錯的信。

## 2. 為什麼不直接再排除 `superseded_by_card`

| 做法 | 問題 |
|---|---|
| view 加 `cancelled_reason <> 'superseded_by_card'` | 員工取消時的理由是**自由文字**,只有 `payment_expired` 被擋(`20260903093000` 保留字閘)⇒ 員工剛好打出那串字 ⇒ 那位客人收不到信(漏寄)。 |
| 把 `superseded_by_card` 也加進保留字閘 | 可行,但仍然是「拿理由欄的字面當身分」—— 下一種系統取消出現時同一個洞再開一次。 |

⇒ 要換掉的是**判準本身**,不是再補一個字。

## 4. 範圍(做的時候)

- `pcm_unpaid_cancelled_email_pending`(view)與 `get_order_unpaid_cancelled_gap_counts`(告警 RPC)**同一顆一起換** —— 兩端口徑不一會出現「寄信端收了、告警端不算」。
- TS scanner 不動(它只讀 view)。
- 拋棄式 PG 世界至少四格:
  ① 員工整單取消 ⇒ 要寄
  ② 部分取消 → 逾時自動取消 ⇒ 不寄(`20260915210000` 已有,不得退步)
  ③ 部分取消 → 被刷卡取代(`superseded_by_card`)⇒ **不寄**(本 plan 要關的那一格)
  ④ 員工整單取消而理由欄剛好打了 `superseded_by_card` ⇒ **要寄**(證明判準不再看理由欄字面)
- 前置閘:驗 view / RPC 是 `20260915210000` 那一代的完整定義 md5(同該檔做法)。
- codex 一輪(寄信 + schema)。
