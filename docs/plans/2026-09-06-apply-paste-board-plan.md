## 2. 五段流程(f8 的 ①-⑤,逐條展開成可驗的形狀)

### ① 前置(全部通過才進入 ②)

| # | 檢查 | 不通過時 |
|---|---|---|
| 1 | 貼板檔存在**且唯一**(`~/pcm-mailbox/貼板-0905/<編號>_*.sql` 只命中 1 支) | 印命中幾支 + 全部路徑,停 |
| 2 | 印**貼板檔 sha256** | — |
| 3 | 從**檔名**取版本號(`<編號>_<14 位>_…`);非 14 位數字 ⇒ 停 | 印檔名,停 |
| 4 | `supabase/migrations/<版本號>_*.sql` 存在且唯一 | 停 |
| 5 | 🔴 **貼板檔 sha == repo migration 檔 sha** | **印兩個 sha,停**(f8 的 ④) |
| 6 | `APPLIED.tsv` **第一欄**無此版本(解析欄位,不整行 grep) | 印那一列,停 |
| 7 | 🔴 **唯讀證明「還沒貼」** —— 跑 `is-migration-applied.sh <版本>` 產的 SQL,用 `PCM_READONLY_DATABASE_URL` 執行 | **查出「已貼」⇒ 拒**(f8 的 ④) |

🔴 **第 7 條的兩個已知限度,寫進工具的輸出、不藏**:
· `is-migration-applied.sh` 自己標【判別力:有/無/未知】。**判別力=無** 的版本(例如純 `CREATE OR REPLACE`)
  ⇒ 那一發**證不了「還沒貼」** ⇒ 🛑 **本工具在這種情況下【停下來問人】,不自己放行。**
  📌 理由:「查不出來」與「確定沒貼」印同一個東西,而**放行的代價是重貼一次**。
· 那個唯讀身分是 `pcm_readonly`,**讀不到 `supabase_migrations` schema** ⇒ 它答的是「物件在不在」,不是「平台帳本有沒有記」。

### ② apply

```
psql -v ON_ERROR_STOP=1 -1 -f <repo 的 migration 檔>
```
🔴 **貼的是 `supabase/migrations/` 那一支,不是貼板那一支** —— 兩者 sha 已在前置第 5 條比對相同,
而**帳本第二欄記的是 repo sha**(`APPLIED.tsv` 檔頭逐字)⇒ 貼 repo 那份,兩件事才對得起來。
· `-1` = 單一交易;任何 ERROR ⇒ **整支回滾**。
· 連線串來自 `.env.local`(**只有主樹有**;worktree 沒有 ⇒ 那是設定缺失不是服務故障)。

🔴🔴 **寫入連線的 env 名【我不知道,而我沒有去開 `.env.local`】。**
唯讀那條路用的是 `PCM_READONLY_DATABASE_URL`(從 `scripts/readonly-prod-sql.sh` 與
`~/pcm-mailbox/0905查證/run.sh` **只印名不印值**掃出來的)。
⇒ 提案:**寫入用 `PCM_WRITE_DATABASE_URL`**;工具啟動時若讀不到它 ⇒
**逐字印出缺哪一個名字**、停,由 Sean 補。
🛑 **絕不印值、絕不把連線串寫進 log 或對話**;log 只存 psql 的**輸出**,不存指令列。

### ③ 事後(只有 ② 成功才做)

1. `supabase migration repair --linked --status applied <版本>` —— **只此一支**。
2. `APPLIED.tsv` **追加一行**(TAB 四欄):
   `<版本>` / `<repo 檔 sha256>` / `<貼的日期>` / `@<貼時時刻> 貼板 sha=<貼板 sha>;主視窗依 Sean「貼 <編號>」代貼`
   🔵 第二欄 repo sha、貼板 sha 進第四欄 —— 照 `-f8` 2026-09-05 的裁定。
3. psql **完整輸出**存 `~/pcm-mailbox/貼結果-<編號>-<時刻>.log`。

### ④ 拒絕面(任一命中 ⇒ **不記帳、不 repair**)

編號給錯 · 貼板檔非唯一 · **兩個 sha 不同(印兩個 sha)** · 版本已在帳本 ·
唯讀查說已貼 · **唯讀查的判別力=無** · psql 任何 ERROR(**印整段 ERROR**)。

🔴 **一個 f8 沒點名而我要加的拒絕面**:`psql` 成功但 `repair` 失敗 ⇒
**DB 已經變了而帳本沒記** ⇒ 🛑 **不可以靜靜結束**:印一段「**已 apply 而未記帳**」的紅,
並把要補的那一行 `APPLIED.tsv` 內容印出來讓人手貼。
📌 這一格是**半套狀態**,而它在 rc 上與「什麼都沒做」長得一樣。

### ⑤ selftest(兩世界,走拋棄式 PG)

`--db-url <url>` 覆寫連線 ⇒ selftest 指到 `docs/runbooks/throwaway-postgres-for-migration-verification.md`
起的拋棄式 PG,**永不碰正式庫**。

| 世界 | 餵什麼 | 期望 |
|---|---|---|
| ① 該綠 | 一支合法 migration、帳本無此版本、唯讀查說沒貼 | apply 成功 · 帳本多一行 · log 存在 · rc=0 |
| ② 該紅 | 同一支**再跑一次** | 前置第 6 條擋下 · **帳本沒有第二行** · rc≠0 |
| ③ 該紅 | 貼板檔被改一個字(sha 不同) | 印兩個 sha · **psql 一次都沒被呼叫** |
| ④ 該紅 | migration 裡塞一句必錯的 SQL | ERROR 整段印出 · **交易回滾** · 帳本沒有那一行 · **repair 沒被呼叫** |
| ⑤ 負對照 | 一個不存在的編號 | 停在前置第 1 條 |

🔴 **③④ 兩格要驗的是【沒有做什麼】** —— 「帳本沒多一行」與「repair 沒被呼叫」。
⇒ 做法:selftest 把 `supabase` 與 `psql` 換成**記帳樁**,事後數呼叫次數。
📌 **一個只驗 rc 的 selftest 分不出「擋下來了」與「做了一半才失敗」。**

🔵 另跑 `.husky/`… ⇒ ⛔ **那個路徑不存在**,是 `bash scripts/selftest-git-isolation-gate.sh`
(本片會造拋棄式 git repo ⇒ selftest 第一件事剝 `GIT_DIR` 等七個環境變數)。

## 4. Rollback

| 走到哪一步失敗 | 怎麼回去 |
|---|---|
| ① 前置 | 什麼都沒發生 |
| ② psql ERROR | `-1` ⇒ **整支交易回滾**,DB 未變 |
| ② 成功、③ repair 失敗 | **DB 已變** ⇒ 不可逆。補救 = 手跑 repair + 手記帳(工具會把該貼的那一行印出來) |
| ③ 全成功而事後發現貼錯 | 🔴 **沒有自動 rollback** —— 要那支 migration 自己的 down 腳本;**沒有 down 的就沒有回頭路** |

🛑 **⇒ 所以「一次一支 + Sean 逐支點名」不是流程繁瑣,它是這片唯一的 rollback。**
