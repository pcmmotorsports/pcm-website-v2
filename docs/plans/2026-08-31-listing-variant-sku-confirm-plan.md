## 1. 這道確認要擋的是什麼(而它有真實的病歷)

```
2026-07-27 08:01:32  🔴 7 支幽靈商品被建出來(external_id = 某支商品的 variant sku)
2026-07-27 08:01:35  ✅ 那 7 個【變體】建出來 —— 只差 3 秒 ⇒ **同一跑寫了兩種**
2026-08-06 07:14:33  🔵 有人把那 7 支【下架】(同一秒, 那一秒只動這 7 支)
2026-08-06 07:15:29  ✅ 正牌商品 ARSV421-08 建出來
```
🔴 **⇒ 上一次的處理是【下架】不是【刪除】** —— 而那正是它們今天還在、
**後台按一下就回到架上**的原因。而報價單那邊說「只刪不修,下次跑完會再長回來」。
📌 **⇒ 所以這道確認擋的不是「今天」,是【它們下次又長回來、又有人要上架】的那一刻。**

## 2. 判準(已實跑,命中正好那 8 支)

```sql
-- 「這支商品的 external_id 是某支【別的】商品的 variant sku」
-- **AND**「這支商品自己沒有任何變體」
EXISTS (SELECT 1 FROM product_variants v WHERE v.sku = p.external_id AND v.product_id <> p.id)
AND NOT EXISTS (SELECT 1 FROM product_variants v2 WHERE v2.product_id = p.id)
```
```
✅ 今天命中 **正好 8 支**, 而且答得出【是誰的規格】(ARSV421-08 / YAMT07-06)
🔴 少了第二個條件 ⇒ 命中 **34 支**, 其中 **26 支是正常商品** ⇒ 誤報 **76%**
🟢 那 2 支「可能合法的無變體商品」(EG-75617 / KSP-SEAT-DIABOLUS…)⇒ **不命中**(不誤傷)
```

### 🛑 兩格天花板 —— **本 plan 要求它們寫在【碼旁】,不是只寫在這裡**
```
① 它只認【這一個形狀】:變體 sku 被當成商品 external_id。
   別的方式產生的重複商品, 它一支都抓不到。
② 🔴 它靠【本尊還在】:若 ARSV421-08 哪天被刪掉, 那 7 支孤兒就【不再命中】
   ⇒ **這把尺會在資料變得更糟的時候變得更安靜。**
```
📌 ②那一句要逐字進碼 —— **多數尺在世界變糟時叫得更大聲,而這一把相反。**

## 3. 設計:兩層,而且**只在「要上架」時檢查**

```
· 下架不檢查 —— 把一支可疑商品【下架】永遠是安全的
· 上架才檢查(parsed.delisted === false 那條路)
```
```
第一層(頁面, 早於按鈕):商品頁載入時就算一次 ⇒ 若命中, 在上架鈕旁邊直接顯示
  「這支商品看起來是 ARSV421-08 的一個規格」
  🔵 **為什麼要有這一層**:它讓人在【按之前】就看得到, 而不是按了才被擋
     —— 一個只在按下之後才出現的警告, 讀的人已經在「我要完成這件事」的狀態裡了

第二層(server action, 不信任 client):setProductListingAction 裡再算一次
  · 命中而表單沒帶確認 ⇒ 擋下, redirect 帶新的 ResultCode
  · 命中而表單帶了確認 ⇒ **放行**(這是【確認】不是【封鎖】)
  🔴 兩層都要, 而理由不是保險:第一層是【給人看的】, 第二層是【真的擋的】
     —— 少了第二層, 改個表單就繞過去了; 少了第一層, 它只是一道拒絕
```
