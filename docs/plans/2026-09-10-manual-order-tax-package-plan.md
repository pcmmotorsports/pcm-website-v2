## §1 ② 反向換算 —— **這一格最重要,先講它**

### 1-a 今天的行為(複量,不是讀 fable)

`untaxedFromTaxed(taxed)`:`(taxed*20) % 21 === 0` 才回數字,**否則回 `null`** ⇒ 呼叫端整張表單拒收。
訊息逐字:「單價 1,100 標成含稅,而它換算回未稅是 1047.62(約)—— **不是整數,系統不敢自己四捨五入**(那會安靜地改掉金額)。請跟對方問到未稅金額…」

### 1-b 🔴 **它為什麼「不敢」—— 而那個理由是量到的,不是感覺**

檔內逐字記著(codex 2026-09-06 提供、作者複核):
> 含稅 999 ⇒ 若四捨五入成未稅 951,數量 1 加回 5% 是 999 ✅,而**數量 2 是 1,997 而不是 1,998**
> ⇒ 一塊錢的洞,每一筆都長得很正常。⇒ **拒絕比反推安全。**

🔬 **我自己重算了一遍**(不吃轉述):
```
含稅 1100 ⇒ 四捨五入未稅 1048
  數量 1 ⇒ 小計 1048 + 稅 52  = 1100   員工心裡的 1100   差  0  ✅
  數量 2 ⇒ 小計 2096 + 稅 105 = 2201   員工心裡的 2200   差 +1  🔴
  數量 3 ⇒ 小計 3144 + 稅 157 = 3301   員工心裡的 3300   差 +1  🔴
含稅  999 ⇒ 四捨五入未稅  951
  數量 2 ⇒ 小計 1902 + 稅 95  = 1997   員工心裡的 1998   差 -1  🔴
⚪ 對照(除得盡的那一種):含稅 1050 ⇒ 未稅 1000 · 數量 2 ⇒ 2100  差 0 ✅
```
⇒ 🎯 **四捨五入在【數量 1】永遠對,在【數量 ≥ 2】會差一塊,而且方向兩邊都有。**
⇒ 📌 **那正是那道閘在防的東西,而它防對了。**

### 1-c 🔴 **而 Sean 的算例是【訂單總額】,今天那道閘是【單價】—— 兩個受詞**

他逐字:「運費 100 + 商品 1000,先勾填 1100 再取消勾 ⇒ **1048**」。
🔬 `1100 ÷ 1.05 = 1047.619 → 1048` ⇒ **他算的是【整張單】1100 反推。**
而今天那道閘攔的是**單一品項的單價**(`parseLineEntry` 逐列跑)。
⇒ 🛑 **兩者不是同一個數**:那 1100 裡有 **商品 1000 + 運費 100**,
　 而反推出來的 1048 **要怎麼拆回「商品多少 / 運費多少」,他沒有說。**
⇒ 🔴 **這一格【不是實作細節,是規格缺口】** —— 我不替他決定。

### 1-c-2 🟢🟢 **[2026-09-10 · 我去開了那個發票助手,而它答掉 Q1]**

Sean 逐字:「**我有給你發票助手的網頁,用他們的方式去計算就會是正確的**」⇒ `https://simpany.co/invoice-helper`
🔬 **我用瀏覽器實際輸入,而不是讀它的說明**(只讀,沒有送我們的任何資料進去):

```
輸入含稅 1100  ⇒ 未稅 1048 · 營業稅額 52     ← 🎯 正是 Sean 說的 1048
輸入含稅  999  ⇒ 未稅  951 · 營業稅額 48
輸入含稅 11000 ⇒ 未稅 10476 · 營業稅額 524
```
⇒ 📌 **它的算法是**:`未稅 = round(含稅 ÷ 1.05)`,而 **`稅額 = 含稅 − 未稅`(殘差,不是正推)**。
　 (1100÷1.05 = 1047.619 ⇒ **四捨五入 1048**,不是無條件捨去的 1047 ⇒ 這一格分得出來。)

🎯 **而它的【形狀】答掉了 Q1**:那一頁**只有 5 個輸入欄**——
`company_vat` · `company_name` · `priceWithTax` · `taxAmount` · `priceWithoutTax`
⇒ 🛑 **沒有數量欄、沒有品項欄。**
⇒ 📌 **它的受詞是【一張發票的一個總額】,不是單價、不是逐列。**
⇒ ✅ **Q1 的答案是【乙】** —— 反推的對象是**整張單的總額**,而那正是 Sean 算例的算法。
⇒ 🎯 **而那順帶讓 Q2 消失**:在「反推整張單一次」的模型裡,**數量根本沒有進場的機會。**

### 1-c-3 🔴🔴 **而我撞到一個【它沒答、而且更嚴重】的東西**

**simpany 算稅是【殘差】(`含稅 − 未稅`),而我們的 RPC 是【正推】(`round(未稅 × 5%)`)。**
🛑 **兩者不是同一個算法** ⇒ 我實算 1..20,000 的每一個含稅金額:

```
分岔筆數 = 952 / 20,000(約 4.8%)
  含稅  11 ⇒ 未稅 10 · simpany 稅 1 · 而我們的 RPC 算 0 ⇒ 總額回到 10, 不是 11
  含稅  31 ⇒ 未稅 30 · simpany 稅 1 · 而我們的 RPC 算 2 ⇒ 總額回到 32, 不是 31
  含稅  53 ⇒ 未稅 50 · simpany 稅 3 · 而我們的 RPC 算 2 ⇒ 總額回到 52, 不是 53
⚪ 而 Sean 的 1100 【剛好不在那 952 個裡面】⇒ 他試的那一個看起來完全正常。
```
⇒ 🎯 **所以「照 simpany 的方式反推」【單獨做不成立】** ——
　 反推出 1048 之後,**RPC 會用它自己的方式再加一次稅**,而在約 4.8% 的金額上**加不回原來那個數**。
⇒ 🛑 **那正是原本那道閘擔心的「安靜地改掉金額」,換了一個地方出現。**
⇒ 🔴 **⇒ 這一件【碰 SQL】**:要嘛改 RPC 的算稅法(殘差),要嘛在反推那一步就保證回得去。
　 **而那是 migration + 鐵則 12① ⇒ 不是純前端。**

### 1-d 要他拍的問題(**Q1/Q2 已被那個工具答掉,只剩兩題**)

```
⛔ ~~Q1 反向換算的受詞~~ ⇒ ✅ 那個工具答了:【整張單的總額】(它沒有數量欄也沒有品項欄)
⛔ ~~Q2 數量 ≥ 2 差一塊~~ ⇒ ✅ 在「反推整張單一次」的模型裡, 數量沒有進場的機會 ⇒ 題目消失

🔴 Q2′(新的, 而它比原本的 Q2 嚴重):simpany 算稅是【殘差】, 我們的 RPC 是【正推】,
    1..20,000 裡有 952 個金額兩者差一塊(§1-c-3)。要怎麼收?
  甲 = 把 RPC 的算稅法改成【殘差】—— 與那個工具一致 ⇒ 🔴 碰錢的 migration
  乙 = 反推那一步就只放行【兩種算法一致】的金額, 其餘維持今天的拒收
       ⇒ 純前端, 而他仍會偶爾被擋(約 4.8%)
  丙 = 反推之後把差額補進運費或折扣 ⇒ 動到另一個欄位

Q3: 換算完之後, 畫面要不要讓員工【看見換算結果再按一次】?
  甲 = 要 —— 與截斷那一族同一個殼(「看過再按一次就送」)
  乙 = 不要, 直接換
```
🔵 **Q2′ 我不選邊**(那是他的錢:甲改的是每一張單的算法,乙讓他偶爾被擋)。
　 ⚠️ 而**要跟他講清楚的一句是**:他試的那個 1100 **剛好不在那 952 個裡面**
　 ⇒ 📌 **他看到的「它算得對」是真的,而那不代表每一個金額都對。**
✅ **而 Q3 我建議甲** —— 理由:那道閘原本的訊息逐字擔心的是「**安靜地改掉金額**」,
而**讓他看見再按一次,正好把「安靜」那半拿掉,而保留他要的自動**。

## §2 ① 勾發票的當下畫面數字立刻變

### 2-a 今天的行為(複量)

```
manual-order-form-body.tsx   useState 0 · useMemo 0 · 合計 0     ← 純 server component
manual-order-lines.tsx       useState 3 · useMemo 0             ← 有 state, 而【刻意沒有小計】
manual-order-submit.tsx      useState 5 · useMemo 0
```
`manual-order-lines.tsx:341-342` 逐字:
> ⚠️ 這裡**沒有**小計 —— 金額由 RPC 自己算,它不信任何 client 送的合計。
> **在畫面上算一份會生出「畫面說 A、單子是 B」的第二個真相。**

### 2-b 🔵 而那個顧慮**可以被滿足**,不必推翻它

📌 **它擔心的是「client 算的數字【被送出去】或【與單子不一致】」** ——
而 Sean 要的是**一個預覽**:勾下去看到 1155,而**進 DB 的仍然是 RPC 算的**。
⇒ ✅ **修法**:畫面上顯示的數字**標明它是預覽**,而**送出去的欄位一個都不變**(仍然只送單價 + 稅基 + 勾選)。
⇒ 🛑 **而風險是真的**:預覽的算式與 RPC 的算式**是兩份**,它們遲早會不一樣。
　 而今天那份 RPC 的算式**住在 SQL 裡**(§0-a)⇒ **沒有辦法共用同一支函式**
　 ⇒ 📌 **這是【必須接受的重複】,而它要有一道守門**:
```
✅ 驗收要有一格:拿【同一組輸入】餵預覽與餵真的 RPC(拋棄式 PG), 兩邊的總額必須相同。
   而那一格要含【四捨五入的邊界】:小計+運費 的 5% 落在 .5 的那幾個數。
🛑 沒有這一格的話, 這一片就是在製造它上面那句話警告的東西。
```

### 3-a-3 我們這邊會長什麼樣(用他操作的角度寫)

```
他在建單畫面的「發票」那一區,勾了「這張單要開發票」、選「公司」
⇒ 統編那一格旁邊多一個【自動】的行為:他打完 8 碼, 隔壁「抬頭」自己填好

⇒ 🔴 查不到 / 服務掛掉 ⇒ 那一格【什麼都不做】, 他照樣自己打 —— 畫面不擋、不跳錯誤
   (最多在旁邊一行小字說「這次沒查到,請自己填」)
```
🛑 **而三件要在實作前決定的**:①從瀏覽器打還是從我們 server 打(前者把來源暴露給第三方,後者多一支 route)
②要不要快取(同一個統編一天內不重打)③要不要記下「這個抬頭是查來的還是手打的」。

### 3-b 🛑 而這一件的風險【不在稅】,在【對外連線】

⇒ 📌 它要打**財政部/經濟部的 API**(或第三方)⇒ **這是一個新的對外相依**:
```
· 那支 API 掛掉時, 建單流程會不會跟著卡住?  ⇒ 必須 fail-open(查不到就讓他自己打)
· 要不要快取? 打太多次會不會被擋?
· 🔴 而【誰去打】—— 從瀏覽器打會把我們的來源暴露出去;從 server 打要多一支 route
```
🔵 **建議**:這一件**與另外三件拆開**做 —— 它零 SQL、零金額,而它的風險完全是另一族。
⇒ **不要因為「都在同一個表單上」就綁成一片。**

## §4 ④ 「未稅 / 含稅」下拉的預設

### 4-a 今天:預設**未稅**(`manual-order-lines.tsx:271` `defaultValue={MANUAL_ORDER_LINE_TAX_BASIS_UNTAXED}`)

### 4-b 🔴 而它今天的失敗形狀

Sean 逐字說他「**基本上先 key 未稅**」⇒ **預設值與他的習慣一致**。
🛑 **而危險在【他有時 key 含稅】那幾次**:下拉留預設 + 勾發票
⇒ 系統把那個含稅數字當未稅、再加 5% ⇒ **多收。**
🔬 實算:key `1050`(心裡是含稅)+ 勾發票 + 留預設 ⇒ `round(1050×0.05)=53` ⇒ **收 1,103**。

### 4-c 而「講清楚」有三種做法,代價不同

```
甲 = 只改文案(那一格旁邊寫死「你填的是未稅」)—— 最小, 而它擋不住手滑
乙 = 不給預設, 強迫每一列選一次 —— 擋得住, 而每一張單多 N 次點擊
丙 = 預設維持未稅, 而【勾發票的當下】把那一列的稅基顯示出來(配 §2 那個預覽)
   ⇒ 他勾下去看到 1155 而不是他心裡的 1100 ⇒ 當場發現
```
✅ **我建議丙** —— 理由:**它與 ① 是同一個修法**(勾下去看得到數字),
而**發現錯誤的時機正好是他要看數字的那一刻**。⇒ 一份工,兩件事。
