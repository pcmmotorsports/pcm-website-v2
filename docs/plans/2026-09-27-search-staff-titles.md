# 計畫片段：客人搜尋也比對員工改過的標題與副標（商品編輯片 10，2026-09-27，窗「進度 a0」）

## 1. 問題

- 員工在後台改的標題、副標存在 `products.staff_overrides`（`title` / `subtitle` 兩個鍵，`20260927040000`）。商品頁、目錄卡片讀的 view 用「員工的優先，沒填才用供應商的」，所以客人**看得到**新標題。
- 但關鍵字搜尋 `storefront_search_product_ids` 直接比對 `products.title` / `subtitle`（供應商的原字），**用新標題裡的字搜不到**。
- 目錄頁、品牌頁、經銷站的關鍵字搜尋（`search_catalog_by_vehicle` 與 `_dealer`，`20260922130000`）都在裡面呼叫這一支 ⇒ 只改這一支就全部涵蓋。

## 2. 要比對哪一份（建議：兩份都比）

| 做法 | 客人用新字 | 客人用舊字（供應商原名、網路上查到的型號名） |
| --- | --- | --- |
| **甲（採用）兩份都比** | 找得到 | 找得到 |
| 乙 只比顯示中的（員工優先） | 找得到 | 找不到 |

採甲：員工改標題多半是翻成中文或縮短，客人手上的仍常是原廠英文名；兩份都比不會讓任何今天搜得到的商品消失。主視窗建議同甲。這是技術選擇，不另問 Sean。

## 3. 怎麼改（`supabase/migrations/20260927070000_m4b_search_staff_override_titles.sql`）

1. **新的部分索引** `products_staff_text_override_idx`：`ON products (id) WHERE delisted_at IS NULL AND (staff_overrides ? 'title' OR staff_overrides ? 'subtitle')`。
   - 只收「上架而且員工改過標題或副標」的商品（正式庫 09-27：0 件；以後是員工一件一件手改的量）。
   - 為什麼要：不加的話，每次搜尋都要整張商品表（64 MB）逐列看有沒有員工標題。加了之後只讀這幾件。
   - 不用新函式 ⇒ 沒有「寫入商品的角色要能執行索引函式」那個問題（`20260921010000` 檔頭）。
2. **搜尋函式加一個命中區塊 ①c**：只看上面那批商品，員工標題或副標 `ILIKE '%詞%'`，或（英數詞、折疊後 ≥ 4 碼）折疊比對，規則與原本 ① 和 ⑤ 相同。
   - 中文 1–2 字的詞也在這裡直接 `ILIKE`：這批商品很少，不需要中文字索引；結果與 ①b 的「切字比對」等價。
   - 原本的 ①、①b、②、③、④、④b、⑤ **一字不改** ⇒ 供應商原字照舊搜得到、效能照舊。
3. **整串優先（⑥ `ph_hits`）**：從「每個詞都中」的商品裡挑整串相符的那批時，比對字串多放員工標題與副標。不然員工標題才有整串的商品會被別的商品擠掉。
4. **相關度排序（Sean 09-15）**：「強命中」的判斷多認員工標題與副標（原字 `ILIKE` 或折疊）。原本認的供應商標題、副標、品牌名照舊。層級規則（0 料號完全相符／1 每個詞都強命中／2 部分／3 其他）與同層排序（無真圖排後 → 價高在前 → id）不動。
5. **不動的拍板**：Sean 09-10 純字母料號用相等式（④b）、零價變體照樣搜得到、`is_exact` 只看料號，全部原封不動。

## 4. 驗收（拋棄式 PostgreSQL，本機）

- 放入正式庫現行版本（md5 `8112e9bbe07a90c44933962b61189ea0`，09-27 唯讀撈 `pg_get_functiondef`，與 repo 逐字相同）、三支輔助函式與六支索引，自造商品資料。
- 員工改過標題的商品：用新標題的字（中文 1 字、2 字、3 字以上、英文、折疊寫法）搜得到；用供應商原字也還搜得到。
- 沒有員工標題的商品：多組搜尋詞新舊結果逐筆比對 `(順序, 商品, is_exact, tier)`，差異 0；並有負對照證明比對會抓到差異。
- 下架商品即使員工改過標題也搜不到。
- `EXPLAIN`：①c 走新的部分索引，不是整表掃；原本各區塊的索引使用不變。
- `service_role` 寫商品不受影響；函式仍是 SECURITY DEFINER、`search_path` 空字串、四個 grantee 都在。
- rollback 能退回 md5 `8112e9bb…` 並拿掉新索引。

### 2026-09-27 本機驗證結果（拋棄式 PostgreSQL 17.10，自造 2 萬件商品）

- 正式庫現行函式放進本機後 md5 = `8112e9bbe07a90c44933962b61189ea0`；migration 前置、事後檢查全部通過，新函式 md5 = `396e7d5ffae1af6bfccf2373ef86413b`。前置檢查缺 `products_staff_overrides_shape` 時會擋下（實測）。
- **沒有員工標題時新舊逐筆相同**：35 組詞（1–3 字中文、英文大小寫、折疊寫法、`%` `_`、帶空白、重複詞、空陣列、品牌、料號、多詞）共 142,767 列，比對 `(順序, 商品, is_exact, tier)` 差異 0。負對照兩道：換詞比對 3,062 列差異、只動一列 tier 抓到 1 列。
  - 途中抓到一個錯：相關度那兩格員工欄位沒 `coalesce` 時，沒改過標題的商品 `->>` 是 NULL，`NOT (… OR NULL)` 讓 487 列的 tier 從 2 變 1。已改成 `coalesce(…, '')`，差異歸 0。
- **員工標題搜得到、舊字也還在**（舊版對照都搜不到新字）：1 字「鍛」、2 字「鍛造」、4 字「鍛造輪框」、`forged-x99`、折疊 `forgedx99`、只改副標「賽道版」都找得到；供應商原字「碳纖維」仍找得到；新字＋舊字同時打（AND）找得到；員工標題命中算強命中（tier 1）。
- **下架**：下架商品即使有員工標題，用新字搜不到。
- **整串優先**：員工標題 `QX 7788 ZZ` 的商品在 `{QX,7788,ZZ}` 時留下、只逐詞都中的 `QX 9 ZZ 7788` 被收窄掉；只打 `{QX,ZZ}` 時兩件都在（對照）。
- **service_role** 改員工標題、新增商品都不受新索引影響，改完立刻搜得到。
- **效能**：①c 在函式內走 `products_staff_text_override_idx`（auto_explain 看到 Index Scan，不是整表掃）。9 組詞新舊耗時相同（例：碳 66→55 ms、碳纖維 54→54 ms、carbon 9,482→9,143 ms）。英文詞在自造資料上兩版都慢，是本機資料的特性，與本片無關；正式庫速度沒有量。

## 5. 已知限制

- 員工的**賣點**（`highlights`）不進搜尋；供應商的賣點今天也不進搜尋（搜尋只看標題、副標、說明、料號）。
- 說明欄走「說明鎖」直接改 `description`，本來就搜得到，不在本片。
- 相關度：員工標題與供應商標題都算「強命中」，沒有分先後。
- **既有問題，本片不動**：相關度判斷裡供應商副標那一格 `p.subtitle ILIKE` 沒有 `coalesce`，副標是 NULL 的商品會出現同樣的 NULL 情況，被抬成 tier 1（員工欄位那兩格已避開）。要修會改變現有排序，另開一片並先量影響件數。
- 正式庫目前 0 件有員工標題 ⇒ 貼上後事後檢查 ⑤c 會印「沒有判別力」；員工改了第一件之後要再用那件的新字搜一次。
