# 計畫：客人選了車款，商品列表逾時（等 9-10 秒後看到「載入失敗」）

- 日期：2026-09-23
- 派工：主視窗 pcm-website-v2-90（Sean 2026-09-23 指示另開一件，不併進車款清單那份）
- 相關：`docs/plans/2026-09-23-vehicle-taxonomy-timeout-plan.md` 附錄（那次量測發現這件事）
- 狀態：**只有計畫與查證，沒有改任何程式。** 碰資料庫或公開 API 要 Sean 批准。
- 審查：見文末。

## 1. 發生了什麼（客人的角度）

2026-09-22 台灣 22:30，商品列表有 **2 筆請求**選了車款，伺服器端各花了 **9.2 秒與 10.1 秒**，最後回的頁面顯示**「載入失敗、請稍後再試」**。
⚠️ 用字精確一點：那是**兩筆請求**，不保證是兩個人（來源不明，見第 6 節）；9.2／10.1 秒是伺服器處理時間，**不含把畫面送到瀏覽器的時間**（`page.tsx:731`）。

逐字紀錄（Vercel 執行紀錄，`environment=production`，兩筆都在 UTC 14:30:47）：

```
[callCatalogRpc] 資料庫逾時(57014)⇒ 重試一次
[fetchCatalogPage] search_catalog_by_vehicle failed: { code: '57014', message: 'canceling statement due to statement timeout' }
[catalogRoute] tax=10ms cats=10ms brands=18ms garage=11ms page=6162ms total=9164ms catsN=0 brandsN=0 p=1 per=100 sort=recommend hasVeh=true kw=false rows=0
```

第二筆的 `page=6147ms total=10069ms`，並且印了兩次「重試一次」。

## 2. 那兩次的參數（紀錄裡撈得到的全部）

| 項目 | 值 | 說明 |
|---|---|---|
| 路徑 | `/products` | 商品列表 |
| 有沒有選車款 | **有**（`hasVeh=true`） | 🔴 選車時目錄頁會**接著跑兩發**同一支查詢：先「專用件」（`page.tsx:508` 傳 `fit`），再「通用件」（`page.tsx:529-543`（改動後 `:536-550`）傳 `universal`） |
| 哪一台車 | **紀錄裡沒有** | 那行 log 只印 `hasVeh`，沒有印品牌與車款；也沒有印年份 |
| 第幾頁 / 每頁 | 第 1 頁 / 每頁 100 件 | `p=1 per=100` |
| 排序 | 推薦 | `sort=recommend` |
| 分類 / 品牌篩選 | 都沒有 | `catsN=0 brandsN=0` |
| 關鍵字 | 沒有 | `kw=false` |
| 會員身分 | **紀錄裡沒有**，但可判定是**一般會員或未登入** | 經銷會員走另一支查詢（`search_catalog_by_vehicle_dealer`），失敗訊息會是另一個名字；而正式庫目前經銷會員 0 人 |
| 結果 | 0 筆 | `rows=0`，畫面顯示錯誤提示 |

🛑 **哪一台車查不到，是這次調查的主要缺口。** 要知道的話得在那行 log 補上品牌與車款（見第 5 節選項）。

## 3. 慢的原因

### 我重跑了客人那條查詢（正式庫唯讀，2026-09-23）

🛑 **先講這組數字的限制**：我用的唯讀帳號會**跳過資料列權限檢查**（BYPASSRLS），而客人那條路**不會跳過**——`search_catalog_by_vehicle` 是以呼叫者身分執行，它讀的 `products_list_public` 是 `security_invoker=true`（正式庫實查），所以 anon 要逐列檢查商品有沒有下架。⇒ **下面的數字是客人實際耗時的下界，不是客人的耗時。**

把選車款那段查詢原樣抽出來，用「只看專用件」跑，每台車 3 次：

| 車款 | 符合件數 | 三次耗時 |
|---|---|---|
| Ducati Panigale V4 | 1,194 | 62 / **2,255** / 128 ms |
| BMW S 1000 RR | 969 | 214 / **873** / 173 ms |
| Yamaha MT-09 SP | 500 | 126 / 459 / 106 ms |
| Ducati Panigale V4（2022 年） | 692 | 121 / 116 / 116 ms |

⇒ 這組（下界）大多 0.1-0.2 秒，**而同一句查詢會偶爾跳到 2.3 秒**（12 次取樣出現 1 次）⇒ 只證明「同一句會抖」。**客人那一側常態多少、離 3 秒多遠，還沒有量到。**

### 當下資料庫在忙什麼

同一小時（UTC 14:00-15:00）的執行紀錄：**6,127 個不同路徑**，其中絕大多數是各別商品頁，而且**全部 `cache=MISS`**。失敗前後 15 秒內，每秒有 2-4 個商品頁請求進來。

- ⇒ 看起來是**搜尋引擎在重新抓取整站商品頁**（9/21 才剛提交過網站地圖，Search Console 收了 25,476 筆）。
- 那一小時沒有商品同步（同步排程落在 UTC 08:44-10:07），我自己的壓測是隔天 02:2x，都不重疊。
- 🛑 **這是相關，不是證實。** 我沒有當時的資料庫端統計（唯讀帳號讀不到），所以「爬蟲把資料庫壓慢，於是選車查詢超過 3 秒」是**目前最符合讀數的解釋，不是量到的因果**。

### 為什麼會等到 9-10 秒

資料庫給客人的上限是 3 秒，逾時後程式**自動重試一次**（`lib/retry-on-statement-timeout.ts:14`，只認 `57014`），重試**不等待、也不縮小查詢**。

🔴 而**選車時是兩發接著跑**：

| 順序 | 哪一發 | 最壞情況 |
|---|---|---|
| ① | 專用件（`fit`，`page.tsx:508`） | 3 秒逾時 + 重試 3 秒 = 6 秒 |
| ② | 通用件（`universal`，改動前 `page.tsx:529-543`、改動後 `:536-550`） | 再 3 秒（+ 重試 3 秒） |

第二筆 log 印了**兩次**「重試一次」、`page=6147ms`、`total=10069ms` ⇒ 多出來的那 3-4 秒是**通用件那一發自己也撞到逾時**，不是「頁面其他工作」（那四項是同時跑的，最長一項只有 18 毫秒：`tax=9 cats=18 brands=15 garage=10`）。

⇒ 📌 **最壞情況是 4 次 × 3 秒 = 12 秒。** 今天量到的 9-10 秒就是這個結構造成的。
⚠️ 12 秒只對「第 1 頁、通用區第 1 頁、沒有選新品」這個形狀成立。翻到後面幾頁或選新品時，程式還會多打探查用的查詢（`products.ts:662-668`、`:670-682`），每一發也可能逾時加重試 ⇒ 可能更久。

## 4. 「頁面回 200」那條路：畫面其實有講，而且和「真的沒有商品」分得開

| 位置 | 做了什麼 |
|---|---|
| `apps/storefront/src/lib/products.ts:887-889` | 查詢失敗 ⇒ 回 `{ products: [], total: 0, error: true }` |
| `apps/storefront/src/app/products/(catalog)/page.tsx:756` | 把 `error` 傳給畫面元件 |
| `apps/storefront/src/components/ProductsPage.tsx:726-728` | `error` 為真 ⇒ 顯示 `role="alert"` 的**「載入失敗、請稍後再試」** |
| `apps/storefront/src/components/ProductsPage.tsx:453` | `error` 為真 ⇒ 件數改成不顯示（不會寫成「共 0 件」） |

🔵 **所以「顯示沒有商品」那個擔心不成立** —— 那是我 2026-09-23 第一次回報時的錯誤描述，已更正。
🔴 **真正的傷害是「等 9-10 秒才看到失敗」**，而且客人手上沒有可按的重試按鈕，只能自己重新整理。

## 5. 修法選項（請 Sean 選，可以複選）

### 甲：主清單失敗就別再查通用件（建議先做）

- **做完客人會怎樣**：最壞從 12 秒降到 6 秒；畫面照樣顯示「載入失敗」，但多一個「重新載入」按鈕，客人不用自己找重新整理。
- **要改什麼**：目錄頁 `page.tsx:529`（改動後 `:536`）那一行的條件從「有選車款」改成「有選車款**而且主清單沒失敗**」（`error` 就在同一個作用域，`:481`）；提示旁加一個「重新載入」按鈕（`ProductsPage.tsx` 是 client 元件，用 `router.refresh()` 即可）。不碰資料庫、不碰共用函式。
- 🔵 **影響範圍查過（2026-09-23 訂正）**：側欄件數（`:690-725`）不讀通用件結果，這點成立；🔴 **而「通用區分頁不讀它」是我寫錯的** —— 通用區分頁確實用它算（`ProductsPage.tsx:533`、`:850`）。不過主清單失敗時通用區**本來就不會顯示**（`ProductsPage.tsx` 的 `!error && universal !== null`，改動後 `:832`）⇒ 跳過那一發不會讓客人少看到任何東西。
- **多久**：約 2 片（1 小時），含測試。
- **風險**：低。🔵 甲案省掉的是**目前查了卻不會顯示的結果**，不是「本來會被看到的通用件」（我上一版把這寫成代價，也是錯的）。

🛑 **不要改共用的重試函式。** 它有 5 個呼叫端（`products.ts:627/1290/1447/1554`、`search.ts:105`）。09-22 那天 `/api/search` 重試了 10 次，而那一天**查不到對應的搜尋失敗紀錄**（⚠️ 我沒有單獨數過搜尋的失敗次數，所以只能說「查不到」，不能說「全部成功」）⇒ 拿掉重試很可能把那些原本救得回來的搜尋變成失敗。加 200-300 毫秒延遲也救不到等待時間（3 秒 + 0.3 秒 + 3 秒）。

### 甲之二（可選，收益比我第一版寫的小很多）

- **做完客人會怎樣**：正常情況下少等一發查詢（下界約 0.1-0.2 秒）。
- 🔴 **更正**：我第一版寫「逾時時最壞從 6 秒降到 3 秒」是**錯的**。專用件那一發自己就是 3 秒逾時 + 重試 3 秒 = 6 秒，同時查只是兩發一起等 ⇒ **最壞仍是 6 秒，與甲相同；在失敗那條路上零收益**。
- **要改什麼**：把專用件與通用件那兩發改成同時發（`page.tsx:502-543`）。
- **風險**：低到中。每個選車請求對資料庫多一條並行查詢（背景是每秒 2-4 個商品頁）⇒ 比我第一版寫的小。
- ⇒ 📌 **失敗那條路沒有收益 ⇒ 建議先不做**；要做也只是為了正常情況快一點，那要另外量值不值得。

### 乙：讓爬蟲少打幾次資料庫（要先破解一個限制，見下）

- **做完客人會怎樣**：資料庫平常負載下降，選車查詢超過 3 秒的機會變少；客人感覺不到改動。
- 🔴 **先講清楚現況，因為我第一版寫錯了**：商品頁的資料**已經有 60 秒快取**（`lib/products.ts:1711-1712`，`pdp-product-by-handle-v2`）。紀錄裡那些 `cache=MISS` 是**整頁 HTML 沒有被 CDN 快取**，因為這條路必須是動態的。
- 🛑 **而它必須是動態的，不是疏漏**：`app/products/[slug]/page.tsx:112-123` 逐字寫著，一旦給這條路加 `force-static` 或 `revalidate`，**經銷價會被快取後給一般會員看到**，而且有測試釘住建置輸出必須是動態（`lib/pdp-product-cache.test.ts`、`catalog-tier-all-paths.test.ts`）。⇒ **整頁快取這條路不能走**。
- 🛑 **而「把 60 秒拉長」也沒有用**：`products.ts:1697` 逐字寫著「對單趟掃全站的爬蟲第一趟零命中（每 slug 各一次）」。爬蟲每個網址只抓一次 ⇒ 快取再久也不會命中，資料庫負載不會降。而且 `products.ts:1695` 有既有裁示「PDP 若 300 秒會與目錄頁 60 秒對不上 4 分鐘（主視窗裁）」⇒ 要改等於**推翻那條裁示，要 Sean 明說**。
- **剩下真正可能有用的一條**：只對「沒有登入」的請求做整頁快取，登入的走動態。⚠️ 要新增共用判斷，而且會碰到經銷價隔離那條線（有測試釘住）⇒ **高風險，我不建議現在做**。
- ⇒ 📌 **乙 這一格目前的結論是「先不做」**，除非第 6 節的 user-agent 查證顯示真的有會重複抓同一頁的爬蟲。

### 丙：把那句 log 補上「哪一台車」

- **做完客人會怎樣**：沒有差別，但下一次發生時我們知道是哪一台車、能直接重現。
- **要改什麼**：三件一起：① `page.tsx:735` 那行加印品牌與車款——**那兩個值是網址比對車款字典之後的正規名稱**（`vehicle-url.ts:125-150`），不是客人自由輸入的字，年份也已轉成數字 ⇒ 沒有個資疑慮（那一段本來就有「不印使用者資料」的紀律，`page.tsx:161-162`）② 兩發查詢的 label 帶上是 `fit` 還是 `universal`（現在兩發同名，log 印兩次「重試一次」分不出哪一發）③ `[catalogRoute]` 加印兩發各自的毫秒與有沒有失敗。
- ⚠️ ② 要動共用檔 `lib/products.ts:627`（label 現在寫死 `'callCatalogRpc'`，首頁與品牌頁也走這支）。**只改傳進去的字串、不改行為**，但要一起跑那些呼叫端的測試。
- **多久**：1 片以內（30 分鐘）。
- **風險**：低。

### 丁：讓那句查詢本身變快

- **做完客人會怎樣**：尖峰時比較不會超過 3 秒。
- **要改什麼**：還不知道。今天量到「平常 0.1-0.2 秒、偶爾 2.3 秒」，而**尖峰的成因沒有定位**（沒有資料庫端統計）。要先拿到那句查詢在尖峰時的執行計畫與等待事件，才知道要改索引、改寫法，還是加資源。
- **多久**：先定位 2-3 片；改法要等定位結果。
- **風險**：不明 ⇒ **不建議現在動**。

**我的建議：直接做甲 + 丙**（都只動顧客站、不碰資料庫與經銷價那條線）——它們的效益不需要先知道來源是不是爬蟲。來源那件請有 Vercel 後台權限的人另外查，不要當成前置條件。甲之二、乙、丁 先不要動。

## 6. 驗收方式

- 🛑 **「是不是爬蟲」我們這端查不到（2026-09-23 試過兩種工具）**：
  - Vercel MCP 全文查 `Googlebot`（同一小時、`environment=production`）⇒ 0 筆；**而同窗查 `catalogRoute` 得 72 筆**，代表查法是活的，不是工具壞了。
  - 命令列 `vercel logs --json` 的每一筆只有 `branch / cache / deploymentId / domain / requestMethod / requestPath / responseStatusCode / level / logs / message` 等欄位，**沒有 user-agent**（實際開檔看過欄位名單）。
  - ⇒ 要判斷來源，得由**有 Vercel 後台權限的人**看 Observability 或防火牆那邊的請求紀錄。**在那之前，「那小時是爬蟲」只是最符合讀數的猜測。**
  - 另一個沒排除的來源：商品卡是 `<Link>` 而沒有設 `prefetch={false}`（`ProductCard.tsx:315`），可視範圍的卡片會被預先抓取。⚠️ 但商品頁沒有載入邊界（`no-loading-boundary.test.ts` 釘住），預抓未必真的會執行到那一頁 ⇒ **機率低、未驗證**。
- 用車款清單那份計畫第 3 節同一套量法（`environment=production`、完整日時間窗、`group_by=requestPath`），每天數：
  - `fetchCatalogPage`（客人那一發自己失敗）
  - `重試一次`（資料庫逾時過，含重試成功）
  - 同時記 `/products` 與各商品頁的總請求數（分得出「錯誤變多」與「流量變多」）
- 甲做完：同一種失敗的 `total=` 應該從 9-10 秒降到 **6 秒上下**。判準寫清楚：找同一個請求裡既有 `[fetchCatalogPage] search_catalog_by_vehicle failed` 又有 `[catalogRoute] … hasVeh=true … rows=0` 的那些，看 `page≈6000ms` 且 `total − page < 300ms`（今天這個差是 3,000-3,900 毫秒，因為通用件那一發還在跑）。
- ✅ **驗收就是測試本身（2026-09-23 實作那一片訂的，Sean 選甲）**：
  - `page.test.tsx`「選了車而主清單失敗 ⇒ 不再去查通用件」+ 正對照「主清單成功但 0 件 ⇒ 通用件照常查」。**實測：把那一行的 `&& !error` 拿掉 ⇒ 前者紅（1 failed / 64 passed）。**
  - `ProductsPage.test.tsx` 三格：error 時有「重新載入」按鈕、按了真的呼叫 `router.refresh()`、error=false 時沒有那顆按鈕。**實測：把按鈕拿掉 ⇒ 前兩格紅。**
  - ⚠️ **那顆按鈕保留不了頁碼**（R1 審查訂正）：失敗時件數是 0 ⇒ 程式把頁碼算成第 1 頁並把 `page` 從網址刪掉（`ProductsPage.tsx:469`、`products-url-state.tsx:179`）⇒ 客人在第 3 頁遇到逾時，**按按鈕之前網址就已經回到第 1 頁**。這是既有行為、本片沒有動它；要不要改是另一題。
  - 🔵 按鈕有「按過就不能再按」（`useTransition`），避免連按三下打三發、每發最壞 6 秒。
  - `page.test.tsx`「`[catalogRoute]` 那行要印 `veh=` / `uni=` / `err=`」兩組（主清單失敗 / 成功）。**實測：拿掉 `veh=` ⇒ 兩組都紅；拿掉 `uni` 計時 ⇒ 成功那組紅。**
- 🛑 **線上耗時只當觀察，不當通過判準。** 原本寫的兩個量法被 Codex R3 判為不可靠，已刪除，理由留在這裡免得有人再用：
  - ⛔ ~~「日計數 `fetchCatalogPage` 配 `rows=0` 就算客人失敗」~~ —— 分不出「主清單成功但 0 件、接著通用件失敗」。🔵 **現在改用新加的 `err=` 那一格分**（`err=true` 才是主清單失敗）。
  - ⛔ ~~「`page≈6000ms` 且 `total − page < 300ms`」~~ —— `total − page` 還含身分解析（`page.tsx:442`）與等年份資料（`:733`），兩邊都會誤判。🔵 **現在改看新加的 `uni=`**：主清單失敗那些請求，`uni` 應該一律是 `-1ms`（代表沒跑）。
- 每天那次逾時量測照常（另一份計畫的附錄表），觀察 `err=true` 的次數與 `page=` 的耗時走勢。
