## 1. 這個方案主張什麼

**問題不是「這把鑰匙該不該存在」, 是「它不在帳上」。**

```
版控裡建過的角色  ⇒ payment_confirmer(20260611120000:62)· pcm_readonly(20260902210000:306)
版控外建出來的    ⇒ pcm_audit_ro   ⇒ 🔴 零 DDL
```

⇒ 📌 **一個【重放不出來】的正式庫**:拿版控從零重放一次, 建不出 `pcm_audit_ro`,
   而正式庫上它在。**那個差集沒有任何一支測試看得到。**
⇒ 🎯 本方案不判它該不該留, 只讓**帳上的世界與真的世界對得起來**。

## 2. 現成形狀就在隔壁 —— 照抄, 不重新設計

`supabase/migrations/20260902210000_m4b_pfeddl2_staging_and_sync_log.sql:297-315`
已經解過**一模一樣**的題(`pcm_readonly` 也是先在正式庫存在、後補版控):

```sql
DO $$
BEGIN
  -- 🔴 codex R2:角色已存在時一個屬性都不看 ⇒ 一個同名而 SUPERUSER/BYPASSRLS 的角色
  --    會直接拿到下面的 GRANT, 而檔案會印綠。⇒ 已存在就驗它是不是我們想的那種。
  IF EXISTS (SELECT 1 FROM pg_catalog.pg_roles
              WHERE rolname = '<角色>' AND (rolsuper OR rolbypassrls)) THEN
    RAISE EXCEPTION '…那不是唯讀角色, 不對它 GRANT';
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_catalog.pg_roles WHERE rolname = '<角色>') THEN
    CREATE ROLE <角色> NOLOGIN;
    GRANT USAGE ON SCHEMA public TO <角色>;   -- 🔴 這一行是 harness 抓出來的真 bug
  END IF;
END $$;
```

🔵 **那支檔自己留了兩句要一起搬過來的話:**
> **「在我把『角色不存在』這個世界【造出來】之前, 這條分支一次都沒被執行過 —— 25/25 全綠,
> 而其中沒有一格走過它。」**
> **⇒ 🎯 一條從來沒被執行過的修法, 與一條寫錯的修法, 在總分上長得一模一樣。**

⇒ 🛑 **所以本方案的驗收必須含「把角色不存在的世界造出來跑一次」**, 不是只看正式庫上是 no-op。

### 🔴🔴 而照抄之前要知道:**那個守門宣告的不變式, 正式庫【違反】它**

```
守門逐字(:301-305):
  IF EXISTS (… rolname = 'pcm_readonly' AND (rolsuper OR rolbypassrls)) THEN
    RAISE EXCEPTION '角色 pcm_readonly 已存在, 而它是 SUPERUSER 或帶 BYPASSRLS
                     ⇒ 那不是唯讀角色, 不對它 GRANT';

🔬 而正式庫的 pcm_readonly ⇒ rolbypassrls = t
   (來源:auth 量到、tidy 2026-09-08 ~09:0x UTC 覆量並列名冊 —— pcm_readonly ·
    postgres · service_role · supabase_admin · supabase_etl_admin · supabase_read_only_user;
    🟢 正對照 anon ⇒ f  ⚪ 負對照 現造角色名 ⇒ 0 列。

    🛑 我沒有 DB 連線, 這一格是【別人交來的】, 我沒有複量。)
```

⇒ 🎯 **那支檔標 `pcm:never-apply`(`:6`)⇒ 正式庫根本不會跑到它, 所以沒有人會撞到那個 EXCEPTION。**
⇒ 🔴 **而後果不是「守門沒用」, 是【重放庫與正式庫的那個角色不是同一個東西】:**

| | 重放庫的 `pcm_readonly` | 正式庫的 `pcm_readonly` |
|---|---|---|
| 怎麼來的 | 這支 migration 建的 `CREATE ROLE … NOLOGIN`(`:306`) | 版控之外建的 |
| `BYPASSRLS` | **沒有** | 🔴 **有** |
| 它看得到什麼 | RLS 讓它看到的 | **全部**(繞過 RLS) |

⇒ 📌 **任何在重放庫上用這個角色驗出來的 RLS 結論, 不轉移到正式庫** ——
   而**錯的方向是【重放庫看起來比較安全】**:那裡被 RLS 擋住的東西, 正式庫看得到。
⇒ 🛑 **兩個世界印同一片綠。**

### ⚠️ 這一格我證不到的
- **有沒有人真的在重放庫上用這個角色下過 RLS 結論**, 我沒有查(那要掃別條線的交件)。
  ⇒ 本 plan 只指出**那個落差存在且是靜默的**, 不宣稱它已經害過誰。
- 本方案照抄的是**形狀**(條件式建角色 + 已存在就驗屬性), 那個形狀**仍然是對的**;
  🔴 **要一起搬過去的是這一格的警語** —— 否則下一個人會把「守門在」讀成「兩邊一樣」。

## 4. 🔴 這個方案的兩個真風險(不要藏)

### ① **抄一個【錯的現況】會把錯的權限寫成正本**

A 案 §5 那份快照若少報(`information_schema` 是權限過濾的), 我抄進 migration 的就是一份**少的**權限表。
⇒ 而它會被後人讀成「這就是設計」。

🔵 **而那支現成檔已經踩過這個坑兩次, 逐字寫了方向:**
> 兩次猜漏的都是**該有而沒給** ⇒ 「會有人跑不動而叫」;
> **若選另一邊, 漏的會是【不該有而給了】—— 而那不會叫。**

⇒ 📌 **所以抄不確定的格子時, 往【少給】那邊倒** —— 錯了會有人叫。

### ② **把一把「今天讀不到東西」的鑰匙寫進版控 = 給它蓋章**

`pcm_audit_ro` 現在 `permission denied for schema cron`, 而 `pcm_readonly` 讀得到。
⇒ 🔴 **補版控會讓一把已經被取代的鑰匙看起來像是現行設計。**
⇒ 🛑 **這是 A 案存在的理由, 而本案答不了它。**
