## 1. 先講結論

1. 待辦板那一列的原始症狀「切分類要 3 秒」**已經不成立**：今天實測正式站切分類 0.14-0.43 秒，100 張商品卡是伺服器產好在 HTML 裡的。
2. **但那一族還不能關**，關閉條件逐字是「不再逾時 ⇒ 三列一起關」，而今天還量到一次逾時（資料庫 3 秒上限砍掉車款清單查詢）。
3. **成因還沒查出來。** 資料庫端執行只要 0.24 秒，離 3 秒很遠；那一次逾時發生在什麼情況下，我們手上的唯讀帳號量不到。
4. 所以**建議先不動資料庫**，改成先數「客人那一層實際失敗幾次」：Vercel 的執行紀錄裡有現成的兩行字可以數（見第 5 節）。
5. 客人實際受影響的機會比看起來低，但**不是零**：車款資料在網站端有 1 小時快取、逾時會自動重試一次，失敗時還會回上一份好資料（最多 2 小時）。⚠️ **而剛啟動的伺服器沒有上一份好資料，第一發失敗就會直接讓客人看到提示。**

## 2. 今天量到什麼（2026-09-23 正式站，唯讀 / anon 實打）

### 頁面那一層（原始症狀）

| 網址 | 三次 |
|---|---|
| `/products` | 0.43 / 0.20 / 0.38 秒 |
| `/products?category=排氣系統` | 0.24 / 0.16 / 0.14 秒 |
| `/products?category=碳纖維部品` | 0.16 / 0.14 / 0.15 秒 |

HTML 內含 100 張商品卡。⚠️ 這個數字**量不到車款查詢冷不冷**：車款資料有 1 小時快取（`apps/storefront/src/lib/products.ts:182`、`app/api/catalog/vehicle-models/route.ts:33`），頁面多半拿的是快取。

### 車款清單那支查詢（剩下的問題）

用 anon key 直接打 REST，每 3 分鐘一次：

| 時間 | `get_vehicle_taxonomy_base` | `get_vehicle_model_years('Ducati')` |
|---|---|---|
| 02:32 | 789 ms | 538 ms |
| 02:35 | 885 ms | 570 ms |
| 02:38 | 2,268 ms | 541 ms |
| 02:41 | 1,314 ms | 546 ms |
| 02:44 | 912 ms | 567 ms |
| 02:47 | 1,219 ms | 558 ms |

另外 02:2x 連打的第一組：中位 2,643 ms，**其中一次回 HTTP 500 `57014 canceling statement due to statement timeout`**（被資料庫 3 秒上限砍掉）；緊接著再打 6 次全部正常（中位 648 ms）。

**⇒ 單發逾時：今天 15 發裡量到 1 次。這是一個點，不是頻率**（樣本太小，真實比例可能落在很寬的範圍）。客人實際看到失敗的機率更低，還沒有量到。

### 這些時間花在哪

| 量的是什麼 | 數字 |
|---|---|
| 資料庫端執行（`EXPLAIN ANALYZE`） | base 241 ms、years 277 ms |
| anon 打 REST 的整趟來回 | 0.45-1.16 秒（回 159,641 bytes） |
| 純 REST 來回基準（不查資料） | 0.046 秒 |

⇒ 中間約 0.3 秒是 PostgREST、連線池與 JSON 傳輸，不是資料庫在算。

**而 `57014` 只會在資料庫端真的超過 3 秒時出現。** 我用 anon 直打量到的那一次就是這種（資料庫端真的變慢）。
🔴 **但線上那 3 次車款失敗是另一種**：等 15 秒沒回應被自己中止（見第 3 節丙案的基準）。⇒ **兩種失敗要分開看，不要混成一個數字。**

### 兩條已經被實測否定的說法（都要寫清楚，免得下一個人再走一次）

1. ⛔ ~~「客人身分要逐列檢查商品有沒有下架，所以慢」~~ — **錯。** `vehicle_taxonomy_public` 是 `security_invoker=false`（正式庫實查 `pg_class.reloptions`），讀底表時用擁有者身分，資料列權限規則根本不套用。`supabase/migrations/20260811020000` 檔頭第 19-40 行早就記著這件事，是當初為了避開 3 秒逾時才刻意這樣設的。⇒ **把那兩支查詢改成「以擁有者身分執行」對速度是零效果。**
2. ⛔ ~~「改成一次 JOIN 掉下架商品，反而 8.5 秒」~~ — 那個寫法先接 48 萬列再去重，本來就慢。改成每張表先去重、再用 EXISTS 過濾，實測 **543 ms**（見下面丁案）。

#### 怎麼數（可重複跑，照這個做就會得到同一種數字）

用 Vercel 的執行紀錄查詢工具（本 session 用的是 Vercel MCP 的 `get_runtime_logs`），每次帶四個條件：

要數的字串跑三次，每次一個（**只能填單一個詞，填兩個詞以上會查不到東西**）：

| 查什麼 | 意思 |
|---|---|
| `fetchVehicleTaxonomyBase` | 車款清單那支查詢出問題的次數（本案主角） |
| `重試一次` | 資料庫回逾時（57014）之後自動重試的次數（我們自己那行 log，`apps/storefront/src/lib/retry-on-statement-timeout.ts:16`） |
| `get_vehicle_model_years` | 年份那支查詢出問題的次數 |

🔴 **三個去重與誤讀的陷阱（前一位助手在這裡虛報過 20 倍）**：

1. **用 `group_by=requestPath` 拿「次數」，不要自己翻頁去數行。** 分組是伺服器端算的，不會像翻頁那樣把同一筆重複吐出來。
2. **不要查 `57014` 當主要指標。** 快取重算失敗時，錯誤訊息會把整段程式原文一起印出來，而那段原文裡本身就有 `57014` 這個字 ⇒ 會把「沒有真的逾時」的請求也算進去。今天實測：查 `57014` 得 8 筆，其中 3 筆只是程式原文。
3. **不要鎖版本編號（`deploymentId`）。** 今天實測鎖到前兩個 production 版本都回「查無」，因為正在服務客人的是另一個版本（`dpl_Gnzgna…`）。不鎖版本、只給時間窗才數得到。
4. 分組結果如果是空表，先做一次對照：同一時間窗不帶查詢字串、只用 `group_by=requestPath`，要看得到 `/products` 之類的正常流量。**看得到流量才能說「今天沒有發生」；看不到就是查法壞了。**

#### 今天的基準（2026-09-23 台灣 00:00 → 10:50）

| 指標 | 次數 | 發生在哪 |
|---|---|---|
| 車款清單查詢失敗 | **3** | `/products/kspeed-1q097`（04:14）、`/products/gilles-fo-k66-0-03-set`（06:11）、`/products/rpm-atu42105`（08:10） |

#### 🔴 這個基準推翻了本檔原本的病因假設

那 3 次車款失敗**不是資料庫回逾時**，是**我們自己的連線等了 15 秒還沒拿到回應就中止**（錯誤字面是 `TimeoutError: The operation was aborted due to timeout`，等候上限 `CATALOG_FETCH_TIMEOUT_MS = 15_000`，`apps/storefront/src/lib/catalog-anon-client.ts:13`）。

- 資料庫給客人的上限是 3 秒，超過就回 `57014` 錯誤碼 ⇒ **會變成 15 秒沒回應，代表請求根本沒走到「查詢在跑」那一步**（例如連線池排隊、連線建立、或伺服器剛啟動）。
- ⇒ 所以「把查詢改快」（甲案）**對這 3 次沒有用**。要先知道那 15 秒卡在哪。
- 🔵 而那 3 次都發生在**背景重算快取**，三個頁面都仍然回 200（客人拿到的是上一份好資料）⇒ **今天沒有量到任何客人因此看到失敗**。

- 一週後回報：次數是穩定的少數、還是會突然變多；以及有沒有出現「客人那一發自己失敗」（回 500/503，或同一個請求連兩次失敗）。

### 甲：把車款清單先算好存起來

- 做法：做一份算好的車款清單（約 3,783 組品牌＋車款），每天商品同步跑完後更新一次；兩支查詢改讀它。
- 好處：讀取降到幾十毫秒，資料庫端離 3 秒很遠。
- ⚠️ **只有在「查詢本身慢」時才有效。** 今天線上實際發生的 3 次是「等 15 秒沒回應」，不是查詢慢 ⇒ 甲案對那 3 次沒有用。另外若逾時是等鎖等出來的（3 秒上限含等鎖時間），一張「同步收尾才更新」的表正是會被鎖住的對象，幾十毫秒的查詢一樣會被砍。
- 代價與要注意的：新物件要開資料列權限並決定給誰讀；更新要掛在同步收尾；**車款資料變成隔天生效**。你 2026-09-11 拍過「車款資料隔天生效可接受」，但那題問的是供應商同步，**沒有問過「後台手動下架一筆商品、車款清單要不要等一天」**，這點要再確認。
- 工作量：約 4-6 片（2-3 小時）。

### 丁：把「只剩下架商品」的車款濾掉

- 🔴 **還要正面回答一條既有決定**：`supabase/migrations/20260811020000` 檔頭第 2 節明寫這個檢視**刻意不碰 `product_id`**，因為碰了就會逾時（當時實測 3,047 ms）。丁案等於把那個欄位接回來，不論寫在檢視裡還是函式裡，都要先說明為什麼這次不會重蹈覆轍。
- 工作量：約 3-4 片（1.5-2 小時）。
- 只有在你想拿掉那 3 台幽靈車款時才值得做。

## 5. 驗收方式（選甲或丁之後）

- **不能只量暖機狀態**：今天暖機時 6 發就已經 0 逾時、最慢 1.3 秒，那個標準區分不出有沒有修好。
- **主要依據：客人那一層。** 改之前先數一週，改之後再數一週，比較 Vercel 執行紀錄裡 `資料庫逾時(57014)⇒ 重試一次` 與「車款清單暫時無法載入」各出現幾次。這是唯一數得到「客人真的失敗幾次」的地方。
- **不要用「打 24 次沒逾時」當通過標準**：以今天量到的比例推算，就算完全沒修，24 發全過的機率也有將近兩成。
