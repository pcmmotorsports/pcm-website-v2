## 2. 那真正的窗口在哪(**這是推的, 不是量的 —— 見 §4**)
`FOR UPDATE` 與 FK 的 `KEY SHARE` **不相容** ⇒ 兩邊**會**互相排隊。而 `SKIP LOCKED` 決定了誰讓路:
· **收款先到**:它的 FK 持 `KEY SHARE` ⇒ cron 的 `FOR UPDATE … SKIP LOCKED` **跳過這張單** ⇒ 這一輪不取消 ⇒ **安全**。
· 🔴 **cron 先到**:cron 持 `FOR UPDATE` ⇒ 收款 INSERT 的 FK 要 `KEY SHARE` ⇒ **卡住等** ⇒ cron 取消並提交 ⇒ **收款才落帳**
  ⇒ **這就是板列描述的「已取消而錢在裡面」。**
⇒ 📌 **所以問題不是「沒有鎖」, 是【取消贏了之後, 收款那一側沒有再看一眼】。**

## 3. ⇒ 修法的方向因此改變(三個候選, 我推丙)
· **甲 · 讓 cron 也拿同一把 advisory**:要改 cron + 十條收款路徑的鎖序 ⇒ 面最大, 而且沒有解決「取消贏了之後怎麼辦」。
· **乙 · cron 不取消有在途收款的單**:要定義「在途」, 而在途的證據散在多張表 ⇒ 判準會漂。
· ✅ **丙 · 收款那一側在【拿到鎖之後】重讀訂單狀態** —— 若已取消 ⇒ 走既有的「取消後收到錢」那條路
  (板列已寫過 `20260901080000` 那條退款路徑**不成立**, 需另查現況)⇒ **面最小、而且直接對準真正的窗口**。
  🛑 **而丙要先答一格**:取消後才落帳的那筆錢, **現在有沒有一條路把它變成待退款**?板列 2026-09-05 已把舊的那句劃掉。**未查。**

## 4. 🛑 本 plan 證不到什麼(逐條, 不美化)

# J. 鑽機跑完了(拋棄式 PG 17.10, 埠 55458)—— **網接得住, 而我的第一版鑽機自己是錯的**

## J-1 三個世界 + 一發突變(逐字讀數)
```
世界A cron先          ⇒ 收款列=1 待退款列=1 已取消=true    ← 網接住了
世界B 收款先(我第一版) ⇒ 收款列=1 待退款列=0 已取消=true    ← 🔴 這一發是【鑽機錯】, 不是發現
世界B2 收款先(訂正後)  ⇒ 收款列=1 待退款列=0 已取消=false   ← cron 跳過, 安全
突變 拿掉網 cron先     ⇒ 待退款列=0
還原               ⇒ 待退款列=1
```

## J-2 🔴 **我的第一版鑽機把 `UPDATE` 寫成無條件的, 而真的 cron 是 CTE 綁住的**
真檔逐字(`20260904230000`, `expire_unpaid_orders`):
`WITH target AS (SELECT o.id … FOR UPDATE OF o SKIP LOCKED) UPDATE public.orders o … FROM target t WHERE o.id = t.id;`
⇒ 跳過的列**不會被 UPDATE 到**。而我第一版寫成 `SELECT … FOR UPDATE SKIP LOCKED;` 之後**另一句無條件 `UPDATE`**
⇒ 📌 **它印出「已取消=true」, 而那個 true 是我自己造的** —— 差一點被我讀成「FK 鎖擋不住取消」的新發現。
🛑 **抓到它的不是我更小心, 是我去開了真檔對形狀** —— 而我當時是為了「確認這是真洞還是鑽機錯」才去開的。

## J-3 結論(每一句都對得上上面的讀數)
· **cron 先到**:收款卡住 ⇒ cron 取消 ⇒ 收款落帳 ⇒ **網開出一列待退款** ⇒ 錢有人接。
· **收款先到**:cron 的 `FOR UPDATE … SKIP LOCKED` **跳過那張單**(`已取消=false`)⇒ 根本不會取消 ⇒ 安全。
· **突變證明那個 1 是網做的**:拿掉 trigger ⇒ 0;裝回去 ⇒ 1。
