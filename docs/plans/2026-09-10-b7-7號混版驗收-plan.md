## 二、「舊版釘成 artifact」—— ✅ **spec 已經寫死做法,而我把兩側的值量出來了**

spec `:311` 逐字:
```
cd ~/API大量上架/PCM報價單-V2 && git rev-parse HEAD
git show <hash>:app/api/sso/authorize/route.ts
git show <hash>:app/api/sso/exchange/route.ts    ← 測試跑【這兩份】
🔴 hash 以【B4 那顆 commit 的 HEAD^】為準, 不要用本表落筆當下的值
```
📎 **它的理由**:「手寫一份『舊 exchange』的替身**證明的是我會寫舊版,不是舊版會怎樣**。」

### 【量的】報價單那一側 —— **規則直接套得上**
```
B4 那顆      a5276748  feat(sso): B4 帶身分 — authorize 寫兩欄、exchange 回 sub  (2026-08-21)
🔴 舊版      1220073d06fe313a760fe5da6ef0129190f26f3a   ( = a5276748^ )
             authorize  76 行 · sub_kind 命中 0      |  今天 main  91 行 · 命中 1
             exchange   74 行 · sub_kind 命中 0      |  今天 main  90 行 · 命中 3
⚪ 負對照 現造路徑 ⇒ fatal: path … does not exist
```

### 🔴 【量的】admin 那一側 —— **規則【套不上】,而這一格是本 plan 最實用的發現**
spec 那句是「**B4 那顆 commit 的 `HEAD^`**」。**照著套到 admin 會釘錯。**
```
952c0c42a^   result.sub 命中  0 處   ← 🔴 這才是乾淨的「舊 admin」
952c0c42a    命中 2 處   fix(admin): SSO 的 sub … 在最後一行被丟掉
ede728796    命中 9 處   feat(admin): B5-a 後台吃身分
b21dc3fa8    命中 10 處  feat(admin): 簽票那一刻才問「他還在職嗎」
⚪ 負對照 現造 ref ⇒ fatal: invalid object name
```
📌 **⇒ admin 側的改動散在【三顆】commit 上** ⇒ **要釘在【第一顆的 parent】,不是那顆 `feat` 的 parent。**
🛑 **我第一發就是照 spec 的規則取 `ede728796^`,而它【還有 2 處】** —— 那不是乾淨的舊版。
🎯 **⇒ 「B4 那顆的 `HEAD^`」這個規則,它的前提是【那件事只有一顆 commit】。而 admin 側不是。**

### ⇒ 誰維護
🔵 **不需要維護** —— 兩側都是 `git show <釘死的 hash>:<路徑>`,**而 hash 是不會動的**。
🛑 **要做的只有一件:把那兩個 hash 寫進測試檔的註解與板列**,並寫一句「**它們是釘死的,不要跟著 HEAD 走**」。
🔴 **而有一格會爛**:若那兩支檔將來被**改路徑或改名**,`git show` 會回 `does not exist` ⇒ **測試紅,而紅的理由不是安全性壞掉。**
⇒ ✅ **處置(寫進測試)**:那個錯要**明說是「舊版取不到」不是「混版壞掉」**。

### 🔵 而我踩了一格,寫在這裡免得下一個人重踩
我用 `git log --all` 找 B4 那顆 ⇒ 撈到 `a413a075 index on main: …` —— **那是一個 stash,不是 commit。**
📌 **`--all` 含 `refs/stash`。** ⇒ 找「哪一顆做了這件事」時,**`--all` 的分母比你以為的大。**

## 三、🔴 `7b` / `8b` / `7c` 怎麼跨到 admin —— **這一格我不確定做不做得到**

**要驗的東西**:報價單回一個(不帶 `sub` 的)回應 ⇒ **admin 收下之後,最終簽出來的那顆 cookie 長什麼樣。**

### 甲案:**兩個 repo 各起一份,真的打**
```
起報價單(舊版的那兩支 route)⇒ 起 admin ⇒ 走一次完整的 authorize → callback → exchange
需要:兩個埠 · 兩套 env · Supabase(或替身)· SSO 共享 secret · 兩份舊版檔要 checkout 到某處
```
🔴 **我不確定做不做得到**,而不確定的是這三格:
· **報價單的舊版要怎麼跑起來** —— `git show` 出來的是**兩支檔**,而它們依賴的 `lib/session.ts` 等**也是舊的**。
  📌 **只換那兩支檔 = 一個【新舊混合體】,而那不是「舊版」。** ⇒ 要跑真的舊版,得 `git worktree add <舊 hash>` **整棵**。
· **admin 的舊版同理** —— 要整棵舊的 admin。
· **兩邊都要 Supabase** —— 而 `sso_codes` 那張表在舊版與新版的欄位不同(`sub_kind` 兩欄是 B4 加的)⇒ **要兩個 DB 世界。**
🔵 而 `docs/runbooks/throwaway-postgres-for-migration-verification.md` 起得了 PG;**PostgREST 那一層沒有人在這個專案裡做過**(今天量到的)。

### 乙案:**只驗 admin 那一半 —— 餵它一個「報價單會回的那種回應」**
```
不起報價單。直接對 admin 的 callback 餵 exchange 的回應(不帶 sub / 帶 sub 兩種)
```
✅ **做得到**,而且 admin 那一側**今天就有 route 測試的做法**(`b7-login-route-negative.test.mts` 是同一個形狀)。
🛑 **而它替不了什麼(先寫出來)**:
· **替不了「舊版報價單真的會回那個形狀」** —— 那是**我寫的**回應,不是**它產生的**。
  📌 **⇒ 這正是 spec `:311` 明文反對的那件事:「證明的是我會寫舊版,不是舊版會怎樣」。**
· **替不了 `7c`(飛行碼)** —— 那一格要的是**一顆真的由舊 authorize 發出、被新 exchange 兌換**的碼。
· **替不了 7 與 8** —— 那兩格看的是報價單的回應本身。

### 丙案:**混合 —— `7`/`8` 用真的舊版跑報價單那一側;`7b`/`8b` 用乙案餵 admin**
```
7 / 8    ⇒ git worktree add 舊 hash ⇒ 起報價單 ⇒ 打 exchange ⇒ 看 HTTP 回應(不需要 admin)
7b / 8b  ⇒ 餵 admin 一個「§一 那一格量到的、逐字相同的」回應
7c       ⇒ 🛑 仍然做不到(要跨越部署那一刻的真碼)
```
🔵 **而丙案的 `7b`/`8b` 有一件甲案沒有的好處**:餵進去的那個回應**不是我編的,是 `7`/`8` 那兩格【真的量到的】** ⇒ 📌 **它替得比乙案少一格。**

🔴 **我的傾向是丙,而我沒有把握** —— **要不要走,我想聽 Sean 或主視窗的。**
