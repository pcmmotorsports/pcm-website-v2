## 1. 改什麼

**把那個 view 換成 repo 現在這一版。** 具體差異(`a5eadca43` → `origin/dev`):

| | 帳上那版(= 正式庫今天) | repo 現在 |
|---|---|---|
| 建法 | `CREATE OR REPLACE VIEW` | `CREATE VIEW`(裸) |
| 結構 | 單一 `SELECT` | `manual_blank` CTE + **`UNION ALL` 四塊** |
| 欄 | 6 欄 | 多 `surface` / `shipment_id` / `corrected_at_key` |
| 語意 | 一列 = **一張單** | 一列 = **一個本來會發生的通知** |
| 述詞 | 只判「手動 + 信箱留白」 | 與四支 pending view 的其餘述詞同形 |

🛑 **而「換」不是一句 `CREATE OR REPLACE`** —— 新版是裸 `CREATE VIEW` 且欄位變了
⇒ 要 `DROP VIEW` 再 `CREATE`。**那支 migration 自己的 rollback 已經寫過這個順序**
(R2 commit 訊息④ 逐字:「先 DROP 伴生 view,再把那【四】支回 080000」)。

🔴 **本 plan 刻意【不提供】那支 SQL。** 理由見 §6。

## 2. 為什麼(= 那七輪裡哪一輪是【必要的】—— 主視窗指定要答的那一格)

### 2-1. ✅ R2 ① 是一個**正確性修正**,而它今天還在 repo 裡沒上線
R2 的 commit 訊息**逐字**:

🔬 我核過那段述詞,帳上那版的 `WHERE` **逐字**只有兩條:
```sql
WHERE o.order_source IN ('manual_phone', 'manual_line', 'manual_other')
  AND nullif(pg_catalog.btrim(o.notification_email, public.pcm_js_trim_whitespace()), '') IS NULL;
```
⇒ ✅ **「舊版沒有排除那三種」是【可驗證的事實】,不是轉述。**
⇒ 🔴 **所以這不是「檔案漂了」,是【一個修好的東西沒上線】。** 那是本 plan 存在的理由。

### 2-2. R2 的其餘幾條(在這支檔裡的)
- ③ 改裸 `CREATE VIEW`(為了讓突變測試紅在它該紅的那一句)⇒ **工程性,不是正確性。**
- ④ rollback 重寫成兩步 + 補自證⑥⑦ ⇒ **只影響退場,不影響線上行為。**

### 2-3. 🛑 R2 ⑤(那個 `WHEN query_canceled`)**不在這支檔** —— 差點記錯帳
