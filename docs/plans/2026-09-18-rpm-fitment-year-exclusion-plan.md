## 3. ① 🔴 資料從哪來 —— **這題是本片會不會三個月後靜默過期的關鍵**

`product_fitments` 由 rpm-import 從報價單同步,**每次匯入會覆寫**。
⇒ 🛑 **所以「手動改 DB 那幾列」= 下一次匯入就被沖掉,而且沒有人會知道。**

三條路,我**不自己決定**:

| | 做法 | 好 | 壞 |
|---|---|---|---|
| **甲** | 在 rpm-import 的 `supplier-config.ts` 加一張**具名例外表**(18 件裡的 B 那 5 件),匯入時套用 | 🟢 **匯入沖不掉**,而且例外寫在程式裡、看得到、進得了 code review | 🟡 供應商改了年份沒人知道 ⇒ 要配一道「例外表裡的料號還在不在來源」的對帳 |
| **乙** | 從英文描述**解析**年份 | 🟢 自動 | 🔴 **新增一個解析器**,而窗C 今天證明純樣式判定會誤報(它自己 5 抽只敢認 2 件);**錯的年份比沒有年份更糟** |
| **丙** | 後台開一個「fitment 年式覆寫」CRUD,員工自己維護 | 🟢 不用改碼就能維護、鐵則 9 的正解 | 🔴 工作量最大,而且今天沒有人在維護它 |

🔵 **我推薦甲**,理由:
- **B 只有 5 件** ⇒ 一張 5 列的具名表,成本最低
- 例外寫進 `supplier-config.ts` ⇒ **它會出現在 diff 裡**,不像 DB 手改那樣隱形
- 🛑 **而甲要配一道對帳才算完整**:那 5 個料號如果從來源消失、或供應商自己補了年份,
  **例外表要叫** —— 否則就是「今天對、三個月後靜靜過期」的那種東西。

🛑 **這題沒答之前不要動手** —— 它決定這片是一次性修補還是一個會活著的機制。

```

```
適用車款

🔵 年式 chip 的三態格式是元件既有的(`ProductFitments.tsx:20-25`),**本片不新增樣式**:
```

起, 迄=null           → 「2017 年起」
```
🛑 **而「2021 年以後不適用」這句【不會】出現** —— 那張表的語意是「列出適用的」,不是「列出不適用的」。
