## 0. 這一片為什麼存在(第一行,主視窗指定)

Sean 2026-09-01 給了根因並自己處置了:
> 「因為這一筆 20 元交易銀行自動請款,並且自動提領,導致我們 tappay 戶頭沒錢,所以退不了款,
>   我會把 tappay 改成不要自動提領(三天自動提領)」

🔴 **而那【縮小窗口,不消除】**:三天內的退款有餘額 ✅;**三天之後的退款仍會撞到同一件事** ——
而真實客人的退款多半**不是**三天內(收到貨 → 發現不對 → 聯絡客服,通常一到兩週)。
⇒ 📌 **所以那個設定改的是【我們測試時方便】,不是【正式營運時不會發生】。**

⇒ ⇒ **本片修的不是「餘額不足」,是【餘額不足發生時,我們有沒有辦法把它收乾淨】。**
```
今天同一個真實原因(戶頭沒錢)走出兩種系統狀態:
  6 筆 manual_failed        ⇒ 收得了尾 ✅
  1 筆 adapter_threw/error_unclassified ⇒ **卡在 processing、沒有編號、沒有人收得了尾**
```

### ⛔ ~~① 失敗路徑也把 `tappay_refund_id` 寫進那一列~~ ⇒ **撤銷,DB 兩欄都不准**

📌 **⇒ 「它給了我們一個編號」與「它受理了」是兩個宣稱 —— 而那一欄要的是後者。**
🔵 **⇒ 而真正的發現是:「unknown:拿到編號而不知道結果」在資料模型裡【沒有位子】。**
   schema 有【受理的證據】欄、有【失敗的詳情】欄(CHECK 限定 `status='failed'`)——**沒有第三格**。
   ⇒ 而它今天的落點是 `admin_audit_log` 的 detail ⇒ **那其實是對的地方,只是沒有人會去看。**

### ⛔ ~~② `TP36` ⇒ 判得出來~~ ⇒ **兩處錯,兩處都致命**

**錯一:欄位錯。** ⛔ ~~TP36~~ ⇒ **`10016`(顯示為 TP36)**
```
TP36  = 顯示 / 銀行碼(`bankResultCode`, **string**)
10016 = TapPay 的 `wire.status`(**數字**, 與 10051 / 10024 同一欄)
⇒ 📌 照「TP36」寫會【比對錯欄位】—— 而那個字串是從後台畫面抄來的, 讀起來完全像程式碼。
```

**錯二:兩道准入閘,而兩道都是刻意的。**
```
① `TAPPAY_REFUND_STATUS` 檔頭逐字:**新增碼必須先有 sandbox 實證**
   現有實證全是 kind='partial'(2026-08-01 兩個獨立 probe:10051 兩組邊界 / 10024 連退四次)
🔴 ② 更硬:我們這一筆 `kind='full'`, 而檔頭逐字
   「`kind='full'` 撞**任何**非 0 碼 = 未實證組合, adapter **一律 throw(unknown-state)**」
   ⇒ 實查 `TapPayChargeAdapter.ts:444`:已處理的分支**全部**是 `kind === 'partial' && …`
   ⇒ ⇒ **就算把 10016 加進常數表, 這一筆仍然走 unknown-state ⇒ 對今天這筆零效果。**
```
🔵 **⇒ 而那個保守不是懶惰,它就是為了我們現在這個處境設計的**
   —— 判 failed 而錢其實動了 ⇒ 會再退一次 ⇒ **退兩次**。
