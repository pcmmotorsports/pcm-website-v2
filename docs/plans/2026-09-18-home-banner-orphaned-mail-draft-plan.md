## 一句話

一張**信件來的**大圖草稿,放過 90 天之後,系統會把它變成**看起來像是員工手動建的**,
而「手動建的不用配到商品」⇒ **那道「要配到商品才能上首頁」的閘就對它失效了**。
員工勾個授權就發得上首頁,**而不需要任何人犯錯**。

### 三步,每一步都是設計好的,錯在它們串起來

### 失效的是**兩道**,不是一道 —— 修法要兩道都蓋到

| # | 在哪裡 | 逐字 |
|---|---|---|
| A | 表上 CHECK `home_banners_mail_published_needs_match`(`20260916180000:68`) | `(status <> 'published') OR **(source_email_id IS NULL)** OR (cardinality(matched_variant_ids) > 0 AND link_path ~ '^/products($\|[?/])')` |
| B | `admin_home_banner_publish` 函式內(`20260916180000:241`) | `IF v_before.source_email_id IS NOT NULL THEN` → 才檢查「配到商品」與「連結指 /products」 |

🔬 A 我從**正式庫** `pg_get_constraintdef` 撈過,逐字相符。

### 🔴 而那個 `IS NULL` 分支**不是 bug** —— 這一格最容易被改錯

`20260916180000:14` 逐字:「**手動新增的大圖不受「要配到商品」這條管**(`source_email_id IS NULL`):
Sean 自己建的季節性大圖本來就沒有」。

⇒ 📌 **病不在「NULL 放行」,病在【一張本來是信件來的圖,會被系統改成看起來不是信件來的】。**
⇒ 🛑 **所以不可以把那個 `IS NULL` 分支拿掉** —— 拿掉會讓 Sean 手動建的季節大圖全部發不出去。

### 觸發條件(不需要任何人犯錯)

```
信件來的草稿建立 → 放著沒發布 → 超過 90 天 → 清理排程跑 → 員工打開它 → 勾授權 → 按發布
```
全程沒有人做錯事,**而到那一刻沒有任何東西會叫**。

### 🔴 而我第一發的「對照組」自己也是 0 —— 記在這裡,不要照抄那個做法

我原本跑:`source_email_id 非空的 draft` ⇒ 0 · `source_email_id IS NULL 的 draft` ⇒ 0。

✅ 換成**會動的尺**才算數:同一條 `WHERE` 換門檻 ——
`created_at < now() - interval '0 days'` ⇒ **2**(不是 0)· `'9000 days'` ⇒ **0**;
再把現有兩列逐列攤開看得到。⇒ **尺會動,0 是真的 0,不是連線回空。**

## ③ 修法:先答「跟第一扇門一不一致」這題

### 第一扇門當初是**怎麼**修的 —— 我去把它的理由挖出來,不看結論看原則

`20260916250000:38-49` 逐字:

> ⛔ ~~原本不複製,理由寫「複製品不是那封信生的」~~
> 🔴 **那句話聽起來很對,而它把一個【來歷】的問題講成一個【出身】的問題。**
>    複製品的**內容**就是那封信來的;把來歷丟掉 = **把那個內容該受的管一起丟掉**。
> ✅ **現在的規則:來歷跟著內容走** —— 與 `rights_note` 跟著圖走**是同一條**。

⇒ 🎯 **第一扇門的【原則】是「來歷跟著內容走」,它的【形式】是「把 `source_email_id` 原樣帶過去」。**

### 🛑 而第二扇門**沿用不了那個形式** —— 這是本片最該被讀懂的一格

第一扇門:來源那一列**還在** ⇒ 把 id 抄過去就保住了來歷。
第二扇門:來源那一列**正在被刪** ⇒ **id 本身保不住**,抄無可抄。

⇒ 📌 **形式沿用不了,原則沿用得了。**
⇒ ✅ **建議寫進兩扇門的檔頭:第三扇門出現時,要照的是【來歷跟著內容走】這條原則,不是「複製那個欄位」那個動作。**
   🔴 而這正是主視窗問的那題的答案:**不是「兩扇一起換成另一種」,也不是「照抄第一扇」,是【把原則寫下來當共同判準】。**

### 三個選項

#### 甲 —— 清信時,**不刪還有大圖指著的那幾封**(最小改動,**建議**)

```sql
DELETE FROM public.supplier_inbound_emails e
 WHERE e.created_at < now() - interval '90 days'
   AND NOT EXISTS (SELECT 1 FROM public.home_banners b WHERE b.source_email_id = e.id);
```

- **動的東西**:一支函式、一個 `AND NOT EXISTS`。**零新欄位、零 CHECK 改動、零 publish 函式改動。**
- **為什麼它對**:直接不讓第 2 步發生 ⇒ A、B 兩道閘**一個字都不用動** ⇒ 不會改錯那個 `IS NULL` 分支。
- **形式上**它跟第一扇門也是同一句話:**保住來歷**。
- 🔴 **代價,講明白**:與 Sean 2026-09-16 Q8 甲「信件 90 天後刪」**有出入** —— 會有少數幾封留得比 90 天久。
  🔵 而那個代價**比聽起來小**:那張表**逐字不存信件內文**(`20260916150000` 的
  `supplier_inbound_emails_extracted_check` 註解逐字「extracted 只放抽出來的品名 / 料號 / 圖網址 / 廠商連結,**不放信件內文**」,而且限 16KB)。
  留著的是寄件者、主旨、收信時間、抽出來的品名料號。
- 🔴 **而「留多久」這一格我不含糊**:**只要還有任何一張大圖指著那封信,它就一直留著** ——
  發布、封存都**不會**清掉 `source_email_id`(我查過:`save_draft` 對這一欄是「不傳就別動」,
  `_publish` / `_archive` 只動狀態欄)⇒ **那張大圖活多久,那封信就留多久,沒有上限。**
  🔵 會被刪的只有一種:那張大圖**整列被刪掉**(今天沒有任何路徑會刪大圖 ⇒ 實務上 = 不會)。
  ⇒ 📌 **所以誠實的說法是「那幾封等於永久保留」,不是「留久一點」。** 數量 = 有信件來的大圖幾張。
- ⚠️ **這一條需要 Sean 點頭**,因為它改的是他拍過的板,而且改的幅度比「延後刪除」大。

#### 乙 —— 加一個**清不掉的來歷標記**

加一欄(例如 `from_supplier_mail boolean NOT NULL DEFAULT false`),A、B 兩道閘改看它。

- **好處**:來歷與那封信的生死**脫鉤**,最徹底。
- **代價**:動 schema 加欄 + 改表上 CHECK + 改 `admin_home_banner_publish` + 回填既有列
  (今天 2 列、都不是信件來的 ⇒ 回填本身 trivial)
  + **五支寫入函式裡至少三支要記得設它**(`save_draft` / `_duplicate` / `system_supplier_mail_record`)。
- 🔴 **它自己帶一個新的洞**:哪支函式忘了設 ⇒ **又生出一張「看起來不是信件來的」** ⇒ 同一個病,新的門。
  📌 **甲不會有這個問題,因為甲沒有第二個真相來源。**

#### 丙 —— FK 改成 `ON DELETE RESTRICT` ⇒ **不建議**

清理排程會**整個失敗**(只要有一封被指著),Sean 的「90 天後刪」直接壞掉,而且是**靜靜壞掉**(排程回錯,沒人看)。

### 建議


### 🔵 甲+ —— 甲的加強版:**留下那一列,但把內容清掉**

我寫完甲的代價那段才想到:「**刪那一列**」與「**刪那些資料**」是兩件事,而我們**只需要後者**。

```
清理時不 DELETE,改成把有大圖指著的那幾封【就地清空內容】:
  subject → NULL · extracted → NULL · gmail_thread_id → NULL · error_code → NULL
  (沒有大圖指著的,照舊 DELETE)
```

- ✅ **兩邊都拿到**:來歷(那一列的 id)保住 ⇒ 兩道閘照樣有效;而**真正的資料 90 天準時消失** ⇒ Sean 的 Q8 精神保住。
- 🔴 **而它有一格要先查,不要當成已經成立**:`sender` / `gmail_message_id` / `received_at` / `status` 都是 **NOT NULL**,
  `sender` 還有 CHECK(`<> ''` 且 `= lower(btrim(...))`)⇒ **那四欄清不掉**,只能留著或塞一個墓碑值。
  ⇒ 📌 **所以甲+ 不是「全部清光」,是「清得掉的清掉」。** 要 Sean 知道**寄件者與收信時間會留著**。
- ⚠️ 比甲多動一點(一支函式內從一句 DELETE 變成 DELETE + UPDATE),而仍然是**零新欄位、零 CHECK 改動、零 publish 改動**。
