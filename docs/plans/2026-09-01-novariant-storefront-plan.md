## 1. 🔴 第一題:它現在【為什麼加得進購物車】—— 四層逐一量過

```
① 商品頁(PDP)的加入鈕     ⇒ **不擋**。而它【不是漏做的】,見下面那個拍板
② 商品卡片(列表)的直加    ⇒ **不擋**。`ProductCard.tsx:112` 逐字 `if (hasVariants) return;`
                              ⇒ 有變體的走導頁, **零變體的就地加進購物車**(刻意的)
③ 購物車 / 結帳前          ⇒ **不擋**。`CartView.tsx:42` 與 `useResolvedCart.tsx:54`
                              兩處都寫 `variantId ?? null` —— 它們【handle 了】沒有變體, 不是攔它
④ 按下付款之後             ⇒ 🔴 **擋在這裡**。`useChargePayment.tsx:140` `if (!it.variantId)`
                              ⇒ 那是**填完卡號、按下確認付款【之後】**
```
📌 **⇒ 答案:四層裡只有最後一層擋,而那是最晚的一層。**
🔴 而更精確的是:**前三層不是「忘了擋」,是【明文設計成不擋】** ——
`cart/actions.ts` 逐字「genuine 無變體商品的 variantId 欄為 undefined、走下方正常路」。
⇒ 📌 **購物車那一側的契約說「無變體合法」,而結帳那一側說「沒有 variantId 就整單拒」。**
**兩邊各自都對,而它們對同一件事的定義不同 —— 那就是為什麼沒有人的 code review 抓得到。**

## 3. 選項(而判準是【客人多早知道】)

```
甲 商品頁 + 卡片:**不給加**(最早)—— 而它命中 #161 那個拍板 ⇒ 🛑 **排除**
乙 商品頁 + 卡片:**照樣可點**,而點下去不是加入購物車,是一句
   「這件商品目前不能單獨購買,請洽客服」⇒ 不 disable、不推翻 #161  ← **我推薦**
丙 購物車那一層擋(比現況早兩步,而客人已經加進去了)
丁 維持現況(付款後才擋),只把那句訊息改成講得出下一步
```

### 🔵 為什麼推薦乙
```
· 它**不碰 #161**:鈕還是永遠可點, 變的是「點下去發生什麼」
· 客人在【還沒填卡號】之前就知道 ⇒ 比現況早三層
· 而它**不碰結帳那條路** ⇒ 不動錢(見 §5 鐵則 12 逐條)
🛑 而乙的代價明寫:客人會覺得「為什麼看得到卻買不到」——
   ⇒ 所以那句話要**說得出下一步**(洽客服), 不能只說「無法購買」
```
### 🛑 而丁(維持現況)不是「不做」,它有一個真實的成本
```
現況那句「購物車有商品缺少規格資訊,請返回購物車重新確認」——
🔴 **而購物車上沒有東西可以修**(那支商品本來就沒有規格可選)⇒ 客人卡死。
⇒ 若選丁, **那句話一定要改**, 否則我們是在叫他去做一件做不到的事。
```

## 4. 🔴 閘要驗【結構】不驗【結果】

```
今天架上零變體商品 = **0 支**(2026-08-31 唯讀正式庫實量)
⇒ 📌 **任何「驗現在有沒有這種商品」的測試都會【恆綠】。**
⇒ 要驗的是:**一件零變體的商品【被餵進來時】會怎樣**, 不是「現在有沒有」。
```
**驗收(每一格都要有一個會紅的世界)**:
```
🔴 ① 餵一件零變體商品 ⇒ 點加入 ⇒ **不進購物車**, 而且畫面說得出下一步
🟢 ② 餵一件【有變體】的商品 ⇒ 照樣加得進去  ← 少了它,「永遠擋」的實作會全綠
🔴 ③ 突變:把那道判斷拿掉 ⇒ **必須紅**
🛑 ④ 而【付款後那道】不得移除 —— 它是最後一道, 前面加了不代表可以拆後面
   ⇒ 加一格釘住 `useChargePayment` 那道還在(它是 fail-closed 的底線)
```
