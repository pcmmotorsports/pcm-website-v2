## 0. 一句話

**要接兩個落點,不是一個。** 而它們的形狀相反:一個有錢動、一個沒錢動。

```
落點① 有錢動的 → pcm_sync_order_refund_payment_status(匯流點)
                 7 支退款函式真的呼它(剝行註解後實數;raw 13 行 ⇒ real 9 行)
落點② 沒錢動的 → 取消那條路
                 🔴 未付款就取消的單【沒有任何退款事件】⇒ 匯流點永遠不會叫
                 🔴 而匯流點自己會【拒絕】unpaid:
                    `IF v_ps NOT IN ('paid','partiallyRefunded','refunded') THEN RAISE`
                    (`20260907140000:191`)⇒ 硬塞進去會炸,不是沒反應
```

📌 **⇒ 這兩個不能塞進同一個落點。** 而 Sean 的 Q1 甲(掛匯流點)與 Q5 甲(取消就退券)
各自都對 —— **是它們的交集多出一件事**,不是誰答錯。

## 1. 🔴 Q1 · 落點② 掛在哪?

### 今天取消那條路的形狀(實量)

```
admin_cancel_order (19,899 字元) / admin_mark_order_cancelled (6,247 字元)  剝行註解後:
  order_refunds f · order_pending_refunds f · pcm_pending_refund_open_for f
  pcm_sync_order_refund_payment_status f · coupon f   ⇒ 它們只碰 payment_status
⇒ 📌 那兩支【自己不退錢】, 只是把單標成取消。

接力的是一支 trigger(不是函式呼叫 ⇒ 只數函式呼叫的尺看不到它):
  order_pending_refund_open_au   AFTER UPDATE OF cancelled_at ON public.orders
    → pcm_pending_refund_on_cancel()  (175 字元, 只有一件事)
    → pcm_pending_refund_open_for(...)
  🔵 它只在【轉換的那一刻】做事:`IF OLD.cancelled_at IS NOT NULL OR NEW.cancelled_at IS NULL THEN RETURN NULL`
  ⚠️ tgenabled = 'O'
```

```
甲(推薦)= 掛那支 trigger 的函式 `pcm_pending_refund_on_cancel()`
        ✅ 一個落點蓋住【所有】把 cancelled_at 從 NULL 改成有值的路 ——
           包含 admin_cancel_order、admin_mark_order_cancelled,
           以及**任何未來新增的、或直接 UPDATE 的**取消路徑
        ✅ 它本體只有 175 字元、只做一件事 ⇒ 改動面最小
        ✅ 它已經有「只在轉換那一刻做事」的判斷, 不必自己再寫一份
        🔴 **而它的代價要寫死**:`tgenabled = 'O'` ⇒ 在
           `session_replication_role = replica`(還原 / 大量匯入)之下**整支被跳過**
           ⇒ 那時候取消不會退券。
           📌 而 `20260901021000` 的自檢**要求它自己那支 trigger 必須是 'A'**, 理由逐字
              「`O` 之下券沒被扣而 UPDATE 照樣成功」⇒ **同一張表上兩套標準, 而沒有人裁過。**
           ⇒ 🛑 選甲的話, 要不要把它改成 'A' 是**第五題**(見下)。

乙       = `admin_cancel_order` 與 `admin_mark_order_cancelled` 各呼一次
        ✅ 不受 `session_replication_role` 影響(它是函式呼叫不是 trigger)
        ⚠️ 兩個落點要各自維護, 而**漏掉第三條取消路的那天沒有人會知道**
        🔴 而今天就已經有第三條:任何直接 `UPDATE orders SET cancelled_at = …`
           (那正是 trigger 存在的理由)
```

🔵 **推薦甲的理由**:🎯 **守在所有人都會經過的那個路口,而不是守在門口** ——
　 它擋得住**還沒被寫出來的那一條取消路**。而乙擋不住。

## 2. 🔴 Q2 · 錢動完之後才夠格的那條路 —— 誰來退券?

### 情境(codex R1 給的反例,R3 追到底)

```
total=1000 · confirmed=400 · processing=600
⇒ 今天:v_moved = 400 < 1000 ⇒ 【不退券】(正確)
⇒ 那 600 後來成功時, codex R3 追出來的實際路徑:
     refund-actions.ts:581 → refund-repository.ts:531 → admin_finalize_order_refund
     → RPC:353-361 把 processing 改 confirmed, RETURNING INTO v_after
     → RPC:401-402 因 v_after.status = 'confirmed' 呼【匯流點】
     → 匯流點讀到同交易剛寫入的 600 ⇒ v_moved = 400 + 600 = 1000
🟢 ⇒ 到【匯流點】接得上。而到【退券函式】今天還沒接 —— 那正是本份要做的事。
```

```
甲(推薦)= 落點① 就掛在匯流點本體, 而且【無條件】呼 —— 由退券函式自己判夠不夠格
        ✅ 上面那條路自動被蓋到:那一刻 v_moved 變 1000 ⇒ 退券函式自己算出「夠了」⇒ 才退
        ✅ 靠的是退券函式的**冪等**(`WHERE reverted_at IS NULL`), 不是靠誰記得補呼一次
           🔬 而冪等已經實測過:同一筆第二次 ⇒ 0 列 · reverted_at 沒被覆寫
        ✅ 匯流點的 7 個呼叫端**一個都不用改**
        ⚠️ 代價:每一次退款狀態同步都會多呼一次退券函式(絕大多數回 0)
           ⇒ 那是一次 orders 的 FOR NO KEY UPDATE + 三個 SUM。**同一交易已經鎖過那張單**
             ⇒ 重複鎖是 no-op(codex R2 逐字核過鎖序, 未找到反向)

乙       = 匯流點裡先判「這一次是不是剛好退滿」再呼
        ⚠️ 那等於**把判準寫到第三個地方**(退券函式一份、匯流點一份)
        🛑 而今晚最貴的一個錯就是「兩把尺回答不同問題」⇒ 不要再造第三把
```

🛑 **而甲要寫死一格**:匯流點掛在**哪一行**。
　 codex R3 逐字:「目前匯流點到 `20260907140000:230` 的 `RETURN` 為止,都沒有呼退券函式」。
　 ⇒ 📌 **要掛在【所有 early-return 之前 or 之後】是一個要答的細節**,而它有前例可抄:
　 　 `pcm_noncard_settle_recompute` 檔裡逐字寫過「位置刻意在**所有 RETURN 之前**——
　 　 下面每一條 early-return 都會漏掉它」。⇒ **寫 SQL 那一輪要照這個形狀想一次。**

## 4. Q4 · rollback 怎麼寫?

```
甲(推薦)= 反向 `CREATE OR REPLACE` 回「不含退券呼叫」的那一版
        ✅ 那一版的原文就在 20260907140000 / 20260908060000 裡, 逐字可取
        🔴 而 rollback 檔要**內含那一版的完整 body**, 不可以寫「請去某某檔複製」
           📌 回捲的人是在出事的當下讀它, 那時候他沒有心情去翻另一支檔
        🔴 **單向的那一格要明寫**:已經被寫上 reverted_at 的那些 redemption
           **不會**跟著回來 —— 回捲只拿掉「以後還會不會退」
乙       = DROP 掉退券函式
        🛑 不行:那會讓 021000 / 030000 的前置閘重新變成擋著 ⇒ 影響面比本支大得多
```

## 5. 🔴 Q5(新增)· 那支 trigger 要不要從 `'O'` 改成 `'A'`?

**這一題是選甲(掛 trigger)才會出現的,而它不能跳過。**

```
🔬 實量:public.orders 上 5 支 trigger, 其中 4 支 tgenabled = 'O'(那是 PG 的預設)
        唯一 'A' 的是 zzz_pcm_invoice_requested_false_is_final
        而 20260901021000 的自檢【要求它自己那支扣券 trigger 必須是 'A'】, 理由逐字:
        「`O` 在 session_replication_role=replica 之下整支被跳過, 而那是還原 / 大量匯入用的模式。
          實測:`O` 之下券沒被扣而 UPDATE 照樣成功。」

甲(推薦)= 不動它, 維持 'O', 而**把這個限制寫進檔頭**
        ✅ 改動面最小, 不碰別人的 trigger
        🔴 代價:還原 / 大量匯入時取消不會退券
        🔵 而那個代價今天的分母是 0(那種模式只有 Sean 在還原時才會用到)
乙       = 改成 'A', 與扣券那支對齊
        ⚠️ 那是改一支【別人的】trigger 的行為 ⇒ 影響面超出本片
        ⚠️ 而它會讓還原時取消也退券 —— 那在還原情境下**是對還是錯, 沒有人判過**
```
🛑 **而不管選哪個,「同一張表上兩套標準」這件事要有人裁** ——
　 今天扣券那支要 'A'、退券這條路是 'O',**兩邊對 replica 模式的答案相反。**
