## 要改什麼(形狀,不是碼)

### ① 病在哪(板列已記,這裡只留座標)
`SIGKILL` 讓 lint-staged 的 task 死掉 ⇒ husky 印 `pre-commit script failed (code 1)`
⇒ 🔴 **那個 `code 1` 與「你的碼有問題」在畫面上逐字相同** ⇒ 撞到的人會去查自己的碼。

### ② 修法 = **把既有的接上去,不是發明一個新分類**
`scripts/greenlight.sh` 已經是三態(`GREEN(0)` / `RED(1)` / `ENV-FAIL(2)`),
而它自己的檔頭逐字寫著「**看到 `ENV-FAIL` 不要查你的碼**」。
⇒ 📌 這是**機制優先律的教科書案例**:缺的不是分類,是**那條線**。

### ③ 最小形狀(三選一,我推薦甲)
```
甲(推薦)pre-commit 收到非 0 時, 先看是不是 137/143(SIGKILL/SIGTERM)或 log 含 SIGKILL
        ⇒ 印一行「🔴 這不是你的碼 —— 工具被系統砍掉了(記憶體壓力)」+ 建議先看 swap
        ⇒ 仍然 exit 1(**不放行**), 只是把【訊息】換掉。
        🔵 為什麼仍然 exit 1:放行等於讓一次沒跑完的檢查變成綠 —— 那比訊息不好更糟。
乙      改成 exit 2 走 greenlight 的三態 ⇒ 🛑 而 husky 對非 0 一律當失敗,
        exit 2 與 exit 1 對 git 是同一件事 ⇒ **它只換數字不換行為**, 收益等於甲而多動一層。
丙      不改 hook, 改 lint-staged 的 task 包一層 ⇒ 🛑 要動 62 個 task 的每一個, 爆炸半徑最大。
```

### ④ 驗收(兩個世界,而第二個是這一片的難處)
```
🟢 正對照  真的有 lint 錯 ⇒ 訊息【不得】變成「不是你的碼」
🔴 負對照  構造一個被 SIGKILL 的 task ⇒ 訊息要換掉
          ⚠️ 而【怎麼構造】是這一片最貴的一格:
             `kill -9` 自己的子程序做得到, 而它是不是與「核心因為 swap 滿而砍」走同一條路
             —— **我沒有量過**, 不要寫成「等價」。
          ✅ **做法有了(主視窗 `-f8` 2026-09-05 給), 而它【還沒跑】**:
             用 `ulimit -v` 把子 shell 的記憶體壓小, 讓 node **自己 OOM**(不是被別人 kill),
             與 `kill -9` **各跑一發, 看 rc 是不是都是 137**。
             🛑 **量到再改上面那句「我沒有量過」** —— 在那兩發跑完之前, 那句話仍然是這一格的事實。
```
