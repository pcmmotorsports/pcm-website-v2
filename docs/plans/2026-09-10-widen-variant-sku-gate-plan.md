
## 2. ① 那道閘【為什麼窄】—— 三個條件各自在擋什麼(逐字,不是我推的)

`20260906900000_m4b_storefront_search_variant_sku.sql:184-227` 自己寫著:

| 條件 | 它在擋什麼 |
|---|---|
| `t.term ~ '[0-9]'` | 逐字(`:149`)「② 詞裡**同時**有字母與數字 —— 少了它,打 `a` ⇒ 前綴 `A%` ⇒ **命中所有 A 開頭的料號**」 |
| `~ '[A-Za-z]'` **或** 純數字 `>= 7` | 擋 `'0'` `'1'` `'01'` 那種**會命中上萬**的詞(逐字:「根本進不了第 ④ 塊」) |
| 正規化後 `length >= 4` | 🔴 **這一條的理由是【cap 懸崖】,不是誤命中** —— 見下 |

### 🔴 那個 `>= 4` 的真正理由:**cap = 1000,而過 cap 是懸崖不是斜坡**
該檔逐字帶著一張唯讀實測表(`scripts/20260906900000-cap-headroom.sql`):
```
詞    今天(舊三塊)  貼完(加 ④)   cap = 1000
R1      1540          1696        ⇐ 今天就過了
A1       924           964        ⇐ 🔴 只差 36 就跨過去
1R        32           414
M8       305           346
```
⇒ 逐字:「過 cap 的後果是**整發搜尋退回舊路**(`SupabaseProductAdapter.ts:872`),
而舊路**沒有正規化也沒有變體比對** ⇒ 📌 **原本搜得到的東西會消失。**」
🎯 **⇒ 所以放寬的風險【不是結果變髒】,是【某個詞跨過 1000 之後那一整發降級】。**

### 🔵 而「用包含不用前綴」也有理由,一併帶走(免得下一個人想改它)
sku **沒有一致的形狀**(2026-09-06 唯讀全掃 59,841 列):有破折號 35,064 / 沒有 24,777;
而「破折號左半 = 母商品 `external_id`」**只有 16,348 列(27%)**
⇒ 📌 **「右半就是變體料號」這個假設對 73% 的列不成立。**
🔵 而 sku 上**沒有可用索引** ⇒ 前綴唯一的好處(吃索引)在這條路上本來就拿不到。

### 🛑 找不到理由的那一格,明寫
`t.term ~ '[0-9]'` 那一條我找到的理由(`:149`)講的是**前綴命中太多**,
而第 ④ 塊用的是**包含**不是前綴 ⇒ 🔴 **那個理由是為了【第 ③ 塊(母料號)】寫的,
它對第 ④ 塊成不成立,該檔沒有分開講。** ⇒ 📌 **這一格是「理由可能被沿用到不同的受詞上」,而我沒有更好的答案。**

## 3. ② 放寬之後的代價 —— **量的,不是推的**(2026-09-10 唯讀正式庫)

### 收益:那道閘今天實際擋掉多少
```
變體總數                                61,156
🔴 正規化後【完全不含數字】的料號          429   ← 「含數字」那道閘擋掉的全部
   樣本:ADLA · ADLAU · ADLB · ADLBU · ADLRR · ADLRRU · ADLS · ADLST
正規化後【短於 4 碼】的料號                 53   ← 「≥4」那道閘擋掉的全部
```
⇒ 🎯 **429 個變體料號,客人把它貼進搜尋框今天拿到 0 件。** 那是真實的、可數的缺口。
🛑 **而 codex 給的反例 `KIT-BLK` 在這個庫裡命中 0** ⇒ 📌 **它是一個形狀正確而【今天不存在】的例子** —— 真正的例子是 `ADLA` 那一族。

### 代價:純字母詞新進第 ④ 塊會多命中多少
```
詞       長度  變體塊命中商品數
BLUE      4        31
RACE      4         7
BLACK     5         4
SILVER/KITBLK/GOLD/CARBON/TITAN     0
🟢 正對照 PET52R ⇒ 1(今天就進得了第 ④ 塊)   ⚪ 負對照 ZZQ9999X ⇒ 0
```
⇒ 🔵 **多出來的量很小**,而最大那個 `BLUE`(31)離 cap 1000 還很遠。
🛑 **而這一格的射程要講清楚**:我量的是**第 ④ 塊自己新增的命中**,
**不是那個詞的總命中**(總命中要把第 ①②③ 塊一起算)⇒ 📌 **cap 是對【總數】判的,而我沒有量總數。**
⇒ **實作時要用 `scripts/20260906900000-cap-headroom.sql` 那把尺重跑一次,對【總數】量。**

### 效能/索引
該檔逐字:sku 上**沒有可用索引**,第 ④ 塊本來就是**全表掃 + 每列一次 regexp**
⇒ 🔵 **放寬入口閘【不改變掃描方式】** —— 它只讓更多詞進得了那一塊。
🛑 **而「更多詞進來」= 更多次全表掃** ⇒ **延遲我沒有量。** 實作時要 `EXPLAIN (ANALYZE)` 一次。

## 4. 改什麼(最小)

```sql
-- 20260906900000:184 第 ④ 塊的入口閘
-- 現在
   t.term ~ '[0-9]'
   AND ( t.term ~ '[A-Za-z]' OR length(正規化) >= 7 )
   AND length(正規化) >= 4
-- 建議
   ( t.term ~ '[0-9]' OR t.term ~ '[A-Za-z]' )      ← 放寬:純字母也算料號
   AND ( t.term ~ '[A-Za-z]' OR length(正規化) >= 7 )
   AND length(正規化) >= 4                            ← 🛑 這一條【不動】, 它守的是 cap 懸崖
```
🛑 **`>= 4` 不動** —— 它擋的 53 個料號**不值得換掉那個懸崖**;而要動它得先重量 `A1` 的總命中(今天 964 / cap 1000)。
🔴 三支一起改?**不用** —— 本片只動 `storefront_search_product_ids` **一支**,兩支目錄 RPC 不動(它們只是消費它)。
⚠️ migration 號段 **`…07xxxx`**;實作時**當場重跑撞號閘**,不沿用本 plan 猜的號碼。
