## 3. 🔴 新的風險模型(2026-09-10 唯讀正式庫全部重量,量具自陳 `products_visible 26,425 · variants_visible 61,156 · 02:55 UTC`)

cap 死了 ⇒ 沒有懸崖。**而那【不等於】隨便放寬都可以。** 重量之後剩下兩個代價,而其中一個大到會改設計。

### 3-1 🔴🔴 噪音 —— 而它把 v1 的做法直接否掉

v1 打算讓純字母詞走**現成的包含式**。實測那會發生什麼:

```
詞       現行三塊  第 ④ 塊(包含式)  真正新增給客人看見
FIRE        19          727              719      🔴
NINJA      867          727              702      🔴
BLUE         3           31               30
GUARD      402          218                0
RACE       343            7                0
ADLA         2            2                0
```
🎯 **那 719 件是什麼?** 唯讀撈了樣本:
```
sku            商品標題
APR-1-FIRE     防爆水管 8件組
HON-24-FIRE    防爆水管 4件組
KAW-44-FIRE    防爆水管 2件組
BET-15-FIRE    防爆水管 4件組 (水龜廢除)
```
📌 **`FIRE` 不是料號,是【供應商編碼的字尾慣例】。** 客人打「FIRE」拿到 719 條防爆水管。
🔴 **⇒ 這是本片最重要的一格:純字母窗格與含數字窗格【性質不同】。**
　`PRN0`、`RN014` 這種含數字的片段**沒有人會打**,所以包含式對它們是安全的;
　而 `FIRE`、`NINJA`、`BLUE` 是**真的英文字**,包含式會把編碼慣例變成搜尋詞。

**噪音上界(同一把尺掃全庫,不是我挑的詞)** —— `normalize(sku)` 裡每一個長度 L 的子字串,最多拉幾件商品:
```
L   純字母窗格種類  最大命中   前五
2       565          4,602    PR=4602 · RN=3682 · AR=2351 · OR=1774 · BL=1727
3     3,047          3,649    PRN=3649 · SIL=1454 · TAR=1440 · NER=1408 · ROS=1099
4     3,723            727    INJA=727 · FIRE=727 · NINJ=727 · KTAR=702 · SCTP=446
5     3,003            727    NINJA=727 · TARYA=279 · GUARD=218
6     2,020            138    KTARYA=138 · SETGBR=125 · DGPEVO=121
```
⚠️ **射程**:這是**上界** —— 多數窗格沒有人會打。而它兩邊用同一把尺,所以拿來**比較**是公平的。

### 3-2 ✅ 因此設計要改:純字母詞走【完全相等】,含數字詞維持【包含】

```
詞       包含式命中   相等式命中   第一塊已有
FIRE        727          0            19      ⇐ 噪音歸零
NINJA       727          0           867
BLUE         31          0             3
ADLA          2          1             2
ADLAU         1          1             0      ⇐ 收益還在
PET52R        1          — (含數字, 走包含式, 仍是 1)
```
```
🎯 收益一件沒少:純字母 >= 4 碼而現行三塊撈不到的 363 種 ⇒ 相等式接得住 363 種(363/363)
🎯 噪音上界:整個庫裡, 一個純字母詞用相等式最多拉【1 件】(ADLAU=1 · ADLB=1 · ADLBU=1 …)
   對照:包含式是 727
```
📌 **⇒ 同樣的收益,噪音從 727 降到 1。** 這一格是量出來的,不是設計品味。

### 3-3 🔴🔴 `>= 4` 留著 —— **而它的理由今天倒了【兩次】,第三次我不編了**

```
第一個理由(v1)  守 cap 1000 懸崖              ⇒ ⛔ 死碼, 2026-09-07 拿掉
第二個理由(v2 初) L=4 727 / L=3 3,649 ⇒ 5 倍懸崖 ⇒ ⛔ 族群錯了(codex R2 nit, 而他對)
```
🎯 **第二個錯在哪**:那把尺量的是**純字母**窗格,而純字母改走**相等式**之後
**這道長度閘只剩「含數字」那一族會經過它** ⇒ 📌 **量的族群與受管的族群不是同一個。**

🔬 **量對族群之後(含數字 且 (含字母 或 ≥7 碼),2026-09-10 唯讀正式庫):**
```
L=2  最大 3,894 (N0)        L=4  最大 3,606 (PRN0)
L=3  最大 3,607 (RN0)       L=5  最大 3,065        L=6  最大 933
```
🛑 **4 掉到 3 沒有懸崖 —— 3,607 對 3,606,是平的。**

🔬 **它實際擋掉什麼**(該詞經第 ④ 塊會多拉幾件 / 第 ① 塊本來就有幾件):
```
1B  1,021 / 150      A1  950 / 926      N0  3,894 / 3,851      R1  743 / 1,565
⇒ 真正新增最多的是 1B(約 +871), 而那不是客人會打的詞
```
✅ **⇒ 所以這道閘留著的理由是【它不在本片範圍】,不是「它守著什麼」。**
🛑 **不要再替它編第三個理由。** 要動它就自己量一次,而那是另一片。
🔵 而相等式那一支**根本不需要它**(相等式上界實測 = 1 件)⇒ 對純字母它是多餘的。

### 3-4 🔴🔴 延遲 —— v1 這一格講反了

v1 逐字:「放寬入口閘**不改變掃描方式** —— 它只讓更多詞進得了那一塊。」
**實測(`EXPLAIN ANALYZE`,正式庫唯讀):**
```
今天 · 純字母詞 NINJA   Result → One-Time Filter: false        Execution Time  0.035 ms
放寬 · 純字母詞 NINJA   Seq Scan on product_variants           Execution Time  126.209 ms
放寬 · 相等式   ADLA    Seq Scan, Rows Removed by Filter 61155 Execution Time  124.871 ms
對照 · 含數字   PET52R  Seq Scan(今天就在掃)                 Execution Time  124.576 ms
```
🎯 **今天純字母詞的成本是【零】** —— PG 在計畫期就把閘證成 false,那一塊**整個不執行**。
🔴 **放寬之後它變成一次全表掃,+125 ms,而那是每一發搜尋都付。**
📌 **⇒ 真正的代價不是「更多詞進來多掃幾次」,是「本來一次都不掃的那一族,現在每次都掃」。**
🔵 誰會踩到:**只有 Latin 字母 >= 4 碼的詞。中文詞不受影響**(唯讀驗過:`'煞車' ~ '[A-Za-z]'` = `f`)
　⇒ 客人打中文仍然是 0.035 ms 那條路。
🔴 **而「每次」不只一次(codex R2 nit,他跑實際 TS 加模擬 RPC 數的)**:
`apps/storefront/src/lib/products.ts:566` 那條路,**尾頁會發 2 次、新品無結果會發 3 次**,
每次帶相同 `p_terms`;搜尋疊層經 `/api/search` 也呼叫同一支 helper。
⇒ 📌 **125 ms 是【一次】的數字,不是一個 request 的數字。** ⚠️ 而逾時**沒有實測** ⇒ 不宣稱「整頁多 375 ms」。

⚠️ **升級路徑(不是本片)**:相等式吃得到 **btree 運算式索引**
　`ON product_variants (upper(regexp_replace(sku,'[^A-Za-z0-9]','','g')))` ⇒ 125 ms 會變成索引查找。
　`pg_trgm` 也已經裝了(唯讀確認)⇒ 包含式那一支要救也有路。**兩者都要一支新 migration ⇒ 另一片。**

## 4. 改什麼(最小)

```sql
-- 20260906900000:184 第 ④ 塊的入口閘
-- 現在
   t.term ~ '[0-9]'
   AND ( t.term ~ '[A-Za-z]' OR length(正規化) >= 7 )
   AND length(正規化) >= 4
   AND upper(正規化(pv.sku)) LIKE '%' || upper(正規化(t.term)) || '%'
-- v2 建議
   ( t.term ~ '[0-9]' OR t.term ~ '[A-Za-z]' )              ← 放寬:純字母也算料號
   AND ( t.term ~ '[A-Za-z]' OR length(正規化) >= 7 )        ← 不動(見 §7 第 1 條)
   AND length(正規化) >= 4                                   ← 不動, 而【新理由】見 §3-3
   AND CASE WHEN t.term ~ '[0-9]'
            THEN upper(正規化(pv.sku)) LIKE '%' || upper(正規化(t.term)) || '%'   -- 含數字:包含式
            ELSE upper(正規化(pv.sku))  =        upper(正規化(t.term))            -- 純字母:相等式
       END
```
🔬 **這個形狀 2026-09-10 在正式庫唯讀跑過整支**:`ADLA` ⇒ 1 · `PET52R` ⇒ 1 · `FIRE` ⇒ **0**。
🔴 三支一起改?**不用** —— 本片只動 `storefront_search_product_ids` **一支**,兩支目錄 RPC 不動(它們只是消費它)。
⚠️ migration 號段 **`…07xxxx`**;實作時**當場重跑撞號閘**,不沿用本 plan 猜的號碼。

  ⇒ 📌 **363 這個數字回答的是「庫裡有幾種搜不到」,不是「有幾個客人搜過」。**
