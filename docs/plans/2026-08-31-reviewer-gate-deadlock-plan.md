# Plan:兩道規矩把 commit 的出口鎖死 —— 而它【是真的】,我複現了

> 線【出貨】`-1e` · 板上落點 `⟦b9-GATEDEADLOCK1⟧` · Sean 批「甲 授權我們改那道閘」

> 🛑 **本檔是提案,一行閘都沒動。改守門是所有改動裡最容易造成【全隊停擺】的一種。**

## 0. 🔴 第一步不是改,是【證明那個鎖死是真的】—— 而它是

主視窗交代:今天已有 20 列的前提不成立,所以先證。**我證了,而且是複現不是引用。**

```
拋棄式 repo(env -u GIT_DIR,不碰共用樹)· 一支只印 write-tree 的 pre-commit hook
① 我 stage 兩支檔 ⇒ 我這一側 `git write-tree` = 0fe6fde7…
② `git commit -m … -- A.txt`(帶 pathspec)
   ⇒ **hook 裡** `git write-tree` = **a9c9fd34…**   ← **不一樣**
   ⇒ **hook 裡** `GIT_INDEX_FILE` = `.git/next-index-66042.lock`  ← **暫時 index**
③ 對照:**不帶** pathspec 時 ⇒ 兩者 **d90826a8… 逐字相同**
```
✅ **⇒ 死結成立,而它的觸發條件是【帶 pathspec】。**
📌 而閘的判準是 `.husky/reviewer-gate.sh:150` `now_staged=$(git write-tree)`
⇒ 它拿到的是**暫時 index 的 tree**,而標記釘的是**我寫標記那一刻的真 index tree** ⇒ 對不上。

## 1. 🔵 而它為什麼【今天沒有咬到我】—— 這一格解釋了為何前提看起來像不成立

**我今天用 `git commit -F … -- <pathspec>` 成功了約十次。** 而那不是因為閘被修好了:
```
我每一次的 index 裡【只有我自己那幾支檔】
⇒ 暫時 index == 真 index ⇒ 兩個 tree 逐字相同 ⇒ 閘放行
```
🔴 **⇒ 死結只在【index 裡還有別人的檔】時發生 —— 而那正是 `規矩A` 要求帶 pathspec 的那個條件。**
📌 **⇒ 兩條規矩不是「各自都對而合起來壞」,是【它們的觸發條件是同一個】** ——
**別人有檔在 index ⇒ 規矩A 叫你帶 pathspec ⇒ 帶了就撞閘B。**
⚠️ **⇒ 所以「我今天用了十次都沒事」是【最誤導的那種證據】** —— 它為真,而它取樣的是死結不成立的那個世界。

## 2. 🛑 而最自然的修法【行不通】,我試過

```
想法:閘改成讀【真 index】的 tree ⇒ 就與標記對得上了
實測(同一支 hook 裡):
  GIT_INDEX_FILE=$GIT_DIR/index git write-tree
  ⇒ fatal: Unable to create '…/.git/index.lock': File exists.
  🔴 commit 期間真 index 被鎖著 ⇒ **write-tree 需要寫 lock ⇒ 拿不到。**
```
📌 **⇒ 一個看起來一行就能解的問題,那一行在這個時點是被鎖住的。**

## 3. ✅ 而有一條【唯讀】的路,我量到它可行

```
GIT_INDEX_FILE=$GIT_DIR/index git ls-files -s   ← 唯讀, 不需要 lock
實測(hook 內, 帶 pathspec 的 commit 進行中):
  真 index 指紋   = 9296b8a62dcc99ee   ← **與我 commit 前算的逐字相同**
  暫時 index 指紋 = d4e6aab801f1e115   ← 不同
  對照:同一發 `git ls-files` 讀真 index ⇒ 7 條 / 讀暫時 index ⇒ 6 條 ⇒ **兩邊真的不同**
```
⇒ **修法方向**:閘與標記**兩邊都改用同一個唯讀指紋**(`ls-files -s` 的雜湊),不再用 `write-tree`。
🛑 **而這是【方向】不是成品** —— 它要動 `.husky/reviewer-gate.sh` 與 `scripts/write-reviewer-marker.sh`
**兩支必須同一顆 commit 改**,否則舊標記與新閘互不認得 ⇒ **那本身就是一次全隊停擺。**

## 4. 🔴🔴 它壞掉時全隊怎麼繞過去(主視窗指名要這一節)

```
🛑 **不能是 `--no-verify`** —— 板上那一列自己寫著:
   「誠實的人會停下來等, 而不誠實的人會用參數跳過守門」
   ⇒ 一道把正路關死的閘, 會把流量推向它自己的盲區。
```
✅ **⇒ 所以修法必須自帶【三態】,照本 repo 既有成例**(`scripts/greenlight.sh` 的 `GREEN/RED/ENV-FAIL`):
```
PASS      標記在, 指紋對得上           ⇒ 放行
BLOCK     標記不在 / 理由沒寫          ⇒ 擋(這是它該擋的)
ENV-FAIL  🔴 **閘自己算不出指紋**(讀不到 index、git 版本不吃那個旗標、環境怪)
          ⇒ **放行, 而且印一行很吵的字**, 並把「本次未驗」寫進一個檔
          ⇒ 📌 **「我擋不住」與「你沒審」是兩個宣稱, 而今天它們印同一個紅。**
```
🔴 **而 ENV-FAIL 選【放行】是刻意的**:這道閘擋的是「忘記審查」——
一個**忘記**的人不會因為多擋一天而改變行為,而**全隊停擺的代價是即時且全面的**。
⚠️ **而這個取捨要 Sean 或主視窗拍板,不是我能定的** —— 它把一道守門的失敗方向翻過來。
