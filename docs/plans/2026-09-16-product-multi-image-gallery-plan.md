## 1. 匯入端:要動哪幾行、資料會變多少

- 派工單指的那一行:`scripts/rpm-transform.ts:509` `images: [repImage]` —— 它決定的是**群層 `products.images` 只留一張**。
- 🔴 **但它不是相簿的瓶頸**(§0 A3/A4)。把它改成收完整陣列,**相簿不會多出任何一張圖** —— 因為那些圖已經從變體層進去了,而相簿有 `Set` 去重。
- **資料量估算(⚠️ 估算,不是實測)**:群層若改存完整陣列,最壞情況是把變體層的 176,112 張在群層**再存一份** ⇒ `products.images` 從 25,402 個網址變成約 **17.6 萬個**(≈ **7 倍**)。
  以每個網址約 90 bytes 估:約 2.2MB → **約 15.8MB**(只算字串本身,不含 jsonb 額外開銷)。
  🔵 1d 給的報價單端平均(rpm 12.64 / materya 9.31 / wrs 7.57)是**同一件事的另一個量法**,量級吻合。
- ⇒ 🎯 **建議:這一行先不要動。** 它的收益是「群層自己也有完整清單」,而**目前沒有任何一個畫面需要那個**;代價是資料×7 與一條新的同步不一致風險(群層與變體層兩份要一起對)。
  要動的話理由應該是**別的需求**(例如卡片想輪播),不是相簿。

## 5. 風險:多圖**確實**會拖慢商品頁 —— 這是本片唯一的真工作

🔬 **實測(手機 390,正式站,各跑一次)**:

| | 對照:3 張圖(`extreme-duc-v4080`) | 圖最多:122 張(`dna-dna-204`) | 倍數 |
|---|---:|---:|---:|
| `<img>` 元素 | 14 | **261** | 18.6× |
| **一開始就抓的圖** | 7 | **126** | 18× |
| 傳輸量 | 48 KB | 168 KB | 3.5× |
| DOMContentLoaded | 433 ms | **899 ms** | 2.1× |
| load | 1,317 ms | **3,074 ms** | 2.3× |
| 最慢的單張圖 | 957 ms | **2,196 ms** | 2.3× |

- 🔴 **根因**:hero 的 **122 張 slide 全部進 DOM 且沒有 `loading="lazy"`**(縮圖列有 lazy、hero 沒有)⇒ 一開頁就抓 126 張。
  碼的位置:`ProductGallery.tsx:205`(hero `<img>`,無 loading 屬性)vs `:256-260`(縮圖 `<img>`,有 `loading="lazy"`)。
- 🎯 **建議做的就是這一件**:hero 只即時載「目前這張 + 前後各一張」,其餘捲到 / 滑到再載(或照 Q13-1 甲限制張數)。
  ⚠️ 🔴 **第一張不可以 lazy** —— 它就是商品頁的 LCP(昨天才調好的那個),改錯會把 LCP 弄壞。
- **佔位圖混進相簿**:目前**沒有**(122 張那件實測 0 張;兩道濾網見 §0 A6)。
  全站有 **576 件**商品的變體圖裡含佔位圖、其中 **43 件**是「真圖與佔位圖混在一起」⇒ 這 43 件正是濾網在擋的,**改動後要回頭驗這 43 件**。

## 6. 影響 / rollback / 驗收(若批准做 §5 那一件)

- 影響面:只有商品頁相簿的**載入時機**,不動資料、不動 schema、不動匯入 ⇒ **沒有 migration**。
- Rollback:單一 commit revert(純前端)。
- 驗收:
  1. `dna-dna-204` 手機 390:一開頁抓的圖 **從 126 降到個位數**,而**滑到第 N 張時那張要出現**(不能只是變快卻看不到圖)。
  2. **LCP 不變差**(與改前同一台、同一網路各跑 3 次比中位數)。
  3. 那 **43 件混合商品**相簿裡**仍然 0 張佔位圖**。
  4. 「01 / 122」這個總數**不變**(只改載入時機,不改張數;除非 Q13-1 選甲)。
