## 2. 🔬 數字全部量過(不是推的)

```python
# 1..20,000 的含稅金額
整除(今天表單收得下來)   952 個  ⇒ 📌 收件率 4.8% ⇒ 【拒收 95.2%】
兩種算法分岔(殘差 vs 正推) 952 個  ⇒ 與那支 migration 檔頭逐字的「952 個金額差一塊」對上
🔴 交集 = 0                        ⇒ 整除就不會分岔 ⇒ 兩個 952 是【同分母的巧合】(20000/21 = 952.4)

湊不湊得回員工打的那個數:
   殘差法 湊不回 = 0     🟢 而那個 0 是【結構上必然】:(t − u) + u ≡ t,不是量出來的巧合
   正推法 湊不回 = 952
```
⇒ 🎯 **「用減的」的意思就是這個:不是四捨五入回去,是【湊回原數】。**

**Sean 那個例子逐格**:
```
含稅 1,100 ⇒ 未稅 round(1100×20/21) = 1,048 · 殘差 = 1100 − 1048 = 52
           ⇒ 小計 1,048 + 稅 52 = 1,100   ✅ 湊得回
qty 2 / 3 / 7:小計 2096+104 / 3144+156 / 7336+364 ⇒ 2200 / 3300 / 7700 ✅ 全部湊得回
   (那支 migration 逐字「殘差跟著那一列走、乘以數量」)
```
⚠️ **而 1,100 這個例子【不是判別格】** —— 它在正推法下也剛好給 1,100。
📌 **要判別得挑分岔的那 952 個**,例如 `含稅 11`:殘差 ⇒ 10+1 = **11** ✅ · 正推 ⇒ 10+0 = **10** 🔴。

## 3. 修法(三件,**同一片**)

```
甲  ManualOrderLineInput 加【選填】unit_price_taxed;表單在【含稅 + 勾發票】時送它
    · untaxedFromTaxed 那個「整除才收」的拒收【拿掉】—— 改成 round(含稅×20/21)
      ⇒ 那正是 Sean 2026-09-10 拍的「Q2′ 甲 = 改成用減的」, 而殘差就在 RPC 裡等著
    🛑 而【不要在表單裡自己算稅】—— 算在 server, 瀏覽器只預覽。那是既有分工, 不破壞它
       (表單算的是「這一列的未稅」, 那是 RPC 要求呼叫端送、而它自己會再驗一次的東西)

乙  manual-order-total-preview.tsx:90 的 get() ⇒ 改成與另外兩處同一條規則(getAll 取最後)
    🔵 而預覽也要跟著會算殘差:含稅 1100 + 勾發票 ⇒ 預覽印【1,100】不是 1,155

丙  🔴 而主視窗要我答的那一格:那個讀法能不能【只有一支】?
    ⇒ ✅ 能, 而【型別對得上是量過的不是推的】:
      `readInvoiceRequestedFromForm(form: HTMLFormElement)`(`manual-order-form.ts:90`)
      而預覽那支的 `readPreview(form: HTMLFormElement)`(`:68`)⇒ **同一個型別**。
      🔵 而它已經被【另一支 client 元件】叫著(逐列比價 `:250`)⇒ **預覽改叫它即可, 不必新抽。**
      🔵 順帶撿到一格:逐列比價那支對 `null` 的處理逐字是「**那一格壞掉了 ⇒ 不說話**」
         ⇒ 📌 預覽也該照做(判不出來就不要編一個總額出來), 而不是把 `null` 當成 `false`。
    🛑 而 server 那一側(:825)【叫不到它】—— 它拿的是 server action 的 `FormData`,
      不是 `HTMLFormElement`, 型別就不同。
      ⇒ 📌 **所以「只有一支」做得到【兩處】而不是三處, 而第三處必須明寫為什麼**。
    🔵 可做也可不做:把「取最後 + 只認 on/off」那幾行抽成一支吃 `FormData` 的純函式,
      三處都叫它。⚠️ 而那會動到 server 那條錢路徑 ⇒ **建議本片不做, 另開一片**。
```

**推薦:甲 + 乙同一片;丙只做「預覽改叫既有那支」那一半,抽共用函式另開。**
理由:甲乙不做完整套,Sean 看到的數字仍然是錯的;而丙的後半碰 server 錢路徑,**不該搭這班車**。
