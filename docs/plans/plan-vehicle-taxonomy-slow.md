🎯 **而這一格反過來幫【乙】**:拉長 TTL 正是在減少冷快取次數。

## 1. 量到的骨架(全部唯讀實查,2026-09-11)

```
vehicle_taxonomy_public   relkind = 'v'  ⇒ view, 沒有任何實體儲存
輸出                       12,340 列
輸入                       product_fitments 193,058 列 + product_fitments_effective 280,742 列
快取                       Next unstable_cache · revalidate = 60 秒 · tags = ['catalog']
索引                       ix_pf_lookup / ix_pfe_lookup 都在, 而且 EXPLAIN 顯示兩邊都在用
```

**`EXPLAIN`(只規劃、未執行)的成本分布:**

```
Merge Append                              129,259
├─ Unique ← Index Only Scan pf              5,281   ( 4.1%)
└─ Unique ← Nested Loop Anti Join         123,780   (95.8%)   ← 🔴 這裡
      估計產出 rows = 314
```

🎯 **一句話:95.8% 的成本花在找出那 ~314 列,而那是 12,340 列裡的 2.5%。**
✅ 與 `cache_hit_rate 99.99%` 對得上 —— 不是在等磁碟,是 28 萬次索引探查在算。

⚪ **「加索引」這條路已經關掉**:`index_advisor_result` 全 null,而 `EXPLAIN` 證實兩邊
本來就走 Index Only Scan ⇒ **沒有索引可加,成本是這個【形狀】本身帶來的。**

📌 **而有一句是這個 plan 的支點:那 12,340 列,每一次算出來都長得一模一樣。**
它只在供應商型錄同步之後才會變。

## 3. 選項(四個,含「什麼都不做」)

### 甲 · 什麼都不做

| | |
|---|---|
| 客人感覺得到什麼 | 首頁選車維持現狀:快取命中 0ms,快取過期那一次約 0.5 秒 |
| 資料多久變 | 不影響 |
| 碰 schema | ❌ 零 |
| 壞掉的形狀 | 沒有新的。既有的形狀是:上線後客人變多 ⇒ 每 60 秒就有人吃到那 0.5 秒 |
| **它會不會叫** | 🔴 **不會。** 慢不會紅、不會告警;只有人去看 Query Performance 才看得到 |
| rollback | 不適用 |

🔵 **它的代價,照分母寫**:今天真客人 **0 人** ⇒ **半秒沒有人在等**。
🔴 **而它的代價會隨上線長大**:60 秒快取 + 多個 serverless instance
⇒ 尖峰時**每分鐘每個 instance 各吃一次 0.5 秒**,而那是客人進站的第一個動作。

---

### 乙 · 只拉長快取,不碰資料庫

把 `CATALOG_REVALIDATE_SECONDS`(現行 60)對**車款那一支**單獨拉長(例如 1 小時),
並在供應商同步完成後打 `revalidateTag('catalog')`。

| | |
|---|---|
| 客人感覺得到什麼 | 0.5 秒那一次從「每分鐘」降到「每小時」⇒ 幾乎沒有人會遇到 |
| 資料多久變 | 🔴 **要 Sean 答甲**。答乙則必須接主動失效,否則最久晚 1 小時 |
| 碰 schema | ❌ 零 migration。只動 storefront TS 一個常數 + (可選)一個失效端點 |
| 壞掉的形狀 | 🔴 **快取沒失效 ⇒ 客人看到舊車款,而畫面完全正常** |
| **它會不會叫** | 🔴 **不會。** 這正是昨晚整晚在抓的那一格 |
| rollback | 改回 60,重新部署。**一顆 commit revert,零資料風險** |

⚠️ repo 自己已經標過這條路的債:`products.ts:121-125` 逐字「**這是止血不是治本**」,
且「接 `revalidateTag('catalog')` 要新增端點 + 密鑰、**命中鐵則 12④**」。

### ⛔ 丙 · Materialized View(實體化那 12,340 列)+ 排程刷新 —— **已出局**

> 🛑 **Sean 2026-09-11 拍 Q1 乙 + Q2 甲之後出局。**
> Q1 乙 = 只拉長快取、不碰資料庫;Q2 甲 = 一天變一次、隔天生效可接受
> ⇒ 丙 要的 migration + 新排程,買到的是「幾毫秒」,而甲已經把「半秒」降到每小時一次。
> 🔵 **不刪這一段** —— 下一個人上線後看到真實流量、覺得每小時一次仍然太多時,
> 這裡有現成的成本與壞法,不必重想一次。**要復活它,先回去看 §1 那個 95.8%。**

| | |
|---|---|
| 客人感覺得到什麼 | 0.5 秒 ⇒ 個位數毫秒(變成讀一張 12,340 列的小表) |
| 資料多久變 | 跟著刷新排程走。甲 ⇒ 一天一次;乙 ⇒ 同步完觸發刷新 |
| 碰 schema | 🔴 **要 migration**(建 matview + 索引 + GRANT + 刷新排程)⇒ **鐵則 8 + 鐵則 12** |
| 壞掉的形狀 | 🔴 **刷新的 cron 死掉 ⇒ 車款永遠停在某一天,而畫面完全正常** |
| **它會不會叫** | 🔴 **預設不會。** 除非另外做一格「上次刷新時間超過 N 小時就叫」 |
| rollback | matview 與 view 可並存:先建 matview、不改任何讀取端;確認正確後才切讀取端。**切回去 = 改一個名字** |

🔵 它把「每次現算」換成「每天算一次」,而那正好對上「12,340 列每次都一樣」。
🔴 而它引入一個**新的活體**(刷新排程),而那個活體死掉的症狀是**安靜的**。
