## §2 算式

```
稅基     = subtotal + shipping_fee − discount_total      ← ②③④
tax_total = ROUND(稅基 × 0.05)
total     = subtotal + shipping_fee − discount_total + tax_total
          = 稅基 + tax_total
```

🔴 **`ROUND` 的方向要寫死並測**:`ROUND(x)` 在 Postgres 對 `.5` 是**四捨五入到偶數**還是**遠離零**,
依型別而異(`numeric` 是遠離零,`double precision` 是銀行家捨入)。
⇒ ✅ **一律先轉 `numeric` 再 `ROUND`**,並用 `x.5` 的世界寫一格測試釘住它。
### 🔴 三個邊界(codex #1),而每一個都要在函式裡**明確擋**,不是靠 CHECK 事後炸

1. **稅基為負**(折扣 > 小計 + 運費)⇒ 稅會是負數 ⇒ 🛑 **函式要當場 `RAISE`,不要算下去。**
   ⚠️ 靠 `orders_total_balances` 擋 ⇒ 錯誤訊息是**約束名**, 員工看不懂是哪一格。
2. **加稅後溢位**:`total` 是 `integer`(上限 2,147,483,647)⇒ 稅加上去可能越界
   ⇒ 既有 `create_order` 已經有這道(`20260604130000:229` 逐字 `IF v_total > 2147483647`)
   ⇒ ✅ **本片照抄同一道, 不自創第二種**。
3. **負運費** ⇒ 建單 RPC 已擋(`p_shipping_fee < 0` ⇒ RAISE),**沿用**。

### 🔴🔴 而 ④ 折扣那一條:**它今天不可達**(codex #2)

🔬 實查:建單 RPC 的 `INSERT` 逐字 `v_subtotal::integer, p_shipping_fee, 0, v_total::integer`
(`20260905130000:594`)⇒ **`discount_total` 是寫死的 0**, 函式**收不到折扣**。
⇒ 🛑 **所以「折扣在稅前」這條規則在本片【沒有任何一條路走得到】** ——
   而 §6 的測試 #3 **造不出那個世界**。
⇒ ✅ **兩個選項, 而我選後者**:
   · ~~把折扣寫進算式並留一格永遠測不到的測試~~ ⇒ 那是一格**恆綠**的裝飾
   · **算式寫成 `subtotal + shipping_fee − discount_total`(它天生正確, 而今天那一項恆為 0),
     並在註解裡逐字寫「折扣路徑今天不存在 ⇒ 這一項未被任何測試涵蓋」**,
     §6 把 #3 標成**待折扣功能存在後才可測**。
   📌 **不要為了讓表格好看而寫一格造不出來的世界。**

⚠️ **本 plan 不替 `ROUND` 決定方向** —— 見 §7(而那一題的答案不是二選一, 見該節)。

## §3 🔴🔴 新舊單分不出什麼 —— **而我第一版把它講錯了**

⛔ ~~舊單 `tax_total = 0` 而 `total` **含稅**;新單 `total` = 稅基 + 稅 ⇒ 兩種單的 `total` 意思不同~~

🔴 **codex 2026-09-05 關卡 1 抓到,而它是對的**:
**兩種單的 `total` 意思【一樣】** —— 都是**客人要付的、含稅的那個總數**。
· 舊單:單價含稅 ⇒ `subtotal` 含稅 ⇒ `total = subtotal + 運費 − 折扣 + 0`
· 新單:單價未稅 ⇒ `subtotal` 未稅 ⇒ `total = subtotal + 運費 − 折扣 + 稅`
⇒ ✅ **兩邊的 `total` 都是同一個東西。差的是 `unit_price` 與 `subtotal` 含不含稅。**

📌 **我錯在哪,寫下來**:我從「`tax_total` 從 0 變成非 0」推出「`total` 的語意變了」——
而那一步**沒有量,只是聽起來很順**。⇒ ⇒ **一個講得通的推論,在錢的算式上與量過的事實一樣有說服力。**

### ⇒ 所以真正分不出的是這個

**`subtotal` 這個數字含不含稅** —— 而它今天沒有任何欄位說得出來。
🛑 **誰會被它咬到**:任何**拿 `subtotal` 去反推稅**、或**拿 `unit_price` 去比價**的人
(報表、對帳、退款算式、匯出 CSV)。⇒ 而 `tax_total = 0` **分不出**
「舊單(價含稅)」與「新單但真的免稅(稅基 0)」。

### 甲 · 加一個欄位說明「單價是含稅還是未稅」(建議)

🔴 **而它【不叫 `tax_basis`】**(codex #3):`tax_basis` 在 §2 已經是**一個數字**的名字
(稅基 = 小計 + 運費 − 折扣)⇒ **同一個詞指兩個東西, 而它們都會出現在退款與報表裡。**
✅ **改叫 `price_tax_mode`**,值域封閉兩值:
```
'inclusive'  單價含稅(顧客站, 與今天所有既有單)
'exclusive'  單價未稅、稅另計(本片之後的後台手動單)
```
🔴 **必須配一條封閉值域 CHECK**(codex #4)—— 沒有它,**拼錯字也進得去**,
而一個拼錯的值會被每一個讀它的人當成「不是這兩種」而各自處置。
🛑 **DEFAULT 要設 `'inclusive'`** —— 而那代表**任何沒被改過的 writer 寫進來的單會【自稱含稅】**。
⇒ ⚠️ **那不是安全的預設,那是一個會說謊的預設** ⇒ 📌 **所以本片必須同時盤點【所有寫 orders 的路徑】**
(§5-6),而不是只改建單那一支。

| | 甲(加欄) |
|---|---|
| ✅ | 它是**一個宣稱**,不是推論 —— 讀那一列就知道 `subtotal` 是什麼 |
| ✅ | 免稅單與舊單**分得開** |
| ⚠️ | 一支 `ALTER TABLE ADD COLUMN` ⇒ `admin_order_list_v` 會再落後一欄(§5) |
| 🔴 | DEFAULT 會讓沒改到的 writer **靜靜冒充含稅** ⇒ 要盤點所有 writer |
