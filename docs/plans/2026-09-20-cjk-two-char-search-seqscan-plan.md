# 中文兩字以內搜尋撞爆 3 秒上限 —— plan(鐵則 8,等 Sean 批)

> 板列 `⟦search-CJK2CHARTIMEOUT⟧`(`docs/launch-todo.md`)。
> 線 `-17` 2026-09-20 寫;2026-09-21 補 §8(migration 已寫好、本機驗證通過,等 Sean 批准貼到正式庫)。

---

## 0. 一句話

客人打「煞車」「拉桿」這種**兩個字**的中文詞,搜尋要等 **3–5 秒**;打三個字只要 **0.3 秒**。
成因是 **`pg_trgm` 索引在 2 字元以下用不上** ⇒ 整張 `products`(26,533 列)全表掃。

---

## 1. 為什麼(讀數,兩把互相獨立的尺)

**尺 A —— 客人那一端的延遲**(Vercel runtime log,`n=99`,2026-09-17 12:07Z – 09-19 21:18Z)

```
qlen 1    n= 6   中位 4,844 ms
qlen 2    n= 5   中位 3,020 ms
──────────────── 懸崖 ────────────────
qlen 3    n=16   中位   325 ms
qlen 4-6  n=13   中位   255 ms
qlen 7+   n=59   中位   310 ms
```

- 99 筆裡帶 `[searchProducts] 資料庫逾時(57014)⇒ 重試一次` 的 **6 筆**,`qlen` 是 **2·1·1·2·1·1 ⇒ 全部 ≤2**;`qlen ≥3` 的 88 筆 **0 筆**。三個不同時間、三個不同部署。
- ⇒ 那 3–5 秒 = **PG 的 3,000 ms `statement_timeout` + 重試那一發**。

**尺 B —— 資料庫那一端的計畫**(正式庫 `EXPLAIN`,唯讀,**沒跑 `ANALYZE`**)

```
詞             計畫                                  cost
碳(1 字)      Seq Scan on products                 0.00..8679.66
煞車(2 字)    Seq Scan on products                 0.00..8679.66
排氣管(3 字)  Bitmap Heap Scan + BitmapOr ×4       113.38..2022.86
```

3 字那一發的 `BitmapOr` 底下四支 trgm 索引全命中;1 字與 2 字**一支都沒出現在計畫裡**。

🎯 **兩把尺沒有共用任何來源,而它們指到同一個切點(2 與 3 之間)。**

**受詞確認**:`splitSearchTerms(q)` 對中文不切詞(`product-query-support.ts:89` 逐字「本函式不做中文斷詞」)⇒「煞車」= 一個詞兩個字元 ⇒ 進 `storefront_search_product_ids` 的 **hits 區塊①**(`title` / `subtitle` / `description` / `external_id` 四欄 `ILIKE`)。料號區塊③對中文詞是 `never executed`(函式註解 + EXPLAIN 兩邊背書)⇒ **慢的不是料號那塊。**

---

## 2. 改什麼 —— 三條路,而其中一條已經被讀數淘汰

### 丙:短詞只比 `title` + `subtitle`(不比 `description`)⇒ 🔴 **實測否決,不要做**

```
EXPLAIN 只比 title+subtitle ⇒ Seq Scan  cost 0.00..8547.00
對照 四欄                   ⇒ Seq Scan  cost 0.00..8679.66
⇒ 只便宜 1.5%,而它【仍然是全表掃】
```
代價卻是實的(`delisted_at IS NULL` 下的命中數):

```
詞     四欄    只前兩欄   少掉
煞車   2,618   2,038      -22%
拉桿   3,211   2,989       -7%
```

📌 **⇒ 省不到時間,而少給客人兩成結果。這一條寫在這裡是為了讓下一個人不要再想一次。**

### 甲:裝 `pgroonga`,對 CJK 建可用於 1–2 字的索引

```
🔬 pg_available_extensions 實查:pgroonga 3.2.5 **可裝、未裝**;pg_bigm **不在清單裡**
```

- 優點:PGroonga 就是為 CJK 子字串搜尋做的,1–2 字有索引可用。
- 缺點:**在正式庫裝一個新擴充**,影響面遠大於一支索引;要 Sean 批、要評估 Supabase 那一端的支援與升級路徑。
- 🛑 **我沒有實測它在這張表上的效果** —— 沒裝過,不能宣稱它會快。

### 乙:自建 bigram 欄 + GIN(不裝新擴充)

把 `title`/`subtitle`/`description`/`external_id` 串起來,切成 **2-gram 的 `text[]`**,做成 generated column,對它建 `GIN (… array_ops)`;區塊① 在 `length(term) <= 2` 時改用 `bigrams @> ARRAY[term]`。

- 優點:不動擴充,全部在我們自己的 schema 裡。
- 缺點:**新欄位 + 新索引 + 改一支 SECURITY DEFINER 函式**,三樣都要審。
- 🛑 **索引大小沒量** —— 估:`description` 平均 94 字元 ⇒ 每列約 93 個 bigram × 26,533 列 ≈ 2.5M 筆。現況 `products_description_trgm_idx` 是 **22 MB**,`products` 表 67 MB、索引合計 62 MB。**新索引可能是同一個量級,而我沒有量,寫「未量」。**

**建議**:**乙**。理由是它不動平台擴充,爆炸半徑留在我們自己的 schema 裡;而甲留著當乙做不出效果時的下一步。
🛑 **而這是建議不是拍板** —— 甲乙都碰 DB 物件,兩條都要 Sean 批。

## 3. 影響

- **前台**:客人打兩字中文詞從 3–5 秒變快(**幅度未量**,見 §5)。三字以上**不應該變**(它們今天就走索引)。
- **後台**:不碰。`storefront_search_product_ids` 只有顧客站在用(區塊①的四欄是 `products_public` 的欄位)。
- 🆕 **這一改會不會讓別的查詢變慢 / 變大**:
  - **寫入**:乙案的 generated column 會在**每一次商品新增 / 改標題 / 改描述**時重算 bigram 陣列並更新 GIN 索引 ⇒ **上架與同步那條路會變慢**。🛑 **沒量** —— 要知道有多慢,得先做出來量。
  - **儲存**:多一支索引,**大小未量**(估算見 §2 乙)。今天 `products` 索引合計已經 62 MB > 表本身 67 MB 的九成。
  - **讀取**:三字以上的查詢**不應該**改走新索引(條件只在 `length(term) <= 2` 觸發),但 **planner 會不會自己選它,沒量**。
  - 🔴 **甲案(pgroonga)的影響我完全沒量** —— 裝一個擴充會動到什麼,本檔答不出來。

## 4. Rollback

- **乙**:`DROP INDEX`(`CONCURRENTLY`)+ `ALTER TABLE … DROP COLUMN` + 把 `storefront_search_product_ids` 換回現行定義(先 `bash scripts/latest-definition-of.sh storefront_search_product_ids` 留一份)。
  🛑 **順序**:先把函式換回去(不再引用那一欄),**再**丟索引與欄位 —— 反過來會讓線上的函式當場找不到欄位。
- **甲**:`DROP EXTENSION pgroonga` ⇒ 🛑 **而那會連帶丟掉所有依賴它的索引,影響面比乙大** ⇒ 這是甲要 Sean 批的主要理由之一。

## 5. 怎麼驗它真的好了 —— **用同樣那兩把尺,不要換新的**

```
尺 A(客人那端):修完後同樣撈 Vercel runtime log 的 [api/search],
      判準 = 同一個窗口內 **qlen ≤2 且帶「資料庫逾時(57014)」的筆數 = 0**
      🟢 正對照:同一把尺撈 qlen ≥3 的筆數必須 > 0(否則那個 0 可能是尺撈不到東西)
尺 B(資料庫那端):同一條 4 欄 OR,`EXPLAIN` 兩字詞
      判準 = **不再是 Seq Scan**
      🟢 正對照:三字詞仍然走 BitmapOr(證明沒有把原本好的那半弄壞)
```

📌 **兩把都要,而且要是原來那兩把。** 換一把新尺去驗,會驗到一個沒有比較點的綠。

## 6. 沒做 / 證不到(照抄,不要美化)

1. **沒跑 `EXPLAIN ANALYZE`** —— 那會在正式庫真的跑一次全表掃。**`cost` 是估的,不是實際耗時。** 它與尺 A 方向一致,而那是兩個獨立來源,不是同一個數字。
2. **機制沒實測** —— 「`pg_trgm` 存 3 字元一組 ⇒ 長度 < 3 切不出完整 trigram」這句是**說明**;`extensions.show_trgm()` 唯讀角色 **permission denied**(逐字)。
   🔴 **⇒ 本 plan 的修法【不建立在這句話上】,建立在 §1 尺 B 那三個計畫上。** 若有人要拿「因為 trgm 是 3-gram」去推別的結論,那句還沒證過。
3. **`products_search_fold_trgm_idx`(折疊欄的 trgm)對中文兩字詞有沒有用 —— 未確認。** 區塊①走的是原欄 `ILIKE`,不走折疊欄;但那支索引存在,而我沒有查它。**要做乙案之前應該先查這一格 —— 它可能讓乙案變得不必要。**
4. **甲案沒有任何實測。**
5. **乙案的索引大小、寫入變慢幅度、planner 會不會誤用 —— 三格全部沒量。**
6. `qlen 1` 只有 6 筆、`qlen 2` 只有 5 筆 ⇒ 那兩個中位數**不是精確值**。
7. 撈不到 2026-09-17 12:07Z 以前的 log ⇒ 那是**查詢工具逾時**,**不是 log 不存在**,兩者分不出來。
