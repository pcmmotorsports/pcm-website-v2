## 0. 🔴 先講這件事,因為它決定整支腳本的形狀

`supabase/migrations/20260829190000_m4b_d1restore_audit_source_ops.sql:22` **逐字**寫著:

> 反向(把 CHECK 改回兩值)只在**一列 `source_app='ops'` 都還沒寫進去**時成立;

⇒ 🎯 **這支 migration 的回滾【正確與否, 取決於正式庫裡有沒有資料】。**

⇒ 🛑 **而回滾演練是跑在一個【空的】拋棄式 PG 上的。**
　 在空庫上, 那條反向 SQL **一定會成功** —— 因為沒有任何一列違反舊 CHECK。

📌 **⇒ 空庫上的回滾演練, 對「資料相依的回滾」天生全綠。**
📌 **⇒ 而那正是最危險的那一類:它會給我一張綠票, 去做一件在正式庫上會炸的事。**

🔴 **所以本支腳本【必須】把結果分成兩種, 而不是 PASS / FAIL 兩格**:

| 判 | 意思 | 它證了什麼 |
|---|---|---|
| `REVERSIBLE` | 反向 SQL 跑得動, **且**空庫與有資料兩個世界都跑得動 | 回滾在正式庫上大概率安全 |
| `DATA-DEPENDENT` | 空庫跑得動, **餵一列真實形狀的資料就炸** | 🔴 **有反向 SQL ≠ 回得去** |
| `NO-ROLLBACK` | 檔內找不到反向區段 | 缺口, 列出來 |

⇒ **`DATA-DEPENDENT` 這一格就是本片存在的理由。** 沒有它, 這支腳本只是一台印綠票的機器。

## 2. 要做什麼

### 產出
1. `scripts/rollback-drill.sh`(帶 `--selftest`)
2. 板列一列(錨 `⟦db-ROLLBACKDRILL⟧`), 記分母、三種判、以及「空庫全綠陷阱」那句
3. 一份缺口清單(`NO-ROLLBACK` 的那些), **只列不修** —— 補反向 SQL 是另一件事, 不混進來

### `rollback-drill.sh` 做什麼(一支 migration 一輪)
```
① 起一台拋棄式 PG(沿用 throwaway-postgres 那支 runbook 的 bootstrap)
② 依序 apply 到【這支的前一支】為止        ⇒ 得到「改動前」那個世界
③ 對 pg_catalog 拍一張快照(物件/約束/policy/ACL) = W0
④ apply 這一支                              ⇒ W1
⑤ 跑它的反向區段                            ⇒ W2
⑥ 比 W2 與 W0
   · 相同        ⇒ 候選 REVERSIBLE, 但還沒完 ⇒ 進第 ⑦ 步
   · 不同        ⇒ FAIL, 印出差在哪
⑦ 🔴 資料相依那一關(本片的核心):
   重跑 ②-④, 而在 ⑤ 之前【餵一列這支 migration 放行、而舊世界不放行的資料】
   ⇒ 反向仍成功 ⇒ REVERSIBLE
   ⇒ 反向炸掉   ⇒ DATA-DEPENDENT(這是【正確】的結果, 不是紅)
```

### 第一個實例 = `20260829190000`
- 它沒有反向區段 ⇒ 先落 `NO-ROLLBACK`。
- 而本片**替它寫一段反向**(`CHECK` 改回兩值)當作 ⑦ 的測試檢體:
  餵一列 `source_app='ops'` ⇒ 反向必炸 ⇒ **判 `DATA-DEPENDENT`**。
- 🟢 **這一發同時就是這支腳本的正對照** —— 它證明第 ⑦ 步真的會叫。

### `--selftest` 至少要有的格(每格都要有【它該紅的那個世界】)
| 格 | 該綠 | 對應的該紅世界 |
|---|---|---|
| A | 一支真可逆的 migration ⇒ `REVERSIBLE` | 把反向 SQL 改壞 ⇒ 必 FAIL |
| B | `20260829190000` + ops 那一列 ⇒ `DATA-DEPENDENT` | 🔴 **把第 ⑦ 步整段拔掉 ⇒ 這格必須從 DATA-DEPENDENT 掉成 REVERSIBLE** |
| C | 沒有反向區段的一支 ⇒ `NO-ROLLBACK` | 塞一段假的反向 ⇒ 必須不再是 NO-ROLLBACK |
| D | 期望格數釘子 `EXPECT_TOTAL` | 少跑一格 ⇒ 必紅(⟦db-SELFTESTCELLPIN⟧ 那一族) |

🔴 **B 的紅世界是本 plan 最重要的一格** —— 它就是判別句「把那個功能整段拔掉, 輸出會少哪一行」的答案。

## 4. 🛑 它答不出什麼(先寫, 免得綠票被讀太寬)

1. **拋棄式 PG 與正式庫不是同一個世界** —— 沒有 Supabase 的 roles/extensions/既有資料。
   ⇒ 綠票的射程是「這段反向 SQL 在一個乾淨的 PG 上, 對一個我造的資料形狀, 回得去」。
2. **我餵的那一列資料是我造的** ⇒ 它是不是正式庫真正的形狀, **本片答不出**。
   (⚠️ 這正是 `feedback_my-fixture-drifts-toward-my-conclusion` 那條:**測資由我造 ⇒ 它會長成我要的形狀**。
   　⇒ 修法:每一個測資旁邊註明「對應正式碼 `<檔>:<行>`」。)
3. **N 支的 N 是我訂的** ⇒ 沒被掃到的那 (351−N) 支, **未演練 ≠ 可逆**。
4. `DATA-DEPENDENT` 這個判**不告訴你正式庫現在有沒有那種資料** —— 那要一發唯讀查, 不在本片。
