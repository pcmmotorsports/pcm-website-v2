## 4. 選項(互斥、可執行,而問的是**同一個產品問題**)

> **真正要 Sean 答的是一句話:一件【沒有任何規格可選】的商品,我們到底賣不賣?**

```
Q: 一件沒有規格可選的商品(例:保護貼、護蓋),顧客站要不要賣?
A: 甲 不賣 —— 這種商品不准上架, 後台按上架時當場擋下並說原因
   乙 要賣 —— 讓結帳收得下它(改結帳與 schema, 對齊購物車那一側)
```

### 甲「不賣」⇒ 擋在**上架**那一層
```
· 改哪裡:後台上架動作加一道檢查(零變體 ⇒ 不准上架, 訊息說「這支商品沒有規格, 請先建規格」)
          + 一支測試釘住;可選再加一道 DB 約束當第二道
· 動幾支檔:約 2-3 支(product-listing-actions + 測試)
· 客人看到的差別:**沒有差別** —— 他永遠不會看到這種商品
· 代價:🔴 **員工想賣一件真的沒有規格的東西時, 會被擋住而且沒有出路**
        ⇒ 而今天架上零變體 = 0, 所以這條路今天不影響任何人
· 🔵 它同時把「休眠」變成「真的不會復活」——那顆上架鈕會被擋住
```

### 乙「要賣」⇒ 改**結帳與 schema**那一層
```
· 改哪裡:useChargePayment 那道 `if (!it.variantId)` 放行無變體行
          + `packages/schemas` 的 `variantId` 由必填改成選填
          + 下游建單 RPC 要能收 NULL variant(**未查:那支 RPC 收不收, 要先查**)
· 動幾支檔:至少 4-5 支, 且**跨到金流寫入路徑**(鐵則 12① 錢)
· 客人看到的差別:那種商品可以正常買完
· 🔴🔴 代價(這一格最重要):`variantId: z.uuid()` 現在是一道 **fail-closed 的價格守門** ——
  檔內逐字寫著「顯示路徑有變體缺 variantId … 寫入路徑同情境 REJECT 整單」。
  ⇒ **把它改成選填, 等於讓「有變體的商品掉了 variantId」那個世界也一起通過**,
    而那個世界會回錯價(群價 vs 變體價)。
  ⇒ 📌 **要做乙就必須把兩個世界分開**(「本來就沒有變體」vs「有變體而值掉了」),
    而那是新的判別邏輯, 不是放寬一個 `if`。
```

### 🔵 而我推薦 **甲**,理由是量出來的
```
· 架上零變體 = 0、歷來下單 = 0 ⇒ **乙要付的代價現在沒有人在收**
· 乙動到金流寫入路徑與一道現役的價格守門(鐵則 12①)⇒ 貴且脆
· 甲把「休眠」變成「不會復活」, 而它今天不擋住任何人
🛑 而甲的代價要跟著問題一起講:**哪天真的要賣一件沒有規格的東西, 就要回來改。**
```
