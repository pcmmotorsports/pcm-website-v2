**要動**:`apps/storefront/src/app/checkout/`(`page.tsx` / `charge-actions.ts` /
`checkout-form-types.ts`)+ `create_order` 要收 channel。
🔴 **而 `create_order` 今天的簽名裡沒有 payment_channel** ⇒ 這一段含一支 migration。

**卡什麼**

# 段 2 · 匯款帳號要有一個家

**現況**:🔴 **零載體。** `bank_account|bank_code|匯款帳號|銀行帳號|收款帳戶`
在 packages·apps·migrations ⇒ **0 檔**(🟢 正對照 `notification_email` ⇒ 23 檔);
DB 也沒有任何 setting / config / bank 開頭的表。

**鐵則 9 分級 —— 這一格我判得了, 判 L1**
```
判準是【改動頻率】:公司收款帳戶只在換銀行時變 ⇒ 年 0-1 次 ⇒ **L1, hardcode 可**
```
🛑 **而 L1 有一個代價要明寫, 它不是頻率問題**:hardcode ⇒ 改帳號要**重新部署**。
   ⇒ 🔴 而這是**印在客人信上的收款帳號** —— 印錯 = 客人把錢匯到別的地方。
   ⇒ ✅ 所以這一段的驗收不是「能顯示」, 是 **「那串數字有沒有第二個人對過」**。
**卡什麼**:🔴 卡 Sean —— **他要給那組帳號**(戶名 / 銀行 / 分行 / 帳號)。這不是一個字回得完的,
它是一筆資料 ⇒ 端他的時候要給一張**填空表**, 不是一個問句。

# 段 3 · `expire_unpaid_orders` 依 channel 分流

**現況(對正式庫活函式查的)**:無 channel 濾、`interval '1 day'`。
**要動**:一支 migration,`CREATE OR REPLACE pcm_cron.expire_unpaid_orders`,
把那個 interval 改成依 `payment_channel` 分流。

🔵 **而寫下這條的人已經預告過今天**:`20260809160000_...:66-69` 那一節標題逐字
「重估觸發(Sean 拍板時逐字要求寫死在規格裡)」, 內容逐字
> 開放匯款付款時「1 天」**必須重看** —— 匯款常要 1-3 天, **1 天會把正常等匯款的單殺掉**。

📌 **⇒ 那不是一個過期的數字, 是一個【自己寫下失效條件】的數字, 而今天正是那個條件。**

**✅ 已拍板 —— Sean 2026-09-03 本人逐字回「乙 5天」**

# 段 4 · 下單信本身

四樣資料各自從哪來:
```
訂單編號  ✅ orders.display_id                        —— 已有
金額      ✅ orders 的總額欄                          —— 已有(🔴 整數/Decimal, 禁 number)
匯款帳號  🔴 **段 2 的產出**                          —— 今天不存在
期限      🔴 **段 3 那個數字**                        —— 今天不存在
```
**觸發條件**:`payment_channel = 'bank_transfer'` **且** `payment_status = 'unpaid'`
🛑 **判別要用 `payment_channel`(有 CHECK), 不要用 `payment_method`(零 CHECK、自由文字)。**
🛑 **不得改 `order_created`** —— 它觸發於 `payment_status='paid'`、主旨「付款成功通知」,
   改它 ⇒ **已付款的客人會收到匯款資訊**。

**卡什麼**:段 2 與段 3 都沒有產出之前, 這一段**寫了就是死碼**。
🔴 **而 `email_outbox.event_type` 的第五種【現在不要加】** ——
   加了而沒有寫入端 = 一個永遠不會有列的值, 而它會讓下一個人以為那封信做好了。
   🎯 **與 `order_created` 這個名字騙到我的形狀一模一樣。**
