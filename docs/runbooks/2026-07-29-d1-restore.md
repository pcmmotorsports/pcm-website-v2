## 3. 🔴 卡住時的正解(這一節是重點)

### 3-1 `HEADER MATCH` 報錯:欄位對不上

長這樣:`ERROR: column name mismatch in header line`。

**這是預期會發生的。** 備份存 180 天,期間 schema 幾乎一定改過(E10 第 2、3 批都會加欄)。
`HEADER MATCH` 就是為了讓你在這裡停下來 —— 沒有它,多一欄會讓整排資料**錯位靜默寫入**,
還原「成功」但每一欄的內容都挪了一格。

**❌ 絕對不要做的事:把 `HEADER MATCH` 改成 `HEADER`。** 那不是修好,那是把安全帶剪掉。

**✅ 正解:改用顯式欄位清單載入。**

1. 看備份的表頭有哪些欄:
   ```bash
   head -1 ~/d1-backup-20260729-v2/orders.csv
   ```
2. 看現在的表有哪些欄:
   ```sql
   SELECT string_agg(column_name, ',' ORDER BY ordinal_position)
     FROM information_schema.columns
    WHERE table_schema='public' AND table_name='orders';
   ```
3. 比對差異,分兩種:
   - **新增的欄**:暫存表建成 `CREATE TEMP TABLE d1r_orders (LIKE public.orders)` 之後,
     `\copy d1r_orders (<備份表頭的欄位清單>) FROM ... WITH (FORMAT csv, HEADER, NULL '\N')`
     —— 顯式列出備份有的欄,新增欄會留 NULL 或預設值。
     🔴 **若新增欄是 NOT NULL 且無預設值**,這裡沒有正確答案 —— 停下來問 Sean
     那 26 張的該欄應該填什麼,不要自己編一個值。
   - **被刪掉的欄**:備份有、現在沒有 ⇒ 那份資料無處可放。停下來記錄,由 Sean 決定
     是接受遺失、還是先把欄位加回來再還原。

### 3-2 叢集識別碼不符

長這樣:`D1:本腳本是 production 版,但連到的不是 production 叢集`。

`scripts/d1-guard.ts` 裡的 `PRODUCTION_CLUSTER_ID` 是 2026-07-29 當下實查的值。
**它會因為 Supabase 平台側遷移、大版本升級、或他們自己做災難還原而改變** ——
而最後那種情況正好跟「你需要用這包備份」高度重疊。

**先確認你真的連對地方**(Supabase dashboard 的專案 ref 對不對),再:

```sql
SELECT system_identifier FROM pg_control_system();
```

確認新值之後,**由 Sean 拍板**更新 `scripts/d1-guard.ts` 的常數,並在 commit body 寫明
「舊值 X → 新值 Y,原因是 Z」。🔴 **不要為了讓守門過就順手改掉它** —— 那道守門存在的
唯一理由就是擋住「連錯資料庫」,改掉它等於當天沒有守門。

同理,`preflight` 會擋「備份來源叢集不是 production」。平台遷移後舊備份的
`cluster_id` 是舊值、合法但過不了 —— 這時同樣是人工覆核後才放行,不是改程式碼繞過。

### 3-3 外鍵錯誤:父列不見了

長這樣:`violates foreign key constraint "orders_customer_user_id_fkey"`。

備份裡已經含了五張父表(客戶 / 地址 / 商品 / 商品規格 / 條款版本),wrapper 會先補齊它們。
還是報錯的話,**幾乎一定是客人自己刪了帳號** —— `auth.users` 沒有備份
(Sean 2026-07-29 拍板 Q3=A:那張表含密碼雜湊,不放進備份),客戶資料連帶被 CASCADE 清掉。

這是**已知並已拍板接受的殘餘風險**。停下來報給 Sean,由他決定那筆訂單怎麼處理 ——
不要自己建一個假帳號把它塞回去。

## 4. 還原成功之後會發生什麼(先知道,免得誤判成故障)

待刪組裡有 **3 筆 `pending` 的 `payment_charge_attempts`**。它們一被還原進活的系統,
pg_cron 的 settle sweeper(每 2 分鐘一次)下一輪就會掃到,拿幾個月前的交易去問 TapPay,
可能因此發出告警信或改動狀態。

**這是預期行為,不是還原出錯。** 「還原回來的資料是靜止的」這個直覺是錯的 ——
它們回到的是一個活著的系統。如果不希望它動,還原前先停掉 sweeper
(`cron.alter_job(job_id, active := false)`),事後記得開回來。
