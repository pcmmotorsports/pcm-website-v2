## 3. 🔴 卡住時的正解(這一節是重點)

### 3-1 `HEADER MATCH` 報錯:欄位對不上

長這樣:`ERROR: column name mismatch in header line`。

**這是預期會發生的。** 備份存 180 天,期間 schema 幾乎一定改過(E10 第 2、3 批都會加欄)。
`HEADER MATCH` 就是為了讓你在這裡停下來 —— 沒有它,多一欄會讓整排資料**錯位靜默寫入**,
還原「成功」但每一欄的內容都挪了一格。

**❌ 絕對不要做的事:把 `HEADER MATCH` 改成 `HEADER`。** 那不是修好,那是把安全帶剪掉。

**✅ 正解:改用顯式欄位清單載入。**

1. 看備份的表頭有哪些欄:
   ```bash
   head -1 ~/d1-backup-20260729-v2/orders.csv
   ```
2. 看現在的表有哪些欄:
   ```sql
   SELECT string_agg(column_name, ',' ORDER BY ordinal_position)
     FROM information_schema.columns
    WHERE table_schema='public' AND table_name='orders';
   ```
3. 比對差異,分兩種:
   - **新增的欄**:暫存表建成 `CREATE TEMP TABLE d1r_orders (LIKE public.orders)` 之後,
     `\copy d1r_orders (<備份表頭的欄位清單>) FROM ... WITH (FORMAT csv, HEADER, NULL '\N')`
     —— 顯式列出備份有的欄,新增欄會留 NULL 或預設值。
     🔴 **若新增欄是 NOT NULL 且無預設值**,這裡沒有正確答案 —— 停下來問 Sean
     那 26 張的該欄應該填什麼,不要自己編一個值。
   - **被刪掉的欄**:備份有、現在沒有 ⇒ 那份資料無處可放。停下來記錄,由 Sean 決定
     是接受遺失、還是先把欄位加回來再還原。

## 4. 還原成功之後會發生什麼(先知道,免得誤判成故障)

它們回到的是一個活著的系統。如果不希望它動,還原前先停掉 sweeper
(`cron.alter_job(job_id, active := false)`),事後記得開回來。

## 4-a. 🔴 收尾必做:確認這次還原【留下了紀錄】

還原的最後一步會往 `admin_audit_log` 寫一筆 `action='ops.d1.restore'`
(`source_app='ops'`,`actor` = `session_user` = **DB 自己講的那一格**;
而**你在 `D1_OPERATOR` 填的名字**進的是 `after->>'operator_self_reported'`,兩欄分開放 —— 理由見下面。)

🔴 **而它跑在 `COMMIT` 之【後】** —— 所以它失敗時,**還原早就落地了,資料是安全的**。
畫面會先印這一行,再跑留痕:

```
== 以下是留痕。還原【已經 COMMIT 完成】—— 這一段失敗不影響它,但請手動記錄。==
```

### 🔴🔴 `rc≠0` 有【兩種】,而分辨法在畫面上

`psql` 以非零退出碼結束時(`ON_ERROR_STOP on`),**它可能是兩件完全不同的事**:

```
甲 還原失敗          ⇒ 交易 ROLLBACK ⇒ 【資料沒有被動過】
乙 還原成功而留痕失敗 ⇒ 資料【已經寫進去了】，只是沒有紀錄
```

🔴 **而退出碼本身也分得出一部分**(2026-08-29 codex 查證,附官方 psql 文件):
```
rc = 3  ⇒ SQL 腳本裡的語句出錯（ON_ERROR_STOP 之下）
rc = 2  ⇒ 【連線中斷】—— 那不是 SQL 錯，是連不上或斷了
rc = 1  ⇒ psql 自己的致命錯誤（例如記憶體不足、找不到檔）
rc = 0  ⇒ 全部跑完
```
⚠️ **而 `rc=3` 【仍然】分不出甲乙** —— 兩者都是 SQL 語句出錯。
⇒ 所以下面那個「看畫面上有沒有印那一行」的判法**還是要用**。
📌 **⇒ 退出碼告訴你【哪一類】失敗,而那一行 `\echo` 告訴你【失敗在哪一段】。**

**分辨法 —— 看畫面上有沒有印出這一行(它一定會印,因為它排在留痕之前):**

```
== 以下是留痕。還原【已經 COMMIT 完成】—— 這一段失敗不影響它,但請手動記錄。==
```
- **印了** ⇒ 是【乙】。還原成功。去做上面那個 `SELECT` 確認,並手動補記進事故紀錄。
- **沒印** ⇒ 是【甲】。還原沒成功,照 §3 查原因。

### ⚠️ 而「要不要重跑」—— **重跑是安全的,而它沒有用**
```
🔴 重跑【不會二次破壞】：`INSERT INTO public.orders`（產生器 :681）
   【沒有】ON CONFLICT ⇒ 第二次會撞主鍵、直接失敗 ⇒ ON_ERROR_STOP ⇒ 整批 ROLLBACK
   （父表那幾張是 ON CONFLICT DO NOTHING ⇒ 第二次是 no-op）
⇒ 所以【乙】的情況下重跑，結果是「又一次 rc≠0」，而資料還是好的
```
📌 **⇒ 所以不要用「重跑看看」來判斷是甲還是乙 —— 兩種都會再給你一個非零碼。**
**⇒ 用上面那一行畫面訊息判。**

### 🛑 `一致 = false` 的時候,照這個順序查(不要跳步)

```
① 🔴 先看【退出碼】—— 它先把「還原有沒有跑完」分掉
   0 ⇒ 全部跑完（含留痕與這道一致性閘）
   3 ⇒ SQL 出錯　　2 ⇒ 連線斷　　1 ⇒ psql 自己的致命錯
   而畫面上「== 以下是留痕。還原【已經 COMMIT 完成】==」那一行有沒有印：
     沒印 ⇒ 還原【沒有】落地 ⇒ 停在這裡，照 §3 查，下面幾步都不用做
     印了 ⇒ 還原落地了，往 ② 走

② 再看【已改號 / 總數】那兩個數字
   26/26 ⇒ 資料是 post　　0/26 ⇒ 資料是 pre　　其他（例 13/26）⇒ 跳到 ④

③ 拿它跟【要求的版本】比
   要求 post 而資料 0/26 ⇒ 改號段沒跑到（而它自己有斷言，理論上會擋 ⇒ 回 ① 看退出碼）
   要求 pre  而資料 26/26 ⇒ 這批單【之前就被改過號】⇒ 不是這次還原造成的

④ 兩個數字都不是 26 或 0（例如 13/26）
   🔴 那代表【有人在還原之後動過這批單】—— 還原自己有逐列比對，它不會留下半套
   ⇒ 去查 admin_audit_log 在那個時間點前後有沒有別的動作
```
📌 **順序是【先退出碼、再數字】,而不是反過來** ——
因為退出碼先把「還原有沒有落地」分掉,而在還原沒落地的世界裡,那兩個數字沒有意義。
⚠️ **而「並行修改」與「還原沒跑完」因此分得開**:
前者退出碼可能是 0 而數字很怪(④);後者退出碼非 0 且畫面少印那一行(①)。

⚠️ **那兩欄不要混著讀**:
```
actor                    ⇒ DB 自己記的 session_user ⇒ 【偽造不了，而它每一筆都一樣】
                            （guard 強制 postgres ⇒ 它答不出「這次是誰」）
operator_self_reported   ⇒ 跑的人自己打的字 ⇒ 【答得出「這次是誰」，而它填假的填得出來】
```
📌 **⇒ 一個偽造不了而答不出誰,一個答得出誰而偽造得了 —— 兩欄合起來仍然【不是證據】,是線索。**

- **有一列而且時間對得上** ⇒ 留痕成功,把它貼進事故紀錄。

  ⇒ `source_app='ops'` 被 CHECK 擋下)。**還原本身仍然是成功的** ——
