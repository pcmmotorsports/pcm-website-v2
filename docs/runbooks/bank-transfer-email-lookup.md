# 匯款客人說「你們寄的帳號是錯的 / 我沒收到信」—— 怎麼查

> **開列**:線【信】`-mail` 2026-09-06(主視窗 `-f8` 派;來源 = opus R2 · N4「這一欄目前**只寫不讀**」)。
> 🔬 **「只寫不讀」是量到的, 而且帶正對照**(2026-09-06, `pcm-wt-mail` HEAD `60a087283`):
> ```
> apps/admin/src/lib/mail/dead-letter-read.ts        provider_message_id=0  recipient_email=2
> apps/admin/src/lib/orders/email-log-repository.ts  provider_message_id=0  recipient_email=1
> ```
> 🔴 **那兩個 0 曾經是【假的】** —— 我第一發打的路徑是 `packages/adapters/src/email/…`,
> **那兩支檔在那裡不存在** ⇒ grep 印 0 而它答的是「路徑錯」。📌 **一個 0 沒有正對照就沒有意義。**
> **對象**:客服 / 值班的人。**不需要會寫程式**,而**每一步都要有人幫你跑**(標了 🧑‍💻 的那幾行)。
> **射程**:只講**匯款單成立信**(`bank_order_created`)。其他信種的欄位一樣,而判準不一定一樣。
>
> 🔴🔴 **本檔的體例:每一格都寫【兩個世界印什麼】。**
> 一個只會印一種東西的檢查, 你分不出「查到了」與「它壞了」——
> 📌 **那正是客服最需要分開的兩件事**:是**我們沒寄**, 還是**他沒收到**。

---

## 0 · 先分清楚客人在講哪一種(三選一, 後面的路不同)

| 客人的話 | 他在問的 | 去哪一節 |
|---|---|---|
| 「我**根本沒收到**信」 | 我們到底寄了沒 | §1 ⇒ §2 |
| 「信裡的**帳號 / 金額**是錯的」 | 他收到的**那一封**寫了什麼 | §2 ⇒ §3 |
| 「我**收到兩封不一樣的**」 | 那是出貨信的族, **不是本檔** | `docs/runbooks/duplicate-shipping-email-sop.md` |

🛑 **不要跳過這一格。**「沒收到」問的是**我們的 `email_outbox`**(§1),
「收到而內容錯」問的是**Resend 上那一封**(§2)—— **兩個地方, 而兩邊都可能印出一個看起來像答案的東西**。

## 1 · 路 A:先問我們的系統「這封信寄了沒」

🧑‍💻 **要有人幫你跑一段唯讀查詢。** 那條路存在(`~/pcm-mailbox/0905查證/run.sh`),而它有三條規矩,**缺一不可**:

```
① 唯讀與 apply 是【兩個授權】, 而 Sean 只給了唯讀 ⇒ 不得拿它改任何東西
② 跑不動是【對的】, 不是壞掉 —— 那由跑的人的權限決定
③ 絕不把連線字串印進對話
```

要查的東西(把 `PCM-2026-XXXX` 換成客人的訂單編號):

```sql
select status, last_error_code, sent_at, provider_message_id, recipient_email, attempts
from public.email_outbox
where event_type = 'bank_order_created'
  and order_id = (select id from public.orders where display_id = 'PCM-2026-XXXX');
```

### 🔴 兩個世界印什麼 —— 這是本節的本體

| 印出來的 `status` | 意思 | 下一步 |
|---|---|---|
| **零列**(什麼都沒有) | 這張單**從來沒有排進寄信佇列** | ⚠️ **不是「沒寄」那麼簡單** ⇒ §1a |
| `sent` | 我們**確實送出去了** | 去 §2 拿證據 |
| `pending` | 排隊中, **還沒寄** | 等下一輪 cron;超過 15 分鐘 ⇒ 報工程 |
| `sending` | **卡在寄送中** | 🔴 那是異常 ⇒ 報工程(可能信已寄出而標記沒寫回去) |
| `failed` | 試過而失敗 | 看 `last_error_code`, 報工程 |
| `skipped_order_ineligible` | **故意不寄** | 🔴 **真相不在 `status` 裡** ⇒ §1b |

### §1a 零列的兩個世界(這一格最容易誤判)

**零列不代表「系統忘了」。** 它至少有兩個成因, 而它們印的是**同一個東西**:

```
① 這張單不是【匯款】單(刷卡的不寄這封信)   ⇒ 正常
② 它符合資格而沒被排進來                     ⇒ 異常, 要報工程
```
🧑‍💻 分辨法 —— 再跑一發, **問這張單是不是匯款單**:
```sql
select payment_channel, order_source, status from public.orders where display_id = 'PCM-2026-XXXX';
```
- `payment_channel` **不是** `bank_transfer` ⇒ **①**, 到此為止, 跟客人說這種單本來就沒有這封信。
- 是 `bank_transfer` 而上面那發仍是零列 ⇒ **②**, 報工程。

> 🔴 **為什麼用 `payment_channel` 而不是 `order_source`**:`order_source` 有預設值 `'web'`
> ⇒ 它**印 `web` 不代表那張單真的從網站來**;`payment_channel` 的預設是 `'tappay'`
> ⇒ **它印 `bank_transfer` 就真的是選了匯款**。📌 **一個有預設值的欄位, 答不出「是誰填的」。**

### §1b `skipped_order_ineligible` 的**五**個世界(看 `last_error_code`, 不要看 `status`)

`status` 這一欄是**共用的桶**。🔬 **當場數過 = 5 個不同的碼共用它**
(`packages/adapters/src/email/SupabaseEmailOutboxAdapter.ts:661/674/688/696/713`;
數法 `grep -n -A2 "status: 'skipped_order_ineligible'" <該檔> | grep last_error_code`):

| `last_error_code` | 白話 | 跟客人怎麼說 |
|---|---|---|
| `order_ineligible` / `order_ineligible_at_send` | 那張單已經**取消**了 | 這封信不該寄了 |
| `bank_order_not_mailable_at_send` | 寄送當下發現**已經付掉 / 已取消 / 已過期** | 同上 |
| `bank_order_snapshot_stale` | 🔴 **後台把金額或收件人改了**, 而我們手上那份是舊的 | ⇒ §1c |
| `tracking_superseded` | 出貨追蹤號被更新蓋過 | **不屬匯款線**, 列在這裡是因為它共用同一個桶 |

⚠️ **而 `skipped_no_real_email`(那張單只有合成信箱、沒有真信箱)是【另一個 status】, 不在這個桶裡**
—— 📌 所以你在 `status` 那一欄會直接看到它, 不必翻 `last_error_code`。處置:請客人補信箱。

🛑 **`bank_order_snapshot_stale` 是「我們寧可不寄」, 不是「壞了」** ——
少寄一封 < 寄一個錯的金額給錯的人。

### §1c 後面兩種:修好之後它**會自己重寄嗎**

**會** —— 而**只有這兩個碼會**(`bank_order_not_mailable_at_send` / `bank_order_snapshot_stale`)。
其他 `skipped_*` 的列**永久擋住**那張單, 修好也不會自己重排 ⇒ 要報工程手動處理。

🔴 **兩個世界怎麼確認它真的重排了**:修好之後等一輪 cron, 再跑一次 §1 那發查詢 ——
- 出現**第二列**(新的 `pending` 或 `sent`)⇒ 重排成功。
- **還是只有那一列** ⇒ 沒重排, 報工程。
📌 **不要用「舊那列的 status 有沒有變」當判準** —— 舊列**本來就不會變**, 那個檢查在兩個世界印同一個東西。

## 2 · 路 B:去 Resend 後台看**客人實際收到的那一封**

Resend = 我們的寄信服務商。**信的內文只存在他們那裡, 我們自己沒有留**
(Sean 2026-09-06 拍**乙**:只存一個編號, 不留全文)。

### 兩條進去的路 —— 先試 ②, 它比較準

**① 按收件人搜尋**(`resend.com` 後台 → Emails → 搜尋框貼客人的 email)

| 看到什麼 | 意思 |
|---|---|
| 有一封 `Delivered` 而主旨是「訂單 … 已成立」 | ✅ 我們寄了、他們也收了 ⇒ 請客人查垃圾信 |
| 有一封而狀態是 `Bounced` / `Complained` | 🔴 他的信箱**退信**了 ⇒ 請他換一個信箱 |
| **一封都沒有** | ⚠️ **不要就此下結論** ⇒ 見下面那道紅字 |

> 🔴🔴 **「一封都沒有」有一個很常見的假成因:你搜的信箱跟我們寄的那個【不一樣】。**
> 客人常用另一個信箱跟你講話。⇒ 拿 §1 那發查詢印出來的 **`recipient_email`** 去搜, **不要用他跟你講話的那個**。
> 📌 **兩個世界**:用對的信箱搜 ⇒ 有;用他講話的信箱搜 ⇒ 沒有。**而「沒有」那個畫面長得一模一樣。**

**② 按編號直接開那一封**(準, 而**要 §1 先給你編號**)

§1 那發查詢印出來的 `provider_message_id` 就是它。貼進 Resend 後台的搜尋 ⇒ 直接開到**那一封**。

| `provider_message_id` 印什麼 | 意思 | 下一步 |
|---|---|---|
| 一串像 `49a3999c-0ce1-…` 的東西 | ✅ 有編號 | 貼進 Resend 後台 |
| **`NULL`**(空的) | ⚠️ **兩個世界, 而這一欄自己分不出來** | ⇒ §2a |

### §2a `NULL` 的兩個世界(⚠️ 這一格容易得到相反的結論)

```
①【舊資料】那封信寄出去的時候, 我們還沒開始記編號   ⇒ 正常
②【新資料而沒拿到】寄出去了, 而編號沒取到           ⇒ 要報工程
```
🧑‍💻 分辨法 —— 先問**我們從哪一刻開始記**:
```sql
select min(sent_at) from public.email_outbox where provider_message_id is not null;
```
- 你那封的 `sent_at` **晚於**這個時刻 ⇒ **②**, 報工程。
- **早於** ⇒ **①**, 正常, 改走路 B-① 按信箱搜。

> ⚠️ **那個時刻是【下界】不是精確時刻**:上線後最早那幾封若剛好都沒拿到編號, 這個值會**偏晚**
> ⇒ 🔴 **只有「晚於」那一邊可以下結論**;「早於」那一邊**混得進②**, 不要拿它去跟客人保證。

### 🛑 30 天天花板(**先講, 不要查到一半才發現**)

Resend **只留 30 天**。超過 30 天 ⇒ **有編號也開不出那封信**。
📌 這一欄**縮短不了那個天花板** —— 它只是把「30 天內要靠人翻」變成「30 天內開得到」。
⇒ 🔴 **客人講的是一個月以前的事** ⇒ 直接跳到 §3, 不要在 Resend 上耗。

## 3 · 沒有那封信的時候, 帳號正不正確要怎麼答

信不見了不代表答不出來 —— 匯款帳號**不是每封信各寫各的**, 它來自同一個地方。

🔬 **落點(主視窗 `-f8` 2026-09-06 給, 我複核過)**:帳號**寫死在碼裡** ——
`packages/domain/src/order/remittance-info.ts`(`:34` 銀行 · `:35` 分行 · `:38` 帳號 · `:65` 期限天數)。
⇒ 📌 **「當時那張單看到的帳號」= 那支檔在 `sent_at` 那一刻的版本。**

🧑‍💻 要有人幫你跑(**不要把帳號貼進聊天視窗**, 看完就好):
```
git log --format='%h %ci %s' -- packages/domain/src/order/remittance-info.ts
git show <sent_at 之前最近那顆 hash>:packages/domain/src/order/remittance-info.ts | grep 'ACCOUNT_NO ='
```

### 🔴🔴 兩個世界 —— **而這一格有一把很自然而【錯】的尺**

⛔ ~~「`git log` 印幾顆 ⇒ 改過幾次」~~ **那把尺是錯的。**
🔬 **當場量過**(2026-09-06):那支檔的 log 有 **3 顆**, 而帳號那一行的內容 **三顆完全相同**
(數法:`for h in <三顆>; do git show $h:<該檔> | grep 'ACCOUNT_NO =' | shasum; done` ⇒ **三個一樣的雜湊**)。
⇒ 🛑 **檔案被改過 ≠ 帳號被改過** —— 那三顆動的是別的東西(文案、期限寫法)。

✅ **正確的尺 = 比那一行的【內容】, 不是數 commit**:
| 讀數 | 意思 | 下一步 |
|---|---|---|
| `sent_at` 之前那顆的帳號 = 客人手上那組 | ✅ 客人手上的是對的 | 可能他看錯或轉錯 |
| **不同** | 🔴 帳號真的被改過 | **停下來報工程與 Sean** —— **影響的不只他一個人** |
| log 只有一顆 / 每顆內容都一樣 | 帳號**從來沒變過** | ⇒ 客人手上那組若不同, **那不是我們寄的** ⇒ 當詐騙處理、報 Sean |

⚠️ **金額**這一項不一樣:它會隨後台改單而變。⇒ 客人說金額對不上時, 先看 §1b 有沒有 `bank_order_snapshot_stale`
—— 有的話, **那正是系統發現金額被改過而【故意不寄】**, 那時客人手上那封是**舊的**。
