# 客人拿著【兩封不一樣的出貨通知】打電話進來 —— 怎麼辦

> 🔵 **這一份是給客服看的, 不是給工程師看的。** 白話寫。
> 🔴 **而它存在的理由是**:這件事**是我們知道的、而且是刻意接受的** ——
> 客服不必懷疑系統壞了, 也不必去找工程師。
>
> 📌 **而更重要的是下面「我們查不出來」那一節** —— 那一格請先讀完再回覆客人。

---

## 症狀(以下任一)
```
· 客人說他收到【兩封】出貨通知, 而【追蹤號不一樣】
· 客人問「到底哪一個才對」
· 客人說「你們是不是出了兩次貨」
```

---

## 一句話回覆客人

> **「不好意思, 這是我們系統在極少數情況下會重複發出的通知。您的訂單只有一批貨,**
> **請以【最新收到的那一封】為準 —— 我幫您確認一下目前的追蹤號。」**

🔵 **然後在後台訂單詳情頁看那張單目前的出貨資訊, 把【現在的追蹤號】唸給客人。**
🛑 **不要說「系統出錯了」** —— 它沒有出錯, 它在做我們選的那件事(見下)。

---

## 為什麼會這樣(一段就好)

一批貨被【作廢】之後又被【復原】的時候, 系統會重新排一次出貨通知。
⇒ 而如果第一封已經寄出去了, 客人就會收到兩封。

**而還有第二條路會走到同一個結果**(2026-09-03 線 `-account` 查到, 補進來):

> **員工發現出貨單號打錯了 ⇒ 後台【改不了】⇒ 他只能把那一箱作廢、重開一張新的
> ⇒ 系統把新的那一箱當成一次新的出貨 ⇒ 重新排一封信。**

⇒ 所以客人手上會有**兩個不同的追蹤號**, 而 ⛔ ~~**後面那一個才是對的**~~。
🔵 ⛔ ~~**給客服的一句話**:遇到這種, 請客人**用最新那一封**的追蹤號查件。~~

## 🔴🔴 【2026-09-05 訂正 —— 搜「用最新那一封」或「後面那一個才是對的」的人請在這裡停下】

**那兩句在【它們自己描述的那個世界】裡完全正確**(作廢 + 重開一張新箱 ⇒ 新的那一箱就是真的那一箱)。
🛑 **而它們被寫成【一句話規則】, 而規則會被套到別的世界。**

### 它在哪個世界會給【錯的】答案

```
員工把追蹤號從 A 改成 B  ⇒ 系統補寄一封說「正確的是 B」
⇒ 🔴 然後他【又改回 A】(打錯了、或原本那張才對)
⇒ 客人手上【最新那一封】說 B      而後台現在是 A
⇒ 照「用最新那一封」⇒ 客服會唸 B 給客人 ⇒ 🛑 客人拿著錯的號碼去查件, 查不到
```
📌 **⇒ 「最新那一封信」與「現在的事實」是兩件事, 而它們只在【號碼只往前改、不改回去】時相等。**
🔴 **而改回去是合法操作** —— 沒有任何東西擋它。

### ✅ 正確的判法(**本檔 `:25` 本來就寫對了**)

> **看後台那張單【現在的】出貨資訊, 把現在的追蹤號唸給客人。**
> **不要用「客人最後收到哪一封」去推。**

🎯 **⇒ 本檔原本就同時有【對的規則】(`:25`)與【錯的規則】(`:40-41`)** ——
而**錯的那個被包裝成「給客服的一句話」** ⇒ 📌 **它才是會被照做的那一句。**
⇒ ⇒ **一份文件裡兩條相反的指示, 誰會被執行, 取決於哪一條長得比較像可以照抄的。**

⇒ 📌 **它不是歷史紀錄, 它還會再發生。** 而每發生一次, 客人就會多收到一封。

**Sean 2026-08-31 拍板接受了這件事, 而他當時的原話是:**
> 「極少數情況客人會收到**兩封不一樣的**出貨通知 —— 例如兩個不同的追蹤號,
>   而他不知道該信哪一封」
> 「我用一個**常態的病**換一個**極少數的病** —— **不是零代價, 你要知道**」

**而換掉的那個「常態的病」是**:以前那種情況下, 客人會**一封都收不到** ——
貨已經出了而他不知道, 他會打電話問、或直接申請退款。

📌 **判準是:漏信是【無聲的】, 矛盾信是【有聲的】。**
⇒ **客人打這通電話, 本身就是這個設計要的結果。**

## 🔴 我們查不出來的那一格 —— **請先讀完再回覆**

**你【不會】在後台找到「這張單發生過重複通知」的任何標記。**

```
系統裡留下的痕跡, 與【一切正常】的情況長得一模一樣。
⇒ 所以你不能靠後台確認「這位客人是不是踩到了這個」
```

🛑 **⇒ 所以請照下面做:**
1. **相信客人**。他說他收到兩封, 那就是兩封 —— 你查不到不代表沒發生。
2. **不要承諾「我幫您查一下當時發生什麼事」** —— 那查不出來, 而承諾了會變成第二通電話。
3. **把這一通記下來**(客人姓名 / 訂單編號 / 兩個追蹤號 / 日期), 交給工程。
   🔵 **為什麼要記**:這是目前**唯一**的發現路徑 —— 沒有任何一支監控會告訴我們它發生了。

## ⚠️ 而還有一種情況, 它與上面【不同】

```
客人說他收到出貨通知, 但是【貨其實沒有出】
```
🔴 那**不是**本篇這一件。那是另一條路(貨被作廢, 而通知在那之前就送出去了)。
⇒ **一樣照上面第 3 點記下來交給工程, 而請在紀錄上註明「客人說貨沒出」** —— 那兩件的處理不同。

## 📎 給工程的技術錨(客服不必讀)

- 落點:`packages/adapters/src/email/SupabaseEmailOutboxAdapter.ts` 的 `markSkippedShipmentVoided`
  (錨:逐字 `⟦b4-SHIPUNVOID1⟧ 2026-08-31`)。
- 機制:寫下 skip 的同一發 UPDATE 把 `dedup_key` 退休成 `<原鍵>:voided:<列 id>`
  ⇒ 掃描 view 的 anti-join 比不到 ⇒ 下次掃描排一列新的。
- 🔴 **而「兩個交錯順序」那一格是承重的**:退休必須發生在【寫下 skip 的那一刻】,
  不是在 unvoid 那一側 —— 因為「先 unvoid 後 skip」**實測可達**。
- 🛑 **本檔沒有驗的**:我(`-15`)是**讀碼推出來的**, **沒有真的跑過一次「作廢 ⇒ 復原 ⇒ 下次掃描」**。
  ⇒ 要把它變成量到的, 得在拋棄式庫演一遍, 或在正式庫讀一筆真的退休鍵。
- ⚠️ 另一條**本來就在**的路(本片沒關掉):sweeper 讀到箱 live 之後、到真的送出去之間,
  箱仍可被作廢, 而它**不重查** ⇒ 那就是上面「貨沒出卻收到通知」那一種。
