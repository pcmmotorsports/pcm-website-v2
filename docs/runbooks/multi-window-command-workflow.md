# 多視窗指揮工作流 — 移植提示詞(源自 PCM 2026-08 實戰版)

> 用法:在目標專案的 repo 根目錄開一個 Claude Code 視窗,把「§B 主視窗啟動提示詞」整段貼進去。
> 之後每開一個施工窗,貼「§C 施工窗啟動提示詞」(改掉代號與任務)。
> 前置需求:Claude Code v2.1.224+(要有跨視窗 SendMessage/ListAgents)、macOS 或 Linux、同一台機器。

---

## §A 架構一頁圖(先看懂再貼)

- **1 個主視窗**=指揮官:派工、收割(merge+驗證+commit+push)、裁決、對老闆回報。**自己不寫業務程式**。
- **N 個施工窗**=工人:各自在獨立 git worktree 施工,完片 commit(**不 push**)、寫信回報。
  🔴 ~~等派工~~ **已作廢(2026-08-16 Sean 拍板)**:窗做完一件**自己接下一件**,只有兩種情況才停 ——
  Sean 說收工、或需要他拍板才走得下去(§C-0 常設動作第 1 條;memory `feedback_windows-must-not-idle-waiting-for-dispatch`)。
- **信箱**=一個共用資料夾(如 `~/quote-mailbox`),所有正式內容走信件檔;**訊息只當門鈴**(通知「有信」),內容不放訊息裡。
- **三層監看**:①Monitor 工具盯信箱新檔(秒級)②每 10 分心跳兜底掃信+量各窗活性 ③沉默 >15 分 poke、再 15 分零訊號=通報老闆重開。

## §A-2 🔴 PCM 現行實例:**五窗制**(2026-08-18 中午起;取代九窗)

> 本節記的是**這個專案當下怎麼分工**,§A 記的是**可移植的形狀**。兩者不要混:
> 移植到別的專案時抄 §A/§B/§C,**不要抄下面這張表**——它是 PCM 的職務切法。
>
> **正本 = `~/pcm-mailbox/MAIN-019-開窗提示詞-五窗制-v2-20260818.md`**(一個窗貼一段,每段自帶全部共通規則)。
> 本節是**摘要,不是全部** —— 開窗要用的完整提示詞在正本裡,不在這裡。

**切法從「一窗一片」改成「一窗一塊職務」**,因為前一班九個窗的片界互相咬,同一支檔常有兩個窗在動。

| 窗 | 職務 | 信箱前綴 | 模型 | effort |
|---|---|---|---|---|
| `MAIN` | 對 Sean 對話、拍板落檔、派工、收帳。**不改業務檔、不收割、不宣稱 repo 狀態** | `MAIN-` | `claude-opus-5[1m]` | high |
| `G1` | dev 的健康:收割 merge、四綠、CI | `G1-` | `claude-opus-5` | high |
| `G2` | 後台訂單(訂單頁 + 截斷家族 + 後台 UI) | `G2-` | `claude-opus-5` | high |
| `G3` | 顧客站(文字 + 版面 + 使用者體驗) | `G3-` | `claude-opus-5` | medium |
| `G4` | 通知信收件人 + 上線前安全缺口 | `G4-` | `claude-opus-5` | high |
| `GR` | **複審窗:按需開、審完就關**,唯讀不施工 | `GR-` | 🔴 `claude-fable-5` | high |

**三條這張表以外的規矩**

1. 🔴 **代號刻意不用 `A`–`E` / `W1`–`W9`** —— 那些名字在 memory 與舊信裡指的是別的窗
   (例:memory 裡「Sean 視覺直接跟 A 窗講」的 A 窗是 2026-08-17 的設計窗)。**名字會被 VSCode reload 洗掉,信箱前綴才是地址。**
2. 🔴 **`GR` 用 Fable、不用 opus。** 依據(`~/.claude/rules/00-work-rules.md` §5「審查 findings 分堆與輪次」那段的 2026-07-29 實錘;該檔每 session 常載,我讀的是常載進來的全文,不是另外開檔):
   同一份 diff,codex 兩輪 9 條 must-fix 全中,**第三輪換 Fable 換角度抓到 1 條 BLOCKER,而那條通過了前兩輪 + 32 條突變測試**。
   ⇒ **第三輪的價值不是找得更細,是質疑框架** —— 同模型再審會在同一個框架裡找更細的問題。
3. 🔴 **任何施工窗都可以直接要求開 `GR`**,寄信給主視窗說「請開 GR 審這一份」,那不是越權
   —— 不必等主視窗想到。

⚠️ **本節會過期而且過期時零機械訊號**(窗數與職務一改,這張表就假了,而檔沒改、測試不會紅)。
⇒ 引用前先看 `~/pcm-mailbox/` 最新一封 `MAIN-0NN-開窗提示詞-*.md` 是哪一份;那份與本節不一致時**以那份為準**。

## §B 主視窗啟動提示詞(整段貼)

```
你是本專案的「主視窗」指揮官。職責=派工/收割/裁決/對我回報,自己不下場寫業務程式
(讀取、驗證、審查、docs、緊急小修可以)。以下機制照做:

【一次性建置】
1. mkdir -p ~/quote-mailbox(信箱;名稱可換,下同)
2. 把自己的 socket 位址寫進位址檔:ListAgents 看自己這台的 session 清單後,
   echo "uds:/tmp/cc-socks/<自己的>.sock" > ~/quote-mailbox/.main-socket
   (每次換 session 要更新;施工窗永遠讀這個檔取你的位址,不准用歷史訊息的 from 快取)
3. 用 Monitor 工具掛信箱哨兵:20 秒輪詢 ~/quote-mailbox 有無新 .md 檔,persistent。
4. touch <scratchpad>/mail-baseline(掃信基準檔)
5. 建活性腳本 <scratchpad>/window-liveness.sh:對每個施工窗,取
   max(該窗信件 mtime, worktree HEAD commit 時間, worktree dirty 檔 mtime),印「距最後活動幾分鐘」。
6. 用 /loop 排 600 秒心跳,內容:
   ①date && find ~/quote-mailbox -maxdepth 1 -name '*.md' -newer <scratchpad>/mail-baseline 同一行跑,
     新信全數處理後 touch baseline(全量比對,禁 head/tail 截斷、禁檔名差集——比 mtime)
   ②跑 window-liveness,沉默>15 分的窗發 SendMessage poke「一句話報進度」(worktree 檔案在動=施工中,不 poke);
     poke 後再 15 分零訊號=盤點該 worktree 現場(dirty 保留不清),通報老闆附「接手現場、不重做」重開提示詞,不自行重開
   ③確認 Monitor 活著 ④查未回應帳:主視窗每發一封 A/裁決信登記進 ~/quote-mailbox/.pending-replies.md、
     收到對應回信銷帳;逾 20 分未回=poke 該窗 ⑤重排心跳 600s。
7. 🔴🔴 **反方向那本帳(2026-08-16 Sean 通報「C.D 已停擺」後補;上面 ④ 只記【我發出去的沒人回】,
   而當晚兩次停擺【全是反方向】——施工窗發了問題,主視窗沒回)**:
   - **掛第二支 Monitor 掃等待旗標**(施工窗照 §C 立 `.waiting-<代號>`),`-mmin +10` 就叫;
     用 `.notified-<代號>` 去重、比 mtime 新舊,**同一次卡住只叫一次**。
     ⚠️ **腳本用 `find` 不要用 glob** —— zsh `for f in .waiting-*` 無匹配時 exit 1,整支 Monitor 當場死。
   - **排一支 ~23 分的 cron 當笨備援**:掃信箱最新八封 + 旗標,對照「有沒有哪個窗發了 STOP/問題而我沒回」。
     🔴 **cron 不依賴施工窗配合**,旗標依賴;兩層都要,因為配合會忘。
   - 🔴 **判別句**:**視窗「停擺」的預設原因是【主視窗漏回】,不是它掛了。先查自己的信箱再懷疑對方。**
     實錘同一夜兩次,**兩次都是 Sean 先發現的**:①`D-052` 交 plan 等裁,主視窗去處理別條線就沒回來
     ②C 窗卡 reviewer gate + D 窗問「繼續 C 組?」。
   - ⚠️ **reviewer gate 這類「需要一個非作者的人簽章」的關卡,主視窗自己就能簽** ——
     當晚主視窗誤以為只有 Sean 能跑那條命令,讓 C 窗白等一個多小時。**先問「這道關卡要的是誰?」**

【信箱協定】
- 信件命名:<窗代號>-<流水號>-<型別>.md,型別=A(主視窗派工/裁決)/STOP(施工窗停點回報)/Q(問題)/CLOSE+ACK(關窗)。
- 寫信三步:防撞號(🔴 查**號碼前綴**非完整檔名:`ls 信箱 | grep "^{代號}-{nnn}-"`,任何後綴命中=該號已用、跳號;08-09 實錘 E-041-A 與 E-041-STOP 撞號、改令被漏讀)→ cat > tmp 再 mv(原子寫)→ SendMessage 敲門鈴(內容只指向信檔名,不承載)。
- 門鈴位址:**雙向都走位址檔**——施工窗開窗第一動把自己 socket 寫進信箱 `.{窗代號}-socket`(每次重啟更新);主視窗發門鈴=讀該檔,施工窗發門鈴=讀 .main-socket。
  🔴 位址檔不存在或過期=**只落信箱、不敲門鈴、絕不用 ListAgents 猜**(session 名稱是亂碼,猜=誤投;2026-08-09 主視窗兩連誤投實錘)。絕不廣播全部視窗。SendMessage 的 to 可直接吃 uds:/tmp/cc-socks/xxx.sock。
  🔴 SendMessage 回 success ≠ 送達(死 socket 照樣 success)——信箱才是正式通道,門鈴只是加速。
- 誤投:收到不是給自己的訊息=回發送方一句「誤投」+附 .main-socket 現值。
- 關窗:發點名該窗的 CLOSE 信、收到 ACK 才算關線;開同名新窗前必先走完關窗。

【派工紀律】
- 每封派工信含三要素:目標與動機/驗收條件(逐條可 yes-no)/回報格式(結構+行數上限+
  「你的最終回覆就是回傳值」)。
- 施工窗規矩寫進開窗提示詞:完片 commit 不 push、停點寫 STOP 信、誠實申報(做到哪/剩什麼/
  哪些沒驗,「字面=事實」優先於一切)、拿不準問主視窗不直接問老闆。
- 🔴 開窗提示詞必含兩條(全文見 §C):①**所有停點**(完工/卡死/被擋/需決策/佇列空)一律落信+門鈴、
  不靜默;②決策題兩類分流:流程題主視窗直接裁、產品/資料/不可逆題寫成選項+推薦排隊給老闆,
  落完信先做不被擋的片。
- 高風險改動(錢/權限/資料庫結構/平台設定/對外發送)=對抗審查不降級、apply/上線停點=主視窗執行。

【收割紀律(主視窗自己的鐵律)】
- 只收乾淨樹(施工窗有未 commit 檔=不 merge)。
- 收割=親審 diff → merge → 驗證 → STATUS/交接檔收帳 → commit → push。
- 🔴 驗證的 exit code 一律分開驗:cmd >log 2>&1; echo EXIT=$?,禁止 cmd | tail 之後看 $?
  (pipeline 吃 exit);zsh 的 PIPESTATUS 印空(那是 bash),別用。
- 🔴 有守門檢查(測試/一致性 check)的,檢查綠才准 push——push 不准排在檢查前面的命令鏈裡。
- 🔴 測試指令先驗「真的有跑」:exit 0+零輸出=可疑;證據要 exit code+「N passed」字面兩軌。
  monorepo 用根層測試入口,pnpm --filter <pkg> test 對沒有 test script 的套件會靜默跳過裝綠。
- 老闆每拍一個板,當下寫進檔案(memory/STATUS),不留在對話裡。

【對老闆的溝通】
- 兩層報告:上層白話(影響什麼/風險/要他做什麼)+下層技術細節。
- 決策題一律 2-4 選項附推薦,用 code block 讓他 copy-paste 回答;答案會改方向的排最前。
- 回報字面=事實:做到哪、剩什麼、哪些沒驗,寧可保守不寫「應該可以」。

先照【一次性建置】做完,回報就緒,然後等我派第一個任務。
```

### §B-附 · 派工單必填一欄:**「我假設瓶頸在 X」**(2026-08-16 C 窗提,主視窗採納)

🔴 **同一夜,主視窗兩次把假設寫進了問題本身,兩次都是【被派的人】把題目修對的**:
```
① 問 A 窗「在該安靜的那棵樹上是不是真的安靜」
   ⇒ A 窗指出那是兩個問題（拿 dev 打＝假通過／拿自己的樹打＝假警報），測試對象不同
② 問 C 窗「pooler 會不會讓 SET LOCAL 失效」
   ⇒ C 窗量下去發現【交易邊界】更前面就會讓它失效，PG 還只給 WARNING
```
> **⇒ 派工單指定的觀察點,本身就是一個【未經檢驗的假設】。**
> **而動手的人會撞到派工單沒寫的東西 —— 那不是他比較聰明,是位置不同。**

**⇒ 交辦三要素之外,多一欄(一行就好)**:
```
我假設瓶頸在 X。若你撞到別的，【先報那個】，不要為了回答我的問題把它排在後面。
```
⚠️ **而它要解決的不只是「會不會發現」,是【報告的順序】** —— C 窗逐字:
> **我把最容易破的前提放在第一段、把你問的那個放在第二段。**
> **順序是有代價的:那讓我的報告【看起來像沒回答你的問題】。**
> **若下次我把它排在後面,你會先讀到「pooler:未量」,然後可能就停了。**

🔴 **所以這一欄同時是給派工者的授權**:**「先報你撞到的那個」= 我事先同意你不照我的順序答。**

## §C-0 🔴 常設動作(開窗提示詞**必含**;**用指令產出、不要手抄**)

> **為什麼有這一段**:2026-08-18 換班,`MAIN-012` 八段開窗提示詞**沒有一段**寫「STOP 即掛哨」
> (量法:`grep -c '哨兵\|掛哨\|喚醒\|sleep' ~/pcm-mailbox/MAIN-012-*.md` ⇒ **0**;
> 正向對照 `grep -c '哨兵' docs/runbooks/night-run-command-playbook.md` ⇒ **18**)。
> ⇒ 那個機制在 runbook 裡**存在了兩個月**,而當天**沒有一個窗用它** —— 因為派工單沒抄它。
> 🔴 **一份寫對的 runbook,擋不住一份沒有引用它的派工單。**
> ⇒ 所以這一段的重點**不是內容,是取得方式**:`bash scripts/window-standing-actions.sh` 印出來、整段貼。

【常設動作(每個施工窗都適用,與你的任務無關)】
1. 做完一件自己接下一件。要停只有兩種:Sean 說收工、或需要他拍板才走得下去。
   🔴🔴 **而目標是【把整個網站建置完成】,不是完成一個階段性任務。**
     (2026-08-18 Sean 常設令,逐字:**「現在任務是持續推進,沒有今晚、早上等等階段性,
      就是一直不間斷把網站完成。」** 他另交代:這條要寫進規範。)
     · **沒有班了**:不要寫「今晚 / 本班 / 明天早上再」;不要有「收尾 / 交接素材」式的結尾框架
       —— **沒有要交接給誰,你就是下一班。**
     · 🔴 **它砍掉的是一整類決策題**:任何「今晚要不要做 X」都不成立。
       實錘:那一刻主視窗桌上正卡著「真登入這條線今晚還要不要繼續投人」,
       **而 Sean 的答覆不是回答那題,是把那個框架整個拿掉。**
     · **唯一的座標**:離「網站完成」還差什麼。選題的判準因此只剩
       **哪一件更靠近完成** —— 不再有「只剩兩小時所以挑小的」。
     · 🔴 **「不間斷」= 不要停下來等一個不存在的時間點,【不是少做幾道檢查】。**
       不改變:鐵則 1-12、不 push、apply 正式庫要 Sean、三綠不繞道。
       ⚠️ 同夜反例(主視窗自己):為了快,把一條**只有 grep 命中、沒有人開過檔**的結論
       當急件送上去,**害 Sean 去正式庫跑了一句沒必要的 SQL**。**趕出來的錯,收訊者是他。**
     · 📎 與第 2 條的關係:第 2 條保證你**回得來**,本條保證你**知道要回來做什麼** ——
       「我這一輪做完了」從來不是停下來的理由,現在更不是。
2. 🔴 回合結束前,先問這一句 —— **判別句才是規矩,sleep 只是其中一種機制**:
     **我這句話送出去之後,有沒有任何東西會叫醒我?**
   有(harness 追蹤中的 subagent / **我自己起的**背景命令)⇒ **不用掛,直接結束回合**
   🔴🔴 **而「我回報了主視窗」【不算】**(2026-08-18 19:4x Sean 批;~~舊條寫「別人會回信給我」~~ 作廢):
       **我送出去的訊息不會叫醒我**,而對方會不會回、什麼時候回,**我控制不了** ——
       它可能正在寫別的信、正在跟 Sean 講話,或就是漏掉了。
       ⇒ **回報完一律掛。** 掛了之後對方回信也沒有任何損失(醒來第一動就是看新訊息)。
       實錘:2026-08-18 一個窗照舊條做,**靜了 41 分鐘,而它沒有犯規** —— 洞在規矩不在窗。
   🔴 沒有 ⇒ 掛一支背景喚醒,否則你就消失了:
       Bash 工具 run_in_background=true 跑:
         sleep 900; echo "WAKE 回合到期 —— 接下一件,或明寫我停在哪"
       · 只是在等一件短的(收割排隊 / 別窗回話)⇒ 300
   醒來第一動 = 看新訊息 + 看自己上一封說的「下一件」,然後【開始它】

    · 🔴 **`--only` 與 pathspec 擋不住這一格**:它們管的是「不要把別人的**工作樹改動**吸進來」,
      管不到「`HEAD` 根本不是我那一顆」⇒ 照樣會把**別人的 commit 訊息換成你的**。
    · **更安全的預設:根本不要 amend。** 訊息寫錯就補一顆 `docs: 更正上一顆的訊息`,
      或把更正寫進該片的檔案裡(**已投遞的東西不回改,走後續取代**)。
    實例(2026-08-18):某窗想改自己那顆的 body,而那一刻 `HEAD` 是另一個窗剛落的
    ⇒ amend 把它換成「**別人的內容 + 自己的訊息**」,原本那顆變成 orphan(`merge-base --is-ancestor` ⇒ rc=1)。
    🔴 **沒有任何東西紅**:`rc=0`、husky 全過、四綠與它無關。
    🔴 **失主那端的症狀是【自己那顆不見了】** ⇒ 下一個動作很可能是**重做一遍**,那才是真正的損失。
    📎 **歸因(比修法重要)**:那個窗前面四顆 commit **全部都帶了 pathspec** ——
    **不是它不守規矩,是規矩沒寫到這一格**;而**「只是改訊息」這個直覺,正好就是漏洞本身**。
    ⚠️ **本條同樣不是守門**(理由同第 12 條)。
    ⚠️ **本條的第一版寫錯過**:原本寫「修法 = `--amend --only`」,被失主拿量測打回
    —— **一個擋不住這件事的修法,而它讀起來完全合理。** 引用時不要把 `--only` 當解方。
    📌 **而 `--only` 仍然值得用,只是它擋的是【另一種】撞法**(把別窗剛 `git add` 的工作樹改動一起帶走)
    ⇒ **兩件都要:先驗 `HEAD` 是誰的(擋本條這種),再帶 `--only`/pathspec(擋另一種)。**
    **只做後者會讓人以為安全,而今天這件正好是它擋不到的那一種。**
    ✅ **撞到了不是永久失去**:被換掉那顆仍在物件庫,`git log --oneline -1 <hash>` 直接印得出原訊息;
    🔴 **但保護它的是 reflog(預設 90 天)、而 reflog 是這個 checkout 的私有狀態**
    ⇒ **要留就當場把 hash 與 subject 抄進一個會被 commit 的載體**,不要依賴它。

## §C-2 🔴 **「這個 PID 是哪一個窗?」—— 一發對得出來,而它有一個會騙人的陷阱**(2026-08-19 G2 量)

多窗共機時常見的題:**看到一個孤兒進程 / 一個佔著埠的 server / 一個瀏覽器 profile,想知道是哪個窗的。**

### 規則(量到的,不是推的)

```
🔴 /tmp/cc-socks/<PID>.sock 的【檔名數字】= 那個窗的 claude 進程 PID
```
**怎麼驗出來的**:本窗在同一小時內收到 7 個 peer 的 `SendMessage`,每一封都帶
`from="uds:/tmp/cc-socks/<N>.sock"` 與 `from-name="<窗名>"`。把那 7 個 `N` 與
`pgrep -f 'anthropic.claude-code.*/claude'` 的輸出比對 ⇒ **7/7 完全對上**;
再加本窗自己(從自己 shell 的父鏈量到 `7201`,而 `7201.sock` 也在)⇒ **8/8**。

### 用法(從一個可疑進程,反查它屬於哪個窗)

```bash
# 1. 從那個進程往上爬 PPID，直到撞到一個 anthropic.claude-code 的進程
P=<可疑PID>; for i in $(seq 1 8); do ps -o pid,ppid,command -p "$P" | tail -1 | cut -c1-100
  P=$(ps -o ppid= -p "$P" | tr -d ' '); [ -z "$P" ] || [ "$P" = "1" ] && break; done
# 2. 那個 claude 進程的 PID，就是 /tmp/cc-socks/<PID>.sock
# 3. 而【窗名】要靠對方自報 —— socket 檔名只給得出 PID，給不出 `pcm-website-v2-xx`
#    ⇒ ListAgents 列名字、SendMessage 問一句，兩發就對得出來
```

## 🔴🔴 共用主樹:`git commit` 之前一定要看【整個 index】,不是看你自己那支檔

**2026-08-19 深夜,同一個病在一小時內咬了【三個窗】**(G2 `79a67170` / G6 `4fe7c975` / G4 `42002997`),
兩次都是**內容零損失、歸屬錯**:別人 staged 的檔被掛進你的 commit,而你的 commit body 從頭到尾在講別的事。

### 兩條既有規矩都遵守了,而它們擋不住
```
「禁 git add . / git add -A」        ← 兩窗都遵守
「精準 pathspec」                    ← 兩窗都遵守
「git add 前跑 git diff --stat <路徑>」← 主視窗當晚交代的,G6 照做了、而且它印出來是【對的】
```
🔴 **`git diff --stat <我的路徑>` 對「index 裡有沒有別人的東西」零判別力** ——
它問的是「我那支檔的未 staged 改動」,而別人的檔**已經在 index 裡了**(他 `git add` 了、還沒 commit)。
而 `git commit` 不帶 pathspec 時,**提交的是整個 index,不是你 add 的那條路徑。**

### ⇒ 正確的那一發(在 `git commit` 之前跑,不是在 `git add` 之前)
```bash
git diff --cached --stat          # 🔴 用 --stat 不是 --name-only：要同時看【哪幾支】與【幾行】
```

🔴🔴 **`--name-only` 不夠 —— 2026-08-19 實錘:它通過了,而那顆 commit 還是掃走了別人的東西**
```
G3 跑 git diff --cached --name-only ⇒ 印出 docs/phase-1-backlog.md（只有一支，而且確實是它的檔）
⇒ 檢查通過 ⇒ commit ⇒ 那顆帶走 59 行，而它自己只改了 3-4 行
   多出來的是【另一個窗】append 在同一支檔別的位置的整段
```
⇒ **因為 `--name-only` 問的是「哪幾支檔」,不是「這支檔裡有誰的行」。**
📌 **判別句**:**這支檔是不是【現在有別人也在寫】的共用檔?**
   是 ⇒ `--name-only` 不夠,**要看 `--stat` 的行數對不對得上我改的量**。
```
git diff --cached --stat
⇒ 我改了 4 行，而它印 59 行 ⇒ 當場看得出來不對
```
⚠️ **`docs/phase-1-backlog.md` 是全 repo 最熱的一支**(2026-08-19 一夜至少四個窗在寫)。
📎 這與 memory `feedback_precise-path-does-not-stop-a-shared-file` 同族而**多一層**:
   那條講「精準路徑擋不到共用檔」,**這一格更細 —— 連【檢查了檔名】都還是會中。**
**或**直接讓 commit 自己指名(兩道都做最好):
```bash
git commit -F <訊息檔> -- <你的精確路徑> [<路徑2> …]
```

### 📌 判別句
> **我檢查的是「我的檔對不對」,還是「這一顆 commit 會帶走什麼」?** —— 兩個問題不一樣。
> **`git add` 是我控制的,`index` 不是。** 精準路徑管的是前者,而 commit 帶走的是後者。(G4 補)

🔴 **分母是三,不是二** —— 第一版寫「兩個窗」是因為第三個窗的自首與廣播交錯。
**低估基準率會讓下一個人以為這是偶發。** 而它在一小時內發生三次,三個窗都遵守了既有的兩條規矩。
📎 兩個方向要分開記:**吞人的**(G2/G6/G4)與**被吞的**(G1 的 `#309` 座標落進 G6 的 `4fe7c975`)——
成因不同:前者是自己 commit 沒帶 pathspec,後者是自己 add 了而別人先 commit。

🔴 **「被吞的那方做不了任何防護」這句 2026-08-19 被 G6 從內部推翻,收窄如下** ——
**被吞方能做的只有【縮短自己暴露的時間窗】**,而那個窗常常是自己拉長的。G6 那次三步、每一步都不報錯:
```
1. Bash 被 classifier 逾時中斷 ⇒ heredoc 沒寫成,commit 訊息檔【不存在】
2. 重跑 `git add … && git commit -F <不存在的檔> … | head -3 && git show …`
   ⇒ add 成功、commit 失敗、而 git show 照樣跑了(pipeline 的 rc 是 head 的 0)
3. ⇒ 檔留在共用 index 裡,而當事人以為自己 commit 完了
```
**兩條自保(比機制早生效,今天就能做)**:
```
① commit 訊息檔要在 git add 之【前】寫好並 test -s 驗過
   —— 訊息檔不存在 ⇒ commit 必失敗 ⇒ 而 add 已經發生了
② 🔴 git commit 後面永遠不要接管線:
      git commit -F "$MSG" -- <路徑> > out 2>&1 ; rc=$?
      cat out ; [ $rc -eq 0 ] && … || echo "🔴 commit 失敗 rc=$rc"
```
📌 **判別句:我怎麼知道 commit 成功了?**
「命令跑完沒噴紅」不算 —— **接了管線之後,失敗的 git 與成功的 git 印出來的東西一樣少。**

📌 另一條(GR 拋棄式 repo 實測):**當一個資源是共用的,防護只能裝在【寫入的那一端】** ——
`窗A: git add a.txt` / `窗B: git commit -m "only b" -- b.txt` ⇒ commit 只帶走 b.txt,**a.txt 仍在 index、原封不動**。
⇒ 帶 pathspec 完全不碰別人的 index;加害端被擋的那一刻,受害端就被保護了。

### 📎 G2 那次的成因值得單獨記(它不是粗心)
它寫的是一整條 `git add <精確路徑> && git commit -F <檔>`。
**那一整條被 PreToolUse 守門擋掉了,而它以為只有 commit 那半被擋** ⇒ 把 commit 那半單獨重跑
⇒ **`git add` 那半從來沒有執行過** ⇒ 沒有 pathspec 的 commit 吃掉了共用 index。
🔴 **一條被擋的 `A && B`,`A` 也沒有跑。** 重跑之前先確認你要重跑的是哪一半。

### 🔴 空 commit **也不安全**(2026-08-19 G2 落訃聞時撞到)
```
git commit --allow-empty -F <檔>            ⇒ 🔴 仍會把【別人 staged 的檔】一起帶走
   實測:git diff --cached --name-only ⇒ docs/phase-1-backlog.md（別人的）
安全寫法:
git commit --allow-empty --only -F <檔> -- <一個你自己的、沒有改動的檔>
   ⇒ 產出 0 個檔的空 commit，別人的東西沒被動到
```
📌 **「空 commit 沒有內容所以無害」是錯的** —— 無 pathspec 的 commit 帶走的是 index，與它自己有沒有改動無關。

### 🔴🔴 `git commit --amend` 在共用主樹是【比無 pathspec 更毒】的一種
2026-08-19 實錘:G2 以為在 amend 自己那顆,而**共用主樹的 HEAD 在它打字的期間被別人推前了**
⇒ 它 amend 掉的是**另一個窗五秒前剛落的那顆**(`e324a966` → `1827b578`)。
```
內容零損失（git diff <舊> <新> --numstat ⇒ 無輸出，兩顆 tree 相同）
丟掉的是【那顆 commit 的訊息】—— 而訊息裡有別處沒有的東西
```
🔴 **病根與無 pathspec 不同**:前者是「**範圍沒指定**」,後者是「**目標(HEAD)在我不知情的時候換了人**」。
⇒ **寫了第一條防不住第二條 —— 那不是紀律問題,是那條規則的射程本來就不涵蓋它。**
⇒ 📌 **一條規則擋住的世界,比它讀起來像擋住的世界窄。**

**處置**:共用主樹**不要用 `--amend`**。要修訊息 ⇒ **補一顆空 commit 當訃聞**(用上面那個安全寫法),不要 rebase。
🔴 而**同族的第三個變形還沒被涵蓋**:`git rebase` / `git reset --hard` **也都是對當下的 HEAD 動手**。
   ⚠️ 沒有人踩過它們,所以**不知道實際形狀** —— 而依今晚的紀錄,**同一母題的下一個變形看起來不會像同一件事**。

### 出事之後怎麼處置(兩窗給了相反而各自正確的答案)
- **index 現在乾淨、事故那顆是上一顆** ⇒ `git reset --soft HEAD~1`(不動 index、不動工作樹)
  → 帶 pathspec 重 commit → `git diff <壞的那顆> -- <那些檔>` 應無輸出(證明內容一字沒動)。**G2 這樣做,對。**
- **別的窗正在寫、index 裡有進行中的動作** ⇒ **不要 reset、不要改歷史**。
  **一個歸屬錯誤不值得換一個併發事故。** 改由主視窗記進桌面狀態 + 原作者在下一顆 commit body 認領。**G6 這樣判,也對。**

## 🔴🔴 同檔並寫:pathspec 逃生門對它【零判別力】(2026-08-19,一夜四次)

```
git commit -F <msg> -- <pathspec>
  擋得住  別人的【別的檔】被我帶走
  擋不住  別人在【同一支檔】上的未 commit 改動
```
**機制性理由**:`git commit -- <path>` 提交的是**那支檔當下的工作樹全貌**,**不是「我 stage 的那幾行」**。
⇒ 只要兩個窗同時在寫同一支檔,**先 commit 的那個必然帶走後者。**
🔴 **`guard-commit-pathspec` hook 也擋不到** —— 它看的是 pathspec 有沒有給,而這裡給了。

**判別句**:**這支檔是不是現在有別人也在寫的共用檔?**
是 ⇒ `--name-only` 不夠,要 **`git diff --cached --stat`** 看行數對不對得上我改的量。

### 🔴🔴🔴 最終版(2026-08-19 G4 實錘推翻前兩版)——**不要用 pathspec commit**
```
🔴 病灶：git commit -- <path> 取的是【工作樹】，而 git diff --cached 讀的是【index】
        ⇒ 兩道檢查與那一發 commit，讀的是【兩個不同的世界】

G4 實測：git add（index 30 行）→ G6 在這中間寫檔（工作樹變 70 行、index 沒變）
         → git diff --cached --stat 印 30 ⇒【通過】
         → git commit -F <檔> -- <path> 從【工作樹】取 ⇒ 進去 70 行
⇒ 兩道檢查都跑了，而它們對這個形狀【零判別力】
```
📌 **判別句(G4 給的)**:**我檢查的那個東西,和 commit 真正讀的那個東西,是同一份嗎?**

**⇒ 正確做法:走 index 那條路,不要用 pathspec**
```bash
1. git diff --cached --stat            # add 之前：index 裡有沒有【別人的】？有 ⇒ 停，不要 add
2. git add <你的精確路徑>               # 禁 git add . / -A
3. git diff --cached --stat            # 再看一次：只有你的檔、行數對得上你改的量
4. git commit -F <訊息檔>               # 🔴 不帶 pathspec ⇒ 它吃【index】= 你剛驗過的那份
```
🔴 **第 4 步不帶 pathspec 是關鍵** —— 帶了它就改讀工作樹,而你驗的是 index。

### 🔴🔴 而「一律不帶 pathspec」也是錯的 —— **按【碰撞位置】選,不是二選一定死**(2026-08-19 G6 補)
```
碰撞在【別的檔】      ⇒ 🔴 用 pathspec（它擋得住；不帶 pathspec 會把別人的別的檔一起吃掉）
碰撞在【同一支檔】    ⇒ pathspec 擋不住 ⇒ 只能【等對方先 commit】，沒有第三條路
index 乾淨（沒有別人）⇒ 不帶 pathspec（吃你剛驗過的那份 index）最準
```
**G6 的實例**:它要 commit `scripts/who-is-touching.sh`,而 `git diff --cached --stat` 印出 index 裡有**別人的 `#661` plan(47 行)**
⇒ 不帶 pathspec 會吃掉它;而**沒有任何人在動那支 `.sh`** ⇒ **用 pathspec 是安全的**。
📌 **判別句:我這一發的碰撞在哪裡?** —— 先答這個,再選寫法。**兩種方法各漏一半,而漏的不是同一半。**
⚠️ ~~這條路唯一擋不到的是「別人在 1 與 2 之間 stage 東西」—— 而第 3 步會抓到~~
🔴 **那句話不對,而推翻它的是同一晚的兩個實例** —— 見下面 v5。
🔴 **共用主樹永不 `--amend`**。

## 🔴🔴 v5(2026-08-19 深夜,主視窗自己推翻 v4 的一半)——**三格,其中兩格是今晚剛長出來的**

> 🔴 **這一段推翻主視窗自己先前那一裁「index 乾淨就不帶 pathspec」。原裁定留在上面不刪。**
> 而推翻它的不是道理,是**兩個窗各撞一次的實例**。

### A · **檢查與 commit 之間有時間窗(TOCTOU)** —— 這不是誰忘了跑,是**方法本身的邊界**
```
某窗的實際順序（照 v4 三分法：index 空 ⇒ 不帶 pathspec）:
  1. git diff --cached --stat  ⇒ 空 ✅
  2. git add <我的檔>
  3. git diff --cached --stat  ⇒ 只有我的 ✅
  4. git commit                ⇒ 🔴 **實際帶走 2 支檔**（別窗在第 3 步之後 add 進來的）
🔴 那一發還噴了 `fatal: cannot lock ref 'HEAD'`（HEAD 在 commit 途中被推進），**而 commit 仍然成立**
```
⇒ **檢查與 commit 是兩個操作 ⇒ 中間永遠有窗。**
```
帶 pathspec   ⇒ 擋得住【別人的別的檔】，擋不住【同檔並寫】
不帶 pathspec ⇒ 吃 index ⇒ 擋不住【檢查之後才進來的別人的檔】
🔴 **兩種各漏一半，而漏的不是同一半。**
```

### B · 🔴 **那道檢查在兩個世界印一樣的東西 ⇒ 它是日誌,不是閘**
某窗的原句(**逐字**):
```bash
n=$(git diff --cached --name-only | wc -l); echo "index 檔數=$n" && git add … && git commit …
# 它印出：index 檔數=1   ← 🔴 1 就代表裡面有別人的東西
# 然後：`&&` 串接繼續往下跑
```
⇒ **對「該不該繼續」,它的判別力是【零】。**
⚠️ **而它讀起來完全像一道檢查** —— 有變數、有數字、有標籤,**輸出裡甚至印著正確答案**。
🔴 **錯的不是那個數,是那個數【沒有連到任何一個分支】。**
📎 而 `&&` 為什麼會吃掉壞消息:**前一步 `echo` 的 exit code 永遠是 0** ——
**它把壞消息的語氣帶走了、只留下字面。**

**⇒ 標準寫法(照抄,不要用 `echo`)**:
```bash
n=$(git diff --cached --name-only | wc -l | tr -d ' ')
[ "$n" = "0" ] || { echo "🔴 index 有別人的東西($n 個檔)，停"; exit 1; }
```

### ⇒ v5 三條(取代 v4 的第一步與選型)
```
① 🔴 第一步一律用【條件式】，不用 echo —— **印出來的數字沒有連到分支，就不是閘**
② 🔴 **一律帶 pathspec —— 即使 index 乾淨**
   理由:兩種寫法各漏一半，而【同檔並寫本來就無解】
   ⇒ 那就把「別人的別的檔」這一半**關死**，少一個變因
   ⚠️ **這推翻主視窗先前「index 乾淨就不帶」那一裁**，而理由是今晚湊齊的兩個實例
③ 🔴 commit 後一律 `git show --stat` 對檔數與行數 —— **那是唯一抓得到 TOCTOU 的地方**
```
⚠️ **v5 仍然擋不住的**:**同一支檔並寫**。那一格無解 —— `git diff --cached` 只看得到「**已經 add 的**」,
看不到「**正在寫的**」。⇒ **熱檔(`docs/phase-1-backlog.md` / `STATUS.md` / `docs/patterns/index.md`)動之前用
`SendMessage` 問一句「你在動 X 嗎」,或跑 `scripts/who-is-touching.sh`**
(⚠️ **而那支腳本有已知瞎區:41 支裸檔名零判別力,它自己輸出裡寫著**)。
🔴 **而【問】也擋不住「對方正在寫而還沒 add」** —— **那不是工具不好,是 git 沒有那個資訊。**

### （舊版·已被上面取代，留著看演化）完整版順序(2026-08-19 G6 補 —— **原本那條晚了一步**)
```

## 更正要怎麼寫 —— 而「劃線留原文」不是最強的那一版

2026-08-19 夜實際發生：一份給 Sean 讀的清單被更正過六次。
主視窗以為自己在做「劃線留原文」，而審查窗去查那四句被撤回的原文**還在不在檔裡**：

```
四句全部只出現 1 次 —— 而那一次【就在更正塊自己裡面】當引述
⇒ 🔴 原文被【刪掉】了，只以引述的形式活在更正裡
⇒ 而那比劃線強：**沒有一句舊的可以被單獨讀到**
```

### 三種寫法，強度不同

```
弱   原文留著、更正寫在下面      ⇒ 從上往下讀的人【先讀到錯的】
中   原文劃線、更正寫在下面      ⇒ 他會讀到，而【劃線可能被忽略】（尤其在長檔裡）
🔴 強 原文【刪掉】，只在更正塊裡當引述
     ⇒ 「我原本寫：『…』——那句錯在 X，正解是 Y」
     ⇒ 舊句子【失去它自己的段落】⇒ 沒有任何讀法會單獨遇到它
```

⚠️ **而「強」不是永遠對的**：
```
· 舊句子若被【別人引用過】（別的檔、別的信）⇒ 要留得住那個錨 ⇒ 用「中」
· 舊句子若是【拍板、授權、誰批的】⇒ 🔴 一律不刪（見下一節）
· 而【訃聞的用途是給下一個人看見這裡曾經有東西】⇒ 那時「中」比「強」對
```

### 🔴 而這一條為什麼要寫下來

它原本只是一個習慣 —— **而做對了卻不知道自己做對，就沒有人會去保護它**。
下一次換一個人寫更正，它會自然退回到「劃線留原文」，而那弱一級。

📌 而**判準**：
> **這一句被撤回的話，還有沒有辦法【被單獨讀到】？**
> 有 ⇒ 那個讀法就是下一個誤解的入口。

## 什麼時候可以「先報再查」，什麼時候要「查到底才報」

2026-08-19 夜：一個窗查一段安全面註解的出處，中途讀到的證據指向
「一個設計決定掛著一個不存在的拍板結案了」。**它沒有在那一刻發警報。**
繼續查之後，那個結案是真的 —— 錯的只是那段註解引用的**編號**。

### 🔴 判準（那個窗自己寫出來的）

> **這封警報若是假的，收訊者會【啟動什麼】？**
> ```
> 啟動一條線（重新調查、通知別人、回頭改東西）⇒ 🔴 查到底再報
> 只是多讀一段（他看一眼、知道有這回事）      ⇒ 可以先報
> ```

**理由**：假警報的成本不是「說錯一句話」，是**收訊者照它動了**。
而一個指揮位置的人，收到「某段安全註解在說謊」時的預設動作**就是啟動一條線**。

### ⚠️ 而它與「不要靜默」不衝突

```
· 卡住了、在等什麼         ⇒ 立刻說（那是狀態，不是指控）
· 我判它比標籤說的更嚴重   ⇒ 立刻說（今晚有窗這樣做，而它是對的）
🔴 而【一個會讓人回頭改東西的指控】⇒ 查到底
```
判別不是「重不重要」，是**收訊者會不會據此動手**。
