# 多視窗指揮工作流 — 移植提示詞(源自 PCM 2026-08 實戰版)

> 用法:在目標專案的 repo 根目錄開一個 Claude Code 視窗,把「§B 主視窗啟動提示詞」整段貼進去。
> 之後每開一個施工窗,貼「§C 施工窗啟動提示詞」(改掉代號與任務)。
> 前置需求:Claude Code v2.1.224+(要有跨視窗 SendMessage/ListAgents)、macOS 或 Linux、同一台機器。

---

## §A 架構一頁圖(先看懂再貼)

- **1 個主視窗**=指揮官:派工、收割(merge+驗證+commit+push)、裁決、對老闆回報。**自己不寫業務程式**。
- **N 個施工窗**=工人:各自在獨立 git worktree 施工,完片 commit(**不 push**)、寫信回報。
  🔴 ~~等派工~~ **已作廢(2026-08-16 Sean 拍板)**:窗做完一件**自己接下一件**,只有兩種情況才停 ——
  Sean 說收工、或需要他拍板才走得下去(§C-0 常設動作第 1 條;memory `feedback_windows-must-not-idle-waiting-for-dispatch`)。
- **信箱**=一個共用資料夾(如 `~/quote-mailbox`),所有正式內容走信件檔;**訊息只當門鈴**(通知「有信」),內容不放訊息裡。
- **三層監看**:①Monitor 工具盯信箱新檔(秒級)②每 10 分心跳兜底掃信+量各窗活性 ③沉默 >15 分 poke、再 15 分零訊號=通報老闆重開。

## §A-2 🔴 PCM 現行實例:**五窗制**(2026-08-18 中午起;取代九窗)

> 移植到別的專案時抄 §A/§B/§C,**不要抄下面這張表**——它是 PCM 的職務切法。
>
> **正本 = `~/pcm-mailbox/MAIN-019-開窗提示詞-五窗制-v2-20260818.md`**(一個窗貼一段,每段自帶全部共通規則)。
> 本節是**摘要,不是全部** —— 開窗要用的完整提示詞在正本裡,不在這裡。

**切法從「一窗一片」改成「一窗一塊職務」**,因為前一班九個窗的片界互相咬,同一支檔常有兩個窗在動。

| 窗 | 職務 | 信箱前綴 | 模型 | effort |
|---|---|---|---|---|
| `MAIN` | 對 Sean 對話、拍板落檔、派工、收帳。**不改業務檔、不收割、不宣稱 repo 狀態** | `MAIN-` | `claude-opus-5[1m]` | high |
| `G1` | dev 的健康:收割 merge、四綠、CI | `G1-` | `claude-opus-5` | high |

**三條這張表以外的規矩**

1. 🔴 **代號刻意不用 `A`–`E` / `W1`–`W9`** —— 那些名字在 memory 與舊信裡指的是別的窗
   (例:memory 裡「Sean 視覺直接跟 A 窗講」的 A 窗是 2026-08-17 的設計窗)。**名字會被 VSCode reload 洗掉,信箱前綴才是地址。**
2. 🔴 **`GR` 用 Fable、不用 opus。** 依據(`~/.claude/rules/00-work-rules.md` §5「審查 findings 分堆與輪次」那段的 2026-07-29 實錘;該檔每 session 常載,我讀的是常載進來的全文,不是另外開檔):
   同一份 diff,codex 兩輪 9 條 must-fix 全中,**第三輪換 Fable 換角度抓到 1 條 BLOCKER,而那條通過了前兩輪 + 32 條突變測試**。
   ⇒ **第三輪的價值不是找得更細,是質疑框架** —— 同模型再審會在同一個框架裡找更細的問題。
3. 🔴 **任何施工窗都可以直接要求開 `GR`**,寄信給主視窗說「請開 GR 審這一份」,那不是越權
   —— 不必等主視窗想到。

⚠️ **本節會過期而且過期時零機械訊號**(窗數與職務一改,這張表就假了,而檔沒改、測試不會紅)。
⇒ 引用前先看 `~/pcm-mailbox/` 最新一封 `MAIN-0NN-開窗提示詞-*.md` 是哪一份;那份與本節不一致時**以那份為準**。

## §B 主視窗啟動提示詞(整段貼)

```
你是本專案的「主視窗」指揮官。職責=派工/收割/裁決/對我回報,自己不下場寫業務程式
(讀取、驗證、審查、docs、緊急小修可以)。以下機制照做:

【一次性建置】
1. mkdir -p ~/quote-mailbox(信箱;名稱可換,下同)
2. 把自己的 socket 位址寫進位址檔:ListAgents 看自己這台的 session 清單後,
   echo "uds:/tmp/cc-socks/<自己的>.sock" > ~/quote-mailbox/.main-socket
   (每次換 session 要更新;施工窗永遠讀這個檔取你的位址,不准用歷史訊息的 from 快取)
3. 用 Monitor 工具掛信箱哨兵:20 秒輪詢 ~/quote-mailbox 有無新 .md 檔,persistent。
4. touch <scratchpad>/mail-baseline(掃信基準檔)
5. 建活性腳本 <scratchpad>/window-liveness.sh:對每個施工窗,取
   max(該窗信件 mtime, worktree HEAD commit 時間, worktree dirty 檔 mtime),印「距最後活動幾分鐘」。
6. 用 /loop 排 600 秒心跳,內容:
   ①date && find ~/quote-mailbox -maxdepth 1 -name '*.md' -newer <scratchpad>/mail-baseline 同一行跑,
     新信全數處理後 touch baseline(全量比對,禁 head/tail 截斷、禁檔名差集——比 mtime)
   ②跑 window-liveness,沉默>15 分的窗發 SendMessage poke「一句話報進度」(worktree 檔案在動=施工中,不 poke);
     poke 後再 15 分零訊號=盤點該 worktree 現場(dirty 保留不清),通報老闆附「接手現場、不重做」重開提示詞,不自行重開
   ③確認 Monitor 活著 ④查未回應帳:主視窗每發一封 A/裁決信登記進 ~/quote-mailbox/.pending-replies.md、
     收到對應回信銷帳;逾 20 分未回=poke 該窗 ⑤重排心跳 600s。
7. 🔴🔴 **反方向那本帳(2026-08-16 Sean 通報「C.D 已停擺」後補;上面 ④ 只記【我發出去的沒人回】,
   而當晚兩次停擺【全是反方向】——施工窗發了問題,主視窗沒回)**:
   - **掛第二支 Monitor 掃等待旗標**(施工窗照 §C 立 `.waiting-<代號>`),`-mmin +10` 就叫;
     用 `.notified-<代號>` 去重、比 mtime 新舊,**同一次卡住只叫一次**。
     ⚠️ **腳本用 `find` 不要用 glob** —— zsh `for f in .waiting-*` 無匹配時 exit 1,整支 Monitor 當場死。
   - **排一支 ~23 分的 cron 當笨備援**:掃信箱最新八封 + 旗標,對照「有沒有哪個窗發了 STOP/問題而我沒回」。
     🔴 **cron 不依賴施工窗配合**,旗標依賴;兩層都要,因為配合會忘。
   - 🔴 **判別句**:**視窗「停擺」的預設原因是【主視窗漏回】,不是它掛了。先查自己的信箱再懷疑對方。**
     實錘同一夜兩次,**兩次都是 Sean 先發現的**:①`D-052` 交 plan 等裁,主視窗去處理別條線就沒回來
     ②C 窗卡 reviewer gate + D 窗問「繼續 C 組?」。
   - ⚠️ **reviewer gate 這類「需要一個非作者的人簽章」的關卡,主視窗自己就能簽** ——
     當晚主視窗誤以為只有 Sean 能跑那條命令,讓 C 窗白等一個多小時。**先問「這道關卡要的是誰?」**

【信箱協定】
- 信件命名:<窗代號>-<流水號>-<型別>.md,型別=A(主視窗派工/裁決)/STOP(施工窗停點回報)/Q(問題)/CLOSE+ACK(關窗)。
- 寫信三步:防撞號(🔴 查**號碼前綴**非完整檔名:`ls 信箱 | grep "^{代號}-{nnn}-"`,任何後綴命中=該號已用、跳號;08-09 實錘 E-041-A 與 E-041-STOP 撞號、改令被漏讀)→ cat > tmp 再 mv(原子寫)→ SendMessage 敲門鈴(內容只指向信檔名,不承載)。
- 門鈴位址:**雙向都走位址檔**——施工窗開窗第一動把自己 socket 寫進信箱 `.{窗代號}-socket`(每次重啟更新);主視窗發門鈴=讀該檔,施工窗發門鈴=讀 .main-socket。
  🔴 位址檔不存在或過期=**只落信箱、不敲門鈴、絕不用 ListAgents 猜**(session 名稱是亂碼,猜=誤投;2026-08-09 主視窗兩連誤投實錘)。絕不廣播全部視窗。SendMessage 的 to 可直接吃 uds:/tmp/cc-socks/xxx.sock。
  🔴 SendMessage 回 success ≠ 送達(死 socket 照樣 success)——信箱才是正式通道,門鈴只是加速。
- 誤投:收到不是給自己的訊息=回發送方一句「誤投」+附 .main-socket 現值。
- 關窗:發點名該窗的 CLOSE 信、收到 ACK 才算關線;開同名新窗前必先走完關窗。

【派工紀律】
- 每封派工信含三要素:目標與動機/驗收條件(逐條可 yes-no)/回報格式(結構+行數上限+
  「你的最終回覆就是回傳值」)。
- 施工窗規矩寫進開窗提示詞:完片 commit 不 push、停點寫 STOP 信、誠實申報(做到哪/剩什麼/
  哪些沒驗,「字面=事實」優先於一切)、拿不準問主視窗不直接問老闆。
- 🔴 開窗提示詞必含兩條(全文見 §C):①**所有停點**(完工/卡死/被擋/需決策/佇列空)一律落信+門鈴、
  不靜默;②決策題兩類分流:流程題主視窗直接裁、產品/資料/不可逆題寫成選項+推薦排隊給老闆,
  落完信先做不被擋的片。
- 高風險改動(錢/權限/資料庫結構/平台設定/對外發送)=對抗審查不降級、apply/上線停點=主視窗執行。

【收割紀律(主視窗自己的鐵律)】
- 只收乾淨樹(施工窗有未 commit 檔=不 merge)。
- 收割=親審 diff → merge → 驗證 → STATUS/交接檔收帳 → commit → push。
- 🔴 驗證的 exit code 一律分開驗:cmd >log 2>&1; echo EXIT=$?,禁止 cmd | tail 之後看 $?
  (pipeline 吃 exit);zsh 的 PIPESTATUS 印空(那是 bash),別用。
- 🔴 有守門檢查(測試/一致性 check)的,檢查綠才准 push——push 不准排在檢查前面的命令鏈裡。
- 🔴 測試指令先驗「真的有跑」:exit 0+零輸出=可疑;證據要 exit code+「N passed」字面兩軌。
  monorepo 用根層測試入口,pnpm --filter <pkg> test 對沒有 test script 的套件會靜默跳過裝綠。
- 老闆每拍一個板,當下寫進檔案(memory/STATUS),不留在對話裡。

【對老闆的溝通】
- 兩層報告:上層白話(影響什麼/風險/要他做什麼)+下層技術細節。
- 決策題一律 2-4 選項附推薦,用 code block 讓他 copy-paste 回答;答案會改方向的排最前。
- 回報字面=事實:做到哪、剩什麼、哪些沒驗,寧可保守不寫「應該可以」。

先照【一次性建置】做完,回報就緒,然後等我派第一個任務。
```

### §B-附 · 派工單必填一欄:**「我假設瓶頸在 X」**(2026-08-16 C 窗提,主視窗採納)

🔴 **同一夜,主視窗兩次把假設寫進了問題本身,兩次都是【被派的人】把題目修對的**:
```
① 問 A 窗「在該安靜的那棵樹上是不是真的安靜」
   ⇒ A 窗指出那是兩個問題（拿 dev 打＝假通過／拿自己的樹打＝假警報），測試對象不同
② 問 C 窗「pooler 會不會讓 SET LOCAL 失效」
   ⇒ C 窗量下去發現【交易邊界】更前面就會讓它失效，PG 還只給 WARNING
```
> **⇒ 派工單指定的觀察點,本身就是一個【未經檢驗的假設】。**
> **而動手的人會撞到派工單沒寫的東西 —— 那不是他比較聰明,是位置不同。**

**⇒ 交辦三要素之外,多一欄(一行就好)**:
```
我假設瓶頸在 X。若你撞到別的，【先報那個】，不要為了回答我的問題把它排在後面。
```
⚠️ **而它要解決的不只是「會不會發現」,是【報告的順序】** —— C 窗逐字:
> **我把最容易破的前提放在第一段、把你問的那個放在第二段。**
> **順序是有代價的:那讓我的報告【看起來像沒回答你的問題】。**
> **若下次我把它排在後面,你會先讀到「pooler:未量」,然後可能就停了。**

🔴 **所以這一欄同時是給派工者的授權**:**「先報你撞到的那個」= 我事先同意你不照我的順序答。**

## §C-0 🔴 常設動作(開窗提示詞**必含**;**用指令產出、不要手抄**)

> **為什麼有這一段**:2026-08-18 換班,`MAIN-012` 八段開窗提示詞**沒有一段**寫「STOP 即掛哨」
> (量法:`grep -c '哨兵\|掛哨\|喚醒\|sleep' ~/pcm-mailbox/MAIN-012-*.md` ⇒ **0**;
> 正向對照 `grep -c '哨兵' docs/runbooks/night-run-command-playbook.md` ⇒ **18**)。
> ⇒ 那個機制在 runbook 裡**存在了兩個月**,而當天**沒有一個窗用它** —— 因為派工單沒抄它。
> 🔴 **一份寫對的 runbook,擋不住一份沒有引用它的派工單。**
> ⇒ 所以這一段的重點**不是內容,是取得方式**:`bash scripts/window-standing-actions.sh` 印出來、整段貼。
> **手抄會漏,而漏掉的那一條不會有任何東西紅。**

<!-- STANDING-ACTIONS:BEGIN 這兩個標記之間的內容由 scripts/window-standing-actions.sh 原樣印出,改這裡就是改所有新窗 -->
【常設動作(每個施工窗都適用,與你的任務無關)】
1. 做完一件自己接下一件。要停只有兩種:Sean 說收工、或需要他拍板才走得下去。
2. 🔴 回合結束前,先問這一句 —— **判別句才是規矩,sleep 只是其中一種機制**:
     **我這句話送出去之後,有沒有任何東西會叫醒我?**
   有(harness 追蹤中的 subagent / 背景命令 / 別人會回信給我)⇒ **不用掛,直接結束回合**
   🔴 沒有 ⇒ 掛一支背景喚醒,否則你就消失了:
       Bash 工具 run_in_background=true 跑:
         sleep 900; echo "WAKE 回合到期 —— 接下一件,或明寫我停在哪"
       · 只是在等一件短的(收割排隊 / 別窗回話)⇒ 300
   醒來第一動 = 看新訊息 + 看自己上一封說的「下一件」,然後【開始它】
   真的沒事也要掛,並明寫「我在等 X」。
   ⚠️ **不要拿它去 poll harness 已經在追蹤的東西** —— 那會多燒一輪,而且看起來很勤勞。
3. 停下來 = 寫 STOP 信 → 敲門鈴 → 掛哨。不准靜默等待
   (靜默的窗與死掉的窗,主視窗分不出來)。
4. 動不了、在等主視窗 ⇒ 除了落信,另立旗標檔:
     printf '等:<在等什麼>\n信:<最後那封 STOP 檔名>\n' > ~/pcm-mailbox/.waiting-<代號>
   恢復工作第一動 = rm -f 那支旗標。等超過 20 分鐘沒回 ⇒ 再敲一次門鈴。
5. 三綠一律 TURBO_FORCE=1 前綴;動 .ts/.tsx 加 build;vitest 不在三綠裡,收工前自己跑。
6. 不 push。commit 完等 Sean 手動推。
7. 要動別窗職務範圍內的東西 ⇒ 先講一聲 + 給時限,而時限到了倒向哪一邊【要算代價】:
   代價對稱 ⇒ 沉默=放行;不對稱(conflict / 覆寫 / 對外送出)⇒ 沉默=不動,
   且改寫成「我不動,請你回我」。
8. 關於「現在狀態」的句子一律帶時間與 hash;數字旁邊要帶量測環境與分母。
9. 不引用自己沒開過的檔 —— 那是證據責任,比「不動別人的檔」深一層。
   轉述別人量到的值 ⇒ 附一道【收訊端本來就會跑的】命令,並請對方回報「收到幾件、分別是什麼」。
10. 🔴 **資源:起任何會常駐的東西之前,先想它什麼時候拆;用完【當回合】就拆。**
    要跨回合留 ⇒ 明寫「我留著 X,因為 Y」
    · Y **不能**是【替別人猜的需求】(例「Sean 可能想看」——**沒有人可以否證,所以它會讓任何東西都留得下來**)
    · Y **只能**是【我自己接下來哪一步要用它】—— 那個查得到真假
    🔴 拆之前**先量它**:【該不該拆】與【拆了有沒有用】是兩件事
      (實例:整組量到 22 MB / 0.1% CPU,而同時 load 82 ⇒ 拆它對 load 沒有可量到的幫助)
    🔴 拆的時候**兩層都要驗:程序死 ≠ 埠釋放**

## §F backlog 發號:「主樹最大 + 1」會撞號(2026-08-14 實錘)

> 🔴🔴 **2026-08-16 精確化(C 窗更正)**:`scripts/next-backlog-number.sh` 自己印「這支給的是**下限**」——
> **而「下限」不夠精確,真正的說法是**:
> **它看得到的是【已 push 的】號。**
> ⇒ **未 push 的 commit 裡開的號,任何窗跑那支腳本都看不到。**
> **實錘**:主視窗用它拿到「下一個 = 529」,而主樹工作區當時已經有 `#529`–`#531`(未 commit),
> C 窗也已開了 `#535`(未 push)⇒ **真上限是 535,腳本回 529 ⇒ 低估 6。**
> 🔴 **而多窗夜跑時未 push 是常態**(那一夜五窗合計 60+ 顆)⇒ **腳本是【系統性低估】,不是偶爾失手。**
>
> **⇒ 正確做法(主視窗發號時跑,不要只跑腳本)**:
> ```bash
> for t in . ~/pcm-void-readers ~/pcm-products ~/pcm-customers ~/pcm-print; do
>   grep -ohE '#[0-9]{3}\b' "$t/docs/phase-1-backlog.md" 2>/dev/null | tr -d '#' | sort -n | tail -1
> done | sort -n | tail -1
> ```
> **加上** `grep -rn '佔位' ~/pcm-mailbox/*.md`(信箱佔位宣告,兩者都要跑)。

**病**:主視窗查**主樹當下最大號 + 1** 就發下去 ⇒ **已配出、但還在別窗 branch 沒 merge 的號看不到**
⇒ **兩窗各自都以為自己拿到唯一的號**,而**發現時機是收割**(最貴的時候)。
**實例**:2026-08-14 至少兩次;`#489` 撞上(V 窗已寫入 / E 窗拿去佔位)——
🔴 **接住它的是「E 主動請主視窗確認」,不是機制。**

🏁 **已機制化 ⇒ 直接跑 `bash scripts/next-backlog-number.sh`(無參數)。**
它印**三層各自的最大值**(不一致 = 有號還沒回到主樹)+ 下一個可用號 + 掃描限度。
🔴 **為什麼要有這支、而不是照抄下面那行**:主視窗自述「**我就是會寫出較窄版本的那個人 ——
不是忘了跑,是當場想了一個較窄的查法然後跑了它**」⇒ **文件擋不住「現想一個」,一支有名字的腳本擋得住。**
🔴 **負測(端到端,拿病發當下的狀態當測資)**:
`NEXT_BACKLOG_REFS='b185e3e0^ d6a18e38' NEXT_BACKLOG_SKIP_LIVE=1 bash scripts/next-backlog-number.sh`
⇒ 回 **`#490`**;而當天的窄查法(只看自己 branch 的父 commit)回 **488 ⇒ 發 `#489` ⇒ 正是撞掉的那個號。**

**底層數法(腳本內就是這一行;要手算或移植到別的專案時抄它)**:
```bash
{ for w in $(git worktree list --porcelain | awk '/^worktree /{print $2}'); do
    cat "$w/docs/phase-1-backlog.md" 2>/dev/null; done
  git for-each-ref --format='%(refname)' refs/heads | while read r; do
    git show "$r:docs/phase-1-backlog.md" 2>/dev/null; done
} | grep -oE '^### #[0-9]+' | grep -oE '[0-9]+' | sort -n | tail -1
```
🔴 **`cat` 工作區檔那一段不能省** —— 它才抓得到「已經寫進檔案、但還沒 commit」的號。
🔴 **禁 `sort -t'#' -k2 -n`**(BSD sort 對它的行為不同,已列進量具方言坑集)。

**窗這一側的規矩**:**號一律跟主視窗要**;真要先佔位,**必須標明「佔位、請主視窗確認」**,不得當成已配發。

**限度(要寫明,不要當成全掃)**:
- 上面第二段掃**本機 branch**,所以關掉的窗留下的 branch 也涵蓋(本機實查:**33 branch / 7 worktree**,差 26 條全靠它)。
- **掃不到**:只存在於 remote、本機沒有對應 branch 的號;以及**還沒寫進檔案、只存在於某封信裡**的號。
