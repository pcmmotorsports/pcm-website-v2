## 2. 它會在哪裡停(每一道停的意思不同)

| 停在 | 意思 | 你該做什麼 |
|---|---|---|
| ① 貼板編號命中 ≠ 1 支 | 編號給錯 / 貼板有重號 | 對編號 |
| ③ 檔名取不出 14 位版本號 | 貼板檔名不合格式 | 改檔名或問寫的人 |
| ④ repo 裡那個版本 ≠ 1 支 | migration 沒進版控 / 重號 | 先處理版控 |
| ⑤ **兩個 sha 不同** | 貼板那份與 repo 那份**不是同一份內容** | 看 diff,決定哪一份才對 |
| ⑥ 版本已在 `APPLIED.tsv` | 已經記過帳 | 不要重貼 |
| ⑥ **`APPLIED.tsv` 有而平台帳本沒有** | 貼過了而沒 repair | **只補 repair**,不要重貼 |
| ⑦ **平台帳本上已經有這個版本** | `supabase_migrations.schema_migrations` 有此 version ⇒ **貼過了** | 不要重貼;若 `APPLIED.tsv` 沒記,只補那一行 |
| ⑦ **查不動(連不上 / 沒權限)** | 🔴 fail-closed ——「沒有查」不是「查無」 | 看它印的 psql 錯誤 |
| ⑦ **含 psql meta-command(任何反斜線指令)** | 🔴 `\include` 可跑不在 SHA 裡的 SQL · `\c` 可換庫(**而 A/B 驗證看不到**)· `\!` 執行任意 shell · 關掉 `ON_ERROR_STOP` 讓錯誤後照跑而 rc=0 | 那支要人判 |
| ⑦ **交易形狀 messy** | 中途 `COMMIT` / 只有一半 ⇒ `-1` 帶或不帶都不對 | 那支要人判 |
| ⑦ **檔在前置與 apply 之間被改過** | SHA 回核不符 ⇒ **我不知道 DB 跑的是哪一份** | 不記帳,交給人判 |
| ⑦ **那張表不存在** | 🔴 fail-closed —— 表不存在時 `count` 也會回 0,**那個 0 是尺的 0** | 確認寫入身分讀得到 `supabase_migrations` |

🔴🔴 **「還沒貼」要【兩本帳都說沒有】**:平台帳本(⑦)**與** `APPLIED.tsv`(⑥)。
🛑 **理由是量到的**:平台帳本今晚才補到**還缺 65 支**,而其中**有在 SQL Editor 貼過卻沒 repair 的**
⇒ 📌 **只問平台帳本會重貼。**

🔵 **v3 把整層啟發式刪掉了。** v1/v2 用「新物件在不在」與「函式 body md5」去*推論*貼了沒 ——
codex 兩輪各打掉一層,而**病灶是同一個:我在用一把量不到的尺**。
⇒ 🎯 **那個問題有一個權威答案**,就是平台帳本本身。而我當初繞路,是因為**唯讀身分讀不到它** ——
**我把一個身分的限制帶進了設計**,而寫入那條連線不是那個身分。

## 3. 🔴 貼完之後出事怎麼辦

| 情況 | 狀態 | 怎麼辦 |
|---|---|---|
| psql 印 ERROR · 檔案**自帶** `BEGIN…COMMIT`(shape=clean) | 🔴 **本工具【不帶 `-1`】** —— 原子性由**檔案自己**保證;錯在 COMMIT 之前 ⇒ 連線關閉時回滾 | 看 log 的 ERROR |
| psql 印 ERROR · 檔案**零交易控制**(shape=none) | 本工具帶 `-1` ⇒ 整支回滾 | 看 log 的 ERROR |
| **psql rc=2(連線中斷)** | 🔴🔴 **這一種不能斷言 DB 未變** —— 若在 COMMIT 的回應之前斷線, 可能已經提交 | **先唯讀查再決定**,不要重跑 |
| **psql 成功而 `repair` 失敗** | 🔴🔴 **半套:DB 變了而平台帳本沒記** | 工具會把**要手補的兩行印出來** —— 照著補 |
| 全成功,事後發現貼錯 | 🔴 **沒有自動 rollback** | 要那支 migration 自己的 down;**沒有 down 就沒有回頭路** |

🛑 **⇒ 所以「一次一支 + Sean 逐支點名」不是流程繁瑣,它是這片唯一的 rollback。**
📌 而「半套」那一格在 `rc` 上與「什麼都沒做」長得一樣 —— 所以工具**不會靜靜結束**,它會印紅。

## 4. selftest

```bash

```
起一個**拋棄式 PostgreSQL**(`initdb` + `pg_ctl`,隨機埠,`LC_ALL=C`),跑十八組世界、**81 格**(硬閘寫死在 `--selftest` 尾端;數法 `bash scripts/apply-paste-board.sh --selftest | tail -1`)。
🔴 **`supabase migration repair` 一律走樁,selftest 絕不呼叫真的 CLI。**
🔴 有紅時**保留現場**並印出目錄 —— 「它紅了」與「它為什麼紅」是兩件事。

⚠️ **selftest 全綠證不了什麼**:拋棄式 PG 與正式庫**不是同一個世界**(PG 版本 / extension / 既有資料)。

## 5. 它答不出什麼(照實列)

· ⑦ 答的是「**平台帳本有沒有記**」——**不是**「東西在不在」。那兩件事今晚分岔過一次,
  所以 ⑥⑦ 要**一起**成立才算「還沒貼」。
· 連線串走 psql 的 argv(與 `scripts/readonly-prod-sql.sh:27` 同形)⇒ **`ps` 上看得到**。
  ⚠️ 同一個使用者本來就讀得到 `.env.local` ⇒ **沒有比現況更差**;而本支**絕不把它印進 stdout / log / 對話**。
· 它**不驗那支 migration 對不對** —— 只驗「該貼的是這一份」與「還沒貼」。
