## 🔴🔴 最重要的一句:**沒收到信,本身就是訊號**

這封信**每天都會寄**,包括**「昨天沒有人刷不過」那一天** ——
📌 **「今天零失敗」是一個要被說出來的答案,不是沉默。**

⇒ 🛑 **連續兩天沒收到 = 出事了**,而出的事**不一定是刷卡**:
比較可能是**寄這封信的那條線自己停了**。

### 為什麼會這樣(這一格是刻意的取捨,不是設計失誤)

這封信搭的是**既有的告警排程** `pcm-anomaly-alert`(每天 01:00 UTC 跑一次)。
🔴 而那支路由是 **fail-closed**:它有**十幾個出口**,任何一格「讀不到」就 `return 503`,
**整發結束 —— 包括這封信。**

⇒ 📌 **這封信,活在它要監看的那條線上。**(板列 `⟦f3-ALERTSAMELINE1⟧` 講的就是這個結構。)
✅ **而我們仍然這樣做**,理由是:在它之前,**替代品是零**。
　 一封「會跟著線一起停」的信,比沒有信多一格 —— **只要沒收到信這件事本身被當成訊號。**
　 🛑 **而那正是這一節存在的原因。** 少了這一節,這個取捨就變成一個安靜的缺口。

## 沒收到信,照這個順序看(每一步都要**看到**東西,不是「應該有」)

**① 先看排程有沒有跑**(要有人幫你跑,標 🧑‍💻)
🧑‍💻 唯讀查 `public.sweeper_heartbeat` 的 `pcm-anomaly-alert` 那一列:
```
last_success_at 在 26 小時內  ⇒ 🟢 排程有跑而且成功了 ⇒ 問題在寄信那一段, 跳到 ③
last_failure_at 比 last_success_at 新 ⇒ 🔴 路由跑了而失敗了 ⇒ 看 ②
兩欄都很舊 / 沒有那一列 ⇒ 🔴 排程根本沒跑 ⇒ 那是 pg_cron 的事, 不是這封信的事
```
🔵 **兩個世界會印不同的東西** —— 這一格分得出「沒跑」與「跑了但失敗」。

**② 路由為什麼失敗** 🧑‍💻 看 Vercel 那個部署的 log,找 `[anomaly-alert]` 開頭那幾行。
它**會自己印出是哪一格讀不到**(例:`get_search_log_health 讀失敗 { code: '42501' }`)。
📎 **前例**:2026-09-06 就是這樣壞的 —— 四支函式權限被收掉(`42501`),
修法 `20260906970000`(貼板 64)。⇒ **同樣的症狀先問「是不是又有東西被收權了」。**

**③ 排程成功了而信沒到** ⇒ 先看**垃圾郵件**;再確認 `ALERT_EMAIL_TO` 這個設定還在
(🔴 只看**名稱**在不在,**不要把值印出來**)。

## 信裡的數字怎麼讀(每一個都有它答不出來的事)

| 數字 | 它是什麼 | 🛑 它**不是**什麼 |
|---|---|---|
| 刷卡失敗數 | 過去 24 小時**建立**的刷卡嘗試裡,現在是失敗的幾筆 | **不是**「昨天發生了幾次失敗」—— 25 小時前建立、1 小時前才失敗的那一筆,今天不算 |
| 3DS 失敗數 | 同一批裡,被觀察到 3DS 回 -1 或 5 的幾筆 | **不可以**和上面那個相加 —— 同一筆可以兩者皆是 |
| 總數(分母) | 同一批的全部 | 沒有它,讀的人會自己補一個,而他補的多半是「全部」 |

🔴 **兩個 0 有兩種成因**:①真的沒有人刷不過 ②**沒有人來刷**。
⇒ **看分母那一格。** 分母也是 0 ⇒ 那是第二種,而它**不是好消息**。

🛑 這封信**答不出「客人為什麼刷不過」** —— 卡片問題、3DS、我們自己的 bug,在這裡長得一樣。
明細要到後台看,信裡**刻意不放單號**(主視窗 2026-09-06 裁:PII 不下放)。
