## 🛑 先讀這一段:為什麼原本沒有開關

`apps/storefront/src/app/api/cron/email-sweep/route.ts:8` 逐字寫著「本片**不設** `*_ENABLED` gate」。
那是刻意的:**這條線的開關就是「pg_cron 有沒有在排它」**。
⇒ 📌 **所以停它的方式不是改程式、不是改環境變數,是【把那個排程拿掉】。**

---

## 停(一句)

```sql
SELECT cron.unschedule('pcm-email-sweep');
```
🔬 那個名字**逐字**來自 `supabase/migrations/20260819160000_m4a_e2b_email_sweep_pgcron.sql:213`
(`cron.schedule('pcm-email-sweep', '*/5 * * * *', …)`)。**不要憑印象打**,名字錯了它會回錯而不是停錯。

## 開回來(一句)

```sql
SELECT cron.schedule(
  'pcm-email-sweep',
  '*/5 * * * *',
  $job$SELECT pcm_cron.invoke_cron_route('/api/cron/email-sweep')$job$
);
```
🔬 同樣逐字來自那支 migration 的 `:213-214`。
⚠️ 那支 migration 在排完之後還有一行 `cron.alter_job(job_id => v_id, active => true)`
(`:216`,理由逐字「by-name upsert 不會改 active」)—— **如果曾經有人把它設成 inactive,只跑上面那句不會開回來**。

## 生效多快

排程是 `*/5 * * * *`(每 5 分鐘)⇒ **停:下一輪本來要跑的那一次就不會跑了**(最多等 5 分鐘)。
🛑 **而【已經在跑的那一輪不會被打斷】** —— 它會把手上那批寄完。

---

## 🔴 停了之後,信會怎樣(這一段是開檔核過的,不是推的)

**信會累積,不會丟。**
🔬 依據:sweeper 認領的條件是 `status IN ('pending','failed')` 且 `next_retry_at <= now`
(`SupabaseEmailOutboxAdapter.ts:79` 的 `CLAIMABLE_STATUSES` 與 `:474-475`)。
⇒ 停了之後,新的信照樣被**排進** `email_outbox`(排信與寄信是**兩段**,排信不靠這個排程),
它們只是**沒有人來拿** ⇒ 開回來之後**下一輪就會被拿走**。
🟢 而**沒有任何排程在刪 `email_outbox` 的列** —— 全 repo 唯一的 `DELETE FROM public.email_outbox`
是後台那顆「撤銷人工寄信登錄」的按鈕(一次一列、要有人按)。

### ⚠️ 而有一種列會卡住,要知道

停的那一刻**正在寄**的那些列,狀態是 `sending`,而 `sending` **不可再認領**。
它們要等**回收**,而回收是 sweeper 自己做的第一步 ⇒ 🔴 **排程停著的期間沒有人回收它們**。
⇒ 📌 **開回來之後它們才會被撿回去** —— 那不是壞掉,是這個設計的形狀。
⇒ 🛑 **所以「停很久」的代價不是丟信,是那幾封信會躺得比別人久。**

## 🔴 重開之後撞到「批次上限閘」怎麼辦

**停信幾小時之後重開, 你很可能會撞到它 —— 而那是對的, 不是壞掉。**

⟦b4-EMAILTRIAGE⟧ 甲-3 在排信那一層加了一道閘:**同一種信、同一輪, 超過 20 封就不排**
(`packages/use-cases/src/enqueue-batch-cap.ts`, `ENQUEUE_BATCH_CAP`)。
它擋的是「cutoff 貼錯年份 ⇒ 一次補寄一大堆」——
而**「停了三小時之後累積的那批」與「貼錯年份撈出來的那批」, 在那道閘眼裡長得一模一樣**。

### 症狀
- 排程回 **503**(不是 200), 而**寄送那一半照跑**(已經在 outbox 裡的信照寄)
- log 一行:`reason_detail: enqueue_batch_cap_exceeded` + `eventType` + `count` + `cap`
- **只有撞閘的那一種信不排**, 其他五種照排

### 處置(順序不可調)
1. **先看 log 那一行的 `eventType` 與 `count`** —— 它告訴你是哪一種信、要排幾封。
2. **確認那批【真的該寄】** —— 三件事逐一看, 不要跳:
   - **cutoff 對不對**(年份有沒有貼錯 / 有沒有被改過)
   - **那些單的日期合不合理**(是這幾小時累積的?還是幾個月前的舊單突然冒出來?)
   - **筆數與停機時長對不對得上**(停 3 小時而冒出的量遠超過那段時間的正常單量 ⇒ 那不是累積, 是別的東西)
     ⚠️ **而你在 log 上看到的 `count` 最多就是 50** —— 上游 `ENQUEUE_LIMIT` 一輪只給 50 筆
     ⇒ 📌 **單輪的數字看不出「總共積了多少」**, 那要去查 outbox 或掃描面的列數。
3. 三件都確認了 ⇒ **改 `ENQUEUE_BATCH_CAP` 這個常數、重新部署**, 讓那一批過去。
   🔴 **而改常數會撞到兩格測試**(它們刻意寫死 20, 就是為了讓這個動作留下痕跡):
   **兩格都在** `packages/use-cases/src/enqueue-batch-cap.test.ts`:
   一格斷言 `ENQUEUE_BATCH_CAP` 等於 20, 一格斷言撞閘的錯誤帶 `cap: 20`(`:123`)。
   🔵 查法(不要抄上面那個行號, 它會漂):`grep -rn 'cap: 20\|ENQUEUE_BATCH_CAP).toBe' packages`
   ⇒ **要一起改才推得上去** —— 那不是阻礙, 那是**這個動作被看見的方式**。
4. 放完之後**改回 20、把那兩格測試改回來、再部署一次**, 然後**確認生效**:
   下一輪的 log 不再出現 `enqueue_batch_cap_exceeded`, 而排程回 200。
   🛑 **這一步很容易忘, 而忘了等於這道閘從此不存在** —— 留在 50 以上時,
   `ENQUEUE_LIMIT = 50` 已經把單輪列數壓在 50 ⇒ **六種信的閘全部再也不會觸發**,
   而它看起來跟一道有效的閘一模一樣。今天防忘的機制**只有這段文字**, 沒有機械閘。

### 🔴 為什麼不給一個環境變數開關
給了 `*_ENABLED` 之後, 「解除大量寄信的保護」就變成**改一個環境變數**就好 ——
那是鐵則 12④(平台設定)自己長出來的第二個入口, 而**改 env 不會留下 diff、不會過審查、不會有人看到**。
📌 **改常數重新部署很麻煩, 而那個麻煩就是這道閘的一部分。**

### 🛑 這道閘擋不到的
**慢速大量**:每輪 19 封、連續好幾小時 ⇒ **每一輪都合法**, 而總量一樣很大。
修法是累計視窗, 本片沒做 ⇒ 板列 `⟦mail-ENQUEUEBATCHCAP⟧`。
