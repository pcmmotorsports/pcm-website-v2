# 夜跑多窗指揮 Playbook(常設工法)

> 2026-08-06 Sean 拍板:「本次的方式變成以後常用的夜跑方式」。本檔=該夜實跑方法的固化,單一權威;
> 信箱協定細節以 `/Users/sean_1/pcm-mailbox/README.md`(含補訂)為準,本檔不重複。
> 啟動前提:夜跑=多代理實作,**每次由 Sean 說「今晚夜跑」才開跑**(鐵則 7 批准制;08-01 拍板夜跑常態化=模式常設、單次仍要點頭)。

## 1. 角色拓樸

- **主視窗**:指揮/收割/裁決,**不下場實作**(例外:收割時的 nit 折入、docs/STATUS 收帳、鐵則允許的機械修)。
- **施工窗 ×N**:各自獨立 worktree+分支(絕不共用工作樹);代號沿用 A-E,新線開新代號並在信箱 README 補訂登記。
- **溝通**:全走信箱檔案(審計軌跡),不經對話轉貼;主視窗 `<代號>-1xx-A`、施工窗 `<代號>-2xx-Q/STOP`。

## 2. 主視窗開工儀式

① `git branch/status/log` 檢查(dirty 有主才續)②掛**三合一哨兵**(session scratchpad 生成 `sentinel-v2.sh`,樣板見本檔尾註):信箱 mtime 基準比對(**絕不用號段最大號**,主視窗 1xx 恆小於施工窗 2xx)+各施工分支 HEAD 快照+**靜默偵測**(任一窗 45 分零 commit/零信/工作樹零檔案異動=喚醒主視窗主動查——防「窗死了沒人知道」,08-06 B 窗斷線是 Sean 先發現的教訓);任一事件即喚醒,處理後 `rearm` 一行重掛;**發完信的動作序固定=寫信→同一條背景命令 `rearm && watch`**(排除自己的信、且不靠記憶補掛)③全量 `ls -t` 信箱補讀,自己認未讀;**每次被任何事喚醒,第一動=全量掃信箱處理所有新信,不只處理喚醒那一封** ④讀 CURRENT checkpoint+收割筆記(scratchpad)⑤**長 turn 收尾前自檢一行 `ps aux | grep sentinel`**——哨兵不在跑=先重掛再收尾(08-06 實錘:主視窗兩度差點裸奔,Sean 人肉當了哨兵)。

## 3. 派工單六要素(每封 1xx 派工信)

①環境自建(worktree/分支/基於哪個 dev)②任務與硬序(引母 plan `檔案:行號`)③工法(偵察 grep 全樹→施工→三綠 `--force`+全套→code-reviewer R1 折入→高風險片 codex 關卡2 不降級→commit→STOP)④紅線(不 push/不動 STATUS·CURRENT/不 checkout·stash·reset·clean/繁中/精準 add/金流頁與 migration 等禁區逐條點名)⑤收工總 STOP 格式(進度表+每片 commit+測試數對帳,基線寫死在單裡)⑥時程(08:30 收尾、09:00 前總 STOP)。

## 4. 夜間節奏(與白天不同,派工單必明文)

- 施工窗寫完 STOP **不掛等待、直接續下一片**;佇列空了才進「守望態」;主視窗批次收割;審出 must-fix 主視窗寫 1xx 信插隊。
- **STOP 即掛哨(施工窗標準動作,2026-08-06 增補;2026-08-11 改基準)**:每封 STOP 寫完的最後一動=掛信箱小哨兵(run_in_background,樣板見尾註 B;**基準=最後一封你已讀已處理的來信**、mtime 比對、pattern 涵蓋本窗所有信型並排除自己會寫的型)。~~基準=自己剛寫的那封 STOP 檔~~ **已於 2026-08-11 廢止**——它與「掛哨當下 touch 時戳」都會漏掉「你埋頭做事期間送達」的信(實測與理由見尾註 B 增補 1)。哨兵推播→全量讀所有新信→接工前先重掛(新基準=剛讀完的最新來信)。施工中不輪詢(工作即狀態),每片收工時全量掃一次即可。壓縮/重啟後第一動=重讀自己最新 STOP+全量掃信箱,**不信任何舊哨兵**。
  🔴 **掃信要貼輸出當證據,不寫「我掃過了」(2026-08-07 增補)**:STOP 裡的掃信那行必須是**實跑後貼上的輸出**
  (`find -newer <自己最新 STOP>` 的結果,無輸出就寫「無輸出=無漏讀」)。病根實錘:D-271 掃信句自陳「沒執行過」——
  一句沒有輸出的「已掃描」在字面上與有掃過完全一樣,讀的人分不出來。
- **發信防撞號 + 寫入原子性(所有人)**:
  - 防撞號:寫信前 `test -e` 驗檔名,存在=取下一號,絕不覆寫既有檔(撞號=整封信被蓋、集合式掃描零推播,08-05 A-32 實錘)。
  - 🔴 **原子性(2026-08-07 增補)**:信一律**先寫暫存 → `test -s` 驗非空 → `mv` 到信箱**,不直接寫目標檔。
    直接寫的失效形狀:對方的哨兵在你寫到一半時就被 mtime 觸發,讀到半截信。
    三步是一組、缺一不可:`cat > $TMP` → `test -s $TMP` → `test -e $DST || mv $TMP $DST`。
- 🔴 **信在兩端各有一種死法,兩端都要守(2026-08-07 增補;當夜兩端都真的發生過)**
  症狀完全一樣(對方空等),但病根與修法相反,所以**寫成一條、不拆兩條**:
  - **發送端(主視窗)**:**每處理完一封 STOP,回信未發不得開下一件。**
    實錘:E 窗 10:48 的 STOP 主視窗 10:52 就收割完,回信被別線岔走沒發,讓該窗空等 40 分。
  - **接收端(施工窗)**:**開窗第一動比對「自己最新 STOP」與「最新 `-A`」的 mtime;`-A` 較新 = 漏讀、必須補讀。**
    🔴 **這道比對在「寫每封 STOP 前」都要再跑一次、不是只在開窗時跑一次**(2026-08-07 增補,D 窗實錘):
    開窗那次通過≠永久事實 —— D 窗開場比對確實通過,然後埋頭施工兩小時半,寫 STOP 時**把開場快照當當下事實**寫出去,
    漏了中間進來的兩封。「最新給我的是 X」是**會過期的自指字面**,與寫死行號同族;
    修法=落筆當下重跑 `ls -lt`、**把輸出與掃描時間貼進信裡**(§4 掃信貼輸出那條的字面已涵蓋,這裡點名時機)。
    🔴 同日第二錘(同窗,更重):它在**解釋自己要改掉這個病的那封信裡**,寫了「本信落筆當下的掃信結果」段落
    **但沒有真的執行那次掃描** —— 沒看還說看了。這是「貼輸出」為何必須是機制而非自律的最硬實證:
    一句沒有輸出的「已掃過」在字面上與真掃過完全一樣,**唯一可查核的形狀是貼上的輸出本身**。
    🔴 **同日第三、四錘後的機制版(2026-08-07 夜定稿):掃描時機 ≠ 喚醒時機**。哨兵觸發時印的清單是**它那一刻**的,
    施工窗做完一片才落筆——時間差裡進來的信全漏,把哨兵舊輸出冠上「落筆當下實跑」貼進信照樣是假掃描
    (D-287/D-288 兩封連環,D 窗自查 `! -newer` 反推坐實)。修「錨點」不修「時機」必復發。
    **定稿命令形狀**:`cd 信箱 && date '+%H:%M:%S' && find . -maxdepth 1 -name '<本窗>-*-A.md' -newer <最後讀過的-A>.md | sort`
    ——`date` 與 `find` **同一行串接、輸出整塊貼進 STOP**。區塊裡有機器印的時鐘,與 STOP 落筆時間一比,
    貼舊輸出會當場自曝,不依賴任何人記得。**哨兵輸出只准當喚醒訊號,永不當掃描結果貼。**
    🔴 **號段高低不能拿來推斷主視窗有沒有回** —— 兩條號段各自獨立遞增,
    施工窗 2xx 恆大於主視窗 1xx,看起來像「我發很多他沒回」,事實可能完全相反。
    實錘:E 窗某 session 開場時 STOP 號段 245、`-A` 號段僅 150,實際是**漏讀了兩封**(`E-149-A`/`E-150-A` 都比 STOP 新)。
  - **機制形狀**:
    - **接收端做得成機制**(純機械判斷,建議做):開窗儀式跑一行
      `find $MB -name '<窗>-*.md' -newer "$(ls -t $MB/<窗>-*STOP.md | head -1)"`;
      有輸出=有漏讀、逐封處理完才准開工;無輸出才開工。
    - **發送端做不成完整機制**(依 §4 機制優先律,退成文字條前先答「為何做不到」):
      主視窗「處理完一封 STOP」**沒有機器可觀測的完成事件** —— 收割動作散落在 merge / 測試 / STATUS 更新,
      沒有單一時點可掛 hook。最接近的機制需要「哪封 STOP 已回」這個狀態,而它目前只存在主視窗的工作記憶裡。
- **guarded-edit 使用時機(2026-08-07 增補)**:凡**區間刪除/起訖索引切片/批次 sed 改多行**一律走 `scripts/guarded-edit.sh`(Δ 對帳+備份還原+fail-loud;E 窗 #339 落地)——手切段落靜默吃鄰居已實錘多次(`feedback_range-delete-silently-eats-neighbors`),單行小改不必。
- 拿不準的產品判斷=跳過記 STOP,不猜、不硬標。
- **佇列預派**:每窗「下一份工作」在其現任務跑著時就先寫好(scratchpad `dispatch-queue.md`),STOP 一到即發;佇列永不空;08:30 起不發新單。免批准型優先(plan 起草/唯讀偵察報告/截圖包/smoke test/清單彙總);需 Sean 拍的只列決策題不執行。
- **續工授權**:派工完成後的加班清單預先寫進主動通知信(等 Sean 授權「不需同意的盡量推進」後)。

## 5. 收割工法(主視窗,逐線)

押住等 STOP → **R1 FAIL 必有確認輪**(紀錄面=主視窗以 SHA 窄確認;行為面=fresh reviewer;第 3 輪起換模型換角度;codex FAIL 的裁決型 finding 可由既有拍板/裁定處置,寫進 commit body)→ `merge --no-ff` → `turbo typecheck lint build --force`(0 cached)+全套 `pnpm test` **精確調和**(「預期 Δ vs 實際 Δ」逐片對帳,完整輸出留檔 scratchpad)→ 錢面加拋棄庫重跑 → **nit 順手清**(reviewer gate 標記引審查紀錄)→ STATUS 七欄收帳+欠的落檔(母 plan 註記/立案)同批 docs commit → push(夜跑持續授權;`dev`=pcm-admin production,收割即上線要心裡有數)。

## 6. 裁決分層(主視窗)

- **可自裁**:施工序/流程/方法論題(判準=不改產品可見行為、不動資料、可逆),**裁定前必親驗施工窗引用的事實**(`檔案:行號` 逐條),裁定信寫依據、落檔責任歸自己。
- **轉 Sean**:產品可見變化/不可逆/與既有拍板衝突/品味題 —— prose code block `Q:…/A: A|B|C` 附推薦,不擋施工的標明「不擋」;拍板即落 memory+發信給窗折入。
- **codex 與 Sean 拍板衝突以拍板為準**(CLAUDE.md 明文),不採的 finding 在 commit body 具名記理由。

## 7. 韌性

- **context 壓縮**:各窗自動壓縮可續跑,防的是「狀態只在對話」——每片 commit+STOP=checkpoint;改到一半先寫 scratchpad checkpoint 檔;壓縮後第一動=重讀自己最新 STOP。主視窗同理(收割筆記+本檔+STATUS)。
- **斷線復原**:主視窗盤點該 worktree 現場(未 commit 檔/拋棄庫埠/磁碟產物完成度)→ 寫「接手現場、不重做」重啟提示詞給 Sean 貼;施工窗產出隨做隨落檔=斷線零損失的前提。
- **死哨兜底(2026-08-06 增補)**:派工信發出 **30 分**後對方零反應(無回信+分支未動+工作樹靜默)=假設**對方哨兵死了,不是信丟了**——先驗信在(`ls -la`+`head`),然後請 Sean 貼「**指名讀檔**」喚醒詞(格式:「不要掃信箱,直接用 Read 讀 <絕對路徑> 並照做」),不再寄新信占號。實錘:08-06 兩窗「說沒新信」,四封信全在,指名讀檔一次解決。
- **macOS 防火牆彈窗**(本機 postgres 拋棄庫觸發):按允許一次即可;重啟單明寫「接手既有拋棄庫、不重 provision」。
- **🔴 中繼檔禁放 `/tmp`(2026-08-09 P 窗兩次實錘;2026-08-13 D 窗補上第三種失效模式)**:macOS 會在長 session 中途清 `/tmp`;第一次吃掉 commit message 檔(git 報錯好抓),第二次吃掉 codex prompt 檔——**codex 收到空字串照樣回話**,差點被當成一輪有效審查。中繼檔一律放各窗 scratchpad;凡「餵檔案給外部工具」前先 `test -s` 驗非空。
  🔴 **第三種失效模式=被別的窗覆寫,不是被清掉(2026-08-13 D 窗實錘,最毒)**:D 用 `/tmp/cmsg.txt` 當 commit 訊息檔,**另一個窗用同檔名寫了自己的內容**(「④-a plan 草稿 v0」)⇒ 檔案**還在、非空、`test -s` 照樣過**,差一點用**別窗的訊息**送出自己那顆 commit。與前兩例的關鍵差別:**清掉會報錯、覆寫不會**——所有「檔案存在」類的守門(`test -e`/`test -s`)對它零判別力。當天是**全稱句守門吐回來的命中段落根本不是自己的字**才被抓到(靠內容不靠存在性)。
  ⇒ 規則:**多窗期間,凡寫入 `/tmp` 的檔名一律視為共用命名空間**;commit 訊息 / prompt / 中繼資料一律寫各窗 **session scratchpad**(路徑天生含 session id、不可能撞)。真的要用 `/tmp`,檔名必須帶窗代號+PID。**驗收改成驗內容不驗存在**:餵出去前 `grep` 一個只有自己會寫的字串。

  ⇒ 規則:**migration 一旦進 `APPLIED.tsv` 就是凍結檔**,任何改動(含純註解、含空白)都會讓台帳對帳失效。要補說明只有兩條路:①寫在**應用層**的檔頭(單向指標)②開**新的 migration** 帶 COMMENT。
  ⇒ **與 `/tmp` 覆寫同型、要一起記**:**破壞不會當場報錯,只有主動比雜湊才看得到**(D 自己的話)。所以動任何 migration 檔前先 `grep <版本號> supabase/APPLIED.tsv`,命中=停手。

  ③ 主視窗心跳(10 分)承擔全域盯窗;施工窗只需盯「自己發出待回」的信。

## 尾註 C:**數法五坑**(2026-08-11 夜 E 窗立;每條都是當場踩到或當場擋下的)

> 五條的共同形狀 = **「你以為在數 A,其實在數 B」**。
> 所以判別法一律是同一句:**先讓它在一個你已經知道答案的樣本上跑一次**。
> 每條附**可複跑命令**與**實錘座標**;沒有實錘的條目不准進本尾註。

### C-1 拿 regex 去數東西之前,先用**正負對照**證它會動

**症狀**:整批統計得到「全部沒做 / 全部沒有」這種漂亮又整齊的結果 —— 而那正是壞掉的 regex 的長相。
**做法**:準備一個**該中**與一個**不該中**的樣本,先跑給自己看,再拿去數真的東西。
```bash
printf 'x A11a 欄\nx A11a-1 列表\nx A11a\n' > /tmp/t.txt
grep -nE '\bA11a([^A-Za-z0-9-]|$)' /tmp/t.txt   # 期望:第 1、3 行中,第 2 行不中
```
**實錘**:`(^|[^A-Za-z0-9-])ID` 這種寫法在**本機的 `grep`** 下**恆 0 命中**
(同一行 `[^…]A2b1` 中、`(^|[^…])A2b1` 不中,複跑兩次)。
沒先跑正負對照的話,完成地圖 §-5 的 40 片會**全部**被數成「沒做」。
🔴 **適用範圍只到本機這支**:`grep --version` 自證是 **ugrep 7.5.0**(aarch64-apple-macosx),
**不是 BSD grep,也沒在 GNU grep 上驗過** —— 原始筆記寫成「BSD grep」是錯歸因,
已於完成地圖 `c555f680` 更正。**這個錯本身就是 C-4 的示範:排除法只排掉一個候選,
不等於指認了另一個**,而 `grep --version` 一行就問得到。

### C-2 改文件裡的舊字面,用 `count==1` 當**唯一性閘**,不要盲改

**症狀**:以為在改現況段,其實改到歷史原文;或一次 `replace` 改了兩處但你只想改一處。
```python
old = '| 9 | 單號追蹤 | ❌ |'
assert s.count(old) == 1, s.count(old)   # 不唯一 = 當場停,不是靜默改
s = s.replace(old, new)
```
**實錘**:這條當場擋下一次 —— 該字面在完成地圖的**新舊兩張表各有一列**,
盲改會改到 08-01 的歷史原文。腳本在寫檔前 assert,**檔案原封不動**。
⇒ 「改 spec/PRD 前先建舊字面清單」那條教訓**可以做成機制**,不必靠記得先 grep。

### C-3 片號**不是全 repo 唯一**:命名空間看 migration 檔名前綴

**症狀**:`grep 片號` 撈到**別條線**的片,而且兩邊 commit 主旨都長得像「做完了」。
**實錘**(全部來自同一支 `git log dev --format='%h|%s'`):

| 片號 | 這條線 | 另一條線 |
|---|---|---|
| `A1` | E10 訂單品項數量摘要表(`feat(schema)`) | storefront 導覽小修(`feat(storefront)`) |
| `A2` | E10 `order_item_procurement` | storefront `?pick=vehicle` 落地開燈 |
| `S1b` | `…_m4b_e10_s1b_procurement_supplier_fk` | `…_m4b_e10_b2_s1b_shipment_items`(B2 出貨線) |

**判別法(由強到弱)**:

「有沒有人在主旨裡打過這串字」。要判完成,**看成品座標**(檔案/migration/掛載鏈)。

### C-4 「0 命中」是**時點觀察**,不是屬性 —— 而**動作序**才抓得到它過期

**症狀**:文件裡的「查無 / 全缺 / 零命中」被下一個人(或三小時後的自己)當成屬性沿用。
**做法**:①落筆時附**時刻** ②**`git merge` 後、收工前,重跑本次用過的每一條 `grep`**。
**實錘**:完成地圖 §-4 第 15 項 **19:0x** 量到 0 命中標 ❌;**19:20 同一條命令命中 2 支**
(隨當批 merge 進 dev)⇒ 同一份文件裡 **13 分鐘**就過期一格。
🔴 發現它的**不是規則、是動作序** —— merge 完順手重跑撞到的。
⇒ 本條要落成**動作序**(merge 後重跑受影響的斷言),寫成規則文字沒用:
規則版在完成地圖檔頭已經寫了三次,第 15 項照樣過期。

### C-5 `grep 關鍵字` 會把**註解**算進去

**實錘**:`grep -rn 'window.print\|揀貨\|列印' apps/admin/src` = **6 命中**,
逐條開檔後**全是註解**(「可列印 ASCII」×4、「每**列印**一個 0」的斷詞巧合、「列印、色弱」)
⇒ 該功能其實不存在。
**判別法**:數功能要數**語法位置**(函式定義 / 元件掛載 / import),不是數關鍵字;
**命中數 >0 只是「該去開檔」的訊號,不是「存在」的證據**。

### C-6 「無新信」三個字必須有一條**本次真的跑過**的掃信命令墊底(2026-08-12 主視窗+D 窗同日兩例後立)

**實錘**:D 窗八代把「另一條命令的時間戳」貼在一條**從來沒執行過**的 `find` 底下、寫「零行=無新信」——
而當下信箱裡躺著 17 分鐘前的停點令。七代 `D-534-NOTE` §7 同型;主視窗同日凌晨「落款估時冒充 date 實跑」同族。
三例共同形狀=**把「我不知道」寫成「沒有」**,比漏接嚴重:漏接是缺口,這是主動填假。
**機制(兩條,D 八代立、全窗適用)**:
1. 落筆「無新信」之前,那條掃信命令與其輸出**必須是本次 Bash 呼叫裡真的出現過的字串**;
   拿不出來就寫「**未掃**」,不寫「無」。(七代版「find 輸出只准原樣貼」擋不住「連跑都沒跑」,本條往前一步。)
2. 看到哨兵 stopped/死亡通知=**當場重掛**,不排進待辦——排待辦的下場就是上面那個 17 分鐘的洞。

**C-6 增補(2026-08-12 午,D 八代第二例後)**:兩次實錘都**不是寫「無」、是連時間戳一起編**
(第二次內容碰巧對、落款前自核攔下——「碰巧對」不等於沒犯)。
⇒ 補一條:信裡任何 `date`/`find`/查詢輸出,一律**從終端機複製貼上**,不准憑記憶重打。

### C-8 sessionId 反查 pid **可能命中多個** —— `grep -l` 會挑錯,`ppid` 才是決定性的(2026-08-14 D 窗實測後立)

**現行做法的缺陷**(本檔 §C 與各窗開窗提示詞都寫過這條):
```
grep -l "<你的 sessionId>" ~/.claude/sessions/*.json   # ← 這一步可能回兩個以上
```
🔴 **實測**:D 窗 resume 過之後,同一個 sessionId **命中兩個 pid(30961 / 31647),而且兩者都活著、都有 socket**。
⇒ 挑錯的話,位址檔會指向一個**活著但不是你**的 session ⇒ 門鈴投到別人家、而且 **`SendMessage` 照樣回 success**
(同族:`reference_sendmessage-success-not-delivery`)。

**正確做法**:
```
grep -l "<sessionId>" ~/.claude/sessions/*.json     # 先縮小候選
ps -o ppid= -p $$                                    # ← 決定性:這個才是「我自己」
```
命中一個時兩者一致;**命中多個時以 `ppid` 為準**。

⚠️ **主視窗給窗的提示詞要一起改** —— 只寫 `grep -l` 的版本在 **resume 過的 session 上會失準**,
而 resume 在長夜跑裡是常態。
🔴 **更一般的形狀**:「用一個**不保證唯一**的鍵去查身分」= 這個坑的通式。
查之前先問「**這個鍵會不會命中多個**」,而不是查完看到一個就當答案。
