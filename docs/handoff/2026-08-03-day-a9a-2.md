## 3. 🔴 A10b(下游)開工前必讀的四條契約債

1. **全量 payload,不是 patch** —— A5a(`20260803160000:20-24`)選填欄送 NULL = 寫成 NULL,
   ⇒ 表單必**全欄 hydrate 自 `procurements[]` 的那一列、先讀後送**。本讀模型逐欄都投影了就是為了這件事;
   少送一欄 = 靜默清掉既有值。`supplierId` + `id` 都在,upsert 業務鍵 =(order_item_id, supplier_id)。
2. **停用的供應商照常出現在既有採購列**(`S1b:183` 明文本鍵不阻止指向已停用者)。
   `supplierIsActive === false` ⇒ UI 顯示「已停用」提示,**不得把整列藏起來**;
   `null` = **內嵌沒回來、不知道**,不得靜默當 true。被 A5a 擋的只有「新建」與「調升 allocated」。
3. **三軸數量不要拿 `procurements[]` 加總** —— 權威是 `order_item_quantity_summary`(A1 表 + A4a trigger)。
   截斷時加總更是錯的。那個讀模型是 **A9c**(列表投影)的事,本片沒做、明細頁要用得另外接。
4. **`procurementTruncated === true` ⇒ 清單可能不完整**(兩個來源:觸及上限 **或** 內嵌鍵整個沒回來)。
   🔴 **寫入端不得送出表單** —— 拿一份不可信的 hydrate 去送 A5a 全量 payload = 用空白/舊值覆蓋真實採購事實;
   顯示端也要說出來(同 A9a-1 的 `notesTruncated` 慣例)。
5. **`AdminOrderDetail.itemsTruncated` 是上一條的前提**:品項自己被切掉時,那個品項的
   `procurementTruncated` 會連同品項一起消失、看到的旗標全是 false ⇒ **兩個要一起讀**。目前無 UI 在讀它。

## 4. 為什麼多開一個 `created-at-order.ts`

A9a-1 的 `compareNotes` 有三層(毫秒 → 同毫秒比時間字面 → id),中間那層是因為
**`Date.parse` 只到毫秒而 `created_at` 是微秒精度**。A9a-2 要一模一樣的邏輯 ——
抄第二份的話兩份會各自漂移,而漂移的症狀(次毫秒排錯)**不會有任何測試轉紅**。
⇒ 抽成單一實作,兩邊共用。行為一字未改;突變 M3(拿掉中間那層)讓 **order-notes 與 order-procurement
兩支測試同時轉紅** = 抽取沒有弱化 A9a-1 的既有保證。
