## A–G 各一句結論

- A：絕對「零 writer」不成立，owner 可直寫；repo 靜態搜尋未見既有 RPC、動態 SQL或 trigger cascade 參照新表，但正式庫 catalog 與 `session_replication_role` SET 權限未確認，普通 service_role 目前只有 SELECT。
- B：tracking_number 的任意非空修改是 Q2=A 明文選擇，但 hct_* 可回 draft、清證據、填空白 request id，確實能做出違反「外部軌跡」語意的資料。
- C：現行 NKU 下沒有看到 stale-pass；B 不是等 A 後讀新列，就是先鎖讓 A 排後，逾時是 55P03、真正成環才是 40P01，但本批沒有兩 session 實證。
- D：正常 DML 加 append-only 下找不到最終非草稿零品項逃逸；例外是 S1b 建 trigger 前的既有違規列，以及具權限者停用 trigger／replica mode 的旁路。
- E：多數整支守門消融會紅，但上表至少 14 類承重分支或契約漂移仍會綠，且多個成功格根本未觸發 deferred X1。
- F：三個檔尾的實際物件清單未漏 X1，索引隨表走也正確；但規格函式數寫錯、前置閘未 pin 精確世界、S1b 未驗 cut-point 既有列。
- G：註解超出實作的核心有「零 writer／空表即自證」、「hct_* 均有恆時守門接住」、「約束集合雙向」、「P1/P1b 已被 regex 證明」及數個 harness「成功即落庫／commit 流程」宣稱。
