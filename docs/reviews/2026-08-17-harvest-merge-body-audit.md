# 2026-08-17 收割 merge body 自查 —— 12 批逐批核「寫的顆數 vs 實際顆數」

> **誰做的**:I 窗(收割窗)自查,不是別人指出的。
> **為什麼要做**:收割紀錄是下一個人數「這一輪收了什麼」的唯一依據,
> 而 merge subject 是最常被複製走的那一行。

## 量法(可重跑,逐批跑)

```
p1=$(git rev-parse <merge>^1)      # 併之前的 dev
p2=$(git rev-parse <merge>^2)      # 被併進來那支的 tip
git rev-list --count $p1..$p2      # ← 這一批【實際】併進來幾顆
```

🔴 **不要用 `git show --stat` 數檔案數,也不要相信 subject。**
第二父系那條路徑才是「這一批帶進來什麼」。

## 結果:12 批,11 批相符,**1 批不符**

```
ef549cc1  實際=1    subject 寫「收割 customers 3 顆（含 WAF 方案）+ products 1 顆」
```

**事實**:
- `ef549cc1` **只併了 `products` 的 `4c288b1a`(1 顆)**
- `customers` 那 3 顆是**另一顆 `5ac0c0e0`** 併的(`40716ee5` / `87e8d61a` / `a925f044`)

**成因**:我把兩批的說明寫成同一個訊息檔,
第一個 merge 用 `-m` 給了一句短 subject、第二個 merge 用 `-F` 吃了那個**含兩批**的檔
⇒ **合併後的敘述掛在只做了一半事情的那一顆上。**

📎 **與 C 窗同日自陳那條同族:訊息的落筆時間與它描述的動作錯開。**
它那次是 body 寫在 `git add` 之前;我這次是 **body 寫給兩個動作、只掛在其中一個上**。

## 處置

**不改寫歷史** —— 那兩顆已在 dev 上,而**內容本身沒錯,錯的是掛的位置**。
⚠️ **對讀者的實際影響(不淡化)**:照 subject 數收割批次的人**會把 `customers` 那 3 顆算兩次**。

## 給下一任收割窗的一條

**一個 merge 訊息只描述一個 merge。**
兩批要連著收就分兩個訊息檔,不要為了省事寫成一份 ——
**省下的是打字,付出的是「紀錄與事實脫鉤」,而那是收割窗唯一的產品。**

## 命中二:`5ac0c0e0` 的 body 是【空的】

```
git log -1 --format=%B 5ac0c0e0  ⇒ 只有一行 subject，零 body
```

🔴 **這條比命中一嚴重,而理由是:「零 body」不會被任何檢查抓到** ——
它不是錯字面,是**缺席**。而**缺席讀起來像「那批沒什麼好說的」**。
📎 交件宣告會消失、merge body 進 git 歷史 ⇒ **轉述錯是永久的,而【沒轉述】也是永久的。**

### 補記:那一批(`customers` 3 顆,`40716ee5` / `87e8d61a` / `a925f044`)該被記下的三件

1. **WAF 方案(`docs/security/2026-08-17-vercel-waf-setup-plan-hobby.md`)是【主視窗審核批准後才放行落檔】的**
   —— E 窗先前**刻意 held、不 commit**,等批准才進。**那不是流程延誤,是刻意的。**
2. **該批純 `.md` ⇒ 三綠沒跑**,E 窗已自行標明(**不寫成綠**);它自核的量法是
   `git show --name-only --format= <c> | sed 's/.*\.//' | sort -u` ⇒ 只有 `md`。
3. **E 窗這輪四次改 tip**(`93e06336` → `6f3835d5` → `87e8d61a` → `40716ee5`),
   **每一次都主動補交件宣告、不等收割窗來對** ——
   📎 那正是「**宣告的效期只到你下一次 commit**」(C 窗同日抽出)的正面實踐。

🔴 **本批的完整交件宣告在信箱,而信箱會消失 ⇒ 這裡是它唯一的永久副本。**

## 命中三(同日稍後自查再撈到):「每併一支跑一次四綠」不是全稱真

我在 `STATUS.md` 116/117 與多封回報裡寫過「**每併一支跑一次四綠**」。
**逐批查時間戳之後,那句對 12 批而言【不成立】**:

```
量法：git log --oneline 43abb127..HEAD --merges --format='%h %cI %s'
24701059  14:07:04   ┐ 相隔 33 秒
92b3c929  14:07:37   ┘ ⇒ 連著併，之後才跑一次四綠
5ac0c0e0  14:37:09   ┐ 相隔 1 秒
ef549cc1  14:37:10   ┘ ⇒ 同上
```

⇒ **那兩對之中【先併的那一支】,沒有屬於它自己的那一次四綠。**
⚠️ **實際風險不高**(後一次四綠涵蓋了兩批的合併結果),
**而那不是重點** —— 重點是**我寫下的句子比我做的事強**,
且**它與命中一、命中二同源:為了「兩批連著收、省一次」**。

---

## 給下一任收割窗的兩條(第一條原本就在,第二條是命中三加的)

1. **一個 merge 訊息只描述一個 merge。**
2. **一支 merge 配一次四綠。** 連著收兩批就跑兩次 ——
   **「反正後面那次會涵蓋」是對的,而它讓你寫不出「每併一支跑一次」這句話。**

🔴 **兩條的共同形狀:省下的是打字與一次 60 秒的測試,付出的是【紀錄與事實脫鉤】** ——
**而收割窗不產出 code,它產出的就是紀錄。紀錄脫鉤 = 它今天沒有產品。**
