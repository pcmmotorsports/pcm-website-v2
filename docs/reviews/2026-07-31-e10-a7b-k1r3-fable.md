## Findings

- **[must-fix] [plan:116,327,332,114,404]** — E6(`failed→queued`)**靜態不可能**:truth table 規定 `queued` 的 `failed_reason`=N、`refund_call_attempted_at`=N,但 E6「不得改其他欄」、E5「attempted_at 保留不得清」、§5.2-4 不可變 ⇒ CHECK 必拒。任何輸入:第一次失敗落 `failed` 後永遠回不了 `queued` ⇒ 該退的錢卡死、`retry_count` 永達不到 6、永不進 dead、R15 永不告警。修法:E6 明列清空 `failed_reason`(與 attempted_at 語意一併重定,見下條)。
- **[must-fix] [plan:109,114,404,180]** — D2 不可變性與重試迴圈**互斥**:真打過 TapPay 且收到**明確失敗**後 attempted_at 已非 NULL 不可清,而 E1 要求 `refund_call_attempted_at IS NULL` ⇒ 即使 E6 修好,第二次嘗試仍永遠非法。明確失敗 = 結果已知、重打安全,合約卻把它與「不確定」同罪。修法:E5(明確失敗)准清 attempted_at,或 E1 改成允許非 NULL 但上次結果為明確失敗。
- **[must-fix] [plan:112,330,331]** — **E3b 與 truth table 自相矛盾**(題目提示屬實):`reconciling` 列規定 `tappay_refund_id`=R,走 E3b 的列從未成功過、無此值 ⇒ E3b 靜態必拒 ⇒ 「打了沒寫回」的列 E3 也拒(attempted_at 非 NULL)⇒ **永久卡在 processing、lease 過期無人能領、無告警**。連鎖:`completed` 列的 R 與 §5.6(b) 等值對 E3b 出身的 job 同樣不成立。修法:reconciling/completed 的 `tappay_refund_id` 改 −(或條件式),等值檢查改 NULL-aware。
- **[must-fix] [plan:180,110,102,536]** — worker 被要求「獨立交易戳 `refund_call_attempted_at` 並 COMMIT」,但 **E1-E13 沒有任何 edge 允許這個 UPDATE**(E2 要求仍 NULL;「表外組合一律拒絕」)⇒ E4 前置永遠湊不齊、正向 A(§7.4-23)走不通、負測 §7.4-14 的 fixture **無法經合法 edge 構造**。修法:新增明列 edge(processing→processing、僅 attempted_at NULL→now()、lease 不變)。
