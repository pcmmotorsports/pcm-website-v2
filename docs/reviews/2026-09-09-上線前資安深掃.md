## 1. 攻擊面偵察 —— **小得出乎意料,那是好消息**

```
顧客站(apps/storefront)公開 route handler  ⇒ 11 支
  auth/line/callback · auth/line/start
  catalog/facet-counts · search
  checkout/tappay-notify/[secret]          ← 金流回呼
  cron/anomaly-alert · cron/capture-recheck · cron/email-sweep
  cron/order-ineligible-gate · cron/settle-sweep
  orders/[orderId]/payment-status          ← 唯一一支吐訂單資料的
後台(apps/admin)route handler             ⇒ 3 支
  session/renew · sso/callback · sso/start
⚪ 兩個 app 都沒有 middleware.ts
```
📌 **11 + 3 = 14 個入口**。對一個電商來說**非常小** —— 大部分讀取走 server component 直讀,不開 API。
⇒ ✅ **那本身就是一個正面項**:沒有開出來的端點,就沒有被打的端點。

## 2. ✅ 金流回呼(`checkout/tappay-notify/[secret]`)—— 守得好

**攻擊劇本**:偽造一發 TapPay 通知,讓系統以為某張單付款成功。
**實測**:
```
:56  import { timingSafeEqual, createHash } from 'node:crypto';
:75  等長 constant-time 比對;長度不等先回 false
:152 if (!safeEqual(secret, expected)) { … }        ← 比對不過就擋
:8   body:size cap(413、不解析)→ hash-before-parse(raw sha256、不存原文 = PII 零落地)
:187 本機 active attempt 存在性閘(DB-only reader)—— 沒有對應的付款嘗試就不往下走
```
✅ **三道**:constant-time secret 比對 · body size cap + 先 hash 後 parse · **本機必須有對應的 active attempt**。
⇒ 📌 **第三道是關鍵** —— 即使 secret 洩漏,攻擊者也**不能憑空造一筆付款**,他得先讓系統有一筆進行中的嘗試。

### 🟡 一格 hardening note(**不是** HIGH/CRITICAL)
**secret 在 URL path 裡**(`[secret]`)而不是 header ⇒ **URL 會進 log**(Vercel access log / CDN / referrer)。
🛑 **而這不是缺陷是設計限制** —— TapPay webhook 設定端多半只給得了一個 URL。而 constant-time 比對用對了。
⇒ ✅ **處置:記下來,不建議改。** 依 skill §6:縱深防禦缺口 = hardening note,不是 HIGH。
⚠️ **我沒查的**:那個 secret 有沒有出現在任何 log 檔或錯誤訊息裡。**未量。**

## 3. ✅ 訂單 IDOR(`orders/[orderId]/payment-status`)—— 守得好,**雙軸**

**攻擊劇本**:登入後把 URL 的 orderId 換成別人的,看得到別人的訂單狀態。
**實測**(逐字):
```
:8-9  雙軸 —— ① RLS orders_select_own(auth.uid()=customer_user_id、DB 層)
             ② 應用層縱深 .eq('customer_user_id', userId)
:10   getUser() 向 auth server 驗 JWT(不信任 client 送欄);throw/無 → 401
:76-78  .select('payment_status').eq('id', orderId).eq('customer_user_id', userId)
:97-98  orderId 須為 UUID 形狀,否則 400(不查 DB、不洩)
```
✅ **而回應面也收乾淨了**:`:13` 逐字「**經銷價零洩漏**:select **只取 `payment_status` 單欄**;回應**只含 `{ status: 'paid'|'pending' }`**(零金額/零 PII)」。
⇒ 📌 **偽造他人 orderId 只會拿到 404** —— 而 404 與「單不存在」**同形**,所以連「這張單存不存在」都問不出來。
⇒ ✅ **這是本次看到最乾淨的一支 route。**

## 4. ✅ 🔴 經銷價洩漏(PCM 最高風險攻擊類)—— **四道獨立防線,全守住**

**攻擊劇本**:一般會員(或訪客)看到經銷價 —— 那是商業機密,而 CLAUDE.md 逐字「**經銷價絕不到一般會員瀏覽器**」。

### 我一開始撈到兩個紅旗,而追下去全部是誤報
`grep` 到兩個 **client component** 提到 `dealer`:`components/ProductInfo.tsx` · `components/ProductPage.tsx`。
⇒ 🛑 **而那不是 import 經銷價模組,是收 props 裡的 `dealerPrice`** ⇒ **判準因此落在「server 端有沒有填那個欄位」,不在 client 這一側。**

### 四道防線,逐道實測
```
① tier 是 server 重查的,不信 client
   products/page.tsx:342  const catalogTierStrict = await resolveAuthenticatedTierStrict();
   lib/tier.ts:111-112     .from('customers').select('tier')     ← getUser() 驗過之後才查

② URL 的 ?tier= override 在 production 【硬擋】
   lib/tier.ts:138 逐字「production 硬擋、與 flag 無關」
   lib/tier.ts:174 逐字「NODE_ENV=production 時 override 恆失效,與 PCM_DEV_TIER_OVERRIDE 是否設【無關】」
   lib/tier.ts:181 process.env.PCM_DEV_TIER_OVERRIDE === '1' &&  ← 雙條件

③ 非 store ⇒ props 裡根本沒有那個欄位(不是給 0,是不存在)
   products/page.tsx:458-471
     const dealerPrices = usedKeywordSearch && catalogTier === 'store'
       ? await fetchEffectivePrices({...})
       : new Map<string, number>();            ← 非 store ⇒ 空 Map
     const pricedProducts = dealerPrices.size === 0
       ? products                               ← 空 Map ⇒ 原樣,不加 dealerPrice
       : products.map(...)

④ 首頁那條路根本不收 tier
   app/page.tsx:109-111 逐字「featured(釘 general):不再收 tier —— public view 的
     store/premiumStore 價是 dummy 0…tier 仍寫進 data-tier 供 dev DOM inspector debug」
   ⇒ 首頁的 tier 只進一個 HTML 屬性,不進價格
```
⇒ ✅ **四道各自獨立** —— 任一道失效,其餘三道還在。
⇒ 📌 **而 `products/page.tsx:404` 的註解顯示他們知道這個風險**:逐字「它就會把經銷價快取給一般會員 —— **驗收有一格在釘「general tier 的 props 裡沒有 `dealerPrice`」**」。

### 🛑 而我證不到什麼
- **我沒有真的打一發請求看回應 JSON** —— 那是對正式站的主動探測,禁。⇒ 上面全部是**讀碼**。
- **`fetchEffectivePrices` 內部**我沒讀 —— 它拿到 `tier: 'store'` 之後怎麼查、會不會回超出射程的東西,**未驗**。
- **RSC payload** 我沒有實際檢查 —— 「props 裡沒有那個欄位」是從 `pricedProducts` 的建構推的。
- `resolveTierFromRequest`(讀 URL 那支)**首頁在用**(`page.tsx:104`)⇒ 我驗到它 production 硬擋,**而沒有驗「硬擋」那段碼本身有沒有被繞過的寫法**。
