## 2. ✅ 金流回呼(`checkout/tappay-notify/[secret]`)—— 守得好

**攻擊劇本**:偽造一發 TapPay 通知,讓系統以為某張單付款成功。
**實測**:
```
:56  import { timingSafeEqual, createHash } from 'node:crypto';
:75  等長 constant-time 比對;長度不等先回 false
:152 if (!safeEqual(secret, expected)) { … }        ← 比對不過就擋
:8   body:size cap(413、不解析)→ hash-before-parse(raw sha256、不存原文 = PII 零落地)
:187 本機 active attempt 存在性閘(DB-only reader)—— 沒有對應的付款嘗試就不往下走
```
✅ **三道**:constant-time secret 比對 · body size cap + 先 hash 後 parse · **本機必須有對應的 active attempt**。
⇒ 📌 **第三道是關鍵** —— 即使 secret 洩漏,攻擊者也**不能憑空造一筆付款**,他得先讓系統有一筆進行中的嘗試。

### 🟡 一格 hardening note(**不是** HIGH/CRITICAL)
**secret 在 URL path 裡**(`[secret]`)而不是 header ⇒ **URL 會進 log**(Vercel access log / CDN / referrer)。
🛑 **而這不是缺陷是設計限制** —— TapPay webhook 設定端多半只給得了一個 URL。而 constant-time 比對用對了。
⇒ ✅ **處置:記下來,不建議改。** 依 skill §6:縱深防禦缺口 = hardening note,不是 HIGH。
⚠️ **我沒查的**:那個 secret 有沒有出現在任何 log 檔或錯誤訊息裡。**未量。**

## 3. ✅ 訂單 IDOR(`orders/[orderId]/payment-status`)—— 守得好,**雙軸**

**攻擊劇本**:登入後把 URL 的 orderId 換成別人的,看得到別人的訂單狀態。
**實測**(逐字):
```
:8-9  雙軸 —— ① RLS orders_select_own(auth.uid()=customer_user_id、DB 層)
             ② 應用層縱深 .eq('customer_user_id', userId)
:10   getUser() 向 auth server 驗 JWT(不信任 client 送欄);throw/無 → 401
:76-78  .select('payment_status').eq('id', orderId).eq('customer_user_id', userId)
:97-98  orderId 須為 UUID 形狀,否則 400(不查 DB、不洩)
```
✅ **而回應面也收乾淨了**:`:13` 逐字「**經銷價零洩漏**:select **只取 `payment_status` 單欄**;回應**只含 `{ status: 'paid'|'pending' }`**(零金額/零 PII)」。
⇒ 📌 **偽造他人 orderId 只會拿到 404** —— 而 404 與「單不存在」**同形**,所以連「這張單存不存在」都問不出來。
⇒ ✅ **這是本次看到最乾淨的一支 route。**

## 7. ✅ 🔴 後台入口認證 —— **守得比一般好,而好在一個具體的地方**

段一留了一格:「兩個 app 都沒有 `middleware.ts`,那它靠什麼?」
**答案**:`apps/admin/src/proxy.ts`(Next 新式 middleware 的檔名)。
```
:84  matcher: ['/((?!_next/static|_next/image|favicon.ico).*)']
     ⇒ 📌 只排除靜態資源 —— /api/* 也走這個閘
:40  逐字「登入閘:預設擋(未登入導 /start);只有顯式 dev bypass 才放行」
:65  NextResponse.redirect(startUrl, 303)
```

### 🎯 好在哪裡(這一格值得寫出來)
```
:2 逐字「用【正向】dev bypass flag、預設擋:NODE_ENV 漏設/拼錯/staging 時不會靜默略過整個 admin 登入驗證」
:3 逐字「prod(NODE_ENV=production)永遠擋、bypass 無效」
:4 第三個條件「DB 非本機 ⇒ bypass 不生效」
```
⇒ 📌 **常見的災難形狀是負向判斷**(`if (NODE_ENV !== 'production') 放行`)—— **NODE_ENV 漏設就變成全站免登入**。
⇒ ✅ **這裡用的是正向 flag:要顯式設 `ADMIN_DEV_BYPASS=1` 才放行,而 production 再加一道硬擋。** 三個條件要同時成立才 bypass。
🔵 **而它還有一道 commit 閘在守**(`.husky/admin-dev-bypass-gate.sh`)—— 那道閘自己還修過一個洞:shebang 是 `/bin/sh` 時在 dash 上 `read -d` 會 `Illegal option` ⇒ **迴圈跑 0 次 ⇒ rc=0 ⇒ 危險行靜默放行**。
⇒ 🎯 **一道守門自己踩過「靜默放行」,而它把那件事修掉並寫在檔頭。**

🛑 **我沒驗的**:`verifyAdminSession`(`:29` `if (!verified.ok)`)內部怎麼驗 —— 它是不是真的驗簽章而不只看 cookie 存在。**未量。**

## 16. ✅ `verifySessionDetailed` —— **真的驗簽章,而且順序是對的**

§14 第 2 條:「它是不是真的驗簽章,還是只看 cookie 存在」。
**實測**(`apps/admin/src/lib/session/session.ts:697` 起,相對行號):
```
:4   if (!token) return { ok:false, reason:'absent' }
:9-11 沒有 secret ⇒ ok:false,reason 分 'no_secret' / 'no_env'      ← 🎯 fail-closed
:15  token 形狀檢查(dot 位置)⇒ 不對就 absent
:26  valid = await crypto.subtle.verify('HMAC', key, sig, data)     ← 🎯 真的驗 HMAC
:30  if (!valid) return { ok:false, reason:'sig_invalid' }
:33  parsed = JSON.parse(...)                                        ← 🎯 在【驗完簽章之後】
:37  if (!isPayload(parsed)) return { ok:false, reason:'shape' }
:38  if (parsed.exp <= now) return { ok:false, reason:'expired' }
```

### 🎯 兩格值得寫出來
1. **順序**:**先驗簽章、後 `JSON.parse`**。⇒ 📌 **反過來就是經典漏洞** —— 解析一份還沒驗證的資料,等於把攻擊者的輸入餵進 parser。**這裡順序是對的。**
2. **沒有 secret ⇒ `ok:false`**(不是「沒 secret 就跳過驗證」)⇒ 📌 **又是一次 fail-closed** —— 與 §7 那個正向 bypass flag 同一種設計品味。
🔵 而 `:40` 還有一句逐字:「**順序是硬的**:政策放在最後,一張過期的舊票才會被報成 `expired` 而不是 `version_rejected`」⇒ **連錯誤分類的順序都想過。**

🛑 **仍未驗**:`strongSecret()` 的強度判準是什麼 · HMAC 用的是哪一種雜湊 · 有沒有 replay 防護(同一張票能不能重用到過期為止)。

## 20. ✅ `api/sso/start`(40 行)—— 短而且每一行都在防一件事

```
:28  驗 state cookie 相符(login CSRF)→ server-to-server 兌換 → 簽 admin session(新 sid = 旋轉)

:30  🎯 失敗路徑【只清 state cookie、絕不清 session cookie】

:35  失敗:303 到錯誤頁、清 state cookie、no-referrer;不動 session cookie
```

# 段六 —— 把 §26 那一格的可利用性收窄(我自己剛列的缺口)

§26 我寫死「**我沒有證明它不可利用** —— 若有任何 RPC / SECURITY DEFINER 函式會執行 `TRUNCATE`,那條路我沒掃」。**掃了。**

## 29. ✅ 全庫會執行 `TRUNCATE` 的函式 —— **anon 一支都到不了**
```
nspname   proname                                secdef  anon_exec  auth_exec  anon_schema
pcm_cron  expire_unpaid_orders                     t        f          f          f
public    pcm_acl_digest                           t        f          f          t
public    pcm_cancellation_ledger_block_truncate   f        f          f          t

🔴 【兩道閘都通】(anon 有 EXECUTE 且有 schema USAGE)的 ⇒ 0
🟢 正對照:public 底下 prosrc 含 SELECT 的函式 ⇒ 162 支(尺撈得到函式本體)
⚪ 負對照:現造字 ⇒ 0
```
⇒ ✅ **六支全部 `anon_exec = f`** ⇒ **anon 沒有任何一條「叫一支函式讓它替我 TRUNCATE」的路。**

## 30. ✅ 而**沒有任意 SQL 執行面**
```
掃 proname ~* '(exec|eval|run_?sql|raw_?query|admin_?sql)'
  排除 pg_catalog / information_schema / extensions
⇒ 0 筆
```
⇒ 📌 **庫裡沒有那種「餵我一段 SQL 我幫你跑」的 RPC** —— 那是很多專案會不小心留下的後門,**這裡沒有。**

## 31. 🎯 而那三支函式的名字本身就是一個正面項
```
pcm_cancellation_ledger_block_truncate
pcm_refund_ledger_block_truncate
pcm_d3d_manual_refund_no_truncate
```
⇒ 📌 **它們是【擋 TRUNCATE 的 trigger 函式】** —— 存在的理由是**防止帳本被 TRUNCATE 掉**。
⇒ ✅ **所以「`TRUNCATE` 是 RLS 管不到的那一個」這件事,他們在【我們自己的帳本表上】已經主動防了** —— 而 `storage` 那三張是平台的表,我們碰不到。
🎯 **那讓 §26 的判定更精確**:
> **不是「他們沒想到 TRUNCATE」,是「他們想到了、在自己管得到的表上防了,而平台那三張表管不到」。**

## 32. ⇒ §26 的可利用性,現在收窄到這樣
```
① Data API 沒有曝露 storage(Sean 截圖:Exposed schemas 只有 graphql_public / public)
② PostgREST 沒有 TRUNCATE 端點(它給 GET/POST/PATCH/DELETE,而 DELETE 被零 policy 擋)

```
⇒ ✅ **四道都指向同一個方向。**
🛑 **而仍然剩一條我沒查**:**Supabase Storage 自己的 API**(`/storage/v1/...`)—— 它不走 PostgREST、不走 RPC,是另一個服務。**那條路我完全沒查**,而「它理論上不提供 TRUNCATE」**是我的推論不是量到的**。
⇒ 📌 **所以正確的講法是**:**四條路我查過都不通,而第五條(Storage API)我沒查。**
