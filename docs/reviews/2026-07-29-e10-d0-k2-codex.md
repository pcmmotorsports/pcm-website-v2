## 🟡 兩條刻意不在本片處理 —— 交 Sean 判

### (a) 顯式 `BEGIN` / `COMMIT` 與 Supabase CLI ledger 的原子性

codex 主張:CLI v2.98.1 會在 migration statements 之後追加 ledger INSERT;本檔自己 `COMMIT` 後若 ledger 寫入失敗,會出現「schema 已變、`schema_migrations` 未入帳」的裂縫。

**不在 D0 處理的理由**:
- 這是 **repo 全域慣例** —— 現有 migration(如 `20260726120000_m4b_e8a1_staff_table.sql`)全部是顯式 `BEGIN; … COMMIT;`。讓 D0 單獨破例會製造不一致,而且**拿掉 `BEGIN` 會讓 R1 第 1 條要求的 `SET LOCAL lock_timeout` 失去明確的交易邊界**(兩條 findings 互相拉扯)。
- 失敗情境需要「COMMIT 成功但 ledger INSERT 失敗」的窄窗,且 40 餘支既有 migration 從未踩到。

⇒ **這是全 repo 的決定,不是單片的決定。** 決策題 **D0-1**:

```
Q(D0-1):codex 指出我們所有 migration 都自己寫 BEGIN/COMMIT,理論上與 Supabase CLI
記帳的原子性有個窄縫(schema 改了、但記錄沒寫進去)。要怎麼處理?

A. 維持現狀不動(40 多支既有 migration 都這樣寫,從沒出事;風險窄)
B. 只有 D0 改成不自己寫 BEGIN/COMMIT(會與其他 migration 不一致)
C. 開一張 backlog,之後統一評估全 repo 要不要改寫

A: A|B|C
```
推薦 **A 或 C** —— 過夜不動全域慣例。

### (b) 精確定義比對對 PostgreSQL 版本敏感

codex 主張:`pg_get_constraintdef` 是反編譯輸出、不是穩定的原始 SQL;未來 PG 改變括號或 cast 算繪,語意相同的新環境會直接套用失敗。

**判斷:接受為已知取捨、保留檢查。**
- 失敗模式是 **fail-closed**:migration 明確失敗並印出「預期 vs 實際」,一眼可修,**不是資料風險**。
- 拿掉它就退回 R1 第 3/4 條的假綠(codex 自己前一輪要求加的)。
- 預期字串取自 **2026-07-29 production 實查算繪**,已在檔內註明。
- 突變測試已證明它**不是假綠**:把新格式 regex 從 `{6}` 放寬成 `{1,6}`,斷言確實 fire。
