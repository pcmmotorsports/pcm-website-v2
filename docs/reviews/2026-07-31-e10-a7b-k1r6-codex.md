[must-fix] [docs/specs/2026-07-31-e10-a7b-refund-jobs-plan.md:128-143,471-480] F2 — 「其餘欄不得改」沒有可機械產生的精確欄位集合。
失敗情境：一版漏比 `last_refund_call_at`，另一版把自動更新的 `updated_at` 也列為不可變；前者放行竄改、後者讓合法 edge 永遠失敗，未來新增欄更可能預設可寫。
修法：建立全欄位 canonical manifest；每條 edge 寫 allowed-delta 白名單，`status`、`updated_at` 等自動欄位明列，未知新欄預設禁止。

[must-fix] [docs/specs/2026-07-31-e10-a7b-refund-jobs-plan.md:287-339] F3 — `order_refund_jobs` 不是完整 schema：多個欄位缺精確名稱、型別、NULL、DEFAULT 與完整值域。

修法：補逐欄 DDL manifest或完整 `CREATE TABLE`，列出 name/type/null/default/check/comment；§7 同步斷言 `pg_attribute`、`pg_attrdef`。

[must-fix] [docs/specs/2026-07-31-e10-a7b-refund-jobs-plan.md:71-72,446-520,734-736] F4 — A7b-T 宣稱「六支 trigger」，但 rollback 明列 parent 六支加 child 四支，實際是十支。

修法：列十列 trigger manifest：名稱、table、timing、event bitmap、ROW/STATEMENT、deferrability、function、預期 `tgtype`。

[must-fix] [docs/specs/2026-07-31-e10-a7b-refund-jobs-plan.md:299-306,569-570] F5 — rec/bank ID 的「控制碼／前後空白」沒有精確碼位或 CHECK 表達式。
失敗情境：一人用 `btrim`、一人用 locale regex；TAB、DEL、全形空白會在兩版得到不同結果，而各自挑兩個測例仍可全綠。
修法：定死 locale-independent 表達式與逐碼位測試向量，並列出刻意不涵蓋的 Unicode 邊界。

[must-fix] [docs/specs/2026-07-31-e10-a7b-refund-jobs-plan.md:576-580,687-695] F6 — rule 4 無法只從 §3.1＋§4.4 產生可執行 edge fixture。
失敗情境：兩節缺 staff、cancellation、items、ledger、前代世代、時鐘注入，以及不在 truth table 的 baseline/D9/corrected 欄；實作者只能手寫 seed，harness 不再是「產生器」。
修法：每條 edge 提供 machine-readable old row、patch、支援列、時鐘策略、預期 edge ID、完整 post-row；生成器不得從實作反推 oracle。

指定核點無 finding：

- §4.4 每格都只依同一列，可落成單一 `CASE CHECK`；跨表 job↔ledger／item set 已正確分給 trigger。PostgreSQL 不支援 CHECK 查其他表，但這張 truth table 沒有要求它查表。[PostgreSQL 17 CHECK 文件](https://www.postgresql.org/docs/17/ddl-constraints.html)
- §5.6(a) 的 parent `AFTER INSERT` 與 child `AFTER INSERT OR DELETE` 語法成立；constraint trigger 必須明寫 `AFTER ... FOR EACH ROW`，`OR` 多事件合法。跨表查詢應放函式內，不放 `WHEN` 子查詢。[PostgreSQL 17 CREATE TRIGGER](https://www.postgresql.org/docs/17/sql-createtrigger.html)

## Q3 施工順序與回滾

[must-fix] [docs/specs/2026-07-31-e10-a7b-refund-jobs-plan.md:729-740] F9 — §10 只有 timeout，沒有逐物件 lock manifest 與 create_order 併發探針。
失敗情境：dormant CHECK 的 ADD/DROP 只鎖新 job 表，不會直接卡結帳；真正風險是 M 建指向 `order_items` 的 FK，referenced-table lock 與 create_order INSERT 的 `ROW EXCLUSIVE` 衝突，使結帳等待到 M COMMIT。
修法：列出 M/T 每步鎖定表與 lock mode，沿用 A1 barrier lock probe，量測 migration 持鎖期間 create_order INSERT；`lock_timeout` 只保護 migration 等鎖，不保護結帳等待。[ALTER TABLE](https://www.postgresql.org/docs/17/sql-altertable.html)、[鎖衝突表](https://www.postgresql.org/docs/17/explicit-locking.html)

鎖本身的指定答案：`ADD CHECK(false) NOT VALID` 與 `DROP CONSTRAINT` 都取 `ACCESS EXCLUSIVE`；`NOT VALID` 省掉掃描但仍擋新寫入。M 時表尚未可見、T 時仍被 gate 保持空表，所以這兩把鎖本身不碰 create_order。

[must-fix] [docs/specs/2026-07-31-e10-a7b-refund-jobs-plan.md:732-736] F10 — `pg_depend`「前置」檢查被排在 DROP 完成後，且未定義何謂外部依賴。
失敗情境：照六步執行時，到第六步已無物件可保護；若直接以 `pg_depend` 非空判斷，內部 constraint/index/FK 依賴又會讓空表永遠 abort。
修法：移到任何 DROP 之前，提供精確 allowlist/filter與預期 internal dependency 集合；實際 DROP 全用 `RESTRICT`。

[must-fix] [docs/specs/2026-07-31-e10-a7b-refund-jobs-plan.md:730,738-740] F11 — 「ledger/schema/data 三方狀態矩陣」只有名字，沒有格子、查詢與下一步。
失敗情境：M 或 T 的 SQL 已 COMMIT、但 `supabase_migrations.schema_migrations` 未登記時，盲目重跑會撞非冪等 CREATE；T schema 已生效但 ledger 未記時，gate 已移除且 writer 可能開始寫。
修法：分 M/T 列 migration-version presence、物件指紋、dormant gate、兩表 row count、允許重跑/補 ledger/forward repair/立即停機；明確區分 migration ledger 與 `order_refunds` 業務帳本。
