## §2 🔴 順序,以及【為什麼順序不致命】

**建議順序:先 ① 再 ②**(照時間戳,`060000` 在 `070000` 前)。

**而順序【不致命】,理由要寫清楚**:
- ① 的效果是「**從現在開始**,新建的表不再自動給權限」——
  它**只作用於 apply 那一刻【之後】建的東西**,不回頭修既有的。
- ② 那張表**自己帶了收權指令**(`REVOKE ALL … FROM PUBLIC / anon / authenticated`),
  **不論①有沒有先跑,②那張表都是乾淨的。**

⇒ **順序顛倒不會產生不安全的結果。** 照時間戳只是為了讓版本號單調遞增,與過去幾批同紀律。

🔴 **但「順序不致命」不等於「只做一支就好」** —— 見 §3-甲。

>

> 而 ::regclass 硬轉一個不存在的表【會拋錯】，不是回 0
> 世界 A（表不存在）⇒ ERROR: relation "public.sweeper_heartbeat" does not exist / rc=3 / 一列都不回
> 世界 B（表存在）  ⇒ rc=0 / 一列：0 | 表在 | 0
> ```
> ⇒ 🔴 **舊版寫的「apply 前 ⇒ 殘留=16 | 沒有這張表 | 訪客權限=0」這一行,
> 【不可能是這段查詢印出來的】** —— 那一整段 SQL 在那個世界根本沒有回任何一列。
> **那是我轉錄自別處或別版查詢的數字,而我把它寫成了「我兩個世界各跑一次」的量測結果。**
> ⚠️ 留痕的理由:錯的不只是查詢(可以改),**錯的是我對「我量過」這件事的宣稱** ——
> 而它讀起來比一個沒有量測的版本**更可信**。
> ⇒ 也因此,舊版整段「兩個世界都是 0 所以第③格沒有判別力」的分析**方向是對的、事實是錯的**:
> 真相更硬 —— **apply 前那一格不是「0」,是【整段查詢死掉】,而 Sean 會看到一片紅 ERROR 而 runbook 沒預告。**
>
> 📎 **下面是改好的版本,而它的每一格都在三個世界表演過**(見本節末的實測輸出)。

**在 Supabase 的 SQL editor 貼下面這一段,按執行。**
它會回**一列三格**,而**三格都必須是你期望的那個字**。
🔴 **不論 apply 前還是 apply 後,它都應該【回得來一列】** —— 看到 ERROR 就是這段查詢本身有問題,回報。

```sql
SELECT
  -- ① 以後新建的表還會不會自動給訪客權限？
  --    🔴 【不過濾建表角色】：舊版只看 defaclrole='postgres'，而 supabase_admin 建的表
  --       走的是它自己那份預設授權 ⇒ 舊版在那個世界會印 0 而洞是開的（2026-08-18 實測構造過）。
  coalesce(
    (SELECT string_agg(x, ' | ' ORDER BY x) FROM (
       SELECT DISTINCT d.defaclrole::regrole::text || ' 建的新表 → ' || a.grantee::regrole::text AS x
         FROM pg_default_acl d
         JOIN pg_namespace n ON n.oid = d.defaclnamespace,
              LATERAL aclexplode(d.defaclacl) a
        WHERE n.nspname = 'public' AND d.defaclobjtype = 'r'
          AND a.grantee <> 0
          AND a.grantee::regrole::text NOT IN ('postgres', 'service_role')
     ) s),
    '乾淨')
    AS "①殘留_應為乾淨",

  -- ② 心跳表建起來了嗎？
  (SELECT CASE WHEN to_regclass('public.sweeper_heartbeat') IS NULL
               THEN '沒有這張表' ELSE '表在' END)
    AS "②表_應為表在",

  -- ③ 心跳表上，訪客還有沒有權限？
  --    🔴 三向輸出：表不存在時要說「量不到」，不可以印 0（0 會被讀成「乾淨」）。
  --    🔴 用 to_regclass 不用 ::regclass —— 後者對不存在的表【拋錯】，整段查詢會死。
  (SELECT CASE
     WHEN to_regclass('public.sweeper_heartbeat') IS NULL
       THEN '量不到(表不存在)'
     WHEN (SELECT relacl FROM pg_class
            WHERE oid = to_regclass('public.sweeper_heartbeat')) IS NULL
       THEN '0(ACL 為 NULL = 零顯式授權)'
     ELSE (SELECT count(*)::text
             FROM pg_class c, LATERAL aclexplode(c.relacl) a
            WHERE c.oid = to_regclass('public.sweeper_heartbeat')
              AND a.grantee IN ('anon'::regrole, 'authenticated'::regrole))
   END)
    AS "③訪客權限_應為0";
```

**期望(apply 後)**:`①=乾淨` / `②=表在` / `③=0(…)`。

### 🔴 這段查詢的判別力 —— 三個世界各跑一次的**實際輸出**(2026-08-18,拋棄式 PG 17.10)

```
世界 A  表不存在                ⇒ 乾淨 | 沒有這張表 | 量不到(表不存在)      rc=0
世界 B  表存在、無 anon 授權     ⇒ 乾淨 | 表在       | 0(ACL 為 NULL…)      rc=0
世界 C  表存在、【有】anon 授權  ⇒ 乾淨 | 表在       | 2                     rc=0
```
🔴 **世界 C 是正向對照,它存在的理由是:一個「永遠印 0」的查詢在 A 和 B 都會過關。**
有了 C,我們知道這一格**真的抓得到授權**,不是恆綠。
🔴 **而三個世界印出【三個不同的字】** —— 這正是舊版做不到的事(舊版 A 直接死掉)。

### 🔴🔴 ① 那格**仍然只答得出元資料,答不出行為** —— 要真答,加跑這一段

V 窗 MF-2:`①=乾淨` 的意思是「**預設授權表上沒有殘留**」,
**不等於**「新建的表出生時真的乾淨」。要問後者,就真的去建一張表看它拿到什麼:

```sql
BEGIN;
CREATE TABLE public.pcm_acl_probe_tmp(x int);
SELECT CASE
  WHEN (SELECT relacl FROM pg_class
         WHERE oid = 'public.pcm_acl_probe_tmp'::regclass) IS NULL
    THEN '乾淨(新表零顯式授權)'
  ELSE coalesce((SELECT string_agg(DISTINCT a.grantee::regrole::text, ', ')
                   FROM pg_class c, LATERAL aclexplode(c.relacl) a
                  WHERE c.oid = 'public.pcm_acl_probe_tmp'::regclass
                    AND a.grantee <> 0
                    AND a.grantee::regrole::text NOT IN ('postgres','service_role')),
                '乾淨(只有 owner / service_role)')
END AS "新表出生時被誰拿到權限_應為乾淨";
ROLLBACK;
```
🔴 **整段包在 `BEGIN … ROLLBACK` 裡 ⇒ 那張 probe 表不會留下來。** 貼完整段,不要只貼中間。

**實測(2026-08-18,同一台拋棄式 PG,雙向都表演過)**:
```
種一條 anon 預設授權 ⇒ probe 印「anon」      ← 抓得到
撤掉那條           ⇒ probe 印「乾淨(新表零顯式授權)」
```

⚠️ **而 probe 自己也有射程,不要讀成「全部都驗了」**:
**它量的是【你現在這個連線的角色】建表時會發生什麼。** Supabase SQL editor 一般是 `postgres`;
若某條路徑是 `supabase_admin` 在建表,這段 probe **量不到那一條**
(§6-6 已記:`supabase_admin` 那份預設授權我們動不了)。
⇒ 那一條靠改好的 ① 看(它**不過濾建表角色**,會把 `supabase_admin 建的新表 → anon` 逐條印出來)。
⇒ **兩段一起跑才有意義:① 看得廣(所有角色、但只看元資料)、probe 看得真(行為、但只看你這個角色)。**

📎 教訓母題:**元資料說得出「保護在」,說不出「保護還在」**(memory
`feedback_trigger-metadata-survives-a-gutted-function` 同族)。

⚠️ **而 E 窗的限定要跟著這段走,一個字不能拿掉**:
> **「訪客權限 0」不得外推成「完整不可達」。**
> 四種情況本輪**沒有**驗過:`PUBLIC` 專屬授權 / 只給 `MAINTAIN` 這一種權限 / 透過切換角色繞路 / 第三個陌生角色。
