## §1 兩支是什麼、為什麼要兩支

| 支 | 檔 | 它做什麼(白話) |
|---|---|---|
| **①** | `supabase/migrations/20260817060000_e683_1_public_default_privileges_revoke.sql` | **把「以後新建的表自動給訪客權限」這件事關掉。** 現在每張新表一出生,匿名訪客就自動拿到一整套權限,**包含把整張表清空的權限**(而那個權限**不受一般的資料列保護管**) |
| **②** | `supabase/migrations/20260817070000_m4b_231_3_sweeper_heartbeat.sql` | **新增一張「心跳表」** —— 讓巡邏程式看得出「自動對帳程式是不是死了」。現在如果它死掉,**沒有任何東西會叫**(死掉的程式,在正好用來報告它的那個計數器上產生沉默) |

**兩支互相咬**:②新建的那張表,**正好就是①在講的那種受害者**。
⇒ 所以②**自己也帶了一份收權指令**,不靠①。

## §2 🔴 順序,以及【為什麼順序不致命】

**建議順序:先 ① 再 ②**(照時間戳,`060000` 在 `070000` 前)。

**而順序【不致命】,理由要寫清楚**:
- ① 的效果是「**從現在開始**,新建的表不再自動給權限」——
  它**只作用於 apply 那一刻【之後】建的東西**,不回頭修既有的。
- ② 那張表**自己帶了收權指令**(`REVOKE ALL … FROM PUBLIC / anon / authenticated`),
  **不論①有沒有先跑,②那張表都是乾淨的。**

⇒ **順序顛倒不會產生不安全的結果。** 照時間戳只是為了讓版本號單調遞增,與過去幾批同紀律。

🔴 **但「順序不致命」不等於「只做一支就好」** —— 見 §3-甲。

## §3 🔴 中間失敗的三種世界:你看到什麼、下一步做什麼

### 甲 · ① 成功、② 失敗

**你會看到**:第一支跑完沒有紅字;第二支跑出一行紅色 `ERROR:` 開頭的訊息。

**這個世界的實際狀態**:
- ✅ **以後新建的表不再自動給訪客權限**(①生效了)
- ❌ **心跳表沒有建起來** ⇒ 對帳程式死掉仍然沒人會叫(**維持現狀,沒有變糟**)

**下一步**:把那行 `ERROR:` **原字**貼給施工窗。**不要重跑第二支**,先看錯誤是什麼。
⇒ **這個世界可以停在這裡過夜,不急。**

---

### 乙 · ① 就失敗

**你會看到**:第一支就跑出紅色 `ERROR:`。

**這個世界的實際狀態**:**什麼都沒變。** 兩支都是單一交易(檔內 `BEGIN;` … `COMMIT;`),
任一條斷言不符 ⇒ **整支自動回滾,不會留下半套狀態**。
⇒ **你不需要手動下任何「復原」指令。**

**下一步**:把 `ERROR:` 原字貼給施工窗。

---

### 丙 · 兩支都跑完,而你不確定斷言有沒有真的通過

🔴 **這是最容易被誤讀的一個** ——
**這兩支的斷言【成功時不會印任何東西】,只有失敗時才印紅字。**
⇒ **「跑完了、沒看到紅的」= 通過。**
⚠️ **但②會印一行綠色的 `NOTICE`**,那行是**它自己在報告它檢查了幾個東西**:
```
NOTICE:  ✅ 新物件收權斷言通過:檢查 1 個物件，anon/authenticated 權限 0 項。
```
**看到這行 = ②的收權斷言真的跑過了、而且分母不是 0。**
🔴 **沒看到這行 ⇒ 回報施工窗**(那代表斷言可能被跳過,而「跳過」與「通過」在畫面上長得一樣)。

## §4 🔴 apply 完怎麼確認【真的生效】

**在 Supabase 的 SQL editor 貼下面這一段,按執行。**
它會回**一列三格**,而**三格都必須是你期望的那個字**:

```sql
SELECT
  -- ① 以後新建的表還會不會自動給訪客權限？
  (SELECT count(*) FROM pg_default_acl d
     LEFT JOIN pg_namespace n ON n.oid = d.defaclnamespace,
     LATERAL aclexplode(d.defaclacl) a
    WHERE n.nspname = 'public' AND d.defaclobjtype = 'r'
      AND d.defaclrole = 'postgres'::regrole
      AND coalesce(a.grantee, 0)
          NOT IN ('postgres'::regrole::oid, 'service_role'::regrole::oid))
    AS "①殘留筆數_應為0",

  -- ② 心跳表建起來了嗎？
  (SELECT CASE WHEN to_regclass('public.sweeper_heartbeat') IS NULL
               THEN '沒有這張表' ELSE '表在' END)
    AS "②表_應為表在",

  -- ③ 心跳表上，訪客還有沒有權限？
  (SELECT count(*) FROM pg_class c, LATERAL aclexplode(c.relacl) a
    WHERE c.oid = 'public.sweeper_heartbeat'::regclass
      AND a.grantee IN ('anon'::regrole, 'authenticated'::regrole))
    AS "③訪客權限數_應為0";
```

**期望**:`①殘留筆數_應為0 = 0` / `②表_應為表在 = 表在` / `③訪客權限數_應為0 = 0`。

🔴 **這一段【分得出兩個世界】** —— 我在本機同款狀態下**兩個世界各跑一次**,實際輸出:
```
apply 前 ⇒  殘留=16 | 表=沒有這張表 | 訪客權限=0
apply 後 ⇒  殘留=0  | 表=表在       | 訪客權限=0
```
⇒ **如果你 apply 前後看到的是同一組數字,那不是「通過」,是「這段查詢沒在量你以為的東西」** ⇒ 回報。

🔴🔴 **而第③格【單獨看沒有判別力】,這點我要講白**:
你會發現**兩個世界的第③格都是 `0`** —— 因為 **apply 前那張表根本不存在,數出來當然是 0。**
⇒ **第③格只有在第②格顯示「表在」之後才有意義。**
⇒ **不要把「③是 0」單獨當成好消息** —— 「表不存在」與「表存在且乾淨」在那一格上長得一模一樣。
📎 這正是本專案一直在抓的那個形狀:**一個 0,兩個世界。看的時候要問「這個 0 是哪一種」。**

⚠️ **而 E 窗的限定要跟著這段走,一個字不能拿掉**:
> **「訪客權限 0」不得外推成「完整不可達」。**
> 四種情況本輪**沒有**驗過:`PUBLIC` 專屬授權 / 只給 `MAINTAIN` 這一種權限 / 透過切換角色繞路 / 第三個陌生角色。

## §5 🔴 Rollback:一支退得掉、一支【建議不要退】

| 支 | 退得掉嗎 | 說明 |
|---|---|---|
| **②心跳表** | ✅ **退得掉** | `DROP TABLE IF EXISTS public.sweeper_heartbeat;`。這張表**零業務資料**(只有工作名稱與時間),drop 不會失去任何客戶或金額資料。⚠️ **但退了之後,「對帳程式死掉沒人知道」那個缺口就回來了,而它的症狀是「什麼都沒發生」。** |
| **①預設授權** | ⚠️ **技術上退得掉,但【本檔刻意不提供那行指令】** | 退回去 = **把「新表自動給訪客權限(含清空整張表)」重新打開**。那不是「退回安全」,是**退回一個已知的洞**。🔴 **真的要退 ⇒ 當場找施工窗現寫,不要照著文件貼。** 理由:放在文件裡就會有人在半夜照著貼。 |

🔴 **這一格會影響你要不要現在 apply,所以講白**:
**②可以放心試** —— 出事就 drop,零資料損失。
**①的方向是「把一個洞關起來」** —— 它的風險不是「退不掉」,是**萬一有東西正依賴那個洞**。
⚠️ **而我沒有辦法在這裡跟你保證沒有** —— 見 §6 第一條。

## §6 ⚠️ 這份文件**沒有**做到的事(誠實邊界)

1. 🔴 **我沒有查過「正式站上有沒有任何東西正依賴 `anon` 的那組預設權限」。**
   E 窗量過「既有 46 張表的 `anon` 寫權限實測全為 0」——**那是既有的表**,
   **不是「沒有任何程式碼依賴新表出生時的那組權限」。** 這兩件不同。
   **缺的那道檢查 = apply 前在正式站跑一次唯讀 preflight。**
2. **兩支【沒有在任何真實資料庫上跑過】。** 見 §0。
3. **兩支不是同一個交易。** ⇒ 甲那個世界(①成功②失敗)是**真的可能發生**的,
   🔴 **不得把「其中一支成功」寫成整案完成**(E 窗原字)。
4. **正式站的 `service_role` 有沒有 BYPASSRLS,我沒查。**
   ⚠️ 但②那張表**已經不依賴那個答案**(它同時下了明確的權限與規則兩道)。
5. **心跳表建好之後,還沒有任何程式往裡面寫。**
   ⇒ **apply 完那張表會是空的,而空的是對的。** 寫入端與健康檢查端點是**另一片**,還沒做。
   🔴 **所以 apply 完【不要】期待巡邏就會開始報告 sweeper 狀態** —— 那還要一片。
6. **E683-1 動不了 `supabase_admin` 那一份預設授權**(權限不夠,`postgres` 不是超級使用者)。
   ⇒ **由那個身分建立的物件仍會自帶預設授權。本片不宣稱把這條路關死。**
