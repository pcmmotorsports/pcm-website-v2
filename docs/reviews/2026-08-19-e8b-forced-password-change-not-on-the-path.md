# 🔴 「首次登入強制改密碼」**完全不在路徑上** —— 而母 plan 早就指名這一條最容易漏

> 2026-08-19 · W5 · 來源=B2 spec 關卡1 對抗審查(codex `gpt-5.6-sol`)
> **主視窗裁定要它獨立成檔:「它會被 21 這個數字稀釋掉」。**
> 正本 findings(21 條)在 `docs/reviews/2026-08-19-b2-spec-k1-codex-findings.md`;本檔只講這一條。

---

## §1 這條是什麼(codex 逐字,我沒重打)

```
[must-fix] §3.4「不可能繞過」｜既有新式 v1 session 或 legacy cookie 已存在時，使用者不必重新登入
即可直接打 SSO authorize → `must_change_password_at` 完全不在路徑上。
修法：加入既有 session 的失效／版本切換方案，或在可取得身分後於 authorize 再查旗標。
```
同一輪它另外打中同一個地方的第二個角度(亦逐字):
```
[must-fix] §3.4｜session 是 stateless、只認 exp，migration 回填不會撤銷任何既有 session
→ 最長窗口取決於舊 cookie 到期，而不是首次登入流程。
修法：明定 cookie 名稱或版本輪替及切換時間，不能宣稱立即強制。
```

## §2 🔴 為什麼它比另外 20 條重

**母 plan 自己就指名了它** —— `docs/specs/2026-08-16-m4b-e8b-real-auth-line-plan-v4.md` §6 逐字:

> 🔴 **第 9 條是最容易漏的一條**:攔截點必須在**所有入口之前、包含 SSO `authorize`**,
> 否則員工可以跳過改密碼頁直接走 SSO 進 admin,「強制改密碼」形同虛設。

⇒ **那句話寫於 2026-08-16。三天後,一個 fresh-context 的外部審查器獨立撞到同一格。**
⇒ 🔴 **可複用的判別句:一份 plan 寫下「這一條最容易漏」,不會讓它變得比較不容易漏。**
**指名一個風險 ≠ 覆蓋那個風險** —— 而**指名它會讓後來的人以為它被處理了**,
因為讀的人看到那段紅字,會把「作者知道」讀成「作者做了」。

## §3 這條與另一條是【同一條路上的兩個洞】

主視窗 2026-08-19 裁定,把本條與 **payload 加環境標記**(Sean `q3=甲`)併進同一份 plan。理由:

```
洞一(本條)    舊票【還在】⇒ 強制改密碼繞得過
洞二(環境標記) 舊票【跨環境也驗得過】⇒ preview 簽的票對 production 有效
⇒ 兩者的修法是同一個動作:動 payload / 換版本 / 讓既有票失效
⇒ 分兩次做 = 讓所有人被登出【兩次】
```
